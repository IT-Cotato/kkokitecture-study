#### 개략적인 규모 추정(back-of-the-envelope estimation)

: 보편적으로 통용되는 성능 수치상에서 사고 실험을 행하여 추정치를 계산하는 행위

규모 확장성을 표현하는 데에 필요한 기본기: 2의 제곱수, 응답지연(latency)값, 가용성

### 2의 제곱수

데이터 볼륨의 단위를 2의 제곱수로 표현하면? ⇒ 최소 단위는 1바이트 (=8비트)

- ASCII 문자 하나가 차지하는 메모리 크기가 1바이트.


## 모든 프로그래머가 알아야 하는 응답지연 값

> 응답지연(latency) 이란?
> 

어떤 작업 하나를 요청했을 때, 결과가 돌아오기까지 걸리는 시간

> L1 캐시란?
> 

CPU 옆에 붙어있는, 엄청 작고 엄청 빠른 메모리

즉,

- 변수 하나 읽기 → 거의 즉시 (ns)
- 메모리에서 데이터 가져오기 → 조금 느림 (ns~μs)
- 디스크에서 읽기 → 꽤 느림 (ms)
- 인터넷으로 요청 → 매우 느림 (ms~초)

→ 디스크 접근을 줄이는 게 압도적으로 중요하므로 디스크 탐색은 가능한 피해야 하고, 

- 압축하는 시간 < 네트워크 전송 시간

→ 단순한 압축 알고리즘은 빠르며, 적절한 압축은 네트워크 전송 시간을 절약시킨다.

- 데이터 센터는 보통 여러 지역에 분산되어 있고, 센터들 간에 데이터를 주고 받는 데에 시간이 걸린다.

## 가용성에 관계된 수치들

> 고가용성(high availability)이란?
> 

시스템이 오랜 시간 동안 지속적으로 중단 없이 운영될 수 있는 능력을 지칭하는 용어다.

> SLA(Service Level Agreement)란?
> 

서비스 사업자와 고객 사이에 맺어진 합의를 의미하며, 이 합의에는 서비스 사업자(service provider)가 제공하는 서비스의 가용시간(uptime)이 공식적으로 기술되어 있다.

가용시간은 관습적으로 숫자 9를 사용해 표시함. (가용률 99%, 99.9%, 99.999% ...)

<aside>

**💡 QPS란?**

- 초당 들어오는 요청 수. (Queries Per Second)
    - ex. 1초에 API 요청 100개 들어옴: QPS = 100
- 꼭 DB 쿼리만을 의미하는 것은 아니며, API 요청, HTTP 요청, DB 조회, 로그인 요청 등 전부 포함해서 **시스템이 처리해야 하는 요청 수**
- 중요한 이유
    - 서버가 버틸 수 있는지 판단의 기준이 된다.
        - ex) 서버 1대가 1000 QPS 처리 가능하다면, QPS가 7000이라고 할 때 이론상 최소 7대 필요.
    - 병목 찾기
        - 같은 QPS라도 [CPU 작업 많은 서비스] vs [DB 접근 많은 서비스] 다르게 설계 필요.
- 평균 QPS vs 피크 QPS
    - 트래픽은 24시간 균일하지 않고 시간대마다 변동이 크다. 이에 시스템은 Peak 기준으로 설계하는 게 좋다.
</aside>

#### 가정

- 월간 능동 사용자(monthly active user)는 3억(300million) 명이다.
- 50%의 사용자가 트위터를 매일 사용한다.
- 평균적으로 각 사용자는 매일 2건의 트윗을 올린다
- 미디어를 포함하는 트윗은 10% 정도다.
- 데이터는 5년간 보관된다.

#### 추정

QPS(Query Per Second) 추정치

- 일간 능동 사용자(Daily Active User, DAU) = 3억 × 50% = 1.5억(150million)
- QPS = 1.5억 × 2 트윗 / 24시간 / 3600초 = 약 3500
- 최대 QPS(Peek QPS) = 2 × QPS = 약 7000

미디어 저장을 위한 저장소 요구량

- 평균 트윗 크기
    - tweet_id에 64바이트
    - 텍스트에 140바이트
    - 미디어에 1MB
    - 미디어 저장소 요구량: 1.5억 × 2 × 10% × 1 MB = 30TB / 일
    - 5년간 미디어를 보관하기 위한 저장소 요구량: 30TB × 365 × 5 = 약 55PB

**💡 Thinking Point**

→ 정확한 계산 보다는 대략적인 수치로 빠르게 계산하자.

→ 평균보다 피크 기준으로, “최악의 순간에도 버틸 수 있나?”를 고민해보자.

→ 병목은 어디인가?를 생각할 것. 여기선 스토리지. 텍스트보다는 미디어가 시스템을 지배함, 따라서 “CDN”, “S3”, “이미지 압축”, “썸네일 따로 저장”과 같은 시스템 설계를 고려해볼 수 있다.

→ 미디어 포함 비율을 10%로 가정하고 있는데, 실무라면 “미디어가 10%가 아니라 20%라면?”, “영상 포함되면?”과 같은 고려를 할 수 있다. 따라서 가정 하나가 바뀜에 따라 시스템 설계가 완전히 바뀔 수 있다.

→ 단순 계산(QPS=7000이네)으로 끝나는 게 아니라, 7000 QPS면 “서버는 몇 대 필요한가?”, “DB 샤딩 해야 하나?”, “캐싱 어디에 넣지?”와 같이 `숫자 → 설계`로 이어지는 사고 감각이 중요

</aside>

## 팁

개략적인 규모 추정과 관계된 면접에서 가장 중요한 것은 “문제 해결 능력”, 즉 올바른 절차를 밟아 문제를 풀어나가는 역량이다. 

- 근사치를 활용한 계산(rounding and approximation)
    - 면접장에서 99987 / 9.1과 같은 복잡한 계산보다는 100,000 / 10으로 간소화
- 가정(assumption)들은 적어 두자 (나중에 살펴볼 수 있도록)
- 단위(unit)을 붙이는 습관 (KB, MB 헷갈리지 않게)
- QPS, 최대 QPS 저장소 요구량, 캐시 요구량, 서버 수 추정 ⇒ 많이 출제되는 개략적 규모 추정 문제.
