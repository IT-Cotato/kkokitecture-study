### 1. 트위터가 스노플레이크를 만든 배경

교재에서는 "분산 환경에서 유일 ID가 필요하다"고만 했는데, 실제 트위터의 상황은 이랬다.

트위터는 원래 대부분의 데이터를 MySQL에 저장하고 있었다. 처음엔 DB 인스턴스 하나로 시작했지만, 점점 커져서 결국 수많은 대형 DB 클러스터가 됐다. 그러다 MySQL을 Cassandra 혹은 수평 샤딩 MySQL로 교체하는 작업을 진행하게 됐다. 

여기서 핵심 문제가 생겼다.

**MySQL과 달리 Cassandra에는 유일 ID를 생성하는 기능이 내장되어 있지 않다.** 

즉, 트위터가 스노플레이크를 만든 직접적인 이유는 "Cassandra로 이전하면서 ID 생성 기능을 직접 만들어야 했기 때문"이었다.

### 2. 트위터의 실제 요구사항

트위터는 초당 수만 개의 ID를 고가용성 방식으로 생성할 수 있어야 했다. 이 요구사항이 자연스럽게 "비조율(uncoordinated) 방식", 즉 서버들이 서로 소통하지 않고 독립적으로 ID를 만드는 방향을 유도했다.

> 💡 교재에 나온 "서버들이 서로 소통 없이 독립적으로 ID를 만든다"는 게 바로 이 **비조율(uncoordinated) 방식**을 말하는 것.
> 

또한 ID는 대략적으로 정렬 가능해야 했다. 트윗 A와 B가 비슷한 시간에 올라왔다면, 두 ID도 서로 가까운 값을 가져야 한다는 의미다. 트위터와 대부분의 트위터 클라이언트가 트윗을 이 방식으로 정렬하기 때문이다. 또한 이 숫자들은 64비트 안에 들어와야 했다.

### 3. Options(고려했던 방법들)

트위터는 여러 가지 방법을 고려했는데,

(1) MySQL 기반 티켓 서버는 일종의 재동기화 루틴 없이는 필요한 정렬 보장을 제공하지 못했다. 

⇒ 시간순 정렬 보장 불가

(2) 다양한 UUID도 고려했지만, 찾을 수 있는 모든 방식이 128비트를 필요로 했다. 

⇒ 요구사항 미충족

(3) 그 다음으로 Zookeeper 순차 노드를 살펴봤지만, 필요한 성능을 얻을 수 없었고, 조율(coordinated) 방식이 실질적인 이득 없이 가용성만 낮출 것을 우려했다.

⇒ 성능 부족 + 가용성 저하

#### Zookeeper란?

분산 시스템에서 공통 정보를 중앙에서 관리해주는 서비스.

스노플레이크에서는 아래와 같이 동작한다고 한다:

```
서버 시작 시 (딱 한 번만):
서버 → Zookeeper: "나 워커 번호 주세요"
Zookeeper → 서버: "너는 5번"

이후 평상시:
서버가 Zookeeper 없이 독립적으로 ID 생성
[타임스탬프 | 워커번호:5 | 일련번호]
```

왜 Zookeeper 순차 노드 방식은 탈락인가?

→ Zookeeper를 두 가지 방식으로 쓸 수 있는데,

```
방식 1: Zookeeper로 워커 번호만 결정 (시작할 때 딱 한 번)
  → 이후엔 각 서버가 독립적으로 ID 생성
  → 빠름 ✅  ← 트위터가 최종 채택한 방식

방식 2: Zookeeper 순차 노드로 ID를 매번 직접 발급
  → ID 만들 때마다 Zookeeper에 요청
  → 느리고 Zookeeper가 죽으면 전체 마비 ❌  ← 탈락한 방식
```

방식 2가 탈락한 이유는 티켓 서버의 단점과 똑같기 때문이다. 매번 중앙 서버에 물어봐야 하니까 느리고, 그 서버가 SPOF가 되는 것.

### 4. 최종 Solution

트위터는 결국 비조율 방식으로 대략 정렬된 64비트 ID를 생성하기 위해 `타임스탬프`, `워커 번호`, `시퀀스 번호`의 조합으로 결정했다. 시퀀스 번호는 스레드별로 관리되고, 워커 번호는 시작 시 Zookeeper를 통해 결정된다.

- 워커 번호와 시퀀스 번호란?
    
    ```
    블로그 용어          교재 용어
    ─────────────────────────────────────────
    워커 번호(worker)  =  데이터센터ID(5비트) + 서버ID(5비트)
    시퀀스(sequence)   =  일련번호(12비트)
    ```
    
    - 워커(Worker)란?
        - 블로그에서는 데이터센터ID와 서버ID를 따로 구분하지 않고 그냥 "워커 번호" 하나로 합쳐서 표현했다. 즉, **ID를 생성하는 서버 한 대**를 의미.
    - 시퀀스(Sequence)란?
        - 교재에 나온 일련번호와 완전히 동일한 개념
            
            ```
            같은 밀리초 안에서 요청이 여러 개 오면
            순서대로 번호를 붙여주는 것
            
            10:00:00.001 → 첫 번째 요청 → 시퀀스: 0
            10:00:00.001 → 두 번째 요청 → 시퀀스: 1
            10:00:00.001 → 세 번째 요청 → 시퀀스: 2
            
            10:00:00.002 → 새 밀리초    → 시퀀스: 0 (리셋!)
            ```
            

### 5. 스노플레이크를 채택한 다른 회사들

스노플레이크는 트위터만 쓰는 게 아니며, 많은 회사들이 이 방식을 채택하거나 변형해서 쓰고 있다.

트위터(현 X)는 트윗, DM, 유저, 리스트 등 API로 접근 가능한 모든 객체에 스노플레이크 ID를 사용한다. Discord도 스노플레이크를 사용하는데, 자신들만의 기원 시각(epoch)을 설정해서 쓴다. [Wikipedia](https://en.wikipedia.org/wiki/Snowflake_ID)

소니도 스노플레이크에서 영감을 받아 **Sonyflake**를 만들었는데, 비트 배분을 다르게 했다.

https://github.com/sony/sonyflake

Sonyflake는 39비트를 시간(10ms 단위), `8비트`를 시퀀스 번호, `16비트`를 머신 ID에 할당한다. 트위터 스노플레이크보다 수명이 174년으로 더 길고, 더 많은 머신(2¹⁶대)을 지원하지만, 단일 인스턴스에서 10ms당 생성 가능한 ID 수(2⁸개)는 더 적다.

교재에서 배운 "각 절의 길이 최적화"가 실제로 이렇게 적용된 사례다:

```
트위터 스노플레이크:   [타임스탬프 41비트 | 머신ID 10비트 | 시퀀스 12비트]
→ 69년, 1024대, ms당 4096개

소니 Sonyflake:       [타임스탬프 39비트 | 시퀀스 8비트  | 머신ID 16비트]
→ 174년, 65536대, 10ms당 256개

"더 오래, 더 많은 서버" vs "더 빠른 생성" 트레이드오프!
```
