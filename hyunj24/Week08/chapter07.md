# 7장: 분산 시스템을 위한 유일 ID 생성기 설계

유일 ID를 생성하는 기능에 관한 챕터.

🔗 [정리한 노션 링크](https://www.notion.so/8-5-10-7-ID-35b2c2a9e09280f49a25f69a55e10f57?source=copy_link)

## 0. 왜 이게 어려운 문제인가?

일반적인 작은 서비스에서는 데이터베이스의 `auto_increment` 기능을 사용한다. 레코드를 추가할 때마다 1, 2, 3... 자동으로 번호를 매겨주는 방식이다.
**그런데 분산 환경에서는 이게 불가능하다.**

```
[서버 A] → DB A에 저장 → ID: 1, 2, 3 생성 중...
[서버 B] → DB B에 저장 → ID: 1, 2, 3 생성 중...

→ 둘 다 ID = 1을 만들어버림! 💥 충돌!
```

여러 DB 서버가 각자 ID를 만들면 중복이 생긴다. 또한 서버들 사이에서 매번 "내가 몇 번까지 썼어?" 하고 확인하면 속도가 엄청 느려진다.

## 1단계: 문제 이해 및 설계 범위 확정

### 요구사항 파악 (면접관과의 대화)

시스템 설게 문제를 푸는 첫 단계는 적절한 질문을 통해 **모호한 것을 없애고, 설계 방향을 정하는 것**이다.

| 질문 | 답변 | 왜 중요한가? |
| --- | --- | --- |
| ID의 특성은? | 유일 + 정렬 가능 | 설계 방향 결정 |
| 항상 1씩 증가하는가? | 아니오, 단 시간순 정렬은 돼야 함 | 구현 방법 제한 |
| 숫자로만 구성? | 예 | UUID 같은 문자 혼합 방식 제외 |
| 시스템 규모? | **초당 10,000개** | 성능 요구사항 |

### 최종 요구사항 정리

```
1. ID는 유일해야 한다
2. ID는 숫자로만 구성되어야 한다
3. ID는 64비트로 표현될 수 있어야 한다
4. ID는 발급 날짜에 따라 정렬 가능해야 한다
5. 초당 10,000개의 ID를 만들 수 있어야 한다
```

> 💡 **"64비트"가 왜 중요한가?** 64비트 정수는 최대 약 922경(9.2 × 10¹⁸)까지 표현 가능하다. 대부분의 프로그래밍 언어에서 `long` 타입이 64비트다. 너무 크면 저장 공간 낭비, 너무 작으면 금방 고갈된다.
>

## 2단계: 개략적 설계안 제시 및 동의 구하기

### 방법1: 다중 마스터 복제(multi-master replication)

#### 동작 원리

```
[DB 서버 A] → 1, 3, 5, 7 ... (2씩 증가)
[DB 서버 B] → 2, 4, 6, 8 ... (2씩 증가)
                ↓
             [웹 서버]
```

DB가 2개라면 한 서버는 1씩이 아니라 **k(서버 수)만큼 증가**시킨다.

- 서버 A: 1, 1+2, 1+4 → **1, 3, 5...**
- 서버 B: 2, 2+2, 2+4 → **2, 4, 6...**

서버가 3개라면? 1·4·7... / 2·5·8... / 3·6·9... 이런 식이다.

#### 장단점

| 장점 | 단점 |
| --- | --- |
| 규모 확장성 어느 정도 해결 | 여러 데이터 센터에 걸쳐 규모 늘리기 어려움 |
| DB 늘리면 초당 생산 ID 수도 증가 | **ID가 시간 흐름에 맞춰 커지도록 보장 불가** |
|  | **서버 추가/삭제 시 대응이 어려움** |
- ID가 시간 흐름에 맞춰 커지도록 보장 불가하다는 말은?
    
    요구 사항 중에
    
    ```
    "ID는 발급 날짜에 따라 정렬 가능해야 한다"
    ```
    
    와 같은 내용이 있었고, 이는 즉
    
    ```
    나중에 만들어진 ID > 먼저 만들어진 ID
    ```
    
    이게 항상 보장되어야 한다는 것이다.
    
    그러나 만약 서버 2대가 돌아가는 상황이라고 가정할 때 서버 1대가 만약 잠시 버벅이기라도 했다면,
    
    ```
    시각 10:00:00.004  →  서버 B가 엄청 바빠서 잠깐 버벅임 😵
    시각 10:00:00.005  →  서버 A가 ID 5 발급  ← 시각 005
    시각 10:00:00.006  →  서버 A가 ID 7 발급  ← 시각 006
    시각 10:00:00.999  →  서버 B가 겨우 ID 4 발급  ← 시각 999 (한참 뒤!)
    ```
    
    ID 4가 나중에 발급됐는데도, ID 5, 7보다 ID가 숫자가 낮은 문제 발생.
    
    즉, **"각 서버가 독립적으로 ID를 만드는"**는 구조이기 때문에, 서버 간 속도 차이나 지연이 생기는 순간 **ID 번호 순서와 실제 시간 순서가 어긋나버린다.**
    

> 💡 서버가 3개인 상황에서 서버 1대를 추가하면 기존 패턴(+3씩)을 전부 바꿔야 해서 엄청난 혼란이 생긴다. 그래서 실무에서 잘 안 쓰인다.
> 

### 방법 2: UUID (Universally Unique Identifier)

#### UUID란?

UUID는 **128비트**짜리 숫자로, 생긴 모습은 이렇다:

```
09c93e62-50b4-468d-bf8a-c07e1040bfb2
```

#### 동작 원리

```
[웹서버1]     [웹서버2]     [웹서버3]     [웹서버4]
[ID생성기]    [ID생성기]    [ID생성기]    [ID생성기]
   ↓           ↓           ↓            ↓
     각자 독립적으로 UUID 생성 (서버 간 소통 없음!)
```

각 서버가 **완전히 독립적으로** UUID를 생성한다. 서버끼리 "내가 몇 번 썼어?" 하고 물어볼 필요가 없다.

#### 충돌 가능성은?

위키피디아에 따르면, 중복 UUID가 1개 생길 확률을 50%로 끌어올리려면 **초당 10억 개의 UUID를 100년 동안** 계속 만들어야 한다. 사실상 충돌이 없다고 봐도 된다.

#### 장단점

| 장점 | 단점 |
| --- | --- |
| 만들기 단순 | **ID가 128비트** (요구사항은 64비트!) |
| 서버 간 조율 불필요 → 동기화 이슈 없음 | **시간순 정렬 불가** |
| 규모 확장 쉬움 | **숫자가 아닌 값 포함** (문자, 하이픈 등) |

> 💡 UUID는 요구사항 3가지(64비트, 정렬가능, 숫자만)를 모두 어긴다. 그래서 이 방법도 탈락이다.
> 

### 방법 3: 티켓 서버 (Ticket Server)

#### 동작 원리

```
[웹서버1] ──┐
[웹서버2] ──┼──→ [티켓 서버] (auto_increment DB 하나만 사용)
[웹서버3] ──┘
```

핵심 아이디어는 ID를 각자 만들지 말고, **ID 발급 전담 서버(티켓 서버)를 하나 두고 그거기서만 ID를 만들자는 것.**

 `auto_increment` 기능을 가진 DB를 **딱 하나만, 중앙에서** 사용하는 것이다. 플리커(Flickr)가 실제로 이 방식을 사용했다.

#### 장단점

| 장점 | 단점 |
| --- | --- |
| 유일성 보장 + 숫자만으로 구성된 ID | **티켓 서버가 SPOF(단일 장애점)** |
| 구현 쉬움 | 티켓 서버 장애 시 전체 시스템 마비 |
| 중소규모 앱에 적합 | SPOF 해결하려고 서버 여러 대 쓰면 데이터 동기화 문제 발생 |

> 💡 **SPOF(Single-Point-Of-Failure)란?** 그 하나가 망가지면 전체가 멈추는 지점을 말한다. 마치 전등의 전구 하나가 나가면 그 방 전체가 어두워지는 것처럼이다.
> 

### 방법 4: 트위터 스노플레이크 접근법 ⭐ (최종 채택)

앞의 세 방법은 모두 요구사항을 완전히 만족하지 못했다. 트위터는 `스노플레이크(snowflake)`라는 독창적인 ID 생성 기법을 만들었고, 이것이 모든 요구사항을 만족한다.

#### 핵심 아이디어: ID를 여러 구역으로 나눈다

"각개격파(divide and conquer)" 전략이다. 64비트를 이렇게 쪼갠다:

```
┌─────┬──────────────────────────────────────────┬───────────┬──────────┬────────────┐
│1비트 │              41비트                       │   5비트     │  5비트   │   12비트     │
│사인  │           타임스탬프                        │  데이터센터  │ 서버 ID   │  일련번호    │
└─────┴──────────────────────────────────────────┴───────────┴──────────┴────────────┘
```

## 3단계: 상세 설계

### 각 비트 구역 설명

#### ① 사인(Sign) 비트 - 1비트

```
용도: 현재는 항상 0
이유: 나중을 위해 유보 (음수/양수 구별에 쓸 수 있음)
```

1비트를 할당하며, 지금으로선 쓰임새가 없지만 나중에 음수/양수를 구별하는 데 사용할 수 있다.

#### ② 타임스탬프(Timestamp) - 41비트

41비트에 저장되는 값은:

`타임스탬프 = 현재 UTC 시각 - 트위터 기원 시각(epoch)`

즉, **기원 시각을 빼고 난 차이값**이 저장된다. (= 기원 시각으로부터 흐른 시간(ms))

```
기준: 트위터 스노플레이크 기원 시각 (epoch)
     = 1288834974657 (2010년 11월 4일 01:42:54 UTC)
단위: 밀리초(ms)
```

**왜 기원시각을 빼는가?**

41비트로는 표현할 수 있는 최댓값이 정해져 있는데, 만약 현재 UTC 시각을 그대로 저장하면 41비트로는 금방 고갈된다. 하지만 기원시각을 빼면 숫자가 훨씬 작아져 더 오래 쓸 수 있다.

**왜 타임스탬프가 중요한가?**

- 타임스탬프는 시간이 흐를수록 값이 커진다
- ID에서 앞쪽 비트에 타임스탬프가 있으므로 → **ID를 정렬하면 자동으로 시간순 정렬**이 된다. 이것이 핵심이다.

**41비트로 얼마나 표현 가능한가?**

```
2^41 - 1 = 2,199,023,255,551 밀리초
         ≈ 69년
```

이 ID 생성기는 **약 69년** 동안 사용 가능하다.

> ⚠️ **주의**: 69년이 지나면 타임스탬프가 오버플로우(overflow) 된다. 그때는 기원 시각을 바꾸거나 ID 체계를 바꿔야 한다. 트위터가 2010년에 도입했으니, 2079년쯤에 문제가 생길 수 있다.
> 

**타임스탬프 → UTC 시각 변환 예시** (교재 그림 7-7):

```
ID의 41비트 추출
    ↓ 십진수로 변환
297616116568
    ↓ 트위터 기원 시각(epoch) 더함
1586451091225 (밀리초)
    ↓ UTC 시각으로 변환
Apr 09 2020 16:51:31 UTC
```

#### ③ 데이터센터 ID - 5비트

```
2^5 = 32
→ 최대 32개의 데이터센터를 지원
```

서울, 도쿄, 뉴욕, 런던... 전 세계 데이터센터를 최대 32개까지 구분할 수 있다.

> ⚠️ **중요**: 데이터센터 ID와 서버 ID는 **시스템이 시작할 때 결정**되며, 운영 중에는 바꾸면 안 된다. 잘못 바꾸면 ID 충돌이 발생한다.
> 

#### ④ 서버 ID - 5비트

```
2^5 = 32
→ 데이터센터당 최대 32개의 서버
```

총 32(데이터센터) × 32(서버) = **최대 1,024대의 서버** 운용 가능하다.

- 데이터센터 ID와 서버 ID가 왜 필요한가?
    
    스노플레이크의 핵심 목표는 "서버들이 서로 소통 없이 독립적으로 ID를 만들어도 절대 안 겹치게" 하는 것이라서, 각 서버가 만든 ID에 "나 누구야" 라는 정보가 담겨 있어야한다.
    
    - 데이터센터란?
        
        ```
        [한국 데이터센터]      [미국 데이터센터]      [유럽 데이터센터]
          서버들이 있는          서버들이 있는           서버들이 있는
          건물/시설              건물/시설               건물/시설
        ```
        
        대형 서비스는 전 세계 여러 곳에 서버 건물을 두고 운영하는데, 이 건물 하나하나가 데이터센터다.
        
        이 5비트(0~31)로 각 데이터센터를 구분한다.
        
    - 서버 ID란?
        
        데이터센터 안에도 서버가 여러 대 있는데, 이를 구분하는 게 서버 ID이다.
        
        ```
        [서울 데이터센터 (데이터센터 ID: 0)]
          ├── 서버 0번
          ├── 서버 1번
          ├── 서버 2번
          └── ... (최대 32대)
        
        [도쿄 데이터센터 (데이터센터 ID: 1)]
          ├── 서버 0번
          ├── 서버 1번
          └── ... (최대 32대)
        ```
        
    - 그래서 둘을 합치면
        
        ```
        데이터센터 32개 × 서버 32대 = 총 1,024대
        
        각 서버가 고유한 조합을 가짐:
        
        서울-서버0   → 데이터센터:0, 서버:0
        서울-서버1   → 데이터센터:0, 서버:1
        도쿄-서버0   → 데이터센터:1, 서버:0
        도쿄-서버1   → 데이터센터:1, 서버:1
        ...
        ```
        

#### ⑤ 일련번호 - 12비트

```
2^12 = 4,096
→ 같은 밀리초 안에 최대 4,096개의 ID 생성 가능
```

동작 방식:

- 같은 서버에서 ID를 생성할 때마다 1씩 증가
- **1밀리초가 지나면 0으로 초기화(reset)**

```
1ms 동안:
  첫 번째 요청 → 일련번호 = 0
  두 번째 요청 → 일련번호 = 1
  ...
  4096번째 요청 → 일련번호 = 4095
  (이 이상은 다음 밀리초까지 대기)

다음 1ms:
  일련번호 = 0 (리셋!)
```

초당 생성 가능한 ID 수
= 1초(1,000ms) × 1ms당 최대 4,096개
= 4,096,000개/초 (약 410만개)

요구사항: 초당 10,000개
→ 충분히 만족. ✅

### 전체 구조 다시보기

```
예시 ID 생성 과정:

현재 시각: 2020년 4월 9일 16:51:31.225 UTC
타임스탬프 = 현재시각 - 기원시각 = 297616116568 (ms)

데이터센터 ID = 1 (예시)
서버 ID = 1 (예시)
일련번호 = 0 (이 밀리초의 첫 번째 ID)

→ 64비트 ID 완성!
```

## 4단계: 마무리

### 4가지 방법 최종 비교

| 방법 | 유일성 | 64비트 | 숫자만 | 시간순 정렬 | 초당 10,000개 | 채택? |
| --- | --- | --- | --- | --- | --- | --- |
| 다중 마스터 복제 | ✅ | ✅ | ✅ | ❌ | ✅ | ❌ |

### 💬 추가로 논의할 수 있는 주제들

### 1. 시계 동기화 (Clock Synchronization)

설계 과정에서 모든 서버가 같은 시계를 쓴다고 가정했다. 하지만 실제로는:

- 하나의 서버가 여러 CPU 코어에서 실행될 수 있다
- 물리적으로 독립된 여러 장비에서 실행될 수 있다
- 각 장비의 시계가 조금씩 다를 수 있다 (시계 오차)

해결책: **NTP(Network Time Protocol)** - 네트워크를 통해 서버들의 시계를 동기화하는 가장 보편적인 방법이다. 

### 2. 각 절(section)의 길이 최적화

상황에 따라 비트 배분을 다르게 할 수 있다:

```
동시성이 낮고 수명이 긴 앱이라면?
→ 일련번호 비트 ↓, 타임스탬프 비트 ↑
  (더 오래 쓸 수 있게)
```

### 3. 고가용성 (High Availability)

ID 생성기는 **필수 불가결(mission critical)** 컴포넌트다. 이게 멈추면 전체 서비스가 멈춘다. 따라서 아주 높은 가용성을 제공해야 한다.
