# 4장: 처리율 제한 장치의 설계 요약 정리


## 1단계 문제 이해 및 설계 범위 확정

**처리율 제한 장치(rate limiter)** 란 클라이언트/서비스가 보내는 트래픽의 처리율을 제어하는 장치다. 임계치(threshold)를 넘는 요청은 모두 차단(block)된다.

**활용 사례 예시**

- 사용자는 초당 2회 이상 새 글 게시 불가
- 같은 IP로 하루 10개 이상 계정 생성 불가
- 같은 디바이스로 주당 5회 이상 리워드 요청 불가

**도입 이유**

- DoS 공격으로 인한 자원 고갈 방지
- 비용 절감 (우선순위 높은 API에 자원 집중)
- 봇/잘못된 이용 패턴으로 유발된 트래픽 차단

**요구사항 정리 (면접관과의 Q&A 결과)**

| 항목 | 내용 |
| --- | --- |
| 제한 대상 | 서버 측 API |
| 기준 | IP, 사용자 ID 등 다양한 규칙 지원 |
| 규모 | 대규모 요청 처리 가능 |
| 환경 | 분산 환경 |
| 배포 | 독립 서비스 또는 애플리케이션 코드 포함 |
| 사용자 알림 | 요청이 제한되면 사용자에게 알려야 함 |

**핵심 비기능 요구사항**

- 낮은 응답 시간
- 적은 메모리 사용
- 분산형 처리율 제한 지원
- 예외 처리 명확화
- 높은 결함 내성(fault tolerance)

## 2단계 개략적 설계안 제시 및 동의 구하기

### 처리율 제한 장치는 어디에 둘 것인가?

**클라이언트 측?** ❌ 비추천

- 클라이언트 요청은 위변조 가능, 모든 클라이언트 통제 어려움

**서버 측** ✅ 또는 **미들웨어** ✅

- 서버 앞단에 처리율 제한 미들웨어를 두고, 이 미들웨어가 API 서버로 가는 요청을 통제
- 한도 초과 시 HTTP 429(Too many requests) 반환
- 클라우드 마이크로서비스 환경에서는 보통 **API 게이트웨이**에 구현

**배치 선택 기준**

- 현재 기술 스택 및 언어 지원 여부
- 필요한 알고리즘 지원 여부
- 마이크로서비스 여부 (이미 게이트웨이가 있다면 통합 고려)
- 직접 구현 인력이 없다면 → **상용 API 게이트웨이** 사용 권장

### 처리율 제한 알고리즘

5가지 주요 알고리즘을 비교한다.

#### 1. 토큰 버킷(Token Bucket)

**동작 원리**

- 버킷에 최대 N개의 토큰을 담을 수 있음
- 토큰 공급기(refiller)가 초당 일정량 토큰 보충
- 요청 도착 시 토큰 1개 소비 → 토큰 없으면 요청 버림(drop)

**파라미터:** 버킷 크기, 토큰 공급률

**버킷 수:** API 엔드포인트별 또는 IP별로 별도 버킷 운용

| 장점 | 단점 |
| --- | --- |
| 구현 쉬움 | 두 파라미터 튜닝이 까다로움 |
| 메모리 효율적 |  |
| 짧은 시간 집중 트래픽(burst) 처리 가능 |  |

**사용처:** 아마존, 스트라이프

#### 2. 누출 버킷(Leaky Bucket)

토큰 버킷 알고리즘과 유사하지만 요청 처리율이 고정되어 있다.

**동작 원리**

- FIFO 큐로 구현
- 요청 도착 시 큐에 빈자리 있으면 추가, 없으면 버림
- 일정 시간마다 큐에서 꺼내 처리 (고정 처리율)

**파라미터:** 버킷 크기, 처리율(outflow rate)

| 장점 | 단점 |
| --- | --- |
| 큐 크기 제한 → 메모리 효율적 | 두 파라미터 튜닝 까다로움 |
| 안정적 출력률(stable outflow rate) | 단시간 집중 트래픽 시 큐에 오래된 요청들이 쌓이게 되고, 제때 처리 못하면 최신 요청 버려질 수 있음 |

**사용처:** 쇼피파이(Shopify)

#### 3. 고정 윈도 카운터(Fixed Window Counter)

**동작 원리**

- 타임라인을 고정 윈도(예: 1초)로 분할
- 각 윈도에 카운터 부착, 요청마다 +1
- 임계치 도달 시 새 윈도 열릴 때까지 요청 거부

| 장점 | 단점 |
| --- | --- |
| 메모리 효율, 이해 쉬움 | 윈도 경계 부근에서 허용량의 2배까지 처리될 수 있음 |
| 특정 트래픽 패턴에 적합 |  |

#### 4. 이동 윈도 로깅(Sliding Window Log)

**동작 원리**

- 각 요청의 타임스탬프를 정렬 집합(sorted set)에 보관 (보통 Redis)
- 새 요청 도착 시 만료된 타임스탬프 제거
- 로그 크기 ≤ 허용치 → 요청 전달, 초과 → 거부

| 장점 | 단점 |
| --- | --- |
| 처리율 제한 매우 정교함 | 거부된 요청 타임스탬프도 보관 → 메모리 많이 사용 |

#### 5. 이동 윈도 카운터(Sliding Window Counter)

**동작 원리**

- 고정 윈도 카운터 + 이동 윈도 로깅의 결합
- 현재 윈도 요청 수 + (직전 윈도 요청 수 × 이동 윈도와 직전 윈도가 겹치는 비율)

**예시:** 직전 1분 5개, 현재 1분 3개, 현재 30% 시점 진입
→ 추정치 = 3 + 5 × 70% = 6.5 → 내림하여 6

| 장점 | 단점 |
| --- | --- |
| 짧은 시간 집중 트래픽 대응 가능 | 직전 시간 요청이 균등 분포라 가정 (약간 느슨) |
| 메모리 효율 |  |

> Cloudflare 실험 결과: 40억 요청 중 잘못 처리된 비율이 0.003%에 불과
> 

### 개략적인 아키텍처

**핵심 구성:** 클라이언트 → 처리율 제한 미들웨어 → API 서버 + Redis(카운터 저장)

- **Redis** 사용 이유: 메모리 기반으로 빠르고, `INCR`(카운터 증가) / `EXPIRE`(타임아웃 설정) 명령 지원

**동작 흐름**

1. 클라이언트 요청 → 처리율 제한 미들웨어
2. 미들웨어가 Redis에서 카운터 조회
3. 한도 도달 → 429 반환 / 미달 → API 서버 전달 + 카운터 증가

## 3단계 상세 설계

### 처리율 제한 규칙

리프트(Lyft)는 처리율 제한에 오픈 소스를 사용하고 있다고 한다.

- 규칙은 보통 설정 파일(configuration file) 형태로 **디스크에 저장된다**

```yaml
# 예시 1: 마케팅 메시지 하루 5개 제한
domain: messaging
descriptors:
  - key: message_type
    Value: marketing
    rate_limit:
      unit: day
      requests_per_unit: 5
```

```yaml
# 예시 2: 로그인 분당 5회 제한
domain: auth
descriptors:
  - key: auth_type
    Value: login
    rate_limit:
      unit: minute
      requests_per_unit: 5
```

### 처리율 한도 초과 트래픽의 처리

- 한도 초과 시 **HTTP 429** 반환
- 경우에 따라 초과 요청을 **메시지 큐에 보관**했다가 나중에 처리 가능 (예: 주문 시스템)

#### 처리율 제한 장치가 사용하는 HTTP 헤더

클라이언트가 자신의 요청이 제한되고 있는지 알 수 있도록 응답 헤더 제공:

| 헤더 | 의미 |
| --- | --- |
| `X-Ratelimit-Remaining` | 윈도 내 남은 처리 가능 요청 수 |
| `X-Ratelimit-Limit` | 매 윈도마다 클라이언트가 보낼 수 있는 요청 수 |
| `X-Ratelimit-Retry-After` | 몇 초 뒤에 다시 요청해야 하는지 |

### 상세 설계 (구성 요소)

- **처리율 제한 규칙** → 디스크 저장, 캐시로 로딩
- **처리율 제한 미들웨어** → Redis에서 카운터/타임스탬프 조회
- **API 서버** → 정상 요청만 전달
- **Redis** → 카운터 저장소
- **메시지 큐** → 거부된 요청 보관 옵션

### 분산 환경에서의 처리율 제한 장치 구현

단일 서버 → 쉬움. 분산 환경에서는 두 가지 문제 발생:

#### 1️⃣ 경쟁 조건(Race Condition)

**문제:** 두 스레드가 동시에 카운터를 읽고 각자 +1 → 실제로는 2 증가해야 하는데 1만 증가

**해결책:**

- 락(lock) → 성능 저하 심각
- **루아 스크립트(Lua script)** 사용 ✅
- **정렬 집합(sorted set) Redis 자료구조** 사용 ✅

#### 2️⃣ 동기화 이슈(Synchronization Issue)

**문제:** 처리율 제한 서버 여러 대 → 각 서버가 서로 다른 클라이언트 상태 가짐 → 부정확한 제한

**해결책:**

- 고정 세션(sticky session) → 비추천 (확장성·유연성 부족)
- **중앙 집중형 데이터 저장소(Redis)** 사용 ✅

### 성능 최적화

1. **에지 서버(edge server) 활용**
    - 데이터센터 여러 곳에 처리율 제한 장치 배치
    - 사용자 트래픽을 가장 가까운 에지 서버로 전달 → 지연시간 감소
    - 예: Cloudflare는 194개 지역에 에지 서버 운영
2. **최종 일관성 모델(eventual consistency model)**
    - 제한 장치 간 데이터 동기화 시 사용
    - 자세한 내용은 6장 '키-값 저장소 설계' 참고

### 모니터링

설치 이후 효과적으로 동작하는지 확인 필요. 확인 항목:

- **채택된 알고리즘이 효과적인가?**
    - 규칙이 너무 빡빡 → 유효 요청 버려짐 → 규칙 완화 필요
    - 갑작스러운 트래픽 급증 시 → **토큰 버킷** 알고리즘 적합
- **정의한 처리율 제한 규칙이 효과적인가?**
    - 트래픽 패턴에 맞게 알고리즘·규칙 조정

## 4단계 마무리

**다룬 알고리즘 5가지 요약**

| 알고리즘 | 특징 |
| --- | --- |
| 토큰 버킷 | burst 허용, 구현 쉬움 |
| 누출 버킷 | 안정적 출력률 |
| 고정 윈도 카운터 | 단순, 경계 문제 존재 |
| 이동 윈도 로깅 | 정교하나 메모리 多 |
| 이동 윈도 카운터 | 균형잡힌 접근 |

**추가로 언급할 수 있는 주제들**

- 경성(hard) vs 연성(soft) 처리율 제한
- 다양한 계층에서의 처리율 제한 (L3 IP 레벨 등 OSI 7계층 활용)
- 처리율 제한 회피 방법 (클라이언트 설계 측면)
    - 클라이언트 측 캐시로 API 호출 횟수 줄이기
    - 짧은 시간에 너무 많은 요청 보내지 않기
    - 예외/에러 처리 코드로 graceful 복구
    - 재시도 로직에 충분한 back-off 시간 두기
