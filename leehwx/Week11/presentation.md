# Urban Airship의 25억 건 알림 처리 확장기
> 출처: https://highscalability.com/how-urban-airship-scaled-to-25-billion-notifications-during/
> 

# **문제 정의**

Urban Airship은 2016년 미국 대선 당일 24시간 동안 25억 건의 푸시 알림을 성공적으로 전송해야 했다.

선거 결과에 따라 단일 이벤트로 초당 75,000건 이상의 API 요청(HTTPS ingress)이 들어오는 전례 없는 트래픽 폭주가 발생했다.

기존 2009년에 구축된 초기 아키텍처(Python 기반 워커 및 PostgreSQL 샤드)로는 급증하는 트래픽 규모에 맞춰 서버 용량을 추가하고 처리량을 확장하는 데 한계가 있었다.

# **설계**

새로운 트래픽 규모와 성능 요구 사항을 충족하기 위해 기존 시스템을 서비스 지향 아키텍처(SOA)로 전면 개편했다.

병목 현상이 발생하는 기존 시스템을 추출해 대규모 처리에 적합한 고동시성 Java 서비스로 재구축했다.

## **서비스 지향 아키텍처 SOA**

- 기존의 거대한 단일 애플리케이션을 각각 독립적인 비즈니스 역할을 수행하는 여러 개의 서비스 단위로 쪼개어 구성하는 설계 방식이다.
- 특정 기능에 트래픽이 몰려 병목 현상이 발생할 경우, 해당 서비스만 독립적으로 확장(Scale-out)할 수 있어 대규모 트래픽 처리에 매우 유리하다.

## **고동시성 Java 서비스로의 마이그레이션**

- 기존의 Python으로 작성된 API와 워커(Worker)들을 멀티스레딩 및 고동시성 처리에 더 유리한 Java 기반 서비스로 추출하여 재구축했다.
- 하위 시스템 간 통신 시 불변 객체를 활용하여 복잡한 동시성 제어를 단순화했다.

## 데이터베이스

성능 및 확장성 요구 사항을 충족하기 위해 HBase와 Cassandra를 많이 사용한다.

HBase와 Cassandra는 모두 컬럼형 NoSQL이지만, 각각 장단점이 매우 다르다.

- HBase
    - 응답의 카디널리티가 매우 높은 고처리량 스캔에 적합
    - 장애 발생 시 일관성, 파티션 내성 우선시
- Cassandra
    - 응답에 결과가 소수만 포함될 것으로 예상되는 저카디널리티 조회에 적합
    - 가용성, 파티션 내성 우선시

초기에는 디바이스 데이터를 여러 대의 PostgreSQL 데이터베이스로 나누어 저장(샤딩)했으나, 데이터와 트래픽 규모가 급격히 커지며 확장성 한계에 직면했다.

이를 해결하기 위해 대용량 분산 처리에 특화된 NoSQL 데이터베이스인 HBase와 Cassandra를 결합한 다중 데이터베이스 구조로 마이그레이션했다.

각 서비스의 데이터 저장소를 공유 자원이 아닌 '구현 세부 사항'으로 취급하여, 다른 서비스에 영향을 주지 않고 데이터 모델을 유연하게 변경할 수 있는 환경을 구축했다.

## 데이터 모델링

각 서비스는 근본적으로 동일한 데이터를 다루지만, 성능 최적화를 위해 서로 다른 형태로 데이터를 인덱싱하고 구조화한다.

수많은 서비스 간의 데이터 일관성을 유지하기 위해 빠르고 내구성이 뛰어난 Kafka 시스템에 크게 의존했다.

Kafka는 매우 빠르고 내구성도 뛰어나지만, 속도에 단점이 있다.

Kafka 메시지는 최소 한 번 전송이 보장될 뿐이며, 순서대로 도착한다는 보장은 없다.

### 해결

이 문제를 해결하기 위해 모든 변경 경로가 교환 법칙을 만족하도록 모델링했다.

모든 데이터 변경 작업을 순서에 상관없이 결과가 같도록 설계했다. 즉, 멱등성을 가진다.

⇒ 일회성 데이터 복구, 데이터 백필, 심지어 마이그레이션와 같은 작업을 위해 Kafka 스트림을 재사용할 수 있다.

이를 위해 HBase와 Cassandra의 '셀 버전' 기능을 활용했다.

### **데이터 무결성과 블라인드 쓰기**

수신된 메시지를 개별 열단위로 분해하고, 타임스탬프 기반의 툼스토닝 로직을 결합하여 데이터를 처리한다.

- 타임스탬프 기반 버전 관리
    - 일반적으로 타임스탬프를 셀 버전으로 사용하여 여러 버전의 데이터 중 순서를 결정한다. (단, 시스템 오류를 유발할 수 있는 `MAX_LONG` 같은 극단적인 값은 피한다.)
- 블라인드 쓰기
    - 정교한 버전 관리와 툼스토닝을 통해 데이터를 쓰기 전에 굳이 먼저 읽어서(Read) 확인할 필요 없이 안전하게 덮어쓰는 블라인드 쓰기가 가능해진다.

### **중복 데이터 처리와 성능 모니터링**

블라인드 쓰기는 빠르지만, 시스템 복구를 위한 리플레이 상황 등에서 동일한 데이터가 중복해서 기록될 위험이 있다.

- 멱등성의 한계
    - 멱등성 설계 덕분에 데이터의 최종 상태 값은 변하지 않지만, 스토리지 내부에는 동일한 레코드가 물리적으로 계속 쌓이게 된다.
- 압축 병목
    - 쌓인 중복 레코드들은 압축 과정을 통해 제거되어야 한다.
    - 중복 데이터가 너무 많으면 압축이 지연되고 전체 시스템의 병목 현상을 초래할 수 있다.

⇒ 해결책: 데이터베이스의 압축 소요 시간과 작업 큐 깊이를 엄격하게 모니터링한다.

# 서비스 설계

자바 서비스를 설계할 때 고려하는 일반적인 지침들이 있다.

### 단일 책임 원칙 적용

서비스를 설계할 때는 단 하나의 책임만 부여해야 한다.

### 공유되는 운영 상태 없음

서비스를 설계할 때는 항상 최소 3개의 인스턴스가 동시에 실행 중이라고 가정하고 무상태(Stateless)로 구축해야 한다.

각 서비스는 별도의 외부 조정 과정 없이도 다른 인스턴스와 완전히 동일한 요청을 독립적으로 처리할 수 있어야 한다.

Kafka 컨슈머처럼 내부적으로 파티션 소유권을 조정하는 라이브러리의 동작은 허용하되, 서비스 애플리케이션 로직 자체적으로 상태를 공유하거나 외부 시스템에 의존해 작업을 조정하는 로직은 배제해야 한다.

### 큐에 제한 두기

메모리 고갈과 시스템 다운을 막기 위해 모든 큐에는 반드시 수용 가능한 데이터의 최대 크기를 설정해야 한다.

큐에 제한을 설정할 때는 다음과 같은 예외 상황을 고려하여 각 서비스의 특성에 맞는 적절한 처리 정책을 설계해야 한다.

- 큐가 가득 찼을 때 생산자(Producer)의 대처 방식
    - 자리가 날 때까지 대기(Block)할 것인가?
    - 에러를 발생시키고 요청을 거절할 것인가?
    - 새로운 데이터를 그냥 버릴 것인가(Drop)?
- 대기열의 크기는 얼마나?
    - 큐가 항상 가득 차 있다는 최악의 상황 가정
- 깔끔하게 종료하려면 어떻게?
    - 시스템을 업데이트하거나 종료할 때, 큐에 대기 중이거나 처리 중인 작업들을 어떻게 유실 없이 마무리할 것인지 대비

### **UncaughtExceptionHandler 등록**

커스텀 스레드 풀을 생성할 때는 스레드의 이름을 명확히 지정하고 데몬 상태를 설정했다.

또한, 예측 불가능한 오류로 인해 시스템이 원인도 모른 채 종료되는 것을 막기 위해 예외 처리(UncaughtExceptionHandler)를 필수로 등록하여 심야의 장애 디버깅 시간을 단축했다.

### 가변 상태보다 불변 데이터 객체 사용

복잡한 멀티스레드 환경에서는 가변 상태가 위험할 수 있다.

일반적으로 내부 하위 시스템과 큐 간에 전달할 수 있는 데이터 객체는 불변이다.

불변 객체를 하위 시스템 간 통신의 주요 수단으로 사용하면 동시 사용을 고려한 설계가 훨씬 간단해지고 문제 해결도 쉬워진다.
