# Apache Cassandra

> 출처: https://cassandra.apache.org/doc/stable/cassandra/architecture/overview.html
> 

# 개요

Apache Cassandra는 오픈 소스 분산 NoSQL 데이터베이스이다.

파티셔닝된 와이드 컬럼 스토리지 모델과 최종 일관성 의미 체계를 구현한다.

- **Partitioned**
    - 데이터를 여러 서버(노드)에 나누어 저장한다는 뜻이다.
    - 작동 방식: 특정 기준(Partition Key)을 사용해 데이터를 어떤 노드에 저장할지 결정
    - 장점: 데이터 양이 방대해져도 서버를 옆으로 늘리는 수평적 확장(Scale-out)이 쉬움
- **Wide-column storage model**
    - 전통적인 관계형 데이터베이스(RDBMS)와는 다른 데이터 구조를 가진다.
    - 유연한 스키마
        - 모든 행(Row)이 반드시 같은 컬럼을 가질 필요가 없음
    - 구조
        - 행 키(Row Key) 안에 수많은 컬럼(Column)들이 묶여 있는 구조로, 흔히 Column Family라고도 부른다.
        - 대량의 읽기/쓰기 작업에 최적화되어 있다.
- **Eventually consistent semantics (최종 일관성)**
    - 데이터 변경 사항이 모든 복제본에 반영되는 방식에 관한 규칙
    - 데이터가 업데이트되었을 때, 모든 서버가 그 즉시 똑같은 최신 데이터를 보여주지는 않을 수 있다.
    - 결과**:** 찰나의 순간에는 서버마다 데이터가 다를 수 있지만, 시스템에 문제가 없다면 결국 시간이 지나 모든 노드가 동일한 최신 데이터를 갖게된다.
    - 이유: 데이터 일관성을 조금 희생하는 대신, 시스템이 멈추지 않고 계속 돌아가는 가용성(Availability)과 빠른 응답 속도를 얻기 위함이다.

## **SEDA를 사용한 초기 설계**

카산드라는 페이스북에서 단계별 이벤트 기반 아키텍처(SEDA)를 사용하여 처음 설계되었다.

- **SEDA (Staged Event-Driven Architecture)**
    - 복잡한 서비스 요청을 여러 개의 단계(Stage)로 나누고, 각 단계 사이에 이벤트 큐(Queue)를 두어 처리하는 방식
    - 효과
        - 하나의 작업이 전체 시스템을 블로킹(Blocking)하지 않는다.
        - 트래픽이 폭주할 때 각 단계별로 리소스를 조절하여 시스템의 안정성을 유지할 수 있다.
        - 전통적인 멀티 스레드 모델보다 더 많은 동시 연결을 효율적으로 처리한다.

이 초기 설계는 아마존의 Dynamo 분산 스토리지 및 복제 기술과 구글의 BigTable 데이터 및 스토리지 엔진 모델을 결합하여 구현되었다.

Dynamo 와 BigTable은 모두 확장 가능하고 안정적이며 가용성이 높은 스토리지 시스템에 대한 새로운 요구 사항을 충족하기 위해 개발되었지만, 각각 개선의 여지가 있었다.

- Dynamo의 한계
    - 분산 기술은 훌륭했지만, 단순한 Key-Value 구조라 복잡한 데이터를 구조적으로 담기 어려웠다.
- BigTable의 한계
    - 데이터 저장 모델은 효율적이었으나, 마스터 노드가 죽으면 전체 시스템에 지장을 주는 구조(Single Point of Failure) 문제가 있었다.

## 설계 목표

Apache Cassandra는 다음과 같은 설계 목표를 염두에 두고 이러한 문제들을 해결하도록 설계되었다.

- 완전한 다중 기본 데이터베이스 복제
- 낮은 지연 시간으로 전 세계에서 이용 가능
- 범용 하드웨어에서 확장
- 프로세서가 추가될 때마다 처리량이 선형적으로 증가한다.
- 온라인 로드 밸런싱 및 클러스터 확장
- 분할된 키 지향 쿼리
- 유연한 스키마

# 특징

Cassandra는 SQL과 유사한 언어인 Cassandra Query Language(CQL)를 제공하여 데이터베이스 스키마를 생성, 수정 및 삭제하고 데이터에 접근할 수 있도록 한다.

## Cassandra Query Language(CQL)

CQL을 사용하면 다음과 같은 방식으로 Cassandra 노드 클러스터 내의 데이터를 구성할 수 있다.

- 키스페이스
    - 서로 다른 데이터센터 간에 데이터셋을 복제하는 전략을 지정한다.
    - 복제는 클러스터 내에 저장된 복사본의 수를 의미한다.
    - 키스페이스는 테이블을 담는 컨테이너 역할
- 테이블
    - 행과 열로 구성
    - 열은 테이블 내 단일 데이터에 대한 형식화된 스키마를 정의
    - 테이블은 파티션 키에 제공된 열을 기준으로 파티션됨
    - Cassandra 테이블은 다운타임 없이 유연하게 새 열을 추가할 수 있다.
- 파티션
    - Cassandra의 모든 행이 클러스터 내에서 행이 저장된 노드를 식별하기 위해 반드시 포함해야 하는 기본 키의 필수 부분을 정의한다.
    - 성능이 우수한 모든 쿼리는 쿼리에 파티션 키를 제공한다.
- 행
    - 파티션 키와 선택적으로 추가 클러스터링 키로 구성된 고유한 기본 키로 식별되는 열 모음을 포함한다.
- 열
    - 행에 속하는 유형을 가진 단일 데이터

## CQL이 지원하는 기능

CQL은 분할된 데이터셋에 대해 다음과 같은 다양한 고급 기능을 지원한다.

- 집합, 맵, 리스트를 포함한 Collection 유형
    - 단순한 스칼라 타입(int, text 등) 외에도 복잡한 데이터를 한 컬럼에 담을 수 있는 기능을 제공
- 사용자 정의 타입, 튜플, 함수 및 집계
- Storage-attached indexing (SAI)
    - 기존 방식보다 디스크 공간을 훨씬 적게 차지하며, 숫자 범위 검색이나 문자열 검색 성능이 뛰어나다.
- Local Secondary Indexes (2i)
    - 특정 파티션 내의 데이터에 대해 인덱스를 생성
    - 분산 환경의 특성상 너무 남용하면 여러 노드를 뒤져야 하므로 성능 저하가 올 수 있다.
- 사용자 정의 유형, 함수 및 집합체
- 원자적 비교 및 집합 의미론을 사용하는 단일 파티션 경량 트랜잭션
- Materialized Views (실체화된 뷰)
    - 원본 테이블의 데이터를 다른 정렬 기준(다른 파티션 키)으로 자동 복사해 두는 테이블

## Cassandra가 지원하지 않는 기능

Cassandra는 파티션 간 조정이 필요한 연산을 명시적으로 구현하지 않는다. 이러한 연산은 일반적으로 속도가 느리고 고가용성 전역 의미 체계를 제공하기 어렵기 때문이다.

예를 들어 Cassandra는 다음을 지원하지 않는다.

- 파티션 간 거래
- 분산 조인
- 외래 키 또는 참조 무결성

# 운영

Apache Cassandra 설정은 구성 **`cassandra.yaml`**파일에 저장되며, 이 파일은 수동으로 편집하거나 구성 관리 도구를 사용하여 편집할 수 있다.

일부 설정은 온라인 인터페이스를 통해 실시간으로 변경할 수 있지만, 다른 설정은 변경 사항을 적용하려면 데이터베이스를 재시작해야 한다.

## 클러스터 관리를 위한 CLI 도구

**`nodetool`**

- 실행 중인 카산드라 노드의 제어 인터페이스(JMX)와 통신하여 노드 상태를 관리
- 주요 기능
    - 런타임 설정 변경**:** 서비스 중단 없이 `cassandra.yaml`에 정의된 설정값 일부를 즉시 수정할 수 있다.
    - 상태 모니터링: 각 노드의 가동 여부, 데이터 용량, 컴팩션(Compaction) 진행 상태 등을 확인한다.
    - 클러스터 관리: 노드를 추가/제거하거나 데이터 복구(Repair) 명령을 내릴 때 사용한다.

**`auditlogviewer`**

- 시스템에서 발생한 보안 관련 활동을 추적하는 도구
- 카산드라의 감사 로그(Audit Log)를 사람이 읽을 수 있는 형태로 보여준다.
- 주요 기능
    - "누가, 언제, 어떤 쿼리를 실행했는가?"에 대한 기록을 확인한다.
    - 성능 저하 없이 바이너리 형태로 저장된 감사 로그를 분석하여 보안 침해 사고 조사나 규정 준수(Compliance) 확인에 활용한다.

**`fqltool`** 

- Full Query Logging(FQL) 기능을 통해 수집된 데이터를 다루는 도구
- 클러스터로 들어온 모든 쿼리 로그를 조회, 재현, 비교한다.
- 주요 기능:
    - View: 바이너리 로그 파일을 텍스트로 변환하여 확인합니다.
    - Replay: 운영 환경에서 캡처한 실제 쿼리들을 개발/스테이징 환경에서 똑같이 다시 실행해 본다. → 성능 테스트 시 매우 유용
    - Compare: 두 클러스터 간의 쿼리 결과나 성능 차이를 비교 분석한다.

또한 Cassandra는 기본적으로 원자적 스냅샷 기능을 지원하여 Cassandra 데이터의 특정 시점(PIT) 스냅샷을 생성하므로 다양한 백업 도구와 쉽게 통합할 수 있다.

Cassandra는 데이터가 기록되는 즉시 백업되는 증분 백업도 지원한다.
