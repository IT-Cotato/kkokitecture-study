<!--StartFragment--><h1>6장. 키-값 저장소 설계</h1>
<h1>키-값 저장소</h1>
<ul>
<li>비 관계형 데이터베이스</li>
<li>저장되는 값은 고유 식별자를 키로 가져야 한다.</li>
<li>키와 값 사이의 연결관계를 키-값 쌍이라고 한다.</li>
<li>키는 유일해야 하며, 해당 키에 매달린 값은 키를 통해서만 접근할 수 있다.
<ul>
<li>키는 일반 텍스트 or 해시 값
<ul>
<li>“last_logged_in_at”, 253DDEC4</li>
</ul>
</li>
<li>키는 짧을수록 좋다.</li>
</ul>
</li>
<li>값은 문자열 or 리스트 or 객체</li>
<li>아마존 다이나모, memcached, 레디스 등</li>
</ul>
<h1>문제 이해 및 설계 범위 확정</h1>
<ul>
<li>키-값 쌍의 크기는 10KB 이하이다.</li>
<li>큰 데이터를 저장할 수 있어야 한다.</li>
<li>높은 가용성을 제공해야 한다. → 시스템은 장애가 있더라도 빨리 응답</li>
<li>높은 규모 확장성을 제공해야 한다. → 트래픽 양에 따라 자동적으로 서버 증설/삭제</li>
<li>데이터 일관성 수준은 조정 가능해야 한다.</li>
<li>응답 지연시간(latency)이 짧아야 한다.</li>
</ul>
<h1>단일 서버 키-값 저장소</h1>
<p>한 대 서버만 사용하는 키-값 저장소를 설계하는 것은 쉽다.</p>
<p>가장 직관적인 방법은 키-값 쌍 전부를 메모리에 해시테이블로 저장하는 것이다.</p>
<p>단점</p>
<ul>
<li>모든 데이터를 메모리 안에 두는 것이 불가능할 수도 있다.</li>
</ul>
<p>개선책</p>
<ul>
<li>데이터 압축</li>
<li>자주 쓰이는 데이터만 메모리에 두고 나머지는 디스크에 저장</li>
</ul>
<p>그러나 한 대 서버로 부족한 때가 찾아오므로 많은 데이터를 저장하려면 분산 키-값 저장소를 만들 필요가 있다.</p>
<h1>분산 키-값 저장소</h1>
<h2>CAP 정리</h2>
<p>데이터 일관성(consistency), 가용성(availability), 파티션 감내(partition tolerance)를 동시에 만족하는 분산 시스템을 설계하는 것은 불가능하다는 정리다.</p>
<ul>
<li>데이터 일관성(consistency)
<ul>
<li>분산 시스템에 접속하는 모든 클라이언트는 어떤 노드에 접속했는지에 관계없이 언제나 같은 데이터를 보게 되어야 한다.</li>
</ul>
</li>
<li>가용성(availability)
<ul>
<li>분산 시스템에 접속하는 클라이언트는 일부 노드에 장애가 발생하더라도 항상 응답을 받을 수 있어야 한다.</li>
</ul>
</li>
<li>파티션 감내(partition tolerance)
<ul>
<li>파티션 : 두 노드 사이에 통신 장애가 발생하였음</li>
<li>네트워크에 파티션이 생기더라도 시스템은 계속 동작해야 한다.</li>
</ul>
</li>
</ul>
<p>CAP 정리는 이 요구사항 중 두 가지를 충족하려면 나머지 하나는 반드시 희생되어야 한다는 것을 의미한다.</p>
<p>

<img width="1004" height="851" alt="Image" src="https://github.com/user-attachments/assets/cc47fca3-dfda-466a-bacd-02a5bf9dd6e9" />

</p>
<p>키-값 저장소는 어느 두 가지 요구사항을 만족하느냐에 따라 다음과 같이 분류한다.</p>
<ul>
<li>CP 시스템
<ul>
<li>일관성, 파티션 감내 지원</li>
<li>가용성 희생</li>
</ul>
</li>
<li>AP 시스템
<ul>
<li>가용성, 파티션 감내 지원</li>
<li>데이터 일관성 희생</li>
</ul>
</li>
<li>CA 시스템
<ul>
<li>일관성, 가용성 지원</li>
<li>파티션 감내 희생
<ul>
<li>그러나 네트워크 장애는 피할 수 없는 일로 여겨지므로, 분산 시스템은 반드시 파티션 문제를 감내할 수 있도록 설계되어야 한다. → 실세계에서 CA 시스템은 존재하지 않는다.</li>
</ul>
</li>
</ul>
</li>
</ul>
<h3>세 대의 복제 노드 n1, n2, n3에 데이터를 복제해 보관하는 상황</h3>
<p>이상적 상태</p>
<ul>
<li>네트워크가 파티션되는 상황은 일어나지 않는다.</li>
<li>n1에 기록된 데이터는 자동적으로 n2, n3에 복제된다.</li>
</ul>
<p>

<img width="1046" height="832" alt="Image" src="https://github.com/user-attachments/assets/4839e207-fb9c-43b3-9a9b-ca7f0c1fa77c" />

</p>
<p>실세계의 분산 시스템</p>
<ul>
<li>분산 시스템은 파티션 문제를 피할 수 없다.
<ul>
<li>파티션 문제가 발생하면 일관성과 가용성 사이에서 하나를 선택해야 한다.</li>
</ul>
</li>
</ul>
<p>

<img width="956" height="873" alt="Image" src="https://github.com/user-attachments/assets/d5874514-d43f-4055-a8c4-9046304f3e0f" />

</p>
<ul>
<li>클라이언트가 n1 또는 n2에 기록한 데이터는 n3에 전달되지 않는다.</li>
<li>n3에 기록되었으나 아직 n1, n2로 전달되지 않은 데이터가 있다면 n1, n2는 오래된 사본을 갖고 있을 것이다.</li>
<li>가용성 대신 일관성을 선택한다면(CP 시스템) 세 서버 사이에 생길 수 있는 데이터 불일치 문제를 피하기 위해 n1, n2에 대해 쓰기 연산을 중단시켜야 한다
<ul>
<li>가용성이 깨진다.</li>
<li>은행권 시스템은 보통 데이터 일관성을 양보하지 않는다.
<ul>
<li>ex) 온라인 뱅킹 시스템이 계좌 최신 정보를 출력하지 못한다면 큰 문제</li>
<li>네트워크 파티션 때문에 일관성이 깨질 수 있는 상황이 발생하면 이런 시스템은 상황이 해결될 때까지 오류를 반환해야 한다.</li>
</ul>
</li>
</ul>
</li>
<li>일관성 대신 가용성을 선택한다면(AP 시스템)은 낡은 데이터를 반환할 위험이 있더라도 계속 읽기 연산을 허용해야 한다.
<ul>
<li>n1, n2는 계속 쓰기 연산 허용</li>
<li>파티션 문제가 해결된 뒤에 새 데이터를 n3에 전송</li>
</ul>
</li>
</ul>
<h2>시스템 컴포넌트</h2>
<ul>
<li>데이터 파티션</li>
<li>데이터 다중화(replication)</li>
<li>일관성(consistency)</li>
<li>일관성 불일치 해소(inconsistency resolution)</li>
<li>장애 처리</li>
<li>시스템 아키텍처 다이어그램</li>
<li>쓰기 경로(write path)</li>
<li>읽기 경로(read path)</li>
</ul>
<h2>데이터 파티션</h2>
<p>고려해야 할 부분</p>
<ul>
<li>데이터를 여러 서버에 고르게 분산할 수 있는가</li>
<li>노드가 추가되거나 삭제될 때 데이터의 이동을 최소화할 수 있는가</li>
</ul>
<p>→ 안정 해시는 이 문제를 푸는데 적합한 기술이다.</p>
<p>안정 해시를 사용해 데이터를 파티션하면 좋은 점</p>
<ul>
<li>규모 확장 자동화(automatic scaling): 시스템 부하에 따라 서버가 자동으로 추가/삭제되도록 만들 수 있다.</li>
<li>다양성(heterogeneity): 각 서버의 용량에 맞게 가상 노드의 수를 조정할 수 있다.
<ul>
<li>고성능 서버는 더 많은 가상 노드를 갖도록 설정</li>
</ul>
</li>
</ul>
<h2>데이터 다중화</h2>
<p>높은 가용성과 안정성을 확보하기 위해서는 데이터를 N개의 서버에 비동기적으로 다중화(replication)할 필요가 있다.</p>
<ul>
<li>N은 튜닝 가능한 값</li>
</ul>
<p>N개의 서버를 선정하는 방법</p>
<ul>
<li>어떤 키를 해시 링 위에 배치, 그 지점으로부터 시계 방향으로 순회하며 만나는 첫 N개의 서버에 데이터 사본을 보관한다.</li>
</ul>
<p>

<img width="1112" height="1136" alt="Image" src="https://github.com/user-attachments/assets/ed551515-0071-42f2-83c7-49fafafd07b9" />

</p>
<p>N=3일 때, key0은 s1, s2, s3에 저장된다.</p>
<p>가상 노드를 사용한다면 위와 같이 선택한 N개의 노드가 대응될 실제 물리 서버 개수가 N보다 작아질 수 있다.</p>
<ul>
<li>
<p>노드를 선택할 때 같은 물리 서버를 중복 선택하지 않도록 해야 한다.</p>
</li>
<li>
<p>같은 데이터 센터에 속한 노드는 정전, 네트워크 이슈 등의 문제를 동시에 겪을 수 있다.</p>
<p>⇒ 데이터의 사본은 다른 센터의 서버에 보관하고, 센터들은 고속 네트워크로 연결한다.</p>
</li>
</ul>
<h2>데이터 일관성</h2>
<p>여러 노드에 다중화된 데이터는 적절히 동기화가 되어야 한다.</p>
<p>정족수 합의 프로토콜을 사용하면 읽기/쓰기 연산 모두에 일관성을 보장할 수 있다.</p>
<ul>
<li>N = 사본 개수</li>
<li>W = 쓰기 연산에 대한 정족수
<ul>
<li>쓰기 연산이 성공한 것으로 간주되려면 적어도 W개의 서버로부터 쓰기 연산이 성공했다는 응답을 받아야 한다.</li>
</ul>
</li>
<li>R = 읽기 연산에 대한 정족수
<ul>
<li>읽기 연산이 성공한 것으로 간주되려면 적어도 R개의 서버로부터 응답을 받아야 한다.</li>
</ul>
</li>
</ul>
<p>

<img width="879" height="821" alt="Image" src="https://github.com/user-attachments/assets/3b4fdbd4-3666-4558-9b31-ab5015e87973" />

</p>
<p>W = 1의 의미는 쓰기 연산이 성공했다고 판단하기 위해 중재자는 최소 한 대 서버로부터 쓰기 성공 응답을 받아야 한다는 뜻이다.</p>
<ul>
<li>s1으로부터 응답을 받았다면, s0, s2로부터의 응답은 기다릴 필요가 없다.</li>
<li>중재자는 클라이언트와 노드 사이에서 프락시(proxy) 역할을 한다.</li>
</ul>
<p>W, R, N의 값을 정하는 것은 응답 지연과 데이터 일관성 사이의 타협점을 찾는 전형적인 과정이다.</p>
<ul>
<li>W = 1 또는 R = 1인 구성
<ul>
<li>중재자는 한 대 서버로부터의 응답만 받으면 되므로 응답속도는 빠를 것이다.</li>
</ul>
</li>
<li>W나 R이 1보다 큰 경우
<ul>
<li>시스템의 데이터 일관성 수준은 향상되지만 중재자의 응답 속도는 가장 느린 서버로부터의 응답을 기다려야 하므로 느려진다.</li>
</ul>
</li>
<li>W + R &gt; N
<ul>
<li>강한 일관성이 보장된다.</li>
<li>일관성을 보증할 최신 데이터를 가진 노드가 최소 하나는 겹칠 것이기 때문이다.</li>
</ul>
</li>
</ul>
<p><strong>N, W, R 값을 어떻게 정해야 할까</strong></p>
<ul>
<li>R = 1, W = N: 빠른 읽기 연산에 최적화</li>
<li>W = 1, R = N: 빠른 쓰기 연산에 최적화</li>
<li>W+R&gt;N: 강한 일관성 보장(보통 N = 3, W=R=2)</li>
<li>W+R≤N: 강한 일관성 보장 X</li>
</ul>
<h2>일관성 모델</h2>
<ul>
<li>강한 일관성
<ul>
<li>모든 읽기 연산은 가장 최근에 갱신된 결과를 반환한다. → 클라이언트는 절대로 낡은 데이터를 보지 못한다.</li>
<li>모든 사본에 현재 쓰기 연산의 결과가 반영될 때까지 해당 데이터에 대한 읽기/쓰기를 금지하는 것</li>
<li>고가용성 시스템에 적합 X → 새로운 요청의 처리가 중단되기 때문</li>
</ul>
</li>
<li>약한 일관성
<ul>
<li>읽기 연산은 가장 최근에 갱신된 결과를 반환하지 못할 수 있다.</li>
</ul>
</li>
<li>결과적 일관성
<ul>
<li>약한 일관성의 한 형태로, 갱신 결과가 결국에는 모든 사본에 반영(즉, 동기화)되는 모델이다.</li>
<li>쓰기 연산이 병렬적으로 발생하면 시스템에 저장된 값의 일관성이 깨질 수 있는데, 이 문제는 클라이언트가 해결해야 한다.</li>
<li>다이나모, 카산드라</li>
</ul>
</li>
</ul>
<h2>비 일관성 해소 기법: 데이터 버저닝</h2>
<p>데이터를 다중화하면 가용성은 높아지지만 사본 간 일관성이 깨질 가능성은 높아진다.</p>
<p>버저닝(versioning)과 벡터 시계(vector clock)는 그 문제를 해소하기 위해 등장한 기술이다.</p>
<p>버저닝은 데이터를 변경할 때마다 해당 데이터의 새로운 버전을 만드는 것이다.</p>
<ul>
<li>따라서 각 버전의 데이터는 변경 불가능</li>
</ul>
<p>데이터의 일관성이 깨지는 과정</p>

</p>
<ul>
<li>데이터의 사본이 n1, n2에 보관
<ul>
<li>서버 1, 서버 2는 get(”name”) 연산의 결과로 같은 값을 얻는다.</li>
</ul>
</li>
</ul>
<p>

<img width="1048" height="551" alt="Image" src="https://github.com/user-attachments/assets/39ee35bf-2e9b-44aa-948b-4a8403ef3b7b" />

<ul>
<li>서버 1은 “name”에 매달린 값을 다른 값으로 바꾸고, 서버 2도 다른 값으로 바꾸는 경우
<ul>
<li>각각을 v1, v2라고 하자.</li>
</ul>
</li>
</ul>
<p>v1, v2 사이의 충돌을 해결하려면 충돌을 발견하고 자동으로 해결해 낼 버저닝 시스템이 필요하다.</p>
<h3><strong>벡터 시계</strong></h3>
<ul>
<li>[서버, 버전]의 순서쌍을 데이터에 매단 것</li>
<li>어떤 버전이 신행, 후행 버전인지, 다른 버전과 충돌이 있는지 판별하는데 쓰인다.</li>
<li>D([S1, v1], [S2, v2], …, [Sn, vn])
<ul>
<li>D: 데이터, vi: 버전 카운터, Si: 서버 번호</li>
</ul>
</li>
<li>데이터 D를 서버 Si에 기록하면 시스템은 아래 작업 중 하나를 수행해야 한다.
<ul>
<li>[Si, vi]가 있으면 vi를 증가시킨다.</li>
<li>그렇지 않으면 새 항목[Si, 1]을 만든다.</li>
</ul>
</li>
</ul>
<p>

<img width="1113" height="1143" alt="Image" src="https://github.com/user-attachments/assets/8599b069-ac9c-43dc-b3a2-3ef125a8865d" />

</p>
<ol>
<li>클라이언트가 D1을 시스템에 기록
<ul>
<li>벡터 시계는 D1[(Sx, 1)]</li>
</ul>
</li>
<li>다른 클라이언트가 D1을 읽고 D2로 업데이트한 다음 기록
<ul>
<li>쓰기 연산은 같은 서버 Sx가 처리한다고 가정</li>
<li>백터 시계는 D2[(Sx, 2)]</li>
</ul>
</li>
<li>다른 클라이언트가 D2를 읽어 D3로 갱신한 다음 기록
<ul>
<li>쓰기 연산은 Sy가 처리한다고 가정</li>
<li>백터 시계는 D3[(Sx, 2), (Sy, 1)]</li>
</ul>
</li>
<li>또 다른 클라이언트가 D2를 읽고 D4로 갱신한 다음 기록
<ul>
<li>쓰기 연산은 Sz가 처리한다고 가정</li>
<li>백터 시계는 D4[(Sx, 2), (Sz, 1)]</li>
</ul>
</li>
<li>어떤 클라이언트가 D3, D4를 읽으면 데이터 간 충돌이 있다는 것을 알게 된다.
<ul>
<li>D2를 Sy, Sz가 각기 다른 값을 바꿨기 때문</li>
<li>이 충돌은 클라이언트가 해소한 후 서버에 기록한다.</li>
<li>쓰기 연산을 처리한 서버는 Sx였다고 가정</li>
<li>벡터 시계는 D5[(Sx, 3), (Sy, 1), (Sz, 1)]</li>
</ul>
</li>
</ol>
<p>벡터 시계를 사용하면 어떤 버전 X가 버전 Y의 이전 버전인지 쉽게 판단할 수 있다.
버전 Y에 포함된 모든 구성요소의 값이 X에 포함된 모든 구성요소 값보다 같거나 큰지만 보면 된다.</p>
<ul>
<li>ex) D[(s0, 1), [s1, 1])은 D[(s0, 1), [s1, 2])의 이전 버전 → 두 데이터 사이의 충돌은 없음</li>
</ul>
<h3><strong>벡터 시계의 단점</strong></h3>
<ul>
<li>충돌 감지 및 해소 로직이 클라이언트에 들어가야 하므로 클라이언트 구현이 복잡해진다.</li>
<li>[서버:버전]의 순서쌍 개수가 굉장히 빨리 늘어난다.
<ul>
<li>해결하려면 그 길이에 어떤 임계치를 설정하고, 임계치 이상으로 길어지만 오래된 순서쌍을 벡터 시계에서 제거하도록 해야 한다.
<ul>
<li>이렇게 하면 버전 간 선후 관계가 정확하게 결정될 수 없으므로 충돌 해소 과정의 효율성이 낮아진다.</li>
</ul>
</li>
<li>실제 서비스에서는 이런 문제가 나타나는 것을 발견한 적 없으므로 대부분의 기업에서는 벡터 시계를 적용해도 괜찮다.</li>
</ul>
</li>
</ul>
<h2>장애 감지</h2>
<p>분산 시스템에서는 한 대 서버가 서버 A가 죽었다고 한다고 해서 바로 서버 A를 장애처리 하지는 않는다.</p>
<p>두 대 이상의 서버가 똑같이 서버 A의 장애를 보고해야 해당 서버에 실제로 장애가 발생했다고 간주한다.</p>
<ul>
<li>모든 노드 사이에 멀티캐스팅 채널을 구축하는 방법
<ul>
<li>서버가 많을 때 비효율적</li>
</ul>
</li>
</ul>
<h3>가십 프로토콜 같은 분산형 장애 감지 솔루션을 채택하는 방법</h3>
<p>가십 프로토콜의 동작 원리</p>
<ul>
<li>각 노드는 멤버십 목록 유지
<ul>
<li>멤버십 목록은 각 멤버 ID와 그 박동 카운터 쌍의 목록</li>
</ul>
</li>
<li>각 노드는 주기적으로 자신의 박동 카운터를 증가시킴</li>
<li>각 노드는 무작위로 선정된 노드들에게 주기적으로 자기 박동 카운터 목록을 보냄</li>
<li>박동 카운터 목록을 받은 노드는 멤버십 목록을 최신 값으로 갱신</li>
<li>어떤 멤버의 박동 카운터 값이 지정된 시간 동안 갱신되지 않으면 해당 멤버는 장애(offline) 상태로 간주</li>
</ul>
<p>

<img width="1328" height="523" alt="Image" src="https://github.com/user-attachments/assets/ca4763e5-7705-493a-bd5d-d48afe5bed34" />

</p>
<h2>일시적 장애 처리</h2>
<p>가십 프로토콜로 장애를 감지한 시스템은 가용성을 보장하기 위해 필요한 조치를 해야 한다.</p>
<p>느슨한 정족수(sloppy quorum) 접근법</p>
<ul>
<li>정족수 요구사항을 강제하는 대신, 쓰기 연산을 수행할 W개의 건강한 서버와 읽기 연산을 수행할 R개의 건강한 서버를 해시 링에서 고른다.</li>
</ul>
<p>단서 후 임시 위탁 기법</p>
<ul>
<li>네트워크나 서버 문제로 장애 상태인 서버로 가는 요청은 다른 서버가 잠시 맡아 처리한다.</li>
<li>그동안 발생한 변경사항은 해당 서버가 복구되었을 때 일괄 반영해 데이터 일관성을 보존한다.</li>
<li>임시로 쓰기 연산을 처리한 서버에는 그에 관한 단서를 남겨둔다.</li>
</ul>
<h2>영구 장애 처리</h2>
<p>반-엔트로피 프로토콜을 구현해 사본들을 동기화</p>
<ul>
<li>반-엔트로피 프로토콜은 사본들을 비교해 최신 버전으로 갱신하는 과정을 포함한다.</li>
<li>사본 간의 일관성이 망가진 상태를 탐지하고 전송 데이터의 양을 줄이기 위해서는 머클 트리를 사용할 것이다.</li>
</ul>
<p>머클 트리 = 해시 트리</p>
<ul>
<li>각 노드에 그 자식 노드들에 보관된 값의 해시, 또는 자식 노드들의 레이블로부터 계산된 해시값을 레이블로 붙여주는 트리</li>
<li>해시 트리를 사용하면 대규모 자료 구조의 내용을 효과적이면서 보안상 안전한 방법으로 검증 가능</li>
</ul>
<h3>키 공간이 1부터 12까지일 때 머클 트리를 만드는 예제</h3>
<ol>
<li>키 공간을 4개의 버킷으로 나눈다.</li>
</ol>
<p>

<img width="1240" height="472" alt="Image" src="https://github.com/user-attachments/assets/42473f9f-b122-4448-bece-d5621200b057" />

</p>
<ol>
<li>버킷에 포함된 각각의 키에 균등 분포 해시 함수를 적용해 해시 값을 계산한다.</li>
</ol>
<p>

<img width="1241" height="278" alt="Image" src="https://github.com/user-attachments/assets/9756ae6a-1faf-44d9-8799-908156adff15" />

</p>
<ol>
<li>버킷별로 해시값을 계산한 후, 해당 해시 값을 레이블로 갖는 노드를 만든다.</li>
</ol>
<p>

<img width="1276" height="372" alt="Image" src="https://github.com/user-attachments/assets/c596ca91-ac7a-4db0-a063-45b1e5680481" />

</p>
<ol>
<li>자식 노드의 레이블로부터 새로운 해시 값을 계산하여, 이진 트리를 상향식으로 구성해 나간다.</li>
</ol>
<p>

<img width="1248" height="657" alt="Image" src="https://github.com/user-attachments/assets/27b80c2c-2a61-4a48-90ff-f1eb931f0813" />

</p>
<p>이 두 머클 트리의 비교는 루트 노드의 해시값을 비교하는 것으로 시작한다.</p>
<ul>
<li>루트 노드의 해시 값이 일치하면 두 서버는 같은 데이터를 갖는 것</li>
</ul>
<p>값이 다른 경우에는 왼쪽 자식 노드이 해시 값을 비교한 후 오른쪽 자식 노드의 해시 값을 비교한다.</p>
<p>아래쪽으로 탐색해 나가면 다른 데이터를 갖는 버킷을 찾을 수 있으므로 그 버킷들만 동기화하면 된다.</p>
<p>머클 트리를 사용하면 동기화해야 하는 데이터의 양은 실제로 존재하는 차이의 크기에 비례할 뿐, 두 서버에 보관된 데이터의 총량과는 무관해진다.</p>
<ul>
<li>실제로 쓰이는 시스템의 경우 버킷 하나의 크기가 꽤 크다</li>
<li>10억(1B) 개의 키를 백만(1M) 개의 버킷으로 관리하는 경우 하나의 버킷은 1,000개 키를 관리하게 된다.</li>
</ul>
<h2>데이터 센터 장애 처리</h2>
<p>데이터 센터 장애에 대응할 수 있는 시스템을 만드려면 데이터를 여러 데이터 센터에 다중화하는 것이 중요하다.</p>
<h2>시스템 아키텍처 다이어그램</h2>
<p>아키텍처의 주된 기능</p>
<ul>
<li>클라이언트는 키-값 저장소가 제공하는 두 가지 단순한 API, 즉 get(key) 및 put(key, value)와 통신한다.</li>
<li>중재자는 클라이언트에게 키-값 저장소에 대한 프락시(proxy) 역할을 하는 노드다.</li>
<li>노드는 안정 해시의 해시 링 위에 분포한다.</li>
</ul>
<p>

<img width="1254" height="753" alt="Image" src="https://github.com/user-attachments/assets/59d0435d-1085-4907-9564-c2b7ca9b572d" />

</p>
<ul>
<li>노드를 자동으로 추가 또는 삭제할 수 있도록, 시스템은 완전히 분산된다.</li>
<li>데이터는 여러 노드에 다중화된다.</li>
<li>모든 노드가 같은 책임을 지므로, SPOF는 존재하지 않는다.</li>

<h2>쓰기 경로</h2>
<p>쓰기 요청이 특정 노드에 전달되면 발생하는 일</p>
<p>

<img width="1314" height="654" alt="Image" src="https://github.com/user-attachments/assets/9b2199ad-8c4a-461f-a0f4-3cdbab373d9d" />

<ol>
<li>쓰기 요청이 커밋 로그 파일에 기록</li>
<li>데이터가 메모리 캐시에 기록</li>
<li>메모리 캐시가 가득차거나 사전 정의된 임계치에 도달하면 데이터는 디스크에 있는 SSTable에 기록된다.
<ul>
<li>SSTable : Sorted-String Table, &lt;키, 값&gt; 순서쌍을 정렬된 리스트 형태로 관리하는 테이블</li>
</ul>
</li>
</ol>
<h2>읽기 경로</h2>
<p>읽기 요청을 받은 노드는 데이터가 메모리 캐시에 있는지부터 살핀다.</p>
<p>있는 경우 해당 데이터를 클라이언트에 반환한다.</p>
<p>

<img width="1243" height="643" alt="Image" src="https://github.com/user-attachments/assets/2ae066c8-722f-4a08-9041-c0e3e3e4e3bf" />

<p>없는 경우 디스크에 가져와야 한다.</p>
<ul>
<li>어느 SSTable에 찾는 키가 있는지 알아낼 효율적인 방법이 필요하다.
<ul>
<li>블룸 필터(Bloom filter)가 흔히 사용된다.</li>
</ul>
</li>
</ul>
