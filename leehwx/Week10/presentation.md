# 24시간 만에 10억 웹페이지를 크롤링한 대규모 크롤러 구축기
> 출처: https://andrewkchan.dev/posts/crawler.html
> 

# 문제 정의

- 24시간 내에 10억 웹페이지 크롤링이라는 목표 설정
- 예산은 몇백 달러(최종 약 462달러)로, 2012년 사례와 비슷한 수준에 맞춤
- HTML만 수집하며, 자바스크립트는 실행하지 않고 `<a>` 링크만 추출
- 예의 있는 크롤러
    - robots.txt 준수, User Agent 정보 포함, 요청시 도메인 제외
    - 인기 상위 100만 도메인만 대상, 같은 도메인에 70초 대기 등 적용
- 내결함성 확보: 노드 장애 시 재시작 및 일부 데이터 유실을 감안, 샘플 기반 접근

# 설계

기존 시스템 설계 면접 설계(기능별 분산)와 달리, 각 노드가 모든 기능(크롤 상태, 파싱, 페치, 저장 등) 자체적으로 처리하는 구조를 선택했다.

- 제한된 예산이기 때문에 작은 규모로 시작해 많은 것을 하나의 기계에 담아내 다음, 확장해 나가는 것이 합리적이라고 생각했다.

## 노드의 구성 요소

12개 노드, 각 노드는 `i7i.4xlarge`(16 vCPU, 128GB RAM, 10Gbps, 3750GB 스토리지) 인스턴스 사용

**단일 Redis 인스턴스**

- 크롤링 상태를 나타내는 데이터 구조 저장
- 도메인별 크롤링 범위 or 크롤링할 URL 목록
- 크롤링 지연 시간을 기준으로 다음 검색 가능 시점에 따라 정렬된 도메인 대기열
- 방문한 모든 URL에 대한 항목이 표시되며 , 각 URL에는 메타데이터와 저장된 콘텐츠의 경로가 연결
- URL 블룸 필터 사용 → URL이 이미 프론티어에 추가되었는지 여부 확인
- 도메인 메타데이터:  도메인이 수동으로 제외되었는지 여부, 원래 시드 목록에 포함되었는지 여부, robots.txt의 전체 내용 포함
- 파싱 큐

**수집기 프로세스 풀 (Pool of fetcher processes)**

- fetcher는 루프 방식으로 동작
    - 레디스에서 다음으로 준비된 도메인을 꺼내고, 그 다음 프론티어에서 다음 URL을 꺼내 가져온 후 결과를 파싱 큐에 추가
- 각 프로세스는 asyncio를 통해 높은 동시성
- 주 병목은 CPU에서 발생
- fetcher, parser 모두 robots.txt 내용과 같은 중요한 도메인 데이터에 대해 LRU 캐시를 유지하여 Redis 부하 최소화

**파서 프로세스 풀**

- 각 파서는 80개의 비동기 워커로 구성되어 파싱 큐에서 다음 항목을 가져와 HTML 콘텐츠를 파싱
    
    → 링크를 추출하여 Redis의 해당 도메인 경계에 기록 → 저장된 콘텐츠를 영구 저장소에 기록
    
- 파싱 작업이 CPU에 의존했기 때문에 동시 실행률이 낮았음

**스토리지**

- S3 대신 인스턴스 로컬 스토리지 선택, 대용량 페이지 저장 비용 절감

**샤딩**

- 도메인별로 노드에 분배(크로스 커뮤니케이션 없음)
- 인기 도메인 불균형 문제 해결 위해 샤딩 노드 수 조정

# 주요 대안

SQLite, PostgreSQL 등 다양한 저장소 실험해보았으나, 최종적으로 Redis가 성능이 우수했다.

수직적 확장(단일 대형 인스턴스)도 시도했으나 소프트웨어 한계로 병목이 발생했고, 결국 수평 확장(여러 노드) 구조로 결정했다.

각 노드 간 크로스 커뮤니케이션 제거하고 단일 노드 내에서 병렬 처리하도록 설계했다.

# 교훈

### **파싱이 가장 큰 병목**

- 평균 페이지 크기가 과거(2012년 51KB)보다 훨씬 커짐(평균 242KB, 중앙값 138KB)
- lxml 대신 selectolax(Lexbor 기반) 로 변경 시 파싱 속도 대폭 향상
- 페이지 콘텐츠를 파서에 전달하기 전에 250KB로 줄여 효율 개선

결과적으로, 단일 parser에서 초당 160페이지 파싱을 할 수 있었고, 최종적으로 fetcher:parser 비율을 9:6으로 조정해 약 950페이지/초 처리할 수 있었다.

### **Fetching: 쉬워진 점과 어려워진 점**

- 네트워크 대역폭은 오히려 병목이 아님(노드당 25Gbps 중 8Gbps 정도만 사용)
- **DNS** 병목도 인기 도메인만 대상으로 하여 문제되지 않음
- 반면, SSL 핸드셰이크가 전체 CPU 사용의 25%로 최대 병목 중 하나로 등장
- 대부분의 페이지가 HTTPS로 전환됨에 따라, CPU 비용이 증가함

### **실전 크롤 실행 및 문제**

- 초기 실험에서는 단일 노드(`i7i.2xlarge`)로 수 시간만 진행하다가, 본 크롤은 12노드로 확장
- 메모리 문제 발생: 인기 도메인의 프론티어(미방문 URL)가 수십 GB까지 증가해, 노드가 다운되는 현상 반복
- 인기 도메인(예: [yahoo.com](http://yahoo.com/), [wikipedia.org](http://wikipedia.org/)) 또는 비정상적으로 링크가 많은 사이트들이 문제를 일으킴

문제 도메인은 수동으로 제외하고, 장애 발생 시 노드 재시작 및 프론티어 트렁케이션으로 복구했다.

> 프론티어 트렁케이션 : 크롤러가 앞으로 방문해야 할 URL 대기열(Frontier)에 너무 많은 데이터가 쌓여 시스템이 뻗었을 때, 처리가 밀려있는 뒷부분의 URL 목록을 과감하게 잘라내어 날려버리는 조치
→ 메모리 부족이나 락(Lock) 현상으로 멈춘 시스템을 정상 상태로 빠르게 되살리기 위함
> 

### **이론과 실전 비교**

- 기존 교과서적인 방법인 "5대 머신으로 5일에 100억 페이지" 추정과 비교, 실제 수치는 어느 정도 근접함
- 각 노드의 실제 네트워크 및 CPU 활용률을 감안하면, 최적화 여부에 따라 더 높은 처리량도 가능함

### 향후 과제

- HTML 파싱만으로도 상당수 웹페이지에 접근 가능함을 재확인, 단 대형 플랫폼(예: GitHub 등)은 의미 있는 본문이 JS 내 포함되어 파싱 불가
- 미래 과제로 JS 렌더링 기반 대규모 크롤링 비용 및 방식 탐구가 필요
- 데이터 분석(실제 수집된 페이지의 메타 정보, 활성/비활성 비율 등)도 후속 주제로 언급
- 최근에는 AI와 결합한 공격적 크롤링이 늘어나고 있으며, Cloudflare의 pay-per-crawl 등 신규 방어 체계가 등장하는 등 웹 크롤링 환경이 다시 변화 중임
