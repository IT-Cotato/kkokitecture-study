# **Bitly: 월 60억 클릭을 처리하는 분산 시스템 구축을 통해 얻은 교훈**

> 출처: https://highscalability.com/bitly-lessons-learned-building-a-distributed-system-that-han/

# 개요

Bitly는 URL 단축 서비스 자체로 수익을 창출하는 것이 아니라, 웹에서 수집한 데이터와 URL 클릭 데이터를 결합하여 고객이 웹에서 사람들이 무엇에 관심을 기울이는지 파악하도록 돕는 분석 제품으로 수익을 창출한다.

분석 제품은 웹 서버 로그를 크롤링하는 백엔드 서비스로 시작되었다. 로그에는 주석이 달린 링크 데이터와 쿠키 데이터가 포함되어 있어 페이지의 어느 위치에서 링크를 클릭했는지, 누가 클릭했는지, 링크의 내용은 무엇인지 등을 알 수 있었다.

그러나 모든 링크는 웹사이트의 도메인으로 연결되었다. 링크를 자신의 도메인이 아닌 다른 도메인으로 연결하여 제3자가 분석을 수행할 수 있도록 하는 아이디어는 다소 불안하게 느껴질 수 있지만, 동시에 훌륭한 발상이기도 하다.

# 분산 시스템의 본질

## **추상화에 대한 패러다임의 변화**

- 기존 접근 방식: 시스템이 실제로는 분산되어 있음에도 불구하고, 마치 분산되어 있지 않은 단일 시스템처럼 보이도록 복잡한 추상화 계층을 만드는 방식
    - ex) 무한한 디스크가 있는 것처럼 착각을 주는 NetApp 시스템
    - 현실의 분산 복잡도를 감추고 고가용성을 제공하는 Oracle 데이터베이스
- 새로운 접근 방식: 분산 시스템이 가진 고유한 한계와 특성을 그대로 받아들이고, 이를 시스템 설계와 추상화 도구에 명확히 반영하는 방식
    - 효과: 추상적 개념이 실제 물리적 구현과 밀접하게 연관되므로, 현실적이고 효과적인 절충안을 마련할 수 있어 비용과 운영 효율성이 극대화

## 분산 시스템의 문제

**구성 요소의 동시성 (Concurrency)**

- 여러 머신이 동시에 작업을 수행하므로 수평 확장이 가능해지지만, 반대로 머신 간의 정렬과 조정을 위한 비용이 발생
- 데이터를 잠그거나(Locking) 동기화를 위해 서로를 기다리게 만드는 순간 분산 시스템의 장점인 동시성은 상실됨

**글로벌 시계의 부재 (No Global Clock)**

- 분산된 각 기기는 저마다 불완전한 고유의 시계를 가짐
- 따라서 여러 대의 기기에서 일어난 이벤트를 완벽한 시간 순서대로 정렬하는 것은 불가능
- 이벤트 발생 간격이 수 초 이내라면 어떤 이벤트가 절대적으로 먼저 일어났는지 확정할 수 없음

**독립적인 고장 판정 (Independent Failures)**

- 전체 시스템의 중단을 막기 위해 특정 장비(A)가 고장 나더라도 다른 장비(B)는 영향을 받지 않고 계속 독립적으로 작동할 수 있어야 함

# 분산 시스템 구현 전략

## **서비스 지향 아키텍처**

Bitly는 거대한 단일 애플리케이션 대신 네트워크를 통해 통신하는 수십 개의 작은 서비스로 시스템을 쪼개어 구성한다.

**시스템 수준의 추상화**

- 코드 레벨에서 함수를 만들어 복잡성을 숨기듯, 시스템 레벨에서 서비스를 독립된 컴포넌트로 분리
- 개발자는 전체 시스템의 세부 사항을 알 필요 없이 API 경계와 데이터 계약에만 집중하면 됨

**개발 및 운영의 효율성**

- 잘 설계된 서비스는 단 몇백 줄의 코드로도 구현이 가능하므로 유지보수가 쉬움
- 장애가 발생했을 때도 어떤 서비스에 문제가 생겼는지 빠르게 파악하여 디버깅할 수 있음

**장애 격리와 단계적 기능 저하 (Degradation)**

- 각 서비스는 자체적인 영구 저장소를 가지며 철저히 격리
- 특정 서비스에 장애가 발생하더라도 전체 시스템이 셧다운되지 않고, 해당 서비스가 담당하는 기능만 제한
    - ex) 통신/메트릭 시스템에 장애가 발생해 통신 데이터 수집이 멈추더라도, 핵심 기능인 URL 단축 요청 서비스는 아무런 영향을 받지 않고 정상 작동

## 비동기 메시징

비동기 메시징은 송신자가 수신자의 응답을 즉각적으로 기다리지 않고 메시지를 전송하는 방식이다.

### 비동기 메시징의 특징

- 장애 내성 및 결함 격리
    - 구성 요소 사이에 큐(Queue)를 추가하여 의존성을 제거
    - 장치 A가 장치 B로 메시지를 보내는 동안 장치 B에 장애가 발생하더라도, 메시지는 큐에 임시 저장되었다가 B가 복구될 때 안전하게 처리됨
- 유연한 오류 처리
    - 특정 장치에 문제가 생겨도 메시지 유실 없이 나중에 처리할 수 있음
    - 장치 A는 장치 B의 내부 문제나 장애 여부를 알 필요도 없고 신경 쓸 필요도 없음
- 구조적 단점
    - 수행하려는 작업의 성격상 즉각적인 결과 확인이 필요한 동기식 요청으로 모델링하는 것이 더 자연스러울 때는 비동기 방식을 적용하기 어려움

## 동기vs 비동기 선택 기준

### 동기식 프로세스: URL 단축 서비스 요청

- 사용자에게 최대한 빠르게 단축 URL을 반환해야 하므로 대기열(Queue)에 요청이 쌓여 지연되는 것을 허용하지 않는다.
- 여러 사용자에게 동일한 단축 URL을 중복 발급하는 오류를 차단해야 한다.
    - 오작동하거나 잘못된 링크를 사용자에게 제공하는 것보다, 차라리 그 즉시 실패 에러를 표시하는 것이 낫다.

### 비동기식 프로세스: 메트릭(통계) 시스템

- 사용자가 Bitly 링크를 클릭하면 URL 변환 및 리디렉션은 HTTP를 통해 동기식으로 즉시 완료되어 사용자에게 반환된다.
    - 이후 클릭 관련 통계 데이터는 분석 및 하위 시스템 처리를 위해 큐에 비동기식으로 추가된다.
- 메트릭 데이터를 수집하고 처리하는 과정에 약간의 지연이 발생하더라도, 실제 사용자의 링크 접속 서비스에는 아무런 영향을 주지 않는다.

## 메시지의 형태: 명령 vs 이벤트

- 명령
    - "X 작업을 수행하라"고 지시하는 형태
    - 송신자가 수신자가 누구인지 명확히 알아야 하므로 시스템 간 결합도가 높아짐
- 이벤트
    - “X라는 일이 발생했다"고 사실만 알리는 형태
    - 시스템 간의 격리를 대폭 강화할 수 있어 분산 시스템에서 훨씬 더 유용한 추상화 개념으로 작용
    - 발행자는 누가 이 메시지를 가져가서 소비하는지 신경 쓸 필요가 없음

## 이벤트 기반 구조의 확장성

**다중 소비자 처리**

- 하나의 이벤트가 발행되면 수많은 하위 서비스가 동시에 독립적으로 데이터를 가져가 처리할 수 있음
- Bitly의 경우, URL 디코딩 이벤트가 발생하면 디코딩 서비스는 단순히 이벤트를 게시한다.
    
    이후 HDFS/S3 아카이브 서비스, 실시간 분석 서비스, 장기 기록 분석 서비스, 주석 서비스 등이 생산자에 대한 정보 없이 이벤트를 수신하여 각자 작업을 수행한다.
    
    - 하위 서비스는 이벤트를 수신하기만 하면 되며, 누가 어떻게 보냈는지에는 관심이 없다.

**새로운 기능 확장 용이**

- 기존 생산자의 코드를 수정할 필요 없이, 새로운 서비스를 만들고 해당 이벤트에 등록(구독)만 하면 시스템 확장이 완료됨
- 소비자의 처리 방식이 바뀌어도 생산자는 영향을 받지 않음

**느슨한 결합**

- 생산자와 소비자는 서로 철저히 격리되어 있으며, 오직 이벤트에 명시된 데이터 계약을 통해서만 연결됨

# 서비스 간 상호작용 및 탄력성 확보

독립된 서비스들이 병목 현상 없이 유기적으로 맞물려 돌아가도록 예외 처리와 우회 경로를 설계해야 한다.

## **백프레셔 사용**

특정 하류(수신 측) 서비스가 과부하 상태에 빠지면, 상류(요청 측) 서비스들에게 요청 속도를 줄이도록 지시하여 부하를 조절한다.

지수 백오프 등의 알고리즘을 결합하여 연쇄 장애를 방지하고 시스템 복구 속도를 높일 수 있다.

예를 들어, 캐싱에 의존하는 서비스는 가동 초기 데이터가 채워지는 워밍업 기간이 필요하다.

이 기간 동안 요청 서비스들이 백오프를 하지 않고 트래픽을 밀어붙이면 배후의 데이터베이스가 과부하로 다운될 수 있다.

## **장애 발생 시 우회 경로 설정 (호스트 풀 관리)**

서버 장애에 대응하기 위해 서비스 간 동적 로드 밸런싱을 수행한다.

Bitly는 호스트 풀 라이브러리를 통해 이를 처리한다. 

- 클라이언트는 서비스를 이용할 때 호스트 풀에 사용 가능한 호스트를 요청한다.
- 만약 특정 호스트에 대한 요청이 실패하면, 클라이언트는 그 실패 사실을 즉시 호스트 풀에 피드백한다.
- 호스트 풀은 이 피드백을 기반으로 상태가 나쁜 노드를 제외하고 가용성이 높은 안정적인 호스트로 트래픽을 분산한다.

# 분산 환경에서의 모니터링

서버가 수백 대에 달하는 대규모 분산 인프라에서는 장애 인지와 원인 분석을 자동화해야 한다.

### **인프라 상태 및 데이터 무결성 검사**

- **Nagios** 같은 모니터링 도구를 사용하여 전체 서버의 건강 상태를 체크하고, 서버가 정상적으로 전환되고 있는지 통계를 확인한다.
- 단순히 서버가 살아있는지(200 OK 응답 여부)만 보는 것을 넘어, 시스템이 반환하는 데이터가 깨지거나 오염되지 않았는지 검증하는 데이터 무결성 검사를 주기적으로 실행한다.

### **중앙 집중식 로깅**

- 수많은 호스트에서 발생하는 로그를 한곳으로 모으는 아키텍처는 에러 원인 분석에 필수적이다.
- 특정 사용자의 악성 요청이나 IP 하나가 모든 호스트를 돌아가며 에러를 유발하는 경우, 개별 서버의 로그만 봐서는 문제의 원인을 파악하기 어렵다.
- 로그를 중앙으로 집중시켜야 전체적인 맥락을 쉽게 파악할 수 있다.

### UI

- 시스템의 복잡한 데이터를 시각화하여 적절한 운영자에게 적절한 시기에 전달해야 한다.
- NSQ 어드민 UI
    - 큐의 동작 방식을 직관적으로 보여주어, 큐가 정체되는 병목 현상이 발생했을 때 그것이 어떤 특정 호스트의 문제 때문인지 쉽게 식별할 수 있도록 돕는다.
- 배포 시스템용 웹 UI
    - 간편한 배포 기능과 함께 상세한 배포 이력을 제공한다.
    - 모니터링 도구(Nagios)에 갑자기 경고가 발생했을 때 최근 배포 내역을 즉시 대조해 보면 배포된 코드가 장애 원인인지 빠르게 유추할 수 있다.

# 얻은 교훈

- 추상화 계층의 누수를 처리하는 코드를 작성하라.
- SOA와 큐, 비동기 메시징을 결합하면 강력한 조합이 된다.
    - 구성 요소를 격리하고 작업을 동시에 처리할 수 있게 하며, 각 구성 요소가 독립적으로 장애를 발생시키도록 하면서도 구성 요소를 쉽게 이해할 수 있도록 해준다.
- 속도와 일관성이 가장 중요한 경우에는 동기식 요청을 사용하라.
    - 느리거나 잘못된 응답을 제공하는 대신 사용자에게 오류를 표시
- 메시지 형태는 이벤트가 명령보다 좋다.
    - 시스템 간의 격리가 더 잘 이루어지고 여러 소비자를 자연스럽게 지원한다.
    - 서비스는 본래의 기능 수행에만 집중하고 그 외의 다른 사항에 대해서는 신경 쓰지 않아도 된다.
- 필터링보다는 주석을 활용하라.
    - 생산자 수준의 필터는 하위 서비스가 무엇에 관심을 갖는지에 대한 가정을 전제로 한다.
    - 예를 들어 공개 링크와 비공개 링크를 구분하는 경우, 비공개 링크를 스트림에서 필터링하면 비공개 링크에 관심 있는 서비스는 필요한 링크를 얻지 못한다.
    - 대신, 링크가 공개인지 비공개인지 여부를 이벤트에 주석으로 추가하고, 서비스가 자신에게 필요한 유형의 이벤트만 처리하도록 하라.
- 서비스들은 서로 원활하게 작동해야 한다.
    - 서비스 과부하를 방지하기 위해 백프레셔를 사용하고, 장애가 발생한 서비스는 우회 경로로 라우팅해야 한다.
