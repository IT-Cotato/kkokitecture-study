# **Discord는 어떻게 Elixir를 사용하여 500만 명의 동시 접속자를 감당할 수 있었는가**

> 출처 : https://discord.com/blog/how-discord-scaled-elixir-to-5-000-000-concurrent-users
> 

# 개요

Discord는 고도의 동시성을 갖춘 실시간 시스템을 구축하기 위해 초기부터 **Erlang VM**과 **Elixir**를 도입했다. 

- **Eralng VM** : 수백만 개의 동시 작업을 처리하고, 에러가 나도 스스로 복구하는 실행 환경(가상 머신)
- **Elixir** : Eralng VM 위에서 돌아가는 프로그래밍 언어

시스템이 동시 접속자 500만 명, 초당 수백만 개의 이벤트가 발생하는 규모로 성장하면서 여러 성능 한계에 직면했다. 

이를 해결하기 위해 직접 연구하고 개발한 3가지 핵심 최적화 기법과 오픈소스 라이브러리를 소개한다.

# 메시지 팬아웃 (Message Fanout)

## 동작 방식

Discord의 대부분의 기능은 Pub/Sub 방식으로 구현된다.

- 메시지가 발생하면 길드 프로세스가 연결된 모든 세션 프로세스에 메시지를 보낸다.
    - 길드(Guild) 프로세스 : 하나의 채팅 서버를 담당하는 프로세스
    - 세션(Session) 프로세스 : 각 사용자의 연결을 담당하는 프로세스
- 사용자가 온라인 상태가 되면, 길드에 연결되고 길드는 연결된 모든 세션에 현재 상태를 알린다.

```elixir
def handle_call({:publish, message}, _from, %{sessions: sessions}=state) do
  Enum.each(sessions, &send(&1.pid, message))
  {:reply, :ok, state}
end
```

## 문제점

처음 Discord를 25명 이하의 소규모 그룹에 맞춰 개발했을 때는 이 방식이 적절했으나, 대규모 그룹에 사용하기 시작하면서 문제가 생겼다.

- Erlang 프로세스는 기본적으로 **단일 스레드**로 동작한다.
- 만약 한 서버(길드)에 3만 명이 있다면, 길드 프로세스는 `send/2` 함수를 3만 번 루프를 돌며 호출해야 한다.
    - `send/2` 함수 : Elixir(및 Erlang)의 가장 기본적인 메시지 전송 함수 → 길드가 세션에게 메시지를 보낼 때 사용
    - `send/2` 호출 한 번에 30~70μs가 소요된다고 할 때, 3만 명에게 보내는 데 약 2초 소요
    - 2초 동안 길드 프로세스는 다른 메시지를 처리하지 못해 대기열(Mailbox)이 쌓이고 시스템이 느려진다.

### **샤딩**

- 하나의 큰 길드를 여러 개의 작은 조각(Shard)으로 쪼개서 여러 프로세스에 나눠 담는 방식

그러나 샤딩을 적용하려면 기존의 모든 길드 로직과 데이터베이스 구조를 다시 설계해야 한다.

작업 규모가 너무 방대하고 복잡도가 높기 때문에 당장 해결해야 하는 상황에서는 최선의 선택이 아니었다.

### 메시지 발송 전용 일회용 프로세스 생성

Erlang에서 프로세스 생성 비용이 저렴하기 때문에 처음에는 각 메시지 게시를 처리하기 위해 새 프로세스를 생성하는 방식을 생각했다.

문제점

1. 이벤트의 선형성 파괴
    - 채팅 앱에서는 메시지의 순서가 중요하다.
    - 길드 프로세스가 메시지 A를 보내는 프로세스 1번을 만들고, 곧바로 메시지 B를 보내는 프로세스 2번을 만들었다고 가정
        
        → CPU 스케줄링에 따라 프로세스 2번이 1번보다 먼저 실행될 수 있다.
        
2. 서비스 확장성 문제
    - 길드 서비스는 단순히 메시지만 전달하는 게 아니라, 점점 더 많은 비즈니스 로직(권한 체크, 상태 관리 등)을 처리해야 한다.
    - 전체 시스템의 자원 관리 측면에서 또 다른 병목(프로세스 관리 오버헤드 등)을 가져올 수 있다.

# 해결책 - Manifold

전달 작업을 수신 노드들에 분산시키는 라이브러리 Manifold를 개발했다.

Manifold는 메시지 전송 작업을 PID의 원격 노드에 분산시켜, 전송 프로세스가 관련된 원격 노드 수만큼만 `send/2`를 호출하도록 보장한다.

- PID : 세션 프로세스의 ID

## 동작 방식

1. 길드 프로세스는 메시지를 받을 대상(PID)들을 노드(서버)별로 그룹화한다.
2. 각 노드에 있는 Partitioner 프로세스에게 메시지를 한 번만 보낸다.
3. 메시지를 받은 각 노드의 Partitioner는 해당 노드 내에서 CPU 코어 수에 맞게 Worker들에게 작업을 나누고, 최종적으로 세션 프로세스들에게 메시지를 전달한다.
    - `:erlang.phash2/2` 를 사용해 PID를 일관되게 해싱

⇒ 선형화 가능성 유지 및 Partitioner 과부화 방지

```elixir
Manifold.send([self(), self()], :hello)
```

## 결과

길드 프로세스의 CPU 부하를 획기적으로 줄였고, 노드 간 중복 네트워크 트래픽도 줄일 수 있었다.

# **빠른 액세스 공유 데이터 (Fast Access Shared Data)**

Discord는 **안정 해싱**(Consistent Hashing)을 통해 구현된 분산 시스템이다.

- 특정 데이터가 어느 노드에 있는지 알기 위해 링 구조를 사용한다.
- 모든 세션은 연결될 때마다 이 링을 조회해야 한다.

초기에는 C 언어로 작성된 외부 라이브러리를 **Erlang C 포트**를 통해 연결하여 사용했다.

- Erlang C 포트 : Erlang 프로세스가 외부 C 프로그램을 별도 프로세스로 실행해 통신하는 방식

## 문제점

서비스 규모가 커지고 유저들이 한꺼번에 재접속(Burst)하는 경우에 문제가 생겼다.

- 링 데이터를 관리하는 단일 Erlang 프로세스에 요청이 몰리면서 요청을 제때 처리하지 못해 시스템 전체가 과부하가 생겼다.

### 비용 계산

- 한 명의 유저는 평균 5개의 길드에 속함
- 서버 한 대당 최대 50만 개의 활성 세션을 가짐
- 세션 서버가 재시작되면 총 2,500,000번(50만 × 5)의 조회 발생
- 프로세스 간 통신(Request/Reply) 비용은 건당 약 12μs
- 결과적으로 조회에만 약 30초가 소요

### ETS (Erlang Term Storage) 도입

조회 속도를 높이기 위해 가장 먼저 떠올리는 대안은 ETS이다.

> **ETS**
> 
> - Erlang VM에 내장된 인메모리 저장소
> - 매우 빠르지만 데이터를 읽을 때 복사(Copy)가 발생한다.
- 기존 C 포트 방식을 순수 Elixir 코드로 변환하고, 링 데이터를 ETS에 저장해 여러 프로세스가 직접 읽게 했다.

문제점

- ETS는 빠르지만, 데이터를 읽어올 때 해당 데이터를 프로세스의 개인 메모리 공간으로 복사한다.
    - ETS 읽기 비용: 건당 약 7μs
    - 총 소요 시간: 250만 번 × 7μs = 17.5초
- 링 데이터 구조가 매우 크기 때문에 ETS로 데이터를 복사하고 삭제하는 과정이 성능을 저하시켰다.

# 해결책 - FastGlobal (mochiglobal 기법)

"복사조차 하지 않고 모든 프로세스가 데이터를 공유할 수 없을까?"라는 고민 끝에 Erlang VM의 특성을 활용한 기법을 도입했다.

- Erlang VM은 상수를 반환하는 함수를 컴파일할 때, 그 데이터를 읽기 전용 공유 힙(Read-only Shared Heap)에 저장한다.
    - 여기에 저장된 데이터는 프로세스 간에 복사 없이 주소만 참조하여 읽을 수 있다.

## 동작 방식

1. 링 데이터가 변경되면, 런타임에 그 데이터를 통째로 하드코딩한 새로운 Elixir 모듈을 생성한다.
2. 이 모듈을 즉석에서 컴파일하여 메모리에 올린다.
3. 다른 프로세스들은 이 모듈의 함수를 호출하여 데이터에 접근한다.

## 결과

- 조회 비용: 7μs → 0.3μs로 단축
    - 데이터 복사 X
- 총 소요 시간: 17.5초 → 750ms(0.75초)로 단축

링처럼 큰 데이터 구조를 가진 모듈을 런타임에 생성하는 데는 최대 1초가 소요될 수 있지만, 링 데이터는 자주 바뀌지 않으므로 이 정도의 성능 저하는 감수할 만하다고 생각했다.

# 제한된 동시성 (Limited Concurrency)

노드 조회 속도를 개선하자, 길드 노드에서 guild_pid 조회를 담당하는 프로세스들이 Back Pressure 현상을 겪고 있음을 발견했다.

> Back Pressure : 시스템의 한 부분에서 데이터가 너무 빨리 들어올 때, 물리적인 저항이 생겨서 데이터의 흐름을 스스로 조절하게 되는 현상
> 
- 이전에는 노드 조회 자체가 느려서, 노드 조회 단계의 병목 현상이 PID 조회 단계로 몰리는 트래픽 속도를 늦춰줬다.
- 노드 조회 속도가 빨라지자, 대기하던 500만 개의 세션 프로세스가 길드 노드에 있는 단 10개의 레지스트리 프로세스(노드당 1개)에 한꺼번에 요청을 보내게 되었다.
    
    > 길드 레지스트리 : 길드 ID → 실제 프로세스 주소(PID)로 변환해주는 주소 조회용 프로세스
    > 

## 문제점

단순히 이 처리 경로의 속도를 개선하는 것만으로는 문제를 해결할 수 없었다.

1. 요청 폭주
    - 레지스트리 프로세스의 메시지 대기열이 감당할 수 없을 만큼 쌓인다.
2. 타임아웃 및 재시도
    - 세션 프로세스는 응답이 늦어지면 타임아웃을 내고 다시 요청을 보낸다.
    - 하지만 원래 보냈던 요청은 여전히 레지스트리 대기열에 남아 자원을 소모한다.
3. 메모리 고갈(OOM)
    - 세션 프로세스들은 레지스트리의 응답을 기다리느라 블로킹(Blocking)된다.
    - 그사이 다른 서비스에서 오는 메시지들은 계속 쌓여 세션의 메시지 큐가 팽창하고, 결국 Erlang VM 전체에 메모리 고갈 문제가 생긴다.
4. 연쇄 장애
    - 한 서버가 죽으면 부하가 다른 서버로 전이되어 전체 서비스가 중단된다.

# 해결책 - Semaphore (세마포어)

### 서킷 브레이커(Circuit Breaker)를 쓰지 않은 이유

- 서킷 브레이커는 에러가 일정 수준을 넘으면 아예 호출을 차단한다.
- 타임아웃이 많이 발생한다고 해도 호출이 아예 차단되는 것을 원치 않았기 때문에 서킷브레이커를 쓰지 않았다.

Erlang VM은 프로세스 간 통신을 통한 조정을 중심으로 설계되었다.

하지만 카운터 전용 프로세스를 만들어 사용한다면, 이 프로세스에 병목이 생길 수 있다.

## ETS 활용

프로세스 간 통신 없이도 여러 프로세스가 동시에 안전하게 접근할 수 있는 `:ets.update_counter/4`를 활용했다.

- **원자적 카운터 (Atomic Counter)**
    - 특정 키의 값을 원자적으로 증가시키고 그 결과를 즉시 반환받는다.
- 동작 방식
    - 요청을 보내기 전, ETS에 저장된 '현재 실행 중인 요청 수'를 1 증가시킨다.
    - 만약 이 숫자가 미리 정해둔 최대치를 넘으면 요청을 보내지 않고 즉시 에러를 반환한다.

```elixir
# Discord가 만든 Semaphore 라이브러리 사용 예시
semaphore_name = :my_sempahore
semaphore_max = 10
case Semaphore.call(semaphore_name, semaphore_max, fn -> :ok end) do
  :ok ->
    IO.puts "success"
  {:error, :max} ->
    IO.puts "too many callers"
end
```

## 결과

이 라이브러리(Semaphore)는 우리 Elixir 인프라를 보호하는 데 핵심적인 역할을 했다.

프레즌스 서비스(Presence Service, 사용자 상태 정보 관리)가 별개의 문제로 인해 충돌하여 다운되었다.

과거에는 프레즌스 서비스가 다운되면 이를 참조하는 세션 서비스들까지 대기열이 쌓이며 연쇄 장애로 이어졌으나, Semaphore 도입 후 세션 서비스는 전혀 영향을 받지 않았다.

프레즌스 서비스는 재시작 후 몇 분만에 복구되었다.
