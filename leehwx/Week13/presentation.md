# **디스코드가 수십억 개의 메시지를 저장하는 방법**

> 출처: https://medium.com/discord-engineering/how-discord-stores-billions-of-messages-7fa6ec7ee4c7
> 

# 개요

Discord CTO Stanislav Vishnevskiy가 수십억 건의 메시지를 저장하기 위해 MongoDB에서 Cassandra로 전환한 과정과 그 과정에서 겪은 문제들을 소개하는 글이다.

Discord는 초기부터 모든 채팅 내역을 영구 보관해 어떤 기기에서든 언제든지 조회할 수 있도록 하는 것을 목표로 삼았다.

2016년 7월 하루 4천만 건이었던 메시지 수가 같은 해 12월 1억 건, 글 작성 시점에는 하루 1억 2천만 건을 넘어섰다.

# 우리가 하고 있던 일

2015년 초 약 두 달 만에 만든 초기 Discord는 빠른 개발을 위해 MongoDB 단일 복제 세트에 모든 데이터를 저장했다.

메시지는 `channel_id` 와 `created_at` 을 복합 인덱스로 사용하는 컬렉션에 저장했다.

2015년 11월 저장된 메시지가 1억 건에 달하면서 데이터와 인덱스가 더 이상 RAM에 올라가지 않기 시작했고 응답 지연이 예측 불가능해졌다. 

# 적합한 데이터베이스 선택하기

데이터베이스를 교체하기 전에 읽기/쓰기 패턴을 분석했고, 읽기와 쓰기 비율이 약 50:50이며 읽기가 매우 무작위(random)하다는 것을 파악했다.

채널 유형에 따라 메시지 발생 패턴이 크게 달랐다.

- 음성 채팅 중심 디스코드 서버
    - 메시지 전송량이 거의 없어 연간 1,000건 미만이지만, 조회 시 디스크 랜덤 탐색이 많이 발생해 캐시 적중률이 낮다.
- 소규모 텍스트 채팅 서버
    - 연간 10만~100만 건의 메시지를 생성하며 최신 메시지만 주로 조회하지만 요청 빈도가 낮아 디스크 캐시에 남아있기 어렵다.
- 대형 공개 서버
    - 하루에 수천 건의 메시지를 주고받아 최근 1시간 내 메시지를 자주 조회하며, 빈번한 요청 덕분에 데이터가 디스크 캐시에 남아있을 가능성이 높다.

## 요구사항

- **선형 확장성**
    
    : 나중에 솔루션을 재검토하거나 데이터를 수동으로 재분할하고 싶지 않다.
    
- **자동 장애 조치**
    
    : Discord가 최대한 자체 복구되도록 설계했다.
    
- **유지보수가 거의 필요 없음**
    
    : 한 번 설정해 놓으면 바로 작동, 데이터가 증가할 때만 노드를 추가하면 된다.
    
- **효과가 입증된 기술**
    
    : 새로운 기술을 시도해 보는 것을 좋아하지만, 너무 새로운 기술은 선호하지 않는다.
    
- **예측 가능한 성능**
    
    : API 응답 시간의 95번째 백분위수가 80ms를 초과하면 알림이 울리도록 설정되어 있다. 또한 Redis나 Memcached에 메시지를 캐싱하는 것도 원하지 않는다.
    
- **블롭 저장소가 아니다.**
    
    : 초당 수천 개의 메시지를 작성하는 경우, 블롭을 지속적으로 역직렬화하고 추가해야 한다면 효율적이지 않을 것이다.
    
    > 블롭 저장 방식: 데이터를 구조화하지 않고, 하나의 덩어리 형태로 저장하는 방식
    > 
- **오픈 소스**
    
    : 제3의 회사에 의존 X
    

앞으로 멘션 이력 조회, 핀 메시지 이동, 전체 텍스트 검색 기능이 추가될 예정이었기 때문에 무작위 읽기가 더욱 늘어날 것이 확실했다.

위 요구사항을 모두 충족한 데이터베이스는 Cassandra뿐이었다.

# 데이터 모델링

Cassandra는 KKV 저장소로 이해하면 쉽다. 

첫 번째 K는 파티션 키로 어떤 노드에 데이터가 저장될지를 결정하고, 두 번째 K는 클러스터링 키로 파티션 내에서 행을 식별하고 정렬하는 역할을 한다.

- 파티션 키: `channel_id`
- 클러스터링 키: `메시지 ID`
    
    → `created_at`대신 메시지 ID를 쓴 이유는 같은 시각에 두 메시지가 생성될 수 있기 때문이었다.
    

⇒ Discord의 모든 ID는 Snowflake 형식으로 시간순으로 정렬 가능하기 때문에, `(channel_id, message_id`를 기본 키로 삼으면 특정 채널에서 범위 탐색(range scan)으로 메시지를 빠르게 조회할 수 있었다.

```sql
// 메시지 테이블의 간소화된 스키마 (약 10개 열 생략)
CREATE TABLE messages (
  channel_id bigint,
  message_id bigint,
  author_id bigint,
  content text,
  PRIMARY KEY (channel_id, message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

카산드라는 관계형 데이터베이스와 유사한 스키마를 가지고 있지만, 변경 비용이 저렴하고 일시적인 성능 저하를 유발하지 않습니다. 따라서 블롭 저장소와 관계형 저장소의 장점을 모두 확보할 수 있다.

### 문제점 - 파티션 크기 제한 필요

데이터를 가져오기 시작하자 Cassandra 로그에 파티션 크기가 100MB를 초과한다는 경고가 나타났다. 

하나의 채널이 몇 년에 걸쳐 계속 커질 수 있기 때문에 파티션 크기를 제한할 방법이 필요했다.

> KKV 저장소 파티션: 키(K1)와 클러스터링 키(K2) 두 개의 키로 데이터를 찾는 Cassandra의 저장 구조
> 

### 해결 방법 - 메시지를 버킷 단위로 나눔

메시지를 시간 버킷 단위로 나누어 약 10일치 메시지가 하나의 버킷에 담기도록 설계했다. 

```python
# Discord 에포크: 2015-01-01 00:00:00 UTC를 밀리초로 표현한 값
# Snowflake ID의 타임스탬프는 이 시점을 기준으로 계산된다
DISCORD_EPOCH = 1420070400000

# 버킷 하나의 크기: 10일을 밀리초로 표현한 값
# 1000(ms) * 60(sec) * 60(min) * 24(hour) * 10(day)
# 파티션이 무한정 커지는 것을 막기 위해 메시지를 10일 단위로 쪼개어 저장
BUCKET_SIZE = 1000 * 60 * 60 * 24 * 10

def make_bucket(snowflake):
    """
    Snowflake ID(또는 None)를 받아 해당 메시지가 속하는 버킷 번호를 반환한다.
    버킷 번호 = (Discord 에포크 기준 경과 밀리초) / BUCKET_SIZE의 몫
    """
    if snowflake is None:
        # snowflake가 없으면 현재 시각을 Discord 에포크 기준 밀리초로 변환
        timestamp = int(time.time() * 1000) - DISCORD_EPOCH
    else:
        # Snowflake의 상위 42비트에 Discord 에포크 기준 밀리초 타임스탬프가 담겨 있다.
        # 하위 22비트(워커 ID, 프로세스 ID, 시퀀스)를 오른쪽으로 밀어내어 타임스탬프만 추출
        timestamp = snowflake_id >> 22

    # 타임스탬프를 버킷 크기(10일)로 나누어 버킷 번호 반환
    return int(timestamp / BUCKET_SIZE)

def make_buckets(start_id, end_id=None):
    """
    start_id부터 end_id까지의 메시지가 걸쳐 있는 버킷 번호 범위를 반환한다.
    end_id가 None이면 make_bucket 내부에서 현재 시각 기준 버킷을 사용한다.

    예) 메시지를 시간 역순으로 조회할 때, 현재 버킷부터 start_id 버킷까지
        순서대로 탐색하는 데 사용한다.
    """
    # make_bucket(end_id) + 1 을 하는 이유: range()는 끝값을 포함하지 않으므로
    # end_id가 속한 버킷까지 포함하려면 +1이 필요
    return range(make_bucket(start_id), make_bucket(end_id) + 1)
```

- 기본 키: `((channel_id, bucket), message_id)`
    
    ```sql
    CREATE TABLE messages (
       channel_id bigint,
       bucket int,
       message_id bigint,
       author_id bigint,
       content text,
       PRIMARY KEY ((channel_id, bucket), message_id)
    ) WITH CLUSTERING ORDER BY (message_id DESC);
    ```
    

최신 메시지를 조회할 때는 현재 시간부터 채널 생성 시점까지 버킷을 순서대로 뒤져 충분한 메시지 수가 모일 때까지 탐색한다.

비활성 채널은 여러 버킷을 탐색해야 할 수 있지만, 활성 채널은 대부분 첫 번째 버킷에서 충분한 메시지가 확보되어 실제로는 문제가 없었다.

# Dark Launch

새 시스템을 프로덕션에 바로 투입하는 것은 위험하기 때문에, MongoDB와 Cassandra에 동시에 읽기/쓰기를 수행하는 Dark Launch(이중 쓰기 테스트) 방식을 사용했다.

이 과정에서 `author_id`가 null로 기록되는 오류가 발견됐다.

> **Dark Launch**: 사용자에게는 영향을 주지 않으면서 새 시스템을 실제 트래픽으로 미리 검증하는 기법이다. 새 시스템의 처리 결과는 실제 서비스에 반영하지 않거나, 기존 시스템과 결과를 비교하는 방식으로 진행한다.
> 

> **이중 쓰기(Double Write)**: 같은 데이터를 두 시스템에 동시에 쓰며 두 결과를 비교 검증하는 마이그레이션 기법이다.
> 

# 최종 일관성

Cassandra는 AP 데이터베이스로, 강한 일관성 대신 가용성을 선택한다.

- Cassandra에서는 쓰기가 항상 upsert로 처리되기 때문에 특정 컬럼만 써도 나머지 컬럼은 null이 된다.
    
    한 사용자가 메시지를 수정하는 동시에 다른 사용자가 같은 메시지를 삭제하는 경쟁 조건이 발생하면, primary key와 text 컬럼만 남고 나머지가 모두 null인 손상된 행이 생길 수 있다.
    
    ⇒ 필수 컬럼(`author_id`)이 null인 경우 해당 메시지를 삭제하는 방식을 선택했다.
    
    > **Upsert**: 데이터가 존재하면 업데이트, 없으면 삽입하는 쓰기 방식이다. Cassandra에서는 모든 쓰기가 업서트로 처리된다.
    > 
- Cassandra에서 컬럼에 null을 쓰는 것과 컬럼을 삭제하는 것은 모두 내부적으로 tombstone를 생성한다.
    - 메시지 스키마가 16개 컬럼인데 평균 4개 값만 실제로 채워져, 나머지 12개 컬럼에 매번 묘비를 생성하고 있었다.
    
    ⇒ null이 아닌 값만 쓰도록 변경해 해결했다.
    
    > **Tombstone**: Cassandra에서 삭제를 표현하는 방식이다. 데이터를 즉시 지우는 대신 "삭제됐다"는 마커를 남겨두고, 이후 컴팩션 시점에 실제로 제거한다.
    > 

# 성능

어떤 데이터를 조회하든, 1주일의 테스트 기간 내내 성능은 일관되게 유지됐다.

Cassandra는 쓰기가 읽기보다 빠른 것으로 알려져 있으며 실제로도 그랬다. 

쓰기는 1밀리초 미만, 읽기는 5밀리초 미만의 지연시간을 기록했다.

# **대서사시**

MongoDB를 완전히 걷어내고 약 6개월이 지난 시점에 Cassandra가 갑자기 응답 불능 상태에 빠졌다.

### 원인

한 공개 Discord 서버에서 API를 통해 수백만 건의 메시지를 삭제하고 채널에 단 1개의 메시지만 남겨둔 것이 원인이었다.

사용자가 해당 채널에 접근하면 실제 메시지는 1개뿐이지만, Cassandra는 수백만 개의 tombstone를 전부 스캔해야 했다. 

이 과정에서 JVM이 처리할 수 없는 속도로 가비지가 쌓여 10초짜리 stop-the-world GC가 반복됐다.

### 해결 방법

- tombstone 유지 기간 단축
    - 매일 밤 Cassandra repair를 실행하고 있었기 때문에 tombstone 유지 기간을 기본값 10일에서 2일로 줄였다.
- 빈 버킷 추적
    - 조회 쿼리 코드를 수정해 메시지가 없는 빈 버킷을 기억해 두고, 이후 요청 시 해당 버킷은 건너뛰도록 했다.

# 미래

당시 12개의 노드 클러스터를 Replica Factor 3으로 운영 중이었으며, 필요에 따라 노드를 추가하는 방식으로 확장할 계획이었다.

> **Replica Factor**: Cassandra에서 데이터 복사본을 몇 개의 노드에 나누어 저장할지를 정하는 설정값이다. 3이면 3개의 노드에 같은 데이터를 복제한다.
> 

## 단기 계획

- Cassandra 2 → Cassandra 3으로 업그레이드
    - Cassandra 3의 새 스토리지 포맷은 저장 공간을 50% 이상 줄일 수 있다.
- 각 노드의 저장 용량을 현재 1TB에서 2TB로 늘려 클러스터 노드 수를 줄이는 것도 검토 중

## 장기 계획

- C++로 구현된 Cassandra 호환 데이터베이스인 Scylla 도입 검토
    - 피크가 아닌 시간대에 수행하는 repair 작업이 CPU를 많이 사용하는데, Scylla는 repair 소요 시간이 훨씬 짧다고 알려져 있다.
- 사용이 없는 채널은 Google Cloud Storage의 플랫 파일로 아카이빙하고, 요청이 들어올 때 다시 로드하는 방식을 구축하는 것도 후보로 두고 있지만 실제로 필요하게 되지는 않을 것으로 예상한다.

> 아카이빙: 자주 접근하지 않는 오래된 데이터를 저렴한 스토리지(예: 오브젝트 스토리지)로 옮겨 보관하는 방식이다. 필요할 때 다시 불러올 수 있다.
