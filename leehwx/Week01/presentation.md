# Active-Active

여러 서버나 데이터센터를 동시에 가동하여 트래픽을 분산 처리하는 고가용성(HA) 구성 방식

## Active-Active 아키텍처 요구사항

- 서비스는 상태 저장 X
    - 모든 데이터/상태 복제는 데이터 계층에서 처리
- 리소스는 반드시 동일 리전 내에서 로컬로 접근해야 함
    - 여기서 리소스는 S3, SQS(메시지 큐) 등
    - 하나의 S3 버킷에 데이터를 게시하는 여러 애플리케이션은 동일한 데이터를 여러 리전의 S3 버킷에 게시해야 함
    - 격리를 위함
        - 다른 리전의 리소스에 의존성이 있는 경우, 해당 리전 장애 시 현재 리전에도 영향
- 사용자의 호출 경로(Call Path)에는 리전 간 호출이 없어야 함
    - 지연 시간 최적화 → 리전 간 통신은 지연이 발생
- 데이터 복제는 비동기적으로 이루어져야 함
    - 리전 간 데이터 동기화는 사용자 응답과 별개로 백그라운드에서 비동기적으로

### 정상적 운영 상태

- 지리적 DNS 라우팅 → 가장 가까운 AWS 리전으로 연결되며, 연결 비율은 약 50/50

- 'Thundering Herd' 대응을 위한 트래픽 셰이핑 및 부하 차단
    - 장애 복구 직후 등 대기하던 사용자 요청이 서버로 한번에 들어오는 경우
    - Traffic Shaping : 서버가 감당할 수 있는 만큼만 요청이 들어오도록 제어

# DNS - Denominator를 사용하여 사용자 트래픽 제어하기

DNS 서비스를 하나만 쓰지 않고, UltraDNS와 Route53 항목을 조합하여 사용자의 트래픽을 서비스로 전달한다.

**DNS**

- 사람이 읽는 도메인을 컴퓨터가 이해하는 IP 주소로 변환

**UltraDNS**

- 기업용 관리형 DNS 서비스
- 지리적 라우팅 목적으로 사용
- 사용자의 위치에 따라 특정 리전으로 정확히 보내줌

**Route53**

- AWS에서 제공하는 DNS 서비스
- AWS 인프라(ELB 등)와 연동이 쉽고, API 응답 속도가 빠름

**Denominator**

- 넷플릭스의 오픈소스 프로젝트
- UltraDNS와  Route53처럼 서로 다른 DNS를 하나의 라이브러리나 명령어로 동시에 제어할 수 있게 해줌

## UltraDNS + Route53을 조합해 사용하는 이유

구조 : `사용자` → `UltraDNS(지역 배분)` → `Route53(전환 스위치)` → `ELB(부하 분산)`

- UltraDNS 사용 이유
    - 북미 전역의 사용자를 특정 지역 엔드포인트로 정교하게 분산하기 위함
    - 지연 시간 기반(Latency-based) 라우팅의 예측 불가능한 트래픽 이동을 피하고 싶어 했음
- Route53 사용 이유
    - API 응답 속도가 빠르고 안정적
    - 장애 시 트래픽 전환 설정 변경 속도가 빠름
    - 복잡한 지리적 그룹 설정을 건드리지 않고, Route53 CNAME만 변경하면 트래픽을 한 리전에서 다른 리전으로 이동시킬 수 있음

# **Zuul —** Traffic Shaping

### Traffic Shaping 트래픽 셰이핑

- 네트워크 대역폭을 효율적으로 사용하기 위해 트래픽 전송 속도를 제한하거나 조정하는 네트워크 관리 기술

### Zuul

- Zuul은 넷플릭스 모든 서비스 입구에 위치한 API Gateway
- 트래픽을 적절한 서비스 클러스터로 전달하는 방법 제공
- 런타임에 라우팅을 변경할 수 있는 기능 제공
- 하위 서비스의 과부하를 방지하기 위해 부하를 분산해야 하는지 여부를 결정할 수 있는 기능 제공

## Active-Active 충족을 위한 Zuul 기능 확장

- 잘못된 라우팅 처리
    - 사용자 요청이 지리적 경로 기록과 일치하지 않으면 잘못된 경로로 전송된 것으로 정의
    - 단일 사용자 장치 세션이 여러 리전에 걸쳐 전송되는 것 방지
    - 이스머스(isthmus) 모드 : 올바른 리전으로 요청 전달
    - 리다이렉션 : 클라이언트를 올바른 리전으로 직접 안내
- failover 모드
    - 특정 리전을 failover로 선언
    - 잘못 들어온 요청을 다른 리전으로 라우팅하려고 시도하지 않고 로컬에서 처리
- 부하 차단
    - 특정 시점에 최대 트래픽 수준 정의 → 초과 요청은 자동으로 차단(에러 응답)
        
        → 하위 서비스가 폭증하는 요청으로부터 보호되도록
        
    - 확장 중인 서비스나 리전 캐시가 부족한 상황에서 영구 저장 계층이 요청으로 과부하되는 것 방지

# 데이터 복제 - Cassandra 및 EvCache

Active-Active 아키텍처에서 가장 어려운 과제인 리전 간 데이터 정합성을 해결하기 위해 넷플릭스는 Apache Cassandra를 채택했다.

## Apache Cassandra 아파치 카산드라

- NoSQL
- 분산형 구조, Peer-to-Peer
- 다방향 및 다중 데이터센터(다중 리전) 비동기 복제를 지원
    - 여러 데이터 센터에 데이터를 복사하는 기능을 내장
    - 설정만 하면 미국 동부 DB에 쓴 데이터를 서부 DB로 알아서 비동기 복제해줌
- 사용자 요청을 처리하기 위해 읽고 쓰는 모든 데이터는 Cassandra에 저장

## 캐시 계층 : EvCache (Episodic-Volatile-Cache)

사용자에게 끊김 없는 경험을 제공하려면 데이터 계층 읽기 속도가 1ms 이내 속도를 보장해야 한다.

### EvCache (Episodic-Volatile-Cache)

- 넷플릭스가 개발한 분산 인 메모리 캐시 시스템
- E (Episodic) : 데이터가 에피소드(그룹) 단위로 관리될 수 있음

## Active-Active 환경에서의 캐시 문제

Active-Active 환경에서는 동부와 서부 리전의 캐시 데이터가 서로 다를 수 있다.

- 캐시 자체를 리전끼리 실시간으로 복제(Multi-master)할 것인가?
    
    ⇒ 복제 로직이 너무 복잡해지므로 **원격 캐시 무효화 방식**을 선택
    

## 원격 캐시 무효화 동작 방식 **(Remote Cache Invalidation)**

1. 데이터 쓰기 발생 (리전 A)
    - 사용자가 A에서 데이터 수정
    - A 리전의 Cassandra와 EvCache는 즉시 최신 데이터로 업데이트
2. 무효화 메시지 전송 (SQS 이용)
    - A의 EvCache 클라이언트는 데이터 변경을 감지 후 리전 B에 SQS로 메시지 전송
    - 리전 B의 캐시 데이터가 유효하지 않다고 알려줌
3. 다른 리전 캐시 삭제 (리전 B)
    - 리전 B의 EvCache 클라이언트가 SQS 메시지 수신
    - 캐시에서 해당 데이터를 즉시 삭제
4. 후속 읽기 요청 및 캐시 미스 (리전 B)
    - B 리전 사용자가 해당 데이터 요청
    - 캐시에서 삭제되었으므로 캐시 미스 발생
5. 데이터 재계산 및 로컬 캐시 업데이트
    - 서버는 캐시에 데이터가 없으므로  Cassandra에서 최신 데이터를 가져옴
    - 가져온 최신 데이터를 B 리전의 로컬 캐시에 다시 저장해 이후 요청부터는 빠르게 응답

# **원숭이 -  고릴라, 콩, 스플릿브레인**

더 큰 규모의 장애에도 아키텍처가 탄력적인지 검증하기 위해, 더 큰 규모의 Simians 시뮬레이션을 진행했다.

### Simian Army 심리안 아미

- 넷플릭스가 클라우드 인프라(AWS)의 복원력을 테스트하기 위해 만든 장애 유발 소프트웨어 도구 모음
- 의도적으로 시스템에 장애를 일으킴

### **Chaos Gorilla 카오스 고릴라**

- 가용 영역(AZ) 전체 중단시켜 남은 AZ들이 서비스 품질 저하 없이 트래픽을 감당하는지 확인

### **Split-brain 스플릿 브레인**

- 리전 간 네트워크 차단
- 데이터 복제 작업 중 일부가 대기열에 쌓이더라도 각 리전 서비스가 정상 작동하는지 확인

### **Chaos Kong 카오스 콩**

- 리전 전체가 마비된 상황을 가정하고 진행하는 가장 큰 규모의 장애 시물레이션
- 리전 failover 검증
    - 한 리전이 죽었을 때 모든 사용자 트래픽을 다른 리전으로 옮겨 서비스 가용성을 유지할 수 있는지 확인
- 최대 부하 처리 능력 입증
    - 특정 리전(US-West-2 등)이 넷플릭스 전체 트래픽의 100%를 감당할 수 있는지 실제 환경에서 증명
- 주요 실행 전략
    - **사용자 경험 보호**
        - 장애 리전 접속자를 정상 리전으로 강제 리다이렉션
        - 사용자가 오류 메시지 대신 적절한 응답을 받음
    - **점진적 트래픽 전환**
        - 비상 상황보다 더 천천히 트래픽 비중을 옮김
            
            → 서버의 오토 스케일링과 캐시 워밍 시간을 벌어주기 위해
            
    - 장기 가동 테스트
        - 모든 트래픽을 한 리전으로 몰고 24시간 이상 유지
        - 일일 트래픽 패턴 전체를 안정적으로 처리하는지 확인

### 시뮬레이션 결과

- 트래픽 이동 : 미국 동부(US-East) → 미국 서부(US-West)로 대부분의 트래픽을 성공적으로 이전
- 영향 범위 : 유럽 리전(EU-West) 등 타 대륙 리전에는 영향을 주지 않고 완벽하게 격리됨을 확인
- Active-Active 아키텍처가 이론뿐만 아니라 실제 거대 장애 상황에서도 유효함을 입증

# 실제 장애 조치

Chaos Kong을 통해 다중 지역 격리 및 이중화를 검증하기 전 실제 상황에서 지역 장애 조치를 테스트할 기회가 있었다.

### 장애 상황

- 한 지역의 미들 티어 시스템에서 심각한 성능 저하가 발생하여 결국 클러스터 대부분이 응답하지 않음

### 장애 조치

- 장애 리전을 고치는 대신 추가적인 도구를 활용해 사용자 요청을 정상 리전으로 라우팅
- 짧은 시간 안에 전 세계 사용자의 서비스 품질이 복구됨
- 이후 원인 파악 및 수정 사항 배포 후 트래픽을 다시 원래 리전으로 돌려놓음
<br>

### 운영 자동화 및 속도 최적화

- 시스템은 살아 있는 상태이므로 장애 여부를 판단하기 모호

### **Latency Monkey (레이턴시 몽키)**

간헐적 지연/에러 상황에 대비하기 위해 Latency Monkey라는 도구를 개발했다.

- 네트워크 지연이나 특정 비율의 에러를 의도적으로 주입
- 클라이언트와 서버 모두에 장애를 주입해 시스템의 내구성 테스트
