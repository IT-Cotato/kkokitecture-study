# **티켓 서버: 분산 기본 키를 저렴하게 구현하기**

> 출처: https://code.flickr.net/2010/02/08/ticket-servers-distributed-unique-primary-keys-on-the-cheap/
> 

# 개요

Flickr가 분산 데이터베이스 환경에서 고유한 기본 키를 생성하기 위해 고안한 '티켓 서버(Ticket Server)' 방식에 대한 글이다.

복잡한 분산 환경에서도 저렴하고 단순하게 전역적으로 고유한 ID를 생성하는 방법을 설명한다.

# 도입 배경

Flickr는 서비스 확장을 위해 데이터베이스를 샤딩(Sharding)하여 여러 대의 데이터베이스에 부하를 분산한다.

## 샤딩

- 데이터베이스에 저장할 데이터가 방대해질 때, 이를 여러 대의 서버(데이터베이스)에 조각내어(Partitioning) 분산 저장하고 처리하는 기술

## MySQL Auto-increment의 한계

MySQL의  Auto-increment는 단일 데이터베이스 내에서는 고유성을 보장하지만, 샤딩된 여러 물리적/논리적 데이터베이스 간에는 전역적인 고유성을 보장할 수 없다.

데이터 마이그레이션이나 복제 환경에서 키 충돌을 방지하려면 전역적으로 고유한 ID가 필수적이다.

# 대안 기술과 한계

## GUID(Globally Unique Identifier)

- 128비트의 식별자 문자열, UUID라고도 함

### 한계

크기가 너무 커서 MySQL에서 인덱싱 성능을 크게 저하시킨다.

MySQL의 속도를 유지하는 방법 중 하나는 쿼리하려는 모든 항목에 인덱스를 생성하고, 실제로는 인덱스에 있는 데이터에 대해서만 쿼리하는 것이다.

데이터베이스를 빠르게 유지하려면 인덱스가 메모리에 적재되어야 하는데, GUID는 크기로 인해 이 효율성을 크게 떨어뜨린다.

## Consistent Hashing (일관된 해싱)

- 0부터 2^32-1까지의 숫자를 원형으로 배치한 해시 링에 서버와 데이터를 배치한 후, 각 데이터를 링 위에서 시계 방향으로 먼저 만나는 서버에 저장하는 방식

Amazon의 Dynamo 와 같은 일부 프로젝트는 GUID/샤딩 문제를 처리하기 위해 데이터 저장소 위에 일관된 해싱 링을 사용한다.

### Dynamo & LSMT (쓰기에 최적화된 구조)

Amazon Dynamo나 Cassandra 같은 NoSQL은 주로 LSM Tree (Log-Structured Merge-Tree) 구조를 사용한다.

- 저렴한 쓰기
    - 데이터를 수정하거나 삭제할 때 기존 데이터를 찾아 바꾸는 게 아니라, 새로운 로그를 끝에 덧붙인다(Append-only).
    - 쓰기 작업이 매우 빠르고 비용이 낮다.
- 일관된 해싱
    - 일관된 해싱은 서버 간 데이터 이동이 잦을 수 있다.(노드 가입/이탈 시)
    - LSMT 환경에서는 데이터 이동도 결국 '새로운 쓰기' 작업으로 처리되므로, 시스템 부하가 상대적으로 적다.
- 가용성 중심
    - Dynamo는 데이터 일관성보다 "언제든 쓸 수 있어야 함(Availability)"을 중시한다.
    - 일관된 해싱을 통해 노드가 바뀌어도 즉각적으로 대응하며 쓰기 작업을 이어가기에 유리하다.

### MySQL & B+ Tree (읽기에 최적화된 구조)

MySQL(InnoDB)은 데이터를 정렬된 상태로 유지하는 B+ Tree 인덱스 구조를 사용한다.

- 빠른 무작위 읽기
    - B+ Tree는 특정 키 값을 찾기 위해 트리를 타고 내려가 데이터 위치를 정확히 짚어내는 성능이 뛰어나다.
- 일관된 해싱과의 충돌
    - 데이터 지역성 파괴
        - MySQL 같은 RDBMS는 연관된 데이터를 물리적으로 가까운 곳에 모아두는 것이 성능에 유리하다. (예: 같은 유저의 게시글들)
        - 일관된 해싱은 키 단위로 링 위에 흩뿌리기 때문에, 여러 테이블을 조인(Join)하거나 범위 검색(Range Scan)을 할 때 여러 서버를 뒤져야 하므로 성능이 급격히 떨어진다.
    - 인덱스 관리 비용
        - 서버가 추가되어 데이터가 이동하면, MySQL은 B+ Tree 인덱스를 다시 구성하고 물리적 페이지를 재정렬해야 한다.
        - 이는 단순한 로그 추가인 LSMT에 비해 훨씬 무겁고 비싼 작업이다.
    - 커넥션 관리
        - MySQL은 연결(Connection) 비용이 상대적으로 높다.
        - 일관된 해싱으로 인해 쿼리가 여러 노드로 분산될 경우, 애플리케이션이 관리해야 할 DB 커넥션 풀이 복잡해지고 오버헤드가 커진다.

## **중앙 집중식 Auto-Increment**

모든 ID를 발급하는 거대한 단일 테이블을 하나 두고, 데이터를 저장할 때마다 이 테이블에서 ID만 발급받는 방식이다.

그러나 초당 수십 개의 사진, 댓글, 태그 등이 업로드되는 환경에서는 ID 발급용 테이블이 순식간에 비대해져 성능 저하와 관리 문제가 발생한다.

# 티켓 서버의 설계

Flickr는 단일 데이터베이스가 설치된 전용 서버를 구축하고, MySQL의 `REPLACE INTO` 명령어를 활용하여 이 문제를 해결했다.

## `REPLACE INTO`

- 기존 테이블에 동일한 기본 키나 고유 키를 가진 데이터가 존재하면, 기존 행을 삭제한 뒤 새로운 행을 삽입하는 MySQL의 비표준 확장 명령어

### 작동 방식

- `Tickets64`와 같은 테이블을 생성하고, 자동 증가하는 `id` 컬럼과 단일 문자 고유 키인 `stub` 컬럼을 만든다.
    
    ```sql
    CREATE TABLE `Tickets64` (
      `id` bigint(20) unsigned NOT NULL auto_increment,
      `stub` char(1) NOT NULL default '',
      PRIMARY KEY  (`id`),
      UNIQUE KEY `stub` (`stub`)
    ) ENGINE=InnoDB
    ```
    
    ```
    +-------------------+------+
    | id                | stub |
    +-------------------+------+
    | 72157623227190423 |    a |
    +-------------------+------+
    ```
    
- 새로운 고유 ID가 필요할 때마다 다음 쿼리를 실행한다.
    - 기존 ‘a’라는 값을 가진 행이 삭제되고 새 행이 삽입되면서, 원자적으로 새로운 자동 증가 ID가 발급된다.
    
    ```sql
    REPLACE INTO Tickets64 (stub) VALUES ('a');
    
    # 새로 발급된 고유 ID를 가져와 사용
    SELECT LAST_INSERT_ID();
    ```
    

테이블 내에 단 하나의 행만 유지되므로 데이터베이스 크기가 비대해지지 않으면서도, 계속해서 순차적으로 증가하는 전역 고유 ID를 얻을 수 있다.

## 고가용성(HA) 및 SPOF 방지

하나의 티켓 서버만 운영할 경우, 해당 서버가 다운되면 전체 ID 발급이 멈추는 문제가 발생하므로 두 대 이상의 서버를 운영하여 가용성을 높인다.

## 홀수/짝수 분산 및 로드 밸런싱

두 서버가 충돌 없이 동시에 ID를 발급하기 위해 MySQL의 시스템 변수를 활용하여 ID 범위를 나눈다.

```sql
TicketServer1:
auto-increment-increment = 2
auto-increment-offset = 1
# 1, 3, 5, 7... (홀수 발급)

TicketServer2:
auto-increment-increment = 2
auto-increment-offset = 2
# 2, 4, 6, 8... (짝수 발급)
```

- 라운드 로빈
    - 여러 대의 서버에 작업을 순차적으로 할당하는 부하 분산 방식
    - 클라이언트는 두 서버에 번갈아 요청을 보내어 부하를 분산한다.
- 홀수/짝수 ID 차이
    - 두 서버의 처리 속도 차이로 인해 홀수와 짝수 ID의 발급 개수가 수십만 개 정도 차이 날 수 있으나, 전역적 고유성만 유지된다면 서비스에는 아무런 피해가 없다.

## 엔티티별 전용 시퀀스 관리

모든 ID를 하나의 카운터로 관리하지 않고, 데이터의 성격과 처리량에 따라 별도의 테이블 시퀀스를 운영한다.

Sequence (시퀀스)

- 데이터베이스 내에서 순차적으로 증가하는 고유한 숫자를 생성해주는 객체나 테이블
- 주로 기본 키(PK) 값을 생성할 때 사용한다.

### **주요 시퀀스 테이블**

- Tickets32 / Tickets64
    - 데이터 타입 크기에 따른 구분 (32비트/64비트 정수)
- 오프라인 작업
    - 처리량이 매우 많으므로 별도의 시퀀스를 사용하여 사진이나 계정 같은 중요 항목의 ID 번호가 불필요하게 급증하는 것을 방지한다.
- 그룹 및 계정
    - 상대적으로 생성 빈도가 낮으므로 별도의 시퀀스로 분리하여 관리 효율성을 높인다.
- 사진
    - 기존에 사용하던 자동 증가 테이블과 동기화하여, 발급된 ID만 보고도 현재까지 업로드된 총 사진 수를 쉽게 파악할 수 있는 관리 지표로 활용한다.

## 이 설계의 장점

Flickr가 복잡한 분산 알고리즘이나 고가의 솔루션 없이 기존 MySQL의 기본 기능만으로 구현했기 때문에 비용이 저렴하다.

- Zero Communication
    - 서버 간 통신 비용(Network Round-trip)이 없어 속도가 매우 빠르다.
- Stateless 클라이언트
    - 애플리케이션은 어느 서버에 접속하든 고유한 ID를 받을 수 있으므로 로직이 단순해진다.
- 예측 가능성
    - 발급된 ID만 보고도 어떤 서버에서 생성된 ID인지 즉시 파악할 수 있어 디버깅에 유리하다.

> <참고>
이 방식은 ID가 완전히 순차적으로 생성되지 않을 수 있다. (예: 1번 서버 요청 후 2번 서버 요청이 지연되면 ID가 1, 3, 2 순으로 들어올 수 있음)
하지만 분산 환경에서 '전역적 고유성'을 보장하는 것이 더 중요하므로 이는 사소한 트레이드오프로 간주된다.
