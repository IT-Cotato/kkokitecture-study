# 검색어 자동완성

검색어 자동완성은 검색 시스템의 기본 기능이다. 

사용자가 직접 검색어를 입력하는 수고를 덜어주고, 오타를 입력하지 않도록 도와주며, 사용자의 의도와 연관된 검색어를 발견할 수 있게 도와준다. 

즉, 사용자가 원하는 결과를 빠르고 쉽게 찾도록 돕는 것이 목적이다. 

# **Efficient Neural Query Auto Completion**

## **MCG (Maximum Context Generation)**

!image.png

### 작동 방식

- 'cheapest flights from seattle to' 같은 검색어가 들어오면 검색어 로그로 구성한 FST를 통해 뒤에 나올 단어를 생성한다.
- 생성할 단어가 없을 때는 앞에서부터 하나씩 단어를 지워가며 검색어 후보군을 생성한다.

### 특징

단계적으로 맥락을 덜 고려하게 되는 방식으로, 예제의 경우 초반에는 'flights from seattle to' → 'sfo'를 생성하다가 앞 단어가 생략되면서 이후에는 'to' → 'airport', 'study'까지 다양한 검색어를 생성한다.

### 장점

- 단순하지만 성능이 좋음
- 이전에 검색된 적 없는 새로운 검색어를 추천 가능
- MCG 기반으로 검색어 후보군에 대한 Ranking을 학습한 언어 모델이 높은 성능을 보인다.

## **FST (Finite State Transducers)**

알고리즘 구현을 위해 먼저 검색 로그를 기반으로 QueryFST와 SuffixFST를 만들어야 한다. 

QueryFST는 검색어들을 그대로 사용하고, SuffixFST는 검색어들을 뒤에서부터 n-gram으로 구성한다.

## 자동완성의 prefix 단위

검색어 자동완성에서 한글은 독특한 특징을 가진다. 

교착어로서 하나의 문자를 초성·중성·종성으로 나눌 수 있다는 점이다. 

이로 인해 조합형(초성·중성·종성을 각각 따로 표시)과 완성형(글자 하나마다 코드를 부여) 두 가지 인코딩 방식이 존재한다.

### 문제

현재는 완성형 인코딩을 사용하기 때문에 'ㅅ', '사' 각각이 하나의 문자로 인식된다. 

그래서 '상습사기'라는 검색어 로그로 전처리 없이 QueryFST를 만들면 `'상' → '습' → '사' → '기'`로 구성된다.

### 해결

하지만 이는 키보드로 자음·모음 단위로 하나하나 입력하는 방식과 차이가 있다. 

따라서 QueryFST도 자음·모음 단위로 구성되어야 한다.

```
'ㅅ' -> 'ㅏ' -> 'ㅇ' -> 'ㅅ' -> 'ㅡ' -> 'ㅂ' -> 'ㅅ' -> 'ㅏ' -> 'ㄱ' -> 'ㅣ'
```

## 추천 검색어 성능

엘박스는 검색어 자동완성 기능을 '추천 검색어'라는 서비스명으로 제공한다. 

성능 지표로는 SR@K(success rate at top K)를 사용한다.

> **SR@K (Success Rate at top K)**
> 
> 
> 실제 검색된 쿼리들 중에서 제안된 추천 검색어가 (상위 K개 안에) 포함된 비율 
> 

랭킹이 지표로 들어가는 경우 보통 MRR을 사용하지만, 엘박스의 추천 검색어 창에는 '빠른 검색 명령어', '최근 검색 명령어' 등 다른 카테고리 추천이 함께 포함되어 있어, 랭킹 수치에 크게 좌우되는 MRR보다 SR@K가 더 적합한 지표로 판단되었다.

> **MRR (Mean Reciprocal Rank, 평균 역순위)**
> 
> - 정답이 검색 결과에서 몇 번째에 등장하는지를 역수로 환산해 평균 낸 랭킹 성능 지표
> - 정답이 상위에 위치할수록 값이 높아진다.

### 성능 개선

!image.png

MCG 알고리즘이 검색어 빈도수를 기반으로 후보군을 만들기 때문에, 계속 추가되는 쿼리 로그로 인해 더 적합한 후보군을 추천하게 된다. 

하지만 어느 정도 기간이 지나 로그가 충분히 쌓이면, 새 로그가 추가되어도 추천 검색어에는 큰 차이가 생기지 않는다. 

여기에 문자 단위 자동완성을 자음·모음 단위로 변경하면서 더 많은 추천이 가능해졌고 실제 성능도 향상되었다.

# 오타교정

검색어 입력 오타는 크게 세 가지 종류가 있다.

- 검색어 입력 오타
    - '음쥬운전' → '음주운전' → SymSpell로 오타 교정
- 한글을 영어로 입력
    - 예) 'dmawndnswjs' → '음주운전' → 알파벳과 자음모음 매칭 후 조합
- 띄어쓰기
    - 예) '공유재산변상금' → '공유재산 변상금' → soyspacing을 통한 띄어쓰기 교정

## SymSpell

오타 교정 알고리즘은 edit distance를 기반으로 구현이 되어 있다.

> **Edit Distance (편집 거리)**
> 
> 
> 한 문자열을 다른 문자열로 바꾸는 데 필요한 최소 편집(삽입·삭제·교체) 횟수
> 

예시:  '음주운전'에 대해 edit distance 1을 기준으로 하는 오타

-> `(자모기준) 음주운전 -> [음쥬운전, 음주운젼, 은주운전 등...]`

edit distance 기반 오타를 미리 생성해 매핑하는 방식은, 단어가 길어질수록 생성할 오타 후보군 수가 많아져 메모리 사용량이 급격히 증가한다.

### **SymSpell (Symmetric Delete Spelling Correction)**

모든 오타 후보군을 생성하는 것이 아니라, edit distance 기준 '삭제'만을 추가하고, 오타 교정으로 들어온 입력 또한 '삭제' 기준의 후보군을 만들어 탐색하는 방식이다. 

삽입·교체를 모두 생성하는 대신 '삭제' 연산만 대칭적으로 적용해, 메모리와 검색 속도 면에서 기존보다 크게 빨라졌다.

## 띄어쓰기

한국어 띄어쓰기는 어려운 문제다. 예를 들어 '이번 주', '지난주', '다음 주'처럼 규칙이 헷갈린다. 사람은 띄어쓰기가 틀려도 문맥으로 이해할 수 있지만, 시스템에게는 혼동을 줄 수 있다.

### 필요성

검색의 가장 기본 알고리즘은 TF-IDF로, Term을 기반으로 구성된다. 

Term은 보통 한글의 형태소 단위로 구성되므로, 문서를 형태소 단위로 잘 나누는 것이 제대로 된 검색 결과를 만드는 기본이 된다.

형태소를 제대로 나누려면 올바른 띄어쓰기가 필요하다. 

예를 들어 '공유재산 변상금'은 ["공유", "재산", "변상", "금"]으로 잘 나뉘지만, '공유재산변상금'은 ["공유", "재", "산변", "상금"]처럼 잘못 분리될 수 있다.

### 해결

띄어쓰기는 lovit의 soyspacing으로 교정한다. 

규칙 기반 휴리스틱 알고리즘이라 속도가 빠르고, 더 많은 판례에서 보이는 띄어쓰기 형식으로 글이 교정되기 때문에 선택되었다.

## 검색 성능 Zero Result Rate

오타 및 띄어쓰기를 교정하면 검색 성능 지표 중 ZRR에 직접적인 영향을 줄 수 있다. 

검색어에 오타가 있거나 띄어쓰기가 잘못되면 아무런 검색 결과를 얻지 못하는 경우가 많기 때문이다.

ZRR 지표는 다양한 상황에 의존해 값이 요동치는 경향이 있지만, 오타·띄어쓰기 교정 이후 그 비율이 줄어드는 것을 확인할 수 있다.

> **ZRR (Zero Result Rate)**
> 
> 
> 전체 검색 중 검색 결과가 하나도 나오지 않은 검색의 비율
> 

## 검색어 로그 파이프라인

검색어 자동완성과 오타 교정 모두 검색어 로그를 기반으로 하므로, 주기적으로 업데이트해 주는 데이터 파이프라인이 필요하다. 

이 파이프라인을 통해 기존 검색어 로그를 기반으로 서비스를 업데이트하면, 데이터가 쌓일수록 점점 더 정확한 검색어를 추천할 수 있게 된다.

### **Apache Airflow**

데이터 파이프라인 도구로 Apache Airflow를 사용한다. 

Python 코드를 기반으로 워크플로우를 손쉽게 작성할 수 있고, Airflow 2 버전에서는 TaskFlow API를 통해 더 직관적으로 코드를 작성할 수 있다.
