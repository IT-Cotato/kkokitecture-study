# 1단계 문제 이해 및 설계 범위 확정

## 요구사항

- 빠른 응답 속도: 페이스북 문서 → 시스템 응답속도는 100ms 이내
- 연관성: 사용자가 입력한 단어와 연관된 것이어야 함
- 정렬: 시스템의 계산 결과는 인기도 등의 순위 모델에 의해 정렬되어 있어야 함
- 규모 확장성
- 고가용성

## 개략적 규모 추정

- 일간 능동 사용자(DAU)는 천만 명으로 가정
- 평균적으로 한 사용자는 매일 10건의 검색을 수행한다고 가정
- 질의할 때마다 평균적으로 20바이트의 데이터를 입력한다고 가정
    - 문자 인코딩 방법: ASCII → 1문자=1바이트
    - 질의문은 평균적으로 4개 단어로 구성, 각 단어는 평균 다섯 글자로 구성
    - 질의당 평균 4 x 5 = 20바이트
- 검색창에 글자를 입력할 대마다 클라이언트는 검색어 자동완성 백엔드에 요청을 보냄
    - 평균적으로 1회 검색당 20건의 요청
    - ex) dinner 검색 시 다음 6개 요청이 순차적으로 백엔드에 전송
        - search?q=d search?q=di search?q=din search?q=dinn search?q=dinne search?q=dinner
- 대략 초당 24,000건의 질의(QPS) 발생 (=10,000,000사용자 x 10질의 / 일 x 20자 / 24시간 / 3600초)
- 최대 QPS = QPS x 2 = 대략 48,000
    
    > **x2 인 이유**
    > 
    > - 정확한 배수는 실제 서비스마다 다르고, 시간대별 트래픽 로그를 분석해야 정확히 알 수 있다.
    > - 하지만 시스템 설계 인터뷰나 개략적 추정(back-of-envelope estimation) 단계에서는 그런 실측 데이터가 없으므로, **피크 시간대에는 평균의 대략 2배 정도 트래픽이 몰린다**는 보수적이고 관습적인 가정을 사용한다.
    > - 안전 마진을 확보하기 위한 근사치
- 질의 중 20% 가량은 신규 검색어라고 가정
    - 0.4GB = 10,000,000사용자 x 10질의  / 일 x 20자 x 20%
    - 매일 0.4GB의 신규 데이터가 시스템에 추가됨

```sql
WHERE query Like `prefix%`
ORDER BY frequency DESC
LIMIT 5
```

# 3단계 상세 설계

## 트라이(trie) 자료구조

관계형 데이터베이스를 이용해 가장 인기 있는 다섯 개 질의문을 골라내는 방안은 비효율적이다.

⇒ 트라이(trie, 접두어 트리 prefix tree라고도 함)를 사용해 해결

트라이는 문자열들을 간략히 저장할 수 있는 자료구조다.

### 트라이 자료구조의 핵심 아이디어

- 트라이는 트리 형태의 자료구조
- 이 트리의 루트 노드는 빈 문자열을 나타낸다.
- 각 노드는 글자 하나를 저장, 26개의 자식 노드를 가질 수 있다.
- 각 트리 노드는 하나의 단어 또는 접두어 문자열을 나타낸다.

<img width="742" height="474" alt="Image" src="https://github.com/user-attachments/assets/2d19d8d8-9727-45c4-95f9-3515d9f3299a" />

기본 트라이 자료구조는 노드에 문자들을 저장한다.

이용 빈도에 따라 정렬된 결과를 내기 위해선 노드에 빈도 정보까지 저장해야 한다.

<img width="696" height="398" alt="Image" src="https://github.com/user-attachments/assets/32bee9ef-ef4f-4d2f-8bef-c72c7c31c398" />

- p: 접두어의 길이
- n: 트라이 안에 있는 노드 개수
- c: 주어진 노드의 자식 노드 개수

### 가장 많이 사용된 질의어 k개를 찾는 방법

- 해당 접두어를 표현하는 노드를 찾는다.
    - 시간 복잡도= O(p)
- 해당 노드부터 시작하는 하위 트리 탐색하여 모든 유효 노드를 찾는다.
    - 유효 노드: 유효한 검색 문자열을 구성하는 노드
    - 시간 복잡도 = O(c)
- 유효 노드들을 정렬하여 가장 인기 있는 검색어 k개를 찾는다.
    - 시간 복잡도 = O(clogc)

### 예제

<img width="634" height="442" alt="Image" src="https://github.com/user-attachments/assets/7a1e6c84-dfa5-47b0-af01-f247133f9130" />

k=2, 검색창에 ‘be’를 입력한 경우

1. 접두어 노드 ‘be’를 찾는다.
2. 해당 노드부터 시작하는 하위 트리를 탐색하여 모든 유효 노드를 찾는다.
    1. 여기서는 [beer:10], [best:35], [bet:29]
3. 유효 노드를 정렬하여 2개만 골라낸다.
    1. [best:35], [bet:29]

알고리즘의 시간 복잡도 = O(p) + O(c) + O(clogc)

직관적이지만, 최악의 경우 k개 결과를 얻으려고 전체 트라이를 검색해야 할 수 있다.

⇒ 해결방법 1. 접두어의 최대 길이 제한 2. 각 노드에 인기 검색어를 캐시

### 접두어의 최대 길이 제한

사용자가 긴 검색어를 입력하는 일은 거의 없으므로 p 값은 작은 정숫값이라고 가정해도 안전하다.

검색어의 최대 길이를 제한한다면 접두어 노드를 찾는 단계의 시간 복잡도는 O(1)로 바뀐다.

### 노드에 인기 검색어를 캐시

각 노드에 k개의 인기 검색어를 저장해 두면 전체 트라이를 검색하는 일을 방지할 수 있다.

각 노드에 질의어를 저장할 공간이 많이 필요하지만, 빠른 응답속도가 중요할 때는 이 정도를 희생할 가치가 있다.

## 데이터 수집 서비스

사용자가 검색창에 타이핑 할 때마다 실시간으로 데이터를 수정하는 방법의 문제점

- 매일 수천만 건의 질의가 입력되는데 그때마다 트라이를 갱신하면 질의 서비스는 심각하게 느려짐
- 일단 트라이가 만들어지고 나면 인기 검색어는 자주 바뀌지 않음 → 트라이를 자주 갱신할 필요 X

규모 확장이 쉬운 데이터 수집 서비스를 만들려면 데이터가 어디서 오고 어떻게 이용되는 지를 봐야 한다.

- 트위터 같은 실시간 애플리케이션: 제안되는 검색어를 항상 신선하게 유지
- 구글 검색 등: 자주 바꿀 필요 없음

## 트라이(trie)  연산

검색어 자동완성 시스템의 핵심 컴포넌트

### 트라이 생성

작업 서버가 담당하며, 데이터 분석 서비스의 로그나 데이터베이스로부터 취합된 데이터를 이용한다.

### 트라이 갱신

1. 매주 한 번 갱신: 새로운 트라이를 만들고 기존 트라이 대체
2. 트라이의 각 노드를 개별적으로 갱신
    - 본 설계에서는 이 방법을 채택하지 않음 → 성능이 안 좋음
    - 트라이가 작을 때는 고려할 방안
    - 트라이 노드를 갱신할 때 그 모든 상위 노드도 갱신해야 하는데, 상위 노드에도 인기 검색어 질의 결과가 보관되기 때문이다.

### 검색어 삭제

트라이 캐시 앞에 필터 계층을 두고 부적절한 질의어가 반환되지 않도록 한다.

필터 규칙에 따라 검색 결과를 자유롭게 변경할 수 있다.

데이터베이스에서 해당 검색어를 물리적으로 삭제하는 것은 다음번 업데이트 사이클에 비동기적으로 진행하면 된다.

## 저장소 규모 확장

### **첫 글자를 기준으로 샤딩하는 방법**

- 두 대 서버가 필요한 경우
    - ‘a’~’m’으로 시작하는 검색어 → 첫 번째 서버에 저장
    - 나머지 → 두 번째 서버에 저장
- 세 대 서버가 필요한 경우
    - ‘a’~’i’으로 시작하는 검색어 → 첫 번째 서버에 저장
    - ‘j’~’r’으로 시작하는 검색어 → 두 번째 서버에 저장
    - 나머지 → 두 번째 서버에 저장

문제점: 사용 가능한 서버는 최대 26대로 제한되는데, 영어 알파벳에는 26자 밖에 없기 때문이다.

이 이상으로 서버 대수를 늘리려면 샤딩을 계층적으로 해야 한다.

→ 데이터를 각 서버에 균등하게 배분하기가 불가능

### 해결 - 과거 질의 데이터의 패턴을 분석해 샤딩

검색어 대응 샤드 관리자는 어떤 검색어가 어느 저장소 서버에 저장되는지에 대한 정보를 관리한다.

- ‘s’로 시작하는 검색어의 양이 ‘u’, ‘v’, ‘w’, ‘x’, ‘y’, ‘z’로 시작하는 검색어를 전부 합친 것과 비슷하다면 각각을 샤드 하나로 두어도 충분
