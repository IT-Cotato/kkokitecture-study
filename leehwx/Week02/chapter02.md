# 2장. 개략적인 규모 추정

시스템 설계 면접을 볼 때, 때로는 시스템 용량이나 성능 요구사항을 개략적으로 추정해 보라는 요구를 받게 된다.

> 개략적인 규모 추정은 보편적으로 통용되는 성능 수치상에서 사고 실험을 행하여 추정치를 계산하는 행위로서, 어떤 설계가 요구사항에 부합할 것인지 보기 위한 것이다.
> 

개략적 규모 추정을 효과적으로 하려면 규모 확장성을 표현하는 데 필요한 기본기에 능숙해야 한다. 

# 2의 제곱수

- ASCII 문자 하나가 차지하는 메모리 크기가 1바이트

수치 분석 결론

- **메모리는 빠르지만 디스크는 아직도 느리다.**
    - 메인 메모리 참조(100ns)와 디스크 탐색(2,000,000ns = 2ms)을 비교하면 2만 배 차이가 난다.
    - 따라서 성능을 위해서는 데이터를 최대한 메모리에 캐싱하려는 노력이 필요하다.
- **디스크 탐색(seek)은 가능한 한 피하라.**
    - 디스크 탐색(2ms)는 디스크에서 1MB를 순차적으로 읽는 시간(825µs)보다 훨씬 길다.
    - 순차 읽기는 빠르지만, 랜덤 액세스는 성능 저하를 일으킨다.
- **단순한 압축 알고리즘은 빠르다.**
    - 1KB를 Zippy로 압축하는 데 걸리는 시간은 2,000ns(2µs)이다.
    - 따라서 CPU를 조금 더 써서(단순 압축) 데이터의 크기를 줄이는 것이 시스템 성능 면에서 이득이다.
- **데이터를 인터넷으로 전송하기 전에 가능하면 압축하라.**
    - 네트워크 전송 시간은 CPU 전송 시간보다 압도적으로 길다.
    - 1Gbps 네트워크에서 2KB를 보내는 시간보다, 데이터를 압축해서 보내는 CPU 비용이 훨씬 저렴하다.
    - 10MB의 데이터를 1MB로 압축해서 보내면 네트워크 전송 시간은 1/10로 줄어든다.
        - 압축에 드는 CPU 시간(ms 단위 미만)을 투자해서 수십~수백 ms가 걸릴 수 있는 네트워크 전송 시간을 아낄 수 있다.
- **데이터 센터는 보통 여러 지역(region)에 분산되어 있고, 센터들 간에 데이터를 주고 받는 데는 시간이 걸린다.**
    - 같은 데이터 센터 내 왕복 시간(0.5ms)과 대륙 간 왕복 시간(CA to Netherlands: 150ms)은 300배 차이가 난다.
    - 글로벌 서비스를 설계할 때는 사용자와 가까운 지역에 서버를 두는 에지 컴퓨팅이나 멀티 리전 배치가 필수적이다.

# 가용성에 관계된 수치들

### **고가용성(high availability)**

시스템이 오랜 시간 동안 지속적으로 중단 없이 운영될 수 있는 능력

- 고가용성을 표현하는 값은 퍼센트로 표현
    - 100% : 시스템이 단 한 번도 중단된 적이 없었음
    - 대부분의 서비스는 99%~100% 사이 값을 가진다.

### SLA(Service Level Agreement)

서비스 사업자와 고객 사이에 맺어진 합의

- 서비스 사업자가 보편적으로 사용하는 용어
- 서비스 사업자가 제공하는 서비스의 가용시간(uptime)이 공식적으로 기술되어 있다.
    - 아마존, 구글, 마이크로소프트 같은 사업자는 99% 이상의 SLA를 제공한다.

가용시간은 관습적으로 9를 사용해 표시한다. 9가 많으면 많을수록 좋은 것이다.

# 예제: 트위터 QPS와 저장소 요구량 추정

## 가정

- 월간 능동 사용자는 3억명
- 50%의 사용자가 트위터를 매일 사용
- 평균적으로 각 사용자는 매일 2건의 트윗을 올림
- 미디어를 포함하는 트윗은 10%
- 데이터는 5년간 보관

## 추정

### QPS(Query Per Second)란 무엇인가?

QPS는 초당 처리량 즉, 1초 동안 서버가 몇 개의 요청(Query)를 처리할 수 있는지, 사용자가 몇 개의 요청을 보내는지를 나타내는 지표이다.

- 예를 들어 QPS가 3,500이라면, 1초에 3,500건의 트윗이 전 세계에서 동시에 올라오고 있다는 뜻이다.

### **QPS를 계산하는 이유**

1. **서버 및 인프라 규모 산정 (Sizing)**
    - 서버 한 대가 초당 처리할 수 있는 요청 수는 한계가 있다.
    - 서버 한 대가 초당 500개의 요청을 처리한다면, 평균 QPS 3,500을 견디기 위해서는 최소 7대의 서버가 필요하다.
        - 여기에 장애 대비용(Redundancy) 서버까지 고려해 총 몇 대의 서버가 필요한 지 결정
2. **데이터베이스 선정 및 설계**
    - Write QPS(쓰기) vs Read QPS(읽기)
        - 트위터는 읽기 요청이 쓰기 요청보다 훨씬 많다.
        - 쓰기 QPS가 3,500이라면 일반적인 RDBMS 한 대로도 감당 가능하지만, 만약 350,000이라면 단일 DB로는 불가능 →  샤딩(Sharding)이나 NoSQL 도입을 고려해야 한다.
3. **피크 타임(Peak Time) 대비**
    - 평균치에 맞춰 설계하면 안 된다.
    - 트래픽에 몰리는 시간에도 서비스가 유지되도록 최대치를 견딜 수 있도록 해야 한다.
4. 비용 예측
    - QPS가 높을수록 네트워크 대역폭을 많이 사용한다.

### QPS(Query Per Second) 추정치

- 일간 능동 사용자(Daily Active User, DAU) = 3억 x 50% = 1.5억
- QPS = 1.5억 x 2 트윗 / 24시간 / 3600초 = 약 3500
- 최대 QPS(Peek QPS) = 2 x QPS = 약 7000

### 미디어 저장을 위한 저장소 요구량

- 평균 트윗 크기
    - tweet_id에 64바이트
    - 텍스트에 140바이트
    - 미디어에 1MB
    - 미디어 저장소 요구량 : 1.5억 x 2 x 10% x 1MB = 30TB / 일
        - 일간 능동사용자 x 하루 트윗 수 x 미디어 포함 트윗 비율 x 미디어 크기
    - 5년간 미디어를 보관하기 위한 저장소 요구량 : 30TB x 365 x 5 = 약 55PB

# 팁

개략적인 규모 추정과 관계된 면접에서 가장 중요한 것은 문제를 풀어 나가는 절차다.

올바른 절차를 밟느냐가 결과를 내는 것보다 중요하다. 즉 문제 해결 능력이 중요하다.

- 근사치를 활용한 계산
    - 계산 결과의 정확함을 평가하는 것이 목적이 아니므로 “99987/9.1”의 계산 결과는 무엇인가?에 시간을 쓰는 것은 낭비다.
    - “100,000/10”으로 적절한 근사치를 활용해 간소화하자.
- 가정(assumption)들은 적어 두라. 나중에 살펴볼 수 있도록.
- 단위(unit)을 붙이라.
    - 5KB인지 5MB인지 알 수가 없다.
    - 단위를 붙이는 습관을 들여두면 모호함을 방지할 수 있다.
- 많이 출제되는 개략적 규모 추정 문제는 QPS, 최대 QPS, 저장소 요구량, 캐시 요구량, 서버 수 등을 추정하는 것이다.
    - 면접에 임하기 전 이런 값들을 계산하는 연습을 미리 하자.
