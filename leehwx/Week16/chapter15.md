# 15장 구글 드라이브 설계

# 1단계 문제 이해 및 설계 범위 확정

## 설계 범위

- 주요 기능: 파일 업로드/다운로드, 파일 동기화, 알림
- 모바일 앱, 웹 앱 지원
- 모든 파일 형식 지원
- 파일 암호화(저장소의 파일은 반드시 암호화)
- 파일 크기 10GB 제한
- 일간 능동 사용자(DAU) 1000만 명

## 기능적 요구사항

- 파일 추가: 가장 쉬운 방법은 파일을 구글 드라이브 안으로 drag-and-drop
- 파일 다운로드
- 여러 단말에 파일 동기화: 한 단말에서 파일을 추가하면 다른 단말에도 자동 동기화
- 파일 갱신 이력 조회(revision history)
- 파일 공유: 가족, 친구, 동료와 공유
- 파일 편집/삭제/새롭게 공유 시 알림 표시

> 구글 문서 편집 및 협업 기능(여러 명이 같은 문서를 동시에 편집하는 기능)은 설계 범위에서 제외한다.
> 

## 비-기능적 요구사항

- 안정성(Reliability)
    - 저장소 시스템에서 안정성은 아주 중요하다.
    - 데이터 손실은 발생하면 안 된다.
- 빠른 동기화 속도
    - 파일 동기화에 시간이 너무 많이 걸리면 사용자는 인내심을 잃고 제품을 떠난다.
- 네트워크 대역폭
    - 이 제품이 네트워크 대역폭을 불필요하게 많이 소모한다면 사용자는 좋아하지 않을 것이다.
    - 모바일 데이터 플랜을 사용하는 경우면 더욱 그렇다.
- 규모 확장성(Scalability)
    - 아주 많은 양의 트래픽도 처리 가능해야 한다.
- 높은 가용성(High availability)
    - 일부 서버에 장애가 발생하거나, 느려지거나, 네트워크 일부가 끊겨도 시스템은 계속 사용 가능해야 한다.

## 개략적 추정치

- 가입 사용자: 5000만 명 / DAU 사용자: 1000만 명
- 모든 사용자에게 10GB의 무료 저장공간 할당
- 매일 각 사용자가 평균 2개 파일을 업로드한다고 가정, 각 파일의 평균 크기는 500KB
- 읽기:쓰기 비율 1:1
- 필요한 저장공간 총량 = 5000만 사용자 × 10GB = **500 페타바이트(PB)**
- 업로드 API QPS = 1000만 사용자 × 2회 업로드 / 24시간 / 3600초 = **약 240**
- 최대 QPS = QPS × 2 = **480**
    
    > **× 2 인 이유**
    > 
    > - 정확한 배수는 실제 서비스마다 다르고, 시간대별 트래픽 로그를 분석해야 정확히 알 수 있다.
    > - 하지만 시스템 설계 인터뷰나 개략적 추정(back-of-envelope estimation) 단계에서는 그런 실측 데이터가 없으므로, 피크 시간대에는 평균의 대략 2배 정도 트래픽이 몰린다는 보수적이고 관습적인 가정을 사용한다.
    > - 안전 마진을 확보하기 위한 근사치다.

# 2단계 개략적 설계안 제시 및 동의 구하기

처음부터 개략적 설계 다이어그램을 제시하는 대신, 서버 한 대로 시작해 점진적으로 수백만 사용자를 지원하도록 규모를 확장하는 방식으로 접근한다. 

## 초기 설계

우선 아래와 같은 구성의 서버 한 대로 시작한다.

- 파일을 올리고 다운로드하는 과정을 처리할 웹 서버
- 메타데이터(사용자 데이터, 로그인 정보, 파일 정보 등)를 보관할 데이터베이스
- 파일을 저장할 저장소 시스템. 파일 저장을 위해 1TB 공간 사용

몇 시간에 걸쳐 아파치(Apache) 웹 서버, MySQL 데이터베이스, 업로드된 파일을 저장할 루트 디렉터리 `drive/`를 설정한다.

- `drive/` 아래에는 **네임스페이스(namespace)** 라 불리는 디렉터리 목록이 있다.
- 각 네임스페이스에는 해당 사용자가 업로드한 모든 파일이 담긴다.
- 서버에 저장된 파일명은 원본 파일명과 동일하게 유지한다.
- 각 파일과 폴더는 **네임스페이스 + 상대 경로**를 이어 붙여 유일하게 식별할 수 있다.

## API

세 가지 API가 필요하다: **파일 업로드, 파일 다운로드, 파일 갱신 이력 조회**

### 1) 파일 업로드 API

두 가지 업로드 방식을 지원한다.

- **단순 업로드(simple upload)**: 파일 크기가 작을 때 사용한다.
- **이어 올리기(resumable upload)**: 파일 크기가 크고 네트워크가 끊길 가능성이 높을 때 사용한다.

이어 올리기 예시:

```
URL: https://api.example.com/files/upload?uploadType=resumable

Params:
  - uploadType=resumable
  - data: 업로드할 로컬 파일
```

이어 올리기는 다음 세 단계로 이루어진다.

1. 이어 올리기 URL을 받기 위한 최초 요청 전송
2. 데이터를 업로드하고 업로드 상태 모니터링
3. 업로드가 중단되면 중단된 시점부터 다시 업로드

### 2) 파일 다운로드 API

예시:

```
URL: https://api.example.com/files/download

Params:
  - path: 다운로드할 파일 경로

Params 예시:
{
  "path": "/recipes/soup/best_soup.txt"
}
```

### 3) 파일 갱신 이력 조회 API

예시:

```
URL: https://api.example.com/files/list_revisions

Params:
  - path: 갱신 이력을 조회할 파일 경로
  - limit: 조회할 갱신 이력의 최대 개수

Params 예시:
{
  "path": "/recipes/soup/best_soup.txt",
  "limit": 20
}
```

> 모든 API는 사용자 인증을 요구하며 HTTPS를 사용한다. SSL로 클라이언트와 백엔드 서버 간 데이터 전송을 보호한다.
> 

## 한 대 서버의 제약 극복

파일이 계속 업로드되면 결국 저장 공간 부족 경고를 받게 된다.

가장 먼저 떠오르는 해결책은 데이터를 **샤딩(sharding)** 하여 여러 저장 서버에 나눠 저장하는 것이다. 예를 들어 `user_id` 기준으로 샤딩할 수 있다.

<img width="436" height="312" alt="Image" src="https://github.com/user-attachments/assets/3b0408e1-29ba-4956-b9e5-bc34398bbc21" />

샤딩으로 저장 공간 문제는 해결했지만, 저장 서버 장애 시 데이터 손실 위험이 남는다. 

넷플릭스, 에어비앤비 같은 여러 선도 기업이 사용하는 **Amazon S3**를 도입한다.

- Amazon S3는 업계 최고 수준의 확장성, 가용성, 보안, 성능을 제공하는 객체 저장소 서비스다.
- **같은 리전(region) 복제**와 **여러 리전 간 복제**를 모두 지원한다. 리전은 AWS 데이터센터가 위치한 지리적 영역이다.
- 여러 리전에 파일을 중복 저장해 데이터 손실을 막고 가용성을 보장한다. (버킷은 파일 시스템의 폴더와 같은 개념)

<img width="616" height="252" alt="Image" src="https://github.com/user-attachments/assets/ffd44fef-9bd9-4eca-9547-58e43bf95542" />

이후 다음과 같은 부분을 추가로 개선한다.

- **로드밸런서(load balancer)**: 네트워크 트래픽을 고르게 분산하고, 웹 서버 장애 시 트래픽을 재분배한다.
- **웹 서버**: 로드밸런서 도입 후 트래픽에 따라 웹 서버를 쉽게 추가/제거할 수 있다.
- **메타데이터 데이터베이스**: 서버에서 분리해 단일 장애 지점(SPOF)을 없앤다. 가용성·확장성을 위해 데이터 복제와 샤딩을 적용한다.
- **파일 저장소**: Amazon S3를 사용하고, 가용성과 내구성을 위해 두 개의 서로 다른 지리적 리전에 파일을 복제한다.

이 개선을 적용하면 웹 서버, 메타데이터 DB, 파일 저장소가 단일 서버에서 성공적으로 분리된다.

## 동기화 충돌(Sync conflicts)

구글 드라이브처럼 큰 저장 시스템에서는 동기화 충돌이 종종 발생한다. 두 사용자가 같은 파일이나 폴더를 동시에 수정하면 충돌이 생긴다.

**처리 전략**: 먼저 처리된 버전이 이기고(win), 나중에 처리된 버전은 충돌(conflict)이 발생한 것으로 본다.

- 예: 사용자 1과 사용자 2가 같은 파일을 동시에 수정했지만 사용자 1의 파일이 먼저 처리되면, 사용자 1의 수정은 반영되고 사용자 2는 동기화 충돌을 받는다.
- 충돌이 나면 시스템은 두 버전(사용자 2의 로컬 사본과 서버의 최신 버전)을 함께 제시한다.
- 사용자 2는 두 파일을 병합하거나 한 버전으로 다른 버전을 덮어쓸 수 있다.

## 개략적 설계안(High-level design)

<img width="596" height="474" alt="Image" src="https://github.com/user-attachments/assets/4644a550-39a3-4bac-b1a1-350ca8886d6e" />

주요 컴포넌트는 다음과 같다.

- **사용자(User)**: 브라우저 또는 모바일 앱으로 애플리케이션 사용
- **블록 저장소 서버(Block servers)**
    - 블록을 클라우드 저장소에 업로드
    - 파일은 여러 블록으로 분할되고, 각 블록은 고유한 해시값을 가지며 메타데이터 DB에 저장된다.
    - 각 블록은 독립된 객체로 저장소(S3)에 저장되며, 파일을 복원할 때는 블록을 특정 순서로 이어 붙인다.
    - 블록 크기는 드롭박스를 참고해 **최대 4MB**로 잡는다.
- **클라우드 저장소(Cloud storage)**: 파일을 작은 블록으로 나눠 저장
- **아카이빙 저장소(Cold storage)**: 오랫동안 사용되지 않은 비활성 데이터 보관용
- **로드밸런서(Load balancer)**: 요청을 API 서버들에 고르게 분산
- **API 서버**: 업로드 흐름을 제외한 거의 모든 것을 담당(사용자 인증, 사용자 프로파일 관리, 파일 메타데이터 갱신 등)
- **메타데이터 데이터베이스**: 사용자·파일·블록·버전 등의 메타데이터 저장(파일 자체는 클라우드에 있고, 여기에는 메타데이터만 저장)
- **메타데이터 캐시**: 자주 쓰이는 메타데이터를 캐싱해 빠르게 조회
- **알림 서비스(Notification service)**: 발행/구독(pub/sub) 시스템. 특정 이벤트(파일 추가/편집/삭제) 발생 시 관련 클라이언트에 통지해 최신 변경분을 받아가도록 한다.
- **오프라인 사용자 백업 큐(Offline backup queue)**: 클라이언트가 오프라인이라 최신 변경분을 받을 수 없을 때, 정보를 보관했다가 온라인이 되면 동기화

# 3단계 상세 설계

여기서는 블록 저장소 서버, 메타데이터 DB, 업로드 흐름, 다운로드 흐름, 알림 서비스, 저장 공간 절약, 장애 처리를 자세히 살펴본다.

## 블록 저장소 서버(Block servers)

정기적으로 갱신되는 큰 파일을 매번 통째로 전송하면 대역폭 낭비가 크다. 두 가지 최적화로 네트워크 트래픽을 줄인다.

- **델타 동기화(Delta sync)**: 파일이 수정되면 전체가 아니라 **변경된 블록만** 동기화한다.
- **압축(Compression)**: 블록을 압축해 데이터 크기를 크게 줄인다. 파일 유형에 맞는 알고리즘을 쓴다(텍스트는 gzip/bzip2, 이미지·비디오는 다른 알고리즘).

블록 저장소 서버는 업로드의 무거운 작업을 담당한다. 새 파일이 추가될 때의 동작:

- 파일을 작은 블록으로 분할
- 각 블록을 압축
- 보안을 위해 각 블록을 암호화한 뒤 클라우드 저장소로 전송
- 블록을 클라우드 저장소에 업로드

<img width="622" height="360" alt="Image" src="https://github.com/user-attachments/assets/40ad1cd3-68e2-409e-b446-63ffad780d5d" />

델타 동기화 시에는 변경된 블록만 전송한다. 예를 들어 "block 2"와 "block 5"만 바뀌었다면 그 두 블록만 클라우드 저장소에 올린다.

## 높은 일관성 요구사항(High consistency requirement)

이 시스템은 기본적으로 **강한 일관성(strong consistency)** 을 요구한다. 같은 파일이 서로 다른 클라이언트에게 다르게 보여서는 안 된다. 메타데이터 캐시와 DB 계층 모두 강한 일관성을 제공해야 한다.

메모리 캐시는 기본적으로 최종 일관성(eventual consistency) 모델을 채택하므로, 강한 일관성을 달성하려면 다음을 보장해야 한다.

- 캐시 사본과 마스터의 데이터가 일치
- DB에 쓰기가 일어나면 캐시를 무효화(invalidate)해 캐시와 DB가 같은 값을 갖도록 함

관계형 데이터베이스는 ACID(원자성, 일관성, 격리성, 지속성)를 기본 지원하므로 강한 일관성 달성이 쉽다. 반면 NoSQL은 ACID를 기본 지원하지 않아 동기화 로직에 직접 구현해야 한다. 그래서 이 설계에서는 관계형 데이터베이스를 채택한다.

## 메타데이터 데이터베이스

<img width="628" height="448" alt="Image" src="https://github.com/user-attachments/assets/6a27ceee-744d-4e97-a3e3-f04393112c2a" />

주요 테이블

- **User**: 사용자 기본 정보(사용자명, 이메일, 프로파일 사진 등)
- **Device**: 단말 정보. `push_id`는 모바일 푸시 알림 송수신용. 한 사용자가 여러 단말을 가질 수 있다.
- **Namespace**: 사용자의 루트 디렉터리
- **File**: 최신 파일과 관련된 모든 정보
- **File_version**: 파일의 버전 이력. 기존 행은 읽기 전용으로 유지해 갱신 이력 무결성을 보장
- **Block**: 파일 블록과 관련된 모든 정보. 특정 버전의 파일은 블록들을 올바른 순서로 이어 붙여 복원할 수 있다.

## 업로드 절차(Upload flow)

<img width="640" height="380" alt="Image" src="https://github.com/user-attachments/assets/b04771fe-5f65-4366-b806-3b9ea79d136f" />

파일 업로드 시 두 요청이 **병렬로** 전송된다(둘 다 클라이언트 1에서 시작).

**① 파일 메타데이터 추가**

1. 클라이언트 1이 새 파일의 메타데이터 추가를 요청
2. 메타데이터를 메타데이터 DB에 저장하고 업로드 상태를 "대기중(pending)"으로 변경
3. 알림 서비스에 새 파일 추가를 통지
4. 알림 서비스가 관련 클라이언트(클라이언트 2)에 파일 업로드 중임을 통지

**② 클라우드 저장소로 파일 업로드**

1. 클라이언트 1이 파일 콘텐츠를 블록 저장소 서버로 업로드
2. 블록 저장소 서버가 파일을 블록으로 나누고 압축·암호화하여 클라우드 저장소에 업로드
3. 업로드가 끝나면 클라우드 저장소가 업로드 완료 콜백을 트리거하고, 그 요청이 API 서버로 전달됨
4. 메타데이터 DB의 파일 상태를 "완료(uploaded)"로 변경
5. 알림 서비스에 파일 상태가 "완료"로 바뀌었음을 통지
6. 알림 서비스가 관련 클라이언트(클라이언트 2)에 파일 업로드 완료를 통지

> 파일이 편집될 때의 흐름도 이와 유사하다.
> 

## 다운로드 절차(Download flow)

다운로드는 다른 곳에서 파일이 추가되거나 편집되었을 때 시작된다. 클라이언트가 변경을 알게 되는 방식은 두 가지다.

- 클라이언트 A가 **온라인**일 때 다른 클라이언트가 파일을 바꾸면, 알림 서비스가 변경 사실을 알려 최신 데이터를 받아가게 한다.
- 클라이언트 A가 **오프라인**일 때 파일이 바뀌면 변경 정보가 캐시에 저장되고, 다시 온라인이 되면 최신 변경분을 받아간다.

<img width="622" height="334" alt="Image" src="https://github.com/user-attachments/assets/e53426cd-2562-4fc4-b431-08035924c642" />

변경을 알게 된 클라이언트는 먼저 API 서버로 메타데이터를 요청한 뒤 블록을 내려받아 파일을 복원한다.

1. 알림 서비스가 클라이언트 2에 다른 곳에서 파일이 변경됐음을 통지
2. 클라이언트 2가 메타데이터를 가져오기 위해 요청 전송
3. API 서버가 메타데이터 DB에서 변경 메타데이터를 조회
4. 메타데이터가 API 서버로 반환됨
5. 클라이언트 2가 메타데이터를 받음
6. 클라이언트 2가 블록 저장소 서버에 블록 다운로드 요청 전송
7. 블록 저장소 서버가 클라우드 저장소에서 블록을 내려받음
8. 클라우드 저장소가 블록을 블록 저장소 서버로 반환
9. 클라이언트 2가 모든 새 블록을 내려받아 파일을 재구성

## 알림 서비스(Notification service)

파일 일관성을 유지하려면 로컬에서 일어난 파일 변경을 다른 클라이언트에 알려 충돌을 줄여야 한다. 알림 서비스는 이벤트 발생 시 데이터를 클라이언트로 전달한다. 두 가지 방식이 있다.

- 롱 폴링(Long polling): 드롭박스가 사용하는 방식
- 웹소켓(WebSocket): 클라이언트와 서버 간 지속 연결을 제공하는 양방향 통신

**롱 폴링을 택한 이유**

- 이 알림 서비스의 통신은 양방향이 아니다. 서버가 클라이언트에 파일 변경을 알리는 단방향이면 충분하다.
- 웹소켓은 채팅 앱처럼 실시간 양방향 통신에 적합하다. 반면 구글 드라이브의 알림은 빈번하지 않고 한 번에 많은 데이터가 몰리지 않는다.

**동작 방식**

각 클라이언트가 알림 서비스에 롱 폴링 연결을 유지한다. 

파일 변경이 감지되면 클라이언트는 연결을 닫는데, 연결을 닫는다는 것은 메타데이터 서버에 접속해 최신 변경분을 내려받아야 함을 의미한다. 

응답을 받거나 연결이 타임아웃되면 클라이언트는 즉시 새 요청을 보내 연결을 다시 연다.

## 저장 공간 절약(Save storage space)

파일 버전 이력과 안정성을 위해 같은 파일의 여러 버전이 여러 데이터센터에 저장된다. 모든 갱신 이력을 자주 백업하면 저장 공간이 빠르게 찬다.

- **중복 블록 제거(De-duplicate)**: 계정 단위로 중복 블록을 제거한다. 두 블록의 해시값이 같으면 동일한 블록이다.
- **지능적 백업 전략**
    - **버전 수 제한**: 저장할 버전 개수에 상한을 두고, 한도에 도달하면 가장 오래된 버전을 새 버전으로 대체한다.
    - **가치 있는 버전만 보관**: 자주 편집되는 파일은 짧은 시간에 1000번 넘게 저장될 수 있다. 불필요한 사본을 줄이기 위해 저장 버전 수를 제한하고, 최근 버전에 더 큰 가중치를 준다. 최적 버전 수는 실험으로 찾는다.
- **비활성 데이터를 콜드 저장소로 이동**: 수개월~수년간 접근되지 않은 콜드 데이터는 Amazon S3 Glacier 같은 저렴한 콜드 저장소로 옮긴다. (S3보다 훨씬 저렴하다.)

## 장애 처리(Failure Handling)

대규모 시스템에서는 장애가 발생하기 마련이므로 이를 다루는 설계 전략이 필요하다.

- **로드밸런서 장애**
    - 주 로드밸런서가 죽으면 부 로드밸런서가 활성화되어 트래픽을 넘겨받는다.
    - 로드밸런서들은 하트비트(주기적 신호)로 서로를 감시하며, 일정 시간 하트비트가 없으면 장애로 간주한다.
- **블록 저장소 서버 장애**: 다른 서버가 미완료·대기 작업을 넘겨받는다.
- **클라우드 저장소 장애**: S3 버킷은 여러 리전에 복제되어 있어, 한 리전에서 파일을 못 가져오면 다른 리전에서 가져온다.
- **API 서버 장애**: 무상태(stateless) 서비스이므로, 장애 시 로드밸런서가 트래픽을 다른 API 서버로 넘긴다.
- **메타데이터 캐시 장애**: 캐시 서버가 여러 벌 복제되어 있어, 한 노드가 죽어도 다른 노드에서 데이터를 가져온다. 장애 노드는 새 캐시 서버로 교체한다.
- **메타데이터 DB 장애**
    - **주(master) 장애**: 부(slave) 중 하나를 새 주로 승격하고, 새 부 노드를 추가한다.
    - **부(slave) 장애**: 다른 부로 읽기 요청을 넘기고, 장애 노드를 교체할 새 DB 서버를 추가한다.
- **알림 서비스 장애**
    - 온라인 사용자마다 롱 폴링 연결을 유지하므로 한 서버에 매우 많은 연결이 붙는다(2012년 드롭박스 발표 기준 서버당 100만 개 이상의 연결)
    - 서버가 죽으면 모든 롱 폴링 연결이 끊겨 클라이언트가 다른 서버로 재접속해야 하는데, 끊긴 연결을 한꺼번에 복구할 수 없어 비교적 느린 과정이다.
- **오프라인 백업 큐 장애**: 큐를 여러 벌 복제한다. 한 큐가 죽으면 소비자가 백업 큐를 다시 구독한다.

# 4단계 마무리

이번 장에서는 구글 드라이브를 지원하는 시스템을 설계했다. 강한 일관성, 낮은 네트워크 대역폭, 빠른 동기화의 조합이 이 설계를 흥미롭게 만든다. 설계는 크게 두 흐름으로 나뉜다.

- **파일 메타데이터 관리 흐름**
- **파일 동기화 흐름**

알림 서비스도 중요한 컴포넌트로, 롱 폴링을 사용해 클라이언트가 파일 변경에 대해 최신 상태를 유지하도록 한다.

시스템 설계에 완벽한 정답은 없으며, 회사마다 제약이 다르므로 그에 맞게 설계해야 한다. 설계와 기술 선택의 트레이드오프를 아는 것이 중요하다. 시간이 남으면 다음과 같은 대안적 설계를 논의할 수 있다.

1. **블록 저장소 서버를 거치지 않고 클라이언트가 직접 클라우드 저장소에 업로드**
    - **장점**: 파일을 클라우드 저장소로 한 번만 전송하면 되므로 업로드가 빨라진다. (기존 설계에서는 블록 저장소 서버 → 클라우드 저장소로 두 번 전송)
    - **단점**
        - 블록 분할·압축·암호화 로직을 여러 플랫폼(iOS, Android, Web)에 각각 구현해야 해 오류가 생기기 쉽고 엔지니어링 비용이 크다. 기존 설계에서는 이 로직이 블록 저장소 서버 한 곳에 집중되어 있다.
        - 클라이언트는 쉽게 해킹·조작될 수 있어 암호화 로직을 클라이언트 측에 두는 것은 바람직하지 않다.
2. **온라인/오프라인 로직을 별도 서비스(presence service)로 분리**
    - 온라인/오프라인 상태 관리를 알림 서버에서 떼어내 별도의 프레즌스 서비스로 분리하면, 다른 서비스에서도 이 기능을 쉽게 통합해 쓸 수 있다.
