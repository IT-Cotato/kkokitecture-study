# 개요

Magic Pocket은 Dropbox가 직접 만든 엑사바이트급 blob 저장 시스템이다. 

사용자 파일의 실제 콘텐츠를 담는 곳으로, 원래 Amazon S3에 얹어 쓰던 파일 저장을 자체 데이터센터로 들여오면서 만들어졌다. 

성능을 스택 끝까지 직접 조율하고, 원가를 크게 낮추려는 두 가지 이유가 컸다.

한 가지 짚고 갈 점은 이 시스템이 콘텐츠만 담는다는 것이다.

Dropbox는 데이터를 파일 콘텐츠와 메타데이터(파일·사용자 정보) 두 종류로 나눠 저장하는데, MP는 그중 콘텐츠 담당이다. 

파일 변경 이력 같은 가변(mutable) 로직은 FileJournal이라는 별도 시스템이 상위 계층에서 처리하고, MP 자신은 "한 번 쓰면 안 바뀌는" 불변 블록만 다룬다.

| 항목 | 내용 |
| --- | --- |
| 저장 대상 | 파일 콘텐츠(블록). 메타데이터는 별도 |
| 블록 크기 | 최대 4MB, 압축·암호화 후 저장 |
| 블록 식별 | 콘텐츠의 SHA-256 해시 |
| 리전 구성 | 미국 서부·중부·동부 3개 존(zone) |
| 복제 | 블록당 최소 2개 존에 독립 저장 + 존 내부 복제 |
| 내구성 목표 | 연간 99.9999999999% 이상 |
| 가용성 목표 | 99.99% 이상 |
| 규모 | 초기 수십 PB 프로토타입 → 약 6개월 만에 멀티 엑사바이트 |

> 불변(immutable) 저장
> 
> - 한 번 디스크에 쓴 블록은 절대 수정하지 않는다. 파일이 바뀌면 새 블록을 쓰고 옛 블록은 나중에 회수(compaction)될 때까지 그대로 둔다.
> - 불변이라 블록을 자유롭게 옮기고 복제·인코딩할 수 있어 시스템이 훨씬 단순해진다.

> erasure coding(소거 부호)
> 
> - 데이터를 여러 조각(fragment)으로 쪼갠 뒤 소수의 패리티 조각을 덧붙여, 일부가 사라져도 원본을 복원할 수 있게 하는 기법
> - 전체 복사본을 여러 벌 두는 복제보다 훨씬 적은 추가 용량으로 같은 수준의 장애 내성을 얻는다.
> - MP는 거의 모든 데이터에 이 방식을 쓴다.

# 1. 설계 원칙 - 단순함이 곧 신뢰성

MP를 관통하는 제1원칙은 "단순하게 유지하라"다. 대규모 분산 저장 시스템은 만드는 것보다 오래도록 안정적으로 굴리는 것이 훨씬 어렵기 때문이다.

- 쿼럼 방식 합의나 분산 코디네이션을 최대한 피하고, 대신 장애 내성 있고 확장 가능한 형태의 중앙 집중 코디네이션을 적극 활용한다.
- Block Index를 분산 해시 테이블 대신 거대한 샤딩 MySQL 클러스터로 구현한 게 대표적이다.
    - 키-값 저장소가 성능은 좋지만, 이미 사내에 수천 대의 DB 노드를 운영하며 쌓은 역량을 재활용하는 편이 개발을 단순화하고 미지수를 줄였다.

# 2. 데이터 모델 - 블록, 버킷, 볼륨

MP에 무엇이 저장되는지부터 정리하면 세 층위로 나뉜다.

- 블록(Block): 파일을 쪼갠 최대 4MB 조각
    - 압축·암호화된 상태로 들어오고, 이름(키)은 콘텐츠의 SHA-256 해시다.
- 버킷(Bucket): 4MB는 엑사바이트 규모에서 옮겨다니기엔 너무 잘아서, 블록들을 1GB 논리 컨테이너로 묶은 것
    - 한 버킷 안의 블록들은 서로 아무 관련이 없고, 그저 비슷한 시점에 업로드됐을 뿐이다.
- 볼륨(Volume): 하나 이상의 버킷을 여러 물리 노드에 복제한 단위
    - 갓 올라온 블록은 여러 머신에 그대로 복제되고, 시간이 지나면 버킷들이 모여 소거 부호로 인코딩돼 저장 효율을 높인다.

```
블록(해시로 식별) → 버킷에 기록 → 볼륨 형태로 여러 머신에 복제 또는 인코딩되어 저장
```

# 3. 아키텍처 - 존과 셀

MP는 미국 서부·중부·동부에 서버 클러스터를 둔 멀티 존 구조다. 각 블록은 최소 두 개의 서로 다른 존에 독립적으로 저장되고, 존 내부에서 다시 안정적으로 복제된다. 이 이중화는 자연재해나 대규모 장애를 견디게 해줄 뿐 아니라, 존 사이에 뚜렷한 관리 경계를 만들어 한쪽의 설정 실수나 혼잡이 다른 존으로 번지지 않게 막는다.

핵심 동작은 대부분 존 하나 안에서 일어난다. 존 안의 구성 요소는 다음과 같다.

## Frontend

시스템 바깥에서 오는 저장 요청을 받는 관문. 블록을 어디에 저장할지 판단하고, MP 내부에 읽기/쓰기 명령을 내린다.

## Block Index

각 블록이 어느 버킷에 있는지 매핑하는 서비스. 스키마를 단순화하면 이렇다.

```
hash → cell, bucket, checksum
```

RPC 서비스 계층을 앞에 둔 거대한 샤딩 MySQL 클러스터로 구현했다. 

원래는 전용 키-값 저장소를 만들 계획이었지만, MySQL만으로 충분했고 오히려 표현력 있는 데이터 모델 덕에 스키마와 기능을 시간이 지나며 손쉽게 확장할 수 있었다.

## Cell(셀)

약 50PB 규모의 자기완결적 논리 저장 클러스터

공간이 더 필요하면 보통 새 셀을 하나 띄운다. 

셀은 논리적으로 완전히 독립이되, 물리적으로는 여러 랙에 걸쳐 배치해 다양성을 확보한다.

 셀 하나는 코디네이션 오버헤드 때문에 약 100PB가 상한이며, 셀을 여러 개 두는 편이 배포와 장애 격리 측면에서도 편하다.

## 셀 내부 구성 요소

- OSD(Object Storage Device): 디스크로 가득 찬 저장 박스
    - 머신 하나에 1PB 넘게, 랙 하나에 8PB 넘게 담는다.
    - 캐싱·디스크 스케줄링·데이터 검증 같은 복잡한 로직은 있지만, 시스템 전체 관점에선 셀 구조나 분산 프로토콜을 모르는 노드다. 그냥 블록을 저장할 뿐이다.
- Replication Table: 각 버킷이 어느 볼륨과 OSD에 있는지 알려주는 셀 내부 인덱스
    - Block Index보다 훨씬 작고 갱신도 드물어, 워킹셋이 통째로 메모리에 올라간다.
    - 여기엔 open 플래그가 있는데, open 볼륨은 새 데이터 쓰기만 받고, closed 볼륨은 불변이라 셀 안에서 안전하게 옮길 수 있다.
- Master: 셀의 관리인이자 코디네이터
    - OSD 상태를 감시하다 하나가 죽으면 복구(Repair)를 촉발하고, 새 버킷 생성·가비지 컬렉션·작은 버킷 병합 같은 배경 작업을 조율한다.
    - 중요한 점은 Master가 데이터 경로에 없다는 것. 실트래픽이 통과하지 않으므로 Master가 죽어도 셀은 읽기를 계속 제공한다.
    - 상태는 Replication Table에 있어 Master 자신은 soft-state다. 셀당 하나만 둬서 복잡한 분산 프로토콜 없이 중앙 코디네이션을 얻는다.
- Volume Manager: 셀의 힘쓰는 일꾼
    - Master 지시를 받아 볼륨을 옮기거나 소거 부호로 인코딩한다.
    - 여러 OSD에서 읽어 다른 OSD로 쓰는 작업이라 네트워크를 많이 먹기에, 노는 저장 하드웨어를 활용하도록 OSD와 같은 물리 머신에서 돈다.

# 4. 핵심 프로토콜 - Put, Get, Repair

## Put (쓰기)

Frontend는 미리 각 셀의 여유 공간과 쓰기 가능한 open 볼륨 목록을 파악해 둔다. 

Put 요청이 오면,

1. Block Index로 블록이 이미 있는지 확인
2. 셀 부하를 고르게 분산하고 네트워크 트래픽을 최소화하도록 대상 볼륨 선택
3. Replication Table에서 그 볼륨을 저장 중인 OSD들을 조회
4. 해당 OSD들에 저장 명령 → 모두 디스크(또는 SSD)에 fsync 후 응답
5. 성공하면 Block Index에 새 항목 추가하고 클라이언트에 성공 반환

중간에 OSD가 실패하면 다른 볼륨(필요하면 다른 셀)으로 그냥 재시도한다. Block Index가 실패하면 다른 존으로 요청을 넘긴다. 

쿼럼 방식으로 일부 OSD에만 써서 꼬리 지연을 줄일 수도 있었지만, 복잡도를 감수하는 대신 타임아웃을 잘 관리하는 재시도 방식으로도 충분히 낮은 지연을 얻어 이쪽을 택했다.

## Get (읽기)

Block Index에서 셀과 버킷을, Replication Table에서 볼륨과 OSD를 찾은 뒤, OSD 하나에서 블록을 가져온다. (실패하면 재시도)

- 복제 볼륨: 각 OSD가 모든 블록을 갖고 있어 읽기가 쉽다.
- 소거 부호 볼륨: 각 블록을 OSD 하나에서 통째로 읽을 수 있게 인코딩해, 대부분의 읽기가 디스크 하나만 건드린다. 그 OSD가 죽으면 Volume Manager의 도움으로 다른 OSD들의 인코딩 데이터를 읽어 블록을 재구성한다.

## Repair (복구)

Master가 하는 가장 중요한 일, 디스크가 죽으면 볼륨을 다시 복제하는 작업이다.

- Master는 서비스 디스커버리로 OSD 건강을 계속 감시하다rk OSD가 15분 오프라인이면 복구를 촉발한다.
    
    → 노드 재시작으로 인한 불필요한 복구는 피하되, 취약 구간은 짧게 가져가는 균형점
    
- 볼륨은 셀 전체에 다소 무작위로 흩어져 있고 OSD 하나에 수천 개씩 들어간다. 그래서 OSD 하나를 잃어도 수백 개의 다른 OSD에서 동시에 볼륨을 재구성할 수 있어, 복구 트래픽을 수백 장의 네트워크 카드와 수천 개의 디스크에 분산해 복구 시간을 최소화한다

### 복구 과정

1. 죽은 OSD의 볼륨을 모두 closed로 바꿔 더 이상 쓰기를 받지 않게 한다(이제 안전하게 이동 가능)
2. 부하를 고르게 퍼뜨리는 재구성 계획을 세워, 복사할 OSD와 복제받을 OSD를 고른다.
3. Volume Manager가 데이터를 옮기고 필요하면 인코딩한다.
4. 마지막 커밋이 핵심이다. 새 OSD에 볼륨이 복사됐어도 아직 이동은 확정되지 않은 상태다. 
    1. Master는 새 OSD의 볼륨 generation 번호를 올린 뒤 Replication Table의 매핑을 갱신한다(이 지점이 커밋). 
    generation 번호 덕분에 죽었던 OSD가 되살아나도 어느 쪽이 진짜인지 혼동이 없다.

이 프로토콜은 어떤 노드가 어느 시점에 죽어도 시스템을 불일치 상태로 남기지 않는다. 

실제로 DB 프론트엔드가 한 시간을 얼어붙었다 살아나 요청을 흘리는 사이 Master도 죽었다 재시작하며 전혀 다른 복구를 내린 사례도 있었는데, 일관성 프로토콜은 이런 막장 상황에서도 견뎌야 한다.

 open/closed 볼륨 모델이 바로 이 견고함의 열쇠로, 실트래픽과 배경 작업이 서로 간섭하지 않게 해 훨씬 단순한 일관성 프로토콜을 쓸 수 있게 해준다.

# 5. 불변성의 대가 - 삭제해도 공간이 안 빠진다 (2026 심화)

불변 저장의 아키텍처는 10년 넘게 그대로지만, 그 위에서 저장 효율을 지키는 싸움은 계속 진화하고 있다.

불변 저장의 숙명은 삭제가 즉시 공간을 비우지 못한다는 것이다.

 Dropbox는 수조 개의 blob을 저장하고 매일 수백만 건의 삭제를 처리하는데, 데이터가 불변이라 삭제해도 옛 데이터는 볼륨 안에 그대로 남는다.  

볼륨은 한 번 닫히면 다시 열리지 않는다. 그래서 삭제가 쌓일수록 볼륨은 군데군데 비게 되고(fragmentation), 살아있는 데이터가 필요 이상으로 많은 디스크에 흩어진다.

## 2가지 회수 단계

| 단계 | 하는 일 | 공간이 비는가? |
| --- | --- | --- |
| **가비지 컬렉션** | 더 이상 참조되지 않는 blob을 찾아 "제거해도 안전"으로 표시 | 표시만 |
| **컴팩션(Compaction)** | 살아있는 blob만 새 볼륨에 다시 쓰고, 옛 볼륨은 폐기 | 실제 회수 |

닫힌 볼륨은 수정이 불가능하므로, 지우는 게 아니라 **살아있는 것만 옮겨 담고 통째로 버리는** 방식으로 공간을 되찾는다.

> **저장 오버헤드를 보는 법**
볼륨에서 살아있는 데이터가 차지하는 비율로 생각하면 쉽다.
> 
> - 절반만 살아있음 → 필요한 용량의 **2배** 사용
> - 10%만 살아있음 → 약 **10배** 사용
> 
> 엑사바이트 규모에선 이 비율이 조금만 올라도 곧장 하드웨어 구매·증설 비용으로 직결된다.
>

# 6. 컴팩션의 진화 - L1 / L2 / L3

## 재검토를 부른 사건

즉석에서 소거 부호를 입히는 신규 서비스 **Live Coder**를 여러 리전에 점진 배포하던 중, 이 경로로 만들어진 볼륨들이 심하게 덜 채워지는 문제가 몇 주간 방치됐다.

- 최악의 경우 할당 용량의 5% 미만만 살아있는 데이터였다.
- 볼륨 크기는 고정이라, 덜 찬 볼륨도 꽉 찬 볼륨과 똑같은 디스크를 먹는다.
- 결과 → fragmentation 급증, 오버헤드 상승

기존 컴팩션도 계속 돌긴 했지만, 이렇게 **극단적으로 덜 찬 볼륨이 긴 꼬리로 쌓이는 상황**엔 애초에 설계되지 않았다. 이 사건이 다층 전략의 계기가 됐다.

## 한눈에 보는 세 전략

| 전략 | 겨냥하는 볼륨 | 방식 | 한 줄 요약 |
| --- | --- | --- | --- |
| **L1** | 거의 꽉 찬 볼륨 | host에 donor를 조금씩 채움 | 평상시 유지 |
| **L2** | 절반 이하로 덜 찬 볼륨 | 여러 개를 묶어 한 번에 | 중간 지대 통합 |
| **L3** | 거의 텅 빈 볼륨 | Live Coder 스트리밍으로 배수 | 희박한 꼬리 청소 |

## L1 - 평상시 전략

수년간 잘 작동해 온 기본 전략. 컴팩션을 일종의 **패킹 문제**로 본다. 이미 많이 찬 host 볼륨을 고르고, 그 여유 공간에 딱 들어갈 donor 볼륨들을 골라 새 볼륨에 합친다.

- **장점:** 선택 로직이 단순하고 빠르며, 배치 리스크와 메타데이터 갱신이 낮다.
- **단점:**  한 번 돌 때 수십 GiB를 읽고도 대개 새 볼륨 하나만 만든다. 평균적으로 한 번에 한 볼륨도 회수하지 못한다.
- **전제:** "대부분의 볼륨이 거의 꽉 차 있다." 사건으로 이 전제가 깨졌다.

## L2 - 덜 찬 볼륨 통합

host에 donor를 야금야금 채우는 대신, **덜 찬 볼륨 여러 개를 묶어** 새 목적지 볼륨을 거의 꽉 채우도록 조합을 고른다. 여러 개를 한 번에 회수하니 공간 회복이 훨씬 빠르다.

내부적으로는 동적 계획법(DP)으로 푸는 제한된 패킹 문제다.

```
입력:
  volumes[]           각 볼륨의 LiveBytes
  maxVolBytes         목적지 볼륨 용량
  maxVolumesToUse     사용할 볼륨 개수 상한
  granularity         스케일 축소 계수

1) live bytes와 용량을 granularity로 나눠 DP 테이블 크기를 줄인다.
2) (볼륨 index, 개수 k, 용량 c) 위에서 DP, 최대로 채운 바이트를 유지.
3) 선택 내역을 별도 choice 테이블에 기록해 복원에 사용.
4) 최적 (k, 용량)에서 역추적해 선택된 볼륨들을 복원.
```

한 번에 쓰는 소스 볼륨 개수를 제한하고 바이트 수를 거칠게 반올림해 탐색 공간을 줄인다. 덕분에 프로덕션 규모에서도 계산·메모리를 묶어둔 채 촘촘한 패킹을 만든다.

성과

- L1보다 오버헤드를 2~3배 빠르게 감소
- L2를 켠 셀은 며칠 만에 지속 가능한 수준으로 회복
- 일주일 기준, L1만 쓴 셀보다 컴팩션 오버헤드 30~50% 낮음

## L3 - 가장 텅 빈 볼륨 배수

L2는 중간 지대엔 강하지만, 살아있는 데이터가 극소량만 남은 **가장 희박한 볼륨**엔 비효율적이다. 이 극단의 꼬리는 다른 접근이 필요했다.

컴팩션은 본질적으로 **제약된 재인코딩**이다 — 한 무리 볼륨의 살아있는 데이터를 모아 새 볼륨을 만드는 일. L3는 여기에 착안해, 사건을 일으켰던 Live Coder를 이번엔 **스트리밍 파이프라인**으로 되레 활용한다.

- 배치로 묶는 대신, 심하게 덜 찬 볼륨의 남은 blob을 계속 Live Coder에 흘려보낸다.
- 시간을 두고 새 볼륨으로 인코딩·축적하고, 소스 볼륨의 데이터가 다 빠지면 즉시 회수한다.
- 가장 희박한 볼륨부터 처리하니, 회수 볼륨당 다시 써야 하는 데이터가 최소가 되어 회복이 빠르다.

### **트레이드오프**

blob을 통째로 새 볼륨에 쓰므로, 모든 blob이 새 식별자와 메타데이터 갱신을 유발해 저장·메타데이터 시스템에 부하를 준다. 

평상시 덜 찬 볼륨 양에선 감당 가능하며, 시스템을 압도하지 않도록 한도를 둔다.

# 7. 운영 튜닝과 안전장치

세 전략은 볼륨 분포의 서로 다른 구간을 노리는 계층 구조를 이룬다. 관건은 이들을 **동시에 돌리되 서로 간섭하지 않게** 하는 것이었다.

- **동적 제어 루프**
가장 민감한 레버는 "어떤 볼륨을 컴팩션 대상으로 볼지" 정하는 host 적격 임계값이다.
    - 너무 높으면 → 대상이 적어 오버헤드 상승
    - 너무 낮으면 → 계산·I/O만 쓰고 회수는 미미
    정적 튜닝을 버리고, 오버헤드가 오르면 임계값을 높여 고수익 컴팩션을 우선하고, 안정되면 낮춰 삭제에 민감하게 반응하는 제어 루프로 바꿨다.
- **후보 순서 조정**
어느 볼륨을 먼저 컴팩션하느냐로 회수 속도와 메타데이터 부하가 갈린다. L1은 보수적으로 donor 수를 제한, L2는 더 공격적으로 묶어 밀도를 높이고, L3는 가장 희박한 볼륨부터 처리한다.
- **부하 격리**
각 경로를 rate-limit하고 트래픽을 셀 안에 가둬(데이터센터 간 전송 회피), 사용자 트래픽·다운스트림 서비스와 경쟁하지 않게 한다.

# 8. 무엇을 배웠나

- **단일 휴리스틱은 안 된다.** L1은 평상시엔 훌륭했지만 분포가 흔들리자 무너졌다. 문제를 여러 전략으로 쪼개 볼륨 채움 정도의 전 구간을 커버했다.
- **수동 튜닝은 확장되지 않는다.** 임계값은 엑사바이트 규모에서 손으로 관리하기엔 너무 민감하다. 플릿 신호에 연동된 동적 제어 루프가 오버헤드를 안정시키고 개입 필요를 줄였다.
- **메타데이터 용량이 가장 큰 제약이었다.** L1·L2는 많은 blob이 같은 볼륨 정체성을 유지해 donor blob만 위치를 다시 쓰면 되지만, L3는 새 볼륨에 쓰므로 대부분 새 위치 항목이 필요하다. 볼륨을 효율적으로 패킹하는 것만으로 부족하고, 얼마나 많은 재작성을 유발하는지까지 통제해야 했다.
- **가시성이 필요하다.** Live Coder 생산량, 플릿 전반의 볼륨 채움 정도, 주 단위 오버헤드 변화를 추적하는 지표와, 컴팩션이 뒤처지기 시작하면 조기 경고하는 모니터링을 붙였다. 오버헤드가 너무 오르기 전에 분포 변화를 잡아 사후 수습이 아니라 선제 대응하는 게 목표다.
