# 개요

초기 당근은 중고거래를 넘어 동네에서 일어나는 모든 비즈니스를 연결하는 O2O 서비스를 목표로 했다.

> O2O(Online to Offline): 온라인 활동을 오프라인 거래·서비스 이용으로 연결하는 사업 모델
> 

하지만 피드에 노출될 콘텐츠 유형을 미리 예측할 수 없어 일반적인 SNS 피드 설계 구조를 그대로 가져오기는 어렵다고 판단했다.

이에 따라 피드 서비스는 두 가지에 집중했다.

1. 사내의 새로운 서비스들의 콘텐츠들을 피드에 쉽게 노출할 수 있을 것 (Backend)
2. 앱 업데이트가 없더라도 콘텐츠가 노출될 수 있을 것(Frontend)

# Phase 1. Just Push It!

당근은 중고거래, 중고차, 당근알바 등 콘텐츠 다양성이 매우 커서 일반적인 피드 모델인 Fan-in이나 Fan-out을 그대로 적용하기 애매했다.

하나의 큰 저장소에 콘텐츠를 모아두면 서비스별로 원하는 정렬 방식과 조회 빈도를 예측할 수 없는 문제가 있었다.

## 초기 설계

한 명이 피드 서비스를 만들고 운영해야 했기 때문에, 다양한 서비스의 콘텐츠를 빠르게 노출하고 개인화를 지원할 방법을 고민했다.

피드 서비스가 모든 콘텐츠를 직접 모아 노출하는 대신, 각 서비스가 피드에 노출할 콘텐츠를 1차로 정렬해 전달하도록 권한을 위임하는 방식을 택했다.

피드 서비스는 전달받은 콘텐츠들을 어떤 순서와 우선순위로 노출할지 정하는 역할만 맡았다.

<img width="956" height="516" alt="Image" src="https://github.com/user-attachments/assets/e9f51da4-2bcd-4d7b-9817-abee0f0c5476" />

사용자들은 당근 홈피드를 "중고거래 피드"로 인식하고 있어, 중고거래 외 콘텐츠는 일종의 광고처럼 취급해 노출 위치와 경쟁 서비스 간 우선순위를 조정하는 장치를 두었다.

HTTP(이후 gRPC) 통신에서 노출 위치(index), 콘텐츠 식별자(id, sid), 엔티티 타입(model), 랭크 값(score) 등을 담은 공통 응답 구조를 정의해, 이 구조만 따르면 어떤 서비스든 피드에 콘텐츠를 노출할 수 있게 했다.

> gRPC: 구글이 만든 고성능 RPC(원격 프로시저 호출) 프레임워크로, 서비스 간 통신에 사용된다.
> 

```json
{
  "data": [
    {
      "index": "int", // 노출 할 위치
      "resource": {
        "id": "int", // integer id
        "sid": "string", // string id
        "model": "string", // entity type
        "score": "float64", // 콘텐츠의 rank  값
        "serialized": "stringified viewtype" // 아래에서 소개될 viewtype 데이터
      }
    }
  ]
  "meta": {
  }
}
```

콘텐츠 서빙과 개인화를 일단은 각 서비스에 위임하고 콘텐츠를 빠르게 노출할 수 있는 방향으로 설계했다.

앱에서도 별도의 업데이트 없이 빠르게 노출하기 위해 Viewtype이라는 것도 만들었다.

## Viewtype

당근 사용자 중 30~60대 비중이 높고 구형 안드로이드 사용자도 많아 앱 업데이트 주기가 느렸다.

이를 극복하기 위해, 새 앱 화면을 웹뷰로 만드는 방식에서 착안해 피드 아이템을 그릴 때 필요한 정보만 응답으로 보내주는 Viewtype을 고안했다.

⇒ 앱 업데이트 없이도 새로운 형태의 콘텐츠를 빠르게 피드에 노출할 수 있었다.

<img width="720" height="743" alt="Image" src="https://github.com/user-attachments/assets/28bc0781-9665-4338-bf30-24990b4822a5" />

다만 아이템 클릭 시 웹뷰로 이동하는 구조라, 좋아요·채팅 수 같은 상태 변화나 네이티브 영역과의 인터랙션을 구현하기는 어려웠다.

## **e.g. 당근알바**

동네 구인구직 플랫폼인 당근알바는 초기 유입 확보 단계에서 피드를 활용했다.

피드에 콘텐츠를 노출한 결과 공고 수가 100% 성장했고, 서비스 전체 지표도 50% 성장했다.

# **Phase 2. Assemble!**

초기 전략으로 피드 노출 자체는 빠르게 적용할 수 있었지만, 콘텐츠가 충분히 쌓인 뒤에는 각 서비스가 자기 데이터만으로 개인화하는 방식이 더 이상 큰 효과를 내지 못했다.

모든 서비스의 사용자 데이터를 조화롭게 함께 활용할 수 있는 상태도 아니었다.

그래서 사내 모든 콘텐츠를 한데 모아 전체 최적화를 하는 방향으로 전환을 결정했다.

이를 위해 피드품질팀, 피드 ML 인프라팀, Feed Infra팀을 합쳐 24명 규모의 "피드실"을 신설했고, Feed Infra팀은 10명 규모가 됐다.

## Backend

Feed Infra팀은 세 가지 새로운 컴포넌트를 구축하고 있다.

<img width="828" height="333" alt="Image" src="https://github.com/user-attachments/assets/40c52be5-889e-4daa-9e2d-adcd2acc2f3f" />

- **Feed Mixer**: Feed에 노출되기 전에 적용되어어야 하는 정책을 담당하고 콘텐츠의 조합을 담당
- **Feed Entity Service**: 피드에 노출될 수 있는 모든 콘텐츠(엔터티)를 한데 모아 수집·서빙하는 서비스
- **Feedback Service**: 콘텐츠에서 발생하는 다양한 명시적 피드백을 저장

### Feed Mixer

클라이언트의 요청을 받아 추천 모델을 통해 개인화된 콘텐츠와 아직 개인화를 하기에는 충분히 성장하지 않는 서비스들의 콘텐츠들을 섞고 피드 정책에 따른 페널티를 적용하는 서비스이다.

### Feed Entity Service

피드에서 안정적인 서빙과 다양한 실험을 위한 인프라를 구축하기 위해서 피드에 노출될 수 있는 모든 엔터티를 수집하고 서빙하는 서비스이다.

목적사내 다양한 콘텐츠를 통합해 하나의 추천 모델로 다루기 위한 준비 작업이다.

### Implicit Feedback Service

관심, 좋아요, 댓글, 채팅, 신고, 차단, 안 보기 등 콘텐츠에서 발생하는 다양한 사용자 반응(피드백)을 저장하는 서비스이다.

## Frontend

기존 Viewtype을 넘어, 다양한 콘텐츠를 다양한 UI로 다룰 수 있도록 SDUI 방식의 ViewTemplate을 새로 만들었다.

> SDUI(Server-Driven UI): 화면 구성 정보를 서버가 내려주고 클라이언트는 이를 받아 그리는 방식으로, 앱 업데이트 없이도 UI를 바꿀 수 있게 해주는 설계
> 

Text, Image, Button 등의 컴포넌트를 조합하고 스타일을 자유롭게 적용할 수 있도록 설계했다.

당시 팀에 백엔드 엔지니어만 있었기 때문에, 아이디어 검증을 위해 먼저 웹 환경에서 구현해보고 이후 관심피드에 실험으로 적용했다.

실험 결과 UI 오류 제보가 없어 가능성을 확인했지만, 클라이언트 리소스 부족과 Mixer·Entity Service 등 더 시급한 과제로 인해 추가 진행은 보류된 상태다.
