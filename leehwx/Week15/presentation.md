# Netflix Live Origin

> 출처: https://netflixtechblog.com/netflix-live-origin-41f1b0ad5371
> 

---

# 개요

Netflix Live Origin은 **라이브 스트리밍 전용으로 Netflix가 직접 구축한 오리진 서버**다. 

업스트림(클라우드 라이브 파이프라인)과 다운스트림(자체 CDN인 Open Connect) 사이의 경계에 서서, **어떤 콘텐츠를 CDN으로 내보낼지 결정하는 중개자(broker)** 역할을 한다.

| 항목 | 내용 |
| --- | --- |
| 위치 | 라이브 파이프라인 ↔ Open Connect 사이 |
| 실행 환경 | AWS EC2 위의 멀티테넌트 마이크로서비스 |
| 통신 | 표준 HTTP (발행은 `PUT`, 조회는 `GET`) |
| 핵심 역할 | 세그먼트 후보 선택 · 결함 세그먼트 차단 · 트래픽 폭주 방어 |
| 대표 규모 | 2024 Tyson vs. Paul 경기에서 **동시 스트림 6,500만** |

# 왜 VOD 방식으론 안 됐나

기존 Open Connect는 **VOD 전송에 고도로 최적화**되어 있었다. 

VOD 자산은 미리 선별된 OCA 서버에 **사전 배치(pre-position)** 된다. 

하지만 라이브는 성격이 근본적으로 다르다.

| 구분 | VOD / SVOD | 라이브(Live) |
| --- | --- | --- |
| 콘텐츠 준비 | 미리 인코딩·배치할 시간 충분 | 실시간, 미리 배치 불가 |
| 지연 허용치 | 비교적 여유 | **2초 재시도 예산**으로 매우 빠듯 |
| 요구 저장소 | 대용량 객체 저장소로 충분 | 전역 저지연·고가용성 DB에 가까움 |

> **Origin (오리진 서버)**
CDN 엣지 서버가 캐시할 원본 콘텐츠를 보관·제공하는 최상위 서버. 엣지에 없는(캐시 미스) 콘텐츠는 결국 오리진에서 가져온다.
> 

> **Open Connect / OCA**
Netflix 자체 CDN. 콘텐츠는 사전 선별된 서버 기기(OCA, Open Connect Appliance)에 미리 배치된다. 일반 CDN이 요청 시점에 채우는(fill on demand) 것과 달리, **분산 오리진 서버**에 가깝게 동작한다.
> 

> **Segment (세그먼트)**
라이브/스트리밍 영상을 수 초 단위로 잘게 쪼갠 조각 파일. 클라이언트는 이 조각들을 순서대로 이어받아 재생한다.
> 

> **DVR 재생 윈도우**
라이브 방송 중 시청자가 지나간 장면을 되감아 볼 수 있는 구간. 최신 지점(live edge)뿐 아니라 **과거 세그먼트도 다시 요청**될 수 있다.
>

## 1. 다중 파이프라인·다중 리전 인지 오리진

라이브 스트림은 실시간 특성상 필연적으로 결함을 포함한다.

- 짧은 세그먼트 → 비디오 프레임·오디오 샘플 누락
- 누락된 세그먼트 → 세그먼트 전체가 없음
- 타이밍 불연속 → 디코드 타임 문제

**이중화로 결함을 회피한다.**

```
        ┌── 파이프라인 A (리전 A · 인코더 A · 패키저 A) ──┐
라이브 신호 ─┤                                          ├─→ Live Origin ─→ 유효후보 선택
        └── 파이프라인 B (리전 B · 인코더 B · 패키저 B) ──┘
```

두 파이프라인은 완전히 독립적으로 동작하므로 같은 세그먼트가 양쪽에서 동시에 깨질 확률이 낮다. 

세그먼트가 요청되면 오리진은 각 파이프라인 후보를 정해진 순서로 확인해 첫 번째 유효한 것을 고른다. 

결함은 패키저의 경량 미디어 검사로 탐지되어 메타데이터로 전달되고, 드물게 양쪽 다 결함이면 그 정보를 클라이언트로 내려보내 오류 은폐(error concealment) 에 쓴다.

## 2. Open Connect 스트리밍 최적화

라이브는 Open Connect의 '작은 객체 전송' 모델에 맞지 않아, nginx의 프록시 캐싱 기능을 라이브용으로 확장했다.

### 불필요한 요청 걸러내기

- 세그먼트 템플릿을 OCA에도 제공 → OCA가 "지금 유효한 세그먼트 범위"를 스스로 계산
- 범위 밖 요청은 오리진까지 올라가기 전에 OCA에서 즉시 거절

### 아직 안 나온 세그먼트 다루기

| 상황 | 처리 |
| --- | --- |
| 세그먼트가 아직 없음 | `404` 반환 + 발행 예상 시점까지 캐시되도록 만료 정책 부여 |
| 바로 다음 세그먼트 요청 | 404 대신 요청을 '열어둔 채 유지(hold open)' → 발행되면 즉시 응답 |

이로써 일찍 도착한 요청들이 만드는 네트워크 잡음(chatter)이 크게 감소했다. 

세그먼트가 2초마다 생성되므로 초 단위 캐싱은 너무 거칠어, nginx에 밀리초 단위 캐싱을 추가했다.

### 스트리밍 메타데이터 개선

스트림 내 이벤트 알림을 **HTTP 헤더에 실어** 확장성 있게 전달한다. 

OCA는 세그먼트가 도착할 때마다 헤더에서 알림을 뽑아 이벤트 ID 기반 인메모리 구조를 갱신 → 라이브 엣지보다 뒤처진 클라이언트도 항상 최신 알림을 받는다.

### 캐시 무효화와 오리진 마스크

```
[기본 무효화]  캐시 키에 버전 번호 삽입 → 번호를 올리면 이벤트 콘텐츠 전체 flush
                (주로 이벤트 전 사전 테스트에서 네트워크를 깨끗이 초기화)

[향상된 무효화] 각 세그먼트가 "인코딩 파이프라인 + 요청 리전" 정보를 함께 전달
                → 조건부 무효화 가능
                  예) "인코더 A에서 나온 것만"
                      "인코더 A + 리전 X에서 조회된 것만"
```

> **선택적 인코딩 파이프라인 마스킹(selective encoding pipeline masking)**
여러 인코더(파이프라인) 중 특정 하나에서 나온 문제 있는 세그먼트 범위만 골라 가려서 클라이언트에 전달하지 않는 기능.
> 

⇒ 재생 오류를 일으키는 나쁜 세그먼트를 탐지 즉시 숨겨, DVR 재생 윈도우 동안 되감아 보는 시청자까지 포함해 수백만 클라이언트를 보호한다.

## 3. 오리진 스토리지 아키텍처

### 초기 설계와 한계

처음엔 SVOD처럼 AWS S3를 그대로 썼다. 

트래픽이 적을 땐 충분했지만, 규모가 커지자 문제가 드러났다. S3는 가동률 보장은 지켰지만, 라이브 특유의 2초 재시도 예산 앞에서는 어떤 지연도 문제였다.

라이브의 요구는 객체 저장소보다 **전역 저지연·고가용성 데이터베이스**에 가까웠다.

> **재시도 예산(retry budget)**
실패한 요청을 다시 시도할 수 있는 시간 한도. 라이브는 실시간이라 한도가 2초로 빠듯해, VOD라면 무시할 지연도 라이브에서는 재생 끊김으로 이어진다.
> 

### 스토리지에 요구된 5가지 조건

| 요구사항 | 내용 |
| --- | --- |
| **HA 쓰기** | 단일 리전 내 거의 완전한 쓰기 가용성. 500ms 내 실패는 버그로 간주 |
| **처리량** | 리전 간 수백 MiB 복제 |
| **큰 파티션** | 파티션당 O(10k) 키, 이벤트당 총 O(GiB) |
| **강한 일관성** | 같은 리전 내 `read-your-write` → 1초 미만 읽기 지연 |
| **오리진 폭풍** | 최악의 경우 O(GiB) 읽기를 쓰기에 영향 없이 감당 |

### 해결책 - 기존 자산의 재활용과 확장

Netflix는 이미 Apache Cassandra 기반 KeyValue 스토리지 추상화(큰 값을 청크로 저장, 원래 게임 세이브용)를 갖고 있었고, 이를 라이브용으로 사용했다.

**대용량 쓰기의 고가용성**

- 큰 작업을 청크로 쪼개 멱등하게 재시도·헤징
- Cassandra의 local-quorum(AZ 하나가 죽어도 쓰기 유지) + 쓰기 최적화 LSM 엔진

  ⇒기존 방식의 P50(중앙값) 수준 지연을 P99(꼬리)에서 달성

**Gbps급 읽기의 고가용성**

- 최악 읽기 처리량 O(100Gbps) - 강한 일관성 엔진엔 매우 비쌈
- Cassandra만으로는 동시 쓰기 성능이 무너짐
    
    → EVCache(Memcached 기반)로 청크 write-through 캐싱 도입
    
    → 거의 모든 읽기를 캐시가 처리, 200Gbps 이상 + 읽기·쓰기 분리 달성
    

**최종 구조**

```
                    ┌─────────── 읽기(대부분) ──────────┐
Live Origin ─→ KeyValue ─→ EVCache (캐시 히트)          │
                    │                                    │
                    └─── 캐시 미스만 ─→ Cassandra (청크 분산 저장)
                                        · 쓰기 경로
```

> **P50 / P99**
지연 시간의 백분위. P50은 중앙값, P99는 상위 1% 느린 요청까지 포함한 꼬리 지연. P99가 기존 P50 수준이면 최악의 경우조차 매우 빨랐다는 뜻.
> 

> **write-through 캐싱**
저장할 때 캐시와 원본 저장소에 동시에 쓰는 방식. 이후 읽기는 대부분 캐시에서 처리된다.
> 

> **LSM Tree / local-quorum**
LSM은 쓰기를 로그처럼 순차 기록 후 병합하는, 쓰기에 유리한 저장 구조. local-quorum은 같은 리전 내 노드 다수 응답만으로 확정하는 일관성 수준으로, AZ 하나가 죽어도 쓰기를 계속할 수 있다.
>

## 4. 확장성과 트래픽 폭주 방어

각 라이브 이벤트는 여러 **인코딩 포맷 × 오디오 옵션 × 콘텐츠 버전(광고 유무 등)** 조합으로 수많은 **렌디션**을 만들어, 발행 측에 높은 RPS를 요구한다.

> **Rendition (렌디션)**
같은 콘텐츠의 특정 해상도·비트레이트·언어 조합으로 만든 하나의 버전.
> 

### 스케일링 아키텍처

전통적 **오리진 실드** 대신, 더 나은 캐시 일관성 제어와 단순함을 위해 **고확장 오리진**을 택했다. 오리진은 분산된 상위 계층 Open Connect 노드와 직접 연결되며, 각 사이트에서 **렌디션별 지정 노드만** 오리진에서 직접 채우도록 해 부하를 줄인다.

### 세 겹의 방어선

**1. 발행 격리 (Publishing Isolation)**

발행 트래픽은 급증하는 CDN 검색 트래픽과 달리 예측 가능 → 경로 분리가 효과적

```
발행 경로  : EC2 발행 스택 → KV 쓰기 클러스터 → Cassandra
검색 경로  : EC2 CDN 스택  → KV 읽기 클러스터 → EVCache
```

CDN 트래픽 급증이 **오리진 발행에 전혀 영향을 주지 못한다.**

1. **우선순위 속도 제한 (Priority Rate Limiting)**

부하 시 사용자 영향이 큰 요청을 우선 성공, 작은 요청은 실패 후 재시도.

- 라이브 엣지 트래픽 > DVR 트래픽 으로 우선
- 이 구분은 세그먼트 템플릿(오리진 메모리에 캐시)으로 데이터스토어 접근 없이 판단
- 낮은 우선순위가 제한되면 `max-age=5s` + `HTTP 503` 반환 → Open Connect가 5초간 동일 요청 캐시 → 오리진 반복 요청 차단

> **Live edge vs. DVR 트래픽**
라이브 엣지는 "지금 이 순간" 방송을 보는 트래픽, DVR은 되감아 과거를 보는 트래픽. 부하가 심하면 실시간 시청 경험을 먼저 지킨다.
> 

> **TTL (Time To Live)**
캐시된 데이터가 유효하게 유지되는 시간. 이 시간 동안 엣지는 오리진에 다시 묻지 않고 캐시된 응답을 재사용한다.
> 

1. **404 폭풍 대응 (404 Storm)**
    
    메타데이터를 이벤트 > 렌디션 > 세그먼트 로 계층화하고, 캐싱이 잘 되는 상위 메타데이터로 요청을 선제 거절한다.
    
    | 상황 | 응답 |
    | --- | --- |
    | 이벤트 자체가 미상 | `404` |
    | 이벤트는 알지만 타이밍 불일치 | `404` + 예상 발행 시점 TTL |
    | 세그먼트가 아예 없음 / 마감 초과 | `410 (Gone)` → 클라이언트 재요청 중단 |

메타데이터는 미디어와 분리해 컨트롤 플레인 데이터스토어에 두고(캐시 불일치를 피해 분산 캐시 미사용), 인메모리 캐싱으로 90% 이상 적중률을 얻어 데이터스토어 부담 없이 404 폭풍을 흡수한다.

> **410**
410은 "영구적으로 없음". 410을 주면 클라이언트가 재요청하지 않는다.
>

## 요약

Netflix Live Origin은 최적화된 스토리지 위에 라이브 특화로 설계된 오리진 계층이다.

- 결함 회피 - 이중 파이프라인에서 유효한 세그먼트만 선택, 나쁜 세그먼트는 마스킹으로 차단
- CDN 최적화 - 밀리초 캐싱·요청 hold open으로 네트워크 잡음 최소화
- 저지연·고가용성 스토리지 - Cassandra + EVCache로 쓰기 가용성과 200Gbps급 읽기를 양립
- 폭주 방어 - 발행 격리 · 우선순위 속도 제한 · 404 폭풍 대응의 3중 방어

⇒ 미리 배치할 수 없는 라이브의 제약을, 예측 가능한 세그먼트 스케줄 인지와 경로 분리로 해결했다.
