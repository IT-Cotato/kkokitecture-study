# 채팅 시스템 설계

## 개략적인 설계안 제시

채팅 시스템의 경우 클라이언트는 모바일 앱이거나 웹 애플리케이션이다. (클라이언트는 서로 직접 통신 X)

#### **기본 기능**

- 클라이언트들로부터 메시지 수신
- 메시지 수신자 결정 및 전달
- 수신자가 접속 상태가 아닌 경우 접속할 때까지 해당 메시지 보관

#### **메시지 송신 클라이언트 → 채팅 서비스 → 메시지 수신 클라이언트**

- 채팅을 시작하려는 클라이언트는 네트워크 통신 프로토콜을 사용하여 서비스에 접속
    - 통신 프로토콜 선정 필요
- 송신자는 HTTP 프로토콜을 활용해 채팅 서비스에 요청을 보냄
- keep-alive 헤더를 사용하면 클라이언트와 서버 사이의 연결을 끊지 않고 유지
    - handshake 횟수를 줄일 수 있음
- HTTP는 클라이언트가 연결을 만드는 프로토콜 → 수신 과정이 복잡
    - 폴링
    - 롱 폴링
    - 웹 소켓

**폴링**

클라이언트가 주기적으로 서버에게 새 메시지가 있는지 확인하는 방법

- 폴링 자주하면 비용 증가
- 새 메시지가 없는 경우 자원 낭비

**롱 폴링**

클라이언트가 새 메시지를 받거나 타임아웃 될 때까지 연결을 유지

- 메시지를 보내는 클라이언트와 수신하는 클라이언트가 같은 채팅 서버에 접속하지 않을 수 있음
- 서버 입장에서 클라이언트가 연결을 해제했는지 아닌지 알 방법이 없음
- 타임아웃이 일어나면 다시 연결 필요함

**웹 소켓**

서버가 클라이언트에게 비동기 메시지를 보낼 때 가장 널리 사용하는 기술

- 연결은 클라이언트가 시작
    - 한번 맺어진 연결은 항구적이며 양방향
    - 처음에는 HTTP 연결로 시작하여 핸드셰이크 절차를 거쳐 웹소켓 연결로 변경
    - 이후 서버와 클라이언트는 비동기적으로 메시지 전송 가능
- 방화벽이 있는 환경에서도 잘 동작 (HTTP, HTTPS가 사용하는 기본 포트번호 그대로 사용하기 때문)
- 메시지 송수신 시에 동일한 프로토콜 사용 가능
- 서버 측에서 연결 관리 필요

### 개략적 설계안

#### 무상태 서비스

- 전통적인 요청/응답 서비스에 사용 (로그인, 회원가입 등)

#### 상태 유지 서비스

- 채팅 서비스

#### 제3자 서비스 연동

- 푸시 알림

#### 규모 확장성

- 동시 접속자와 같은 정보를 통해 설계
- 단일 서버의 경우 SPOF 문제 발생

실시간으로 메시지를 주고 받기 위해 채팅 서버와 웹소켓 연결을 끊지 않고 유지해야 함

- 채팅 서버는 클라이언트 사이에 메시지를 중계하는 역할
- 접속 상태 서버는 사용자의 접속 여부를 관리
- API 서버는 로그인, 회원가입, 프로파일 변경 등 그 외 나머지 전부 처리
- 알림 서버는 푸시 알림을 보냄
- 키-값 저장소에는 채팅 이력 보관

### 저장소

채팅 시스템에서 다루는 데이터

- 사용자 프로필, 설정 ,친구 목록 → 관계형 DB
- 채팅 이력
    - 양이 많음
    - 최근 메시지가 주로 사용됨
    - 검색 기능, 언급된 메시지 등 다양한 접근
    - 읽기 쓰기 비율 대략 1:1

**→ 채팅 이력 저장에 키-값 저장소 선택**

- 수평적 규모 확장이 쉬움
- 데이터 접근 지연 시간이 낮음
- 관계형 DB의 경우 롱 테일에 해당하는 부분 처리 어려움

#### 데이터 모델

- 1:1 채팅을 위한 메시지 테이블
    - 기본 키 : message_id
    - 순서 결정에 사용
    - created_at은 메시지가 동시에 생성될 수 있기에 순서 결정에 사용 x
- 그룹 채팅을 위한 메시지 테이블
    - channel_id + message_id 복합 키를 기본 키로 사용
    - 채널은 채팅 그룹을 의미
    - channel_id는 파티션 키로도 활용 → 같은 그룹의 질의를 특정 채널로 보내기 위해

### 메시지 ID

- 고유한 값을 가져야 함
- 정렬 가능해야 하며 시간 순서와 일치해야 함

NOSQL의 경우 auto_increment 기능 없음

→ 스노플레이크, 지역적 순서 번호 생성기 사용

메시지 순서는 같은 지역(채팅방)에서만 유지되어도 되기 때문에 지역적 순서 번호 생성기 사용 가능

## 상세 설계

### 서비스 탐색

클라이언트에게 가장 적합한 채팅 서버를 추천

- 클라이언트 위치
- 서버 용량

→ **아파치 주키퍼 사용**

주키퍼로 구현한 서비스 탐색 기능 동작

1. 사용자가 로그인 시도
2. 로드밸런서가 로그인 요청을 API 서버 중 하나에 전달
3. 사용자 인증 처리 후 사용자를 서비스랑 최적의 채팅 서버를 찾음
4. 찾은 채팅 서버와 사용자 간 웹소켓 연결을 맺음

   사용자 b가 접속 중이 아닌 경우 푸시 알림 메시지를 푸시 알림 서버로 보냄

6. 채팅 서버 2는 메시지를 사용자 b에게 전송. 사용자 b와 채팅 서버 2 사이에는 웹소켓 연결이 있는 상태이므로 이를 이용

### 접속 상태 표시

**사용자 로그인**

클라이언트와 실시간 서비스 사이에 웹소켓 연결이 맺어지면 사용자 a의 상태와 last_active_at 타임 스탬프 값을 키-값 저장소에 보관 → 이후 사용자는 접속 중으로 표시

**로그아웃**

키-값 저장소에 저장된 사용자 상태를 online에서 offline으로 변경 → 이후 사용자는 접속 중이 아닌 것으로 표시

**접속 장애**

인터넷 연결이 끊어지면 웹소켓과 같은 지속성 연결도 끊어짐

→ 장애 발생 시 사용자를 오프라인으로 표시하고 복구 시 온라인으로 변경?

짧은 시간에 장애가 반복되면 접속 상태 변경이 많아짐

**박동 검사를 사용하여 이 문제 해결**

온라인 상태의 클라이언트에게 주기적으로 박동 이벤트를 접속 상태 서버로 보내도록 함

박동 이벤트를 주기적으로 보내면 온라인 상태를 유지

### 상태 정보의 전송

**발행 구독 모델 사용**

각 친구 관계마다 채널을 둠

접속 상태 변경 시 각 채널에 이를 씀

그룹 크기가 작은 경우 유용

→ 큰 경우 이벤트 메시지 수가 커짐

이 경우 그룹 채팅 입장 순간에만 상태 정보를 읽어가게 하거나, 접속 상태를 갱신하고 싶을 때 수동 갱신하도록 하여 해결 가능

## 추가 논의 내용

- 채팅 앱을 확장하여 사진, 비디오 등의 미디어를 지원하도록 하는 방법
- 종단 간 암호화 (발신인 수신자 외에는 메시지 내용 볼 수 없음)
- 캐시 - 이미 읽은 내용 캐시해 두면 서버와 주고 받는 데이터 양 감소
- 로딩 속도 개선 - 슬랙을 통해 데이터 채널 등을 분산
- 오류 처리
    - 채팅 서버 오류 - 서버가 죽을 시 새로운 서버 배정 후 접속할 수 있도록 해야함
    - 메시지 재전송 - 재시도, 큐 활용
