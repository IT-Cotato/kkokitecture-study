> https://discord.com/blog/how-discord-stores-billions-of-messages

## 1. 배경: MongoDB의 한계

- 2015년 초 Discord 첫 버전은 2개월 만에 개발, **MongoDB 단일 replica set**에 전부 저장
- 의도된 선택: "빨리 만들어 제품 검증하되, 더 견고한 솔루션으로 옮길 길을 항상 열어둔다"
- 메시지는 `(channel_id, created_at)` 복합 인덱스 하나로 관리
- 2015년 11월 누적 1억 메시지 → **데이터+인덱스가 RAM을 초과하면서 레이턴시 예측 불가**
- 메시지량: 하루 4천만(2016.07) → 1억(2016.12) → 1.2억+(2017.01), "전체 기록 영구 보관" 정책이라 계속 증가

## 2. 워크로드 분석 → DB 선정

DB를 고르기 전에 읽기/쓰기 패턴부터 분석했다는 게 핵심.

### 서버 유형에 따른 읽기 패턴

| 서버 유형 | 특징 | 캐시 |
| --- | --- | --- |
| 음성 위주 | 메시지가 몇 년치에 띄엄띄엄 → 50개 읽는데 랜덤 시크 다발 | ❌ 미스 |
| 소규모 텍스트 | 최근 데이터만 원하지만 요청 빈도가 낮음 | ❌ 밀려남 |
| 대형 공개 | 최근 1시간 데이터를 자주 요청 | ✅ 히트 |
- read/write 비율 약 50:50, 읽기가 극도로 랜덤
- 핵심 통찰: 3개 유형 중 2개 유형이 **구조적으로 캐시 미스**를 일으킴 → RAM 전제가 깨진 MongoDB에서 디스크 랜덤 I/O 폭발
- 멘션 점프, 고정 메시지, 전문검색 등 랜덤 읽기가 더 늘어날 예정이었음

### 요구사항 → Cassandra

선형 확장성(수동 리샤딩 X) / 자동 페일오버 / 저유지보수 / 검증된 기술 / 예측 가능한 성능(p95 80ms) / blob 저장소 아닐 것 / 오픈소스 → 전부 충족하는 건 Cassandra뿐.

> ① **데이터 모델링으로 랜덤 읽기를 순차 읽기로 변환** — 채널 단위로 데이터를 디스크에 연속 저장하면 캐시에 없어도 range scan으로 빠르게 읽음. 진짜 결론은 "우리 읽기는 랜덤이다"가 아니라 "채널 기준으로 모으면 랜덤이 아니게 된다"였음
② **운영 요구사항(확장/페일오버/저유지보수)을 Cassandra가 충족** — 백엔드 4명이 운영해야 했으니 필수

## 3. 데이터 모델링

### Cassandra = KKV 저장소

- 첫 번째 K = **파티션 키**: 어느 노드에 저장될지 + 디스크 위치 결정
- 두 번째 K = **클러스터링 키**: 파티션 내 정렬 + 행 식별
- 파티션 = 정렬된 딕셔너리

### 초기 설계

```sql
PRIMARY KEY (channel_id, message_id)
WITH CLUSTERING ORDER BY (message_id DESC);
```

- `channel_id` = 파티션 키 (모든 쿼리가 채널 단위)
- `created_at`은 중복 가능 → 클러스터링 키 부적합 → **Snowflake ID**(시간순 정렬 가능) 사용

### 문제: 파티션 비대화

- 임포트 중 100MB 초과 파티션 경고 발생
- 스펙상 2GB까지 지원하지만: 큰 파티션은 compaction 시 GC 압박 + 클러스터 분산 불가
- 채널은 몇 년씩 살아있으니 무한히 커지는 구조

### 해결: 시간 버킷팅

채널 × 10일 구간 의 조합마다 파티션을 하나씩 만든다

```sql
PRIMARY KEY ((channel_id, bucket), message_id)
```

- 10일 단위 버킷이면 최대 채널도 100MB 이하 (실측 기반 계산)
- 버킷 = Snowflake에서 타임스탬프 추출 (`snowflake >> 22`) 후 10일로 나눔
- 조회: 최신 버킷부터 역순으로 훑으며 50개 채울 때까지 순차 쿼리
- 비활성 서버는 여러 버킷을 뒤지는 단점 있으나, 트래픽 대다수인 활성 서버는 첫 파티션에서 해결

## 4. Dark Launch와 Eventual Consistency의 함정

**Dark launch**: MongoDB와 Cassandra에 이중 읽기/쓰기를 걸고 프로덕션 트래픽으로 무영향 검증. (Facebook Chat도 동일 기법 사용)

### 전제가 되는 Cassandra 특성 3가지

1. **쓰기 전에 읽지 않는다** — "이 key에 이 컬럼은 이 값" 하고 던지면 끝. 행이 있으면 덮어쓰고 없으면 생성 = **모든 쓰기는 upsert** (INSERT/UPDATE 구분 없음)
2. **충돌은 컬럼 단위 Last Write Wins** — 행 전체가 아니라 컬럼마다 각각 타임스탬프 비교, 늦은 쪽 채택
3. **삭제 = tombstone** — 분산 환경에서 즉시 삭제하면 죽어있던 노드가 복구될 때 데이터가 부활할 수 있음 → "삭제됨" 마커를 쓰고, 기본 10일 후 compaction 때 실제 제거

### 버그 1: 좀비 행 (edit/delete 레이스 컨디션)

거의 동시에:

```
10:00:00.000  유저 B가 삭제 → 모든 컬럼에 tombstone
10:00:00.001  유저 A가 수정 → content 컬럼 "하나만" 쓰기 (수정 API는 바뀐 것만 보냄)
```

컬럼 단위 LWW로 정산하면:

- `author_id`: 삭제가 마지막 → 삭제됨
- `content`: 수정이 삭제보다 늦음 → 살아남음

→ **PK + content만 있고 author_id는 null인 좀비 행** 탄생. MySQL이면 행 잠금 때문에 불가능한 상황이지만, Cassandra는 잠금도 없고 읽지도 않으니 발생.

**해결 선택지 비교:**

- ❌ 수정 시 행 전체 다시 쓰기 → 삭제된 메시지가 통째로 부활하는 더 나쁜 문제
- ✅ 읽을 때 필수 컬럼(author_id)이 null이면 손상 데이터로 판단하고 삭제 (사후 정리)

### 버그 2: null 쓰기 = tombstone 폭탄

- **컬럼에 null을 쓰는 것 = 그 컬럼 삭제 = tombstone 생성**
- 스키마 16컬럼 중 평균 4개만 값이 있는데, 객체를 통째로 직렬화해서 16컬럼 전부 쓰고 있었음
- → 메시지 1개당 무의미한 tombstone **12개** 생성 (하루 1억 메시지 = tombstone 12억 개)
- 해결: **non-null 값만 골라서 쓰기**

### 성능 결과

쓰기 1ms 미만, 읽기 5ms 미만, 접근 패턴 무관하게 일정 → MongoDB의 문제였던 "레이턴시 예측 불가"가 해결됨 → 1주일 만에 MongoDB 완전 퇴역.

## 5. The Big Surprise — 6개월 뒤의 장애

### 장애 전개

1. Cassandra가 모든 스레드가 10초동안 멈추는 **stop-the-world GC**를 반복하며 무응답
2. 추적해본 결과 특정 채널 하나가 로딩에 20초
3. 원인: Puzzles & Dragons 서브레딧 서버 — 들어가 보니 **메시지가 딱 1개**
4. API로 수백만 개를 삭제하고 1개만 남긴 것

### 왜 터졌나 (단계별)

**① 삭제했는데 디스크는 오히려 늘었다**

```
삭제 전: [msg_1] [msg_2] ... [msg_5,000,000]
삭제 후: [msg_1][💀] [msg_2][💀] ... [💀 499만개] [msg_5,000,000 하나만 생존]
```

원본 + tombstone 마커가 공존. 실제 정리는 10일 뒤 compaction.

**② 메시지 1개 읽는데 20초**

tombstone은 하나하나 **읽어서 확인해야 건너뛸 수 있음** → 수백만 개 스캔 → 살아있는 건 1개

**③ GC 폭발**

Cassandra는 JVM 기반. 스캔 중 tombstone 하나하나가 메모리에 객체로 올라왔다 버려짐 → **생성 속도 > 수거 속도** → GC가 stop-the-world 발동 (전체 스레드 정지 후 청소) → 10초씩 멈춤.

**④ 파급 효과**

노드가 10초 멈추면 그 노드가 담당하는 **무관한 다른 채널들까지 전부** 10초 멈춤. 문제 채널 하나가 노드를 인질로 잡은 것.

### 해결

**1) tombstone 수명 10일 → 2일**

- 쓰레기가 쌓여 있는 최대 시간을 1/5로 단축
- 원래 10일인 이유: 죽었던 노드가 복구되기 전에 tombstone이 사라지면 옛 데이터가 부활(좀비 데이터)함. tombstone은 "모든 노드가 동기화됐다"고 보장되는 기간만큼 살아야 함
- Discord는 **repair(노드 간 강제 동기화)를 매일 밤 돌리고 있었기 때문에** 2일로 줄여도 안전 → **운영 체계가 받쳐줘야 가능한 튜닝**

**2) 빈 버킷 추적**

- 문제 채널은 과거 버킷 수백 개가 "tombstone만 가득, 생존 메시지 0"
- 앱 레벨에서 "이 버킷은 비었더라"를 기억 → 다음 쿼리부터 아예 조회 안 함
- 최악의 경우에도 최신 버킷 하나만 스캔. DB를 고친 게 아니라 **쿼리 경로에서 문제 지역을 우회**

### 교훈: 분산 시스템에서 삭제는 공짜가 아니다

| 시스템 | "삭제"의 실제 동작 |
| --- | --- |
| Cassandra | tombstone 기록 → compaction 때 실제 제거 |
| Kafka | 개별 메시지 삭제 불가. retention 만료로 세그먼트째 폐기 or compaction |
| MySQL(InnoDB) | 삭제 표시 → purge 스레드가 나중에 정리 (undo log) |

공통 패턴: **"지금은 표시만, 정리는 나중에 백그라운드에서"**. 그리고 이 방식의 청구서는 **쓰기가 아니라 읽기 경로로 날아옴** — 삭제 시점엔 문제없어 보이다가, 나중에 누군가 그 데이터를 읽을 때 쌓인 마커가 한꺼번에 발목을 잡는다.
