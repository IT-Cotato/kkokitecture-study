# 알림 시스템 설계

## 알림 유형별 지원 방안

### ios 푸시 알림

- 알림 제공자 : 알림 요청을 만들어 애플 푸시 알림 서비스로 보내주는 주체
    - 단말 토큰 : 알림 요청 보내는데 필요한 고유 식별자
    - 페이로드 : 알림 내용을 담은 JSON 딕셔너리
- APNS : 푸시 알림을 ios 장치로 보내는 역할
- ios 단말 : 푸시 알림 수신하는 사용자 단말

### 안드로이드 푸시 알림

APNS 대신 FCM 사용 나머지는 ios와 동일

### SMS 메세지

트윌리오, 넥스모 같은 제 3 사업자 서비스 사용

### 이메일

센드그리드, 메일침프 같은 상용 이메일 서비스 사용

## 알림 전송 및 수신 절차

1. api를 호출하여 알림 서버로 알림을 보냄
2. 알림 서버는 사용자 정보, 단말 토큰, 알림 설정 같은 메타데이터를 캐시나 데이터베이스에서 가져옴
3. 알림 서버는 전송할 알림에 맞는 이벤트를 만들어 해당 이벤트 큐에 넣음
4. 작업 서버는 메시지 큐에서 알림 이벤트를 꺼냄
5. 작업 서버는 알림을 제 3자 서비스로 보냄
6. 제 3자 서비스는 사용자 단말로 알림 전송

## 상세 설계

### 안정성

- 데이터 손실 방지
    - 알림 데이터 데이터베이스에 보관
    - 재시도 메커니즘 구현
    - 알림 로그 데이터베이스
- 알림 중복 전송 방지
    - 중복 탐지 메커니즘 구현

## 추가 고려 사항

### 알림 설정

```
user_id bigInt
channel varchar // 알림 전송할 채널 - 푸시 알림, 이메일, sns
opt_in boolean // 해당 채널로 알림 받을 것인지 여부
```

### 전송률 제한

한 사용자가 받을 수 있는 알람의 빈도 제한 → 사용자가 알림 비활성화 하는 것 방지

### 재시도 방법

알림 전송 실패 → 재시도 큐에 넣음

### 푸시 알림과 보안

인증된 클라이언트만 api를 사용하여 알림 보낼 수 있음

### 큐 모니터링

큐에 알림이 많이 쌓이면 이벤트 처리를 빨리 하지 못한다는 의미 → 작업 서버 증설

### 이벤트 추적

알림 확인율, 클릭율, 실제 앱 사용으로 이어지는 비율 등을 데이터 분석을 통해 파악
