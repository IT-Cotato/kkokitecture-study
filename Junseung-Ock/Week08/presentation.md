# **Snowflake: 64비트 정수로 만드는 초고속 분산 ID 식별자**

> 출처: https://blog.x.com/engineering/en_us/a/2010/announcing-snowflake
>

# 개요

Twitter가 기존 MySQL의 Auto-increment 방식을 대체하기 위해 만든 고유 ID 생성 시스템이다.

중앙 서버에 의존하지 않고 각 노드(서버)가 독립적으로 정렬 가능한 ID를 생성하는 것이 핵심이다.

# 도입 배경

하나의 작은 데이터베이스 인스턴스에서 시작해, 큰 데이터베이스 인스턴스를 거쳐 여러 개의 대규모 데이터베이스 클러스터로 확장되었다.

이렇듯, Twitter의 데이터 규모가 커지면서 단일 DB의 Auto-increment로는 초당 수만 개의 트윗 ID를 발급하기 어려워졌다.

# 기존 방식의 문제점

- **MySQL 병목:** ID 발급을 위해 중앙 DB에 매번 요청을 보내는 것은 네트워크 비용이 크고, 해당 DB가 죽으면 서비스 전체가 멈춘다(SPOF).
- **정렬 문제:** NoSQL(Cassandra 등)을 사용하면 정렬되지 않은 ID가 생성되어, 트윗을 시간순으로 보여주기 위한 인덱싱 비용이 비싸진다.

**Cassandra는 고유 ID를 생성하는 내장 기능을 제공하지 않는다.**

이는  Cassandra가 유용해지는 규모에서는 모든 경우에 적용 가능한 단일 ID 솔루션을 제공하기 어렵기 때문이다.

이는 샤딩된 MySQL도 마찬가지이다.

# 고려된 옵션

## **1. MySQL 티켓 서버 (Flickr 방식)**

### 문제점

순서를 맞추려니 속도가 느려지고, 속도를 높이려니 순서가 꼬임
Flickr 방식은 여러 대의 DB 서버(홀수/짝수)를 둔다.

문제는 각 서버의 처리 속도가 다르다는 것이다.

예를 들어, 1번 서버(홀수)가 잠깐 느려진 사이 2번 서버(짝수)가 ID를 대량 발급하면,

시간상 나중에 생긴 데이터가 더 작은 ID를 갖는 역전 현상이 발생한다.

### 해결의 어려움
DB 서버 간에 동기화가 필요한데, 이 과정 자체가 네트워크 병목을 일으켜 시스템을 매우 느리게 만든다.

## 2. UUID (128비트 식별자)

## 문제점

UUID는 128비트로 매우 크다.

초당 수만 건의 트윗이 올라오는 서비스에서 ID가 128비트면 DB 인덱스 크기가 순식간에 커짐.

인덱스가 메모리에 다 들어가지 못하고 디스크를 읽기 시작하면 전체 서비스 속도가 기하급수적으로 느려진다.

## 3. ZooKeeper 순차 노드

### 성능 한계

모든 ID 발급 요청마다 전체 노드 간의 합의 과정을 거쳐야 한다.

이는 초당 수만 개의 ID를 찍어내야 하는 고성능 요구사항을 충족시키기 어려움

### 가용성 저하

ID를 발급해주는 ZooKeeper 클러스터에 문제가 생기면 Twitter 전체의 모든 쓰기 작업이 멈추게 된다.

---

→ 각 문제점들을 해결하는 요구사항

# 요구사항

- 높은 가용성을 유지하면서 초당 수만 개의 ID를 생성
- 대략 정렬 가능해야 함
    - 트윗 A와 B가 거의 같은 시간에 게시된 경우 ID가 서로 가까이 있어야 함
- 숫자들은 64비트 안에 들어가야 함
    - 메모리 및 저장 공간의 효율성
    - 데이터베이스 인덱스 성능

### 왜 64비트인가?

MySQL(InnoDB)과 같은 RDBMS에서 인덱스는 B+ Tree 구조로 관리된다.

이때, 인덱스 키가 커지면 한 페이지에 담을 수 있는 인덱스 엔트리 수가 줄어든다.

이는 트리의 높이를 높이고, 결과적으로 디스크 I/O를 증가시켜 검색 성능을 떨어뜨린다.

**결국 독립성과 성능을 위해 약간의 엄격한 순서 보장을 포기한 최선의 선택이 바로 Snowflake**

# Snowflake의 설계 (64비트 구조)

Snowflake는 하나의 ID를 64비트(Long 타입)로 구성하며, 각 비트 영역마다 고유한 의미를 부여한다.

1. **Timestamp (41비트):** 밀리초(ms) 단위 시간. ID의 가장 앞부분에 위치하여 **ID만으로 시간순 정렬**이 가능하게 한다. (약 69년 사용 가능)
2. **Worker ID (10비트):** 각 서버의 고유 번호. 최대 1,024개의 서버가 동시에 ID를 생성해도 중복되지 않게 한다.
3. **Sequence (12비트):** 동일한 1ms 안에 여러 요청이 올 경우 사용하는 일련번호. (1ms당 4,096개 생성 가능)

# Snowflake의 장점

1. **통신 불필요:** ID를 만들 때 서버끼리 통신하거나 DB를 거칠 필요가 없다. (티켓 서버 방식보다 빠름)
2. **대략적인 정렬:** 타임스탬프가 앞에 있어 대략적인 시간순 정렬이 보장된다. 이는 DB 인덱스 성능 최적화에 유리하다.
3. **간결함:** 64비트 숫자로만 이루어져 있어 UUID(128비트)보다 가볍고 저장 공간을 적게 차지한다.

# Snowflake의 단점

1. **시계 동기화 의존성:** ID의 첫 번째 구성 요소가 타임스탬프이기 때문에, 서버 간의 시간이 일치하지 않으면 문제가 발생한다. → NTP로 해결
2. **미래 시간의 한계:** 기준 시점(Epoch)으로부터 약 69년이 지나면 41비트가 가득 차서 더 이상 ID를 생성할 수 없게 됩니다. → 각 절의 길이 최적화로 해결
3. **노드 ID 관리의 복잡성:**
   각 생성기(Node)는 반드시 고유한 worker ID를 가져야 한다. (중복할당 문제, 관리 오버헤드 발생) → ZooKeeper를 활용해 worker ID만 생성하여 해결
