# 규모와 속도가 만드는 장애
- 넷플릭스는 장애가 발생하는 근본 원인을 규모와 변화의 속도 두 가지 함수로 정의

- 규모가 커지면 하드웨어 고장 확률이 높아지고, 변화가 빠르면 소프트웨어 결함 확률이 높아짐

-> 가용성 목표인 99.99%를 달성하기 위해, 단일 리전 내 분산을 넘어 AWS 리전 전체가 중단되어도 서비스가 유지되는 멀티 리전 액티브-액티브를 구축

# 액티브-액티브(Active-Active) 개요 및 요구사항
### 두 리전(미국 동부, 서부)이 동시에 트래픽을 처리하기 위한 필수 조건

- Stateless: 모든 사용자 데이터나 상태 정보는 서비스 계층이 아닌 데이터 계층에서 처리되어야 함

- 로컬 리소스 접근: 리전 내의 서비스는 반드시 해당 리전의 S3, SQS 등을 사용. 
  - 만약 데이터를 S3에 저장한다면, 앱이 직접 여러 리전의 S3 버킷에 동일한 데이터를 발행

- 비동기 복제: 리전 간 복제는 항상 백그라운드에서 비동기로 이루어져야 응답 속도가 유지

- 트래픽 분산: 평상시에는 지리적 DNS(Geo-DNS)를 통해 가장 가까운 리전으로 약 50:50으로 나뉘어 접속. 장애 시에는 정상 리전으로 모든 트래픽 전송

# 기술적 과제 1: DNS와 Denominator
### 사용자 트래픽을 정교하게 제어하기 위해 넷플릭스는 UltraDNS와 Route53을 조합하여 사용하며, 이를 제어하는 Denominator라는 라이브러리를 개발

- UltraDNS: 북미의 특정 지역 사용자를 특정 리전 엔드포인트로 유도하는 지리적 라우팅 기능을 제공(예측 불가능한 트래픽 이동을 초래할 수 있는 지연 시간 기반 라우팅 대신 이 방식을 선호)
- Route53: UltraDNS와 ELB(로드밸런서) 사이에 위치하여, 빠르고 신뢰성 있는 API를 통해 트래픽 스위칭을 담당. 리전 전환 시 Route53의 CNAME만 변경하면 되므로 훨씬 간편

# 기술적 과제 2: Zuul을 이용한 트래픽 쉐이핑(Traffic Shaping)
### 넷플릭스의 모든 서비스 입구인 Zuul은 액티브-액티브를 위해 다음과 같이 강화

- Mis-routed 요청 처리 : 사용자의 요청이 설정된 지리적 규칙과 다르게 들어온 경우,
  -  올바른 리전으로 전달(Isthmus 모드)하거나
  -  클라이언트에게 올바른 리전으로 다시 요청하도록 안내  
  -  이는 한 사용자의 세션이 여러 리전에 걸쳐 발생하는 것을 방지

- Failover 모드: 
  - 특정 리전이 Failover 모드로 선포되면, 
  - 타 리전으로 요청을 넘기지 않고 해당 리전에서 로컬로 모든 것을 처리

- 부하 차단(Load Shedding): 
  - 특정 시점의 최대 트래픽 수준을 정의하여, 그 이상의 요청은 자동으로 에러를 반환
  - 이는 장애 복구 시 트래픽이 몰려드는 'Thundering Herd' 현상으로부터 하위 시스템과 데이터베이스를 보호

# 데이터 복제: Cassandra와 EVcache

- Apache Cassandra: 
  - 카산드라의 다중 데이터센터, 비동기 복제 기능을 사용 -> 어느 Region에서 써도 다른 Region으로 비동기 복제
  - 넷플릭스는 100만 건의 데이터를 한 리전에 쓰고 0.5초 뒤 다른 리전에서 읽는 테스트를 통해 실전 적용이 가능한 수준의 일관성과 적시성을 확인

- EVcache (캐시 일관성): 
  - 빠른 응답을 위해 캐시(Memcached)를 쓰는데, 소스 데이터(Cassandra)와 일치시키는 것이 중요
  - 넷플릭스는 EVcache 클라이언트에 '원격 캐시 무효화' 기능을 추가
  - 한 리전에서 쓰기가 발생하면 SQS를 통해 다른 리전에 메시지를 보내 해당 캐시를 지우고, 다음 읽기 때 최신 데이터를 반영

# 자동화 및 배포: Mimir
- 리전이 늘어나면서 관리해야 할 환경이 6개(테스트/운영 × 3개 리전)로 증가
- 수동으로 6번 배포하는 대신, Mimir라는 워크플로 도구를 개발
- 배포 대상과 규칙을 정의하고, 시스템은 자동화된 카나리 분석(Canary Analysis)과 롤백 절차를 거쳐 여러 지역에 순차적으로 서비스를 배포
- 전 세계 배포 완료 전까지 리전 간 업데이트 간격을 수 시간씩 두어 문제를 조기에 발견

# Simian Army를 통한 검증

- Chaos Gorilla: 하나의 가용 영역(AZ) 전체를 중단시켜 남은 영역이 품질 저하 없이 서비스되는지 확인

- Split-brain: 리전 간 연결을 끊고, 데이터 복제가 지연되는 상황에서도 각 리전이 정상 작동하는지 테스트

- Chaos Kong:  리전 하나를 완전히 죽이고 모든 트래픽을 다른 리전으로 급격히 이동시키는 최종 훈련
