# 대규모 크롤링의 핵심 문제 3가지

## 1. 확장성 (Scalability)

- 수십억 개의 URL을 처리할 때 기존 알고리즘은 **URL 중복 체크**, **robots.txt 확인**, **DNS 캐시 조회** 등에서 성능 저하 발생
- 크롤 규모(N)가 커질수록:
    - 속도(S) ↓
    - 리소스 소모(Ω) ↑
- **트레이드오프**: 속도와 자원 효율성 사이의 균형이 가장 큰 난제

---

## 2. 스팸 (Spam)

- 서버 사이드 스크립트로 무한히 생성되는 **링크 팜**과 **스팸 사이트**가 크롤 큐를 장악
- 대형 합법 사이트(예: 블로그스팟, 야후 등)도 수억 개 페이지 보유
- 단순히 **도메인당 페이지 수 제한** 방식은 효과 없음

---

## 3. 예의 바른 크롤링 (Politeness)

- 서버 과부하 방지를 위해 **접근 속도 제한** 필요
- 문제: 수십억 URL이 소수 호스트에 집중되면
    - RAM 초과 발생 → 대기 큐가 RAM에 존재하는데 속도 제한에 의해 처리가 요청의 속도를 못 따라가 RAM에 요청이 쌓임
    - 크롤러가 멈춰버리는 상황 발생
- **호스트별 균형 있는 접근 제어**가 필수

# 대규모 크롤링의 핵심 기술 솔루션 3가지

## ① DRUM (Disk Repository with Update Management)

- **목적**: URL 중복 체크를 위한 새로운 디스크 자료구조
- 기존 방식(Mercator-B, Polybot)
    - 디스크에 URLseen 이라는 거대한 데이터베이스나 인덱스 파일을 만들어 두고, 새로운 URL이 들어올 때마다 이를 확인하는 방식
    - 문제 : URL 총개수 N도 늘어나는데, URL 당 처리 비용(I/O)도 N에 비례해 늘어나므로 전체 디스크 오버헤드가 **N²에 비례**해 폭발적으로 증가
- **핵심 아이디어**: 버킷 정렬(bucket-sort)
    - 들어오는 URL 해시를 k개의 버킷에 분산 저장 → 디스크 접근 X, RAM 내에서
    - 버킷이 가득 차면 디스크의 URLseen 파일과 **순차적으로 병합**
    - 랜덤 접근 대신 **순차 읽기/쓰기만 사용 → 매우 빠름**
    - 디스크에 접근할 때 버킷에 여러 요청을 모아서 한번에 접근 →I/O 횟수 감소

💡 **전화번호부 비유**

- **기존 방식:** 이름이 무작위로 적힌 수천 페이지짜리 장부에서, 무작위로 들어오는 이름 1,000개를 하나씩 찾으려고 책장을 앞뒤로 계속 넘기는 상황
- **DRUM 방식:** 새로 확인할 이름 1,000개를 가나다순으로 미리 정렬해 두고, 가나다순으로 이미 정렬되어 있는 전화번호부를 **1페이지부터 마지막 페이지까지 딱 한 번만 한 방향으로 넘기면서** 대조하는 상황

**비교 표 (이론적 최솟값 대비 오버헤드 배율):**

| 크롤 규모 | Mercator-B | Polybot | DRUM |
| --- | --- | --- | --- |
| 8억 페이지 | 11.6배 | 69배 | 2.26배 |
| 8조 페이지 | 91,541배 | 660,802배 | 104배 |

## ② STAR (Spam Tracking and Avoidance through Reputation)

- **목적**: 도메인 평판 기반 스팸 방지
    - 시간과 서버 자원 낭비를 막아줌
- **핵심 아이디어**: 스패머가 무한히 늘릴 수 없는 자원을 기준으로 신뢰도 측정
    - 외부의 다른 PLD가 우리 PLD를 링크(인용)해 준 횟수인 **인링크(in-degree)** 수 활용
    - 인링크가 많을수록 신뢰도 ↑ → 더 많은 페이지 수집 예산(budget) 부여
    - **평판이 높은 PLD :** 인링크가 엄청나게 많으므로 신뢰도가 높음. 크롤러는 이 사이트에 많은 **예산**을 줌
    - **평판이 낮은 PLD :** 인링크가 거의 없음. 크롤러는 이 사이트에 **최소한의 예산**만 줍니다.

**핵심 포인트:** 서브 도메인은 마우스 클릭 몇 번으로 무한히 만들 수 있지만, PLD를 새로 파려면 매번 등록 비용이 발생함. 스패머 입장에서는 비용 부담 때문에 이 PLD를 무한정 늘릴 수가 없음. 즉, 조작하기 어려운 **진짜 자원**

- **실험 결과**: 상위 10개 도메인이 [microsoft.com](http://microsoft.com/), [google.com](http://google.com/), [yahoo.com](http://yahoo.com/) 등 실제 신뢰할 수 있는 사이트로 채워짐 → 알고리즘 유효성 검증 완료

## ③ BEAST (Budget Enforcement with Anti-Spam Tactics) 🐾

- **목적**: 예산 초과 URL을 효율적으로 처리하는 큐 관리 알고리즘
- 기존 방식 문제:
    - 실패한 URL을 별도 큐에 모아 통째로 재검사 → 크롤 규모 N에 비례해 디스크 I/O 선형 증가 → 크롤러 멈춤
- **해결책**: 지수적으로 증가하는 다중 큐
    - 예산 내 URL → 앞쪽 큐
    - 예산 초과 URL → 뒤쪽 큐
    - 큐가 모두 소진되면 마지막 큐를 두 배로 확장
- **Q0**: 즉시 처리
- **Q1**: 예산 초과 시, 점검 주기를 2배로 늘려 뒤로 밀림
- **Q2**: 다시 초과 시, 점검 주기를 4배로 늘려 더 뒤로 밀림
- **Q3**: 여전히 초과 시, 점검 주기를 8배로 늘려 사실상 장기 대기

👉 이렇게 지수적으로 큐를 늘려가며 디스크 I/O 부담을 일정한 상한선에 수렴시킴

- **효과**: 디스크 I/O 속도 요구량이 크롤 크기와 무관하게 일정한 상한선(8.2MB/s)에 수렴함을 이론적으로 증명

# 실험 결과

2007년 6월 ~ 8월, **41일간 텍사스 A&M 대학교 단일 서버**에서 진행한 실험 결과:

## 서버 사양

- CPU: 쿼드코어 AMD Opteron 2.6GHz
- RAM: 16GB
- 디스크: 24디스크 RAID-5

## 크롤링 성과

- **수집 페이지**: 63억 8천만 HTML 페이지
- **평균 다운로드 속도**: 319mb/s (초당 1,789페이지)
- **최대 속도**: 470mb/s (초당 3,134페이지)
- **처리한 호스트**: 1억 1천7백만 개
- **파싱한 링크**: 3,946억 개
- **발견한 고유 페이지**: 414억 개

## 주요 관찰

- 크롤 진행 중 새로운 URL 발견 확률 **p ≈ 0.11**로 안정화
- 이는 **63억 페이지를 수집했음에도 웹 전체의 극히 일부만 탐색**했음을 의미

# 논문의 의의와 메시지

## 1. STAR와 BEAST의 스팸 필터링 효과

- 만약 크롤러가 웹의 모든 쓰레기 페이지와 스팸성 무한 생성 페이지까지 **100% 탐색**하려 했다면 → **무한 루프**에 빠져 서버가 터졌을 것임
- 새로운 URL 발견 확률 **p ≈ 0.11**로 안정화
    - 100개의 링크 중 약 11개만 방문할 가치 있는 새로운 고유 페이지로 큐에 진입
    - 나머지 89개는 STAR와 BEAST가 **이미 방문했거나 평판 낮은 스팸 URL**로 과감히 버림
- 결과적으로 **가치 있는 페이지 위주로 효율적 수집** → 웹 전체를 긁지 않고도 핵심 정보만 확보

---

## 2. 단일 서버로 달성한 높은 효율

- 실험은 구글·네이버 같은 대기업 데이터센터가 아닌, **텍사스 A&M 대학교 단일 서버**에서 진행
- 단 한 대의 장비로 **63억 8천만 페이지**를 안정적으로 수집
- DRUM, STAR, BEAST가 없었다면:
    - RAM(16GB)과 디스크는 몇억 페이지도 못 버티고 뻗었을 것

---

## 3. "웹의 무한성"을 데이터로 입증

- 실험 결과가 던지는 메시지:

  > "우리가 DRUM, STAR, BEAST를 총동원해 단일 서버로 63억 개를 긁어모아도, 웹 전체 규모에 비하면 조각 구름 하나 수준이다."

- 따라서 대규모 크롤러 설계 시:
    - **웹 전체를 다 긁겠다는 생각은 버려야 함**
    - STAR/BEAST처럼 **빠른 포기와 우선순위 전략**을 반드시 탑재해야 함
