# 웹 크롤러 설계

## **웹 크롤러**

웹에 새로 올라오거나 갱신된 콘텐츠를 찾아내는 것이 목적

### 1. 검색 엔진 인덱싱 (Search Engine Indexing)

- **목적:** 사용자가 키워드를 검색했을 때, 원하는 웹페이지를 **몇 초 만에 찾아서 보여주기 위함**입니다.
- **설명:**  검색 엔진의 크롤러가 전 세계 웹사이트를 돌아다니며 데이터를 수집하면, 인덱싱 시스템이 단어 별로 어느 페이지에 포함되어 있는지 정리하여 거대한 데이터베이스(색인)를 구축합니다.

### 2. 웹 아카이빙 (Web Archiving)

- **목적:** 시간이 지나면 사라지거나 수정될 수 있는 **웹 자원을 미래를 위해 그대로 보존(기록)하는 것**입니다.
- **설명:** 특정 시점의 웹페이지 형태, 이미지, 텍스트, 링크 구조를 통째로 캡처하여 저장합니다. 사이트가 폐쇄되더라도 아카이브를 통해 과거 그 시점의 모습을 그대로 볼 수 있습니다. (대표적인 예: WayBack Machine)

### 3. 웹 마이닝 (Web Mining)

- **목적:** 방대한 웹 데이터 속에서 의미 있는 **패턴, 추세, 유용한 지식을 추출(Mining)하는 것**입니다.
- **설명:** 데이터 마이닝 기법을 웹에 적용한 것입니다. 단순히 글자를 읽는 것을 넘어 사용자의 행동 패턴, 텍스트의 감정(긍정/부정), 웹페이지 간의 연관 관계 등을 분석합니다.
    - **웹 구조 마이닝:** 하이퍼링크 구조를 분석해 어떤 페이지가 중요한지 파악 (구글의 페이지랭크 알고리즘)
    - **웹 콘텐츠 마이닝:** 웹페이지의 텍스트, 이미지에서 유용한 정보 추출
    - **웹 사용 마이닝:** 사용자의 로그 데이터를 분석해 브라우징 패턴 파악

### 4. 웹 모니터링 (Web Monitoring)

- **목적:** 웹사이트의 **상태, 성능, 보안, 혹은 특정 정보의 변화를 실시간으로 감시하는 것**입니다.
- **설명:** 웹사이트가 다운되지 않고 잘 작동하는지(업타임), 로딩 속도는 정상인지(성능), 해킹 징후는 없는지(보안) 지속적으로 체크합니다. 비즈니스 관점에서는 경쟁사의 가격 변동이나 특정 키워드의 여론 변화를 실시간으로 추적하는 용도로도 쓰입니다.

## 웹 크롤러의 기본 알고리즘

1. URL 집합이 입력으로 주어지면, 해당 URL들이 가리키는 모든 웹 페이지를 다운로드한다.
2. 다운 받은 웹 페이지에서 URL들을 추출한다.
3. 추출된 URL들을 다운로드할 URL 목록에 추가하고 위의 과정을 반복한다.

## 웹 크롤러 설계

### **시작 URL 집합**

크롤링의 시작점으로 다음과 같은 성질을 고려해야 함

- **높은 연결성 (High Connectivity):** 해당 페이지가 다른 수많은 페이지로 가는 링크를 많이 품고 있어야 합니다. (나무의 잔가지로 가기 위한 '큰 줄기' 역할)
- **유효성 (Validity):** 접속 시 `404 Not Found`나 `500 Server Error`가 나지 않는 살아있는 URL이어야 합니다.
- **주기적인 업데이트:** 웹사이트 주소는 생각보다 자주 바뀝니다. 특히 불법 사이트 모니터링이나 특정 타겟 크롤링 시에는 시작 URL 집합을 주기적으로 갱신해 주어야 크롤러가 길을 잃지 않습니다.

### 미수집 URL 저장소

다운로드 할 URL을 저장 → FIFO 큐

### HTML 다운로더

인터넷에서 웹 페이지를 다운로드하는 컴포넌트

다운로드 할 URL은 미수집 URL 저장소가 제공

### 도메인 이름 변환기

URL 주소를 IP 주소로 변환

### 콘텐트 파서

웹 페이지 다운 시 파싱과 검증 절차 필요 → 이상한 웹 페이지 거름

### 중복 컨텐츠인가?

웹 페이지 해시 값 비교를 통해 확인

### 콘텐츠 저장소

HTML 문서를 보관하는 시스템

- 데이터의 양이 많은 경우 대부분의 콘텐츠를 디스크에 저장
- 인기 있는 콘텐츠는 메모리에 두어 접근 지연 시간을 줄임

### URL 추출기

HTML 페이지를 파싱하여 링크들을 골라내는 역할

상대 경로인 경우 절대 경로로 변환

### URL 필터

특정 타입이나 파일, 접속 시 오류가 발생하는 URL, 접근 제어 목록에 있는 URL 등을 크롤링 대상에서 제외

### URL 저장소

이미 방문한 URL 저장

## 웹 크롤러 작업 흐름

1. 시작 URL들을 미수집 URL 저장소에 저장
2. HTML 다운로더는 미수집 URL 저장소에서 URL 목록을 가져옴
3. 도메인 이름 변환기를 사용하여 URL의 IP 주소를 알아내고, 해당 주소로 접속하여 웹 페이지 다운로드
4. 콘텐츠 파서는 다운된 HTML 페이지를 파싱하여 올바른 형식을 갖춘 페이지인지 검증
5. 이후 저장소를 확인하여 중복 콘텐츠인지 확인
    - 이미 저장소에 있는 콘텐츠인 경우 처리하지 않고 버림
    - 저장소에 없는 콘텐츠인 경우 저장소에 저장한 뒤 URL 추출기로 전달
6. URL 추출기는 페이지에서 링크를 골라냄
7. 골라낸 링크를 URL 필터로 전달
8. 필터링이 끝나고 남은 URL만 중복 URL 판별
9. URL 저장소에 이미 저장된 URL은 버림
10. 저장소에 없는 URL은 URL 저장소에 저장하고, 미수집 URL 저장소에도 전달

## 상세 설계

### DFS VS BFS

그래프의 크기가 큰 경우 깊이가 어느 정도인지 가늠하기 어렵기 때문에 보통 BFS 선택

**BFS의 문제점**

- 한 페이지에서 나오는 링크의 상당 수는 같은 서버로 되돌아감 → 서버에 많은 수의 요청이 감 → 과부화
- URL 간에 우선순위를 두지 않음

→ 미수집 URL 저장소를 활용하여 해결 가능

### 미수집 URL 저장소

저장소 구현에 따라 서버 과부화를 방지하고 우선순위와 신선도 구별하는 크롤러 설계 가능

**예의 (서버 과부화 방지)**

큐 라우터에서 매핑 테이블을 참조하여 같은 호스트에 속하는 URL은 같은 큐로 가도록 보장

이후 큐 선택기에서 큐를 선택하고, 해당 큐에 있는 URL이 작업 스레드로 전달됨

이후 작업 스레드에서는 전달된 URL을 다운로드

**우선순위**

페이지랭크, 트래픽 양, 갱신 빈도 등을 사용하여 우선순위 책정

순위 결정 장치에서 URL을 입력 받아 우선순위 계산

이후 큐 선택기에서 우선순위에 따라 다른 횟수로 각 큐에서 URL을 꺼냄

**신선도**

웹 페이지는 수시로 추가, 삭제, 변경되므로 주기적인 재수집 필요

- 변경 이력 활용
- 중요한 페이지는 자주 재수집

**미수집 URL 저장소를 위한 지속성 저장 장치**

**① 쓰기(Write) 비용 줄이기: "모아서 한 번에 저장"**

크롤러가 웹페이지 하나를 긁어서 새로운 하위 URL 500개를 발견했다고 해볼게요.

- **버퍼가 없다면:** 디스크를 500번 찌르며 저장해야 합니다. 디스크 비명이 들리겠죠.
- **버퍼가 있다면:** 메모리 버퍼 큐에 500개를 순식간에 툭 던져두고 크롤러는 자기 일을 계속합니다. 메모리가 꽉 차거나 특정 시간(예: 1초)이 지나면, 시스템이 이 500개를 하나의 거대한 덩어리(Batch)로 묶어서 디스크에 딱 1번만 씁니다. 500번의 I/O 작업이 단 1번으로 줄어드는 마법이죠.

**② 읽기(Read) 비용 줄이기: "디스크 가기 전에 메모리에서 해결"**

일꾼 스레드들이 크롤링할 URL을 다음 줄에서 계속 가져가야 합니다.

- 매번 디스크에서 URL을 한 줄씩 읽어오는 게 아니라, 메모리 버퍼 큐가 디스크에 있는 URL들을 미리 수천 개씩 **뭉텅이로 읽어서(Prefetch)** RAM에 올려둡니다.
- 스레드들은 디스크까지 갈 필요 없이 메모리에서 `poll()` 해 가기 때문에 I/O 비용이 거의 제로에 수렴합니다.

### HTML 다운로더

HTTP 프로토콜을 통해 웹 페이지를 내려 받음

**Robots.txt**

웹 사이트가 크롤러와 소통하는 방식

- **User-agent:** 규칙을 적용할 크롤러의 이름을 지정합니다. (전체 대상은 *)
- **Disallow:** 크롤링을 **금지**할 경로를 지정합니다.
- **Allow:** Disallow로 막힌 경로 중, **예외적으로 허용**할 하위 경로를 지정합니다.

**성능 최적화**

1. 분산 크롤링

크롤링 작업을 여러 서버에 분산시켜 진행

각 서버는 여러 스레드를 돌려 작업 처리

2. 도메인 이름 변환 결과 캐시

도메인 이름 변환기(DNS)에 요청을 보내고 결과를 받기 전까지 다음 작업 수행 불가능 → 동기적

이를 해결하기 위해 요청에 대한 결과를 캐시에 보관해두고 주기적으로 갱신하여 병목 해결

3. 지역성

크롤링 작업 수행하는 서버를 지역별로 분산

크롤링 서버가 크롤링 대상 서버와 가까우면 페이지 다운로드 시간 감소

4. 짧은 타임아웃

응답이 느리거나 응답하지 않는 웹 사이트에 대해 무작정 기다리면 안됨

대기 시간을 미리 정해두고 이 시간을 지나면 다음 페이지에 대한 크롤링 진행

**안정성**

- 안정 해시 : 서버 부하 분산 시에 사용 → 서버 추가 삭제 용이
- 크롤링 상태 및 수집 데이터 저장 : 장애 발생 시 복구 용이
- 예외 처리 : 예외 발생 시 전체 시스템 중단되지 않도록 해야함
- 데이터 검증 : 무한 루프, URL 형식 이상한 경우 등 검증

**확장성**

PNG 다운로더나 웹 모니터 등으로 확장

### 문제 있는 콘텐츠 감지 및 회피

1. 중복 콘텐츠

해시나 체크섬을 활용하여 중복 콘텐츠 탐지

2. 거미 덫

크롤러를 무한 루프에 빠뜨리도록 설계된 웹 페이지 → URL 길이 제한을 통해 방지 가능

3. 데이터 노이즈

얻을 것이 없는 URL은 제외

### 추가적으로 고려해 볼 것

- 서버 측 랜더링
    - 동적으로 생성되는 링크 발견 가능
- 윈치 않는 페이지 필터링
    - 윈치 않는 페이지는 크롤링 하지 않도록
- 데이터베이스 다중화 및 샤딩
- 수평적 규모 확장
- 가용성, 일관성, 안정성
- 데이터 분석 솔루션
