# SVE: Distributed Video Processing at Facebook Scale (SOSP '17)

> Facebook이 기존 모놀리식 인코딩 스크립트(MES)를 대체하기 위해 만든 분산 비디오 처리 시스템 **SVE(Streaming Video Engine)** 논문 요약. 2015년 가을부터 프로덕션 운영 중.
>

---

## 1. 문제 배경

- Facebook에서는 하루 80억 회 이상의 비디오 조회가 발생하며, 업로드된 비디오는 **공유 전에 반드시 검증(validation) + 다중 비트레이트/포맷 재인코딩**을 거쳐야 함
- 비디오 파이프라인 6단계: **record → upload → process → store → share → stream** (이 논문은 share 이전 단계인 upload/process/store에 집중)
- 3가지 핵심 요구사항
    1. **낮은 지연시간(Low Latency)** — 업로드 후 빨리 공유할 수 있어야 함
    2. **유연성(Flexibility)** — 15개 이상의 앱(피드 게시물, Messenger, Instagram 스토리, 360 비디오 등)이 각기 다른 처리 파이프라인을 요구
    3. **장애/과부하 견고성(Robustness)** — 대규모 시스템에서 장애는 일상이고, 바이럴 이벤트로 인한 트래픽 폭증은 예측 불가

## 2. 기존 시스템 MES의 한계

- 비디오를 **하나의 불투명한 파일**로 취급: 업로드 완료 → 저장 → 단일 서버에서 순차 처리
- 문제점
    - 순차 처리로 인한 **높은 지연시간**
    - 하나의 거대한 스크립트라 **새 앱 추가와 모니터링이 어려움**
    - 장애에 취약하고 과부하 시 쉽게 무너짐
- 기존 프레임워크(MapReduce, Spark, Storm 등)를 쓰지 않은 이유
    - 배치 시스템: 데이터가 이미 존재한다고 가정 → 업로드 완료 후 처리 시작이라 지연 큼
    - 스트림 시스템: 연속 쿼리용이라 비디오별 동적 DAG 생성, 비디오 지연 처리(overload control) 등을 지원 못함
    - 범용 시스템은 **비디오 특화 인터페이스/스케줄링/장애 처리**를 제공하지 못함

## 3. SVE 아키텍처

구성: **Client → Front-end → Preprocessor → Scheduler → Worker (+ Storage)**

MES 대비 4가지 핵심 변화:

1. **클라이언트가 비디오를 GOP(Group of Pictures) 단위 세그먼트로 분할**해 업로드 — 각 세그먼트는 독립적으로 디코딩/처리 가능한 "작은 비디오"
2. Front-end가 스토리지가 아닌 **Preprocessor로 전달**
3. MES를 **Preprocessor / Scheduler / Worker 3개 컴포넌트로 분리** — 병렬화, 장애 격리, 과부하 대응 옵션 확보
4. **DAG 인터페이스**로 파이프라인 구성을 노출 — 개발자가 빠르게 반복 개발 가능

### 각 컴포넌트 역할

| 컴포넌트 | 역할 |
| --- | --- |
| **Preprocessor** | 경량 검증·복구, GOP 분할(구형 클라이언트용), 세그먼트 **메모리 캐싱**(write-through), DAG 동적 생성. 동시에 원본을 스토리지에 저장(장애 대비) |
| **Scheduler** | DAG 의존성 추적, 우선순위 큐(high/low)로 워커에 태스크 분배. 비디오 ID 기준 샤딩 |
| **Worker** | 무거운 인코딩 수행. Preprocessor 캐시 또는 중간 스토리지에서 데이터 pull |
| **중간 스토리지** | 데이터 특성별로 다른 저장소 사용. 처리 중에만 필요한 데이터는 **며칠 후 자동 만료**(명시적 삭제보다 단순하고 안전) |

## 4. 저지연 처리 (핵심: 3가지 병렬화) → **MES 대비 2.3~9.3배 개선**

1. **업로드와 인코딩 오버랩**
    - 업로드 시간이 전체 지연의 큰 부분 (3–10MB 비디오의 50%가 10초 이상 소요)
    - GOP 세그먼트 단위로 도착하는 즉시 처리 시작 → 이론상 `업로드 시간 + 마지막 세그먼트 처리 시간`까지 단축
    - 조건 충족 시(원본이 크고, 네트워크가 느리고, 기기가 지원할 때만) **클라이언트 측 재인코딩**으로 업로드량 자체를 줄임
2. **세그먼트 병렬 처리**
    - 세그먼트 크기 트레이드오프: 크면 압축률↑, 작으면 병렬성↑
        - 지연 우선(메시징 등): **10초**
        - 압축 우선(대형 고화질 게시물): **2분**
    - 병렬 처리 후 스티칭(이어붙이기)은 경량 순차 패스로 처리
    - 업로드의 약 3%는 복구(repair) 필요 — 프레임레이트 문제 68%, 메타데이터 누락 30%, 세그먼트 문제 2%
3. **저장(sync)과 처리 오버랩**
    - MES: 저장 완료 후 처리 시작 (sync 중앙값 200ms, P99 900ms + 로딩 시간)
    - SVE: 저장과 처리를 **병렬 수행**, 둘 다 끝나야 사용자에게 알림 → 동일한 내구성 보장을 유지하면서 지연만 제거
    - Preprocessor 메모리 캐시 덕분에 워커가 디스크 접근 없이 세그먼트 fetch

## 5. DAG 실행 시스템 (유연성)

### Stream-of-Tracks 추상화

- 비디오를 **video / audio / metadata 트랙**으로 분해하고, 트랙을 다시 **세그먼트 스트림**으로 분해
- 2차원 granularity로 단순함↔병렬성 트레이드오프 조절
    - 트랙 단위: 음성 인식은 audio만, 썸네일은 video만 → 코드 수정 없이 병렬성 확보
    - 세그먼트 단위: 병렬성 극대화, 대신 태스크가 세그먼트 단위 처리를 지원해야 함 (예: 전체 프레임 추적이 필요한 비디오 분류기는 세그먼트화 어려움)
- 전형적인 DAG 패턴: 트랙 분리 → 세그먼트 분할 → 인코딩별 분기 → 세그먼트 수집/조인 → 트랙 조인
- 가장 무거운 재인코딩만 최대 병렬화, 나머지 태스크는 조인된 트랙 위에서 단순하게 작성 → **병렬성과 단순함의 균형**

### 동적 DAG 생성

- 업로드 시작 시 Preprocessor가 **비디오별로 DAG를 동적 생성** (앱 종류, 비디오 특성 반영)
- 예: 저화질 업로드에는 고화질 인코딩 태스크 미포함, 세그먼트 수는 영상 길이에 따라 결정
- A/B 테스트, 신규 기능 점진적 롤아웃이 쉬움

### 어노테이션

- **Task group**: 여러 태스크를 한 워커에서 묶어 실행 → 스케줄링 오버헤드/데이터 이동 제거하면서 세밀한 모니터링 유지
- **Latency-sensitive**: 사용자 대기 경로의 태스크 표시 (조상 태스크까지 자동 전파) → 과부하 제어에 활용
- 태스크 단위 분리로 **자동 모니터링·장애 지점 식별**이 쉬워짐

## 6. 장애 허용 (Fault Tolerance)

- 컴포넌트별 전략: 상태 외부 복제(front-end, preprocessor, scheduler), 시간적 재실행(worker), 다중 디스크 복제(storage)
- **태스크 재시도 정책 (최대 21회 실행)**
    - 동일 워커에서 로컬 재시도 최대 2회 → 실패 시 스케줄러가 다른 워커로 최대 6회 재스케줄
    - 효과: 첫 워커 성공률 99.788% → 최종 **99.995%**
    - 로컬 첫 재시도만으로 메타데이터/중간 데이터 쓰기 실패 50% 이상 감소
    - 비결정적 버그를 마스킹하면서, 로그로 재시도율 높은 태스크를 발굴해 버그 추적 가능
- **느린 업로드 대응**: 며칠짜리 grace period 동안 원본 세그먼트 보관, DAG job이 purge돼도 업로드 완료 시 재스케줄
- **입력 다양성**: 수천 종 기기, 수백 개 코덱 조합 → 코너 케이스 버그는 모니터링으로 발견 후 수정
- **프로덕션 검증**: 리전 내 preprocessor 20% 강제 종료, 워커 5% 자연 장애 실험 모두에서 **처리량·성공률·E2E 지연 무영향**

## 7. 과부하 제어 (Overload Control)

### 과부하 원인 3가지

1. **Organic**: 새해 전야(일일 피크의 3배), 아이스버킷 챌린지, 2016 터키 쿠데타(1.2배) 등
2. **Load-testing**: Kraken이 데이터센터 드레인 테스트 시 인접 DC에 트래픽 집중
3. **Bug-induced**: preprocessor 메모리 누수, ffmpeg 버전 변경으로 인한 처리 속도 저하 등

### 단계적 대응 (escalating reactions)

1. **지연 비민감 태스크 연기** — 워커 CPU가 "moderate" 임계값 초과 시 latency-insensitive 태스크를 큐 뒤로 보냄
2. **신규 업로드를 타 리전으로 리다이렉트** — 온콜 엔지니어의 수동 조정 + 자동 메커니즘. 태스크가 아닌 *업로드 자체*를 옮겨서 워커와 캐시(preprocessor)를 같은 리전에 co-locate → 크로스 리전 fetch 방지
3. **최후 수단: 신규 업로드 처리 자체를 지연** — preprocessor 메모리 한계 도달 시 새 업로드를 스토리지로 보내 나중에 처리. 전체를 지연시키는 것이 캐시 스래싱으로 모든 비디오가 느려지는 것보다 나음

## 8. 프로덕션 운영 교훈

- **라이브스트리밍과 불일치**: 라이브는 녹화 속도에 맞춰 초당 1초씩만 처리하면 되므로 병렬화·동적 DAG·재시도가 오히려 지연만 추가 → 별도 시스템으로 운영 (현재 워커 통합 검토 중)
- **글로벌 일관성 장애**: 비디오→preprocessor 바인딩을 eventually-consistent 저장소에 두었다가, 업로드가 다른 리전으로 라우팅될 때 바인딩 미복제로 실패 → 재시도 루프로 임시 대응, 장기적으로 강한 일관성 저장소로 이전 검토
- **리전 일관성 장애**: 중간 메타데이터를 cache-only 저장소에 두었다가 워커 풀이 클러스터보다 커지자 stale read/데이터 유실 발생 → **영속 DB로 이전** (연산당 수십 ms 지연 증가를 감수하고 안정성 확보)
- **Continuous Sandboxing**: 태스크마다 Linux namespace 샌드박스를 새로 만들자 메시징(작은 비디오 다수 동시 처리)에서 지연 급증 → **샌드박스를 재사용**하는 방식으로 해결

## 9. 핵심 요약

- 비디오를 **GOP 세그먼트 = 독립적인 작은 비디오**로 쪼개는 것이 모든 설계의 출발점
- **업로드, 처리, 저장 3중 오버랩 + 세그먼트 병렬 처리**로 post-upload 지연 2.3~9.3배 단축
- **비디오별 동적 생성 DAG + stream-of-tracks 추상화**로 15개 이상 앱의 다양한 파이프라인을 단순하게 지원
- 장애는 **재시도 계층화(로컬 2회 + 타 워커 6회)**로, 과부하는 **연기 → 리전 리다이렉트 → 업로드 지연**의 단계적 대응으로 흡수
- 범용 프레임워크 대신 **도메인 특화 시스템**을 만든 것이 핵심 의사결정 — 인터페이스, 스케줄링, 장애 처리, 과부하 제어 모두 비디오 워크로드에 맞춤
