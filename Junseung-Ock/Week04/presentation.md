# Maglev(매그레브) - A Fast and Reliable Software Network Load Balancer
출처 : [Maglev](https://static.googleusercontent.com/media/research.google.com/en//pubs/archive/44824.pdf)

---

## 서론 
구글은 인터넷 트래픽 처리를 위해 2008년부터 Maglev라는 소프트웨어 네트워크 로드 밸런서를 사용
Maglev는 특수 하드웨어 없이 일반 리눅스 서버에서 작동하며, 필요에 따라 서버를 추가하거나 제거하는 것만으로 용량을 조절
주요 목표는 패킷 처리 성능의 극대화(단일 서버로 10Gbps 처리)와 장애 발생 시에도 기존 연결을 유지하는 신뢰성 확보
---
## 시스템 개요
Maglev는 구글 클러스터 내의 모든 트래픽 입구에 위치
- 구조 
  - 외부 라우터가 ECMP(Equal Cost Multipath)를 통해 들어오는 패킷을 여러 Maglev 머신으로 분산. 
  - 각 Maglev 머신은 패킷을 검사하여 적절한 백엔드 서비스 엔드포인트로 다시 전달.

- VIP(Virtual IP)
  - Maglev는 서비스에 할당된 가상 IP를 외부에 노출.
  - 이를 통해 들어오는 트래픽을 실제 백엔드 서버의 IP로 캡슐화(GRE 등 사용)하여 전달.
---
## Maglev 머신 아키텍처 (Maglev Machine Architecture)
성능을 위해 일반적인 리눅스 커널의 네트워크 스택을 사용하지 않는 구조

- Forwarder: 패킷을 전달하는 핵심 엔진

- Steering & Mux: 들어오는 패킷을 여러 CPU 코어에 분산(Steering)하고, 처리된 패킷을 다시 내보내는(Mux) 구조.

- Kernel Bypass: NIC(네트워크 카드)에서 패킷을 직접 가져오는 사용자 공간 전용 드라이버를 사용하여 커널과 사용자 공간 사이의 복사 비용을 제거.

## Maglev 해싱 알고리즘 (Maglev Hashing)

- 일관된 해싱의 한계: 기존 방식은 서버 목록이 변할 때 데이터 재배치 비용이 발생하며, 부하가 아주 미세하게 불균형 발생

- Maglev Hashing의 원리: 각 백엔드 서버는 자신만의 '선호도 목록(Preference List)'을 가짐. Maglev는 이 목록을 사용하여 거대한 '룩업 테이블(Lookup Table)'을 채움.
  - 선호도 목록 : 서버는 M개의 테이블 칸 중 어디를 먼저 찜하고 싶은지 순위를 매김 (시작점과 간격을 사용)
  - 룩업 테이블 채우기 : 모든 서버가 돌아가면서 자기 차례에 가장 높은 순위의 빈칸을 차지 (다른 서버에게 선점되었다면 다음 우선순위 칸 차지)

- 효과: 룩업 테이블 크기가 충분히 크다면, 백엔드 서버 간의 부하 분산이 거의 완벽하게 균등해지며, 특정 서버가 죽더라도 해당 서버로 가던 연결 외의 다른 연결들은 영향을 받지 않음.

---
## Maglev 해싱 알고리즘 예시
1. 준비 단계: 서버의 선호도 목록
각 서버는 요청을 처리할 때 어떤 인덱스(테이블 칸)에 배정되길 원하는지 우선순위를 정함
(offset, skip 수식을 통해 생성된 순서)
- 서버 A: [3, 0, 4, 1, 5, 2, 6]
- 서버 B: [0, 2, 4, 6, 1, 3, 5]
- 서버 C: [6, 2, 5, 1, 4, 0, 3]

2. 배치 단계: 룩업 테이블 구축
서버들이 돌아가면서 빈 칸을 하나씩 차지. 이미 누가 차지한 칸이면 다음 순위로 넘어감.
- 1라운드
- 서버 A → 3번 칸 비었음 → A 배정
- 서버 B → 0번 칸 비었음 → B 배정
- 서버 C → 6번 칸 비었음 → C 배정
- 2라운드
- 서버 A → 0번 칸은 B가 있음 → 다음 4번 칸 비었음 → A 배정
- 서버 B → 2번 칸 비었음 → B 배정
- 서버 C → 2번 칸은 B가 있음 → 다음 5번 칸 비었음 → C 배정
- 마지막
- 남은 1번 칸은 서버 A가 차례대로 확인하여 A 배정

3. 운영 단계: 요청 처리
- 요청 도착: 요청 id = 10
- 인덱스 계산: 10 % 7 = 3
- 룩업 테이블 확인: 3번 칸에는 서버 A
- 연결: 요청은 서버 A로 전달

## 연결 추적 (Connection Tracking)

Maglev는 상태가 있는(Stateful) 연결을 관리.

- Connection Table: 5-tuple(소스 IP, 목적지 IP, 포트 등) 해시를 사용하여 현재 진행 중인 연결이 어떤 백엔드로 가고 있는지 기록.

- 탄력성: Maglev 머신 자체가 교체되는 상황에서도 일관된 해싱 덕분에 패킷이 여전히 올바른 백엔드로 전달될 가능성이 높음.

---

## 전체적인 흐름 요약
- 해싱 (O(1)): 요청의 5-tuple 정보를 숫자로 변환
- 인덱싱: 그 숫자를 테이블 크기 M으로 나눠 인덱스 결정
- 룩업: 미리 공평하게 배정된 테이블에서 담당 서버 확인
- 연결 유지 (Stateful): 이미 연결된 요청이라면 Connection Table을 먼저 확인해 기존 서버로 전달
- 탄력적 확장:
  - 서버가 늘어나면 테이블 일부 칸만 새 서버로 교체 → 대부분 요청은 기존 서버로 유지
  - 로드밸런서 교체 시에도 동일한 알고리즘으로 동일한 테이블을 재구축 → 요청은 원래 서버로 정확히 전달
---

## 운영 경험 및 성능 평가 (Operational Experience)
- 성능: 작은 패킷(64바이트) 환경에서도 단일 Maglev 머신이 10Gbps 회선을 가득 채울 수 있음을 입증.

- 확장성: 구글 검색, Gmail 등 초거대 서비스에서 8년 이상(논문 발표 시점 기준) 안정적으로 작동하며 수조 개의 패킷을 처리.

- 유연성: 하드웨어 장비와 달리 소프트웨어 업데이트만으로 새로운 기능을 즉시 모든 데이터 센터에 적용.
