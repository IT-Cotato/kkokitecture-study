# API 안정성 및 부하 관리 전략 (Stripe 사례 중심)
출처 : [https://stripe.com/blog/rate-limiters](https://stripe.com/blog/rate-limiters)

---

## 1. 개요: 왜 API 보호가 필요한가?
모든 웹 애플리케이션과 API에서 **가용성과 신뢰성**은 최우선 가치  
서비스 규모가 커짐에 따라 단순히 인프라 용량을 늘리는 것만으로는 대응할 수 없는 상황이 발생
특히 **악의적인 공격, 잘못 작성된 클라이언트 스크립트, 내부 시스템 장애** 시에도 핵심 서비스의 연속성을 보장하기 위한 전략적 접근이 필수적

---

## 2. 주요 관리 시나리오
다음과 같은 상황에서 적절한 트래픽 제어는 API의 안정성을 비약적으로 높임

- **특정 사용자의 트래픽 폭주**  
  오작동하는 스크립트나 고의적인 과부하 시도로부터 전체 서비스를 보호해야 할 때.

- **우선순위 기반 리소스 배분**  
  낮은 우선순위(예: 분석 데이터 요청)의 대량 트래픽이 높은 우선순위(예: 결제 처리)의 트래픽을 방해하지 않도록 관리해야 할 때.

- **시스템 비상 상황 대응**  
  내부 결함으로 전체 트래픽 처리가 불가능할 때, 핵심적인 요청만을 선별하여 처리해야 할 때.

---

## 3. 핵심 전략의 구분
Stripe는 트래픽 제어의 목적과 상황에 따라 두 가지 메커니즘을 상호 보완적으로 사용합니다.

### A. 속도 제한기 (Rate Limiter)
- **목적**: 네트워크 송수신 트래픽 속도 제어
- **적용**: 사용자의 요청 간격을 조절해도 서비스 결과에 영향이 없는 경우에 적합
- **효과**: 개별 사용자가 API 엔드포인트에 접근하는 속도를 조절하여 일상적인 운영의 안정성을 유지

### B. 부하 차단기 (Load Shedder)
- **목적**: 시스템 전체의 상태를 기반으로 한 비상 대응
- **적용**: 서비스 속도가 평소보다 느려지거나 장애가 예상되는 긴급 상황에서 작동
- **효과**: 요청자 개인이 아닌 **시스템 전체의 건전성**을 기준으로 결정
    - 비상시 핵심 비즈니스 로직(예: 결제, 전력 공급 유지)을 위해 덜 중요한 요청을 과감히 포기(차단)

## API 안정성 및 부하 관리 전략


---

### 요청 속도 제한기 (Request Rate Limiter)
**"가장 기본적이고 중요한 1차 방어선"**

- **정의**: 각 사용자(User)가 초당 보낼 수 있는 요청 수($N$)를 제한
- **주요 특징**:
    - **스크립트 폭주 방지**: 잘못된 루프나 스크립트로 인한 과도한 트래픽 차단
    - **버스트(Burst) 허용**: 갑작스러운 트래픽 급증을 잠시 수용
    - **환경 일관성**: 개발(Test) 모드와 운영(Live) 모드 동일 제한 적용

---

### 동시 요청 제한기 (Concurrent Requests Limiter)
**"횟수가 아닌, 현재 점유 중인 자원의 양을 제한"**

- **정의**: 초당 횟수가 아닌, **동시에 처리 중인(In-flight) 요청 개수**를 제한 (예: 20개)
- **필요성**:
    - CPU 소모가 크거나 응답 시간이 긴 API 보호
    - 재시도(Retry)로 인한 서버 부하 원천 차단
- **효과**: 비싼 자원 경합(Contention) 문제 해결, 전체 시스템 응답 불능 방지

---

### 함대 사용량 부하 차단기 (Fleet Usage Load Shedder)
**"중요한 비즈니스 로직을 위한 전용 차선 확보"**

- **정의**: 전체 인프라(Fleet) 자원 중 일정 비율(예: 20%)을 '중요 요청' 전용으로 예약
- **작동 방식**:
    - 요청을 중요(Critical) vs 비중요(Non-critical)로 분류
    - 전체 자원 사용률이 임계치(예: 80%) 초과 시 비중요 요청은 **503 Service Unavailable** 반환
- **목적**: 대규모 장애 발생 전 핵심 기능을 지켜내는 예방책

---

### 작업자 활용 부하 차단기 (Worker Utilization Load Shedder)
**"장애 발생 시 시스템 붕괴를 막는 최후의 보루"**

- **정의**: 개별 작업자(Worker)가 한계에 도달하면 우선순위 낮은 트래픽부터 차단
- **우선순위 계층 (차단 순서)**:
    1. 테스트 모드 트래픽 (가장 먼저 차단)
    2. GET 메서드 (단순 조회)
    3. POST 메서드 (데이터 생성/변경)
    4. 중요 메서드 (결제 등 핵심 로직, 가장 나중에 차단)
- **핵심 기술 (Anti-Flapping)**:
    - 차단과 복구는 천천히(Gradually) 진행
    - 부하가 줄었다고 즉시 모든 트래픽을 허용하면 **플래핑(Flapping)** 발생 위험

---

### 요약: 계층적 방어 체계

| 계층 | 대상 | 성격 |
|------|------|------|
| Request Limiter | 사용자별 요청 수 | 예방 |
| Concurrent Limiter | 동시 실행 작업 수 | 자원 보호 |
| Fleet Load Shedder | 전체 인프라 비중 | 중요도 우선 |
| Worker Load Shedder | 개별 서버 가용성 | 최후 방어 |

##  실전 속도 제한 장치 구축 및 운영 가이드

---

### 핵심 알고리즘: 토큰 버킷 (Token Bucket)
Stripe를 포함한 많은 서비스가 선택한 표준 알고리즘

- **작동 방식**
  - 각 사용자마다 '토큰 버킷'이 할당
  - 요청 시마다 토큰이 차감되며, 버킷이 비면 요청이 거부 
  - 토큰은 정해진 속도로 서서히 다시 채워짐
- **구현 도구**: 분산 환경에서 상태를 공유하기 위해 Redis와 같은 고성능 인메모리 데이터베이스를 주로 사용

---

### 안정적인 구현을 위한 4대 원칙
속도 제한기를 만들 때 반드시 고려해야 할 실무 포인트

- **안전한 미들웨어 연결 (Fail-Safe)**  
  속도 제한 로직이나 Redis에 장애가 생기더라도 전체 API 서비스가 중단되어서는 안됨 
  문제가 생기면 차라리 제한을 풀고 통과시키는 방향(Fail-open)으로 설계

- **명확한 에러 피드백**  
  단순히 에러를 던지는 것이 아니라, 상황에 맞는 HTTP 코드 반환:
    - `429 Too Many Requests`
    - `503 Service Unavailable`  
      또한 사용자가 언제 다시 시도할 수 있는지 메시지를 포함해야 합니다.

- **킬 스위치(Kill Switch) 마련**  
  버그로 정상 요청이 차단될 경우를 대비해, 즉시 기능을 끌 수 있는 **기능 플래그(Feature Flag)**와 실시간 모니터링 지표를 설정

- **단계적 적용 및 모니터링**  
  처음부터 트래픽을 강하게 차단하지 말고, 실제 운영 데이터로 시뮬레이션하며 임계값(Threshold)을 조정

---

### 도입 로드맵 (Step-by-Step)
모든 기능을 한꺼번에 구축할 필요는 없음 -> 규모에 맞춰 점진적으로 도입

1. **요청 속도 제한기(Request Rate Limiter)** 구축 → 악의적 공격 및 비정상 스크립트 폭주 방지
2. 서비스 규모 확장 시 **동시성 제한, 함대/작업자 부하 차단기** 단계적 도입 → 내부 인프라 보호
3. **관찰 가능성(Observability)** 강화 → 제한 발생 빈도와 패턴 분석, 비즈니스 로직에 맞게 고도화

---

### 결론
속도 제한은 API 확장을 위한 가장 강력한 도구
처음에는 단순하게 시작하되, **"시스템 장애가 발생해도 서비스는 계속되어야 한다"**는 원칙 하에 안전장치를 겹겹이 쌓아가는 것이 핵심
