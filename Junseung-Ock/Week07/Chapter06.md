# 키-값 저장소 설계

**키-값 저장소**

키-값 데이터베이스라고도 불리는 비 관계형 데이터베이스

저장된 값은 고유한 식별자를 키로 가져야 함

put(key, value) → 키-값 쌍을 저장소에 저장

get(key) → 인자로 주어진 키에 매달린 값을 꺼냄

ex) 아마존 다이나모, memcached, 레디스

**키**

일반 텍스트 or 해시 값

**값**

문자열 or list or 객체 등

## 단일 서버 키-값 저장소

키-값 쌍을 메모리에 해시 테이블로 저장

- 속도 빠름
- 데이터가 많을 경우 메모리에 모두 두는 것이 불가능
    - 데이터 압축
    - 자주 쓰는 데이터만 메모리에 저장, 나머지는 디스크에 저장

## 분산 키-값 저장소

키-값 쌍을 여러 서버에 분산시킴

#### CAP 정리

- 일관성 consistency
    - 어떤 노드에 접속하던지 언제나 같은 데이터를 보게 함
- 가용성 availability
    - 일부 노드에 장애가 발생해도 항상 응답을 받을 수 있어야 함
- 파티션 감내 partition tolearnce
    - 파티션은 두 노드 사이에 통신 장애가 발생했음을 의미
    - 파티션 감내는 파티션이 발생하더라도 시스템은 계속 동작해야 함을 의미

일관성, 가용성, 파티션 감내 중 한 가지의 희생이 반드시 필요

→ 분산 시스템은 반드시 파티션 문제를 감내할 수 있도록 설계해야 함

#### 실세계의 분산 시스템

파티션 문제는 피할 수 없음 → 일관성과 가용성 사이에서 하나를 선택해야 함

은행권의 경우 일관성을 양보하지 않음 → 상황 해결될 때까지 오류 반환

## 시스템 컴포넌트

### 데이터 파티션

대규모 애플리케이션의 경우 데이터를 파티션 단위로 나누어 여러 대 서버에 저장

- 데이터를 여러 서버에 고르게 분산 고려
- 노드가 추가되거나 삭제될 때 데이터 이동 최소화 고려

→ 안정 해시를 통해 해결 (규모 확장 자동화, 다양성)

### 데이터 다중화

높은 가용성과 안정성을 확보하기 위해 데이터를 비동기적으로 다중화

링을 돌면서 만나는 n개 서버에 데이터 사본을 보관 (모든 서버에 사본을 저장하는 것은 비효율적)

→ 가상 노드를 사용하는 경우 같은 물리 서버 중복 선택 방지 필요

### 데이터 일관성

정족수 합의를 통해 다중화된 데이터가 적절히 동기화 되도록 함

N = 사본 개수

W = 쓰기 연산에 대한 정족수(쓰기 연산이 성공한 것으로 간주하기 위해 필요한 쓰기 연산 성공 서버 최소 수)

R = 읽기 연산에 대한 정족수(읽기 연산이 성공한 것으로 간주하기 위해 필요한 읽기 연산 성공 서버 최소 수)

중재자 = 클라이언트와 노드 사이에서 프록시 역할

R=1, W=N → 빠른 읽기 연산에 최적화

W=1, R=N → 빠른 쓰기 연산에 최적화

W+R>N → 강한 일관성 보장

W+R≤N → 강한 일관성 보장 X

**일관성 모델**

- 강한 일관성 : 모든 읽기 연산은 가장 최근에 갱신된 결과를 반환
    - 모든 사본에 쓰기 연산의 결과 반영될 때까지 읽기 쓰기 금지
    - 고가용성 시스템에 부적합
- 약한 일관성 : 읽기 연산은 가장 최근에 갱신된 결과를 반환하지 못할 수 있음
- 결과적 일관성 : 약한 일관성의 한 형태 갱신 결과가 결국에는 모든 사본에 반영
    - 카산드라, 다이나모
    - 쓰기 연산 병렬적 발생 → 일관성 깨짐 → 클라이언트가 이를 해결해야 함

**비 일관성 해소 기법 : 데이터 버저닝**

데이터 다중화 → 가용성 향상, 일관성 깨질 가능성 향상

→ 이를 해결하기 위해 버저닝 벡터 시계 등장

**벡터 시계**

[서버, 버전]의 순서쌍을 데이터에 매단 것

선행, 후행 버전 파악 및 버전 충돌 판별

- **X ≤ Y**: 모든 서버의 카운트에서 X가 Y보다 작거나 같으면, Y가 X 이후 버전(즉, Y가 더 최신).
- **X ≥ Y**: 모든 서버의 카운트에서 X가 Y보다 크거나 같으면, X가 Y 이후 버전(즉, X가 더 최신).
- **X와 Y가 교차**: 어떤 서버에서는 X가 크고, 다른 서버에서는 Y가 크면 → 충돌 발생.

단점

- 클라이언트가 충돌 해결 → 클라이언트 구현 복잡
- [서버, 버전] 순서쌍 수가 빠르게 증가 → 임계치 설정 필요

#### 장애 처리

**장애 감지**

보통 두 대 이상의 서버가 똑같이 서버 A의 장애를 보고해야 장애가 발생했다고 간주

→ 멀티캐스팅 채널 구축 (서버가 많을 때는 비효율적)

→ 가십 프로토콜 (효율적)

**가십 프로토콜**

- 각 노드는 멤버십 목록을 유지 (멤버 ID, 박동 카운터 쌍의 목록)
- 각 노드는 주기적으로 자신의 박동 카운터 증가
- 각 노드는 무작위로 선정된 노드들에게 주기적으로 자기 박동 카운터 목록 보냄
- 박동 카운터 목록을 받은 노드는 멤버십 목록 갱신
- 어떤 멤버의 박동 카운터 값이 지정된 시간 동안 갱신되지 않으면 장애로 간주

**일시적 장애 처리**

가십 프로토콜로 장애를 감지한 시스템은 가용성을 보장하기 위해 필요한 조치를 해야 함

엄격한 정족수 → 읽기와 쓰기 연산 금지

느슨한 정족수
- W개와 R개의 건강한 서버를 해시 링에서 고름 (장애 서버는 무시)
- hinted handoff 기법을 통해 장애 처리 후 일관성 보존

**영구 장애 처리**

반-엔트로피 프로토콜
→ 분산 시스템에서 **노드 간 데이터 불일치**를 줄이고, 모든 노드가 동일한 상태로 수렴하게 만드는 것
→ 이 과정에서 머클 트리 사용

**머클 트리**

- 목적: 데이터 전체를 직접 비교하지 않고, **효율적으로 차이를 탐지**하기 위해 사용
- 구조: 이진 트리 형태로, 리프 노드에는 실제 데이터 블록의 해시값이 저장되고, 상위 노드에는 자식 노드들의 해시를 합쳐서 만든 값이 저장됨
- 장점: 루트 해시만 비교해도 데이터가 동일한지 빠르게 확인 가능

**예시**

- 노드 A와 노드 B가 1,000개의 키-값 데이터를 가지고 있다고 가정
- 모든 데이터를 직접 비교하면 네트워크 비용이 크지만, 머클 트리를 사용하면 효율적
- A와 B는 각각 자신의 데이터로 머클 트리를 생성하고, 루트 해시를 서로 비교
    - 루트 해시가 같으면 → 전체 데이터가 동일
    - 루트 해시가 다르면 → 하위 노드 해시를 단계적으로 비교

**시스템 아키텍처 다이어그램**

- 클라이언트는  get, put과 통신
- 중재자는 클라이언트와 키-값 저장소 사이의 프록시 역할
- 노드는 안정 해시의 해시 링 위에 분포
- 노드 추가 삭제할 수 있도록 시스템은 완전히 분산
- 데이터는 여러 노드에 다중화
- 모든 노드가 같은 책임 → SPOF 존재 X

**쓰기 경로**

1. 쓰기 요청이 커밋 로그 파일에 기록
2. 데이터가 메모리 캐시에 기록
3. 캐시가 가득차거나 임계치에 도달하면 데이터는 디스크의 SSTable에 기록

SSTable : Sorted-String Table → 키 값의 순서쌍을 정렬된 리스트 형태로 관리하는 테이블

**읽기 경로**

데이터가 메모리 캐시에 있는지 확인

- 있는 경우 → 데이터를 클라이언트에게 반환
- 없는 경우 → 디스크에서 데이터를 가져옴

디스크의 SSTable에 찾는 키가 있는지 확인 → 블룸 필터 사용

1. 데이터가 메모리에 있는지 검사 없다면 2로 이동
2. 블룸 필터를 검사
3. 블룸 필터를 통해 어떤 SSTable에 키가 보관되어 있는지 알아냄
4. SSTable에서 데이터를 가져옴
5. 데이터를 클라이언트에게 반환
