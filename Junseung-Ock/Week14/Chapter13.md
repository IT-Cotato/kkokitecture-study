# 검색어 자동완성 시스템

## 개략적인 설계

- 데이터 수집 서비스
    - 사용자가 입력한 질의를 실시간으로 수집하는 시스템
    - 질의와 빈도를 저장
- 질의 서비스
    - 주어진 질의에 다섯 개의 인기 검색어를 정렬해 내놓는 서비스
    - 수집에서 저장된 빈도 중 원하는 순위까지 반환 (ex. top 5 반환)

## 상세 설계

### 트라이 자료구조

관계형 DB에서 인기 있는 5개를 뽑아내는 방법은 비효율적 → 트라이를 활용해 해결

**트라이**

문자열들을 간략하게 저장할 수 있는 자료구조

- 트리 형태의 자료구조
- 루트 노드는 빈 문자열
- 각 노드는 글자 하나를 저장. 26개의 자식을 가질 수 있음 (알파벳 수)
- 각 트리 노드는 하나의 단어 또는 접두어 문자열을 나타냄

**관련 용어**

```
- p : 접두어의 길이
- n : 트라이 안에 있는 노드 개수
- c : 주어진 노드의 자식 노드 개수
```

**가장 많이 사용된 질의어 k개를 찾는 과정**

```
- 해당 접두어를 표현하는 노드를 찾는다. O(p)
- 해당 노드부터 시작하는 하위 트리를 탐색하여 모든 유효 노드를 찾는다.
  유효한 검색 문자열을 구성하는 노드가 유효 노드다. O(c)
- 유효 노드들을 정렬하여 가장 인기 있는 검색어 k개를 찾는다. O(c log c)

일고리즘의 총 시간 복잡도는 소요된 시간의 합
ex) O(p)+O(c)+O(c log c)
```

**전체 트라이를 다 검색하는 경우 방지하기 위한 방법**

- 접두어의 최대 길이 제한

```
사용자가 긴 검색어를 입력하는 일은 거의 없음 -> p는 작은 정수값이라 가정
O(p) 는 O(1)로 바뀜
```

- 노드에 인기 검색어 캐시

```
각 노드에 k개의 인기 검색어를 저장
캐시를 통해 검색어를 질의하는 시간 복잡도 낮춤
각 노드에 질의어를 저장할 공간이 있어야 함
-> 빠른 응답 속도가 중요할 때 사용 O(1)
```

### 데이터 수집 서비스

사용자가 검색 창에 입력 시 실시간 데이터 수정 → 실용적이지 않음

- 수천만 건의 질의에 대해 트라이 갱신 → 속도 저하
- 트라이 생성 후 인기 검색어는 자주 변하지 않음 → 자주 갱신할 필요 x

**데이터 분석 서비스 로그**

검색 창에 입력된 질의에 관한 원본 데이터 보관

- 추가 o, 수정 x
- 인덱스 x

**로그 취합 서버**

많은 양의 로그 취합 (주기는 실시간서의 중요도에 따라 다름)

**취합된 데이터**

주기에 따라 취합한 데이터

쿼리, 시간, 빈도 저장

**작업 서버**

비동기 작업을 실행하는 서버 집합

트라이 자료구조를 만들고 트라이 DB에 저장하는 역할

**트라이 캐시**

읽기 연산 성능을 높임

주기에 맞게 DB 스냅샷을 떠 갱신

**트라이 DB**

지속성 저장소

- 문서 저장소
- 키-값 저장소
    - 모든 접두어를 키로 변환
    - 각 트라이 노드에 보관된 데이터를 해시 테이블 값으로 변환

### 질의 서비스

1. 검색 질의가 로드밸런서로 전송
2. 로드밸런서가 질의를 API 서버로 전송
3. API 서버는 트라이 캐시에서 데이터를 가져와 자동 완성 검색어 제안 응답 구성
4. 트라이 캐시에 데이터가 없는 경우 DB에서 가져와 캐시에 채움

**속도 최적화 방안**

- AJAX 요청

```
요청을 보내고 받기 위해 페이지 새로고침할 필요 x
```

- 브라우저 캐싱

```
검색어 제안 결과는 자주 바뀌지 않음 -> 브라우저 캐시에 저장
```

- 데이터 샘플링

```
대규모 시스템에서 모든 질의 결과를 로깅 -> 자원, 저장 공간 소진
N개의 요청 중 1개만 로깅
```

### 트라이 연산

**트라이 생성**

작업 서버가 담당

**트라이 갱신**

- 매주 한 번 갱신
- 트라이의 각 노드를 개별적으로 갱신
    - 성능 떨어짐
    - 트라이가 작을 때는 고려 가능

**검색어 삭제**

필터 계층을 두고 부적절한 질의어 반환을 막음

**저장소 규모 확장**

- 첫 글자를 기준으로 샤딩 → 가능한 서버 최대 수 = 26
- 샤드 관리자를 통해 분배
    - s로 시작하는 검색어 양과 u,v,w,x,y,z로 시작하는 검색어 전부 합친 양이 비슷하다면 이에 각각 1개씩 배분

## 추가적인 고려

- 다국어 기능 지원 → 유니코드 데이터 저장
- 국가 별로 인기 검색어 순위가 다른 경우 → 다른 트라이 사용
- 실시간 검색어 추이 반영  → 순위 모델 사용
