# 13장 검색어 자동완성 시스템

## 0. 장의 목표

검색창에 사용자가 단어를 입력하는 중간에, 입력 중인 접두어를 기반으로 가장 많이 사용된 검색어를 자동완성으로 보여주는 시스템을 설계하는 장이다.

예를 들어 사용자가 `tw`를 입력하면 `twitter`, `twitch`, `twilight` 같은 검색어 후보를 인기순으로 보여주는 방식이다.

이 장의 핵심은 단순히 검색어를 저장하는 것이 아니라, **빠르게**, **관련성 있게**, **확장 가능하게**, **고가용성 있게** 자동완성 결과를 제공하는 구조를 만드는 것이다.

---

# 1단계 문제 이해 및 설계 범위 확정

## 설계 범위 확인

면접에서는 먼저 요구사항을 명확히 해야 한다. 이 장에서는 다음과 같은 조건을 기준으로 설계를 진행한다.

| 질문 | 결정 |
| --- | --- |
| 자동완성 기준 | 사용자가 입력한 단어의 첫 부분, 즉 접두어 prefix 기준 |
| 출력 개수 | 상위 5개 검색어 |
| 정렬 기준 | 검색 빈도 기반의 인기순 |
| 맞춤법 교정 | 지원하지 않음 |
| 언어 | 우선 영어만 지원 |
| 대소문자 | 모두 소문자로 처리 |
| 사용자 규모 | DAU 1천만 명 |

## 요구사항

### 빠른 응답 속도

사용자가 검색어를 입력할 때마다 자동완성 결과가 바로 보여야 한다. 따라서 응답 속도는 매우 중요하다.

목표 응답 시간은 대략 100ms 이내이다.

### 연관성

자동완성 결과는 사용자가 입력한 접두어와 관련 있어야 한다.

예를 들어 사용자가 `din`을 입력했다면 `dinner`, `dinner ideas`, `dinner recipes`처럼 접두어와 맞는 검색어가 나와야 한다.

### 정렬

결과는 단순히 사전순으로 나열되는 것이 아니라, 검색 빈도나 인기도를 기준으로 정렬되어야 한다.

### 규모 확장성

검색 요청은 매우 많을 수 있다. 따라서 시스템은 높은 트래픽을 처리할 수 있도록 확장 가능해야 한다.

### 고가용성

일부 서버가 장애를 겪거나 네트워크 문제가 생겨도 자동완성 기능은 계속 동작해야 한다.

## 개략적 규모 추정

이 장에서는 다음과 같이 규모를 가정한다.

- DAU: 1천만 명
- 사용자 1명당 하루 평균 검색 횟수: 10회
- 검색어 평균 길이: 20바이트
- 검색어 하나를 입력할 때 평균 20번의 자동완성 요청 발생
- 평균 QPS: 약 24,000
- 최대 QPS: 약 48,000
- 신규 검색어 데이터: 하루 약 0.4GB

핵심은 검색어 데이터 자체보다 **요청 수가 매우 많다**는 점이다. 따라서 읽기 성능과 캐시 전략이 중요하다.

# 2단계 개략적 설계안 제시 및 동의 구하기

검색어 자동완성 시스템은 크게 두 부분으로 나눌 수 있다.

## 데이터 수집 서비스

사용자가 입력한 검색어를 수집하고, 검색어별 사용 빈도를 기록하는 서비스이다.

초기 설계에서는 사용자가 검색할 때마다 빈도 테이블을 바로 갱신한다고 가정한다.

예를 들어 사용자가 순서대로 `twitch`, `twitter`, `twitter`, `twillo`를 검색하면 빈도 테이블은 다음과 같이 변한다.

| query | frequency |
| --- | --- |
| twitch | 1 |
| twitter | 2 |
| twillo | 1 |

이 방식은 이해하기 쉽지만, 실제 대규모 서비스에서는 매번 실시간으로 빈도를 갱신하는 것이 비효율적이다. 이 문제는 상세 설계에서 개선한다.

## 질의 서비스

사용자가 입력한 접두어에 대해 상위 5개의 인기 검색어를 반환하는 서비스이다.

초기 설계에서는 관계형 데이터베이스에 다음과 같은 쿼리를 날릴 수 있다.

```
SELECT*FROM frequency_tableWHERE queryLIKE'prefix%'ORDERBY frequencyDESCLIMIT5;
```

데이터가 적을 때는 괜찮지만, 데이터가 많아지면 이 방식은 매우 느려진다. 따라서 이후 상세 설계에서는 트라이 자료구조를 사용한다.

- 트라이 자료구조
- 데이터 수집 서비스
- 질의 서비스

## 3.1 트라이 자료구조

## 트라이가 필요한 이유

관계형 데이터베이스에서 `LIKE 'prefix%'` 방식으로 매번 검색하면 데이터가 많아질수록 성능이 급격히 나빠진다.

자동완성은 접두어 기반 검색이므로, 접두어 검색에 특화된 자료구조인 **트라이 trie**를 사용하는 것이 적절하다.

트라이는 문자열을 문자 단위로 나누어 트리 형태로 저장하는 자료구조이다.

## 트라이의 기본 구조

트라이의 특징은 다음과 같다.

- 루트 노드는 빈 문자열을 의미한다.
- 각 노드는 하나의 문자를 저장한다.
- 각 노드는 여러 자식 노드를 가질 수 있다.
- 루트에서 특정 노드까지의 경로가 하나의 접두어를 의미한다.
- 검색어가 끝나는 노드에는 검색어 빈도 정보를 저장한다.

예를 들어 `tree`, `try`, `true`, `toy`, `wish`, `win` 같은 검색어를 트라이에 저장할 수 있다.

각 검색어에는 사용 빈도도 함께 저장된다.

| query | frequency |
| --- | --- |
| tree | 10 |
| try | 29 |
| true | 35 |
| toy | 14 |
| wish | 25 |
| win | 50 |

## 기본 검색 알고리즘

사용자가 접두어 `be`를 입력했다고 하자.

기본적인 트라이 검색 과정은 다음과 같다.

1. 접두어 `be`에 해당하는 노드를 찾는다.
2. 해당 노드 아래의 모든 하위 노드를 탐색한다.
3. 완성된 검색어 후보를 모두 찾는다.
4. 후보들을 빈도순으로 정렬한다.
5. 상위 k개를 반환한다.

## 시간 복잡도

기본 알고리즘의 시간 복잡도는 다음과 같다.

- 접두어 노드 탐색: `O(p)`
- 하위 트리 탐색: `O(c)`
- 후보 정렬: `O(c log c)`

따라서 전체 시간 복잡도는 다음과 같다.

```
O(p) + O(c) + O(c log c)
```

여기서 각 기호의 의미는 다음과 같다.

| 기호 | 의미 |
| --- | --- |
| p | 접두어의 길이 |
| c | 해당 접두어 아래에 있는 후보 노드 수 |
| k | 반환할 자동완성 결과 개수 |

이 방식은 직관적이지만, 최악의 경우 하위 트리를 거의 전부 탐색해야 한다. 따라서 최적화가 필요하다.

---

## 3.2 트라이 최적화

## 접두어 최대 길이 제한

사용자가 검색창에 아주 긴 문자열을 입력하는 경우는 드물다. 따라서 접두어 길이에 제한을 둘 수 있다.

접두어 최대 길이를 작은 상수로 제한하면 접두어 노드를 찾는 비용은 사실상 `O(1)`에 가까워진다.

## 각 노드에 인기 검색어 캐시

각 트라이 노드에 해당 접두어 기준으로 가장 인기 있는 검색어 k개를 미리 저장해 둘 수 있다.

예를 들어 `be` 노드에는 다음과 같은 식으로 상위 검색어를 저장한다.

```
be → [best, bet, bee, beer, ...]
```

이렇게 하면 사용자가 `be`를 입력했을 때 하위 트리를 다시 탐색하지 않아도 된다.

즉, 질의 시에는 다음만 수행하면 된다.

1. 접두어 노드 찾기
2. 해당 노드에 캐시된 top k 결과 반환

이 최적화를 적용하면 질의 시간 복잡도는 거의 `O(1)`이 된다.

다만 단점도 있다.

- 각 노드마다 top k 결과를 저장해야 하므로 저장 공간이 증가한다.
- 검색어 빈도가 바뀌면 해당 노드뿐 아니라 상위 노드들의 캐시도 갱신해야 한다.
- 실시간 갱신에는 부담이 크다.

따라서 이 구조는 **읽기 요청이 압도적으로 많고, 인기 검색어가 자주 바뀌지 않는 서비스**에 적합하다.

# 3.3 데이터 수집 서비스

## 초기 설계의 문제점

처음에는 사용자가 검색어를 입력할 때마다 실시간으로 빈도 테이블과 트라이를 갱신한다고 가정했다.

하지만 실제 서비스에서는 이 방식이 좋지 않다.

이유는 다음과 같다.

- 검색 요청이 매우 많아 실시간 갱신 비용이 크다.
- 트라이를 자주 갱신하면 시스템 부하가 커진다.
- 인기 검색어는 보통 초 단위로 급격하게 바뀌지 않는다.
- 자동완성 결과는 약간 늦게 반영되어도 대부분 문제가 없다.

따라서 실시간 갱신보다는 로그를 모은 뒤 주기적으로 집계하는 방식이 더 적합하다.

## 개선된 데이터 수집 구조

데이터 수집 서비스는 다음 흐름으로 구성된다.

```
데이터 분석 서비스 로그
→ 로그 취합 서버
→ 취합된 데이터
→ 작업 서버
→ 트라이 데이터베이스
→ 트라이 캐시
```

## 데이터 분석 서비스 로그

사용자가 입력한 검색어와 시간을 로그로 저장한다.

예시는 다음과 같다.

| query | time |
| --- | --- |
| tree | 2019-10-01 22:01:01 |
| try | 2019-10-01 22:01:05 |
| tree | 2019-10-01 22:01:30 |
| toy | 2019-10-01 22:02:22 |

이 로그는 원본 데이터이며, 바로 검색용으로 사용하지 않는다.

## 로그 취합 서버

로그 데이터를 일정 주기로 집계한다.

예를 들어 주 단위로 검색어별 빈도를 합산한다.

| query | time | frequency |
| --- | --- | --- |
| tree | 2019-10-01 | 12000 |
| tree | 2019-10-08 | 15000 |
| toy | 2019-10-01 | 8500 |
| toy | 2019-10-08 | 6256 |

실시간성이 중요한 서비스라면 취합 주기를 짧게 가져갈 수 있다. 하지만 일반적인 검색어 자동완성에서는 일주일 단위 집계도 충분할 수 있다.

## 작업 서버

작업 서버는 비동기적으로 동작하는 서버이다.

주기적으로 취합된 데이터를 읽고, 새로운 트라이를 생성한 뒤 트라이 데이터베이스에 저장한다.

## 트라이 캐시

트라이 캐시는 메모리 기반 분산 캐시이다.

API 서버는 사용자의 자동완성 요청을 처리할 때 먼저 트라이 캐시에서 결과를 가져온다.

트라이 캐시는 주기적으로 트라이 데이터베이스의 스냅샷을 가져와 갱신된다.

## 트라이 데이터베이스

트라이 데이터베이스는 트라이를 영구 저장하는 저장소이다.

사용 가능한 방식은 크게 두 가지이다.

### 문서 저장소

트라이 전체를 직렬화해서 문서 형태로 저장하는 방식이다.

트라이를 자주 갱신하지 않는다면 문서 저장소를 사용할 수 있다.

### 키-값 저장소

트라이를 해시 테이블 형태로 바꾸어 저장하는 방식이다.

예를 들어 각 트라이 노드나 접두어를 key로 두고, 해당 노드의 데이터와 top k 결과를 value로 저장할 수 있다.

대규모 시스템에서는 키-값 저장소가 더 적합할 수 있다.

# 3.4 질의 서비스

## 질의 서비스 구조

질의 서비스는 사용자가 입력한 접두어를 받아 자동완성 결과를 반환한다.

전체 흐름은 다음과 같다.

```
사용자 단말
→ 로드밸런서
→ API 서버
→ 트라이 캐시
→ 트라이 데이터베이스
```

## 요청 처리 과정

1. 사용자가 검색어를 입력한다.
2. 요청이 로드밸런서로 전달된다.
3. 로드밸런서는 요청을 API 서버로 보낸다.
4. API 서버는 트라이 캐시에서 자동완성 결과를 조회한다.
5. 캐시에 데이터가 있으면 바로 응답한다.
6. 캐시에 없으면 트라이 데이터베이스에서 가져온 뒤 캐시에 채운다.

핵심은 대부분의 요청을 트라이 캐시에서 처리하는 것이다.

검색어 자동완성은 읽기 요청이 매우 많기 때문에 캐시가 성능의 핵심이다.

## 질의 서비스 최적화

### AJAX 요청

웹 애플리케이션에서는 사용자가 검색어를 입력할 때마다 AJAX 요청을 보내 자동완성 결과를 가져올 수 있다.

페이지 전체를 새로고침하지 않아도 되므로 사용자 경험이 좋아진다.

### 브라우저 캐싱

자동완성 결과는 짧은 시간 동안 크게 바뀌지 않는 경우가 많다.

따라서 브라우저 캐싱을 사용하면 같은 접두어 요청에 대해 서버 요청을 줄일 수 있다.

예를 들어 `cache-control` 헤더를 사용해 일정 시간 동안 브라우저에 결과를 저장할 수 있다.

### 데이터 샘플링

대규모 서비스에서는 모든 검색 요청을 로그로 남기면 저장 공간과 처리 비용이 매우 커진다.

따라서 모든 요청을 기록하지 않고, N개 요청 중 일부만 기록하는 샘플링 방식을 사용할 수 있다.

# 3.5 트라이 연산

## 트라이 생성

트라이 생성은 작업 서버가 담당한다.

작업 서버는 로그 취합 결과를 바탕으로 트라이를 만들고, 트라이 데이터베이스에 저장한다.

## 트라이 갱신

트라이 갱신 방식은 크게 두 가지이다.

### 전체 트라이 주기적 재생성

새로운 트라이를 만든 뒤 기존 트라이를 대체하는 방식이다.

검색어 인기도가 자주 바뀌지 않는다면 이 방식이 단순하고 안정적이다.

이 장에서는 매주 한 번 정도 트라이를 갱신하는 방식을 사용한다.

### 개별 노드 갱신

트라이의 각 노드를 개별적으로 갱신하는 방식이다.

하지만 각 노드에 top k 검색어를 캐시해 둔 경우, 어떤 검색어의 빈도가 바뀌면 해당 노드뿐 아니라 상위 노드들도 함께 갱신해야 한다.

따라서 구현이 복잡하고 비용이 커질 수 있다.

## 검색어 삭제

부적절한 검색어는 자동완성 결과에서 제거해야 한다.

예를 들어 혐오 표현, 폭력적 표현, 성적으로 노골적인 검색어 등이 해당한다.

이를 위해 트라이 캐시 앞에 필터 계층을 둘 수 있다.

```
API 서버
→ 필터 계층
→ 트라이 캐시
```

필터 계층은 부적절한 검색어를 결과에서 제외한다.

트라이 데이터 자체에서 해당 검색어를 삭제하는 작업은 다음 갱신 주기에 비동기적으로 수행할 수 있다.

# 3.6 저장소 규모 확장

## 샤딩 필요성

트라이 데이터가 한 서버에 담기 어려울 정도로 커지면 여러 서버에 나누어 저장해야 한다.

이때 샤딩을 사용한다.

## 단순한 첫 글자 기준 샤딩

가장 단순한 방법은 검색어의 첫 글자를 기준으로 나누는 것이다.

예를 들어 서버가 두 대라면 다음과 같이 나눌 수 있다.

```
a ~ m → 첫 번째 서버
n ~ z → 두 번째 서버
```

서버가 세 대라면 다음과 같이 나눌 수 있다.

```
a ~ i → 첫 번째 서버
j ~ r → 두 번째 서버
s ~ z → 세 번째 서버
```

하지만 이 방식에는 한계가 있다.

영어 알파벳은 26개뿐이므로 단순 첫 글자 기준으로는 서버 수를 26개 이상 늘리기 어렵다.

## 다단계 샤딩

서버 수를 더 늘리려면 첫 글자뿐 아니라 두 번째 글자까지 고려할 수 있다.

예를 들어 `a`로 시작하는 검색어가 많다면 다음처럼 나눌 수 있다.

```
aa ~ ag → 한 서버
ah ~ an → 다른 서버
ao ~ au → 또 다른 서버
```

## 단순 샤딩의 문제

검색어는 균등하게 분포하지 않는다.

예를 들어 `c`로 시작하는 검색어가 `x`로 시작하는 검색어보다 훨씬 많을 수 있다.

따라서 단순히 알파벳 범위로 나누면 특정 서버에만 부하가 몰릴 수 있다.

## 샤드 관리자

이 문제를 해결하기 위해 샤드 관리자 shard map manager를 둘 수 있다.

샤드 관리자는 과거 검색어 패턴을 분석해서 특정 접두어가 어느 서버에 저장되어야 하는지 관리한다.

예를 들어 `s` 관련 검색어가 너무 많다면 `s`만 별도 샤드로 분리하고, `u ~ z`는 하나의 샤드에 묶을 수 있다.

핵심은 데이터를 균등하게 나누는 것이다.

# 4단계 마무리

## 다국어 지원

영어 이외의 언어를 지원하려면 유니코드를 사용해야 한다.

유니코드는 다양한 문자 체계를 표현할 수 있는 표준 인코딩 방식이다.

## 국가별 인기 검색어 차이

국가마다 인기 검색어가 다를 수 있다.

따라서 국가별로 다른 트라이를 사용할 수 있다.

또한 트라이를 CDN에 저장하면 사용자의 위치와 가까운 곳에서 데이터를 제공할 수 있어 응답 속도를 줄일 수 있다.

## 실시간 검색어 추세 반영

현재 설계는 주기적으로 트라이를 갱신하는 방식이다.

따라서 갑자기 인기가 높아진 검색어를 즉시 반영하기는 어렵다.

실시간성을 강화하려면 다음과 같은 방법을 고려할 수 있다.

- 작업 대상 데이터를 샤딩해서 처리량을 줄임
- 최근 검색어에 더 높은 가중치를 주는 랭킹 모델 사용
- 스트리밍 데이터 처리 시스템 사용
- Kafka, Spark Streaming, Storm 같은 시스템 활용

## 최종 정리

이 장의 검색어 자동완성 시스템은 다음 흐름으로 정리할 수 있다.

```
사용자 검색 로그 수집
→ 로그 취합
→ 검색어 빈도 계산
→ 트라이 생성
→ 트라이 데이터베이스 저장
→ 트라이 캐시에 적재
→ 사용자의 접두어 요청 처리
→ top 5 자동완성 결과 반환
```

핵심 설계 포인트는 다음과 같다.

- 접두어 검색에는 트라이가 적합함
- 각 노드에 top k 검색어를 캐시하면 질의 속도를 크게 줄일 수 있음
- 검색어 빈도는 실시간 갱신보다 로그 기반 주기적 취합이 적합함
- 읽기 요청이 많으므로 트라이 캐시가 중요함
- 부적절한 검색어 제거를 위해 필터 계층이 필요함
- 대규모 데이터 처리를 위해 샤딩과 샤드 관리자가 필요함
- 다국어, 국가별 검색어, 실시간 트렌드 반영은 추가 확장 포인트임

# 핵심 키워드 정리

| 키워드 | 의미 |
| --- | --- |
| 자동완성 autocomplete | 사용자가 입력 중인 검색어를 바탕으로 후보 검색어를 보여주는 기능 |
| 접두어 prefix | 문자열의 앞부분 |
| 트라이 trie | 접두어 검색에 적합한 트리 기반 자료구조 |
| top k | 가장 인기 있는 k개의 결과 |
| QPS | 초당 처리해야 하는 요청 수 |
| 캐시 cache | 자주 쓰는 데이터를 빠르게 반환하기 위해 임시 저장하는 공간 |
| 로그 취합 aggregation | 원본 로그를 모아 의미 있는 통계 데이터로 만드는 과정 |
| 샤딩 sharding | 데이터를 여러 서버에 나누어 저장하는 방식 |
| 샤드 관리자 shard map manager | 어떤 데이터가 어느 샤드에 저장되는지 관리하는 컴포넌트 |
| CDN | 사용자와 가까운 위치에서 데이터를 제공해 응답 속도를 줄이는 네트워크 |
| 스트리밍 처리 | 실시간으로 들어오는 데이터를 계속 처리하는 방식 |
