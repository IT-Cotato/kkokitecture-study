# Dynamo: Amazon's Highly Available Key-value Store

> SOSP 2007 | Giuseppe DeCandia et al. | Amazon.com
>

---

## 1. 왜 Dynamo를 만들었나?

### 문제: RDBMS는 Amazon 규모에서 한계가 있었다

Amazon의 플랫폼은 수백 개의 마이크로서비스로 구성되어 있다.

이 서비스들 대부분은 사실 **단순한 key로 데이터를 읽고 쓰는 것**이 전부였다.

> 베스트셀러 목록, 장바구니, 고객 설정, 세션 관리, 판매 순위, 상품 카탈로그 …
>

RDBMS는 이런 서비스에 **과분하고**, 비싸고, 확장하기 어려웠다.

게다가 기존 복제 기술들은 **일관성 > 가용성** 순으로 우선순위를 뒀다.

### 핵심 요구사항

- 하나의 페이지 렌더링이 **150개 이상의 서비스**를 호출한다
- 각 서비스는 **엄격한 SLA (지연시간 계약)** 를 지켜야 한다
- Amazon은 SLA를 평균/중앙값이 아닌 **99.9 퍼센타일** 기준으로 측정한다

> 💡 **왜 99.9%인가?**
>
>
> 99.99%로 높이면 비용이 기하급수적으로 증가한다는 비용-편익 분석 결과.
>
> 상위 0.1% 고객(구매 이력이 많은 VIP)도 좋은 경험을 해야 하기 때문.
>

## 2. 핵심 설계 철학

### "Always Writeable" — 쓰기는 절대 실패하지 않는다

**전통적인 시스템**: 충돌을 **쓰기 시점**에 해소 → 불확실하면 쓰기를 거부

**Dynamo**: 충돌을 **읽기 시점**에 해소 → 쓰기는 항상 받아들인다

### 왜 이 결정을 했나? — 장바구니 예시

```
상황: 사용자가 장바구니에 물건을 담으려는데 서버 일부가 다운됨

전통 방식: "지금 저장 불가" → 쓰기 거부 → 고객 불만 → 매출 손실
Dynamo:   오래된 버전에 일단 저장 → 나중에 버전 합치기 → 고객 경험 유지
```

> "Add to Cart 동작은 절대 잊혀지거나 거부되어서는 안 된다"
>
>
> — Dynamo 논문 Section 2.3
>

삭제한 아이템이 다시 나타날 수 있다는 부작용이 있지만,

**장바구니가 아예 동작 안 하는 것보다 훨씬 낫다**는 비즈니스 판단.

### 충돌 해소: 누가 할 것인가?

| 주체 | 방식 | 한계 |
| --- | --- | --- |
| **저장소(DB)** | Last Write Wins (최신 타임스탬프 우선) | 단순하지만 데이터 유실 가능 |
| **애플리케이션** | 비즈니스 로직으로 병합 | 복잡하지만 더 정확함 |

Dynamo는 **두 가지 모두 지원** — 서비스가 선택한다.

장바구니 서비스는 "두 버전을 합친다(merge)"는 방식을 사용.

### 4가지 설계 원칙

| 원칙 | 내용 |
| --- | --- |
| **점진적 확장성** | 노드 1개씩 추가해도 시스템 전체 영향 최소화 |
| **대칭성** | 모든 노드가 동일한 역할, 특별한 마스터 노드 없음 |
| **분산화** | 중앙 집중 제어 배제 → 과거 중앙 제어 방식이 장애를 일으킨 경험 |
| **이기종성** | 서버 성능에 비례해서 부하 분배 (가상 노드로 구현) |

## 3. 시스템 아키텍처

### 기술 스택 요약

| 문제 | 기술 | 효과 |
| --- | --- | --- |
| 데이터 파티션 | Consistent Hashing + 가상 노드 | 점진적 확장 |
| 쓰기 고가용성 | Vector Clock + 읽기 시 충돌 해소 | 버전 크기가 업데이트 속도와 무관 |
| 일시적 장애 | Sloppy Quorum + Hinted Handoff | 일부 노드 다운 시에도 쓰기 보장 |
| 영구 장애 복구 | Anti-entropy + Merkle Tree | 백그라운드에서 사본 동기화 |
| 멤버십/장애 감지 | Gossip Protocol | 중앙 레지스트리 없이 대칭 유지 |

### 인터페이스: put()의 숨겨진 파라미터

책에서는 `put(key, value)`로 단순히 소개하지만, 실제 Dynamo API는:

```
get(key)          → object 또는 충돌 버전 목록 + context 반환
put(key, context, object)  → context에 vector clock 정보 포함
```

`context`가 핵심 — 클라이언트가 어떤 버전을 읽었는지를 시스템에 알려주는 역할.

이 context 없이는 충돌 해소가 불가능하다.

### 가상 노드(Virtual Node)의 실제 동작

기본 Consistent Hashing의 문제:

- 노드를 랜덤 배치하면 **데이터 분포가 불균등**해진다
- 서버 성능 차이를 반영하지 못한다

Dynamo의 해결책: **각 노드를 링 위의 여러 위치에 배치**

- 성능 좋은 서버 → 더 많은 가상 노드 토큰 보유
- 노드 추가/제거 시 **부하가 전체 노드에 균등하게 분산**

### 읽기/쓰기 코디네이터 선택의 디테일

- 쓰기 코디네이터는 항상 첫 번째 노드가 아니라 **직전 읽기에서 가장 빨리 응답한 노드**가 담당
- 이유: "read-your-writes" 일관성 확보 + 99.9 퍼센타일 지연시간 최적화

## 4. Vector Clock 동작 예시

```
① 클라이언트가 새 데이터 저장 → Sx가 처리
   D1([Sx, 1])

② 같은 클라이언트가 업데이트 → Sx가 처리
   D2([Sx, 2])    ← D1을 덮어씀

③ 다른 클라이언트가 D2를 기반으로 업데이트 → Sy가 처리
   D3([Sx, 2], [Sy, 1])

④ 또 다른 클라이언트가 D2를 기반으로 업데이트 → Sz가 처리
   D4([Sx, 2], [Sz, 1])

⑤ 이제 D3와 D4는 충돌! (공통 조상 D2에서 갈라진 두 버전)
   → 클라이언트가 두 버전을 모두 받아서 merge 후 저장
   D5([Sx, 3], [Sy, 1], [Sz, 1])
```

### Vector Clock의 실제 한계와 Dynamo의 해결책

**문제**: 서버가 많아질수록 Vector Clock 크기가 계속 늘어남

**해결**: 임계치(threshold) 도달 시 **가장 오래된 (node, counter) 쌍을 삭제**

논문 고백: *"이 방식이 버전 선후 관계 정확도를 떨어뜨릴 수 있지만, 실제 프로덕션에서 문제가 된 적은 없었다."*

## 5. 실제 운영 경험

### Dynamo의 3가지 사용 패턴

| 패턴 | 방식 | 사용 서비스 예시 |
| --- | --- | --- |
| **비즈니스 로직 기반 충돌 해소** | 애플리케이션이 직접 merge | 장바구니 서비스 |
| **타임스탬프 기반 충돌 해소** | Last Write Wins | 세션 관리 등 |
| **고성능 읽기 엔진** | W=1로 설정, 단일 노드 응답 | 베스트셀러 목록 등 |

### N, W, R 실제 운영 값

> 논문에서 직접 공개한 프로덕션 설정값
>
- 대부분의 Amazon 서비스: **N=3, W=2, R=2**
- W+R > N이므로 **강한 일관성** 보장
- 응답 지연은 R 또는 W개 중 **가장 느린 노드**에 의해 결정

**극단적 설정의 트레이드오프:**

```
W=1, R=1  → 가장 빠름, 하지만 일관성 최저
W=1, R=N  → 쓰기 초고속, 읽기 느림 (읽기 최적화)
W=N, R=1  → 읽기 초고속, 쓰기 느림 (쓰기 최적화)
W=2, R=2 (N=3) → Amazon의 실제 선택 ← 균형점
```

### 실제 성능 수치 (논문 공개 데이터)

- 쇼핑카트 서비스: **하루 3백만 건 이상의 결제** 처리
- 세션 관리 서비스: **수십만 건의 동시 세션** 처리
- 피크 타임(연말 쇼핑 시즌)에도 **다운타임 0**

### Read Repair — 책에서 설명 안 된 최적화

읽기 응답 후 코디네이터가 오래된 버전을 가진 노드를 발견하면,

**즉시 해당 노드에 최신 버전을 업데이트** → Anti-entropy 부담 감소

## 6. 책(6장)과 논문의 차이점 정리

| 항목 | 책 (6장) | Dynamo 논문 |
| --- | --- | --- |
| AP 선택 이유 | CAP 정리로 설명 | **장바구니 비즈니스 로직**으로 설명 |
| SLA 기준 | 언급 없음 | **99.9 퍼센타일** 기준 명시 |
| put() API | `put(key, value)` | `put(key, context, object)` — context가 핵심 |
| 충돌 해소 주체 | 간략히 언급 | 애플리케이션 vs 저장소 선택 가능 |
| W,R,N 실제 값 | 개념만 설명 | **N=3, W=2, R=2** 프로덕션 값 공개 |
| 가상 노드 | 개념만 | 성능에 비례한 **토큰 수 조정** 설명 |
| Read Repair | 없음 | 읽기 후 오래된 노드 자동 업데이트 |

## 7. 결론: Dynamo가 남긴 유산

Dynamo 이후 등장한 시스템들:

- **Cassandra** (Facebook, 2008): Dynamo의 파티셔닝 + BigTable의 데이터 모델
- **Riak**: Dynamo 논문을 거의 그대로 구현한 오픈소스
- **DynamoDB** (AWS, 2012): Dynamo 개념의 상용 서비스화

> 💡 핵심 교훈
>
>
> "완벽한 일관성을 추구하다 서비스가 멈추는 것보다,
>
> 약간의 불일관성을 허용하면서 항상 응답하는 것이 더 낫다."
>
> — 이것이 현대 NoSQL 혁명의 시작점
