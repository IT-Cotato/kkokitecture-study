# 6장. 키-값 저장소 설계

## 개요

- **키-값 저장소(key-value store)** = 키-값 데이터베이스 (비 관계형)
- 키는 고유 식별자, 값은 키를 통해서만 접근 가능
- 키는 짧을수록 좋음 (일반 텍스트 or 해시 값)
- 값은 문자열, 리스트, 객체 등 무엇이든 가능

### 지원 연산

- `put(key, value)` : 키-값 쌍 저장
- `get(key)` : 키에 매달린 값 반환

### 설계 범위 (이번 장 기준)

- 키-값 쌍 크기 ≤ 10KB
- 큰 데이터 저장 가능
- 높은 가용성 (장애 시에도 빠른 응답)
- 높은 규모 확장성 (트래픽에 따라 자동 서버 증설/삭제)
- 데이터 일관성 수준 조정 가능
- 짧은 응답 지연(latency)

---

## 단일 서버 키-값 저장소

- 키-값 쌍을 메모리 해시 테이블에 저장 → 빠르지만 모든 데이터를 메모리에 두기 불가능할 수 있음
- 개선책: **데이터 압축(compression)**, **자주 쓰이는 데이터만 메모리, 나머지는 디스크**
- 한 서버로는 결국 부족 → **분산 키-값 저장소** 필요

---

## 분산 키-값 저장소

### CAP 정리

세 가지 요구사항을 **동시에 만족하는 분산 시스템은 불가능**

| 속성 | 설명 |
| --- | --- |
| **일관성(Consistency)** | 어떤 노드에 접속해도 언제나 같은 데이터를 봄 |
| **가용성(Availability)** | 일부 노드 장애가 있어도 항상 응답 받을 수 있음 |
| **파티션 감내(Partition Tolerance)** | 네트워크 파티션이 생겨도 시스템이 계속 동작 |

### 시스템 분류

- **CP 시스템**: 일관성 + 파티션 감내 (가용성 희생)
- **AP 시스템**: 가용성 + 파티션 감내 (일관성 희생)
- **CA 시스템**: 실세계에서는 존재하지 않음 (파티션 문제는 피할 수 없으므로)

> 💡 분산 키-값 저장소는 CP 또는 AP 중 어느 두 가지를 만족할지 선택해야 함
>

## 시스템 컴포넌트

### 1. 데이터 파티션

대규모 애플리케이션에서는 전체 데이터를 한 서버에 넣는 것이 불가능

→ **안정 해시(Consistent Hash)** 사용

**안정 해시의 장점:**

- **규모 확장 자동화**: 부하에 따라 서버 자동 추가/삭제
- **다양성(Heterogeneity)**: 서버 용량에 맞게 가상 노드 수 조정

**동작 원리:**

1. 서버를 해시 링에 배치
2. 키를 같은 링에 배치 후, 시계 방향으로 순회하여 만나는 첫 서버에 저장

---

### 2. 데이터 다중화(Replication)

- 높은 가용성/안정성을 위해 데이터를 **N개 서버에 비동기적으로 다중화**
- N은 튜닝 가능한 값
- 키를 해시 링에 배치 후, 시계 방향으로 N개의 서버에 사본 보관
- 가상 노드 사용 시, **같은 물리 서버가 중복 선택되지 않도록** 주의
- 안정성을 위해 사본을 **다른 데이터 센터의 서버에 보관**, 센터 간 고속 네트워크로 연결

---

### 3. 데이터 일관성(Consistency)

**정족수 합의(Quorum Consensus)** 프로토콜로 읽기/쓰기 연산 모두 일관성 보장

| 변수 | 의미 |
| --- | --- |
| N | 사본 개수 |
| W | 쓰기 연산의 정족수 (W개 서버로부터 쓰기 성공 응답 받아야 함) |
| R | 읽기 연산의 정족수 (R개 서버로부터 응답 받아야 함) |

**W, R, N 구성:**

- `R=1, W=N` → 빠른 읽기 연산에 최적화
- `W=1, R=N` → 빠른 쓰기 연산에 최적화
- `W+R>N` → **강한 일관성(Strong Consistency)** 보장 (보통 N=3, W=R=2)
- `W+R≤N` → 강한 일관성 보장 안됨

**중재자(Coordinator)**: 클라이언트와 노드 사이의 프락시 역할

---

### 4. 일관성 모델

| 모델 | 설명 |
| --- | --- |
| **강한 일관성** | 모든 읽기 연산이 가장 최근 갱신 결과 반환, 클라이언트는 절대 낡은 데이터를 보지 못함 |
| **약한 일관성** | 읽기 연산이 가장 최근 결과를 반환하지 못할 수 있음 |
| **최종 일관성** | 약한 일관성의 형태, 결과적으로 모든 사본에 반영(동기화)됨 → **다이나모, 카산드라** 채택 |

> 💡 이번 장의 설계는 **최종 일관성 모델** 채택
>

---

### 5. 일관성 불일치 해소: 버저닝(Versioning)

**버저닝**: 데이터를 변경할 때마다 새로운 버전 생성 → 각 버전은 변경 불가(immutable)

**벡터 시계(Vector Clock)**: `D([S1, v1], [S2, v2], ..., [Sn, vn])`

- D: 데이터, vi: 버전 카운터, Si: 서버 번호
- 서버 Si에 데이터 D 기록 시: [Si, vi]가 있으면 vi 증가, 없으면 새 항목 [Si, 1] 추가

**충돌 감지:**

- 버전 X가 버전 Y의 이전 버전 → Y에 포함된 모든 구성요소 값이 X의 해당 구성요소보다 크거나 같음
- 그렇지 않으면 → **충돌 발생**

**단점:**

1. 충돌 감지/해소 로직이 클라이언트에 들어가야 함 → 클라이언트 구현 복잡
2. [서버: 버전] 순서쌍 개수가 빠르게 늘어남 → 임계치 설정하여 오래된 순서쌍 제거 (단, 버전 선후 관계 정확도 저하)

### 6. 장애 처리

### 장애 감지

- 분산 시스템에서는 **두 대 이상의 서버**가 같이 서버 A의 장애를 보고해야 실제 장애로 간주
- **멀티캐스팅 채널** 구축이 가장 쉽지만 서버가 많을 때 비효율
- → **가십 프로토콜(Gossip Protocol)** 채택 (분산형 장애 감지)

**가십 프로토콜 동작:**

- 각 노드는 **멤버십 목록** 유지 (멤버 ID + 박동 카운터)
- 각 노드는 주기적으로 자신의 박동 카운터를 증가시킴
- 무작위로 선정된 노드들에게 주기적으로 박동 카운터 목록을 전송
- 받은 노드는 멤버십 목록을 최신 값으로 갱신
- 어떤 멤버의 박동 카운터가 지정된 시간 동안 갱신 안되면 → **장애(offline) 상태**로 간주

### 일시적 장애 처리

- **엄격한 정족수** 접근법: 읽기/쓰기 연산 금지
- **느슨한 정족수(Sloppy Quorum)**: W개의 건강한 서버, R개의 건강한 서버를 해시 링에서 고름, 장애 상태인 서버는 무시
- **단서 후 임시 위탁(Hinted Handoff)**: 장애 상태인 노드에 대한 요청은 다른 서버가 임시로 처리, 장애 해소 후 갱신 데이터를 전달

### 영구 장애 처리

- **반-엔트로피(Anti-entropy)** 프로토콜로 사본들을 동기화
- **머클 트리(Merkle Tree)** 사용: 동기화해야 하는 데이터 양은 실제 존재하는 차이에 비례

**머클 트리 동기화 과정:**

1. 키 공간을 버킷으로 나눔
2. 각 버킷의 키에 균등 분포 해시 함수 적용 → 해시 값 계산
3. 버킷별 해시값을 레이블로 갖는 노드 생성
4. 자식 노드의 레이블로부터 상향식으로 해시값 계산하여 트리 구성
5. 루트 노드 해시값 비교 → 다르면 자식 노드 비교하며 아래로 탐색 → 다른 데이터를 가진 버킷 찾아 동기화

### 데이터 센터 장애 처리

- 여러 데이터 센터에 데이터를 다중화 → 한 센터가 완전히 망가져도 다른 센터의 데이터 이용 가능

---

### 7. 시스템 아키텍처

**주요 특징:**

- 클라이언트는 `get(key)`, `put(key, value)` API로 통신
- **중재자(Coordinator)**: 클라이언트에게 키-값 저장소의 프락시 역할
- 노드들은 안정 해시의 해시 링 위에 분포
- 완전히 분산화(decentralized): 노드 자동 추가/삭제 가능
- 데이터는 여러 노드에 다중화
- **SPOF(Single Point of Failure) 없음**
- 모든 노드가 동일한 기능 지원 (클라이언트 API, 장애 감지, 데이터 충돌 해소, 다중화, 저장 엔진 등)

---

### 8. 쓰기 경로(Write Path)

(카산드라 사례 참고)

1. 쓰기 요청 → **커밋 로그(Commit Log)** 파일에 기록
2. 데이터 → **메모리 캐시**에 기록
3. 메모리 캐시가 가득 차거나 임계치 도달 시 → **SSTable(디스크)에 기록**
    - SSTable = Sorted-String Table, `(키, 값)` 순서쌍을 정렬된 리스트 형태로 관리

---

### 9. 읽기 경로(Read Path)

1. 데이터가 **메모리 캐시에 있는지** 검사 → 있으면 클라이언트에 반환
2. 없으면 → **블룸 필터(Bloom Filter)**를 통해 어떤 SSTable에 키가 있는지 알아냄
3. SSTable에서 데이터 가져와 클라이언트에 반환
