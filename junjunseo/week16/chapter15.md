# 15장 구글 드라이브 설계

## 개요

구글 드라이브와 같은 클라우드 파일 저장 및 동기화 시스템을 설계한다. 사용자가 파일을 업로드하면 클라우드에 안전하게 저장하고, 여러 단말에서 동일한 파일을 사용할 수 있도록 동기화해야 한다.

이번 장에서 다루는 핵심 내용은 다음과 같다.

- 파일 업로드 및 다운로드
- 여러 단말 사이의 파일 동기화
- 파일 갱신 이력 관리
- 파일 공유 및 변경 알림
- 대용량 파일의 효율적인 전송
- 데이터 안정성과 높은 가용성
- 동기화 충돌 처리
- 저장 공간 절약 및 장애 대응

---

## 1단계 문제 이해 및 설계 범위 확정

### 1.1 기능 요구사항

설계 대상 시스템이 지원해야 하는 주요 기능은 다음과 같다.

- 파일 추가
    - 드래그 앤 드롭 방식으로 파일을 업로드할 수 있어야 한다.
- 파일 다운로드
- 여러 단말 사이의 파일 동기화
    - 한 단말에서 파일을 추가하거나 수정하면 다른 단말에도 자동으로 반영되어야 한다.
- 파일 갱신 이력 관리
    - 이전 버전의 파일을 조회하거나 복원할 수 있어야 한다.
- 파일 공유
- 파일 변경 알림
    - 파일이 편집, 삭제, 추가 또는 공유되었을 때 관련 사용자에게 알려야 한다.
- 웹과 모바일 환경 모두 지원
- 파일 암호화
- 최대 10GB 크기의 파일 지원

구글 문서처럼 여러 사용자가 하나의 문서를 동시에 편집하는 협업 기능은 이번 설계 범위에서 제외한다.

---

### 1.2 비기능 요구사항

#### 안정성

저장소 시스템에서 가장 중요한 요구사항이다. 사용자의 파일이 손실되어서는 안 된다.

#### 빠른 동기화

동기화 시간이 지나치게 길어지면 사용자는 서비스를 불편하게 느끼고 사용을 중단할 수 있다.

#### 네트워크 대역폭 효율성

파일 전체를 반복적으로 전송하면 네트워크 대역폭을 과도하게 사용한다. 특히 모바일 데이터 환경에서는 더욱 중요한 문제이다.

#### 규모 확장성

서비스 이용자가 증가하고 저장되는 데이터가 늘어나더라도 시스템을 쉽게 확장할 수 있어야 한다.

#### 높은 가용성

일부 서버가 중단되거나 네트워크 일부에 장애가 발생하더라도 서비스가 계속 동작해야 한다.

---

### 1.3 개략적 규모 추정

다음 조건을 기준으로 시스템 규모를 추정한다.

- 전체 가입자 수: 5천만 명
- 일간 활성 사용자 수: 1천만 명
- 사용자당 무료 저장 공간: 10GB
- 사용자당 하루 평균 업로드 수: 2개
- 파일 한 개의 평균 크기: 500KB
- 읽기와 쓰기 비율: 1:1

#### 전체 저장 공간

```
5천만 명 × 10GB = 500PB
```

따라서 약 500페타바이트의 저장 공간이 필요하다.

#### 업로드 API QPS

```
1천만 명 × 하루 2회 업로드 ÷ 86,400초 ≈ 240 QPS
```

최대 QPS를 평균 QPS의 2배로 가정하면 다음과 같다.

```
최대 QPS ≈ 480
```

## 2단계 개략적 설계안 제시 및 동의 구하기

## 2.1 단일 서버에서 시작

초기에는 다음 기능을 하나의 서버에서 처리하는 단순한 구조로 시작할 수 있다.

- 파일 업로드 및 다운로드를 처리하는 웹 서버
- 사용자와 파일의 메타데이터를 저장하는 데이터베이스
- 실제 파일을 보관하는 파일 저장소

파일 저장소의 전체 용량은 1TB라고 가정한다.

### 파일 디렉터리 구조

서버의 `drive/` 디렉터리 아래에 사용자별 네임스페이스를 만든다.

```
drive/
├── user1/
│   ├── recipes/
│   └── chicken_soup.txt
├── user2/
│   ├── football.mov
│   └── sports.txt
└── user3/
    └── best_pic_ever.png
```

각 사용자는 고유한 네임스페이스를 가진다. 파일의 전체 경로와 사용자 네임스페이스를 결합하면 파일을 유일하게 식별할 수 있다.

## 2.2 API 설계

시스템에는 기본적으로 다음 세 종류의 API가 필요하다.

- 파일 업로드 API
- 파일 다운로드 API
- 파일 갱신 이력 조회 API

모든 API에는 사용자 인증이 필요하며, 클라이언트와 서버 사이에서 전송되는 데이터를 보호하기 위해 HTTPS를 사용해야 한다.

---

### 파일 업로드 API

파일 업로드는 두 종류로 나눌 수 있다.

#### 단순 업로드

파일 크기가 작고 한 번의 요청으로 업로드할 수 있을 때 사용한다.

#### 이어 올리기 업로드

파일 크기가 크거나 네트워크 연결이 불안정할 때 사용한다. 업로드 도중 장애가 발생하면 처음부터 다시 올리지 않고 중단된 지점부터 재개할 수 있다.

```
https://api.example.com/files/upload?uploadType=resumable
```

요청 데이터에는 업로드할 로컬 파일이 포함된다.

이어 올리기는 다음 과정으로 진행된다.

1. 이어 올리기 URL을 받기 위한 최초 요청 전송
2. 파일 데이터 업로드 및 업로드 상태 확인
3. 장애가 발생하면 중단된 위치부터 업로드 재시작

---

### 파일 다운로드 API

다운로드할 파일의 경로를 전달한다.

```
https://api.example.com/files/download
```

```
{
  "path":"/recipes/soup/best_soup.txt"
}
```

---

### 파일 갱신 이력 API

파일의 이전 버전 목록을 조회한다.

```
https://api.example.com/files/list_revisions
```

```
{
  "path":"/recipes/soup/best_soup.txt",
  "limit":20
}
```

- `path`: 갱신 이력을 조회할 파일 경로
- `limit`: 반환할 이력의 최대 개수

## 2.3 단일 서버의 한계 극복

파일이 지속적으로 추가되면 단일 서버의 파일 저장 공간이 부족해진다.

### 샤딩

사용자 ID를 기준으로 파일을 여러 서버에 분산할 수 있다.

```
server = user_id % 서버 개수
```

그러나 단순 샤딩만으로는 특정 서버 장애에 따른 데이터 손실 문제를 해결하기 어렵다.

---

### 클라우드 저장소 도입

실제 파일은 Amazon S3와 같은 객체 저장소에 저장한다.

S3는 다음 특성을 제공한다.

- 높은 규모 확장성
- 높은 가용성
- 데이터 다중화
- 여러 리전에 걸친 데이터 복제
- 높은 내구성과 보안성

S3의 버킷은 기존 파일 시스템의 폴더와 유사한 논리적 저장 단위이다.

같은 리전 안에 데이터를 복제하거나 여러 리전에 걸쳐 복제할 수 있다. 여러 리전에 데이터를 분산하면 한 지역에 장애가 발생하더라도 다른 지역에서 데이터를 제공할 수 있다.

---

### 로드밸런서

클라이언트의 요청을 여러 API 서버에 고르게 분산한다.

특정 서버에 장애가 발생하면 해당 서버를 요청 대상에서 제외하고 정상 서버로 트래픽을 전달한다. API 서버를 추가하는 것만으로 처리량을 비교적 쉽게 확장할 수 있다.

---

### API 서버

파일 업로드를 제외한 대부분의 요청을 처리한다.

- 사용자 인증
- 사용자 프로필 관리
- 파일 메타데이터 관리
- 파일 공유
- 파일 버전 조회

API 서버는 무상태 서버로 설계하여 어느 서버에서도 같은 요청을 처리할 수 있도록 한다.

---

### 메타데이터 데이터베이스 분리

사용자 정보와 파일 정보를 파일 저장소에서 분리한다.

이를 통해 다음 효과를 얻을 수 있다.

- 파일 저장 서버 장애와 메타데이터 장애의 분리
- 단일 장애 지점 완화
- 데이터베이스 다중화 가능
- 읽기와 쓰기 작업의 독립적인 확장

---

### 개선된 개략적 구조

```
사용자 단말
    │
로드밸런서
    │
API 서버
 ├── 메타데이터 데이터베이스
 ├── 메타데이터 캐시
 ├── 파일 저장소
 ├── 알림 서비스
 └── 오프라인 사용자 백업 큐

블록 저장소 서버
    │
클라우드 저장소
    │
아카이빙 저장소
```

## 2.4 동기화 충돌

두 명 이상의 사용자 또는 두 개 이상의 단말이 같은 파일을 동시에 수정할 수 있다.

먼저 서버에 도착한 수정 요청은 정상적으로 반영된다. 이후 도착한 요청은 최신 버전과 충돌한 것으로 판단한다.

충돌이 발생하면 다음 두 버전을 모두 유지한다.

- 서버에 저장된 최신 버전
- 사용자가 수정한 로컬 버전

사용자는 두 버전을 직접 병합하거나, 로컬 버전을 별도의 파일로 저장할 수 있다.

```
SystemDesignInterview
SystemDesignInterview_user2_conflicted_copy
```

여러 사용자가 하나의 문서를 동시에 편집할 때 발생하는 문제는 차등 동기화와 같은 기술을 통해 해결할 수 있다. 다만 실시간 공동 편집 기능은 이번 설계 범위에 포함하지 않는다.

## 2.5 개략적 설계의 주요 컴포넌트

### 사용자 단말

웹 브라우저나 모바일 앱 등 사용자가 파일을 사용하는 클라이언트이다.

### 블록 저장소 서버

파일을 작은 블록으로 나누고 다음 작업을 수행한다.

- 파일 분할
- 블록 압축
- 블록 암호화
- 변경된 블록만 클라우드 저장소에 업로드

파일을 다시 구성할 때는 블록을 기존 순서대로 조합한다.

### 클라우드 저장소

파일 블록이 실제로 저장되는 공간이다.

### 아카이빙 저장소

오랫동안 사용되지 않은 비활성 데이터를 저장하는 저비용 저장소이다. Amazon S3 Glacier와 같은 서비스를 사용할 수 있다.

### 로드밸런서

사용자의 API 요청을 여러 API 서버에 분산한다.

### API 서버

파일 업로드 이외의 사용자 요청과 메타데이터 변경을 처리한다.

### 메타데이터 데이터베이스

다음과 같은 메타데이터를 저장한다.

- 사용자
- 단말
- 파일
- 디렉터리
- 파일 버전
- 파일을 구성하는 블록

실제 파일 데이터는 저장하지 않는다.

### 메타데이터 캐시

자주 조회되는 파일 및 사용자 메타데이터를 캐싱하여 응답 속도를 향상한다.

### 알림 서비스

파일이 추가, 수정, 삭제 또는 공유되었을 때 관련 클라이언트에 변경 사실을 전달한다.

### 오프라인 사용자 백업 큐

사용자가 오프라인 상태일 때 전달하지 못한 변경 정보를 임시 저장한다. 사용자가 다시 접속하면 큐에 저장된 정보를 이용하여 동기화를 진행한다.

## 3단계 상세 설계

## 3.1 블록 저장소 서버

대용량 파일을 수정할 때마다 전체 파일을 업로드하면 네트워크 대역폭을 많이 소비한다.

이를 개선하기 위해 다음 두 기술을 사용한다.

### 델타 동기화

전체 파일이 아니라 수정된 블록만 전송한다.

예를 들어 블록 2와 블록 5만 변경되었다면 해당 두 블록만 클라우드 저장소에 업로드한다.

```
기존 파일: 블록 1 ~ 블록 10
수정 블록: 블록 2, 블록 5
업로드 대상: 블록 2, 블록 5
```

델타 동기화를 사용하면 네트워크 대역폭 사용량과 업로드 시간을 줄일 수 있다.

---

### 압축

파일을 블록 단위로 압축하여 전송 데이터의 크기를 줄인다.

압축 알고리즘은 파일 형식에 따라 달라질 수 있다.

- 텍스트 파일: gzip, bzip2
- 이미지와 비디오: 해당 형식에 적합한 별도 압축 방식

---

### 블록 업로드 과정

1. 파일을 작은 블록으로 분할
2. 각 블록을 압축
3. 블록을 암호화
4. 클라우드 저장소로 전송

블록의 최대 크기는 Dropbox 사례를 참고하여 4MB로 설정한다.

## 3.2 높은 일관성 요구사항

같은 파일이 사용자나 단말에 따라 서로 다른 상태로 보이는 것은 허용하기 어렵다. 따라서 시스템은 강한 일관성 모델을 지원해야 한다.

메타데이터 캐시와 데이터베이스에도 같은 원칙을 적용한다.

- 캐시의 데이터와 데이터베이스의 원본 데이터가 일치해야 한다.
- 데이터베이스의 원본이 변경되면 캐시의 기존 데이터를 무효화해야 한다.

관계형 데이터베이스는 ACID를 기본적으로 지원하므로 강한 일관성을 구현하기 쉽다.

NoSQL 데이터베이스는 일반적으로 최종 일관성을 기반으로 하므로, 강한 일관성을 제공하려면 추가적인 동기화 로직이 필요하다. 이번 설계에서는 관계형 데이터베이스를 사용한다.

---

## 3.3 메타데이터 데이터베이스

메타데이터 데이터베이스는 다음 테이블로 구성된다.

| 테이블 | 역할 |
| --- | --- |
| `user` | 사용자 이름, 이메일, 프로필 등 사용자 정보 저장 |
| `device` | 사용자의 단말 정보와 푸시 알림 ID 저장 |
| `namespace` | 사용자의 루트 디렉터리 및 공유 여부 저장 |
| `file` | 파일 이름, 상대 경로, 최신 버전, 체크섬 저장 |
| `file_version` | 파일의 갱신 이력과 버전 정보 저장 |
| `block` | 특정 파일 버전을 구성하는 블록의 순서 저장 |

### user

사용자의 기본 정보를 저장한다.

```
user_id
user_name
created_at
```

### device

사용자의 단말 정보를 저장한다. 한 사용자는 여러 개의 단말을 가질 수 있다.

```
device_id
user_id
last_logged_in_at
```

### namespace

사용자의 루트 디렉터리 정보를 저장한다.

```
id
owner_id
is_shared
created_at
```

### file

파일의 최신 상태와 경로를 저장한다.

```
id
file_name
relative_path
is_directory
latest_version
checksum
namespace_id
created_at
last_modified
```

### file_version

파일의 버전 이력을 저장한다. 이 테이블의 레코드는 읽기 전용으로 유지하여 갱신 이력이 변경되거나 손상되는 것을 방지한다.

```
id
file_id
device_id
version_number
last_modified
```

### block

파일 버전을 구성하는 블록과 블록 순서를 저장한다.

```
block_id
file_version_id
block_order
```

특정 버전의 파일은 블록을 `block_order` 순서대로 조합하여 복원할 수 있다.

---

## 3.4 파일 업로드 절차

파일 업로드는 메타데이터 등록과 실제 파일 업로드라는 두 요청이 병렬적으로 처리되는 구조이다.

### 메타데이터 등록

1. 클라이언트가 새 파일의 메타데이터 등록 요청을 API 서버에 전송
2. API 서버가 메타데이터를 데이터베이스에 저장
3. 파일 상태를 `pending`으로 설정
4. 파일이 추가되었다는 사실을 알림 서비스에 전달

### 실제 파일 업로드

1. 클라이언트가 파일을 블록 저장소 서버에 전송
2. 블록 저장소 서버가 파일을 작은 블록으로 분할
3. 각 블록을 압축하고 암호화
4. 블록을 클라우드 저장소에 업로드
5. 업로드가 끝나면 완료 콜백을 API 서버에 전달
6. API 서버가 파일 상태를 `uploaded`로 변경
7. 알림 서비스에 업로드 완료 사실을 전달
8. 알림 서비스가 관련 클라이언트에 변경 사실을 알림

파일을 수정하는 경우에도 전체적인 처리 흐름은 동일하다.

---

## 3.5 파일 다운로드 절차

파일이 새로 추가되거나 수정되면 다운로드 절차가 자동으로 시작된다.

온라인 상태의 클라이언트는 알림 서비스를 통해 변경을 즉시 확인한다. 오프라인 상태인 클라이언트의 변경 정보는 캐시나 백업 큐에 보관하며, 다음 접속 시 동기화한다.

### 다운로드 흐름

1. 알림 서비스가 클라이언트에 파일 변경 사실 전달
2. 클라이언트가 API 서버에 변경 내역 요청
3. API 서버가 메타데이터 데이터베이스에 최신 메타데이터 요청
4. 메타데이터 데이터베이스가 변경 내역 반환
5. API 서버가 최신 메타데이터를 클라이언트에 반환
6. 클라이언트가 블록 저장소 서버에 필요한 블록 요청
7. 블록 저장소 서버가 클라우드 저장소에서 블록 다운로드
8. 클라우드 저장소가 요청된 블록 반환
9. 블록 저장소 서버가 클라이언트에 블록 전달
10. 클라이언트가 전달받은 블록을 순서대로 조합하여 파일 복원

---

## 3.6 알림 서비스

알림 서비스는 파일의 일관성을 유지하기 위해 다른 클라이언트에 변경 사실을 전달한다.

알림 서비스 구현 방식으로 다음 두 가지를 고려할 수 있다.

### 롱 폴링

클라이언트가 서버에 요청을 보낸 뒤 새로운 이벤트가 발생할 때까지 연결을 유지하는 방식이다.

### 웹소켓

클라이언트와 서버 사이에 지속적인 양방향 통신 채널을 제공하는 방식이다.

---

### 롱 폴링을 선택하는 이유

구글 드라이브의 변경 알림은 채팅과 달리 실시간 양방향 통신이 필요하지 않다.

- 서버가 클라이언트에게 파일 변경 사실을 알려주는 단방향 통신에 가까움
- 파일 변경 이벤트가 채팅 메시지처럼 자주 발생하지 않음
- 한 번에 대량의 데이터를 전송할 필요가 없음
- 웹소켓을 사용할 경우 불필요한 연결 관리 비용이 발생할 수 있음

따라서 본 시스템에서는 롱 폴링을 사용한다.

### 롱 폴링 동작 방식

1. 클라이언트가 알림 서버와 롱 폴링 연결 유지
2. 특정 파일의 변경이 감지되면 서버가 응답을 반환하고 연결 종료
3. 클라이언트가 API 서버를 통해 최신 메타데이터 다운로드
4. 동기화가 완료되거나 연결 타임아웃이 발생하면 새로운 롱 폴링 요청 전송

---

## 3.7 저장 공간 절약

파일의 여러 버전을 모두 저장하면 저장 공간이 빠르게 부족해질 수 있다. 이를 방지하기 위해 다음 전략을 사용한다.

### 중복 제거

같은 파일 블록이 여러 번 저장되지 않도록 한다.

블록의 해시값을 비교하여 동일한 블록인지 판단하며, 중복된 블록은 사용자 계정 단위로 제거한다.

---

### 지능적 백업 전략

#### 버전 개수 제한

보관할 파일 버전의 최대 개수를 설정한다. 제한을 초과하면 가장 오래된 버전을 삭제한다.

#### 중요 버전만 보관

파일이 매우 자주 수정되면 짧은 시간 동안 수많은 버전이 생성될 수 있다. 모든 버전을 저장하지 않고 일정 간격의 버전이나 사용자가 지정한 중요 버전만 보관한다.

#### 비활성 데이터 아카이빙

몇 달 또는 몇 년간 사용하지 않은 데이터는 저렴한 아카이빙 저장소로 이동한다.

Amazon S3 Glacier와 같은 저장소는 일반 S3보다 접근 속도는 느리지만 저장 비용이 저렴하다.

---

## 3.8 장애 처리

대규모 시스템에서는 장애를 완전히 피하기 어렵다. 따라서 각 컴포넌트의 장애 상황을 미리 고려해야 한다.

### 로드밸런서 장애

보조 로드밸런서를 활성화하여 트래픽을 이어받도록 한다.

로드밸런서는 주기적으로 하트비트 신호를 교환한다. 일정 시간 동안 주 로드밸런서가 응답하지 않으면 장애가 발생한 것으로 판단한다.

---

### 블록 저장소 서버 장애

다른 블록 저장소 서버가 미완료 작업이나 대기 중인 작업을 이어받는다.

---

### 클라우드 저장소 장애

파일을 여러 리전에 복제한다. 한 지역에서 장애가 발생하면 다른 지역의 복제본을 이용하여 파일을 제공한다.

---

### API 서버 장애

API 서버는 무상태로 설계한다. 로드밸런서가 장애 서버로 요청을 보내지 않고 정상 서버로 우회한다.

---

### 메타데이터 캐시 장애

캐시 서버를 여러 노드에 복제한다. 한 노드에 장애가 발생하면 다른 노드에서 데이터를 조회하고, 장애 서버는 새로운 서버로 교체한다.

---

### 메타데이터 데이터베이스 장애

#### 주 데이터베이스 장애

부 데이터베이스 가운데 하나를 새로운 주 데이터베이스로 승격한다. 이후 새로운 부 데이터베이스를 추가한다.

#### 부 데이터베이스 장애

다른 부 데이터베이스가 읽기 요청을 처리한다. 장애가 발생한 서버는 새로운 서버로 교체한다.

---

### 알림 서비스 장애

알림 서버는 많은 클라이언트와 롱 폴링 연결을 유지해야 한다.

서버 한 대에 장애가 발생하면 해당 서버에 연결되어 있던 수많은 사용자가 동시에 재접속을 시도할 수 있다. 서버가 많은 연결을 유지하는 것은 가능하더라도, 수많은 연결을 동시에 새로 생성하는 것은 어렵기 때문에 복구 속도가 느려질 수 있다.

따라서 다음 사항을 고려해야 한다.

- 알림 서버 다중화
- 연결 재시도에 지연 시간 적용
- 재접속 요청 분산
- 서버별 연결 수 제한
- 장애 발생 시 점진적인 연결 복원

---

### 오프라인 사용자 백업 큐 장애

백업 큐 역시 여러 서버에 복제해야 한다.

큐에 장애가 발생하면 구독 중인 클라이언트가 다른 백업 큐와 다시 구독 관계를 설정하도록 한다.

---

## 4단계 마무리

이번 설계는 높은 안정성, 빠른 동기화, 효율적인 네트워크 사용, 확장성, 높은 가용성을 제공하는 구글 드라이브 형태의 시스템을 목표로 한다.

전체 시스템은 크게 다음 두 부분으로 나뉜다.

1. 파일 메타데이터 관리
2. 파일 저장 및 동기화 처리

알림 서비스는 두 영역과 함께 동작하며, 클라이언트가 파일의 최신 상태를 유지하도록 돕는다.

---

## 4.1 파일을 클라우드 저장소에 직접 업로드하는 대안

블록 저장소 서버를 거치지 않고 클라이언트가 클라우드 저장소에 직접 파일을 업로드하는 방식을 고려할 수 있다.

### 장점

클라이언트가 클라우드 저장소로 직접 파일을 전송하므로 업로드 시간이 단축될 수 있다.

### 단점

파일 분할, 압축, 암호화 로직을 클라이언트에서 처리해야 한다.

따라서 웹, iOS, Android 등 각 플랫폼마다 같은 기능을 별도로 구현해야 한다. 클라이언트가 공격당할 가능성이 있으므로 암호화 로직을 클라이언트 내부에 두는 것도 적절하지 않을 수 있다.

블록 저장소 서버를 사용하면 이러한 복잡한 로직을 서버에 집중시킬 수 있다는 장점이 있다.

---

## 4.2 접속 상태 관리 서비스 분리

클라이언트의 접속 상태를 관리하는 로직을 알림 서비스와 분리하여 별도의 서비스로 구성할 수도 있다.

이를 통해 접속 상태 관리 기능을 다른 서비스에서도 재사용할 수 있고, 알림 서비스의 책임도 단순하게 유지할 수 있다.

---

## 🔑 핵심 정리

- 실제 파일과 메타데이터를 서로 다른 저장소에 분리한다.
- 실제 파일은 S3와 같은 객체 저장소에 저장한다.
- 파일을 블록으로 나누고 수정된 블록만 전송한다.
- 블록을 압축하고 암호화하여 네트워크 사용량과 보안을 개선한다.
- 파일의 강한 일관성을 위해 관계형 데이터베이스와 캐시 무효화 전략을 사용한다.
- 알림은 양방향 통신이 필요하지 않으므로 롱 폴링을 활용한다.
- 중복 제거, 버전 제한, 아카이빙을 통해 저장 공간을 절약한다.
- 서버와 데이터는 다중화하여 단일 장애 지점을 줄인다.
- 오프라인 상태의 사용자를 위해 백업 큐에 변경 정보를 보관한다.
- 동시 수정 충돌이 발생하면 서버 버전과 로컬 버전을 모두 유지한 뒤 사용자에게 해결 방법을 제공한다.
