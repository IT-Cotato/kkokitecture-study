# 대용량 파일은 어떻게 안정적으로 업로드할까?

## Resumable Upload와 Multipart Upload 설계

---

## 1. 문제 상황

파일 크기가 작은 경우에는 하나의 HTTP 요청으로 파일 전체를 전송해도 큰 문제가 없다.

그러나 파일 크기가 수 GB 이상으로 커지면 다음과 같은 문제가 발생한다.

- 네트워크 연결이 중간에 끊길 가능성 증가
- 요청 제한 시간 초과 가능성 증가
- 실패 시 파일 전체를 다시 전송해야 하는 문제
- 서버의 네트워크 대역폭과 메모리 사용량 증가
- 모바일 환경에서 데이터 사용량 증가
- 한 번에 하나의 연결만 사용하므로 업로드 속도가 제한되는 문제

예를 들어 10GB 파일을 99%까지 업로드한 상태에서 연결이 끊겼다고 가정한다.

```
전체 파일 크기: 10GB
업로드 완료: 9.9GB
남은 데이터: 0.1GB

단순 업로드 실패 시 재전송량: 10GB
이어 올리기 적용 시 재전송량: 약 0.1GB
```

단순 업로드에서는 하나의 요청이 실패하면 전체 업로드가 실패한다. 이를 해결하기 위한 대표적인 방법이 **이어 올리기 업로드와 멀티파트 업로드**이다.

---

## 2. 핵심 개념

### 2.1 청크

청크는 하나의 큰 파일을 일정한 크기로 나눈 데이터 조각이다.

```
10GB 파일

[청크 1][청크 2][청크 3] ... [청크 N]
```

파일을 청크 단위로 나누면 일부 청크의 전송이 실패하더라도 실패한 청크만 다시 전송할 수 있다.

---

### 2.2 이어 올리기 업로드

이어 올리기 업로드는 서버가 **파일을 어디까지 받았는지 기록하고**, 연결이 끊기면 마지막으로 성공한 위치부터 업로드를 재개하는 방식이다.

영어로는 주로 다음과 같이 표현한다.

- Resumable Upload
- Resumable File Upload
- Upload Resume

핵심은 서버와 클라이언트가 다음 정보를 공유하는 것이다.

```
현재 서버가 받은 범위: 0 ~ 67108863 byte
다음에 전송할 위치: 67108864 byte
```

---

### 2.3 멀티파트 업로드

멀티파트 업로드는 하나의 파일을 여러 파트로 나누고, 각 파트를 독립적으로 업로드하는 방식이다.

```
파일
 ├── Part 1
 ├── Part 2
 ├── Part 3
 └── Part 4
```

각 파트는 다음과 같이 처리할 수 있다.

- 개별 업로드
- 개별 재시도
- 여러 파트의 병렬 업로드
- 모든 파트 업로드 후 하나의 객체로 결합

Amazon S3에서는 파트를 독립적으로, 순서와 관계없이 업로드할 수 있으며 모든 파트가 완료된 후 서버가 하나의 객체로 조립한다.

---

### 2.4 `multipart/form-data`와의 차이

멀티파트 업로드와 HTTP의 `multipart/form-data`는 이름은 비슷하지만 목적이 다르다.

| 구분 | 목적 |
| --- | --- |
| `multipart/form-data` | 하나의 HTTP 요청에 파일, 문자열, JSON 등 여러 종류의 데이터를 함께 전송 |
| 멀티파트 업로드 | 하나의 대용량 파일을 여러 요청으로 나누어 전송 |

이번 발표에서 말하는 멀티파트 업로드는 **Amazon S3와 같은 객체 저장소의 대용량 파일 업로드 방식**이다.

---

## 3. 이어 올리기 업로드의 동작 과정

이어 올리기 업로드는 일반적으로 **업로드 세션**을 중심으로 동작한다.

### 3.1 업로드 세션 생성

클라이언트가 서버에 업로드를 시작하겠다는 요청을 보낸다.

```
POST /uploads
Content-Type: application/json
```

```
{
  "fileName":"lecture.mp4",
  "fileSize":10737418240,
  "contentType":"video/mp4"
}
```

서버는 업로드 세션을 생성하고 세션을 식별할 수 있는 값을 반환한다.

```
{
  "uploadId":"upload-1234",
  "uploadUrl":"/uploads/upload-1234"
}
```

---

### 3.2 파일 일부 전송

클라이언트는 파일의 특정 바이트 범위를 서버로 보낸다.

```
PUT /uploads/upload-1234
Content-Range: bytes 0-67108863/10737418240
```

```
[0번부터 67108863번까지의 파일 데이터]
```

서버는 받은 범위를 저장한다.

```
수신 완료 범위: 0 ~ 67108863
다음 시작 위치: 67108864
```

---

### 3.3 네트워크 장애 발생

업로드 도중 네트워크가 끊기더라도 이미 성공한 부분은 서버에 남아 있다.

```
Part 1: 완료
Part 2: 완료
Part 3: 전송 중 실패
Part 4: 미전송
```

---

### 3.4 업로드 상태 확인

클라이언트가 다시 접속하면 서버에 현재 업로드 상태를 묻는다.

```
GET /uploads/upload-1234/status
```

```
{
  "uploadedBytes":134217728,
  "nextOffset":134217728
}
```

클라이언트는 `nextOffset`부터 다시 업로드한다.

Google Drive의 재개 가능한 업로드도 먼저 업로드 세션을 만든 뒤 데이터를 전송한다. 업로드가 끝나지 않은 경우 서버는 `308 Resume Incomplete`를 반환하고, 클라이언트는 응답의 `Range` 헤더를 통해 서버가 받은 바이트 범위를 확인한다.

---

## 4. Amazon S3 멀티파트 업로드

S3 멀티파트 업로드는 크게 네 단계로 구성된다.

```
1. 멀티파트 업로드 시작
2. 각 파트 업로드
3. 업로드된 파트 목록 전달
4. 전체 업로드 완료
```

---

### 4.1 멀티파트 업로드 시작

클라이언트 또는 백엔드 서버가 S3에 멀티파트 업로드 시작을 요청한다.

```
CreateMultipartUpload
```

S3는 해당 업로드를 식별하는 `UploadId`를 반환한다.

```
{
  "uploadId":"abc123"
}
```

이후 파트 업로드, 업로드 완료, 업로드 취소 요청에 같은 `UploadId`를 사용한다.

---

### 4.2 파트 업로드

파일을 여러 파트로 나누어 각각 업로드한다.

```
Part 1 ────────────────→ S3
Part 2 ────────────────→ S3
Part 3 ────────────────→ S3
Part 4 ────────────────→ S3
```

각 파트는 다음 정보로 식별된다.

- 객체를 저장할 버킷
- 객체의 키
- `UploadId`
- `PartNumber`

```
UploadPart(
    uploadId = abc123,
    partNumber = 3,
    data = ...
)
```

각 파트는 독립적으로 업로드할 수 있으므로 특정 파트가 실패하면 해당 파트만 재전송하면 된다.

---

### 4.3 병렬 업로드

파트들이 독립적이므로 여러 파트를 동시에 업로드할 수 있다.

```
작업자 1 ── Part 1 ──→ S3
작업자 2 ── Part 2 ──→ S3
작업자 3 ── Part 3 ──→ S3
작업자 4 ── Part 4 ──→ S3
```

병렬 업로드는 네트워크 대역폭을 더 적극적으로 활용하여 전체 업로드 시간을 줄일 수 있다.

다만 병렬 요청 수가 지나치게 많으면 다음 문제가 발생할 수 있다.

- 클라이언트의 메모리 사용량 증가
- 네트워크 혼잡
- 요청 수 증가
- 실패 요청과 재시도 증가
- 모바일 단말의 배터리 사용량 증가

따라서 파트 수만큼 무조건 동시에 전송하는 것이 아니라 제한된 개수의 작업자를 사용하는 것이 일반적인 설계이다.

---

### 4.4 멀티파트 업로드 완료

모든 파트가 업로드되면 클라이언트가 업로드된 파트 목록을 S3에 전달한다.

```
{
  "parts": [
    {
      "partNumber":1,
      "eTag":"etag-1"
    },
    {
      "partNumber":2,
      "eTag":"etag-2"
    },
    {
      "partNumber":3,
      "eTag":"etag-3"
    }
  ]
}
```

S3는 파트를 조립하여 하나의 객체를 생성한다.

```
[Part 1] + [Part 2] + [Part 3]
                 ↓
             lecture.mp4
```

S3는 완료 요청을 받기 전까지 개별 파트를 보관하며, 완료 요청이 성공해야 최종 객체를 생성한다.

---

## 5. 세 가지 업로드 방식 비교

| 구분 | 단순 업로드 | 이어 올리기 업로드 | S3 멀티파트 업로드 |
| --- | --- | --- | --- |
| 요청 수 | 1개 | 여러 개 가능 | 파트마다 별도 요청 |
| 실패 시 처리 | 전체 재전송 | 마지막 위치부터 재개 | 실패한 파트만 재전송 |
| 병렬 업로드 | 어려움 | 구현 방식에 따라 다름 | 가능 |
| 서버 상태 관리 | 거의 없음 | 현재 바이트 위치 관리 | 업로드 ID와 파트 목록 관리 |
| 구현 복잡도 | 낮음 | 중간 | 높음 |
| 적합한 파일 | 작은 파일 | 크거나 중단 가능성이 높은 파일 | 대용량 파일과 객체 저장소 |
| 대표 사례 | 프로필 이미지 | Google Drive API | Amazon S3 |

AWS 문서는 객체 크기가 약 100MB에 도달하면 단일 업로드 대신 멀티파트 업로드 사용을 고려할 것을 안내한다. S3의 각 파트는 마지막 파트를 제외하면 5MiB 이상이어야 하며, 한 업로드에 최대 10,000개의 파트를 사용할 수 있다.

Google Drive는 대용량 파일이나 모바일 환경처럼 네트워크 중단 가능성이 높은 경우 재개 가능한 업로드를 사용하도록 안내한다.

## 6. 직접 설계해 보는 대용량 업로드 시스템

사용자가 10GB 파일을 업로드하는 웹 서비스를 설계한다고 가정한다.

### 6.1 전체 구조

```
┌─────────────┐
│   사용자     │
│ 웹 브라우저  │
└──────┬──────┘
       │ 1. 업로드 시작 요청
       ▼
┌─────────────┐
│  API 서버    │
│ 업로드 관리  │
└──────┬──────┘
       │ 2. UploadId 생성
       │ 3. 파트별 업로드 URL 발급
       ▼
┌─────────────┐
│     S3      │
│ 파일 데이터 │
└─────────────┘
```

대용량 파일 데이터는 API 서버를 거치지 않고 클라이언트가 S3로 직접 전송하도록 설계할 수 있다.

API 서버는 다음 역할만 담당한다.

- 사용자 인증 및 권한 확인
- 업로드 세션 생성
- 파일 크기와 형식 검증
- 파트별 서명된 URL 발급
- 업로드 진행 상태 관리
- 완료 요청 처리
- 파일 메타데이터 저장

---

### 6.2 업로드 흐름

```
1. 클라이언트 → API 서버
   업로드 세션 생성 요청

2. API 서버 → S3
   멀티파트 업로드 생성

3. S3 → API 서버
   UploadId 반환

4. API 서버 → 클라이언트
   UploadId와 파트별 업로드 URL 반환

5. 클라이언트 → S3
   파트 병렬 업로드

6. 클라이언트 → API 서버
   업로드된 PartNumber와 ETag 전달

7. API 서버 → S3
   CompleteMultipartUpload 요청

8. API 서버 → 데이터베이스
   파일 상태를 COMPLETED로 변경
```

---

### 6.3 업로드 상태 관리

업로드 세션은 다음과 같은 상태를 가질 수 있다.

```
INITIATED
    ↓
UPLOADING
    ↓
COMPLETING
    ↓
COMPLETED
```

실패 상황을 포함하면 다음과 같다.

```
INITIATED
    ↓
UPLOADING ─────→ EXPIRED
    │
    ├──────────→ ABORTED
    │
    └──────────→ COMPLETING
                     ↓
                 COMPLETED
```

데이터베이스에는 다음 정보를 저장할 수 있다.

### `upload_session`

| 필드 | 설명 |
| --- | --- |
| `upload_id` | 업로드 세션 식별자 |
| `user_id` | 업로드 사용자 |
| `file_name` | 파일 이름 |
| `file_size` | 전체 파일 크기 |
| `chunk_size` | 파트 크기 |
| `status` | 업로드 진행 상태 |
| `storage_upload_id` | S3의 UploadId |
| `expires_at` | 업로드 세션 만료 시각 |

### `upload_part`

| 필드 | 설명 |
| --- | --- |
| `upload_id` | 업로드 세션 식별자 |
| `part_number` | 파트 번호 |
| `etag` | S3가 반환한 파트 식별 정보 |
| `checksum` | 데이터 무결성 검증값 |
| `size` | 파트 크기 |
| `status` | 파트 업로드 상태 |

## 7. 설계할 때 고려해야 할 문제

### 7.1 파트 크기

파트가 너무 작으면 다음 문제가 발생한다.

- HTTP 요청 수 증가
- 파트 상태 관리 비용 증가
- 요청당 헤더와 인증 처리 비용 증가
- 최대 파트 개수 제한에 도달할 가능성 증가

파트가 너무 크면 다음 문제가 발생한다.

- 실패 시 재전송해야 할 데이터 증가
- 병렬 처리 효과 감소
- 클라이언트 메모리 사용량 증가

```
작은 파트
재시도 비용 ↓
요청 수 ↑

큰 파트
재시도 비용 ↑
요청 수 ↓
```

따라서 파일 크기와 네트워크 환경에 따라 파트 크기를 결정해야 한다.

예를 들어 10GiB 파일을 64MiB 단위로 나누면 약 160개의 파트가 생성된다.

```
10GiB ÷ 64MiB = 160개
```

이는 어디까지나 설계를 설명하기 위한 예시이며, 실제 크기는 서비스 환경에서 측정한 결과를 바탕으로 조정해야 한다.

---

### 7.2 데이터 무결성 검증

전송이 성공했다는 사실만으로 데이터가 정확하다고 단정할 수 없다.

클라이언트와 서버가 파일 또는 파트의 체크섬을 계산하여 비교해야 한다.

```
클라이언트 체크섬: ABC123
서버 체크섬:       ABC123
                  ↓
              데이터 정상
```

```
클라이언트 체크섬: ABC123
서버 체크섬:       XYZ999
                  ↓
              재전송 필요
```

Amazon S3 멀티파트 업로드는 파트 및 전체 객체에 대한 체크섬 검증을 지원하며, SHA-256 등의 알고리즘을 이용하여 업로드 무결성을 확인할 수 있다.

---

### 7.3 재시도 전략

모든 실패를 즉시 같은 간격으로 재시도하면 장애가 발생했을 때 서버에 요청이 몰릴 수 있다.

따라서 일반적으로 다음과 같은 방식으로 재시도 간격을 늘린다.

```
1차 재시도: 1초 후
2차 재시도: 2초 후
3차 재시도: 4초 후
4차 재시도: 8초 후
```

여기에 임의의 지연 시간을 추가하여 여러 클라이언트가 동시에 재시도하는 상황을 줄일 수 있다.

---

### 7.4 멱등성

네트워크 문제로 클라이언트가 업로드 완료 요청을 보냈지만 응답을 받지 못할 수 있다.

```
클라이언트 ── 완료 요청 ──→ 서버
클라이언트 ←─ 응답 손실 ── 서버
```

클라이언트는 완료되지 않았다고 판단하여 같은 요청을 다시 보낼 수 있다.

이때 서버는 같은 요청을 여러 번 받아도 최종 결과가 달라지지 않도록 설계해야 한다.

```
동일 uploadId의 완료 요청

첫 번째 요청: 업로드 완료
두 번째 요청: 이미 완료된 결과 반환
```

---

### 7.5 완료되지 않은 업로드 정리

사용자가 업로드를 시작한 뒤 브라우저를 닫으면 일부 파트만 저장소에 남을 수 있다.

S3에서는 완료되지 않은 파트도 저장 공간을 사용하며, 업로드를 완료하거나 취소하기 전까지 해당 파트에 대한 저장 비용이 발생한다.

따라서 일정 기간이 지난 미완료 업로드는 삭제해야 한다.

```
업로드 시작
    ↓
24시간 동안 추가 요청 없음
    ↓
업로드 세션 만료
    ↓
S3 멀티파트 업로드 취소
    ↓
임시 파트 삭제
```

S3의 수명 주기 규칙을 사용하면 지정한 기간 내 완료되지 않은 멀티파트 업로드를 자동으로 중단하고 관련 파트를 삭제할 수 있다.

---

### 7.6 보안

파트 업로드 URL이 외부에 노출되면 다른 사용자가 데이터를 업로드할 수 있다.

다음과 같은 제한이 필요하다.

- 업로드 URL에 짧은 만료 시간 설정
- 사용자별 업로드 권한 검증
- 파일 크기 제한
- 업로드 가능한 콘텐츠 유형 제한
- 전체 파트 개수 제한
- 파일 이름을 그대로 저장소 키로 사용하지 않기
- 완료 요청 전에 파일 소유자 재검증

---

## 8. 이어 올리기와 멀티파트 업로드의 관계

두 방식의 차이는 다음과 같이 정리할 수 있다.

### 이어 올리기 업로드

```
“어디까지 성공했는가?”
```

- 마지막으로 업로드된 바이트 위치를 관리
- 연결이 끊기면 해당 위치부터 재개
- 업로드 복구가 주요 목적

### 멀티파트 업로드

```
“어떤 파트들이 성공했는가?”
```

- 파일을 독립적인 여러 파트로 분할
- 실패한 파트만 재시도
- 병렬 업로드 가능
- 대용량 파일의 효율적인 전송이 주요 목적

### 두 방식을 결합한 경우

```
파일을 여러 파트로 분할
        ↓
각 파트의 성공 여부 저장
        ↓
연결이 끊기면 성공한 파트는 유지
        ↓
실패하거나 미전송된 파트만 업로드
        ↓
모든 파트를 하나의 파일로 결합
```

즉, S3 멀티파트 업로드도 `UploadId`와 완료된 파트 정보를 클라이언트나 서버가 유지하면 이어 올리기처럼 활용할 수 있다.

## 9. 핵심 정리

대용량 파일 업로드에서 중요한 것은 파일을 단순히 여러 조각으로 나누는 것만이 아니다.

다음 상태를 지속적으로 관리해야 한다.

- 어떤 파일을 업로드 중인지
- 파일이 몇 개의 파트로 나뉘었는지
- 어떤 파트가 성공했는지
- 다음에 어떤 파트를 전송해야 하는지
- 모든 파트가 정상적인 데이터인지
- 업로드가 완료되었는지
- 중단된 업로드를 언제 삭제할지

```
신뢰할 수 있는 대용량 업로드
=
청크 분할
+ 업로드 상태 관리
+ 개별 재시도
+ 데이터 무결성 검증
+ 미완료 데이터 정리
```

### 최종 결론

- 작은 파일에는 단순 업로드가 적합하다.
- 네트워크 중단 가능성이 높다면 이어 올리기 업로드가 필요하다.
- 대용량 객체를 빠르게 전송하려면 멀티파트 업로드가 효과적이다.
- 실제 시스템에서는 이어 올리기와 멀티파트 업로드를 함께 적용할 수 있다.
- 업로드 기능은 파일 전송보다 **상태 관리와 실패 처리 설계가 더 중요하다.**
