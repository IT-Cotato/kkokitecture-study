# URL 단축기를 위한 데이터베이스 샤딩 전략

---

## 0. 들어가며 — 왜 샤딩인가?

지난 시간 URL 단축기 설계에서 우리는 다음과 같은 수치를 봤다.

- 10년간 **3650억 개** 레코드
- 저장 용량 **36.5TB**
- 초당 읽기 **11,600 QPS**, 쓰기 **1,160 QPS**

이걸 **단일 MySQL 인스턴스**로 처리할 수 있을까?

- 일반적인 MySQL 단일 노드: 수백 GB ~ 수 TB가 한계
- 인덱스 크기가 메모리 초과하면 성능 급락
- 단일 노드 장애 = 서비스 전체 중단

**결론**: 샤딩(sharding)은 선택이 아니라 필수.

---

## 1. 샤딩이란?

> **샤딩**: 큰 데이터베이스를 여러 개의 작은 조각(shard)으로 수평 분할하여 여러 서버에 분산시키는 것
>

### 수직 분할(Vertical) vs 수평 분할(Horizontal)

- **수직 분할**: 컬럼 단위로 쪼개기 (예: user 테이블에서 profile_image만 분리)
- **수평 분할 = 샤딩**: 행(row) 단위로 쪼개기 (예: id 1~1억 → 샤드1, 1억~2억 → 샤드2)

URL 단축기에서는 **수평 분할**이 답이다. 레코드 수 자체가 문제니까.

---

## 2. 샤딩 키(Shard Key) 선택

url 테이블은 `id`, `shortURL`, `longURL` 세 컬럼으로 구성된다. 어떤 컬럼을 샤딩 키로 쓸까?

### 후보 비교

| 샤딩 키 | 장점 | 단점 |
| --- | --- | --- |
| **id** | 균등 분포 보장 | shortURL 조회 시 모든 샤드 검색 필요 |
| **shortURL (hashValue)** | 리디렉션 조회가 단일 샤드로 | ID 생성과 샤드 매핑이 별도 관리 필요 |
| **longURL** | 중복 URL 감지 쉬움 | 길이 가변적, 분포 편향 가능성 |

### 결론: **shortURL 기반 샤딩**

URL 단축기의 트래픽 패턴은 **읽기:쓰기 = 10:1**.
가장 빈번한 작업인 **shortURL → longURL 리디렉션 조회**가 단일 샤드에서 끝나야 한다.

---

## 3. 샤딩 전략 3가지

### 3-1. Range-based Sharding (범위 기반)

shortURL의 첫 글자 또는 ID 범위로 분할.

```
샤드 1: shortURL이 0~9로 시작
샤드 2: shortURL이 a~m으로 시작
샤드 3: shortURL이 n~z로 시작
샤드 4: shortURL이 A~Z로 시작
```

**장점**

- 구현이 매우 단순
- 범위 쿼리에 유리

**단점**

- **Hotspot 문제**: base-62 변환 시 ID가 증가하면 특정 문자로 시작하는 단축 URL이 몰림
- 예: 최근 생성된 URL이 모두 'z'로 시작 → 샤드 3에 쓰기 부하 집중
- **재분배가 어렵다**: 샤드 추가 시 대규모 데이터 이동

→ **URL 단축기에는 부적합**

---

### 3-2. Hash-based Sharding (해시 기반)

shortURL에 해시 함수를 적용하고, 그 결과를 샤드 개수로 나눈 나머지(modulo)로 샤드 결정.

```python
shard_id = hash(shortURL) % N    # N = 샤드 개수
```

**장점**

- 데이터 균등 분포 (해시 함수가 좋다면)
- 구현 간단

**단점**

- **Resharding 지옥**: N이 바뀌면 **거의 모든 데이터가 다른 샤드로 이동**해야 함
- 예: 샤드 4개 → 5개로 늘리면 약 80% 데이터 재배치
- 서비스 무중단으로 하기 매우 어려움

---

### 3-3. Consistent Hashing (일관성 해싱)

해시 결과를 **링(ring)** 형태의 공간에 매핑하고, 샤드도 같은 링에 배치.
각 키는 링에서 시계방향으로 가장 가까운 샤드에 저장.

**장점**

- 샤드 추가/제거 시 **평균 K/N개의 키만 이동** (K=전체 키, N=샤드 수)
- 예: 샤드 4→5개로 늘려도 약 **20%만 재배치**
- 가상 노드(virtual node) 도입으로 부하 균등화 가능

**단점**

- 구현 복잡도 증가
- 초기 설계 시 가상 노드 개수 등 튜닝 필요

→ **URL 단축기 샤딩에 가장 적합한 선택**

## 4. 실전 고려사항

### 4-1. ID 생성기와 샤딩의 관계

base-62 변환 방식을 쓴다면 **전역적으로 유일한 ID**가 필요하다.
샤딩 환경에서 auto-increment는 쓸 수 없다 (샤드마다 ID 충돌).

**해결책**

- **Snowflake ID**: timestamp + machine ID + sequence
- **Ticket Server**: 중앙 ID 발급 서버 (Flickr 방식)
- **UUID**: 간단하지만 정렬 불가, 인덱스 비효율

### 4-2. Cross-shard 쿼리 문제

샤딩 후에는 **여러 샤드를 동시에 조회해야 하는 쿼리**가 골치 아프다.

예시

- "최근 1시간 동안 생성된 모든 단축 URL" → 모든 샤드 스캔
- "사용자별 URL 목록" → user_id로도 샤딩하거나 별도 인덱스 필요

**해결책**: Scatter-gather 패턴 또는 별도 집계 테이블

### 4-3. Hotspot 다루기

특정 URL이 바이럴 → 해당 샤드에 트래픽 집중.

**해결책**

- **캐시 우선**: Redis 등에 자주 조회되는 URL 캐싱 (앞서 설계한 캐시 계층)
- **Read replica**: 인기 샤드에만 추가 복제본 배치
- **CDN 활용**: 301 응답을 엣지에서 캐싱

## 5. 실제 사례: Bitly의 아키텍처

bit.ly는 실제로 다음과 같이 운영한다고 알려져 있다.

- **NoSQL (HBase, Riak 등)** 기반 분산 저장소 사용
- shortURL 해시값을 키로 하는 **key-value store**
- Consistent hashing 기반 분산
- 통계 데이터는 별도 분석 파이프라인(Kafka + Spark)으로 분리

**핵심 교훈**: 단순 KV 조회 패턴에는 RDBMS보다 NoSQL이 자연스러움

---

## 6. 정리

### 핵심 메시지

1. URL 단축기는 규모상 **샤딩이 필수**
2. 트래픽 패턴(읽기 위주) 때문에 **shortURL을 샤딩 키로**
3. **Consistent Hashing**이 가장 균형 잡힌 선택
4. 샤딩만으로는 부족 — **캐시 + Replication과 함께 설계**해야 함

### 의사결정 흐름

```
규모 추정 → 샤딩 필요?
  → 샤딩 키 선정 (쿼리 패턴 분석)
  → 분산 전략 선택 (Range/Hash/Consistent)
  → ID 생성 전략 결정
  → Cross-shard 쿼리 대응책 마련
```
