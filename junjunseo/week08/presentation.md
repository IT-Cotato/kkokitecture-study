## 발표를 시작하기 전에

책 7장에서 우리는 트위터 Snowflake가 64비트 정수로 ID를 만든다고 배웠다. 타임스탬프 41비트, 데이터센터 5비트, 서버 5비트, 일련번호 12비트. 깔끔하다.

LINE의 글로벌 이커머스 팀이 작년에 주문 DB를 Oracle에서 MySQL로 옮기면서 ID 생성 방식을 새로 정했는데, 책에서 본 표준 Snowflake랑 꽤 다르다. 왜 그렇게 다르게 만들었는지, 그 과정을 따라가보자.

---

## 표준 Snowflake를 못 쓴 이유

LINE 팀이 처음 고려한 건 책에 나오는 방식들 그대로다. 근데 하나씩 떨어져 나갔다.

**MySQL Auto Increment**부터 보자. 단순하고 좋은 방법인데, JPA의 Batch Insert랑 안 맞는다. JPA는 객체를 영속성 컨텍스트에 보관할 때 ID가 필요해서, 객체 하나 저장할 때마다 INSERT 쿼리가 한 번씩 날아간다. 주문 하나에 상품이 100개 들어 있으면 INSERT가 100번 날아간다는 얘기다. 이러면 성능이 안 나온다.

- *채번 테이블(티켓 서버)**도 시도해봤는데 원하는 만큼 성능이 안 나왔다. 책에서도 SPOF 문제를 지적했던 그 방식이다.

그러면 **표준 Snowflake**를 쓰면 되지 않나? 여기서 가장 흥미로운 제약이 등장한다. **하위 호환성**이다. 이미 운영 중인 주문 ID들이 특정 형식의 숫자 문자열로 쌓여 있고, 결제·배송·정산 같은 외부 연동 시스템들이 전부 이 형식에 의존하고 있었다. 갑자기 64비트 정수로 바꾸면 모든 게 깨진다.

그래서 LINE은 **Snowflake의 아이디어는 빌리되, 형식은 새로 짜는** 길을 택했다.

---

## LINE이 새로 만든 18자리 ID

이렇게 생겼다.

```
| 날짜 8자리 | 인스턴스 번호 3자리 | 시퀀스 7자리 |
| YYYYMMDD  | 001 ~ 999          | 0000000 ~ 9999999 |
```

총 18자리 숫자 문자열이다. 책의 표준이랑 비교해보면 이렇다.

|  | 책 (표준 Snowflake) | LINE 자체 패턴 |
| --- | --- | --- |
| 형식 | 64비트 정수 | 18자리 숫자 문자열 |
| 시간 | 41비트 (밀리초) | 8자리 (날짜) |
| 인스턴스 식별 | 데이터센터 5 + 서버 5 | 인스턴스 번호 3자리 |
| 시퀀스 | 12비트 (4,096개/ms) | 7자리 (천만 개/일) |
| 정렬 단위 | 밀리초 | 일(day) |

가장 큰 차이는 **시간 단위가 밀리초가 아니라 일(day) 단위**라는 것이다. 트위터는 트윗이 초당 수만 건씩 쏟아지니까 밀리초 정렬이 의미 있지만, 이커머스 주문은 그렇게 빈번하지 않다. 대신 **하루 단위로 DB 파티셔닝**을 하니까 ID에 날짜가 박혀 있는 게 더 유용하다. ID만 봐도 어느 파티션에 들어갈지 알 수 있다.

ID 형식은 비즈니스 요구사항에 맞춰서 결정된다는 게 여기서 드러난다.

---

## 인스턴스 번호는 어떻게 줄까

책에서는 데이터센터 ID와 서버 ID를 "시스템이 시작할 때 결정된다"고 한 줄로 넘어간다. 근데 LINE 블로그를 보면 이런 문장이 나온다.

> "Snowflake 방식에서 가장 고민되는 요소는 서버 인스턴스 번호를 얻는 부분이라고 생각합니다."
>

책이 한 줄로 처리한 게 실무에서는 가장 큰 고민거리였다는 얘기다. 왜 어려울까?

요즘은 다 Kubernetes 환경이다. Pod가 수시로 죽고 새로 뜬다. 새로 뜬 Pod한테 어떤 인스턴스 번호를 줘야 할까? 0번부터 차례대로? 그러면 누가 그 "차례"를 관리하지? ZooKeeper 같은 분산 코디네이션 시스템을 쓰면 되긴 하는데, 그러면 운영해야 할 인프라가 또 하나 늘어난다.

**LINE의 해법은 MySQL 테이블 락을 사용했다.**

```
새 Pod 부팅
    ↓
MySQL 인스턴스 번호 테이블에 TABLE LOCK 획득
    ↓
비어있는 번호 하나 선점, 호스트명이랑 시작 시각 기록
    ↓
락 해제하고 그 번호로 ID 생성 시작
```

실제 운영 테이블이 이렇게 생겼다.

| 인스턴스 번호 | 호스트 이름 | 선점 시작 시각 | 선점 종료 시각 |
| --- | --- | --- | --- |
| 1 | api-64b48b6f87-cjr22 | 2023-05-31 09:23:18 | 2023-06-01 21:10:18 |
| 2 | api-6d6b56fd57-bmxdk | 2023-05-31 09:23:18 | 2023-06-01 21:10:18 |
| ... | ... | ... | ... |
| 999 | api-77ffbf76f5-f878z | 2023-05-31 09:23:18 | null |

선점 종료 시각이 `null`이면 현재 사용 중인 번호다. 종료 시각이 박혀 있으면 다음 날 다른 Pod가 그 번호를 다시 가져갈 수 있다. 추가 인프라 없이 MySQL 하나로 분산 환경의 인스턴스 번호 할당을 해결한 셈이다.

시퀀스가 7자리라서 하루에 천만 개까지 만들 수 있는데, 만약 하루 안에 그걸 다 써버리면? LINE은 시퀀스가 거의 다 차면 **새 인스턴스 번호를 비동기로 미리 받아둔다**고 한다. 책에서 마무리에 "각 절의 길이 최적화" 얘기를 살짝 했는데, 그게 실무에서는 이런 식으로 적용된다.

## 효과

LINE이 Oracle에서 MySQL로 넘어가면서 측정한 실제 성능

| API | Oracle (지연 시간 제외) | MySQL | 비고 |
| --- | --- | --- | --- |
| 단일 조회 | 약 60ms | 4ms |  |
| 주문 목록 | 약 150ms | 51ms |  |
| 주문 검색 | 약 300ms | 60ms |  |
| **주문 생성** | **약 2,200ms** | **1,424ms** | **약 800ms 단축** |
| 주문 수정 | 약 400ms | 17ms |  |

조회 성능은 DB 모델을 바꾼 효과가 크지만, **주문 생성에서 800ms가 줄어든 건 ID 생성 방식을 바꾼 영향이 크다**고 LINE은 평가한다. 블로그 원문

> "주문 생성도 약 2,300ms에서 1,420ms로 거의 800ms 가량 줄어들었습니다. 이는 모델을 변경한 효과도 있지만, 기존에 사용하던 Oracle 시퀀스에서 Snowflake로 전환한 효과가 크다고 생각합니다."
>

책에서 "Snowflake가 좋다"고 배웠는데, 그게 실제 프로덕션에서 800ms라는 숫자로 검증된 셈이다.

## 책에 없는 내용

**첫째, ID 생성은 단순한 ID 문제가 아니다.** LINE이 Auto Increment를 안 쓴 이유가 JPA Batch Insert 때문이었다는 게 인상적이었다. ID를 만드는 방식이 ORM 동작 방식이랑 얽혀서 성능을 좌우한다. Snowflake처럼 **애플리케이션이 미리 ID를 알 수 있어야** Batch Insert가 의미 있다. ID 설계는 아키텍처 전체와 연결된다.

**둘째, 하위 호환성이 설계의 절반이다.** 이론적으로 가장 깔끔한 64비트 정수 대신, 이미 운영 중인 형식을 흉내내는 18자리 문자열이 선택됐다. 모든 회사는 신규 시스템이 아니라 레거시 위에서 결정한다. 시험 답안지에 "표준 Snowflake가 정답"이라 적으면 점수는 받겠지만, 실무에서는 그게 정답이 아닐 수 있다.

**셋째, 시간 단위는 비즈니스에 맞춰서 정한다.** 트위터는 밀리초, LINE은 일(day). 같은 Snowflake라도 시간 단위가 다르고, 그건 DB 파티셔닝 전략이랑 직결된다. 책의 비트 구조가 절대적이지 않다는 걸 보여주는 사례다.

**넷째, 인스턴스 번호 할당이 진짜 어려운 문제다.** 책이 한 줄로 넘기는 부분인데, 실무에서는 ZooKeeper, Kubernetes StatefulSet, MySQL 락 선점 등 여러 옵션 중에 골라야 한다. LINE은 "추가 인프라 없이" MySQL 하나로 푸는 길을 택했고, 이게 잘 작동했다.

---

## 정리

책 7장에서 배운 Snowflake는 출발점이다. 실제 회사들은 거기서 변형해서 쓴다.

- LINE은 **64비트 정수 대신 18자리 숫자 문자열**로 만들었다 (하위 호환성).
- 시간 단위는 **밀리초 대신 일(day)** 로 잡았다 (DB 파티셔닝과 정합).
- 인스턴스 번호는 **MySQL 테이블 락으로 경쟁 선점**해서 가져온다 (추가 인프라 회피).
- 결과적으로 **주문 생성 API가 약 800ms 빨라졌다**.

면접에서 ID 생성기를 설계하라는 문제를 받는다면, 책의 표준 Snowflake를 그리는 것까지가 절반이다. 나머지 절반은 "근데 우리 시스템에 맞게 어디를 어떻게 변형할까?"를 말할 수 있느냐다.
