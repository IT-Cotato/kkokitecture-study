# 14장. 유튜브 설계

## 14.0 개요

유튜브와 같은 대규모 동영상 플랫폼은 겉으로는 사용자가 영상을 업로드하고 재생하는 단순한 서비스처럼 보이지만, 실제로는 대용량 저장소, 비디오 트랜스코딩, CDN, 메타데이터 관리, 장애 복구 등 다양한 기술이 결합된 시스템이다.

이 장에서는 제한된 시스템 설계 면접 시간 안에 핵심 기능을 선정하고, 개략적인 구조를 제시한 뒤, 비디오 처리 파이프라인과 최적화 방안을 구체화하는 과정을 다룬다.

---

# 1단계. 문제 이해 및 설계 범위 확정

## 1.1 요구사항 확인

시스템 설계를 시작하기 전에 면접관과 질의응답을 통해 설계 범위를 좁혀야 한다.

교재에서 가정한 주요 요구사항은 다음과 같다.

| 항목 | 요구사항 |
|---|---|
| 핵심 기능 | 비디오 업로드와 비디오 시청 |
| 지원 클라이언트 | 모바일 앱, 웹 브라우저, 스마트 TV |
| 일간 능동 사용자 수 | 약 500만 명 |
| 평균 이용량 | 사용자 한 명당 하루 평균 5개 비디오 시청 |
| 업로드 사용자 비율 | 전체 사용자의 약 10%가 하루에 비디오 1개 업로드 |
| 지원 형식 | 현재 널리 사용되는 주요 비디오 형식 |
| 최대 파일 크기 | 1GB |
| 보안 | 비디오 암호화 필요 |
| 인프라 | 기존 클라우드 서비스 활용 가능 |
| 다국어 | 특정 언어에 제한되지 않아야 함 |

제한된 면접 시간 안에 유튜브의 모든 기능을 설계할 수 없으므로 다음 기능에 집중한다.

- 빠른 비디오 업로드
- 원활한 비디오 재생
- 재생 화질 선택
- 낮은 인프라 비용
- 높은 가용성과 안정성
- 대규모 트래픽에 대한 확장성

댓글, 추천, 채널 구독, 광고 등은 이번 설계 범위에서 제외한다.

---

## 1.2 개략적 규모 추정

### 트래픽 가정

- 일간 능동 사용자 수는 500만 명이다.
- 사용자 한 명은 하루 평균 5개의 비디오를 시청한다.
- 전체 사용자의 10%가 하루에 비디오 1개를 업로드한다.
- 비디오 평균 크기는 300MB이다.

### 하루 신규 저장 용량

```text
500만 명 × 10% × 300MB
= 150TB/일
```

트랜스코딩 결과물, 여러 해상도 사본, 복제본까지 포함하면 실제 필요한 저장 용량은 더 커진다.

### CDN 비용 추정

교재에서는 예시 계산을 위해 다음을 가정한다.

- 모든 트래픽이 미국에서 발생한다.
- CDN 전송 비용은 1GB당 약 0.02달러이다.
- 사용자 500만 명이 하루 5개 비디오를 시청한다.
- 비디오 한 개의 평균 전송 크기는 0.3GB이다.

```text
500만 명 × 5개 × 0.3GB × 0.02달러
= 약 150,000달러/일
```

대규모 비디오 서비스에서는 CDN 비용이 매우 커질 수 있으므로, 상세 설계 단계에서 비용 최적화를 반드시 고려해야 한다.

> 실제 비용은 지역, 트래픽 구간, 캐시 적중률, 계약 조건 등에 따라 달라진다.

# 2단계. 개략적 설계안 제시 및 동의 구하기

## 2.1 기존 클라우드 서비스 활용

시스템 설계 면접에서는 모든 구성 요소를 밑바닥부터 직접 구현할 필요가 없다.

적절한 기술을 선택하고 전체 시스템의 동작 원리를 설명하는 것이 중요하다.

특히 다음 서비스는 직접 구축하기보다 검증된 클라우드 서비스를 활용하는 편이 현실적이다.

- BLOB 저장소
- CDN
- 로드 밸런서
- 관리형 데이터베이스
- 메시지 큐

대규모 서비스 역시 CDN이나 클라우드 인프라를 외부 업체에 의존하는 경우가 많다.

---

## 2.2 최상위 시스템 구성

유튜브 시스템은 개략적으로 다음 세 영역으로 구성된다.

```text
사용자 단말
├─ 비디오 스트리밍 요청 → CDN
└─ 기타 API 요청 → API 서버
```

### 사용자 단말

컴퓨터, 모바일 기기, 스마트 TV 등에서 비디오를 업로드하거나 시청하는 클라이언트이다.

### CDN

비디오 콘텐츠를 캐시하고 사용자에게 스트리밍하는 구성 요소이다.

사용자가 재생 버튼을 누르면 일반적으로 사용자와 가까운 CDN 엣지 서버에서 비디오를 전송한다.

### API 서버

비디오 스트리밍을 제외한 대부분의 요청을 처리한다.

주요 역할은 다음과 같다.

- 추천 피드 제공
- 비디오 메타데이터 조회
- 비디오 업로드 URL 발급
- 사용자 가입 및 인증
- 메타데이터 데이터베이스와 캐시 갱신

---

# 2.3 비디오 업로드 절차

## 2.3.1 주요 구성 요소

비디오 업로드 시스템은 다음 구성 요소로 이루어진다.

### 로드 밸런서

여러 API 서버에 요청을 고르게 분산한다.

### API 서버

업로드 요청, 메타데이터 갱신, 사용자 인증 등 스트리밍 외의 요청을 처리한다.

### 메타데이터 데이터베이스

다음과 같은 비디오 정보를 저장한다.

- 비디오 URL
- 제목
- 설명
- 파일 크기
- 해상도
- 포맷
- 업로더 정보
- 처리 상태

읽기 부하와 가용성을 높이기 위해 복제와 샤딩을 적용할 수 있다.

### 메타데이터 캐시

자주 조회되는 비디오 메타데이터와 사용자 객체를 캐시하여 응답 속도를 높인다.

### 원본 저장소

업로드된 원본 비디오를 보관하는 대용량 BLOB 저장소이다.

### 트랜스코딩 서버

원본 비디오를 여러 코덱, 해상도, 비트레이트로 변환한다.

사용자 단말과 네트워크 환경에 적합한 비디오 스트림을 제공하기 위한 구성 요소이다.

### 트랜스코딩 비디오 저장소

트랜스코딩이 완료된 결과물을 저장하는 BLOB 저장소이다.

### CDN

트랜스코딩된 비디오를 사용자에게 전달한다.

### 트랜스코딩 완료 큐

트랜스코딩 완료 이벤트를 보관하는 메시지 큐이다.

### 완료 핸들러

완료 이벤트를 소비하여 메타데이터 데이터베이스와 캐시의 처리 상태를 갱신한다.

---

## 2.3.2 비디오 업로드 전체 흐름

```text
사용자
→ 원본 저장소에 비디오 업로드
→ 트랜스코딩 서버가 원본 비디오 처리
→ 트랜스코딩 결과 저장소에 결과 저장
→ CDN에 결과 배포
→ 완료 이벤트를 메시지 큐에 전달
→ 완료 핸들러가 메타데이터 DB와 캐시 갱신
→ API 서버가 사용자에게 재생 준비 완료 상태 전달
```

비디오 업로드와 메타데이터 갱신은 병렬로 진행될 수 있다.

---

## 2.3.3 프로세스 A: 비디오 업로드

1. 클라이언트가 원본 비디오를 원본 저장소에 업로드한다.
2. 트랜스코딩 서버가 원본 저장소에서 비디오를 가져온다.
3. 트랜스코딩을 수행한다.
4. 트랜스코딩이 끝나면 다음 작업이 병렬로 진행된다.
    - 트랜스코딩 결과물을 결과 저장소에 업로드한다.
    - 완료 이벤트를 트랜스코딩 완료 큐에 넣는다.
5. 결과 저장소의 비디오를 CDN에 배포한다.
6. 완료 핸들러가 메시지를 소비한다.
7. 메타데이터 데이터베이스와 캐시의 비디오 상태를 갱신한다.
8. API 서버가 사용자 단말에 업로드 및 처리 완료 상태를 전달한다.

---

## 2.3.4 프로세스 B: 메타데이터 갱신

원본 비디오가 업로드되는 동안 클라이언트는 API 서버에 메타데이터 갱신 요청을 별도로 전송한다.

메타데이터의 예시는 다음과 같다.

- 파일 이름
- 파일 크기
- 비디오 포맷
- 제목과 설명
- 사용자 정보
- 해상도

API 서버는 해당 정보를 메타데이터 데이터베이스와 캐시에 반영한다.

---

# 2.4 비디오 스트리밍 절차

## 2.4.1 다운로드와 스트리밍의 차이

다운로드는 비디오 파일 전체를 단말에 내려받는 방식이다.

스트리밍은 원격 비디오에서 데이터 스트림을 지속적으로 전송받아 전체 다운로드가 완료되기 전에도 재생을 시작하는 방식이다.

유튜브와 같은 서비스에서는 CDN을 통해 스트리밍이 이루어진다.

```text
사용자 단말
→ 가까운 CDN 엣지 서버에 재생 요청
→ CDN에서 비디오 스트림 전송
```

가까운 엣지 서버를 이용하므로 전송 지연을 낮출 수 있다.

---

## 2.4.2 스트리밍 프로토콜

스트리밍 프로토콜은 비디오 데이터를 전송할 때 사용하는 표준화된 통신 방식이다.

대표적인 프로토콜은 다음과 같다.

- MPEG-DASH
- Apple HLS
- Microsoft Smooth Streaming
- Adobe HTTP Dynamic Streaming

프로토콜마다 지원하는 코덱과 재생 단말이 다르므로 클라이언트 환경에 맞는 프로토콜을 선택해야 한다.

시스템 설계에서는 각 프로토콜의 구현 세부사항보다 다음을 이해하는 것이 중요하다.

- 여러 해상도와 비트레이트의 스트림을 제공한다.
- 네트워크 상황에 따라 화질을 동적으로 변경할 수 있다.
- 사용자와 가까운 CDN에서 데이터를 전송한다.

# 3단계. 상세 설계

## 3.1 비디오 트랜스코딩

비디오를 업로드한 단말은 특정 포맷과 비트레이트로 영상을 저장한다.

다른 단말에서 해당 영상을 원활하게 재생하려면 여러 해상도, 코덱, 비트레이트로 변환해야 한다.

### 비트레이트

비디오를 구성하는 비트가 초당 얼마나 처리되는지를 나타낸다.

일반적으로 비트레이트가 높을수록 영상 품질이 높지만 다음 비용도 증가한다.

- 저장 공간
- 네트워크 대역폭
- 디코딩에 필요한 연산량

### 트랜스코딩이 필요한 이유

- 원본 비디오는 매우 큰 저장 공간을 차지할 수 있다.
- 단말과 브라우저마다 지원하는 비디오 포맷과 코덱이 다르다.
- 사용자의 네트워크 대역폭에 따라 서로 다른 화질을 제공해야 한다.
- 모바일 환경에서는 네트워크 상태가 지속적으로 변하므로 적응형 화질이 필요하다.

---

## 3.2 컨테이너와 코덱

### 컨테이너

비디오, 오디오, 메타데이터를 하나의 파일에 담는 형식이다.

대표적인 확장자는 다음과 같다.

- `.avi`
- `.mov`
- `.mp4`

### 코덱

비디오 화질을 유지하면서 파일 크기를 줄이기 위한 압축 및 압축 해제 알고리즘이다.

대표적인 코덱은 다음과 같다.

- H.264
- VP9
- HEVC

컨테이너는 미디어 데이터를 담는 형식이고, 코덱은 영상 데이터를 압축하고 해제하는 방식이라는 차이가 있다.

---

# 3.3 유향 비순환 그래프 모델

## 3.3.1 DAG를 사용하는 이유

비디오 처리에는 여러 작업이 필요하며 콘텐츠 제작자마다 요구사항이 다를 수 있다.

대표적인 작업은 다음과 같다.

- 비디오 품질 검사
- 여러 해상도와 코덱으로 인코딩
- 썸네일 추출
- 워터마크 삽입
- 오디오 인코딩
- 메타데이터 추출

일부 작업은 서로 독립적이므로 병렬로 실행할 수 있고, 일부 작업은 앞선 작업이 완료되어야 시작할 수 있다.

이러한 의존관계를 표현하기 위해 DAG를 사용한다.

DAG는 작업을 노드로, 작업 간 의존관계를 방향성이 있는 간선으로 표현한다.

순환 구조가 없으므로 실행 순서를 명확히 정의할 수 있다.

---

## 3.3.2 비디오 처리 DAG 예시

원본 비디오는 다음 세 부분으로 나뉘어 처리될 수 있다.

```text
원본 비디오
├─ 비디오
│  ├─ 검사
│  ├─ 인코딩
│  ├─ 썸네일 추출
│  └─ 워터마크 삽입
├─ 오디오
│  └─ 오디오 인코딩
└─ 메타데이터 추출
```

처리 결과는 마지막에 병합되어 최종 비디오 파일을 만든다.

### 검사

비디오의 품질과 손상 여부를 확인한다.

### 비디오 인코딩

다양한 해상도, 코덱, 비트레이트 조합의 비디오를 생성한다.

예시는 다음과 같다.

- 360p
- 480p
- 720p
- 1080p
- 4K

### 썸네일

업로드한 비디오나 이미지에서 대표 이미지를 자동 추출한다.

### 워터마크

소유자 정보나 회사 로고 등을 이미지 오버레이 형태로 영상에 삽입한다.

---

# 3.4 비디오 트랜스코딩 아키텍처

트랜스코딩 아키텍처는 다음 다섯 가지 핵심 구성 요소로 이루어진다.

```text
전처리기
→ DAG 스케줄러
→ 자원 관리자
→ 작업 실행 서버
→ 인코딩된 비디오

전처리기·작업 서버
↔ 임시 저장소
```

- 전처리기
- DAG 스케줄러
- 자원 관리자
- 작업 실행 서버
- 임시 저장소

---

## 3.4.1 전처리기

전처리기는 다음 작업을 수행한다.

### 1. 비디오 분할

비디오 스트림을 GOP 단위로 분할한다.

GOP는 특정 순서로 배열된 프레임의 그룹이다.

하나의 GOP는 독립적으로 재생할 수 있으며, 보통 몇 초 정도의 영상에 해당한다.

단말이 GOP 단위 분할을 지원하지 않으면 서버 측 전처리기가 비디오를 분할한다.

### 2. DAG 생성

사용자가 정의한 처리 설정을 바탕으로 DAG를 생성한다.

예를 들어 다음 두 작업을 연결할 수 있다.

```text
원본 비디오 다운로드
→ 트랜스코딩
```

DAG는 구성 파일을 기반으로 동적으로 생성할 수 있다.

### 3. 데이터 캐시

분할된 GOP와 메타데이터를 임시 저장소에 보관한다.

인코딩이 실패하더라도 저장된 데이터를 이용해 전체 업로드를 다시 시작하지 않고 실패한 작업만 재시도할 수 있다.

---

## 3.4.2 DAG 스케줄러

DAG 스케줄러는 DAG를 여러 단계로 나누고 각 단계의 작업을 자원 관리자의 작업 큐에 넣는다.

예시는 다음과 같다.

### 1단계

- 비디오 추출
- 오디오 추출
- 메타데이터 추출

### 2단계

- 비디오 인코딩
- 썸네일 생성
- 오디오 인코딩

선행 단계에 의존하지 않는 작업은 병렬로 수행할 수 있다.

---

## 3.4.3 자원 관리자

자원 관리자는 사용 가능한 작업 서버에 작업을 효율적으로 배정한다.

주요 구성은 다음과 같다.

### 작업 큐

실행할 작업을 우선순위에 따라 보관한다.

### 작업 서버 큐

각 작업 서버의 가용 상태를 보관한다.

### 실행 큐

현재 실행 중인 작업과 해당 작업을 수행하는 서버 정보를 보관한다.

### 작업 스케줄러

작업과 서버의 최적 조합을 선택하고 실행을 지시한다.

### 작업 할당 흐름

1. 작업 큐에서 가장 우선순위가 높은 작업을 선택한다.
2. 해당 작업을 수행할 수 있는 적절한 작업 서버를 찾는다.
3. 작업 서버에 실행을 지시한다.
4. 실행 정보를 실행 큐에 기록한다.
5. 작업이 완료되면 실행 큐에서 제거한다.

---

## 3.4.4 작업 서버

작업 서버는 DAG에 정의된 개별 작업을 수행한다.

작업 특성에 따라 서버를 분리할 수 있다.

- 비디오 인코딩 서버
- 오디오 인코딩 서버
- 썸네일 생성 서버
- 워터마크 처리 서버
- 결과 병합 서버

작업 유형별 서버 풀을 분리하면 특정 작업의 부하에 맞춰 독립적으로 확장할 수 있다.

---

## 3.4.5 임시 저장소

임시 저장소에는 트랜스코딩 도중 생성되는 중간 결과물을 저장한다.

어떤 저장 방식을 사용할지는 데이터의 크기, 종류, 사용 빈도, 유효기간에 따라 달라진다.

- 자주 참조하는 작은 메타데이터는 메모리에 캐시할 수 있다.
- 비디오와 오디오 중간 결과물은 BLOB 저장소에 보관하는 것이 적합하다.
- 처리가 완료된 임시 데이터는 삭제하여 비용을 줄인다.

---

## 3.4.6 인코딩된 비디오

인코딩된 비디오는 처리 파이프라인의 최종 결과물이다.

파일명에는 해상도나 코덱 정보를 포함할 수 있다.

```text
video_360p.mp4
video_720p.mp4
video_1080p.mp4
```

---

# 3.5 시스템 최적화

시스템은 속도, 안전성, 비용 측면에서 최적화할 수 있다.

---

## 3.5.1 속도 최적화: 비디오 병렬 업로드

하나의 비디오 전체를 한 번에 업로드하면 일부 구간에서 장애가 발생했을 때 전체 업로드를 다시 시작해야 할 수 있다.

비디오를 작은 GOP 단위로 분할하고 병렬 업로드하면 다음 장점이 있다.

- 여러 조각을 동시에 전송할 수 있다.
- 업로드 속도를 높일 수 있다.
- 일부 조각 전송에 실패해도 해당 조각만 재전송할 수 있다.
- 대용량 파일 업로드의 안정성이 높아진다.

---

## 3.5.2 속도 최적화: 사용자 근처의 업로드 센터

업로드 센터를 여러 지역에 배치하고 사용자를 가까운 업로드 센터로 연결하면 전송 지연을 줄일 수 있다.

예시는 다음과 같다.

- 북미 사용자 → 북미 업로드 센터
- 유럽 사용자 → 유럽 업로드 센터
- 아시아 사용자 → 아시아 업로드 센터
- 남미 사용자 → 남미 업로드 센터

CDN의 엣지 네트워크를 업로드 경로로 활용하는 방식도 고려할 수 있다.

---

## 3.5.3 속도 최적화: 단계 간 병렬화

각 처리 단계가 이전 단계 전체의 완료를 기다리는 구조에서는 지연이 커진다.

메시지 큐를 도입하면 앞 단계의 일부 결과가 준비되는 즉시 다음 단계가 처리할 수 있다.

```text
원본 저장소
→ 메시지 큐
→ 다운로드 모듈
→ 메시지 큐
→ 인코딩 모듈
→ 메시지 큐
→ 업로드 모듈
→ 결과 저장소
→ CDN
```

메시지 큐가 생산자와 소비자를 분리하므로 각 모듈을 독립적으로 확장할 수 있다.

---

## 3.5.4 안전성 최적화: 미리 서명된 업로드 URL

허가된 사용자만 올바른 위치에 비디오를 업로드할 수 있도록 미리 서명된 URL을 사용한다.

### 업로드 흐름

1. 클라이언트가 API 서버에 업로드 요청을 전송한다.
2. API 서버가 접근 권한이 포함된 미리 서명된 URL을 반환한다.
3. 클라이언트가 해당 URL을 사용해 BLOB 저장소에 비디오를 직접 업로드한다.

```text
클라이언트
→ API 서버: 업로드 URL 요청
← API 서버: 미리 서명된 URL
→ BLOB 저장소: 비디오 직접 업로드
```

이 방식의 장점은 다음과 같다.

- 인증되지 않은 사용자의 업로드를 차단할 수 있다.
- 대용량 파일이 API 서버를 통과하지 않는다.
- API 서버의 네트워크 부하를 줄일 수 있다.
- URL 만료 시간을 지정할 수 있다.

Amazon S3에서는 이를 Presigned URL이라 부르고, 다른 클라우드 환경에서는 다른 명칭을 사용할 수 있다.

---

## 3.5.5 안전성 최적화: 비디오 보호

콘텐츠 제작자의 저작권을 보호하기 위해 다음 기술을 적용할 수 있다.

### DRM

디지털 저작권 관리 시스템이다.

대표적인 예시는 다음과 같다.

- Apple FairPlay
- Google Widevine
- Microsoft PlayReady

### AES 암호화

비디오를 암호화하고 허가된 사용자에게만 복호화 키를 제공한다.

암호화된 비디오는 권한이 없는 사용자가 파일을 얻어도 바로 재생할 수 없다.

### 워터마크

소유자 정보, 사용자 식별 정보, 회사 로고 등을 영상 위에 삽입한다.

불법 복제물의 출처를 추적하거나 저작권 정보를 표시하는 데 활용한다.

---

## 3.5.6 비용 최적화

비디오 스트리밍 서비스의 CDN 비용은 매우 크다.

비디오 조회 수는 롱테일 분포를 따르므로 소수의 인기 비디오가 대부분의 트래픽을 차지한다.

이 특성을 이용해 다음과 같이 최적화할 수 있다.

### 인기 비디오만 CDN에 유지

인기 비디오는 CDN에 캐시하고, 조회가 적은 비디오는 원본 또는 비디오 서버에서 직접 전송한다.

### 비인기 비디오의 지연 인코딩

조회 가능성이 낮은 비디오는 모든 해상도로 미리 인코딩하지 않고, 실제 요청이 발생할 때 필요한 형식을 생성할 수 있다.

짧은 영상이라면 필요할 때 인코딩해도 사용자 지연이 크지 않을 수 있다.

### 지역별 인기도 활용

특정 지역에서만 인기 있는 콘텐츠는 다른 지역의 CDN에 미리 복제하지 않는다.

### 자체 CDN 및 ISP 제휴

초대형 서비스는 자체 CDN을 구축하거나 ISP와 직접 연결해 전송 비용을 낮추고 사용자 경험을 개선할 수 있다.

다만 구축과 운영 복잡도가 매우 크므로 일반적인 서비스에서는 상용 CDN을 이용하는 편이 현실적이다.

---

# 3.6 오류 처리

대규모 시스템에서 오류는 피할 수 없으므로, 오류 유형을 구분하고 복구 전략을 설계해야 한다.

## 3.6.1 오류 유형

### 회복 가능한 오류

일시적인 네트워크 장애나 특정 비디오 조각의 트랜스코딩 실패처럼 재시도로 해결될 수 있는 오류이다.

일정 횟수 재시도한 뒤에도 실패하면 클라이언트에 적절한 오류 코드를 반환한다.

### 회복 불가능한 오류

잘못된 비디오 포맷이나 심각하게 손상된 파일처럼 재시도로 해결할 수 없는 오류이다.

작업을 즉시 중단하고 클라이언트에 원인을 알린다.

---

## 3.6.2 구성 요소별 오류 처리

| 오류 상황 | 처리 방법 |
|---|---|
| 업로드 오류 | 일정 횟수 재시도 |
| 비디오 분할 오류 | 클라이언트가 분할하지 못하면 전체 비디오를 서버로 전송하고 서버에서 분할 |
| 트랜스코딩 오류 | 실패한 작업 재시도 |
| 전처리 오류 | DAG 그래프 재생성 |
| DAG 스케줄러 오류 | 작업을 다시 스케줄링 |
| 자원 관리자 큐 장애 | 복제본을 이용하여 복구 |
| 작업 서버 장애 | 다른 작업 서버에서 동일 작업 재시도 |
| API 서버 장애 | 무상태 서버이므로 로드 밸런서가 다른 API 서버로 우회 |
| 메타데이터 캐시 장애 | 다른 캐시 노드에서 데이터를 읽고 장애 노드는 교체 |
| 메타데이터 DB 주 서버 장애 | 부 서버 가운데 하나를 새 주 서버로 승격 |
| 메타데이터 DB 부 서버 장애 | 다른 부 서버로 읽기 요청을 처리하고 장애 서버 교체 |

---

# 4단계. 마무리

설계가 끝난 뒤 시간이 남으면 다음 주제를 추가로 논의할 수 있다.

## 4.1 API 계층의 확장성

API 서버는 무상태로 설계한다.

세션이나 중요한 상태를 서버 로컬에 저장하지 않으면 로드 밸런서 뒤에 서버를 추가하는 방식으로 수평 확장할 수 있다.

---

## 4.2 데이터베이스 계층의 확장성

메타데이터 데이터베이스에는 다음 기법을 적용할 수 있다.

- 복제
- 읽기 전용 부 서버
- 샤딩
- 장애 조치
- 캐시
- 인덱스 최적화

읽기와 쓰기 패턴, 데이터 분포, 일관성 요구사항을 고려해 구조를 결정해야 한다.

---

## 4.3 라이브 스트리밍

라이브 스트리밍도 비디오 업로드, 인코딩, CDN 전송이 필요하다는 점에서는 일반 비디오 서비스와 유사하다.

하지만 다음 차이가 있다.

### 낮은 응답 지연

녹화 영상보다 훨씬 낮은 지연시간을 요구한다.

따라서 스트리밍 프로토콜과 버퍼 크기를 세밀하게 조정해야 한다.

### 낮은 병렬화 가능성

실시간으로 생성되는 작은 데이터 조각을 즉시 처리해야 하므로 일반 업로드 영상처럼 전체 데이터를 자유롭게 병렬 처리하기 어렵다.

### 빠른 오류 처리

오류 복구에 오랜 시간이 걸리는 방식은 사용하기 어렵다.

실시간 시청 경험을 유지하도록 빠르게 우회하거나 품질을 낮춰야 한다.

---

## 4.4 비디오 삭제

다음과 같은 콘텐츠는 삭제 대상이 될 수 있다.

- 저작권을 침해한 비디오
- 선정적이거나 폭력적인 비디오
- 불법 행위와 관련된 비디오
- 서비스 정책을 위반한 비디오

삭제 대상은 업로드 과정에서 자동으로 탐지할 수도 있고, 사용자 신고나 관리자 검토를 통해 발견할 수도 있다.

---

# 핵심 설계 흐름

```text
[업로드]

클라이언트
→ API 서버에서 미리 서명된 URL 발급
→ 원본 BLOB 저장소에 직접 업로드
→ 전처리기가 GOP 분할 및 DAG 생성
→ DAG 스케줄러가 작업 단계 구성
→ 자원 관리자가 작업 서버에 할당
→ 작업 서버가 인코딩·썸네일·워터마크 처리
→ 결과 BLOB 저장소에 저장
→ CDN에 배포
→ 완료 큐를 통해 DB와 캐시 상태 갱신
```

```text
[재생]

클라이언트
→ API 서버에서 비디오 메타데이터와 재생 정보 조회
→ 가까운 CDN 엣지 서버에 스트리밍 요청
→ 네트워크 상태와 단말에 맞는 화질로 재생
```

---

# 면접에서 강조할 핵심 포인트

- 처음부터 유튜브의 모든 기능을 설계하지 않고 업로드와 재생으로 범위를 좁힌다.
- 저장소와 CDN은 직접 구현하기보다 기존 클라우드 서비스를 활용할 수 있다.
- 대용량 비디오가 API 서버를 거치지 않도록 미리 서명된 URL을 사용한다.
- 비디오를 GOP 단위로 나눠 업로드와 트랜스코딩을 병렬화한다.
- DAG를 이용해 비디오 처리 작업의 의존성과 병렬성을 표현한다.
- 메시지 큐를 이용해 각 처리 모듈을 느슨하게 결합한다.
- 여러 해상도와 비트레이트를 생성해 적응형 스트리밍을 지원한다.
- 인기 콘텐츠는 CDN에 캐시하고 비인기 콘텐츠는 필요에 따라 처리해 비용을 줄인다.
- API 서버는 무상태로 설계하여 수평 확장과 장애 우회를 쉽게 한다.
- 처리 중간 데이터를 임시 저장하여 일부 작업 실패 시 전체 과정을 다시 수행하지 않는다.
- 오류를 회복 가능한 오류와 회복 불가능한 오류로 나눠 처리한다.
- DRM, AES 암호화, 워터마크로 콘텐츠를 보호한다.

# 용어 정리

| 용어 | 설명 |
|---|---|
| BLOB 저장소 | 비디오와 같은 대용량 이진 객체를 저장하는 시스템 |
| CDN | 사용자와 가까운 엣지 서버에서 콘텐츠를 전달하는 네트워크 |
| 트랜스코딩 | 비디오를 다른 코덱, 포맷, 해상도, 비트레이트로 변환하는 과정 |
| 컨테이너 | 비디오, 오디오, 메타데이터를 담는 파일 형식 |
| 코덱 | 비디오 데이터를 압축하고 해제하는 알고리즘 |
| GOP | 독립적으로 처리 가능한 연속 프레임 그룹 |
| DAG | 순환 없이 작업 의존성을 표현하는 방향 그래프 |
| Presigned URL | 제한된 시간 동안 특정 객체에 접근할 권한을 포함한 URL |
| 적응형 스트리밍 | 네트워크 상황에 따라 재생 화질을 자동 변경하는 방식 |
| 롱테일 분포 | 소수의 인기 콘텐츠가 대부분의 트래픽을 차지하는 분포 |
| DRM | 디지털 콘텐츠의 접근과 사용 권한을 제어하는 기술 |
