# 뉴스 피드 시스템에서 일관성은 어디까지 보장해야 할까?

## 발표 주제

뉴스 피드 시스템에서 강한 일관성과 최종 일관성을 어떻게 구분해서 적용할 것인지에 대한 내용이다.

책에서는 뉴스 피드 시스템의 발행, 읽기, 캐시, 메시지 큐, 팬아웃 구조를 설명한다. 하지만 실제 서비스에서는 단순히 빠르게 피드를 보여주는 것뿐 아니라, 데이터가 언제 어떻게 최신 상태가 되는지에 대한 일관성 문제도 중요하다.

이번 발표에서는 뉴스 피드 시스템에서 어떤 데이터는 잠깐 늦게 반영되어도 되는지, 어떤 데이터는 반드시 읽기 시점에 검증해야 하는지를 중심으로 정리해 보았다.

---

# 1. 책 내용과의 연결

책에서 설명하는 뉴스 피드 시스템은 크게 두 흐름으로 나뉜다.

## 1.1 피드 발행 흐름

사용자가 새 게시글을 작성하면 게시글이 저장되고, 해당 게시글 ID가 친구들의 뉴스 피드 캐시에 전달된다.

```
사용자 게시글 작성
→ 웹 서버
→ 포스팅 저장 서비스
→ 포스팅 DB / 포스팅 캐시 저장
→ 포스팅 전송 서비스
→ 메시지 큐
→ 팬아웃 작업 서버
→ 친구들의 뉴스 피드 캐시에 post_id 저장
```

이 구조에서는 사용자가 글을 작성하는 즉시 모든 친구의 피드가 동시에 갱신되는 것은 아니다. 팬아웃 작업이 메시지 큐와 작업 서버를 거쳐 비동기로 처리되기 때문이다.

즉, 게시글 원본 데이터와 각 사용자의 뉴스 피드 캐시 사이에 일시적인 불일치가 발생할 수 있다.

## 1.2 피드 읽기 흐름

사용자가 뉴스 피드를 조회하면 뉴스 피드 서비스는 캐시에서 `post_id` 목록을 가져오고, 포스팅 캐시와 사용자 정보 캐시를 조회하여 최종 응답을 만든다.

```
사용자 피드 조회
→ 웹 서버
→ 뉴스 피드 서비스
→ 뉴스 피드 캐시에서 post_id 목록 조회
→ 포스팅 캐시 / 사용자 정보 캐시 조회
→ JSON 응답
→ 클라이언트 렌더링
```

이때 뉴스 피드 캐시가 항상 최신 상태라는 보장은 없다. 따라서 뉴스 피드 시스템에서는 빠른 응답성과 데이터 정합성 사이의 균형이 중요하다.

---

# 2. 핵심 문제

> 친구가 글을 올렸는데 내 피드에 3초 늦게 뜨면 장애인가?
>

이 질문에 대한 답은 상황에 따라 다르다.

뉴스 피드는 결제, 계좌 이체, 재고 차감처럼 즉각적인 정확성이 필수인 시스템과 다르다. 친구의 새 글이 몇 초 늦게 보이는 것은 대부분 허용 가능하다.

하지만 삭제된 게시글, 비공개 게시글, 차단한 사용자의 게시글이 보이는 것은 단순한 지연 문제가 아니다. 이는 권한 문제이자 사용자 신뢰 문제이다.

따라서 뉴스 피드 시스템에서는 모든 데이터에 같은 수준의 일관성을 적용하는 것이 아니라, 데이터의 성격에 따라 다른 일관성 전략을 적용해야 한다.

---

# 3. 일관성 모델 개념

## 3.1 강한 일관성

강한 일관성은 데이터를 쓰자마자 모든 사용자가 즉시 같은 최신 데이터를 볼 수 있는 모델이다.

예를 들어 A가 게시글을 삭제했다면, 그 직후 어떤 사용자도 해당 게시글을 볼 수 없어야 한다.

```
게시글 삭제
→ 즉시 모든 피드에서 삭제 반영
→ 모든 사용자가 같은 상태 확인
```

강한 일관성은 정확성이 매우 중요할 때 필요하다. 하지만 대규모 시스템에서는 모든 캐시와 데이터 저장소를 즉시 동기화해야 하므로 비용이 크고 지연 시간이 늘어날 수 있다.

## 3.2 최종 일관성

최종 일관성은 당장은 데이터가 조금 다르게 보일 수 있지만, 시간이 지나면 결국 같은 상태로 수렴하는 모델이다.

예를 들어 친구가 글을 올렸을 때, 어떤 사용자의 피드에는 바로 보이고 어떤 사용자의 피드에는 몇 초 뒤에 보일 수 있다.

```
게시글 작성
→ 일부 사용자 피드에 먼저 반영
→ 팬아웃 작업 진행
→ 시간이 지나면 모든 대상자의 피드에 반영
```

최종 일관성은 빠른 응답과 확장성을 얻기 위해 많이 사용된다. 뉴스 피드, 좋아요 수, 조회수, 알림처럼 약간의 지연이 허용되는 기능에 적합하다.

# 4. 뉴스 피드에서 발생하는 일관성 문제

뉴스 피드 시스템에서는 원본 데이터와 캐시 데이터가 분리되어 있다. 이 때문에 여러 상황에서 불일치가 발생할 수 있다.

## 4.1 새 게시글 반영 지연

사용자가 글을 작성했지만, 친구들의 피드 캐시에 아직 반영되지 않은 상태이다.

```
A가 게시글 작성
→ Post DB에는 저장됨
→ 메시지 큐에 fanout job 추가됨
→ 아직 B의 feed cache에는 반영되지 않음
```

이 경우 B는 잠시 동안 A의 새 게시글을 볼 수 없다.

이 문제는 대부분 최종 일관성으로 처리할 수 있다. 친구의 글이 몇 초 늦게 보이는 것은 일반적으로 치명적인 문제가 아니기 때문이다.

## 4.2 좋아요 수 불일치

좋아요 수는 여러 사용자가 동시에 변경할 수 있는 데이터이다.

```
사용자 1이 좋아요 클릭
사용자 2가 좋아요 클릭
사용자 3이 좋아요 취소
```

이 경우 캐시, DB, 화면에 보이는 좋아요 수가 잠시 다를 수 있다.

좋아요 수는 실시간으로 완벽히 일치하지 않아도 되는 경우가 많다. 따라서 최종 일관성을 적용하기 적합하다.

## 4.3 알림 지연

사용자가 게시글을 올렸을 때 친구에게 알림이 몇 초 늦게 도착할 수 있다.

알림은 사용자 경험에 영향을 주지만, 대부분의 경우 즉시 도착해야만 하는 데이터는 아니다. 따라서 메시지 큐를 통해 비동기로 처리할 수 있다.

## 4.4 삭제된 게시글 노출

사용자가 게시글을 삭제했는데, 이미 친구들의 뉴스 피드 캐시에 해당 `post_id`가 남아 있을 수 있다.

```
feed:userB = [post100, post91, post80]

post100은 이미 삭제됨
하지만 feed cache에는 post100이 남아 있음
```

이 경우 피드를 읽을 때 삭제된 게시글이 보일 수 있다. 이 문제는 단순한 지연으로 보기 어렵다.

삭제된 게시글은 사용자에게 보이면 안 되므로, 읽기 시점에 게시글 상태를 검증해야 한다.

## 4.5 공개 범위 변경

사용자가 게시글 공개 범위를 “친구 전체”에서 “나만 보기”로 바꾼 경우가 있다.

이미 친구들의 피드 캐시에 해당 게시글 ID가 들어가 있다면, 공개 범위 변경 후에도 피드에 남아 있을 수 있다.

```
기존 상태: FRIENDS
변경 상태: PRIVATE

친구 피드 캐시에는 여전히 post_id 존재
```

이 경우 단순히 피드 캐시만 믿고 응답하면 안 된다. 게시글의 현재 공개 범위를 확인한 뒤 보여줄지 결정해야 한다.

## 4.6 차단 관계 변경

사용자가 특정 사용자를 차단한 경우, 차단한 사용자와 차단당한 사용자 사이의 피드 노출 규칙이 달라져야 한다.

차단은 권한과 프라이버시 문제에 가깝다. 따라서 차단 관계는 피드 읽기 시점에 검증하는 것이 안전하다.

# 5. 뉴스 피드에서 최종 일관성이 허용되는 데이터

뉴스 피드 시스템의 모든 데이터에 강한 일관성을 적용하면 성능과 확장성이 떨어진다. 따라서 다음과 같은 데이터는 최종 일관성을 허용할 수 있다.

## 5.1 새 게시글의 피드 반영

친구가 새 글을 올렸을 때 내 피드에 몇 초 늦게 뜨는 것은 대부분 허용 가능하다.

```
허용 가능 예시:
친구가 10:00:00에 글 작성
내 피드에는 10:00:03에 반영
```

## 5.2 좋아요 수

좋아요 수가 잠깐 다르게 보이는 것은 일반적으로 허용 가능하다.

```
사용자 A 화면: 좋아요 101개
사용자 B 화면: 좋아요 102개
몇 초 뒤 102개로 수렴
```

## 5.3 댓글 수

댓글 목록 자체는 비교적 정확해야 하지만, 댓글 수 카운터는 잠깐 다를 수 있다.

```
댓글 목록에는 댓글 10개
댓글 수 표시는 9개
잠시 후 10개로 반영
```

## 5.4 알림

알림은 몇 초 정도 지연되어도 대체로 허용 가능하다.

```
게시글 작성
→ 알림 이벤트 발행
→ 메시지 큐 적재
→ 알림 서버 처리
→ 푸시 알림 전송
```

---

# 6. 강한 검증이 필요한 데이터

반대로 다음 데이터는 단순히 최종 일관성에만 맡기기 어렵다.

## 6.1 삭제된 게시글

삭제된 게시글은 사용자 피드에 노출되면 안 된다.

따라서 피드 캐시에 `post_id`가 남아 있더라도, 피드 응답을 만들기 전에 게시글 상태를 확인해야 한다.

## 6.2 비공개 게시글

게시글의 공개 범위가 `PRIVATE`로 바뀐 경우, 다른 사용자에게 노출되면 안 된다.

공개 범위는 캐시된 피드 목록보다 원본 게시글의 현재 상태를 기준으로 판단해야 한다.

## 6.3 차단 관계

차단 관계는 사용자 프라이버시와 직접 연결된다.

따라서 캐시에 과거 데이터가 남아 있더라도, 피드 조회 시 현재 차단 관계를 확인해야 한다.

## 6.4 신고 또는 숨김 처리된 게시글

운영 정책상 숨김 처리된 게시글은 피드에서 제외되어야 한다.

이런 게시글은 캐시에 남아 있더라도 응답 단계에서 걸러야 한다.

# 7. 직접 설계안: 빠른 피드 조회와 권한 검증을 함께 적용하기

뉴스 피드 시스템에서는 속도와 정합성을 모두 고려해야 한다. 이를 위해 다음과 같은 혼합 설계를 사용할 수 있다.

## 7.1 Feed Cache

뉴스 피드 캐시는 사용자별로 보여줄 게시글 ID 목록을 저장한다.

```
key: feed:{user_id}
value: post_id 목록
```

예시는 다음과 같다.

```
feed:user123 = [post901, post887, post855, post801]
```

이 캐시는 빠른 피드 조회를 위한 것이다. 게시글 본문 전체를 저장하지 않고, 어떤 게시글을 보여줄지 결정하는 ID 목록만 저장한다.

## 7.2 Post DB 또는 Post Cache

게시글 원본 데이터는 별도로 저장한다.

```
Post
- post_id
- author_id
- content
- status
- visibility
- created_at
```

여기서 `status`는 게시글이 정상인지, 삭제되었는지, 숨김 처리되었는지를 나타낸다.

`visibility`는 공개 범위를 나타낸다.

```
visibility 예시:
- PUBLIC
- FRIENDS
- PRIVATE
```

## 7.3 Block Table

차단 관계는 별도의 저장소에서 관리한다.

```
Block
- blocker_id
- blocked_id
```

피드 조회 시 작성자와 조회자 사이의 차단 관계를 확인한다.

## 7.4 Read-time Validation

사용자가 피드를 조회할 때, 뉴스 피드 캐시에서 가져온 `post_id` 목록을 그대로 응답하지 않는다.

반드시 게시글 상태와 권한을 한 번 더 검증한다.

```
1. feed:{user_id}에서 post_id 목록 조회
2. post_id에 해당하는 게시글 정보 조회
3. 게시글 status 확인
4. visibility 확인
5. 차단 관계 확인
6. 볼 수 없는 게시글 제거
7. 남은 게시글만 응답
```

이 방식은 피드 캐시의 빠른 조회 장점은 유지하면서도, 삭제·비공개·차단 같은 민감한 문제를 방지할 수 있다.

# 8. 해결 전략 비교

## 8.1 모든 캐시를 즉시 갱신하는 방식

게시글이 삭제되거나 비공개로 바뀌면, 해당 게시글이 들어간 모든 사용자의 피드 캐시에서 즉시 제거하는 방식이다.

### 장점

피드 캐시가 항상 깨끗하게 유지된다.

피드 읽기 시점의 검증 부담이 줄어든다.

### 단점

비용이 크다.

팔로워가 많은 사용자의 게시글이라면 수십만 개 이상의 피드 캐시를 수정해야 할 수 있다.

삭제 요청 하나가 대규모 팬아웃 작업이 될 수 있다.

## 8.2 읽기 시점에 검증하는 방식

피드 캐시에 오래된 `post_id`가 남아 있더라도, 사용자가 피드를 읽는 시점에 게시글 상태와 권한을 확인하는 방식이다.

### 장점

쓰기나 삭제 시점의 비용이 작다.

대규모 캐시 갱신 작업을 줄일 수 있다.

권한 검증을 현재 상태 기준으로 수행할 수 있다.

### 단점

피드 읽기 시점에 추가 조회가 필요하다.

삭제된 게시글이 캐시에 계속 남아 있을 수 있다.

필터링 후 보여줄 게시글 수가 부족하면 추가로 더 많은 `post_id`를 가져와야 한다.

## 8.3 혼합 방식

실제 시스템에서는 두 방식을 혼합하는 것이 적절하다.

```
일반적인 새 게시글 반영
→ 최종 일관성 허용

좋아요 수, 댓글 수, 알림
→ 최종 일관성 허용

삭제, 비공개, 차단, 신고
→ 읽기 시점 검증 적용

팔로워 수가 적은 사용자
→ 적극적 캐시 삭제 가능

팔로워 수가 많은 사용자
→ 읽기 시점 검증 중심
```

# 9. 피드 조회 흐름 예시

## 9.1 일반적인 피드 조회

```
사용자 B가 피드 조회
→ feed:B에서 post_id 50개 조회
→ Post Cache에서 게시글 정보 조회
→ User Cache에서 작성자 정보 조회
→ 최종 피드 응답
```

## 9.2 권한 검증이 포함된 피드 조회

```
사용자 B가 피드 조회
→ feed:B에서 post_id 50개 조회
→ 각 post_id의 status 확인
→ 삭제된 게시글 제거
→ visibility 확인
→ B가 볼 수 없는 게시글 제거
→ 차단 관계 확인
→ 차단된 작성자의 게시글 제거
→ 부족하면 다음 post_id batch 조회
→ 최종 피드 응답
```

이 구조에서는 피드 캐시가 완벽히 최신 상태가 아니어도, 최종 응답 단계에서 잘못된 게시글 노출을 줄일 수 있다.

# 10. 상황별 일관성 전략 정리

| 상황 | 허용 가능한 일관성 수준 | 이유 |
| --- | --- | --- |
| 친구의 새 게시글 반영 | 최종 일관성 | 몇 초 지연은 허용 가능 |
| 좋아요 수 반영 | 최종 일관성 | 카운터 값의 일시적 오차는 허용 가능 |
| 댓글 수 반영 | 최종 일관성 | 화면 표시용 카운터는 약간의 지연 허용 가능 |
| 알림 전송 | 최종 일관성 | 약간 늦게 도착해도 치명적이지 않음 |
| 게시글 삭제 | 강한 검증 필요 | 삭제된 글이 보이면 안 됨 |
| 공개 범위 변경 | 강한 검증 필요 | 볼 수 없는 사용자에게 노출되면 안 됨 |
| 차단 관계 변경 | 강한 검증 필요 | 프라이버시 문제와 연결됨 |
| 신고로 인한 숨김 | 강한 검증 필요 | 정책 위반 콘텐츠 노출 방지 필요 |
