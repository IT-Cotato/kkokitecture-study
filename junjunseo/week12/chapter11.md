# 11장 뉴스 피드 시스템 설계

뉴스 피드 시스템은 사용자의 홈 화면 중앙에 지속적으로 업데이트되는 스토리 흐름을 제공하는 시스템이다. 사용자의 상태 업데이트, 사진, 비디오, 링크, 앱 활동, 팔로우한 사람·페이지·그룹의 좋아요 등이 피드에 포함될 수 있다.

비슷한 유형의 시스템으로는 페이스북 뉴스 피드, 인스타그램 피드, 트위터 타임라인 등이 있다.

---

# 1단계 문제 이해 및 설계 범위 확정

시스템 설계를 시작하기 전에 면접관 또는 요구사항 제공자와 질문을 통해 범위를 명확히 해야 한다. 뉴스 피드 시스템은 요구사항에 따라 설계 방향이 크게 달라질 수 있으므로, 먼저 기능 범위와 트래픽 규모를 확인해야 한다.

## 요구사항 확인

### 지원 플랫폼

모바일 앱과 웹 브라우저를 모두 지원하는 시스템으로 가정한다.

### 핵심 기능

사용자는 뉴스 피드 페이지에 새 스토리를 올릴 수 있어야 한다. 또한 친구들이 올린 스토리를 볼 수 있어야 한다.

### 피드 정렬 기준

뉴스 피드는 단순히 시간 역순, 즉 최신 포스트가 위에 오는 방식으로 표시된다고 가정한다. 토픽 점수, 친밀도, 추천 점수 등의 랭킹 알고리즘은 이번 설계 범위에서 제외한다.

### 사용자당 친구 수

한 명의 사용자는 최대 5,000명의 친구를 가질 수 있다고 가정한다.

### 트래픽 규모

매일 천만 명의 사용자가 방문하는 서비스, 즉 10 million DAU 규모로 가정한다.

### 미디어 포함 여부

스토리에는 텍스트뿐 아니라 이미지와 비디오 같은 미디어 파일도 포함될 수 있다.

---

# 2단계 개략적 설계안 제시 및 동의 구하기

뉴스 피드 시스템은 크게 두 부분으로 나뉜다.

## 피드 발행

피드 발행은 사용자가 새 포스트를 작성했을 때 해당 데이터를 저장하고, 친구들의 뉴스 피드에도 반영하는 과정이다.

사용자가 새 스토리를 포스팅하면 포스팅 데이터가 캐시와 데이터베이스에 기록된다. 이후 새 포스트는 친구들의 뉴스 피드에도 전달된다.

## 뉴스 피드 생성

뉴스 피드 생성은 사용자가 자신의 뉴스 피드를 읽을 때 필요한 스토리 목록을 구성하는 과정이다.

이번 설계에서는 지인 관계가 있는 모든 친구의 포스트를 시간 역순으로 모아 뉴스 피드를 만든다고 가정한다.

---

# 뉴스 피드 API

뉴스 피드 API는 클라이언트가 서버와 통신하기 위한 HTTP 기반 인터페이스이다. 상태 업데이트, 뉴스 피드 읽기, 친구 추가 등의 기능을 수행할 수 있다.

이번 설계에서는 핵심 API 두 가지를 중심으로 다룬다.

---

## 피드 발행 API

새 스토리를 포스팅하기 위한 API이다.

```
POST /v1/me/feed
```

### 인자

- `body`: 포스팅 내용
- `Authorization` 헤더: API 호출 인증에 사용

---

## 피드 읽기 API

뉴스 피드를 가져오기 위한 API이다.

```
GET /v1/me/feed
```

### 인자

- `Authorization` 헤더: API 호출 인증에 사용

---

# 피드 발행

피드 발행 시스템의 개략적인 구조는 다음과 같다.

```
사용자
  ↓
로드밸런서
  ↓
웹 서버
  ↓
포스팅 저장 서비스
  ↓
포스팅 캐시 / 포스팅 데이터베이스

웹 서버
  ↓
포스팅 전송 서비스
  ↓
뉴스 피드 캐시

웹 서버
  ↓
알림 서비스
```

## 주요 컴포넌트

### 사용자

모바일 앱이나 웹 브라우저에서 새 포스트를 작성하는 주체이다. 사용자는 `POST /v1/me/feed` API를 호출한다.

### 로드밸런서

클라이언트 요청을 여러 웹 서버로 분산한다.

### 웹 서버

HTTP 요청을 내부 서비스로 중계한다. 인증, 처리율 제한 등의 역할도 수행한다.

### 포스팅 저장 서비스

새 포스팅을 데이터베이스와 캐시에 저장한다.

### 포스팅 전송 서비스

새 포스팅을 친구들의 뉴스 피드로 전달한다. 이 과정을 팬아웃이라고 한다.

### 알림 서비스

친구들에게 새 포스팅이 올라왔음을 알리거나 푸시 알림을 전송한다.

---

# 뉴스 피드 생성

뉴스 피드 생성 시스템의 개략적인 구조는 다음과 같다.

```
사용자
  ↓
로드밸런서
  ↓
웹 서버
  ↓
뉴스 피드 서비스
  ↓
뉴스 피드 캐시
```

## 주요 컴포넌트

### 사용자

뉴스 피드를 읽는 주체이다. 사용자는 `GET /v1/me/feed` API를 호출한다.

### 로드밸런서

요청을 여러 웹 서버로 분산한다.

### 웹 서버

트래픽을 뉴스 피드 서비스로 전달한다.

### 뉴스 피드 서비스

캐시에서 뉴스 피드를 가져오는 서비스이다.

### 뉴스 피드 캐시

뉴스 피드를 렌더링할 때 필요한 피드 ID 목록을 보관한다.

---

# 3단계 상세 설계

상세 설계에서는 피드 발행 흐름과 피드 읽기 흐름을 더 구체적으로 살펴본다.

---

# 피드 발행 흐름 상세 설계

피드 발행 흐름은 사용자가 새 포스트를 작성했을 때 해당 포스트를 저장하고, 친구들의 피드에 반영하는 과정이다.

## 웹 서버

웹 서버는 클라이언트와 직접 통신할 뿐 아니라 인증과 처리율 제한도 수행한다.

### 인증

올바른 인증 토큰을 `Authorization` 헤더에 넣어 API를 호출한 사용자만 포스팅할 수 있어야 한다.

### 처리율 제한

스팸이나 악의적인 콘텐츠가 반복적으로 올라오는 것을 막기 위해 특정 기간 동안 한 사용자가 올릴 수 있는 포스팅 수에 제한을 둔다.

---

# 포스팅 전송 서비스

포스팅 전송, 즉 팬아웃은 한 사용자의 새 포스팅을 친구 관계에 있는 모든 사용자에게 전달하는 과정이다.

팬아웃에는 크게 두 가지 모델이 있다.

## 쓰기 시점 팬아웃

쓰기 시점 팬아웃은 새 포스팅이 작성되는 순간 친구들의 뉴스 피드를 갱신하는 방식이다. 푸시 모델이라고도 부른다.

포스팅이 완료되면 바로 해당 사용자의 친구들의 뉴스 피드 캐시에 포스트 ID를 기록한다.

### 장점

뉴스 피드가 거의 실시간으로 갱신된다.

뉴스 피드가 미리 계산되어 있기 때문에 사용자가 피드를 읽을 때 지연 시간이 짧다.

### 단점

친구나 팔로워가 매우 많은 사용자가 포스팅할 경우, 많은 사용자의 피드를 동시에 갱신해야 한다. 이때 특정 사용자나 키에 부하가 집중되는 핫키 문제가 발생할 수 있다.

서비스를 자주 사용하지 않는 사용자의 피드까지 미리 갱신해야 하므로 컴퓨팅 자원이 낭비될 수 있다.

---

## 읽기 시점 팬아웃

읽기 시점 팬아웃은 사용자가 뉴스 피드를 읽는 시점에 피드를 생성하거나 갱신하는 방식이다. 풀 모델이라고도 부른다.

사용자가 본인 홈페이지나 타임라인을 로딩하는 시점에 새로운 포스트를 가져온다.

### 장점

비활성 사용자나 거의 로그인하지 않는 사용자에게 유리하다. 로그인하기 전까지는 피드를 계산하지 않아도 되므로 자원을 절약할 수 있다.

각 친구에게 데이터를 미리 푸시하는 작업이 필요 없으므로 쓰기 시점의 대규모 팬아웃 부담을 줄일 수 있다.

### 단점

뉴스 피드를 읽을 때 많은 데이터를 조회하고 조합해야 하므로 읽기 지연 시간이 길어질 수 있다.

---

# 팬아웃 전략 선택

이 설계에서는 쓰기 시점 팬아웃과 읽기 시점 팬아웃을 함께 사용하는 혼합 전략을 선택한다.

대부분의 사용자에게는 뉴스 피드를 빠르게 제공하는 것이 중요하므로 쓰기 시점 팬아웃을 사용한다.

하지만 친구나 팔로워가 매우 많은 사용자의 경우에는 쓰기 시점 팬아웃을 사용하면 시스템 부하가 커진다. 따라서 유명인이나 팔로워가 많은 사용자의 포스트는 읽기 시점에 가져오는 풀 모델을 사용한다.

또한 안정 해시를 사용해 요청과 데이터를 고르게 분산함으로써 핫키 문제를 완화한다.

---

# 팬아웃 서비스 동작 흐름

팬아웃 서비스는 다음 순서로 동작한다.

## 1. 친구 ID 목록 조회

그래프 데이터베이스에서 사용자의 친구 ID 목록을 가져온다.

그래프 데이터베이스는 친구 관계나 친구 추천처럼 관계 중심 데이터를 관리하기에 적합하다.

## 2. 친구 정보 조회 및 필터링

사용자 정보 캐시에서 친구들의 정보를 가져온다.

이후 사용자의 설정에 따라 일부 친구를 제외한다. 예를 들어 어떤 친구의 피드 업데이트를 무시하도록 설정한 경우, 해당 친구 관계는 유지되지만 새 포스팅은 뉴스 피드에 반영하지 않는다.

또한 새 포스팅을 모든 친구에게 공개하지 않도록 설정한 경우에도 일부 사용자는 대상에서 제외된다.

## 3. 메시지 큐에 작업 추가

친구 목록과 새 스토리의 포스팅 ID를 메시지 큐에 넣는다.

## 4. 팬아웃 작업 서버 처리

팬아웃 작업 서버가 메시지 큐에서 데이터를 꺼낸다.

이후 뉴스 피드 데이터를 뉴스 피드 캐시에 저장한다.

뉴스 피드 캐시는 `post_id`와 `user_id`의 순서쌍을 보관하는 매핑 테이블처럼 볼 수 있다.

```
post_id → user_id
post_id → user_id
post_id → user_id
```

이 캐시는 사용자 정보와 포스팅 정보 전체를 저장하지 않는다. 캐시 크기를 적정 수준으로 유지하기 위해 포스트 ID만 보관한다.

대부분의 사용자는 최신 스토리만 확인하므로, 어떤 사용자의 뉴스 피드에 올라온 모든 스토리를 전부 보관할 필요는 낮다.

---

# 피드 읽기 흐름 상세 설계

뉴스 피드를 읽는 과정은 사용자가 자신의 피드를 요청하고, 서버가 필요한 데이터를 모아 최종 피드를 구성하는 과정이다.

## 전체 흐름

```
사용자
  ↓
로드밸런서
  ↓
웹 서버
  ↓
뉴스 피드 서비스
  ↓
뉴스 피드 캐시
  ↓
사용자 정보 캐시 / 포스팅 캐시
  ↓
JSON 응답
  ↓
클라이언트 렌더링
```

## 단계별 흐름

### 1. 뉴스 피드 요청

사용자가 뉴스 피드를 읽기 위해 요청을 보낸다.

```
GET /v1/me/feed
```

### 2. 로드밸런서 전달

로드밸런서가 요청을 여러 웹 서버 중 하나로 보낸다.

### 3. 웹 서버 처리

웹 서버는 피드를 가져오기 위해 뉴스 피드 서비스를 호출한다.

### 4. 피드 ID 목록 조회

뉴스 피드 서비스는 뉴스 피드 캐시에서 포스팅 ID 목록을 가져온다.

### 5. 필요한 데이터 조합

뉴스 피드에 표시할 사용자 이름, 사용자 사진, 포스팅 콘텐츠, 이미지 등을 사용자 정보 캐시와 포스팅 캐시에서 가져온다.

미디어 파일은 빠르게 읽을 수 있도록 CDN에 저장한다.

### 6. 응답 및 렌더링

생성된 뉴스 피드를 JSON 형태로 클라이언트에 보낸다.

클라이언트는 전달받은 데이터를 화면에 렌더링한다.

---

# 캐시 구조

캐시는 뉴스 피드 시스템의 핵심 컴포넌트이다. 이 설계에서는 캐시를 다섯 계층으로 나눈다.

```
뉴스 피드
콘텐츠
소셜 그래프
행동
횟수
```

## 뉴스 피드 캐시

뉴스 피드의 ID 목록을 보관한다.

피드 화면을 만들 때 어떤 포스트를 보여줄지 결정하는 데 사용된다.

## 콘텐츠 캐시

포스팅 데이터를 보관한다.

일반 콘텐츠와 인기 콘텐츠를 구분하여 저장할 수 있다. 인기 콘텐츠는 접근 빈도가 높으므로 별도로 관리한다.

## 소셜 그래프 캐시

사용자 간 관계 정보를 보관한다.

팔로어, 팔로잉, 친구 관계 등의 정보를 빠르게 조회하기 위해 사용한다.

## 행동 캐시

포스팅에 대한 사용자의 행위 정보를 보관한다.

예를 들어 좋아요, 답글, 기타 상호작용 정보가 여기에 해당한다.

## 횟수 캐시

카운터 정보를 보관한다.

좋아요 수, 답글 수, 팔로어 수, 팔로잉 수 등이 여기에 해당한다.

# 4단계 마무리

뉴스 피드 시스템 설계에는 정답이 하나만 존재하지 않는다. 회사마다 요구사항, 제약 조건, 트래픽 특성이 다르기 때문에 설계 방식도 달라진다.

중요한 것은 특정 기술을 선택한 이유와 그 선택에 따른 트레이드오프를 설명할 수 있는 것이다.

# 추가로 논의할 수 있는 주제

## 데이터베이스 규모 확장

### 수직적 규모 확장과 수평적 규모 확장

서버 성능을 높이는 방식과 서버 수를 늘리는 방식의 차이를 논의할 수 있다.

### SQL vs NoSQL

관계형 데이터베이스와 NoSQL 데이터베이스 중 어떤 상황에서 어떤 선택이 적합한지 논의할 수 있다.

### 주-부 다중화

마스터-슬레이브 구조를 통해 쓰기와 읽기 부하를 분산하는 방식을 논의할 수 있다.

### 복제본에 대한 읽기 연산

읽기 복제본을 활용해 읽기 트래픽을 분산하는 방식을 논의할 수 있다.

### 일관성 모델

강한 일관성, 최종 일관성 등 데이터 일관성 수준을 어떻게 선택할지 논의할 수 있다.

### 데이터베이스 샤딩

데이터를 여러 샤드로 나누어 저장하는 방식과 샤딩 키 선택 문제를 논의할 수 있다.

## 기타 시스템 설계 주제

### 웹 계층 무상태 운영

웹 서버가 세션 상태를 직접 저장하지 않도록 설계하면 서버 확장과 장애 대응이 쉬워진다.

### 가능한 많은 데이터 캐싱

자주 접근하는 데이터는 캐시에 저장해 응답 속도를 높이고 데이터베이스 부하를 줄인다.

### 여러 데이터 센터 지원

서비스 가용성과 지연 시간 감소를 위해 여러 데이터 센터 또는 리전을 활용하는 방법을 논의할 수 있다.

### 메시지 큐를 통한 결합도 감소

컴포넌트 사이에 메시지 큐를 두면 서비스 간 결합도를 낮추고 비동기 처리를 쉽게 할 수 있다.

### 핵심 지표 모니터링

트래픽이 몰리는 시간대의 QPS, 사용자가 뉴스 피드를 새로고침할 때의 지연 시간 등을 모니터링해야 한다.
