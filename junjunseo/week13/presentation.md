# 13주차 발표자료: Discord는 어떻게 수조 개 메시지를 저장했는가

## 발표 주제

**Discord 메시지 저장소 진화: MongoDB에서 Cassandra, 그리고 ScyllaDB까지**

책에서는 채팅 시스템의 채팅 이력을 키-값 저장소에 저장하는 설계를 제안한다. 이 발표는 그 설계가 실무에서 어떻게 구체화되고, 어떤 문제를 만나며, 어떻게 다시 진화했는지 Discord 사례로 설명하는 내용이다.

> 채팅 이력은 키-값 저장소에 저장하면 끝인가?
>

결론은 아니다. 키-값 저장소를 골라도 데이터 모델, 메시지 ID, 파티션 크기, hot partition, 삭제 데이터, 마이그레이션 전략까지 함께 설계해야 한다.

## 1. 책 내용과 연결

책의 채팅 시스템 설계에서는 채팅 이력 저장소로 키-값 저장소를 추천한다.

이유는 다음과 같다.

- 채팅 메시지 데이터가 매우 크다.
- 대부분의 조회가 최근 메시지 중심이다.
- 특정 채널이나 대화방 단위로 메시지를 읽는다.
- 메시지 쓰기와 읽기가 모두 많다.
- 수평 확장이 필요하다.

즉, 채팅 이력은 단순한 게시글 테이블이 아니라 계속 커지는 append-heavy 데이터이다. 따라서 관계형 데이터베이스의 범용 쿼리 능력보다, 특정 접근 패턴에 최적화된 저장 구조가 더 중요하다.

## 2. Discord의 초기 상황

Discord는 초기에 빠르게 제품을 만들기 위해 MongoDB를 사용했다. 모든 데이터를 하나의 MongoDB replica set에 저장했고, 메시지는 `channel_id`와 `created_at` 복합 인덱스로 조회했다.

초기에는 이 방식이 충분했다. 그러나 저장 메시지가 1억 개 수준에 도달하자 문제가 드러났다.

- 데이터와 인덱스가 RAM에 다 올라가지 않게 됨이다.
- 디스크 접근이 늘어나며 지연시간이 예측 불가능해짐이다.
- 채팅 서버마다 메시지 접근 패턴이 다르기 때문에 캐시 효율이 흔들림이다.

Discord의 메시지 접근 패턴은 단순하지 않았다.

- 읽기와 쓰기 비율이 대략 50:50이다.
- 음성 채팅 중심 서버는 메시지가 적지만, 최근 메시지 조회가 드물어 캐시에 잘 남지 않는다.
- 대형 공개 서버는 메시지가 많고 최근 메시지 조회가 매우 잦다.
- 멘션, 고정 메시지, 검색, 특정 메시지 점프 기능은 오래된 메시지에 대한 랜덤 읽기를 만든다.

따라서 Discord는 단순히 “쓰기 많은 저장소”가 아니라, 큰 데이터셋에서 예측 가능한 읽기 성능까지 필요했다.

## 3. Cassandra 선택

Discord는 MongoDB에서 Cassandra로 이전했다.

Cassandra를 선택한 이유는 다음과 같다.

- 노드를 추가해 선형적으로 확장하기 쉬움이다.
- 일부 노드 장애에도 서비스가 계속 동작하는 자동 장애 대응이다.
- 대규모 서비스에서 이미 검증된 오픈소스 저장소이다.
- 관련 데이터를 디스크에 인접하게 저장해 범위 조회에 유리함이다.
- Redis나 Memcached 같은 별도 메시지 캐시 없이 예측 가능한 성능을 기대할 수 있음이다.

여기서 중요한 점은 “Cassandra가 좋아서”가 아니다. Discord가 자신의 접근 패턴을 먼저 분석했고, 그 패턴에 맞는 저장소를 고른 것이다.

## 4. 메시지 데이터 모델

처음 생각할 수 있는 메시지 테이블의 키는 다음과 같다.

```
PRIMARY KEY (channel_id, message_id)
```

`channel_id`는 파티션 키이다. 대부분의 메시지 조회는 특정 채널 안에서 발생하므로 자연스러운 선택이다.

`message_id`는 클러스터링 키이다. 채널 안에서 메시지를 시간순으로 정렬하고 범위 조회하기 위한 기준이다.

하지만 이 구조에는 문제가 있다. 하나의 채널이 몇 년 동안 계속 커지면 한 파티션이 끝없이 커진다. Cassandra에서 너무 큰 파티션은 compaction, GC, 클러스터 확장 시 큰 부담이 된다.

그래서 Discord는 시간 단위 bucket을 추가했다.

```
PRIMARY KEY ((channel_id, bucket), message_id)
```

이 구조의 의미는 다음과 같다.

- 같은 채널이라도 시간 구간별로 파티션을 나눈다.
- 한 파티션이 무한히 커지는 문제를 막는다.
- 최근 메시지 조회는 최근 bucket부터 순서대로 읽으면 된다.
- 메시지가 적은 채널은 여러 bucket을 훑어야 할 수 있지만, 대부분의 활성 채널은 최근 bucket에서 충분한 메시지를 찾는다.

Discord는 대략 10일치 메시지가 한 bucket에 들어가면 파티션 크기를 적절히 유지할 수 있다고 판단했다.

## 5. 왜 `created_at`이 아니라 `message_id`인가

메시지 정렬에는 `created_at`을 쓰면 될 것처럼 보인다. 그러나 실제 시스템에서는 충분하지 않다.

이유는 다음과 같다.

- 여러 메시지가 같은 시간에 생성될 수 있다.
- 여러 서버에서 동시에 메시지가 생성될 수 있다.
- 정렬 기준이 중복되면 페이지네이션과 특정 메시지 점프가 흔들린다.

그래서 Discord는 Snowflake 방식의 ID를 사용했다. Snowflake ID는 시간 정보를 포함한 정렬 가능한 고유 ID이다.

개념적으로는 다음 구조이다.

```
timestamp | worker_id | sequence
```

- `timestamp`: 시간순 정렬을 위한 값이다.
- `worker_id`: ID를 만든 서버를 구분하는 값이다.
- `sequence`: 같은 밀리초 안에서 여러 ID를 만들 때 충돌을 막는 값이다.

이 방식의 장점은 다음과 같다.

- 데이터베이스의 `auto_increment`에 의존하지 않는다.
- 분산 환경에서 여러 서버가 동시에 ID를 만들 수 있다.
- ID 자체로 시간순 정렬이 가능하다.
- 채널 안에서 `message_id` 범위 스캔이 가능하다.

### 미니 코드 예시

아래 코드는 Snowflake의 핵심 아이디어를 단순화한 예시이다.

```jsx
const EPOCH = 1704067200000n; // 2024-01-01
const WORKER_ID = 7n;

let lastMs = 0n;
let sequence = 0n;

function nextMessageId() {
  const now = BigInt(Date.now());

  if (now === lastMs) {
    sequence = (sequence + 1n) & 4095n;
  } else {
    sequence = 0n;
    lastMs = now;
  }

  return ((now - EPOCH) << 22n) | (WORKER_ID << 12n) | sequence;
}
```

발표에서는 이 코드를 전부 설명할 필요는 없다. 중요한 것은 메시지 ID가 단순한 UUID가 아니라, 저장소 조회 패턴과 정렬 성능을 결정하는 설계 요소라는 점이다.

## 6. Cassandra에서 만난 문제

Discord는 Cassandra로 이전한 뒤에도 다시 문제를 만났다. 여기서 발표의 핵심 재미가 나온다.

### 6-1. Tombstone 문제

Cassandra에서 삭제는 즉시 물리 삭제가 아니다. 삭제 표시인 tombstone을 남기고, 나중에 compaction 과정에서 제거한다.

문제는 어떤 채널에서 수백만 개 메시지를 삭제하고 한 개만 남은 경우이다. 사용자가 그 채널을 열면 Cassandra는 실제 메시지 한 개를 찾기 위해 삭제 표시 수백만 개를 스캔할 수 있다.

즉, “메시지가 거의 없는 채널”이 오히려 매우 느린 채널이 될 수 있다.

이 사례의 교훈은 다음과 같다.

- 삭제도 쓰기이며 비용이 있다.
- 저장소 내부 동작을 모르면 데이터 모델이 위험해진다.
- 대량 삭제는 별도 정책과 운영 도구가 필요하다.

### 6-2. Hot Partition 문제

대형 서버에서 특정 채널이나 bucket에 트래픽이 몰리면 hot partition이 생긴다.

hot partition은 다음 문제를 만든다.

- 특정 노드에 읽기와 쓰기가 집중된다.
- quorum read/write 때문에 관련 노드들의 지연시간이 함께 증가한다.
- 한 파티션의 병목이 전체 클러스터 지연으로 번질 수 있다.

즉, 파티션을 나누었다고 항상 해결되는 것은 아니다. 사용자의 실제 행동이 특정 채널이나 이벤트에 몰리면 다시 병목이 생긴다.

### 6-3. GC와 Compaction 문제

Cassandra는 JVM 기반이다. 대규모 데이터와 높은 트래픽에서는 GC pause가 지연시간 스파이크를 만들 수 있다.

또한 Cassandra는 SSTable compaction을 통해 데이터를 정리한다. compaction이 밀리면 읽기 비용이 증가하고, 읽기 비용 증가는 다시 지연시간 증가로 이어진다.

Discord는 이런 운영 부담이 커지면서 Cassandra 유지에 많은 노력이 필요해졌다고 설명한다.

## 7. ScyllaDB와 데이터 서비스

Discord는 결국 메시지 저장소를 Cassandra에서 ScyllaDB로 이전했다.

ScyllaDB를 선택한 이유는 다음과 같다.

- Cassandra 호환 데이터베이스이다.
- C++ 기반이라 JVM GC 문제가 없다.
- shard-per-core 구조로 CPU 코어별 workload isolation이 가능하다.
- repair와 compaction에서 더 나은 성능을 기대할 수 있다.

하지만 중요한 점은 저장소만 바꾼 것이 아니라는 점이다. Discord는 DB 앞단에 Rust 기반 data service를 두었다.

data service의 핵심 역할은 request coalescing이다.

예를 들어 큰 서버에서 `@everyone` 알림이 발생하면 수많은 사용자가 같은 메시지를 동시에 읽으려 한다. 기존 구조에서는 같은 row를 읽기 위해 DB에 중복 요청이 몰린다.

request coalescing을 사용하면 다음처럼 동작한다.

1. 첫 번째 요청이 DB 조회 작업을 시작한다.
2. 같은 row를 원하는 후속 요청은 같은 작업에 구독자로 붙는다.
3. DB 조회는 한 번만 발생한다.
4. 결과는 여러 요청자에게 함께 반환된다.

또한 Discord는 consistent hashing으로 같은 채널의 요청이 같은 data service 인스턴스로 가도록 했다. 그래야 같은 채널에 대한 요청을 더 잘 합칠 수 있다.

핵심은 다음과 같다.

> hot partition은 데이터베이스만의 문제가 아니라, 데이터베이스 앞에서 트래픽을 어떻게 모으고 제어하느냐의 문제이다.
>

## 8. 무중단 마이그레이션

Discord의 ScyllaDB 이전은 수조 개 메시지를 대상으로 한 대규모 마이그레이션이었다.

주요 전략은 다음과 같다.

- 새 데이터베이스에 데이터를 옮긴다.
- 일부 읽기를 양쪽 데이터베이스에 보내 결과를 비교한다.
- 검증이 끝나면 새 데이터베이스를 primary로 전환한다.
- 문제가 생기면 되돌릴 수 있는 계획을 준비한다.

Discord는 Rust 기반 migrator를 만들어 대량 데이터를 빠르게 옮겼고, 초당 최대 320만 개 메시지 수준의 마이그레이션 속도를 기록했다고 설명한다.

실무에서 인상적인 부분은 기술 선택보다 마이그레이션 방식이다. 대규모 시스템에서는 좋은 저장소를 고르는 것만큼, 사용자가 모르게 갈아끼우는 능력이 중요하다.

### 결론

이 사례의 핵심은 “NoSQL을 쓰면 된다”가 아니다. 채팅 시스템의 저장소 설계는 접근 패턴을 이해하고, 키 설계와 파티션 설계, ID 생성, 삭제 처리, hot partition 대응까지 함께 설계하는 문제이다. 책에서 제안한 키-값 저장소 설계는 출발점이고, 실무에서는 그 위에 운영과 장애 대응 전략이 더해진다.

## 9. 요약

- Discord는 빠른 개발을 위해 MongoDB로 시작했다.
- 메시지와 인덱스가 RAM을 넘어서며 지연시간이 예측 불가능해졌다.
- Cassandra로 이전하면서 `((channel_id, bucket), message_id)` 구조를 사용했다.
- Snowflake 기반 `message_id`는 정렬 가능한 고유 ID로 메시지 범위 조회를 가능하게 했다.
- Cassandra에서는 tombstone, hot partition, GC, compaction 문제가 발생했다.
- ScyllaDB 이전과 Rust data service 도입으로 저장소와 앞단 트래픽 제어를 함께 개선했다.
- 채팅 저장소 설계의 핵심은 저장소 제품 선택이 아니라 접근 패턴 기반 데이터 모델링이다.
