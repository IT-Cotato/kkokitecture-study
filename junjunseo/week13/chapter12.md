# 13주차: 채팅 시스템 설계

## 핵심 요약

- 채팅 시스템 설계의 핵심은 실시간 메시지 전달, 메시지 저장, 접속상태 관리, 푸시 알림, 확장성 확보이다.
- 채팅 앱은 클라이언트끼리 직접 통신하지 않고, 각 클라이언트가 채팅 서비스와 통신하는 구조이다.
- 메시지 송신은 HTTP로도 가능하지만, 메시지 수신과 실시간 양방향 통신에는 웹소켓이 더 적합하다.
- 채팅 서버는 클라이언트와 지속 연결을 유지해야 하므로 상태유지 서비스로 설계한다.
- 로그인, 회원가입, 프로필, 그룹 관리 같은 기능은 일반적인 HTTP 기반 무상태 서비스로 처리한다.
- 채팅 이력은 양이 매우 크고 최근 메시지 조회가 많으므로 키-값 저장소가 적합하다.
- 접속상태 표시는 웹소켓 연결, 하트비트, pub-sub 모델을 함께 사용해 구현한다.

## 1단계 문제 이해 및 설계 범위 확정

채팅 시스템은 앱의 성격에 따라 요구사항이 크게 달라진다. 1:1 채팅 중심 앱인지, 그룹 채팅 중심 앱인지, 음성 채팅 중심 앱인지에 따라 설계 방향이 달라진다. 따라서 면접 초반에는 어떤 채팅 앱을 설계하는지 명확히 해야 한다.

이번 장의 설계 대상은 페이스북 메신저와 유사한 채팅 앱이다.

주요 요구사항은 다음과 같다.

- 응답지연이 낮은 1:1 채팅 지원이다.
- 최대 100명까지 참여 가능한 그룹 채팅 지원이다.
- 사용자의 접속상태 표시 지원이다.
- 하나의 계정으로 여러 단말에 동시 접속하는 기능 지원이다.
- 푸시 알림 지원이다.
- 일일 능동 사용자 수 5천만 명 처리 가능성이다.
- 채팅 이력의 영구 보관이다.
- 텍스트 메시지 중심 설계이다.
- 메시지 길이 제한은 100,000자 이하이다.
- 종단 간 암호화는 핵심 범위 밖으로 두되, 추가 논의 주제로 남긴다.

## 2단계 개략적 설계안

### 클라이언트와 서버의 관계

채팅 클라이언트는 서로 직접 통신하지 않는다. 각 클라이언트는 채팅 서비스와 통신하며, 채팅 서비스는 메시지 저장과 전달을 담당한다.

채팅 서비스의 기본 역할은 다음과 같다.

- 클라이언트로부터 메시지 수신이다.
- 메시지 수신자 결정 및 전달이다.
- 수신자가 접속 중이 아닐 경우 메시지 보관이다.
- 수신자가 다시 접속했을 때 저장된 메시지 전달이다.

### 통신 방식 비교

#### 폴링

폴링은 클라이언트가 주기적으로 서버에 새 메시지가 있는지 묻는 방식이다.

장점은 구현이 단순하다는 점이다. 단점은 새 메시지가 없어도 계속 요청을 보내기 때문에 서버 자원이 낭비된다는 점이다. 폴링 주기가 짧을수록 지연시간은 줄어들지만 비용은 증가한다.

#### 롱 폴링

롱 폴링은 클라이언트가 서버에 요청을 보내고, 새 메시지가 생기거나 타임아웃이 발생할 때까지 연결을 유지하는 방식이다.

장점은 단순 폴링보다 불필요한 요청이 줄어든다는 점이다. 단점은 HTTP 서버가 무상태로 운영될 경우 송신자와 수신자가 서로 다른 서버에 연결될 수 있다는 점이다. 또한 서버가 클라이언트의 연결 해제를 즉시 알기 어렵고, 메시지가 적은 사용자도 타임아웃마다 재연결해야 하므로 여전히 비효율적이다.

#### 웹소켓

웹소켓은 클라이언트가 시작한 연결을 HTTP 핸드셰이크 후 양방향 지속 연결로 업그레이드하는 방식이다.

웹소켓을 사용하면 서버가 클라이언트에게 비동기 메시지를 보낼 수 있다. 메시지를 보내는 경우와 받는 경우 모두 같은 프로토콜을 사용할 수 있어 설계와 구현이 단순해진다. 일반적으로 80 또는 443 포트를 사용하므로 방화벽이 있는 환경에서도 동작하기 좋다.

웹소켓의 주의점은 연결이 항구적으로 유지되므로 서버 측 연결 관리가 중요하다는 점이다.

### 전체 시스템 구성

채팅 시스템은 크게 세 부분으로 나뉜다.

- 무상태 서비스이다.
- 상태유지 서비스이다.
- 제3자 서비스 연동이다.

무상태 서비스는 로그인, 회원가입, 사용자 프로필, 그룹 관리 등을 처리한다. 일반적인 요청/응답 방식이며 로드밸런서 뒤에 위치한다.

상태유지 서비스는 채팅 서버와 접속상태 서버이다. 클라이언트와 웹소켓 연결을 유지하므로 상태를 가진다.

제3자 서비스 연동의 대표 예시는 푸시 알림이다. 새 메시지가 도착했을 때 앱이 실행 중이 아니더라도 사용자에게 알림을 보내야 한다.

### 규모 확장성

이론적으로는 현대적인 서버 한 대가 많은 동시 접속을 처리할 수 있다. 예를 들어 연결 하나에 10KB 메모리가 필요하고 동시 접속자가 100만 명이라면 약 10GB 메모리로 계산할 수 있다.

하지만 서버 한 대에 모든 것을 담는 설계는 좋은 설계가 아니다. 단일 장애 지점이 생기고, 장애 복구와 확장에 취약하기 때문이다. 따라서 실제 설계는 여러 서버와 저장소로 분산해야 한다.

확장된 개략 설계의 주요 컴포넌트는 다음과 같다.

- 채팅 서버는 클라이언트 사이의 실시간 메시지를 중계한다.
- 접속상태 서버는 사용자의 온라인 여부를 관리한다.
- API 서버는 로그인, 회원가입, 프로필 변경 등 일반 기능을 처리한다.
- 알림 서버는 푸시 알림을 보낸다.
- 키-값 저장소는 채팅 이력을 저장한다.

## 저장소 설계

### 데이터 유형

채팅 시스템의 데이터는 크게 두 종류이다.

첫 번째는 사용자 프로필, 설정, 친구 목록 같은 일반 데이터이다. 이 데이터는 안정성이 중요하므로 관계형 데이터베이스에 저장하기 적합하다. 복제와 샤딩을 통해 가용성과 확장성을 확보한다.

두 번째는 채팅 이력이다. 채팅 이력은 채팅 시스템에 고유한 데이터이며, 데이터 양이 매우 크다. 대부분의 사용자는 최근 메시지를 주로 조회하지만, 검색이나 특정 메시지로 이동하는 기능도 필요하다.

채팅 이력의 특징은 다음과 같다.

- 데이터 양이 매우 크다.
- 최근 메시지 접근 빈도가 높다.
- 오래된 메시지는 상대적으로 접근 빈도가 낮다.
- 검색, 멘션, 특정 메시지 점프 때문에 임의 접근도 필요하다.
- 1:1 채팅의 읽기와 쓰기 비율은 대략 1:1이다.

### 키-값 저장소 선택 이유

채팅 이력 저장소로는 키-값 저장소가 적합하다.

그 이유는 다음과 같다.

- 수평 확장이 쉽다.
- 데이터 접근 지연시간이 낮다.
- 관계형 데이터베이스보다 긴 꼬리 데이터와 큰 인덱스에 따른 비용 문제를 줄이기 좋다.
- 이미 대규모 채팅 시스템에서 검증된 방식이다.

대표 사례로 페이스북 메신저는 HBase를 사용하고, 디스코드는 Cassandra를 사용한다.

## 데이터 모델

### 1:1 채팅 메시지

1:1 채팅 메시지는 `message_id`를 기본 키로 둘 수 있다. `message_id`는 메시지의 고유 식별자이면서 메시지 순서를 판단하는 기준이다.

기본 필드는 다음과 같다.

- `message_id`: 메시지 고유 ID이다.
- `message_from`: 송신자 ID이다.
- `message_to`: 수신자 ID이다.
- `content`: 메시지 내용이다.
- `created_at`: 생성 시각이다.

`created_at`만으로는 메시지 순서를 완전히 보장하기 어렵다. 서로 다른 메시지가 같은 시각에 생성될 수 있기 때문이다.

### 그룹 채팅 메시지

그룹 채팅 메시지는 `(channel_id, message_id)` 복합 키를 사용할 수 있다.

`channel_id`는 채팅방이나 채널을 나타내며 파티션 키로 사용할 수 있다. 그룹 채팅에서 대부분의 질의는 특정 채널을 대상으로 하므로 이 방식이 적합하다.

### 메시지 ID

`message_id`는 다음 조건을 만족해야 한다.

- 전역 또는 대화 단위에서 고유해야 한다.
- 정렬 가능해야 한다.
- 시간 순서와 일치해야 한다.
- 새 메시지의 ID는 이전 메시지의 ID보다 커야 한다.

관계형 데이터베이스라면 `auto_increment`를 사용할 수 있다. 그러나 NoSQL 저장소에서는 이 기능을 기본으로 제공하지 않는 경우가 많다.

대안으로는 Snowflake 같은 전역 64비트 순서 번호 생성기를 사용할 수 있다. 더 단순한 방법은 지역적 순서 번호 생성기를 사용하는 것이다. 메시지 순서는 같은 채널이나 같은 1:1 채팅 세션 안에서만 보장하면 충분하므로, 지역적 ID 생성 방식이 구현하기 더 쉽다.

## 3단계 상세 설계

### 서비스 탐색

서비스 탐색의 역할은 클라이언트에게 가장 적합한 채팅 서버를 추천하는 것이다.

서버 선택 기준은 클라이언트의 지리적 위치와 서버 용량 등이다. 구현에는 Apache ZooKeeper 같은 서비스 탐색 도구를 사용할 수 있다.

서비스 탐색 흐름은 다음과 같다.

1. 사용자가 시스템에 로그인한다.
2. 로드밸런서가 로그인 요청을 API 서버로 전달한다.
3. API 서버가 사용자 인증을 처리한다.
4. 서비스 탐색 기능이 사용자를 담당할 최적의 채팅 서버를 찾는다.
5. 클라이언트가 선택된 채팅 서버와 웹소켓 연결을 맺는다.

서비스 탐색은 특정 채팅 서버에 부하가 몰리지 않도록 채팅 서비스와 긴밀히 협력해야 한다.

### 1:1 채팅 메시지 처리 흐름

사용자 A가 사용자 B에게 메시지를 보낼 때의 흐름은 다음과 같다.

1. 사용자 A가 자신이 연결된 채팅 서버로 메시지를 보낸다.
2. 채팅 서버가 ID 생성기를 통해 메시지 ID를 결정한다.
3. 채팅 서버가 메시지를 메시지 동기화 큐로 보낸다.
4. 메시지가 키-값 저장소에 저장된다.
5. 사용자 B가 접속 중이면 사용자 B가 연결된 채팅 서버로 메시지를 전달한다.
6. 사용자 B가 접속 중이 아니면 푸시 알림 서버로 알림을 보낸다.
7. 사용자 B가 접속 중인 경우 웹소켓을 통해 메시지가 사용자 B에게 전달된다.

### 여러 단말 사이의 메시지 동기화

한 사용자는 전화기와 랩톱처럼 여러 단말을 동시에 사용할 수 있다. 각 단말은 별도의 웹소켓 연결을 유지한다.

각 단말은 `cur_max_message_id` 값을 유지한다. 이 값은 해당 단말이 확인한 최신 메시지 ID이다.

새 메시지로 간주되는 조건은 다음과 같다.

- 메시지의 수신자 ID가 현재 로그인한 사용자 ID와 같다.
- 키-값 저장소에 저장된 메시지 ID가 해당 단말의 `cur_max_message_id`보다 크다.

이 방식은 단말마다 독립적으로 최신 메시지 위치를 관리하므로 메시지 동기화를 단순하게 만든다.

### 소규모 그룹 채팅 메시지 처리 흐름

소규모 그룹 채팅에서는 한 사용자가 보낸 메시지를 각 수신자의 메시지 동기화 큐에 복사한다.

이 방식의 장점은 다음과 같다.

- 수신자는 자기 큐만 확인하면 되므로 동기화 흐름이 단순하다.
- 그룹 규모가 작으면 메시지를 수신자별로 복사하는 비용이 크지 않다.

단점은 그룹 규모가 커질수록 쓰기 비용이 급격히 증가한다는 점이다. 예를 들어 매우 큰 그룹에서 한 메시지를 모든 사용자 큐에 복사하면 부하가 커진다. 따라서 이 방식은 소규모 그룹에 적합하다.

## 접속상태 표시

접속상태 표시는 채팅 애플리케이션의 핵심 기능이다. 사용자의 프로필 옆에 표시되는 녹색 점 같은 정보가 이에 해당한다.

접속상태 서버는 클라이언트와 웹소켓으로 통신하는 실시간 서비스의 일부이다.

### 로그인

사용자가 로그인하고 웹소켓 연결을 맺으면 접속상태 서버는 사용자의 상태를 온라인으로 저장한다. 이때 `last_active_at` 같은 타임스탬프를 함께 키-값 저장소에 저장한다.

### 로그아웃

사용자가 로그아웃하면 API 서버와 접속상태 서버를 거쳐 키-값 저장소의 사용자 상태가 오프라인으로 바뀐다. 절차가 끝나면 UI에서도 사용자는 오프라인으로 표시된다.

### 접속 장애와 하트비트

인터넷 연결은 항상 안정적이지 않다. 짧은 시간 동안 연결이 끊겼다가 복구되는 경우마다 사용자를 오프라인으로 표시하면 사용자 경험이 나빠진다.

이를 해결하기 위해 하트비트 검사를 사용한다. 온라인 상태의 클라이언트는 주기적으로 하트비트 이벤트를 접속상태 서버에 보낸다. 서버는 일정 시간 안에 하트비트를 계속 받으면 사용자를 온라인으로 유지한다. 일정 시간 동안 하트비트가 오지 않을 때만 오프라인으로 변경한다.

### 상태 정보 전송

사용자의 상태 변경은 친구들에게 전달되어야 한다. 이를 위해 발행-구독 모델을 사용할 수 있다.

예를 들어 사용자 A와 친구 B, C, D가 있다면 A-B, A-C, A-D 채널을 만들고 각 친구가 해당 채널을 구독한다. A의 접속상태가 바뀌면 각 채널에 이벤트가 발행되고, 구독 중인 친구들이 상태 변화를 받는다.

이 방식은 친구 수나 그룹 크기가 작을 때 효과적이다. 그러나 큰 그룹에서는 한 번의 상태 변경이 수많은 이벤트로 확산될 수 있으므로 비효율적이다.

큰 그룹에서는 사용자가 그룹 채팅방에 들어오는 순간에만 상태 정보를 읽거나, 친구 목록의 접속상태를 사용자가 필요할 때 갱신하도록 유도할 수 있다.

## 4단계 마무리

이번 장의 채팅 시스템은 1:1 채팅과 그룹 채팅을 모두 지원하는 아키텍처이다.

핵심 컴포넌트는 다음과 같다.

- 웹소켓 기반 실시간 통신이다.
- 실시간 메시징을 담당하는 채팅 서버이다.
- 접속상태를 관리하는 접속상태 서버이다.
- 오프라인 사용자를 위한 푸시 알림 서버이다.
- 채팅 이력을 보관하는 키-값 저장소이다.
- 로그인과 프로필 같은 일반 기능을 처리하는 API 서버이다.
- 적절한 채팅 서버를 배정하는 서비스 탐색 기능이다.

면접 말미에 시간이 남으면 다음 주제를 추가로 논의할 수 있다.

- 사진이나 비디오 같은 미디어 메시지 지원이다.
- 미디어 파일 압축, 클라우드 저장소, 썸네일 생성 전략이다.
- 종단 간 암호화 지원이다.
- 클라이언트 캐시를 통한 서버 트래픽 감소이다.
- 지역별 데이터 분산을 통한 로딩 속도 개선이다.
- 채팅 서버 장애 시 서비스 탐색을 통한 재접속 처리이다.
- 재시도와 큐를 이용한 안정적인 메시지 전송 보장이다.

## 면접 답변 흐름 정리

채팅 시스템 설계 면접에서는 다음 순서로 설명하는 것이 자연스럽다.

1. 요구사항을 먼저 확정한다.
2. 메시지 송신과 수신의 통신 방식을 비교한다.
3. 웹소켓을 선택하는 이유를 설명한다.
4. 무상태 서비스와 상태유지 서비스를 분리한다.
5. 채팅 이력 저장소로 키-값 저장소를 선택하는 이유를 설명한다.
6. 메시지 ID 생성 전략을 설명한다.
7. 1:1 메시지 흐름과 그룹 메시지 흐름을 설명한다.
8. 여러 단말 간 동기화 방식을 설명한다.
9. 접속상태 표시와 하트비트 전략을 설명한다.
10. 장애 처리, 재시도, 푸시 알림, 미디어 지원 같은 확장 주제를 덧붙인다.
