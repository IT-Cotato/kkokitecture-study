## 1. Jump Consistent Hash

> 안정 해시의 대안. Google이 2014년 발표. 단 7줄로 구현 가능.
>

### 핵심 아이디어

기존 안정 해시는 링과 가상 노드를 유지해야 해서 메모리와 구현 복잡도가 높다.

Jump Hash는 수학적 점프 계산만으로 균등 분포를 달성한다.

```python
def jump_hash(key: int, num_buckets: int) -> int:
    b, j = -1, 0
    while j < num_buckets:
        b = int(j)
        key = ((key * 2862933555777941757) + 1) & 0xFFFFFFFFFFFFFFFF
        j = (b + 1) * (1 << 31) / ((key >> 33) + 1)
    return b
```

### 안정 해시 vs Jump Hash

| 항목 | 안정 해시 | Jump Hash |
| --- | --- | --- |
| 구현 복잡도 | 링 + 가상 노드 필요 | 7줄 |
| 메모리 | O(서버 수 × 가상 노드 수) | O(1) |
| 균등 분포 | 가상 노드 수에 의존 | 항상 완벽 균등 |
| 서버 제거 | 어느 서버든 가능 | **마지막 서버만** 제거 가능 |
| 주요 용도 | 캐시/DB 파티셔닝 | 배치 처리, 분산 연산 |

### 한계

서버를 임의로 제거할 수 없다는 제약이 있어, 노드 장애가 잦은 환경에는 부적합하다.

서버 수가 순차적으로 늘어나는 환경(배치 처리, 맵리듀스)에 적합하다.

## 2. 파티셔닝 심화 — DDIA 6장

> *Designing Data-Intensive Applications* (Martin Kleppmann) 6장
>

### 키 범위 파티셔닝 vs 해시 파티셔닝

|  | 키 범위 파티셔닝 | 해시 파티셔닝 |
| --- | --- | --- |
| 방식 | 키를 정렬된 범위로 나눔 | 키를 해시한 값으로 나눔 |
| 범위 조회 | 효율적 (연속된 키가 같은 파티션) | 비효율적 (키가 흩어짐) |
| 핫스팟 위험 | 높음 (특정 범위에 쏠림 가능) | 낮음 |
| 사용 예시 | HBase, 초기 Bigtable | Cassandra, DynamoDB |

### 핫스팟 문제 (Celebrity Problem)

해시 파티셔닝을 써도 **특정 키**에 요청이 폭증하면 핫스팟이 생긴다.

```
예시: 유명인 SNS 게시물
  → user_id: "BTS" 로 해시 → 항상 같은 파티션
  → 해당 파티션에만 수백만 요청 집중
```

**완화 방법**: 핫스팟 키에 랜덤 접두사를 붙여 여러 파티션에 분산

```python
import random

def write_key(user_id):
    # 핫스팟 키는 앞에 0~9 랜덤 숫자를 붙여 분산
    prefix = random.randint(0, 9)
    return f"{prefix}_{user_id}"

# 읽을 때는 0~9 모든 키를 조회 후 병합
def read_keys(user_id):
    return [f"{i}_{user_id}" for i in range(10)]
```

### 리밸런싱 전략 3가지

**① 고정 파티션 수**

- 처음부터 파티션을 넉넉하게 만들어 두고 노드가 늘면 파티션을 재배정
- 사용 예시: Elasticsearch, Riak
- 단점: 파티션 수를 처음에 잘못 잡으면 이후 조정 어려움

**② 동적 파티셔닝**

- 파티션이 너무 커지면 자동으로 분할, 너무 작아지면 병합
- 사용 예시: HBase, RethinkDB
- 장점: 데이터 양에 자동 적응

**③ 노드 비례 파티셔닝**

- 파티션 수를 노드 수에 비례해서 유지
- 사용 예시: Cassandra
- 장점: 노드가 늘어날수록 파티션도 늘어나 균형 유지

### Redis Cluster가 안정 해시 대신 슬롯을 선택한 이유

Redis Cluster는 안정 해시 대신 **16384개의 고정 슬롯**을 사용한다.

```
CRC16(key) % 16384 → 슬롯 번호 → 담당 노드
```

안정 해시는 서버 추가/제거 시 재배치가 자동으로 결정된다.

슬롯 방식은 **운영자가 슬롯 이전을 명시적으로 제어**할 수 있어 예측 가능성이 높다.

Redis는 수천 노드 규모까지만 지원하면 되므로, 유연성보다 운영 단순성을 우선했다.

## 3. Maglev Hashing

> Google이 L4 로드밸런서 Maglev에 적용한 해시 방식. 2016년 발표.
>

### 문제 의식

로드밸런서는 같은 클라이언트의 요청을 **항상 같은 백엔드 서버로** 보내야 한다 (연결 일관성).

안정 해시는 O(log n) 조회 + 가상 노드 관리 오버헤드가 있어 초저지연 환경에는 부담이다.

### 동작 방식

1. 각 서버마다 **순열 테이블** 생성 (서버 선호도 순서)
2. 순열 테이블을 라운드로빈으로 순회하며 **lookup 테이블** 채우기
3. 요청이 오면 `hash(key) % lookup_table_size` 로 O(1) 조회

```
lookup 테이블 (크기: 소수 M)

index:  0    1    2    3    4    5    6  ...
server: S2   S0   S1   S0   S2   S1   S0 ...

→ hash("192.168.1.1") % M = 3 → S0으로 전달
```

### 안정 해시 vs Maglev

| 항목 | 안정 해시 | Maglev |
| --- | --- | --- |
| 조회 복잡도 | O(log n) | **O(1)** |
| 분포 균등도 | 가상 노드 수에 의존 | 거의 완벽 균등 |
| 메모리 | 적음 | lookup 테이블만큼 필요 |
| 연결 일관성 | 보통 | 높음 |
| 주요 용도 | 캐시/DB 파티셔닝 | **로드밸런서** |

## 4. 실전 시스템 비교

### 시스템별 파티셔닝 전략

| 시스템 | 방식 | 해시 함수 | 가상 노드 | 리밸런싱 |
| --- | --- | --- | --- | --- |
| Cassandra | 안정 해시 | Murmur3 | O | 자동 |
| DynamoDB | 안정 해시 | MD5 | O | 자동 |
| Redis Cluster | 고정 슬롯 (16384) | CRC16 | X | 수동 |
| Memcached | 안정 해시 | MD5 | O | 수동 |
| Kafka | 파티션 번호 mod N | Murmur2 | X | 수동 |
| Maglev LB | lookup 테이블 | 커스텀 | X | 자동 |

### 언제 무엇을 쓸까?

```
일반적인 캐시/DB 파티셔닝
  → 안정 해시 (Cassandra, Memcached 방식)

서버 수가 순차 증가하는 배치 환경
  → Jump Consistent Hash

초저지연 로드밸런서
  → Maglev Hashing

운영자가 파티션을 직접 제어해야 하는 환경
  → Redis Cluster 슬롯 방식
```

|  | 핵심 장점 | 핵심 한계 |
| --- | --- | --- |
| 안정 해시 | 서버 추가/제거 시 최소 재배치 | 가상 노드 관리 필요 |
| Jump Hash | 메모리 O(1), 완벽 균등 | 마지막 서버만 제거 가능 |

| Redis 슬롯 | 운영 단순성, 명시적 제어 | 자동 리밸런싱 없음 |
