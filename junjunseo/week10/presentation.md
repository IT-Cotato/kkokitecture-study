# DNS 동작 원리와 캐싱

> 웹 크롤러의 HTML 다운로더에서 "도메인 이름 변환기(DNS Resolver)"가 성능 병목이 되는 이유와, 캐싱으로 이를 해결하는 원리를 정리한 보충 자료.
>

---

## 1. DNS란 무엇인가

DNS(Domain Name System)는 사람이 읽는 도메인 이름(`www.wikipedia.org`)을 기계가 쓰는 IP 주소(`198.35.26.96`)로 변환해주는 분산 데이터베이스 시스템. 인터넷의 "전화번호부"에 해당함.

핵심 특징:

- **분산형(distributed)**: 단일 서버가 전 세계 도메인을 관리하지 않음. 계층적으로 나뉜 수많은 서버가 분담함.
- **계층형(hierarchical)**: 도메인은 점(`.`)을 기준으로 오른쪽에서 왼쪽으로 갈수록 하위 계층. `www.wikipedia.org` → `org`(상위) → `wikipedia`(중간) → `www`(하위).
- **캐싱 기반(cache-friendly)**: 같은 질의를 반복하지 않도록 중간 결과를 곳곳에 캐시함. (← 크롤러 성능 최적화의 핵심)

---

## 2. DNS 서버의 계층 구조

DNS 조회에 관여하는 서버는 크게 네 종류.

1. **DNS 리졸버(Recursive Resolver / 재귀 질의 해석기)**
    - 클라이언트(브라우저, 크롤러)를 대신해 답을 찾아주는 "심부름꾼".
    - 보통 ISP(통신사)나 공용 DNS(Google `8.8.8.8`, Cloudflare `1.1.1.1`)가 운영함.
    - 캐시를 가지고 있어, 이미 아는 도메인이면 곧장 답함.
2. **루트 네임서버(Root Name Server)**
    - 계층의 최상단. 전 세계에 13개 논리 서버군(A~M)이 존재함.
    - 도메인 자체의 IP를 알지는 못하고, "`.org`는 저쪽 TLD 서버에 물어봐라"라고 안내만 함.
3. **TLD 네임서버(Top-Level Domain Name Server)**
    - `.com`, `.org`, `.net`, `.kr` 등 최상위 도메인을 관리함.
    - "`wikipedia.org`는 저쪽 권한 네임서버에 물어봐라"라고 안내함.
4. **권한 네임서버(Authoritative Name Server)**
    - 특정 도메인의 실제 IP 주소를 "확정적으로" 알고 있는 최종 서버.
    - 여기서 비로소 진짜 IP 주소를 응답함.

---

## 3. DNS 조회 흐름 (재귀 질의 전체 과정)

`www.wikipedia.org`의 IP를 찾는 과정 예시.

```
[클라이언트]
   │ ① www.wikipedia.org 주소 알려줘
   ▼
[DNS 리졸버] ──② .org 서버 어디야?──▶ [루트 네임서버]
   │         ◀──③ TLD(.org) 서버는 여기──
   │
   │ ──④ wikipedia.org 서버 어디야?──▶ [TLD(.org) 네임서버]
   │ ◀──⑤ 권한 네임서버는 여기──
   │
   │ ──⑥ www.wikipedia.org IP 줘──▶ [권한 네임서버]
   │ ◀──⑦ 198.35.26.96 이야──
   ▼
[클라이언트] ⑧ 198.35.26.96 응답 받음 → 접속
```

1. 클라이언트가 리졸버에 도메인 질의.
2. 리졸버가 캐시에 없으면 루트 네임서버에 질의.
3. 루트가 TLD(.org) 서버 위치를 안내.
4. 리졸버가 TLD 서버에 질의.
5. TLD가 권한 네임서버 위치를 안내.
6. 리졸버가 권한 네임서버에 질의.
7. 권한 네임서버가 최종 IP를 응답.
8. 리졸버가 클라이언트에 IP 전달 + 결과를 캐시에 저장.

> **재귀 질의(recursive query)**: 클라이언트가 리졸버에게 "끝까지 답을 찾아서 가져와"라고 맡기는 방식.
**반복 질의(iterative query)**: 리졸버가 루트→TLD→권한 서버를 차례로 직접 물어보는 방식 (위 ②~⑦ 구간).

## 4. 크롤러에서 DNS가 병목이 되는 이유

책 본문(9장) 핵심 정리.

- DNS 요청은 **요청을 보내고 결과를 받는 작업이 동기적(synchronous)**임. 결과를 받기 전까지 다음 작업 진행 불가.
- DNS 요청 처리에는 보통 **10ms ~ 200ms** 소요됨.
- 크롤러 스레드 중 어느 하나라도 DNS 작업 중이면, 다른 스레드의 DNS 요청은 전부 **블록(block)**됨.
- 크롤러는 초당 수백 페이지(QPS ≈ 400)를 처리해야 하는데, 매번 풀 DNS 조회를 하면 도메인 변환에만 시간을 다 써버림.

## 5. 해결책: DNS 캐싱

### 핵심 아이디어

이미 조회한 "도메인 이름 ↔ IP 주소" 매핑을 캐시에 저장해두고, 같은 도메인은 네트워크 질의 없이 즉시 응답함. 크롤러는 같은 호스트의 페이지를 대량으로 다운받으므로(BFS 특성상 내부 링크가 많음) 캐시 적중률(hit rate)이 매우 높음.

### TTL (Time To Live)

- DNS 레코드에는 **유효 기간(TTL)**이 함께 따라옴.
- TTL이 지나면 캐시된 항목을 폐기하고 다시 조회해야 함.
- TTL이 너무 길면 → IP가 바뀌었는데 옛 주소로 접속하는 문제.
- TTL이 너무 짧으면 → 캐시 효과가 약해지고 조회 부담 증가.

### 크론 잡(cron job)을 이용한 주기적 갱신

- 책에서 언급한 방법: 도메인-IP 매핑을 캐시에 보관하고, **크론 잡 등으로 주기적으로 갱신**.
- 동기적 조회를 크롤링 흐름에서 분리(비동기화)하여, 다운로드 스레드가 DNS 대기로 멈추지 않게 함.

### 캐싱이 일어나는 여러 계층

DNS 캐시는 한 곳이 아니라 여러 단계에 존재함 (다단계 캐시).

| 계층 | 위치 | 설명 |
| --- | --- | --- |
| 애플리케이션 캐시 | 크롤러 내부 | 가장 가깝고 빠름. 직접 구현하는 부분. |
| OS 캐시 | 운영체제 | OS가 관리하는 시스템 차원 캐시. |
| 리졸버 캐시 | ISP/공용 DNS | 리졸버가 보관하는 캐시. |
| 브라우저 캐시 | (일반 사용자) | 브라우저 자체 DNS 캐시. |

## 6. 웹 크롤러 설계와의 연결 고리

- **분산 크롤링**: 여러 다운로더 서버가 각자 또는 공유 DNS 캐시를 둠.
- **지역성(locality)**: 크롤링 서버 근처의 DNS 리졸버를 쓰면 변환 지연이 줄어듦.
- **안정성**: DNS 조회 실패·타임아웃에 대비한 예외 처리와 짧은 타임아웃 필요.

---

## 7. 함께 알아두면 좋은 개념

- **DNS 레코드 타입**: A(IPv4), AAAA(IPv6), CNAME(별칭), MX(메일 서버), NS(네임서버) 등.
- **DNS 부하 분산**: 하나의 도메인에 여러 IP를 응답(Round-Robin DNS)하여 트래픽을 분산.
- **DNS over HTTPS(DoH) / DNS over TLS(DoT)**: 보안·프라이버시 강화 프로토콜.
- **Anycast**: 같은 IP를 여러 지역 서버가 공유하여 가장 가까운 서버로 라우팅(루트/공용 DNS가 사용).

---

## 한 줄 요약

DNS는 도메인을 IP로 바꾸는 계층적·분산형 시스템이며, 동기적 특성 때문에 크롤러의 병목이 되므로 **다단계 캐싱 + TTL 관리 + 주기적 비동기 갱신**으로 최적화하는 것이 핵심.
