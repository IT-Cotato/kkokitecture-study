# Netflix Active-Active 멀티리전 아키텍처 정리

> 출처: Netflix Technology Blog — *Active-Active for Multi-Regional Resiliency* (2013.02)  
> 작성자: Ruslan Meshenberg, Naresh Gopalani, Luke Kosewski

---

## 1. 배경 및 목적

### 왜 Active-Active가 필요했나?

Netflix는 **99.99% 가용성**을 내부 목표로 삼고 있음.  
그런데 서비스 규모(Scale)와 배포 속도(Velocity)가 동시에 커지면 장애는 필연적으로 증가함.

| 상황 | 장애 원인 |
|---|---|
| 규모 크고 속도 느림 | 하드웨어 장애 증가 |
| 규모 작고 속도 빠름 | 소프트웨어 장애 증가 |
| **규모 크고 속도 빠름** | **항상 무언가 터짐** |

Netflix는 세 번째 상황에 해당하기 때문에, 단순한 이중화를 넘어서  
**리전 전체가 죽어도 서비스가 살아있는 구조**를 만들기로 함.

### 핵심 설계 원칙

- **격리(Isolation)**: 한 리전의 장애가 다른 리전에 영향을 주면 안 됨
- **이중화(Redundancy)**: 어느 리전이 죽어도 다른 리전이 전체 트래픽을 감당할 수 있어야 함

## 2. Active-Active 개요

### 구성

AWS의 두 리전에 동시에 서비스를 배포해서 **둘 다 실제 트래픽을 처리**함.

```
US-East-1 (버지니아) ─── 약 50% 트래픽
US-West-2 (오리건)   ─── 약 50% 트래픽
```

평소에는 Geo-DNS를 통해 사용자를 가장 가까운 리전으로 라우팅.  
장애 발생 시, DNS를 조작해 전체 트래픽을 건강한 리전으로 몰아줌.

### Active-Active vs Active-Standby 비교

| 구분 | Active-Active | Active-Standby |
|---|---|---|
| 평소 운영 | 두 리전 모두 실트래픽 처리 | 한 리전만 운영, 나머지는 대기 |
| 장애 전환 시간 | 거의 즉시 (이미 켜져 있음) | 스탠바이 리전을 깨워야 함 |
| 리소스 효율 | 두 리전 모두 활용 | 스탠바이 리전 낭비 |
| 복잡도 | 높음 (데이터 동기화 등) | 상대적으로 낮음 |

### Active-Active 운영을 위한 3가지 필수 조건

1. **서비스는 무상태(Stateless)** 여야 함 → 상태/데이터는 DB 계층에서만 관리
2. **모든 리소스는 같은 리전 내에서만 접근** (S3, SQS 등도 리전별로 중복 운영)
3. **유저 요청 처리 중 크로스 리전 호출 금지** → 데이터 복제는 비동기로만

## 3. 주요 구성요소 상세 설명

### 3-1. Denominator — DNS 통합 관리

**역할**: UltraDNS + Route53 두 DNS 서비스를 하나의 클라이언트로 통합 제어

**왜 두 DNS를 함께 쓰나?**

| DNS | 역할 |
|---|---|
| **UltraDNS** | 지리 기반 방향 라우팅 (미국 동부 → US-East, 서부 → US-West) |
| **Route53** | 빠르고 안정적인 API로 CNAME 전환 → 장애 시 신속하게 트래픽 이동 |

**트래픽 전환 방식**: Route53의 CNAME만 바꾸면 되므로, 복잡한 UltraDNS 방향 그룹을 건드릴 필요 없음 → 운영이 단순해짐.

---

### 3-2. Zuul — 엣지 트래픽 라우팅 & 보호

**역할**: 모든 Netflix 엣지 서비스 앞단에서 트래픽을 받아 처리하는 게이트웨이

Active-Active를 위해 Zuul에 다음 3가지 기능을 추가함:

#### ① 미스라우팅 처리 (Mis-routed Request Handling)
- 사용자가 Geo-DNS 기준과 다른 리전으로 들어온 경우 감지
- 올바른 리전으로 **리다이렉트** 하거나, Isthmus 방식으로 **프록시** 처리

#### ② 페일오버 모드 (Failover Mode)
- 한 리전이 장애 상태로 선언되면, 그 리전으로 들어온 모든 요청을 로컬에서 처리
- 더 이상 미스라우팅 요청을 다른 리전으로 보내지 않음

#### ③ 로드 쉐딩 (Load Shedding)
- 트래픽이 일정 수준 초과 시 자동으로 요청을 에러 처리
- **썬더링 허드(Thundering Herd)** 상황에서 하위 서비스를 보호

> **썬더링 허드(Thundering Herd)란?** 한 리전 장애 후 모든 트래픽이 다른 리전으로 갑자기 몰릴 때, 캐시가 비어있고 서버가 준비 안 된 상태에서 폭발적 요청을 받아 연쇄 장애가 발생하는 현상.

---

### 3-3. Apache Cassandra — 멀티리전 데이터 복제

**역할**: 사용자 데이터를 저장하고 리전 간 비동기 복제하는 NoSQL 데이터베이스

**왜 Cassandra인가?**  
Cassandra는 **멀티 데이터센터(리전) 간 비동기 복제**를 기본으로 지원함.  
Netflix는 이미 US-East + EU-West에서 운영 중이었고, Active-Active에서도 자연스럽게 채택.

**핵심 검증 실험**:
- 한 리전에서 100만 건 쓰기
- 500ms 후 다른 리전에서 동일 데이터 읽기
- 프로덕션 수준의 부하 유지
- **결과: 100만 건 모두 성공적으로 읽힘** → 복제 지연이 허용 범위 안임을 확인

**주요 일관성 레벨(Consistency Level) 설명**:

| 레벨 | 의미 | 특징 |
|---|---|---|
| `CL_ONE` | 단 1개 노드에서 확인 | 빠르지만 일관성 낮음 |
| `CL_LOCAL_QUORUM` | 같은 리전 내 과반수 노드 확인 | 속도와 일관성의 균형 |
| `CL_QUORUM` | 전체 클러스터 과반수 확인 | 느리지만 강한 일관성 |

Active-Active에서는 `CL_LOCAL_QUORUM`을 주로 사용 — 크로스 리전 호출 없이 로컬에서 빠르게 처리.

---

### 3-4. EvCache — 분산 캐시 + 리전 간 무효화

**역할**: Memcached 기반의 캐시 클라이언트, 멀티리전 캐시 일관성 보장

**문제**: Memcached는 멀티리전 복제 기능이 없음.  
한 리전에서 데이터를 업데이트하면 다른 리전의 캐시는 **낡은(stale) 데이터**를 가지게 됨.

**해결책 — 원격 캐시 무효화(Remote Cache Invalidation)**:

```
리전 A에서 데이터 Write
    → EvCache가 SQS 메시지를 리전 B로 전송
        → 리전 B의 EvCache가 해당 캐시 항목 삭제(Invalidate)
            → 리전 B에서 다음 Read 시 Cassandra에서 최신 데이터 재로딩
```

이렇게 하면 두 리전의 캐시가 결국 일치하게 됨 (최종 일관성, Eventual Consistency).

---

### 3-5. Mimir — 멀티리전 자동 배포 워크플로우

**역할**: 여러 리전에 순차적으로 자동 배포하는 워크플로우 엔진

**배경**: Active-Active 도입 후 배포 환경이 2개→6개로 늘어남.

```
기존: Test-USEast / Prod-USEast / Test-EUWest / Prod-EUWest (4개)
이후: + Test-USWest / Prod-USWest 추가 (6개)
```

**Mimir의 배포 순서 (예시)**:

```
1. US-West Test 배포
        ↓ (몇 시간 대기 + 카나리 분석)
2. US-West Prod 배포
        ↓ (몇 시간 대기 + 카나리 분석)
3. US-East Test 배포
        ↓ ...
4. US-East Prod 배포
```

리전 간 배포에 **수 시간씩 간격**을 두어, 문제가 전 세계로 퍼지기 전에 감지하고 자동 롤백.

> **카나리 배포(Canary Deployment)란?** 새 버전을 전체에 올리기 전에 소수 인스턴스에만 먼저 배포해서 문제 없는지 검증하는 방식. 카나리아 새처럼 먼저 들어가서 안전을 확인.

## 4. 장애 테스트 — Simian Army

Netflix는 의도적으로 시스템을 부숴서 **내성을 키우는** Chaos Engineering을 실천함.

| 이름 | 대상 | 설명 |
|---|---|---|
| **Chaos Monkey** | 개별 인스턴스 | 랜덤으로 서버 하나를 종료 |
| **Chaos Gorilla** | 가용 영역(AZ) 전체 | AZ 하나를 통째로 다운 |
| **Split-brain** | 리전 간 네트워크 | 두 리전 사이 통신 완전 단절 |
| **Chaos Kong** | 리전 전체 | 리전 하나를 완전히 죽이는 최대 규모 테스트 |
| **Latency Monkey** | 응답 지연/에러 주입 | 간헐적 지연/오류를 삽입해 부분 장애 시뮬레이션 |

> **가용 영역(AZ, Availability Zone)이란?** 하나의 AWS 리전 내에 있는 물리적으로 분리된 데이터센터 묶음. 리전 > AZ 계층 구조. 예: US-East-1 리전 안에 us-east-1a, 1b, 1c 등 여러 AZ 존재.

> **Split-brain이란?** 분산 시스템에서 네트워크 단절로 두 노드/리전이 서로를 인식 못하고 각자 독립적으로 동작하는 상태. 데이터 충돌 위험이 있어 설계 시 반드시 고려해야 함.

## 5. 실제 장애 대응 사례

Active-Active가 완전히 검증되기 전, **실제 장애**가 먼저 발생함:

```
중간 계층 서비스의 심각한 성능 저하 발생
    → 클러스터 대부분이 응답 불가 상태로 빠짐
        → 기존이라면 → 대규모 장애, 많은 사용자 영향
        → Active-Active → 트래픽을 건강한 리전으로 전환
            → 단시간 내 서비스 정상화
            → 장애 원인 분석 및 수정 후 원복
```

이 사례는 Active-Active가 **이론이 아닌 실전에서도 작동함**을 증명.

## 6. 개념 용어 정리

| 용어 | 설명 |
|---|---|
| **Active-Active** | 두 리전이 동시에 실트래픽을 처리하는 구조 |
| **Active-Standby** | 한 리전만 운영, 나머지는 장애 시 대기 |
| **Geo-DNS** | 사용자의 지리적 위치 기반으로 가장 가까운 서버로 라우팅하는 DNS 기술 |
| **AZ (Availability Zone)** | AWS 리전 내 물리적으로 분리된 데이터센터 묶음 |
| **Thundering Herd** | 트래픽 급증 시 캐시 미스와 폭발적 요청으로 연쇄 장애 발생하는 현상 |
| **Load Shedding** | 과부하 시 일부 요청을 의도적으로 에러 처리해 시스템 보호 |
| **CL_LOCAL_QUORUM** | Cassandra에서 같은 리전 내 과반수 노드에서 확인하는 일관성 레벨 |
| **Split-brain** | 네트워크 단절로 두 노드가 서로 모르고 독립 동작하는 상태 |
| **Canary Deployment** | 신버전을 소수에게 먼저 배포해 안전성 검증 후 전체 배포하는 방식 |
| **Eventual Consistency** | 즉시는 아니지만 결국 모든 노드가 같은 데이터를 갖게 되는 일관성 모델 |
| **Stateless** | 서버가 사용자 상태를 직접 보관하지 않는 설계 방식 |
| **Chaos Engineering** | 의도적으로 장애를 일으켜 시스템의 복원력을 테스트하고 강화하는 기법 |
