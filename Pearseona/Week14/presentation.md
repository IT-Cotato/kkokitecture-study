## 1. 문제 제기: 책은 왜 "필터 계층"이라고만 뭉뚱그렸는가

교재에서는 다음과 같이 짧게 언급하고 넘어갑니다.

> "혐오성이 짙거나, 폭력적이거나, 성적으로 노골적이거나, 여러 가지로 위험한 질의어를 자동완성 결과에서 제거해야 한다. 좋은 방법은 트라이 캐시 앞에 필터 계층(filter layer)을 두는 것이다."

교재는 이미 3단계에서 트라이(Trie)에 인기 검색어를 캐싱하는 최적화를 O(1)까지 끌어올렸습니다. 그런데 "필터 계층"이 만약 캐시에서 top-5를 꺼낸 뒤 **금칙어 사전 수만 개를 하나하나 순회하며 문자열 비교**를 한다면, 어렵게 O(1)로 만든 응답 속도가 필터 단계에서 다시 무너질 수 있습니다.

- 자동완성은 100ms 이내 응답이 요구사항이었음(1단계)

- 그런데 검색어 하나마다 유해어 사전(수천~수만 개)을 전부 대조해야 한다면?

- 게다가 사용자는 키 입력마다 요청을 보내므로(`d`, `di`, `din`, ...) 필터링도 초당 수만 건 발생

즉 "필터 계층"의 실제 구현은 **다중 패턴 문자열 매칭(multi-pattern string matching)** 문제이고, 이것이 바로 트라이를 확장한 **Aho-Corasick 알고리즘**이 등장하는 지점입니다.

## 2. 나이브한 방식의 한계

가장 단순한 구현은 검색어를 금칙어 사전과 하나씩 비교하는 것입니다.

```
for word in blacklist:
    if word in query:
        block()
```

- 검색어 길이를 *n*, 금칙어 사전의 전체 길이 합을 *m*이라 하면 최악의 경우 시간 복잡도는 **O(n × m)**

- 금칙어가 하나도 없는 "깨끗한" 질의를 검사할 때도 전체 사전을 다 훑어야 함

- 사전이 수만 단어로 커질수록 자동완성의 매 키 입력마다 이 비용이 곱해짐

이 한계는 "데이터 양이 적을 때는 괜찮지만 많아지면 DB 병목이 발생"하는 상황과 본질적으로 같은 패턴입니다. 다만 이번엔 트라이 캐시가 아니라 **패턴 매칭 자체**가 병목이 됩니다.

---

## 3. Aho-Corasick: 트라이 + 실패 링크(failure link)

Aho-Corasick은 책에서 이미 다룬 트라이 자료구조를 그대로 재사용하되, 여기에 **실패 링크**라는 개념 하나를 추가합니다.

**핵심 아이디어**

1. 금칙어 집합 전체를 하나의 트라이로 구성한다 (13장에서 인기 검색어를 트라이에 저장한 것과 동일한 방식)

2. 각 노드에 실패 링크를 연결한다 — 현재 위치에서 매칭이 끊겼을 때, 텍스트를 되감지 않고 "이미 확인한 부분과 겹치는 가장 긴 접미사"로 즉시 점프할 수 있는 지름길

3. 검색 대상 텍스트를 **처음부터 끝까지 딱 한 번만** 읽으면서, 이 트라이+실패 링크 구조(오토마타) 위를 이동한다

이렇게 하면 텍스트를 한 글자씩 훑는 동안 여러 금칙어를 동시에 검사할 수 있고, 매칭에 실패해도 텍스트 포인터를 되돌릴 필요가 없습니다. KMP(Knuth-Morris-Pratt)가 "패턴 1개 vs 텍스트"의 되감기를 없앤 것처럼, Aho-Corasick은 이를 "패턴 여러 개 vs 텍스트"로 일반화한 알고리즘이라 볼 수 있습니다.

**시간 복잡도**

| 단계 | 복잡도 | 비고 |
|:---|:---|:---|
| 오토마타 구성(전처리) | O(m) | m = 전체 금칙어 길이의 합, 사전이 바뀔 때만 재구성 |
| 텍스트 검색 | O(n) | n = 검색어(질의) 길이 |
| 매칭 결과 나열까지 포함 | O(n + m + z) | z = 실제로 발견된 매칭 개수 |

나이브 방식의 O(n × m)과 비교하면, 사전 크기 m이 검색 성능에 거의 영향을 주지 않는다는 점이 핵심입니다. 사전이 1,000개든 10만 개든 텍스트 스캔 비용은 그대로입니다.

## 4. 13장 설계와 어떻게 맞물리는가: 필터 계층의 위치

교재의 질의 서비스 흐름(3단계)을 다시 보면:

```
검색 질의 → 로드밸런서 → API 서버 → 트라이 캐시 조회 → top-5 반환
```

여기에 Aho-Corasick 기반 필터를 넣는다면 두 지점 중 하나를 선택할 수 있습니다.

1. **입력 단계 필터링**: 사용자가 입력한 질의 자체가 유해어를 포함하는지 검사 (자동완성 후보를 아예 만들지 않음)

2. **출력 단계 필터링**: 트라이 캐시에서 뽑아온 top-5 후보 각각에 유해어 오토마타를 통과시켜, 걸리는 후보만 제외하고 나머지로 채움

"트라이 캐시 앞에 필터 계층을 둔다"는 설명은 이 중 **출력 단계**에 가깝습니다. 다만 실무에서는 두 단계 모두에 걸어두는 경우가 많습니다 

— 애초에 유해 질의가 인기 검색어 집계(빈도 테이블)에 반영되어 트라이에 캐싱되는 일 자체를 막기 위해서입니다.

또한 책은 "데이터베이스에서 검색어를 물리적으로 삭제하는 것은 다음 업데이트 사이클에 비동기로 진행한다"고 했는데, 이는 Aho-Corasick 오토마타 자체도 **금칙어 사전이 바뀔 때마다 매번 재구성하지 않고 주기적으로만 재빌드**한다는 뜻과 자연스럽게 이어집니다. 트라이를 매주 갱신하는 작업 서버(job server)에 오토마타 재구성 작업을 함께 얹으면 됩니다.

## 5. 실제 사례: 우회(evasion) 문제는 알고리즘만으로 안 풀린다

Aho-Corasick은 "주어진 사전과 정확히 일치하는 문자열"을 빠르게 찾아줄 뿐, 사용자가 금칙어를 변형해서 입력하는 문제는 별개로 풀어야 합니다. 2016년 IGC(인벤 게임 컨퍼런스)에서 발표된 온라인 게임 로컬라이제이션(L10N) 사례는 이 지점을 잘 보여줍니다.

**포함(matching) 방식 vs 블록(blocking) 방식**

- 한 게임은 금칙어와 **완전히 일치**할 때만 걸러내는 매칭/치환 규칙을 썼고, 다른 게임은 금칙어가 **부분 문자열로 포함**되기만 해도 걸러내는 포함/블록 규칙을 썼습니다.

- 후자가 우회에는 강하지만, 정상 단어 안에 우연히 금칙어가 섞여 있는 경우(예: 특정 지명·인명이 금칙어를 부분 문자열로 포함하는 경우) 오탐이 늘어나는 트레이드오프가 있습니다.

**유니코드 정규화를 이용한 우회 방어**

<cite index="22-1,22-2">해당 발표에서는 합자로 묶인 알파벳을 낱개 문자로 분해하는 호환분해(NFKD) 방식의 유니코드 정규화를 필터링 전에 적용하는 방안이 논의되었으며, 실제로는 개발 리소스 문제로 적용을 보류했다는 점도 함께 소개되었습니다.</cite> 즉 이론적으로 좋은 방어책이라도 실무에서는 비용 대비 효과를 따져 보류되는 경우가 흔하다는 것을 보여주는 사례입니다.

**한국어 특유의 우회 문제**

한글은 초성·중성·종성이 조합되어 하나의 완성자로 표현되기 때문에, 영어와는 다른 층위의 우회 경로가 생깁니다.

- 자모를 하나씩 띄어 쓰거나(`ㅅㅂ`처럼 자음만 나열) 특수문자를 끼워 넣는 방식

- 모양이나 발음이 비슷한 모음으로 치환하는 방식(예: 'ㅐ'와 'ㅔ'처럼 헷갈리기 쉬운 모음 쌍을 이용)

한국어 비속어 필터링 관련 특허(KR20100129032A)에서는 <cite index="13-1">텍스트를 형태소(초성·중성·종성) 단위로 분리해 필터링하고, 유사 형태소 리스트와 대체 형태소 리스트를 만들어 우회를 차단하는 방식을 제안합니다.</cite> 이는 Aho-Corasick의 "정확한 문자열 매칭"을 하기 전에, **입력을 자모 단위로 정규화하는 전처리 레이어**를 하나 더 쌓는 접근이라 볼 수 있습니다.

정리하면 실무 파이프라인은 대략 이런 구조가 됩니다.

```
사용자 입력
  → [전처리] 유니코드 정규화(NFKD) / 초성·중성·종성 분리 / 유사 자모 치환
  → [매칭] Aho-Corasick 오토마타로 금칙어 사전 전체를 O(n)에 스캔
  → [정책] 완전 일치(matching) vs 부분 포함(blocking) 규칙 적용
  → [사후처리] 오탐 예외 리스트로 정상 단어 구제
```

## 6. 비교 정리

| | 책의 설계 (필터 계층) | Aho-Corasick 도입 | 한국어 대응 사례 (게임 L10N) |
|:---|:---|:---|:---|
| **핵심 아이디어** | 트라이 캐시 앞단에 필터를 둔다는 원칙만 제시 | 트라이 + 실패 링크로 다중 패턴을 O(n)에 매칭 | 정규화·형태소 분리 전처리 + 포함/블록 정책 |
| **다루는 문제** | 어디에 필터를 둘 것인가(위치) | 얼마나 빠르게 매칭할 것인가(성능) | 어떻게 우회를 막을 것인가(정확도) |
| **한계** | 구체적 알고리즘 부재 | 정확히 일치하는 패턴만 탐지, 변형에는 취약 | 완벽한 우회 차단은 비용 대비 효과 문제로 실무에서 종종 보류됨 |
| **갱신 주기** | 트라이와 함께 매주 갱신(job server) | 사전 변경 시에만 오토마타 재구성 | 채팅용/계정용/게임용 데이터를 별도 관리 |

## 7. 결론

책이 4단계에서 한 문장으로 넘어간 "필터 계층"은 사실 세 가지 서로 다른 문제가 겹쳐 있습니다.

1. **위치의 문제**: 입력 단계에서 막을지, 트라이 캐시 출력 단계에서 막을지

2. **성능의 문제**: 사전이 커져도 자동완성의 100ms 요구사항을 지키려면 나이브한 O(n×m) 대조가 아니라 Aho-Corasick 같은 O(n) 다중 패턴 매칭이 필요

3. **정확도의 문제**: 알고리즘이 아무리 빨라도 정규화되지 않은 입력, 자모 분리, 유사 문자 치환 같은 우회 앞에서는 무력하며, 이는 언어권(특히 한글)마다 별도의 전처리 설계가 필요

결국 트라이 자료구조는 "인기 검색어를 빠르게 찾는 문제"와 "유해 검색어를 빠르게 걸러내는 문제"에 같은 뿌리(트라이)로 접근할 수 있다는 점에서, 자동완성 시스템 설계 전체를 관통하는 자료구조라고 정리할 수 있습니다.
