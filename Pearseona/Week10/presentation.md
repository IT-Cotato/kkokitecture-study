## 1. 왜 URL 순서가 검색 엔진의 품질을 결정하는가?

**모든 페이지를 수집하는 것은 물리적으로 불가능**

- **자원의 한계**: 웹에는 수천억 개의 페이지가 있지만, 우리 시스템(QPS 400)은 한 달에 약 10억 개(전체의 1% 미만)만 수집 가능

- **결정적 차이**: 전체 웹의 1%도 못 가져오는 상황에서, "가져올 가치가 있는 1%"를 먼저 골라내는 능력이 검색 엔진의 핵심 경쟁력

- **BFS의 한계**: 단순히 발견한 순서대로 수집하면, 어제 올라온 중요한 뉴스보다 10년 전 방치된 개인 블로그를 먼저 수집하는 비효율이 발생(자원 낭비)

## 2. PageRank 원리: 랜덤 서퍼 모델

### 2.1 직관적 이해

인터넷을 무작위로 클릭하며 돌아다니는 가상의 사용자를 상상

- 85% 확률로 현재 페이지의 링크 중 하나를 무작위로 클릭

- 15% 확률로 지루함을 느껴 아예 새로운 페이지로 이동

이 사용자가 페이지 내 링크를 무작위로 클릭하다 보면, 결국 링크가 많이 걸린 '유명한 페이지'에 더 자주 머물게 됨

이 과정을 무한히 반복했을 때, **서퍼가 특정 페이지에 머무르는 비율**이 그 페이지의 **PageRank** 값

=> 사용자가 가장 많이 머무는 페이지가 곧 가장 중요한 페이지

### 2.2 수식

    ```
    PR(A) = (1 - d) + d x Σ ( PR(W_i) / C(W_i) )

    ```

이 수식의 핵심은 **재귀적 특징**

- **재귀적 구조**: 내 점수는 나를 가리키는 친구들의 점수에 의존

=> 즉, "유명한 사람이 추천할수록 내 점수도 올라간다"는 의미

### 2.3 크롤러와의 관계

크롤러 입장에서 PageRank를 URL 우선순위로 사용하면 하나의 근본적인 문제 발생

> PageRank를 계산하려면 페이지를 이미 수집해야 하고, 수집 순서를 결정하려면 PageRank가 필요하다.

1. 순서를 정하려면: 페이지의 중요도(PageRank)를 알아야 한다

2. 중요도를 알려면: 일단 그 페이지를 긁어와서(Crawling) 어떤 링크가 걸려 있는지 분석해야 한다.

3. 역설: "페이지를 긁어오기 위해 순서를 정해야 하는데, 순서를 정하려면 이미 페이지를 긁어왔어야 한다"는 논리적 충돌 발생

- 해결책: 실제 Google이나 Bing 같은 거대 검색 엔진은 이 문제를 '반복적 업데이트'로 해결 

- **피드백 루프**: 1회차 크롤링에서 얻은 불완전한 PageRank값을 저장해 두었다가, 2회차 크롤링의 '우선순위 입력값'으로 사용

- **지속적 보정**: 크롤링 회차가 반복될수록 전체 웹 그래프가 완성되면서 PageRank값은 점점 더 정확해지고, 수집 순서도 그에 맞춰 졍교화

## 3. 우선순위 점수의 실제 구성: 단일 지표의 한계

PageRank만으로 우선순위를 결정하는 건 단순하지만 현실적이지 X

다음과 같은 한계 존재

### 3.1 신선도(Freshness)를 반영하지 못한다

뉴스 사이트의 최신 기사는 PageRank가 낮더라도 즉시 수집
반면 5년째 변경이 없는 학술 논문 페이지는 PageRank가 높아도 재수집 우선순위 낮추기 가능

Google은 이를 **크롤 수요(Crawl Demand)** 개념으로 명시화
인기도(Popularity)와 신선도(Staleness)를 함께 고려하여 재수집 빈도를 결정

Mocrosoft Bing 연구팀은 SIGIR 2019에서 이를 최적화 문제로 정식화
각 URL의 변경 빈도와 중요도 점수를 입력으로 받아, 제한된 대역폭(bandwidth) 안에서 인덱스의 평균 신선도를 최대화하는 크롤 속도를 각 URL 별로 계산

### 3.2 동적 콘텐츠에 적합하지 않다

PageRank는 링크 구조 기반이므로 SNS처럼 링크 수는 적지만 트래픽이 폭발적인 콘텐츠를 과소평가

현대 크롤러는 외부 링크 수 외에 검색 쿼리 빈도, 소셜 시그널 등을 추가 가중치로 반영

### 3.3 콜드 스타트 문제

새로 등장한 페이지는 아직 아무도 링크하지 않아 PageRank가 거의 0

하지만 그 페이지가 중요한 신규 콘텐츠일 수도 있음

이를 위해 **사이트맵(sitemap.xml)** 이나 **핑(ping) API**를 통한 신규 URL 우선 처리 루트를 별도로 운영

## 4. 실전 설계: 다중 가중치 스코어링 시스템

세 가지 신호를 합쳐서 우선순위 점수를 설계

```
Priority Score = α × PageRank(URL)
              + β × FreshnessScore(URL)
              + γ × TrafficSignal(URL)
```

- **α, β, γ**: 각 신호의 가중치 (합산 = 1.0)

- **PageRank**: 이전 크롤링 사이클에서 계산된 링크 기반 중요도

    => 웹 세상에서의 권위(남들이 얼마나 링크했나?)

- **신선도(FreshnessScore)**: 1 / (현재시각 - 마지막변경시각) 형태로, 오래된 페이지일수록 재수집 필요성이 높아지도록 설계

    => 마지막 수집 후 흐른 시간 (오래될수록 다시 긁어야 함)

- **트래픽(TrafficSignal)**: 검색 로그에서 추출한 해당 URL의 쿼리 매칭 빈도

    => 실제 사용자들이 검색창에서 얼마나 자주 찾는가?

## 4.1 전면 큐(Front Queue) 구조

위의 점수를 기반으로 우선순위 구간을 N개로 나누고, 각 구간에 별도 FIFO 큐를 배정

```
[Score ≥ 0.9] → Queue_1 (최고 우선순위)
[Score ≥ 0.7] → Queue_2
[Score ≥ 0.5] → Queue_3
...
[Score < 0.1] → Queue_N (최저 우선순위)

```

- **구성**: 1번 큐(최고 우선순위)부터 N번 큐(최저 우선순위)까지 존재

- **큐 선택기(Queue Selector)**: 작업자가 다음 일을 찾을 때, 상위 큐에서 URL을 꺼낼 확률을 높게 설정 (예를 들어 Queue_1은 50% 확률, Queue_2는 30%, Queue_3는 15%, 나머지는 5% 식으로 가중 랜덤 선택을 구현)

- **기아 상태 방지**: 최저 우선순위 큐에도 아주 낮은 확률(예: 1~5%)을 배정하여, 중요도가 낮은 페이지도 언젠가는 반드시 수집되도록 설계

## 4.2 우선순위 점수의 재계산 주기

점수는 고정값이 아니라 다음과 같은 상황에서 재계산이 필요

- URL이 수집된 직후 -> FreshnessScore 리셋

- 외부에서 해당 URL로의 링크가 새로 발견될 때 -> PageRank 업데이트

- 일정 주기(예: 24시간)마다 전체 재산정

## 5. 실무적 난제와 해결책

### 5.1 PageRank 계산의 비용 문제

수십억 개 노드에 대한 PageRank를 수렴할 때까지 반복 계산하는 비용은 방대

Google이 이를 실시간으로 처리하지 않는 이유

**<실용적인 대안>**

- **OPIC(Online Page Impoartance Computiation)**: 페이지를 방문할 때마다 현금(cash)을 조금씩 분배하는 방식으로 PageRank를 근사 계산

    별도의 전역 계산없이 점진적으로 갱신되므로 크롤러에 내장하기 적합

- **주기적 배치 계산**: MapReduce 또는 Spark 기반으로 전체 링크 그래프에 대한 PageRank를 주기적으로 계산하고, 그 결과를 크롤러의 우선순위 입력으로 주입하는 방식

### 5.2 우선순위와 예의(Politeness)의 충돌

> 충돌: 우선순위 높은 URL이 모두 같은 호스트에 몰려 있으면?

예를 들어, wikipedia.org의 URL 100개가 전부 Queue_1에 담겨 있어도, 후면 큐(Back Queue)의 예의 메커니즘이 작동하여 같은 호스트에는 일정 간격으로만 요청

전면 큐(우선순위)는 "누가 중요한가"를 결정하고, 후면 큐(예의)는 "한 사이트에는 1초에 한 번만"이라는 규칙을 강제

=> 이 두 레이어(전면 큐, 후면 큐)는 독립적으로 동작해야 함

### 5.3 크롤 예산 (Crawl Budget)의 배분

실제 Google의 접근 방식을 참고하면, 크롤 예산은 두 요소의 교집합으로 정의

- **크롤 용량(Crawl Capacity)**: 서버 부하를 주지 않고 처리 가능한 최대 속도

- **크롤 수요(Crawl Demand)** : 인기도와 신선도를 기반으로 실제 재수집이 필요한 URL 집합

서버 응답이 느리거나 오류가 잦으면 해당 호스트의 크롤 용량을 자동으로 줄이고, 중요도가 낮고 변경이 없는 URL은 크롤 수요에서 제외

결과적으로 크롤러가 자원을 낭비하지 않고 인덱스 품질을 극대화하도록 동적으로 조율 가능

## 6. 요약 및 결론

**"URL 스케줄링은 단순한 큐 관리가 아니라, 제한된 크롤링 자원으로 인덱스 품질을 극대화하는 최적화 문제"**

**<핵심 설계 원칙 정리>**

- **단일 지표에 의존하지 않는다**:

    PageRank, 신선도, 트래픽 신호를 가중 합산한 복합 점수를 사용

- **우선순위와 예의는 독립적이다**:

    전면 큐(우선순위)와 후면 큐(예의)를 분리하여 각각의 목적을 독립적으로 달성

- **점수는 정적이지 않다**:

    크롤 결과에 따라 지속적으로 재계산되어 시스템이 웹의 변화에 적응

- **기아 상태를 설계적으로 방지한다**:

    낮은 우선순위 URL도 확률적으로 선택되어 영원히 무시되지 않도록 함

=> 결국 좋은 URL 스케줄러는 "중요한 것을 먼저, 예의 바르게, 그리고 변화에 반응하며" 동작하는 시스템
