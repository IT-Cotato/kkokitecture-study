## 1. 문제 제기: 책의 설계는 왜 100명으로 그룹을 제한했는가

교재에서 제시한 그룹 채팅 설계는 Fan-out on Write (쓰기 시점 팬아웃) 방식입니다.

- 방식: 사용자 A가 메시지를 보내면, 그룹 멤버 전원의 개인 큐(Sync Queue)에 메시지를 각각 복사해 줍니다.

- 장점: 읽을 때 자기 큐만 보면 되므로 읽기 속도가 매우 빠르고 직관적입니다.

- 치명적인 한계: 메시지 1건당 쓰기 연산이 멤버 수만큼 곱해집니다($O(N)$).

    - 멤버 10명 $\rightarrow$ 메시지 1건당 10번 쓰기 (여유로움)

    - 멤버 100,000명 $\rightarrow$ 메시지 1건당 100,000번 쓰기 (서버 다운)

- 결론: 책의 '100명 제한'은 시스템 붕괴를 막기 위한 최소한의 타협점이었습니다. 하지만 디스코드나 슬랙처럼 수만 명이 참여하는 채널을 만들려면 이 구조를 반드시 변경해야 합니다.

## 2. Fan-out 전략 세 가지

대규모 트래픽을 다룰 때 비용을 '사용할 때 치를 것인가(Push)', '읽을 때 치를 것인가(Pull)'의 차이입니다. 

### 1) Fan-out on Write (Push방식)

- **방식**: 메시지가 생성되는 즉시, 해당 그룹에 속한 모든 수신자의 개인 큐(Sync Queue) 또는 타임라인 저장소에 메시지를 복사하여 밀어넣는(Push) 방식입니다.

- **비용 구조**:

    - **쓰기 비용** ($O(N)$): 그룹 멤버 수 n에 비례하여 데이터 쓰기 및 네트워크 오버헤드가 선형적으로 폭증
    
    - **읽기 비용** ($O(N)$): 수신자는 아무런 연산 없이 자신의 개인 큐만 조회하면 되므로 극도로 빠름

- **장점 및 한계**: 사용자가 앱을 켰을 때 메시지 로딩 속도가 가장 빠르지만, 멤버 수가 수만 명인 대형 채널에서는 단 1건의 메시지로 인해 수만 번의 Write DB 부하가 발생하는 '쓰기 증폭(Write Amplification)' 현상으로 시스템이 마비됩니다. -> 교재의 100명 인원 제한 사유

- **적합**: 카카오톡 단복방, 소규모 DM (책의 100명 제한)

### 2) Fan-out on Read (Pull방식)

- **메커니즘**: 메시지를 보낼 때 수신자별로 복사하지 않고, 해당 '채널(또는 그룹)의 단일 중앙 로그 저장소'에 딱 1번만 기록합니다. 

수신자들은 앱을 활성화하거나 채널에 진입하는 시점에 이 중앙 저장소로부터 최신 메시지 이력을 긁어옵니다(Pull).

- **비용 구조**: 

    - **쓰기 비용** ($O(1)$) : 송신자가 보낸 메시지를 채널 로그에 한 번만 쓰면 끝
    
    - **읽기 비용**: ($O(N)$) 또는 특정 범위 조회 -> 사용자들이 접속할 때마다 중앙 DB에서 데이터를 조회하고 상태를 취합해야 하므로 읽기 연산 부담 증가

- **장점 및 한계**: 대규모 인원이 모여있는 공개 채널이나 대형 서버에서 쓰기 부하를 획기적으로 줄일 수 있습니다. 하지만 사용자가 동시에 접속하여 과거 이력을 조회할 경우 DB에 대량의 읽기 핫스팟(Read Hotspot)이 발생할 수 있습니다.

- **적합**: 대규모 공개 채널. 인플루언서 피드.

### 3) 하이브리드 (Hybrid)

- **메커니즘**: 시스템의 고부하를 방지하기 위해 그룹의 규모나 사용자의 상태에 따라 Push와 Pull 전략을 유연하게 교차 선택하는 실제 대형 서비스들의 절충안입니다.4

- **대표적인 하이브리드 전환 기준**:

    - **인원수 기준**: 멤버 수 500명 이하의 소규모 그룹이나 DM은 빠른 속도를 위해 Push(Fan-out on Write)를 사용하고, 대형 채널이나 커뮤니티는 Pull(Fan-out on Read) 방식으로 강제 전환합니다.

    - **활성 상태 기준**: 현재 시스템에 웹소켓 연결이 유지되어 있는 '활성(Active) 사용자'에게는 실시간으로 메시지를 Push해주고, 오프라인 상태인 비활성 사용자의 큐에는 데이터를 복사하지 않고 보관했다가 추후 접속 시 Pull해가도록 설계합니다.

## 3. 실제 사례 분석: 디스코드와 슬랙은 어떻게 풀었나?

**사례 1. Discord: "미리 복사하지 않는다, 채널 단위 파티셔닝"**

Discord는 메시지를 미리 각 수신자에게 복사해 두는 대신, **채널(channel) 단위로 메시지를 파티셔닝**해서 저장하고, 접속 중인 클라이언트에게는 실시간으로 브로드캐스트하는 방식을 택했습니다.

- **저장소의 진화와 기술적 한계 극복**

    1. **MongoDB 시절 (초기)** : 
    
        단일 MongoDB 복제 세트에 모든 메시지를 저장했으나, 메시지가 1억 건을 넘어서면서 데이터 인덱스가 메모리에 다 들어가지 않아 읽기/쓰기 지연시간이 들쭉날쭉해지는 핫스팟 장애가 발생했습니다.
    
    2. **Cassandra 시절 (성장기)** : 
    
        Snowflake ID 기반으로 '채널 ID + 시간 버킷(Bucket)'을 묶어 파티셔닝 키로 사용하여 데이터를 분산했습니다. 
        
        덕분에 특정 채널의 메시지가 한 노드에 모여 읽기 최적화가 이루어졌습니다.

    3. **ScyllaDB + Rust 데이터 레이어 (현재)** : 
    
        메시지가 조(Trillion) 단위로 늘어나자 Java 기반인 카산드라의 예측 불가능한 GC(Garbage Collection) 지연시간과 LSM 트리 구조 특유의 읽기 핫스팟이 문제가 되었습니다. 
        이를 해결하기 위해 C++ 기반의 ScyllaDB로 전면 전환하고, 그 앞단에 Rust로 작성된 데이터 서비스 계층(중간 레이어)을 추가했습니다.

=> 저장소는 채널 단위 로그 저장만 전담하고 실시간 전달은 웹소켓 레이어가 찢어서 전송하는 구조로 분리했습니다.

---

**사례 2. Slack: "채널을 서버에 분산한다, Consistent Hashing"**

Slack은 Discord와 다른 각도에서 문제를 풀었습니다. 핵심은 **"채널을 서버에 어떻게 매핑할 것인가"** 입니다.

메시지 전달 흐름은 다음과 같습니다.

```
[Slack 메시지 흐름]
Client → Webapp(HTTP POST) → 로그 기록/인덱싱
                      → Admin Server → Channel Server(해당 채널 담당)
                                                  ↓
                      채널을 구독 중인 모든 Gateway Server에 브로드캐스트
                                                  ↓
                      각 Gateway Server → 자신에게 연결된 클라이언트에게 전달
```

주목할 점은 두 가지입니다.

1. **컨시스턴트 해싱으로 장애 복구 시간 최소화**: 

    CHARM(Consistent Hash Ring Manager)이 상태가 나쁜 Channel Server를 빠르게 교체하며, 새 서버는 20초 안에 트래픽을 받을 준비를 마칩니다.

2. **아키텍처 자체의 진화**: 

    초기에는 클라이언트가 Channel Server에 직접 메시지를 보내고 서버가 브로드캐스트 후 영속화를 하는 구조였지만, 서버가 영속화 전에 죽으면 메시지가 유실될 위험이 있었습니다. 
    
    이를 해결하기 위해 클라이언트가 먼저 Webapp에 HTTP POST로 메시지를 보내고, Webapp이 영속화·인덱싱을 마친 뒤 Channel Server에 실시간 브로드캐스트를 요청하는 구조로 바뀌었습니다.

 Slack의 채널 서버는 책에서 말하는 "채팅 서버"와 개념적으로 유사하지만, 100명 제한이 없는 대신 "채널을 어느 서버가 담당할지"를 컨시스턴트 해싱으로 결정하여 채널 수가 늘어나도 특정 서버에 부하가 몰리지 않도록 설계했습니다.

## 5. 비교 정리

| | 책의 설계 (소규모 그룹) | Discord | Slack |
|:---|:---|:---|:---|
| **핵심 전략** | Fan-out on Write (수신자별 sync queue 복사) | 채널 단위 파티셔닝 저장 + 실시간 push | 컨시스턴트 해싱 기반 채널 서버 분산 |
| **인원 제한 이유** | 멤버 수만큼 쓰기 비용이 곱해지기 때문 | 채널당 메시지량 편차가 워낙 커서 저장소 자체를 재설계 | 채널 수가 워낙 많아 서버 매핑 문제로 치환 |
| **저장소** | 키-값 저장소 (message_id, channel_id 복합키) | Cassandra → ScyllaDB | Vitess(MySQL 샤딩) 기반 |
| **확장 축** | 그룹 인원 수 | 채널당 메시지 처리량 | 채널의 총 개수 |
| **핵심 교훈** | 단순함의 대가로 규모 제한 발생 | "미리 복사"가 아니라 "잘 파티셔닝된 로그 + 실시간 브로드캐스트" | "누구에게 복사할지"보다 "누가 이 채널을 담당할지"가 핵심 문제 |

## 6. 결론: 100명 제한은 임시방편이 아니라 합리적 트레이드오프

**"그룹 채팅을 몇 명까지 지원할 것인가"라는 질문은 사실 "팬아웃 비용을 어느 시점에, 어떤 단위로 분산시킬 것인가"라는 질문과 같습니다.**

- 책의 설계(Fan-out on Write + 100명 제한)는 **면접 상황에서 시간 내에 설명 가능한 가장 단순한 해법**이며, 실제로 소규모 그룹에는 충분히 합리적입니다.

- Discord는 팬아웃 문제를 애초에 "수신자별 복사"가 아니라 **"채널 단위 저장 + 접속자에게만 실시간 전달"**로 바꿔서 인원 제한 없는 대형 커뮤니티를 지원합니다.

- Slack은 채널 자체를 **컨시스턴트 해싱으로 분산**시켜, 문제를 "그룹 인원 수"가 아니라 "채널 개수를 서버에 어떻게 분산할 것인가"로 치환했습니다.

결국 대규모 그룹 채팅 확장성의 본질은 **"메시지 1건을 누구에게, 언제, 어떤 단위로 복제할 것인가"** 를 결정하는 문제이며, 책의 100명 제한은 이 트레이드오프의 한쪽 극단(단순성 우선)을 선택한 결과라고 정리할 수 있습니다.
