# 넷플릭스(Netflix) 알림 시스템 사례 분석: RENO, Zuul Push, 메시징 오케스트레이션

## 1. 문제 정의: 2억 2천만 회원을 실시간으로 동기화한다는 것

**규모와 디바이스 다양성**

- 넷플릭스는 2억 2천만 명이 넘는 활성 회원을 보유하고 있으며, 각 회원은 세션마다 시청, 프로필 변경, 찜 목록(My List) 추가, 멤버십 플랜 변경 등 다양한 행동을 끊임없이 발생시킵니다.

- 한 사용자가 동시에 여러 디바이스(폰, 노트북, 스마트TV, 게임 콘솔 등)로 같은 계정에 접속하는 경우가 흔합니다. 
    - ex) 아이폰에서 보던 콘텐츠를 노트북으로 이어보는 식의 흐름이 자연스럽게 발생

**기존 요청/응답 모델의 한계**

- 전통적인 request/response방식으로는 이런 변화를 "사용자가 다시 요청할 때"까지 반영할 수 없어, 디바이스 간 경험이 어긋나는 문제가 생깁니다.

- 연령 등급 변경처럼 즉시 반영되어야 하는 정보가 지연되면 단순 불편을 넘어 실질적인 문제로 이어질 수 있습니다.

- 이를 해결하기 위해 넷플릭스는 서버가 먼저 디바이스에 통신을 시작하는(server-initiated) 구조가 필요하다고 판단하고, 이 글에서 다룰 세 가지 시스템 **'RENO, Zuul Push, 메시징 오케스트레이션 서비스'**를 구축합니다.

## 2. RENO: 우선순위 기반 이벤트 처리 시스템

### 2.1 단일 이벤트 소스로의 추상화

RENO가 추적해야 하는 이벤트(시청 활동, 추천 갱신, 멤버십 변경, 프로필 변경 등)는 넷플릭스 내부의 서로 다른 시스템에서 제각각 발생합니다.

- 이를 단순화 하기 위해서 Event Management Engine이라는 간접 계층(level of indirection)을 두어, RENO 입장에서는 모든 이벤트가 마치 하나의 소스에서 들어오는 것처럼 처리합니다.

- 내부 시스템이 늘어나거나 바뀌어도 RENO 자체의 처리 로직은 영향을 받지 않도록 설계된 추상화 계층입니다.

### 2.2 우선순위 기반 샤딩과 큐 분리

들어오는 이벤트를 우선순위별로 분리하여 각각 전용 AWS SQS 큐와 그에 대응하는 컴퓨팅 인스턴스 클러스터로 라우팅합니다.

- 연령 등급 변경처럼 즉시 반영돼야 하는 업데이트를 상대적으로 빠르게 처리 가능합니다.

- 우선순위별로 큐와 클러스터가 독립적으로 분리되어 있어, 처리 계층에서 서버를 추가하는 것만으로 수평적 확장이 가능합니다.

- 이 샤딩 전략이 RENO 저체의 수평 확장성을 보장하는 핵심 설계 결정입니다.

### 2.3 신선도(Staleness) 필터: 오래된 이벤트는 버린다

 
이벤트가 생성된 지 오래되어 기준 시간(Threshold)을 넘기면, 시스템은 이를 처리하지 않고 그대로 폐기합니다.

- 즉시 전달되지 않으면 가치가 거의 없는 이벤트가 많기 때문에, 무의미해진 이벤트를 계속 처리하느라 자원을 낭비하지 않도록 하는 장치입니다.

- 단순히 "모든 이벤트를 빠짐없이 처리한다"가 아니라, "더 이상 의미 없는 이벤트는 빠르게 걸러낸다"는 효율 중심의 설계 철학을 보여주는 부분입니다.

### 2.4 처리 규모와 썬더링 허드(Thundering Herd) 문제

넷플릭스는 피크 시점 기준 초당 약 15만 건의 이벤트를 처리합니다.

- 짧은 시간에 이벤트가 한꺼번에 몰리면 내부.외부 다운스트림 서비스에 부하가 집중되는 썬더링 허드 문제가 발생할 수 있습니다.

- 우선순위 기반 샤딩 클러스터별 처리 분산이 이 문제를 완화하는 핵심 장치로 작동합니다.

## 3. Push-Pull 하이브리드 전달 모델

### 3.1 베스트 에포트 푸시 + 영속 저장소

RENO는 디바이스별로 발행된 모든 알림을 Cassandra에 영속적으로 저장합니다.

- 서버는 온라인 상태인 디바이스에 best-effort 방식으로 즉시 푸시를 시도합니다.

- 동시에 디바이스는 애플리케이션 생명주기의 여러 시점에서 자신의 주기에 맞춰 백엔드에 직접 폴링(pull)할 수 있습니다.

- 즉 "푸시를 보냈다가 실패하면 재시도한다"는 단순한 구조가 아니라, "푸시는 최선을 다해 즉시 보내되, 클라이언트가 언제든 와서 가져갈 수 있는 영속 저장소를 항상 유지한다"라는 이원화 전략입니다.

### 3.2 왜 푸시만으로는 부족한가

AWS SNS 같은 순수 푸시 전용 시스템과 달리, RENO는 의도적으로 push-and-pull 조합을 채택합니다.

- 디바이스가 오프라인이거나 네트워크가 불안정하면 푸시 메시지는 그대로 유실될 수 있습니다.

- 구형 디바이스 중에는 애초에 푸시 자체를 지원하지 않는 경우도 존재합니다. 이런 디바이스는 pull 경로만으로도 동기화가 가능해야 합니다.

=> 결과적으로 "Push가 실패해도 Pull이 받쳐준다"는 이중 안전망 구조가 완성되고, 클라이언트(앱) 수신 구간에서는 넷플릭스의 인앱 푸시 메시징 시스템을 거쳐 최종적으로 단말에 도달합니다.

## 4. Zuul Push: 자체 구축한 영속 연결 인프라

### 4.1 왜 자체 인프라가 필요했는가

스마트 TV, 게임 콘솔, 웹 브라우저처럼 표준 모바일 푸시 생태계(APNs/FCM) 밖에 있는 디바이스가 다수 존재합니다.

- 넷플릭스는 자사의 API 게이트웨이인 Zuul(하루 1,000억 이상의 요청을 처리하는 넷플릭스 클라우드 트래픽의 관문)의 코드베이스를 상당 부분 공유하면서, 별도의 실시간 푸시 서비스인 Zuul Push를 만들어냅니다.

- 목표는 클라우드에서 발생한 데이터(예: 개인화된 추천)를 디바이스가 직접 요청하기 전에 먼저 밀어 넣는 것입니다.

### 4.2 아키텍처

- Netty 기반의 고성능 비동기 서비스로, WebSocket과 SSE(Server-Sent Events) 프로토콜을 모두 지원하여 클라이언트와 영속적인 연결을 유지합니다.

- 클라이언트는 AWS 위에서 동작하는 Zuul Push 클러스터에 직접 연결하며, 이 연결을 통해 서버가 먼저 메시지를 내려보낼 수 있습니다.

- 전역적으로 복제되는 클라이언트 레지스트리(globally replicated client registry)를 통해 특정 클라이언트가 현재 어느 서버에 연결되어 있는지를 추적합니다.
    - 넷플릭스 내부의 어떤 마이크로서비스든 이 라우팅 인프라를 거쳐 전 세계 어디서든 원하는 클라이언트에게 메시지를 보낼 수 있습니다.

- 백엔드 메시지 라우팅 계층은 Kafka 기반의 푸시 메시지 처리 큐 위에서 동작하도록 구성되어, 다량의 메시지를 안정적으로 비동기 처리합니다.

### 4.3 해결한 문제와 운영 규모

QCon 발표에서는 Zuul Push 설계 시 마주한 세 가지 핵심 난제로 썬더링 허드(thundering herd), 상태를 가진 연결(stateful connection) 관리, 메시지 라우팅을 선택했습니다.

- 피크 시점 기준 550만 개 이상의 "항상 연결된(always-on)" 클라이언트 연결을 동시에 유지하며 계속 성장 중인 수치입니다.

- 연결 자체가 상태(state)를 가지기 때문에, 일반적인 무상태(staleness) HTTP API 서버보다 운영.오토스케일링 난이도가 훨씬 높습니다.

### 4.4 활용 사례: 폴링을 푸시로 대체

대표 사례는 홈 화면의 추천 그리드("List of List of Movies", LoLoMo)입니다.

- 사용자별 맞춤 추천이 클라우드에서 갱신되는 즉시 클라이언트로 푸시되어, 디바이스가 새로고침을 위해 주기적으로 폴링할 필요 자체를 없앱니다.

- "필요할 때마다 서버에 물어본다"는 패턴에서 "준비되는 즉시 서버가 먼저 알려준다"는 패턴으로 전환함으로써, 불필요한 폴링 트래픽 자체를 줄이는 효과가 있습니다.

## 5. 메시징 오케스트레이션: 인앱과 외부 채널의 통합

### 5.1 구조

자바로 구현된 메시징 인프라가 AWS의 여러 리전에 걸쳐 EC2 인스턴스 클러스터로 배포되어 운영됩니다.

- 넷플릭스 메시징 엔지니어링 팀이 이 플랫폼과, 실제로 발송되는 메시지 자체의 설계를 함께 담당합니다.

### 5.2 처리 흐름

내부 이벤트가 메시징 플랫폼에 수집되면, 완전한 형태의 메시지로 변환된 뒤 외부 채널 또는 인앱 채널 중 하나로 라우팅합니다.

- 외부 채널(예:APNs를 통한 iOS푸시)로 보낼 때는, 필요한 정보를 얻기 위해 다른 넷플릭스 서비스들을 호출하고, 적절한 포맷으로 메시지를 조립한 뒤 곧바로 전달합니다.

- 인앱 채널의 경우, 같은 이벤트 파이프라인을 공유하면서도 화면 내 배너.인박스 메시지 같은 형태로 별도 전달합니다.

### 5.3 페더레이션(Federated) 아키텍처로의 진화

기존에는 UI(웹/앱) 팀이 각각의 화면 내 주요 기능 버튼마다 관련 백엔드 서비스와 개별적으로 통합을 만들어야 했습니다.

- 넷플릭스는 이를 완전히 페더레이션된 구조로 전환하는 방향으로 발전시키는 중입니다.
    - UI플랫폼은 오직 인앱 메시징 서비스 하나와만 인터페이스하면 되고, 어떤 정보를 어떻게 전달할지에 대한 페이로드 계약(payload contract)만 명시하면 됩니다.

- 그 뒤의 다운스트림 호출, 풀백 처리 등은 모두 메시징 서비스가 대신 처리하며, UI팀의 통합 비용과 유지보수 부담을 크게 줄이는 것이 목표입니다.

## 6. 종합 아키텍처

```text
[내부 이벤트 발생: 시청 활동 / 프로필 변경 / 멤버십 변경 / 추천 갱신 등]
        │
        ▼
[Event Management Engine] - 단일 이벤트 소스로 추상화
        │
        ▼
[우선순위별 AWS SQS 큐] ──> [우선순위별 처리 클러스터]
        │  (신선도 필터로 만료 이벤트 폐기, 우선순위 단위로 수평 확장)
        │
        ├─▶ Push 경로 (best-effort, 즉시 시도)
        │     │
        │     ├─▶ 모바일 ──> 메시징 오케스트레이션 서비스 ──> APNs / FCM
        │     │
        │     └─▶ 웹·TV·콘솔 ──> Zuul Push (WebSocket/SSE, Kafka 기반 라우팅, 영속 연결)
        │
        └─▶ Pull 경로 (안전망) 
              │
              └─▶ Cassandra (디바이스별 알림 저장소) <── 디바이스가 자체 주기로 폴링
```
- RENO가 "무엇을 , 얼마나 급하게 보낼 것인가"를 결정하면, 그 결과가 Push 경로와 Pull 경로로 동시에 흘러들어가는 구조입니다.

- 채널별 전달의 세부 사항(외부 vs 인앱, iOS vs TV)은 메시징 오케스트레이션 서비스와 Zuul Push가 나누어 흡수합니다.

## 7. 핵심 설계 결정과 그 이유

|설계 결정|채택한 이유|
|:---|:---|
|Event Management Engine으로 이벤트 소스 추상화|내부 시스템이 늘어나거나 바뀌어도 RENO 자체 로직이 영향받지 않도록 분리|
|이벤트를 우선순위별 SQS 큐로 샤딩|중요 이벤트의 지연을 방지하고, 클러스터 단위로 독립적인 수평 확장을 가능하게 함|
|신선도(Stateness) 필터 적용|의미가 사라진 오래된 이벤트 처리에 자원을 낭비하지 않기 위함|
|Push와 Pull을 함께 사용|오프라인 상태, 네트워크 불안정, 푸시 미지원 구형 디바이스까지 모두 커버하기 위함|
|Cassandra에 디바이스별 알림 영속 저장|디바이스가 자신의 생명주기에 맞춰 언제든 직접 동기화할 수 있는 안전망 확보|
|Zuul 기반 자체 Push 인프라(Zuul Push) 구축|APNs/FCM이 커버하지 못하는 TV.콘솔.브라우저 등 비표준 디바이스까지 실시간 푸시를 지원하기 위함|
|메시징 오케스트레이션 서비스로 채널 통합|채널이 늘어날수록 UI팀이 각 백엔드와 개별 통합해야 하는 부담을 없애기 위함|

## 8. 요약 및 결론

**넷플릭스 알림 시스템은 하나의 서비스가 아니라, '얼마나 급한가(RENO)', '어떻게 도달시킬 것인가(Zuul Push)', '어떤 채널로 통합할 것인가(메시징 오케스트레이션)'를 각각 책임지는 세 계층의 합**
