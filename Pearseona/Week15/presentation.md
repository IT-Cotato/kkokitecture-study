## 1. 문제 제기: 책은 왜 "비디오 삭제"를 한 줄로만 남겼는가

교재는 추가로 논의해 보면 좋을 내용으로 다음 네 가지를 나열합니다.

> "API 계층의 규모 확장성 확보 방안 / 데이터베이스 계층의 규모 확장성 확보 방안 / 라이브 스트리밍 / 비디오 삭제"

교재의 비디오 업로드 파이프라인에는 같은 비디오의 사본이 최소 다음 위치에 흩어져 있습니다.

- **원본 저장소**: 트랜스코딩 이전의 원본 비디오 (BLOB 저장소)
- **트랜스코딩 비디오 저장소**: 해상도·비트레이트·코덱 조합별로 인코딩된 여러 사본
- **CDN**: 트랜스코딩된 비디오가 다시 전 세계 엣지 서버에 캐시되어 있음
- **메타데이터 데이터베이스**: 샤딩·다중화되어 여러 노드에 복제
- **메타데이터 캐시**: 별도로 다중화되어 있는 인메모리 사본
- **트랜스코딩 완료 큐**: 만약 삭제 시점에 아직 트랜스코딩이 진행 중이라면, 큐에는 "곧 완료될 예정"인 이벤트가 남아 있을 수 있음

즉 "비디오 삭제"는 하나의 `DELETE` 문이 아니라, **분산된 여러 저장소·캐시·큐에 걸쳐 있는 사본을 일관되게 지워야 하는 분산 삭제(distributed deletion) 문제**입니다. 

여기에 EU 사용자가 있다면 GDPR의 "잊혀질 권리(right to be forgotten, Article 17)"까지 더해서, "지운 것처럼 보이는 것"과 "실제로 복구 불가능하게 지워진 것"을 구분해야 하는 규제 문제가 추가됩니다.

## 2. 나이브한 방식의 한계: "삭제 = DELETE 문"이라는 착각

가장 단순한 구현은 다음과 같습니다.

```
DELETE FROM videos WHERE video_id = ?;
DELETE FROM video_files WHERE video_id = ?;  -- S3/BLOB 파일도 같이 삭제
```

이 방식(하드 삭제, hard delete)은 직관적이지만 몇 가지 문제가 발생합니다.

- 다른 테이블이 `video_id`를 외래 키로 참조하고 있다면(댓글, 재생목록, 조회 기록 등) 참조 무결성이 깨지거나, `ON DELETE CASCADE`로 인해 의도하지 않은 연쇄 삭제가 발생할 수 있습니다.

- 삭제 즉시 DB 행이 사라지므로, "왜 지난달 조회수가 갑자기 줄었지?" 같은 분석이나 신고 처리를 위한 감사(audit) 기록이 함께 사라집니다.

- 그리고 **DB에서 행을 지워도 백업, 로그, 검색 인덱스, CDN 캐시, 메타데이터 캐시에는 여전히 그 데이터가 남아 있습니다.** 

    실제로 "삭제됐다"고 믿었지만 백업이나 로그에서 개인정보가 복구 가능한 채로 남아 있는 경우가 GDPR 위반의 흔한 원인입니다.

반대로 가장 흔히 쓰이는 대안인 소프트 삭제(soft delete, `deleted_at` 또는 `is_deleted` 플래그만 세우는 방식)는 참조 무결성과 이력 보존 문제는 해결하지만, 정반대의 문제를 만듭니다.

행은 여전히 DB 안에 그대로 존재하고, 관리자 권한이 있으면 여전히 조회할 수 있으며, 익스포트나 검색 인덱스에도 남아 있는 경우가 많습니다. 

즉 **소프트 삭제는 애초에 "삭제(erasure)"가 아니라 "숨김(suppression)"에 가깝습니다.**

## 3. Soft Delete vs Hard Delete 정리

| | Soft Delete | Hard Delete |
|:---|:---|:---|
| **동작 방식** | `deleted_at`/`is_deleted` 플래그만 세우고 행은 유지 | 행/파일을 물리적으로 제거 |
| **장점** | 되돌리기(undo) 가능, 참조 무결성 유지, 분석·감사 이력 보존 | 저장 공간 확보, 쿼리 성능 유지(필터링 불필요), "진짜로 지웠다"는 확실성 |
| **단점** | 관리자 조회·백업·인덱스에 여전히 데이터 존재 → GDPR 삭제 요건 미충족 가능 | 참조 무결성 깨짐, 되돌리기 불가, 관련 통계·이력 손실 |
| **GDPR 관점** | 그 자체로는 "지운 것"으로 인정되기 어려움 | 필요조건이지만, 백업·로그·CDN까지 지워야 충분조건이 됨 |
| **적합한 경우** | 사용자가 실수로 지운 것을 복구해야 하는 일반적인 삭제(휴지통 기능) | 개인정보 삭제 요청, 저작권 신고에 따른 즉시 차단이 필요한 경우 |

정리하면 두 방식은 대립 관계가 아니라 **단계**에 가깝습니다. 

소프트 삭제로 우선 서비스에서 즉시 숨기고(사용자 경험 관점의 "삭제 완료"), 이어서 백그라운드 잡이 실제 저장소·백업·캐시에서 하드 삭제 또는 비식별화(anonymization)를 수행합니다.

 이를 **소프트 TTL(soft TTL)과 하드 TTL(hard TTL)의 조합**이라고 부르기도 합니다. 
 
 소프트 TTL은 즉시 마스킹해서 "지금 당장은 안 보이게" 만들고, 하드 TTL은 정해진 시간 뒤에 모든 사본에서 되돌릴 수 없는 최종 삭제(purge)를 수행하는 방식입니다.

## 4. 어디를, 언제 지울 것인가

교재의 비디오 업로드 아키텍처를 삭제 관점에서 다시 보면 지워야 할 대상이 저장소마다 성격이 다릅니다.

| 저장 위치 | 데이터 성격 | 삭제 난이도 |
|:---|:---|:---|
| 메타데이터 DB (샤딩·다중화) | 구조화된 행 데이터 | 상대적으로 쉬움 — 소프트 삭제 플래그 후 배치로 하드 삭제 |
| 메타데이터 캐시 | 다중화된 인메모리 사본 | 이벤트 기반으로 각 노드에 무효화 메시지 전파 필요 |
| 원본 저장소 (BLOB) | 원본 비디오 파일 | 파일 단위 삭제는 쉽지만, 스냅샷/버전 관리 기능이 있다면 이전 버전이 남을 수 있음 |
| 트랜스코딩 비디오 저장소 | 해상도별 다중 사본 | 인코딩 조합 수만큼 파일이 여러 개 → 전부 찾아 지워야 함 |
| CDN 엣지 캐시 | 전 세계에 분산된 캐시 사본 | 전파 지연 존재 — 모든 엣지 노드에 퍼지(purge) 요청이 도달할 때까지 시간차 발생 |
| 트랜스코딩 완료 큐 | 아직 처리되지 않은 이벤트 | 삭제 요청이 들어온 시점에 이미 큐에 들어있는 이벤트라면, 완료 핸들러가 뒤늦게 메타데이터를 되살릴 위험 |
| 백업 스냅샷 | 특정 시점의 전체 스냅샷 | 개별 레코드만 골라 지울 수 없는 경우가 많음 — 별도 전략 필요 |

여기서 특히 두 가지의 흥미로운 부분을 살펴봐야 합니다.

**(1) 큐에 남아있는 이벤트와의 경합(race condition)**

만약 사용자가 트랜스코딩이 끝나기 전에 삭제를 요청했는데, 이미 큐에 들어간 완료 이벤트가 뒤늦게 처리되면 **삭제된 메타데이터가 되살아나는 문제**가 생깁니다. 

이를 막으려면 완료 핸들러가 메타데이터를 갱신하기 직전에 "이 비디오가 삭제 대기 상태인지"를 한 번 더 확인하는 멱등성(idempotent) 체크가 필요합니다.

**(2) CDN 캐시 무효화의 전파 지연**

CDN은 원본이나 중개 서비스가 퍼지(purge) API를 호출하면 그 신호가 전 세계 엣지 노드로 전파되는 구조입니다. 

이 전파에는 보통 수 초에서 수 분이 걸리며, 일부 CDN 제공자는 URL 단위 퍼지 대신 서로게이트 키(surrogate key) 방식의 태그 기반 무효화를 지원해 한 번의 호출로 관련된 모든 캐시를 지울 수 있게 합니다. 

다만 이 전파 시간 동안에는 어떤 엣지 노드는 이미 삭제를 반영했는데 다른 엣지 노드는 여전히 옛 비디오를 서빙하는 "부분적으로만 지워진" 상태가 필연적으로 발생합니다.

즉 "100% 즉시 전체 삭제"는 이론적으로도 보장하기 어렵습니다.

## 5. GDPR '잊혀질 권리'와 시스템 설계의 충돌

GDPR 제17조는 사용자가 개인정보의 삭제를 요구할 권리를 규정합니다. 문제는 이 요구가 다른 시스템 요구사항과 정면으로 충돌한다는 점입니다.

- **감사 로그/무결성 요구**: 신고·저작권 침해 이력, 결제 기록 등은 법적으로 일정 기간 보존해야 하는 경우가 많습니다.

- **백업**: 암호화된 백업 스냅샷에서 특정 사용자 한 명의 데이터만 골라 지우는 것은 기술적으로 매우 번거롭거나 불가능에 가깝습니다.

- **성능**: 매 삭제 요청마다 모든 저장소·인덱스·백업을 스캔해서 관련 데이터를 찾아 지우는 것은 확장성이 없습니다.

이 모든것을 동시에 만족시키기 어렵다는 것이 여러 실무 사례에서 공통으로 지적되는 지점입니다. 

소프트 삭제는 관리자가 여전히 읽을 수 있다는 점에서 규제 기관의 눈에는 "삭제"로 인정받기 어렵고, 단순 문자열 치환("REDACTED")을 이용한 비식별화도 백업에는 원본 값이 그대로 남아 있고 치환의 완전성을 검증하기 어렵다는 한계가 있습니다.

**대안으로 제시되는 방식: 크립토 슈레딩(crypto-shredding)**

크립토 슈레딩은 데이터를 물리적으로 찾아 지우는 대신, **암호화 키를 파기해서 데이터를 읽을 수 없게 만드는 방식**입니다. 

사용자별로 별도의 데이터 암호화 키(DEK)를 두고, 그 키를 다시 사용자 단위의 키 암호화 키(KEK)로 감싸 두면, 삭제 요청이 들어왔을 때 실제 비디오 파일이나 메타데이터를 건드리지 않고 **그 사용자의 KEK 하나만 파기**하는 것으로 사실상의 삭제 효과를 낼 수 있습니다. 

유럽 데이터보호위원회(EDPB) 가이드라인 5/2019 등에서도 암호화 알고리즘이 충분히 강하고(AES-256 이상), 키 파기가 되돌릴 수 없으며, 그 파기 과정이 감사 가능하다면 암호학적 삭제를 잊혀질 권리의 유효한 이행 방식으로 인정하고 있습니다.

이 방식은 대략 다음과 같은 흐름이 됩니다.

```
사용자의 삭제 요청
  → [1단계] 소프트 TTL: 메타데이터에 deleted_at 세팅 + 캐시 무효화 이벤트 발행
             → API 서버가 즉시 "찾을 수 없음"으로 응답 (사용자 체감상 즉시 삭제)

  → [2단계] 이벤트 기반 전파: 삭제 이벤트를 메시지 큐에 발행
             → 메타데이터 캐시 각 노드가 구독하여 로컬 캐시 무효화
             → CDN 퍼지 API 호출 (서로게이트 키 기반 일괄 무효화)

  → [3단계] 하드 TTL(배치 잡, 예: 매주 갱신 주기에 포함):
             → 원본/트랜스코딩 저장소에서 실제 파일 삭제 또는 사용자별 KEK 파기
             → 메타데이터 DB에서 소프트 삭제된 행을 실제로 hard delete하거나 개인 식별자를 비식별화

  → [4단계] 삭제 완료 로그(deletion ledger) 기록
             → 이후 백업이 복원되더라도, 이 로그를 replay하여 같은 레코드를 다시 파기 처리
```

여기서 3단계를 "매번 즉시"가 아니라 배치 잡으로 처리하는 이유는, 트랜스코딩 완료 큐를 매주 처리하는 job server와 마찬가지로 **삭제도 일정 주기로 모아서 처리하는 편이 시스템 부하 관점에서 합리적**이기 때문입니다. 

다만 GDPR은 삭제 요청 접수 후 통상 한 달 이내 처리를 요구하므로, 이 배치 주기가 그 기한을 넘지 않도록 설계해야 합니다.

## 6. 비교 정리

|| Soft/Hard Delete 조합 | GDPR/크립토 슈레딩 대응 |
|:---|:---|:---|
| **핵심 아이디어** | "비디오 삭제"라는 주제만 제시, 구체적 설계 없음 | 즉시 숨김(소프트) + 배치 완전 삭제(하드)를 단계적으로 분리 | 데이터를 지우는 대신 암호화 키를 파기해 사실상 삭제 |
| **다루는 문제** | 무엇을 논의해야 하는지(범위) | 사용자 체감 속도 vs 데이터 정합성의 트레이드오프 | 법적 삭제 요건 vs 백업/감사 로그 보존 요건의 충돌 |
| **한계** | 구체적 아키텍처 부재 | 여러 저장소·캐시·큐 간 삭제 전파 지연이 여전히 존재 | 키 관리 인프라(KMS) 구축·운영 비용, 제3자 처리자까지는 강제하기 어려움 |
| **관련 기존 설계 요소** | 원본/트랜스코딩 저장소, CDN, 메타데이터 DB/캐시, 완료 큐 | 트랜스코딩 완료 큐와 동일한 "이벤트 기반 비동기 처리" 패턴 재사용 | job server의 주기적 갱신 주기에 하드 삭제 배치를 편입 |

## 7. 결론

비디오 삭제는 겉보기엔 단순한 CRUD 기능이지만, 파고들면 세 가지 독립적인 문제가 얽혀 있다는 것을 확인할 수 있었습니다.

1. **삭제는 위치의 문제입니다.**

     하나의 비디오는 원본 저장소, 트랜스코딩 저장소, CDN 엣지 캐시, 메타데이터 DB, 메타데이터 캐시, 그리고 아직 처리되지 않은 큐 이벤트까지 최소 6곳 이상에 흩어져 있습니다. 
     
     "삭제 버튼을 눌렀다"는 사용자 관점의 단일 행위가, 시스템 내부에서는 서로 다른 속도와 방식으로 처리되는 여러 개의 독립적인 삭제 작업으로 쪼개진다는 점이 이번 학습의 핵심이었습니다.

2. **삭제는 타이밍의 문제입니다.**

     Soft delete와 hard delete는 대립하는 두 선택지가 아니라, 사용자 체감 속도(즉시 숨김)와 시스템 정합성(완전한 제거) 사이의 간극을 메우는 단계적 파이프라인으로 이해하는 게 더 정확했습니다.
     
    이 과정에서 큐에 남은 이벤트가 삭제된 데이터를 되살리는 경합 조건, CDN 전파 지연으로 인해 "부분적으로만 지워진" 상태가 필연적으로 존재한다는 점은, 분산 시스템에서 "삭제 완료"라는 상태가 사실 이분법이 아니라 스펙트럼에 가깝다는 걸 보여줬습니다.

3. **삭제는 증명의 문제입니다**

    GDPR 같은 규제 앞에서는 "안 보이게 만드는 것"과 "실제로 복구 불가능하게 만드는 것"이 명확히 구분되고, 후자만 인정받습니다. 
    
    특히 백업이나 감사 로그처럼 물리적 삭제가 다른 요구사항과 충돌하는 지점에서는, 데이터 자체가 아니라 암호화 키를 파기하는 크립토 슈레딩처럼 "삭제"의 정의 자체를 재설계하는 접근이 필요합니다.
    
    삭제했다는 사실을 사후에 감사 가능하게 남겨야 한다는 것도, 단순히 지우는 것 이상으로 설계에서 신경 써야 할 부분입니다.
