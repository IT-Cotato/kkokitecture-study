# 99.99% 가용성을 향한 여정: SLA와 DR(재해 복구) 전략 분석

> **원문:** [AWS Whitepaper - Disaster Recovery of Workloads on AWS]
(https://docs.aws.amazon.com/whitepapers/latest/disaster-recovery-workloads-on-aws/disaster-recovery-options-in-the-cloud.html)

> **주제 선정 이유:** 1장에서 다룬 ‘데이터 센터’와 ‘다중화’는 결국 서비스의 안정적인 운영, 즉 가용성을 확보하기 위한 개념이라고 생각했습니다. 특히 클라우드 환경에서는 가용성이 곧 서비스의 생존과 직결되기 때문에, 이론을 넘어 실제로 사용되는 지표인 SLA와 복구 전략(DR)에 대해 더 알아보고자 이 주제를 선택했습니다.

---

# 1. 배경

### 1.1 가용성(Availability)이란 무엇인가?
가용성이란 시스템이 장애 없이 **정상적으로 서비스를 제공할 수 있는 상태(Up-time)의 비율**을 말합니다.

- **직관적 의미:** "1년 365일 중 우리 서비스가 얼마나 정상적으로 작동하고 있는가?"를 나타내는 지표입니다.
- **공식:** $가용성 = \frac{정상 운영 시간}{전체 시간(정상 운영 + 장애 시간)} \times 100(\%)$
- 가용성이 높다는 것은 그만큼 시스템이 견고하고, 장애가 발생해도 빠르게 복구된다는 뜻입니다.

### 1.2 SLA(Service Level Agreement)란 무엇인가?
SLA는 서비스 제공자가 고객에게 약속하는 **'서비스 품질 수준'**에 대한 법적/비즈니스적 계약입니다.

- **직관적 의미:** "우리 서비스가 한 달에 이만큼 이상 중단되면 이용료를 깎아줄게" 즉, "이 정도 수준으로 서비스 못 지키면 보상해줄게" 라는 약속입니다.
AWS나 토스 같은 대형 플랫폼이 멈추면 기업 고객들은 막대한 손해를 보기에, 엔지니어는 모든 기술을 동원해 이 **약속된 가용성 지표(예: 99.99%)**를 지켜야 합니다.

### 1.3 DR(Disaster Recovery)이란 무엇인가?
- 지진, 화재, 홍수 또는 리전 전체의 시스템 마비와 같은 거대한 재앙(Disaster)이 발생했을 때, 서비스를 어떻게 다시 살려낼 것인지에 대한 기술적/조직적 계획입니다.

- **직관적 의미:**SLA가 "고객과의 약속"이라면, **DR(재해 복구)**은 그 약속을 지키기 위한 **"실행 전략"**입니다.
- **단순 백업과의 차이:** 백업은 단순히 데이터를 복사해두는 것이지만, DR은 **인프라 전체를 다른 지역(Region)에 새로 구축하거나 즉시 가동시키는 프로세스**를 포함합니다.

### 1.4 가용성 계산의 함정(연쇄 장애) : 왜 서버를 여러 개 두는 다중화가 정답인가?

서버 한 대의 가용성이 90%일 때, 시스템 구성 방식에 따라 결과는 극명하게 갈립니다.

- **직렬 연결 (Serial):** 모든 구성 요소가 동시에 살아야 함 $\rightarrow 0.9 \times 0.9 = 81\%$ (가용성 하락, 장애 포인트 증가)

- **병렬 연결 (Parallel):** 2대를 병렬로 두면, 하나가 죽어도 대안이 있으므로 하나만 살아도 됨 $\rightarrow 1 - (0.1 \times 0.1) = 99\%$ (가용성 상승)

=> 직렬로 연결하면 오히려 가용성이 81%로 떨어지지만, 병렬로 연결하면 99%까지 올라므로 여러 개를 동시에 운영하는 다중화 구조가 사용성을 크게 높여줍니다.
그래서 현재 시스템은 "장애를 막는다"가 아니라 **"장애가 나도 버티게 만든다"**라는 방향으로 설계됩니다.

## 1.5 현대 아키텍처의 철학: "Design for Failure"

과거에는 "장애가 안 나게 관리하자"가 목표였다면, 현대의 대규모 시스템은 **"장애는 무조건 난다. 다만 얼마나 빨리, 자동으로 복구하느냐"**에 집중합니다. 
    - 예시(넷플릭스의 카오스 엔지니어링) : 넷플릭스는 운영 중인 서버를 무작위로 강제 종료시키는 '카오스 몽키'를 실행합니다. 예고 없이 서버가 죽어도 시스템이 자동으로 복구(Self-healing)되는지 실시간으로 검증하기 위함입니다.

# 2. 가용성의 지표: "The Nines" (9의 개수)

가용성은 시스템이 정상적으로 서비스를 제공하는 시간의 비율을 의미합니다.
가용성 숫자는 '9'가 하나씩 늘어날 때마다 엔지니어가 대응해야 하는 기술적 난이도는 기하급수적으로 높아집니다.

| 가용성 (SLA) | 연간 장애 허용 시간 | 기술적 요구사항 및 대응 방식 |
| :--- | :--- | :--- |
| **99.9% (Three Nines)** | 8.77 시간 | 수동 복구 가능, 모니터링 알람 기반 대응 |
| **99.99% (Four Nines)** | **52.56 분** | **자동 복구(Failover) 필수, 데이터 복제 자동화** |
| **99.999% (Five Nines)** | 5.26 분 | 무중단 배포(Blue-Green), 완전 자동화 아키텍처 |

- **Insight:** 99.99%부터는 사람이 장애를 보고 대응하는 방식으로는 절대 불가능합니다 그래서 반드시 **자동 복구 시스템(Failover)** 구조가 필요합니다.

# 3. 고가용성을 위한 핵심 기술 요소

### 3.1 GSLB(Global Server Load Balancing)
- **역할:** 여러 데이터 센터(Region)에 트래픽을 분산하고, 특정 리전 장애 시 즉시 다른 리전으로 유도합니다.
- **차별점:** 일반 로드밸런서는 서버의 상태만 보지만, GSLB는 **리전 전체의 가용성**과 **사용자의 지리적 거리**까지 계산하여 최적의 경로를 제공합니다.

### 3.2 RPO와 RTO (복구 핵심 지표)

장애 상황에서 엔지니어가 반드시 지켜야 하는 두 가지 약속으로, '얼마나 빨리', '얼마나 안전하게' 복구할 것인가를 결정합니다.

- **RPO (Recovery Point Objective):** 마지막 백업 시점으로부터 유실된 데이터 양. (금융권은 0을 지향)
"어느 시점까지의 데이터를 복구할 것인가?" (데이터 유실 허용 범위)
- **RTO (Recovery Time Objective):** 장애 발생 후 서비스 복구까지 걸리는 시간.
"장애 발생 후 서비스 재개까지 얼마나 걸리는가?" (중단 시간 허용 범위)

# 4. 고가용성 설계의 실무적 난제 (Deep Dive)

단순히 서버를 늘린다고 해서 99.99%가 보장되지 않는 이유들입니다.

### 4.1 데이터 정합성 (Consistency) 문제
- **상황:** 리전 A에서 결제했는데 0.5초 뒤 리전 A가 죽어서 리전 B로 접속됨. 리전 B에는 아직 결제 정보가 복제되지 않음.
- **해결:** **강한 일관성(Strong Consistency)**을 택하면 성능이 떨어지고, **최종 일관성(Eventual Consistency)**을 택하면 데이터가 일시적으로 안 맞습니다. 금융권에서는 이 사이의 균형을 잡는 것이 핵심 역량입니다.

### 4.2 전파 장애 (Cascading Failure)
- 한 서버의 장애가 부하 이동을 통해 정상 서버들까지 마비시키는 현상입니다.
- **방어책:** **서킷 브레이커(Circuit Breaker)** 패턴을 도입하여 장애가 발생한 컴포넌트를 즉시 격리해야 합니다.

### 4.3 데이터베이스 샤딩과 가용성
- DB를 쪼개는 샤딩은 가용성을 높이기도 하지만, 샤딩 키가 특정 샤드에 몰리면 해당 샤드가 죽었을 때 전체 서비스 중 일부가 마비되는 리스크가 있습니다.

---

# 5. AWS 기반의 재해 복구(DR) 전략 4단계

비용과 속도 사이의 트레이드 오프(Trade-off)를 보여주는 실전 전략들입니다.

### 5.1 Backup & Restore (가장 저렴)
- **방식:** 데이터를 주기적으로 백업(S3 등)하고, 장애 시 인프라를 처음부터 다시 생성합니다.
- **RTO/RPO:** 수 시간 ~ 수 일. (가장 느림)

### 5.2 Pilot Light (핵심만 점화)
- **방식:** DB만 실시간으로 타 리전에 복제해두고, 서버 이미지는 준비만 해둔 채 꺼둡니다.
- **RTO:** 수십 분 ~ 수 시간. (서버 기동 시간이 필요함)

### 5.3 Warm Standby (준비된 대기 상태)
- **방식:** 최소 사양의 서버 인스턴스를 타 리전에서 미리 가동합니다.
- **특징:** 장애 시 로드밸런서가 트래픽을 넘기면 되며, 서버 사양은 **Auto Scaling**으로 즉시 확장합니다.
- **RTO:** 수 분 이내.

### 5.4 Multi-Site (Active-Active / 완전 무중단)
- **방식:** **넷플릭스 모델.** 모든 리전이 상시 트래픽을 처리합니다.
- **특징:** 한 리전이 통째로 날아가도 사용자는 장애를 인지하지 못합니다. **무상태(Stateless)** 설계가 완벽해야 가능합니다.
- **RTO:** **0 (즉시)**.

---

# 6. 엔지니어로서의 시사점

### 6.1 관찰 가능성 (Observability)
- 자동 복구를 위해서는 시스템의 상태를 정확히 인지하는 로그, 메트릭, 트레이싱(Tracing) 인프라가 선행되어야 합니다.

### 6.2 비용 효율적 설계
- 모든 서비스에 Active-Active를 도입하는 것은 낭비입니다. 서비스 중요도에 따라 전략(Pilot Light vs Warm Standby)을 차등 적용하는 **아키텍처 설계 능력**이 중요합니다.

---

# 7. 요약

* **가용성의 본질:** 가용성은 단순히 서버가 켜져 있는 시간이 아니라, 고객과 약속한 지표(**SLA**)를 지키기 위해 "장애는 반드시 일어난다"고 가정하고 설계하는 **비즈니스적 신뢰의 기술**입니다.

* **엔지니어의 역할:** 따라서 엔지니어는 99.99%라는 엄격한 지표를 달성하기 위해 **자동 복구(Failover)** 체계를 구축하고, 서비스 성격에 맞춰 **비용과 복구 속도(RTO/RPO) 사이의 최적의 전략**을 설계해야 합니다.

---

# 8. 결론

1. **비용 대비 효용성:** 99.999% 가용성은 기술적으로 훌륭하지만 인프라 비용이 수십 배 뜁니다. 비즈니스 요구사항에 맞는 적절한 가용성 목표 설정이 우선입니다.
2. **Failure is Inevitable:** 장애는 반드시 일어난다는 가정(Design for Failure) 하에, 모든 컴포넌트를 격리하고 자동화된 모니터링 체계를 구축하는 것이 중요합니다.
3. **반복적인 확장 과정:** 시스템 규모를 키우는 것은 일회성이 아니라, 가용성을 높이기 위해 지속적으로 아키텍처를 개선해 나가는 과정입니다.
