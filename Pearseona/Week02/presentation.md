# 1. 배경: 왜 '추정'이 중요한가?

## 1.1 추정(Estimation)이란 무엇인가?
> 제한된 정보와 단순화된 가정을 바탕으로 시스템의 규모와 자원 요구량을 빠르게 근사하는 과정
- 정확한 값 X, 빠르고 합리적인 근사값 O

=> 대충 맞추는 것이 아니라, **논리적으로 근사하는 것**

**추정의 목적**
> 추정은 단순 계산이 아니라, 다음을 위해 사용
- 시스템 크기 파악
- 병목 지점 발견
- 필요한 인프라 수준 결정
- 설계 방향 선택

**추정의 핵심 요소 3가지**
1. 가정 (Aussiptions)
    - 예: DAU 1.5억, 하루 2 트윗
2. 단순화 (Simplification)
    - 365 X 5 = 1,800 마일(1,825)
3. 근사 계산 (Approximation)
    - 정확한 값보다 빠른 계산 우선

**중요한 이유**
> 추정 없이 하는 설계는 감에 의존한 설계
- 병목 지점 발견
- 비용 구조 이해
- 아키텍처 선택 기준 확보

=> **"추정은 불완전한 정보 속에서 합리적인 결정을 내리기 위한 엔지니어의 사고 도구"**


## 1.2 Back-of-the-envelope란 무엇인가?
> 종이 뒷면에 빠르게 끄적이듯 대략적인 값을 구하는 비공식적은 추정 방법
> 급하게 계산할 때 종이가 없어서, 봉투(envelope) 뒷면에 계산하던 것에서 유래

**Back-of-the-envelope의 특징**
- 빠름 (Speed)
- 단순함 (Simplicity)
- 근사값 (Approximation)
- 논리 기반 (Logical reasoning)

**중요한 이유**
> 정확한 계산이 아닌, 의사결정을 위한 계산
- 빠르게 설계 방향 결정 가능
- 병목 지점을 초기에 발견 가능
- 비용 감각 키울 수 있음
- 복잡한 문제 단순화 가능

**예시(트위터)**
> "트위터는 하루에 얼마나 많은 데이터가 쌓일까?"
- 사용자: 1.5억
- 하루 트윗: 2개
- 미디어 10%, 1MB

> 몇 초 만에:
- 하루 30TB
- 5년 55PB

=> **완벽한 계산보다, 빠르고 합리적인 추론이 더 중요**

# 2. 트위터 규모 추정 

## 2.1 기본 가정 (Assumptions)

| 항목 | 값 | 비고 |
| :--- | :--- | :--- |
| **DAU** | 1.5억 명 | 총 사용자의 50% |
| **사용자당 트윗** | 2개 / 일 | 매일 3억 건 발생 |
| **미디어 비율** | 10% | 사진/동영상 포함 트윗 |
| **미디어 크기** | 1 MB | 평균 파일 용량 |


## 2.2 트래픽(QPS) 및 저장소 계산

### [QPS(Query Per Second) 계산]
> 초당 요청 수(초당 생성되는 트윗 수)

> 계산식: QPS = (1.5억 × 2) / 86,400 = 약 **3,500 tweets/sec**

**(1) 하루 총 트윗 수**
- 사용자: 1.5억
- 1명당: 하루 2개
=> 1.5억 x 2 = 3억 트윗 / 하루

**(2) 하루 -> 초로 바꾸기**
- 1일 = 86,400초
=> 3억 ÷ 86,400 = 3,472  ≈ 3,500


### [저장소]

**텍스트**
- 140자 ≈ 280 bytes
 => 사실상 무시 가능 수준

**미디어**

- **하루 데이터 계산:**
  > 1.5억 × 2 × 10% × 1MB = **30TB/day**

  **(1) 전체 트윗 수**
  - 1.5억 x 2 = 3억
  **(2) 미디어 포함 트윗만 추리기(10%만 미디어)**
  - 3억 x 10% = 3천만
  **(3) 용량 곱하기**
  - 1개 = 1MB
  - 3천만 x 1MB = 3천만 MB
  **(4) MB -> TB 변환**
  - 1TB ≈ 1,000,000 MB
  - 30,000,000 MB ≈ 30TB

- **5년 데이터 계산:**
  - 30TB × 365 × 5 = **약 55PB**
  **(1) 하루 -> 1년**
  - 30TB × 365 ≈ 10,950TB ≈ 11PB
  **(2) 5년**
  - 11PB × 5 ≈ 55PB

=> 트위터의 본질은 텍스트가 아니라 **미디어 플랫폼**

=> 텍스트는 DB로 충분하지만, 미디어는 **분산 스토리지와 CDN이 필수적**

# 3. 숫자에서 설계로: 실전 전략

## 3.1 면접관에게 해야 할 질문 (Clarification)
> 좋은 설계는 면접관에게 던지는 날카로운 질문에서 시작
- "5년 전 데이터도 지금처럼 빠르게 조회해야 하나요?" => **Storage 계층화 결정(Hot/Cold)**
- "유명인 트윗은 따로 처리하나요?" => **Fan-out 방식 결정(Push/Pull)**
- "삭제 정책이 있나요?" => **데이터 생명주기 관리(TTL, Archiving)**

=> 설계는 답을 잘하는 것이 아니라, 질문을 잘하는 것

## 3.2 핵심 설계 포인트

- **저장 전략:** 데이터 특성에 따라 저장소를 분리하여 효율성과 확장성을 확보

| 데이터 | 저장 방식 |
|:---|:---|
| 텍스트/메타데이터 | RDB 또는 NoSQL |
| 미디어(이미지/영상 ) | Object Storage (예: S3) |
| 오래된 데이터 | Cold Storage |

- **읽기 최적화:** 메모리는 디스크보다 **10만 배** 빠름. 타임라인 생성을 위해 Redis 캐시를 적극 활용
- **쓰기 처리:** QPS 3,500은 감당 가능하나, 진짜 문제는 **Fan-out(전파)**

## 3.3 Fan-out 문제와 Hybrid 전략
> **Fan-out**이란, 하나의 이벤트(트윗)가 여러 사용자에게 동시에 전달되는 현상
> 쉽게 말하면, 한 명이 글을 쓰면, 그 글이 수많은 사람에게 퍼지는 것

**문제 이유**
- **일반 유저(팔로워 100명 보유)**랑 유명인**(팔로워 1,000만 명 보유)**가 같은 트윗 1개를 작성한다 하면
- 일반 유저는 **100번** 전달하면 되지만, 유명인은 **10,000,000번** 전달해야함
=> 이런 현상이 **Fan-out 폭발 문제**

**문제 해결을 위한 두 가지 접근 방식**
-  **Push 모델 (Write 시 전파):** 글을 쓰는 순간, 팔로워 피드에 미리 배달. 읽기는 빠르지만 유명인(Celebrity) 트윗 시 과부하 발생(서버 터짐).
- **Pull 모델 (Read 시 생성):** 사용자가 피드를 볼 때 그때 가져옴. 쓰기는 부담이 거의 없지만 읽기 속도가 저하됨.

    => 상황에 따라 일반 유저는 Push, 유명인은 Pull을 섞어 쓰는 **Hybrid 방식**이 정석

# 4. 55PB를 현실적으로 다루는 법

## 4.1 서버 수 추정 
- 하루 30TB 증가 / 서버 1대 용량 10TB 가정 시: **하루에 서버 3대씩(30TB/10TB)** 추가로 필요
- 5년이면 약 **5,000대**(하루 3대 X 365 X 5 ≈ 5,000대) 이상의 서버 인프라가 필요함을 의미

    => 한 번 구축하고 끝나는 시스템이 아니라, 계속 커지는 시스템

## 4.2 비용과 인프라의 가치
단순 계산만으로도 스토리지, 네트워크, CDN 비용이 천문학적으로 발생
엔지니어는 **"이 서비스가 기술적으로 가능한가?"**를 넘어 **"비용 효율적인가?"**를 고민 필요

=> 대규모 시스템에서는 기술보다 비용이 더 큰 제약

=> 하루 30TB는 숫자 같지만, 실제로는 매일 서버 3대를 계속 사야 한다는 의미. 그래서 대규모 시스템에서는 '가능한가'보다 '지속 가능한가'가 더 중요

# 5. 결론

## 5.1 핵심 요약

- 추정은 단순한 계산이 아니라, 병목을 찾아내는 **강력한 설계 도구**
- 시스템의 본질적인 문제는 항상 **데이터 크기(Scale)**에서 시작
- 좋은 엔지니어는 코드를 짜기 전에 **숫자로 시스템의 한계를 먼저 바라봄**

## 5.2 한 줄 정리
- 숫자는 거짓말을 하지 않으며, 설계의 가장 강력한 근거
