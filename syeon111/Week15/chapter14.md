# 14장. 유튜브 설계

> 유튜브란 사용자가 비디오를 업로드하고, 다른 사람이 올린 비디오를 시청할 수 있는 동영상 스트리밍 플랫폼. 넷플릭스, Hulu 같은 서비스 설계에도 동일하게 적용 가능
>

**유튜브 규모**
- 월간 능동 사용자(MAU): 24억 명
- 매일 재생되는 비디오 수: 50억 건
- 미국 성인 가운데 73%가 유튜브 이용
- 5천만 명의 창작자
- 유튜브 광고 매출: 2019년 기준 2018년 대비 30% 증가
- 모바일 인터넷 트래픽 가운데 37%를 유튜브가 차지

---

## 1단계 문제 이해 및 설계 범위 확정

**요구사항 정리**

- 빠른 비디오 업로드
- 원활한 비디오 재생
- 화질 선택 기능
- 낮은 인프라 비용
- 높은 가용성, 규모 확장성, 안정성
- 지원 클라이언트: 모바일 앱, 웹, 스마트 TV

**개략적 규모 추정**

- DAU: 5백만 명
- 하루 평균 30분 시청, 하루 비디오 업로드 수: 5만 건
- 비디오 저장 공간: 최대 1GB → 저장소 총 용량 = 5만 × 1GB = 매일 50TB 추가
- CDN 비용: CDN에서 서비스하는 비디오 트래픽 기준으로 GB당 $0.02~$0.14 수준 (지역별 차이)

---

## 2단계 개략적인 설계안 제시 및 동의 구하기

실제 유튜브는 아마존 클라우드, 아카마이(Akamai) CDN을 혼용한다. 모든 것을 직접 구축하지는 않고 CDN을 이용하는 게 현실적이다.

#### 컴포넌트 구성

- **로드밸런서**: API 서버 각각으로 고르게 요청을 분산
- **API 서버**: 비디오 스트리밍을 제외한 모든 요청을 처리 (업로드 URL 생성, 메타데이터 관리 등)
- **메타데이터 데이터베이스**: 비디오 메타데이터 보관. 샤딩과 다중화 적용
- **메타데이터 캐시**: 성능을 높이기 위해 비디오 메타데이터와 사용자 객체 캐시
- **원본 저장소(Original Storage)**: 원본 비디오를 보관하는 대형 BLOB(Binary Large Object) 저장소
- **트랜스코딩 서버**: 비디오 인코딩 처리. 다양한 기기와 화질에 맞게 변환
- **트랜스코딩 비디오 저장소**: 인코딩 완료된 비디오를 보관
- **CDN**: 비디오를 캐시하여 사용자 가까운 엣지 서버에서 스트리밍
- **완료 핸들러**: 트랜스코딩 완료 이벤트를 처리하고 메타데이터 DB/캐시를 갱신

#### 두 가지 핵심 플로우

**비디오 업로드 흐름**

1. 원본 비디오를 원본 저장소에 업로드
2. 트랜스코딩 서버가 원본 저장소에서 비디오를 꺼내 트랜스코딩 시작
3. 트랜스코딩 완료 시 두 가지가 병렬로 진행
    - 2a. 완료된 비디오를 트랜스코딩 비디오 저장소로 업로드
    - 2b. 트랜스코딩 완료 이벤트를 트랜스코딩 완료 큐에 적재
        - 2b.1. 완료 핸들러가 이벤트를 큐에서 꺼냄
        - 2b.1.a / 2b.1.b. 메타데이터 DB와 캐시를 업데이트
4. 트랜스코딩된 비디오를 CDN에 올림

**비디오 스트리밍 흐름**

- 비디오는 CDN에서 바로 스트리밍. 가장 가까운 CDN 엣지 서버가 담당
- 전송 지연이 매우 낮음

## 3단계 상세 설계

#### 비디오 트랜스코딩

비디오를 원본 포맷 그대로 저장해서 서비스하면 안 되는 이유가 있다.

- 원본 파일은 용량이 너무 커서 스트리밍에 부적합
- 기기마다 지원하는 코덱이 다름 (iOS, Android, 웹 브라우저 모두 다름)
- 네트워크 상황에 따라 화질을 동적으로 바꿔야 함 (어댑티브 스트리밍)
- 저사양 기기에서 재생하려면 낮은 화질 버전이 필요

**인코딩 포맷 구성 요소**

- **컨테이너**: 비디오 파일의 외부 포맷 (`.mp4`, `.avi`, `.mov` 등)
- **코덱**: 압축/해제 알고리즘. H.264, H.265, VP9 등. 화질과 파일 크기 결정

#### DAG(Directed Acyclic Graph) 기반 트랜스코딩 파이프라인

트랜스코딩은 단순히 해상도만 바꾸는 게 아니라 여러 단계의 병렬 처리가 필요하다.

**전처리기(Preprocessor)**

- 비디오를 GOP(Group of Pictures) 단위로 분할 → 병렬 처리를 위한 기본 단위
- 비디오 분할이 불가능한 구형 기기에서는 전처리기가 직접 GOP로 분할
- GOP 정렬과 메타데이터를 임시 저장소에 보관해서 인코딩 실패 시 재개 가능

**DAG 스케줄러**

- 트랜스코딩 흐름을 여러 단계(stage)로 분할하고 작업 큐에 넣음
- 예시 DAG: 원본 비디오 → {비디오 인코딩 / 썸네일 추출 / 워터마크 삽입} → 완료

**자원 관리자**

- 작업 큐, 작업 서버, 실행 큐, 서버 가용 상태 정보를 관리
- 적합한 작업 서버에 작업을 배정하고 실행 큐에 넣음

**임시 저장소**

- 작업 서버들이 메타데이터, 비디오/오디오 데이터를 주고받는 중간 저장소
- 메타데이터처럼 작고 빈번하게 접근하는 데이터 → 인메모리 캐시
- 비디오/오디오 데이터처럼 큰 데이터 → BLOB 저장소
- 프로세싱이 완료되면 임시 저장소에서 삭제

#### 스트리밍 프로토콜

스트리밍 프로토콜마다 지원 기기와 특성이 다르다.

- **MPEG-DASH** (Dynamic Adaptive Streaming over HTTP): 화질 어댑티브 스트리밍 표준
- **HLS** (HTTP Live Streaming): 애플이 개발. iOS, Safari 지원
- **Microsoft Smooth Streaming**: Microsoft 환경
- **Adobe HDS** (HTTP Dynamic Streaming): Adobe Flash 기반

프로토콜의 동작 원리를 완전히 외울 필요는 없음. 중요한 것은 각 플레이어가 지원하는 프로토콜이 다르고 비디오 인코딩도 다르다는 것.

#### 시스템 최적화

**속도 최적화**

- 업로드 시작 전에 일부 비디오를 미리 업로드 (사용자가 "업로드" 버튼을 누르기 전에 미리 전처리 시작 가능)
- 업로드 센터를 사용자와 가까운 곳에 배치. 불필요한 원거리 전송을 줄임
- 모든 것을 병렬화 — 트랜스코딩, 썸네일 생성, 워터마크 삽입 등을 동시에

**안정성 최적화**

- 업로드 재시도: 업로드 중 실패 시 처음부터 다시 시작하지 않고 실패한 지점부터 재개 (이어올리기)
- 비디오 처리 파이프라인 전체에 걸쳐 재시도 메커니즘 적용

**비용 최적화**

- CDN 비용이 전체 운영 비용의 대부분 → CDN 비용 최소화가 핵심
- 인기 있는 비디오는 CDN에서 서빙, 덜 인기 있는 비디오는 자체 서버에서 서빙
- 특정 지역에서만 인기 있는 비디오는 해당 지역 CDN에만 배포
- 새 비디오는 CDN에 올리지 않고 실시간 인코딩 서버에서 직접 서빙 (조회수가 낮을 때는 CDN 비용이 아까움)

## 4단계 마무리

추가로 논의하면 좋을 것

- **API 계층 규모 확장**: 무상태 API 서버를 수평적으로 확장
- **데이터베이스 계층 규모 확장**: 다중화와 샤딩
- **라이브 스트리밍**: VOD(Video on Demand)와 다른 요구사항. 더 낮은 레이턴시, 다른 스트리밍 프로토콜 필요
- **비디오 삭제**: 저작권 위반, 음란물, 불법 콘텐츠 정책 위반 비디오는 업로드 즉시 또는 사용자 신고를 통해 삭제
