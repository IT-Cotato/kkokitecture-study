# Netflix — 하나의 영상이 수천 개의 인코딩 버전이 되는 과정
---

## 1. 규모와 배경

- 넷플릭스 가입자 2억 8천만 명, 190개국 서비스
- 콘텐츠 하나를 스트리밍하려면 기기마다, 네트워크 상태마다 다른 버전이 필요 — 아이폰과 스마트 TV는 지원하는 코덱이 다르고, 와이파이와 LTE는 감당 가능한 데이터 속도가 다름
- 넷플릭스는 에피소드 하나 스트리밍을 위해 약 1,200개의 파일을 저장. 기기별 코덱 프로파일 × 비트레이트 × 오디오 × 자막 × 언어 조합
- 이 파일들을 만들고 전 세계에 배포하는 인프라가 AWS EC2 기준 10만 개 이상의 서버 인스턴스로 운영

---

## 2. 인코딩 파이프라인 3단계

**1단계 — Ingest (수신 및 검증)**

- 스튜디오에서 원본 파일 수신. 해상도는 보통 4K 이상, 포맷도 촬영 장비마다 다양
- 파일 무결성 검증(체크섬), 메타데이터 추출 후 원본을 Amazon S3에 보관
- 원본 파일은 절대 변경하지 않음 — 이후 모든 처리는 복사본에서 진행. 5년 뒤 더 좋은 코덱이 나와도 원본에서 다시 인코딩 가능

**2단계 — Processing (청크 분할 → 병렬 인코딩)**

- 영상을 GOP(Group of Pictures) 단위로 수백 개의 청크로 분할
- 각 청크를 수백 개의 EC2 인스턴스에 병렬 분산해서 동시에 인코딩
- 영화 한 편을 단일 서버에서 순차 처리하면 수십 시간 → 병렬화로 수 시간 이내로 단축
- 인코딩 완료된 청크들을 다시 합쳐서 최종 스트리밍 파일 생성

**3단계 — Distribution (Open Connect CDN 배포)**

- 완성된 파일들을 넷플릭스 자체 CDN인 Open Connect로 배포
- Open Connect는 전 세계 ISP와 IXP에 물리적 어플라이언스를 직접 설치
- 사용자가 재생 버튼을 누르면 가장 가까운 어플라이언스에서 스트리밍 시작 — 외부 CDN 거치지 않음

## 3. 인코딩 전략의 진화

**2015년 이전 — 고정 인코딩 래더(Fixed Bitrate Ladder)**

- 모든 콘텐츠에 동일한 설정 적용. 예: 1080p는 무조건 5.8Mbps, 720p는 3Mbps
- 문제는 콘텐츠마다 시각적 복잡도가 완전히 다르다는 것. "마이 리틀 포니" 같은 단순 애니메이션에 5.8Mbps는 낭비고, "왕관" 같이 안개와 연기가 많은 드라마에는 여전히 부족

**2015년 — Per-Title Encoding (타이틀별 인코딩)**

- 고정 래더의 문제를 해결하기 위해, 콘텐츠마다 수백 개의 (해상도 × 비트레이트) 조합으로 테스트 인코딩 수행
- 각 테스트 결과를 VMAF로 측정해 **Convex Hull**을 그림 — 해상도별로 비트레이트를 올려도 화질이 더 이상 오르지 않는 포화 지점들을 이어 만든 곡선
- Convex Hull 위의 점들이 "이 비트레이트에서 낼 수 있는 최고의 해상도" → 이 점들의 집합이 해당 타이틀의 맞춤형 인코딩 래더
- 단순한 콘텐츠는 낮은 비트레이트로도 동일 화질, 복잡한 콘텐츠는 필요한 만큼만 비트레이트 올림
- 결과: 동일 화질 기준 대역폭 **20% 절감**
- 단점: 기존 방식보다 인코딩 비용이 수십 배 비쌈 → 하지만 넷플릭스는 콘텐츠 하나를 수억 명이 보기 때문에 초기 인코딩 비용보다 CDN 전송 비용이 훨씬 크므로 투자 가치가 있음

**2018년 — Shot-Based Encoding (장면별 인코딩)**

- per-title은 영상 전체를 하나의 단위로 분석했는데, 같은 영화 안에서도 장면마다 복잡도가 완전히 다름
- **장면 변화 감지 알고리즘(shot-change detection)**: 연속된 프레임 간 픽셀 차이량을 분석해 장면이 바뀌는 지점을 자동으로 탐지
- 영상을 장면 단위(shot)로 분할하고 각 장면마다 독립적으로 최적의 인코딩 파라미터 적용
- I-프레임(인트라 프레임)을 임의의 고정 간격이 아니라 **장면 변화 지점에 정확히 배치** → I-프레임 수 최소화 가능 (I-프레임은 P/B 프레임보다 용량이 훨씬 큼)
- 모든 비트레이트 버전에서 동일한 장면 경계 지점을 사용 → 어댑티브 스트리밍 중 화질 전환 시 플레이어가 정확히 같은 위치에서 전환 가능
- 구현 문제: 장면 평균 길이가 4초라 청크 수가 폭발적으로 늘어남 → 비슷한 길이의 shot 여러 개를 묶어 약 3분짜리 청크로 재구성하는 방식으로 해결
- 결과: per-title 대비 대역폭 추가 **10% 절감**, 고정 래더 대비 총 **30% 절감**

## 4. 화질 측정 — VMAF

- 기존 PSNR(Peak Signal-to-Noise Ratio)은 수학적으로 계산한 화질 지표지만 사람이 실제로 느끼는 화질과 상관관계가 낮음. 예를 들어 블러 처리된 영상은 PSNR이 낮아도 사람 눈에 더 자연스럽게 보일 수 있음
- 넷플릭스가 USC와 공동 개발한 **VMAF(Video Multimethod Assessment Fusion)**: 시각 인지 모델, 세부 정보 손실, 블러 등 여러 메트릭을 기계학습으로 융합해 사람의 주관적 화질 점수와 0.9 이상의 상관관계 달성
- Per-title 인코딩에서 Convex Hull을 그릴 때, VMAF 점수를 y축으로 삼아 "같은 VMAF 점수를 내는 데 필요한 최소 비트레이트"를 찾음
- JND(Just Noticeable Difference) 개념도 적용 — 인접한 두 비트레이트 간 화질 차이가 사람이 눈치챌 수 없는 수준 이하가 되도록 래더 간격을 설계. 사람이 못 느끼는 차이에 비트레이트를 낭비하지 않기 위함
- VMAF는 오픈소스로 공개되어 현재 YouTube, Amazon Prime, Meta 등 업계 표준 화질 지표로 자리잡음

## 5. AV1 코덱으로의 전환

- H.264(AVC) → H.265(HEVC) → 현재 **AV1** 코덱으로 전환 진행 중
- H.265는 화질 대비 용량이 H.264보다 약 40% 우수하지만 특허 라이선스 비용이 발생. 스트리밍 서비스 입장에서는 콘텐츠 전송량이 워낙 크기 때문에 라이선스 비용이 무시할 수 없는 수준
- AV1은 로열티 프리 오픈 코덱. 넷플릭스, Google, Apple, Amazon, Meta 등이 함께 설립한 Alliance for Open Media(AOMedia)에서 개발 — 넷플릭스는 창립 멤버
- 2025년 기준 전체 스트리밍의 약 30%가 AV1, 곧 가장 많이 쓰이는 코덱이 될 전망
- AV1 성과: H.264 대비 VMAF 4.3점 높음, 대역폭 **3분의 1 수준**, 버퍼링 45% 감소
- 단점: AV1 인코딩은 H.264보다 훨씬 느리고 비쌈 → 그러나 CDN 트래픽 비용 절감이 인코딩 비용 증가를 크게 상회하기 때문에 전환이 계속 진행 중

---

## 6. 비용 최적화 — EC2 스팟 인스턴스

- 인코딩은 막대한 컴퓨팅 파워가 필요하지만, 중간에 실패해도 해당 청크만 재처리하면 되는 **내결함성(fault-tolerant) 작업**
- AWS EC2 **스팟 인스턴스** 적극 활용 — AWS가 남는 EC2 용량을 온디맨드 대비 최대 90% 할인 판매하는 방식. 언제든 회수될 수 있지만 인코딩은 그 특성상 중단에 강함
- 스팟 인스턴스가 회수되면 해당 청크만 다른 인스턴스에서 재시작 — 처음부터 다시 할 필요 없음
- 청크 단위 병렬화 구조가 병렬 처리 속도 향상, 비용 최적화, 장애 내성을 한 번에 해결하는 구조적 선택
