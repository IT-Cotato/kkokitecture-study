# 블룸 필터 (Bloom Filter)

> 참고 자료
> 
> - [Network Applications of Bloom Filters: A Survey](https://www.eecs.harvard.edu/~michaelm/postscripts/im2005b.pdf)
> - [Burton Howard Bloom, 1970 원본 논문](https://dl.acm.org/doi/10.1145/362686.362692)

---

## 1. 블룸 필터 주요 특징

- 어떤 원소가 집합에 **속하는지 여부를 확률적으로 판단**하는 자료구조
- 1970년 Burton Howard Bloom이 고안한 **확률론에 기초한 공간 효율적(space-efficient probabilistic) 자료구조**
- **False Positive는 존재**하지만 **False Negative는 절대 없음**
    - "있다"고 했는데 실제로 없을 수 있음
    - "없다"고 했으면 진짜 없음 — 이 특성이 핵심
- 일반적인 해시 테이블 대비 수십~수백 배 적은 메모리로 동일한 집합을 표현 가능

---

## 2. 동작 원리

블룸 필터는 **m비트 배열**과 **k개의 독립적인 해시 함수**로 구성된다.

### 삽입

원소를 삽입할 때 k개의 해시 함수를 각각 적용하여 나온 k개의 인덱스 위치를 모두 1로 설정한다.

```
원소 "https://example.com" 삽입 시
h1(x) = 3 → bit[3] = 1
h2(x) = 7 → bit[7] = 1
h3(x) = 12 → bit[12] = 1
```

### 조회

조회 시 마찬가지로 k개의 해시 함수를 적용하여 해당 위치를 모두 확인한다.

- **모두 1이면** → "있을 수도 있음" (False Positive 가능)
- **하나라도 0이면** → "확실히 없음" (False Negative 불가)

### 삭제 불가

한 번 1로 설정된 비트는 다른 원소와 공유될 수 있기 때문에 **기본 구조에서는 삭제 연산을 지원하지 않는다.** 삭제가 필요한 경우 각 비트 대신 카운터를 두는 Counting Bloom Filter 변형을 사용한다.

---

## 3. 확률론적 공간 효율 — 왜 작은 메모리로 가능한가

블룸 필터가 공간 효율적인 이유는 원소 자체를 저장하지 않고, **원소의 존재 여부만 비트로 인코딩**하기 때문이다.

False Positive율은 비트 배열의 크기와 해시 함수의 수에 의해 결정되며, 이를 계산하는 수식이 존재한다. 자세한 수식은 생략하지만 핵심은 다음과 같다.

- 비트 배열이 클수록 False Positive율이 낮아짐
- 해시 함수 수를 적절히 조정할수록 False Positive율이 낮아짐
- 실무에서는 허용 가능한 False Positive율을 먼저 정하고, 수식으로 m과 k를 역산하여 결정
    - **m**: 비트 배열의 크기
    - **k**: 해시 함수의 개수

### 공간 효율 비교 예시

원소 100만 개, False Positive율 1% 기준:

- 해시 테이블: 약 **40MB** 이상
- 블룸 필터: 약 **1.14MB**

→ 같은 역할을 수십 배 적은 메모리로 수행

## 4. URL 단축기에서의 활용 — 해시 충돌 해소

### 책에서 소개한 해시 후 충돌 해소 전략

책(8장)에서는 단축 URL 생성 시 해시 값이 충돌할 경우 아래 흐름으로 처리한다고 설명한다.

```
1. longURL을 해시 → 단축 URL 후보 생성
2. 단축 URL이 DB에 이미 존재하는지 조회
3. 충돌이면 → 사전에 정한 문자열을 덧붙여 재해시
4. 충돌이 해소될 때까지 2~3 반복
5. DB에 저장
```

### 문제점

충돌이 반복될수록 **DB 조회 횟수가 늘어나 오버헤드가 급격히 커진다.** 책에서는 이를 명시적으로 단점으로 지적하고, 해결책으로 블룸 필터를 제시한다.

### 블룸 필터 적용 후 흐름

```
1. longURL을 해시 → 단축 URL 후보 생성
2. 블룸 필터로 먼저 확인
   - "없다" → DB 조회 없이 즉시 사용 확정 ✓ (False Negative 없으므로 안전)
   - "있을 수도 있다" → 그때만 DB 조회 수행
3. DB에 저장 후 블룸 필터에도 해당 URL 추가
```

→ **대부분의 경우 DB 조회를 생략**할 수 있어 오버헤드를 크게 줄임

## 7. 정리

- 블룸 필터는 **확률론에 기초한 공간 효율적 자료구조**로, "확실히 없다"는 판단을 빠르고 저렴하게 내릴 수 있음
- URL 단축기의 해시 충돌 해소 과정에서 **불필요한 DB 조회를 사전에 차단**하는 용도로 적합
- False Positive율은 비트 배열 크기와 해시 함수 수로 조절 가능하며, 허용 범위 내로 설계할 수 있음
- 완벽한 정확도보다 **속도와 메모리 효율이 우선**되는 대부분의 필터링 계층에 적합
