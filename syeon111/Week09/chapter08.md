## 2단계 개략적 설계안 제시 및 동의 구하기

#### API 엔드포인트

API 엔드포인트를 통해 서버와 통신

1. URL 단축용 엔드포인트: 새 단축 URL을 생성하고 싶은 클라이언트는 단축할 URL을 인자로 실어서 POST 요청을 보냄
    - `POST /api/v1/data/shorten`
        - 인자: {longUrl: longURLstring}
        - 반환: 단축 URL
2. URL 리디레션용 엔드포인트: 단축 URL에 대해서 요청이 오면 원래 URL로 보내기 위한 용도의 엔드포인트
    - `GET /api/v1/shortUrl`
        - 반환: HTTP 리디렉션 목적지가 될 원래 URL

#### URL 리디렉션

Request URL을 넣으면 서버는 원래 URL로 바꿔 301 응답의 Location 헤더에 넣어 반환

- 301 Permanently Moved:
    - 해당 URl에 대한 HTTP 요청의 처리 책임이 영구적으로 Location 헤더에 반환된 URL로 이전되었다는 응답
    - 영구적으로 이전되었으므로, 브라우저는 이 응답을 캐시하기 때문에 서버에 재요청 보내지 않고 캐시에서 꺼내 씀
    - **장점: 서버 부하가 줄어 듦**
    - **단점: 트래픽 분석에서 유리하지 않음**
- 302 Found:
    - 응답이 주어진 URL로의 요청이 ‘일시적으로’ Location 헤더가 지정하는 URL에 의해 처리되어야 한다는 응답
    - 브라우저에 캐시되지 않고 서버에 무조건 요청을 보냄
    - **장점: 트래픽 분석에서 유리**
    - **단점: 서버 부하가 늘음**

#### URL 단축

긴 URL을 해시값으로 대응시킬 해시 함수 찾는 것이 중요

- URL이 다른 값이면 해시 값도 달라야 한다
- 계산된 해시 값은 원래 값으로 복원될 수 있어야 함

## 3단계 상세 설계

#### 데이터 모델

메모리는 유유용하지만 비싸기 때문에 모든 매핑을 해시 테이블에 두지 못 함
→ 순서쌍을 관계형 데이터 베이스에 저장

#### 해시함수

**해시 값 길이**

- 해시 값의 길이에 따라서 만들 수 있는 URL의 개수 차이가 많이 난다

**해시 후 충돌 해소**

정해둔 해시 값 길이보다 긴 경우 앞의 n개의 문자열만 사용한다
→ 문제점: 해시 결과가 서로 충돌할 확률 up!!

충돌 해결 방법: 충돌이 해소될 때까지 사전에 정한 문자열을 해시값에 덧붙임
→ 문제점: 단축 URL 생성할 때 한 번 이상의 데이터베이스 질의를 해야 하므로 오버헤드가 큼

 충돌 해결 방법의 문제점의 해결책: 블룸 필터

**base-62 변환**

수의 표현 방식이 다른 두 시스템이 같은 수를 공유하여야 하는 경우에 유용

- 62진수로 변환해 사용

| 해시 후 충돌 해소 전략 | base-62 변환 |
| --- | --- |
| 단축 URL의 길이가 고정됨 | 단축 URL의 길이가 가변적.
ID 값이 거치면 같이 길어짐 |
| 유일성이 보장되는 ID 생성기 필요 없음 | 유일성 보장 ID 생성기가 필요 |
| 충돌 해소 전략 필요 | 충돌 아예 불가 |
| ID로부터 단축 URL을 계산하는 방식이 아니라 다음에 쓸 수 있는 URL 알아내는 것 불가 | 다음에 쓸 수 있는 단축 URL 찾기 쉬움
→ 보안상 문제 될 소지 있음 |

#### URL 단축키 상세 설계

URL 단축기는 시스템의 핵심 컴포넌트, 논리적으로는 단순하고 기능적으로는 항상 동작하는 상태로 유지되어야 함

1. 입력으로 긴 URL을 받음
2. 데이터베이스에 해당 URL이 있는지 검사
3. 데이터베이스에 있다면 해당 URL에 대한 단축 URL을 만든 적이 있는 것, 따라서 데이터베이스에서 해당 단축 URL을 가져와서 클라이언트에게 반환
4. 데이터베이스에 없는 경우에는 해당 URL은 새로 접수된 것이므로 유일한 ID를 생성, 이 ID는 데이터베이스의 기본 키로 사용
5. 62진법 변환을 적용, ID를 단축 URL로 만듦
6. ID, 단축 URL, 원래 URL로 새 데이터베이스 레코드를 만든 후 단축 URL을 클라이언트에 전달

### URL 리디렉션 상세 설계

쓰기보다 읽기를 더 자주 하는 시스템, 순서 쌍을 캐시에 저장하여 성능을 높임

**로드밸런서의 동작**

1. 사용자가 단축 URL을 클릭
2. 로드밸런서가 해당 클릭으로 발생한 요청을 웹 서버에 전달
3. 단축 URL이 이미 캐시에 있는 경우에는 원래 URL을 바로 꺼내서 클라이언트에게 전달
4. 캐시에 해당 단축 URL이 없는 경우에는 데이터베이스에서 꺼냄
5. 데이터베이스에서 꺼낸 URL을 캐시에 넣은 후 사용자에게 반환

## 4단계 마무리

**추가로 고려할 사항**

- **처리율 제한 장치(rate limiter):** 처리율 제한 장치를 두면, IP 주소를 비롯한 필터링 규칙들을 이용해 요청을 걸러낼 수 있을 것
- **웹 서버의 규모 확장:** 본 설계에 포함된 웹 계층은 무상태(stateless) 계층이므로, 웹 서버를 자유로이 증설하거나 삭제할 수 있음
- **데이터베이스의 규모 확장:** 데이터베이스를 다중화하거나 샤딩(sharding)하여 규모 확장성을 달성할 수 있음
- **데이터 분석 솔루션(analytics):** 성공적인 비즈니스를 위해서는 데이터가 중요
