# 10장. 알림 시스템 설계

> 알림 시스템(notification system)이란 최신 뉴스, 제품 업데이트, 이벤트, 쿠폰 등 고객에게 중요한 정보를 비동기적으로 제공하는 기능
> 

**알림의 종류**

- 모바일 푸시 알림
- SMS 메시지
- 이메일

---

## 1단계 문제 이해 및 설계 범위 확정

**요구사항 정리**

1. 지원 알림 종류: 푸시 알림, SMS, 이메일
2. 실시간성: 연성 실시간(soft real-time) — 가능한 빨리 전달하되 부하가 심하면 약간의 지연은 허용
3. 지원 단말: iOS, Android, 랩톱/데스크톱
4. 알림 생성 주체: 클라이언트 앱이 직접 만들 수도, 서버가 스케줄링할 수도 있음
5. 수신 거부(opt-out) 기능 필요
6. 처리 규모: 천만 건 푸시 알림, 백만 건 SMS, 5백만 건 이메일

---

## 2단계 개략적인 설계안 제시 및 동의 구하기

### 알림 유형별 지원 방안

**iOS 푸시 알림**

- 알림 제공자(provider) → APNS(Apple Push Notification Service) → iOS 단말
- 알림 제공자가 단말 토큰(device token)과 페이로드(payload, JSON 딕셔너리)를 담아 요청 전송

**안드로이드 푸시 알림**

- iOS와 절차는 비슷하나 APNS 대신 FCM(Firebase Cloud Messaging) 사용

**SMS 메시지**

- 트윌리오(Twilio), 넥스모(Nexmo) 같은 제3자 상용 서비스 이용

**이메일**

- 센드그리드(Sendgrid), 메일침프(Mailchimp) 같은 상용 서비스 이용, 전송률·분석 기능 제공

### 연락처 정보 수집 절차

- 사용자가 앱 설치/계정 등록 시 API 서버가 단말 토큰, 전화번호, 이메일 등을 수집해 DB에 저장
- user 테이블(이메일, 전화번호) ↔ device 테이블(device_token) — 1:N 관계 (한 사용자가 여러 단말 보유 가능)

### 알림 전송 및 수신 절차 — 개략적 설계안

**컴포넌트**

- 서비스 1~N: 알림을 트리거하는 마이크로서비스/크론잡
    - (예: 과금 알림, 배송 알림)
- 알림 시스템: 알림 전송/수신 처리의 핵심, API 제공 + 페이로드 생성
- 제3자 서비스: APNS, FCM, SMS·이메일 서비스 등 실제 단말로 전달

**초안의 문제점**

1. SPOF: 알림 서버가 1대뿐 → 장애 시 전체 서비스 중단
2. 규모 확장성 부족: 한 서버가 모든 걸 처리하므로 DB·캐시 등을 개별적으로 늘릴 수 없음
3. 성능 병목: HTML 생성, 제3자 응답 대기 등 무거운 작업을 동기 처리하면 트래픽 몰릴 때 과부하

### 개선된 설계안

- 데이터베이스/캐시를 알림 서버에서 분리
- 알림 서버를 증설해 자동 수평적 확장 가능하도록 함
- **메시지 큐**를 이용해 컴포넌트 간 결합도를 낮춤 (알림 종류별로 별도 큐 사용 → 한 제3자 서비스 장애가 다른 알림에 영향 안 줌)

**전송 흐름**

1. 서비스가 API 호출 → 알림 서버로 전달
2. 알림 서버가 캐시/DB에서 사용자 정보, 단말 토큰, 알림 설정 등 메타데이터 조회
3. 알림 서버가 이벤트를 생성해 해당 큐(iOS 큐, SMS 큐 등)에 적재
4. 작업 서버(worker)가 큐에서 이벤트 꺼냄
5. 작업 서버가 제3자 서비스로 알림 전송
6. 제3자 서비스가 사용자 단말로 최종 전달

## 3단계 상세 설계

### 안정성(reliability)

**데이터 손실 방지**

- 알림은 지연되거나 순서가 바뀌어도 되지만, 절대 유실되면 안 됨
- → 알림 데이터를 DB(알림 로그)에 보관 + 재시도 메커니즘 구현

**알림 중복 전송 방지**

- 분산 시스템 특성상 중복 전송 가능성 있음 → 이벤트 ID 검사로 이미 본 적 있는 이벤트면 버리는 멱등성(idempotency) 로직 도입
- 100% 방지는 불가능하지만 빈도는 최소화 가능

### 추가로 필요한 컴포넌트

**알림 템플릿**

- 메시지 대부분이 형식이 비슷하므로 인자, 스타일, 추적 링크만 바꿔 끼우는 틀을 마련
- 일관성 유지 + 알림 작성 시간 단축

**알림 설정**

- 사용자별로 채널별 수신 여부(opt_in)를 관리하는 설정 테이블 필요
- 전송 전 반드시 해당 설정을 확인해야 함

**전송률 제한(rate limiting)**

- 사용자가 알림을 너무 많이 받으면 알림 기능 자체를 꺼버릴 수 있음 → 채널별 수신 빈도 제한

**재시도 방법**

- 제3자 전송 실패 시 재시도 전용 큐에 적재, 동일 문제 반복되면 개발자에게 알림

**푸시 알림과 보안**

- appKey/appSecret으로 인증된 클라이언트만 알림 전송 API 사용 가능하도록 함

**큐 모니터링**

- 핵심 메트릭: 큐에 쌓인 이벤트 수 → 너무 많으면 작업 서버 증설 신호

**이벤트 추적**

- 알림 확인율, 클릭율 등은 데이터 분석 서비스와 통합해 추적

### 수정된 설계안

- 알림 서버에 **인증** + **전송률 제한** 추가
- 전송 실패 대응 **재시도** 큐 추가
- **알림 템플릿** 사용으로 생성 과정 단순화
- **모니터링/추적 시스템** 통합

---

## 4단계 마무리

- 이번 장에서는 규모 확장이 쉽고, 푸시/SMS/이메일을 모두 지원하며, 메시지 큐로 컴포넌트 간 결합도를 낮춘 알림 시스템을 설계함
- 특히 집중한 주제
    - **안정성**: 안정적인 재시도 메커니즘으로 메시지 전송 실패율 최소화
    - **보안**: appKey/appSecret 등으로 인증된 클라이언트만 알림 전송 가능
    - **이벤트 추적 및 모니터링**: 알림 생성~전송 전 과정을 추적하고 시스템 상태를 모니터링
    - **사용자 설정**: 사용자가 알림 수신 여부를 직접 조정할 수 있도록 함
