## 1. 사용하는 이유

- 분산 환경에서 64비트 숫자형 ID 생성, 시간순 정렬, 초당 10,000개 이상 처리량을 동시에 만족해야 하는 전형적인 분산 ID 생성기 설계 가능
- UUID는 조율 없이 쉽게 만들 수 있고 확장성이 좋지만 128비트이며 숫자만으로 구성되지 않아 조건과 맞지 않음
- 다중 마스터 복제나 중앙 티켓 서버 방식은 구현이 단순하지만 시간순 정렬 보장, 다중 데이터센터 확장, SPOF 회피 측면에서 한계
- Snowflake는 타임스탬프, 데이터센터 ID, 서버 ID, 시퀀스를 조합해 64비트 안에서 유일성과 시간 정렬성을 동시에 만족
- 비트 길이 조정으로 시스템 수명, 동시성, 확장성을 트레이드오프할 수 있어 발표 확장 포인트가 분명함

---

## 2. Snowflake 구조 요약

Snowflake는 64비트 중 1비트는 부호 비트로 비워두고, 41비트는 타임스탬프, 5비트는 데이터센터 ID, 5비트는 워커 ID, 12비트는 시퀀스로 사용한다. 이 구조는 데이터센터 32개, 센터당 서버 32개, 한 서버에서 1밀리초당 4096개의 ID를 생성할 수 있게 한다.

### 비트 분할

| 영역 | 비트 수 | 용도 |
| --- | --- | --- |
| 부호 비트 | 1 | 사용하지 않음 (양수 보장) |
| 타임스탬프 | 41 | 사용자 정의 epoch 이후 경과 밀리초 |
| 데이터센터 ID | 5 | 최대 32개 데이터센터 |
| 워커 ID | 5 | 데이터센터당 최대 32개 서버 |
| 시퀀스 | 12 | 1밀리초당 최대 4096개 ID |

---

## 3. 심화 포인트 1 — Clock Rollback 문제

Snowflake의 핵심 가정은 현재 시간이 이전에 발급한 ID의 시간보다 뒤에 있어야 한다는 점이다. NTP 보정, VM 마이그레이션, 하이퍼바이저 시간 보정, 운영체제 시계 변경 등으로 시스템 시계가 뒤로 밀리면 동일한 타임스탬프 구간에서 중복 위험이 생길 수 있다.

### 대응 방안

| 방식 | 동작 | 한계 |
| --- | --- | --- |
| 대기 후 재시도 | 마지막 사용 시각보다 현재 시각이 작으면 차이만큼 대기 | 큰 역행 시 지연 과다 |
| 예외 발생 | 임계치 초과 시 ID 발급 중단 | 가용성 저하 |
| 논리 시계 도입 | 별도 시계 보정 레이어로 물리 시계 후퇴를 숨김 | 구현 복잡도 증가 |

---

## 4. 심화 포인트 2 — Sequence Overflow 문제

기본 Snowflake에서 시퀀스는 12비트이므로 한 밀리초에 최대 4096개의 ID만 발급할 수 있다. 같은 밀리초 안에 요청이 더 많이 들어오면 다음 밀리초까지 대기해야 하며, 이 지연은 순간적인 burst traffic에서 병목이 될 수 있다.

### 평균 처리량 vs 순간 처리량

- 초당 10,000개는 1초 기준으로는 매우 여유 있는 수치
- 특정 짧은 구간에 트래픽이 몰리면 밀리초 단위 제한이 더 중요해짐
- 발표에서는 "평균 처리량과 순간 처리량을 구분해야 한다"는 점을 짚어야 함

---

## 5. 심화 포인트 3 — Worker ID 관리 문제

Snowflake는 같은 시각과 같은 시퀀스가 겹치더라도 데이터센터 ID와 워커 ID가 다르면 전체 ID는 달라진다. 반대로 워커 ID가 중복 배정되면 타임스탬프와 시퀀스가 같은 순간 충돌 가능성이 생긴다.

### 자동 할당 방식

- ZooKeeper, etcd 기반 분산 락
- DB lease 방식
- Kubernetes StatefulSet ordinal 활용
- 시작 시 충돌 검사 수행

---

## 6. 심화 포인트 4 — 고가용성 설계

ID 생성기는 주문, 결제, 로그, 메시지, 사용자 엔터티 생성 등 여러 핵심 경로에 들어가므로 장애 허용도가 낮다.

### 중앙 집중형 vs 분산형 비교

| 구분 | 중앙 티켓 서버 | Snowflake |
| --- | --- | --- |
| 단순성 | 이해 쉬움 | 비트 분할 설계 필요 |
| 장애점 | SPOF 발생 가능 | 노드 독립 동작 |
| 동기화 | 복제 시 동기화 문제 | 시간 동기화 필요 |
| 운영 부담 | 낮음 | 워커 ID 유일성 관리 필요 |

---

## 7. 비교 대상 — UUIDv7

최신 대안으로 UUIDv7를 짧게 비교하는 구성이 좋다. UUIDv7는 시간 정보를 앞부분에 배치해 정렬 친화성을 높였고, 기존 랜덤 UUID보다 데이터베이스 인덱스 지역성이 더 좋아질 수 있다.

### 한계

- 128비트로 64비트를 요구할때 충족하지 못함
- 일반적으로 문자열 표현을 많이 사용
- "숫자만으로 이루어진 64비트 ID"라는 현재 요구사항에 부적합

---

## 8. 개선안

### 개선 항목

- **시계 역행 처리**: 5ms 이하이면 대기 후 재시도, 초과 시 경고 로그를 남기고 발급 중단
- **워커 ID 자동 할당**: 수동 설정하지 않고 서비스 시작 시 임대 기반으로 할당
- **시퀀스 소진 대응**: 동일 밀리초 내 시퀀스가 모두 소진되면 busy wait 대신 짧은 sleep 또는 event 기반 대기 적용
- **운영 도구 제공**: 생성된 ID에서 타임스탬프와 워커 ID를 역으로 복원할 수 있게 디코더 도구 제공
