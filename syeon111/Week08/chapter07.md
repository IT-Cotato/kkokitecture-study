# 7장. 분산 시스템을 위한 유일 ID 생성기 설계

- auto_increment 송석의 기본키를 가진 관계형 데이터 베이스 
→ 분산 환경에서는 통하지 않음

## 1단계 문제 이해 및 설계 범위 확인

- ID는 유일해야 한다.
- ID는 숫자로만 구성되어야 한다.
- ID는 64비트로 표현될 수 있는 값이어야 한다.
- ID는 발급 날짜에 따라 정렬 가능해야 한다.
- 초당 10,000개 의 ID를 만들 수 있어야 한다.

## 2단계 개략적 설계안 제시 및 동의 구하기

유일성 보장되는 ID를 만드는 방법 4가지

#### 다중 마스터 복제

auto_increment 기능을 활용하지만 값을 1씩 증가시키는게 아니라, 데이터베이스 서버 개수인 k개 만큼씩 증가 시킴

**장점**

- 데이터베이스 수 늘릴수록 초당 생산가능 ID 증가 → 규모 확장성 문제 해결 가능함

**단점**

- 여러 데이터 센터에 걸쳐 규모를 늘리기 어려움
- ID의 유일성은 보장되겠지만 그 값이 시간 흐름에 맞춰 커지도록 보장할 수는 없음
- 서버를 추가하거나 삭제할 때도 잘 동작하도록 만들기 어려움

#### UUID

컴퓨터 시스템에 저장되는 정보를 유일하게 식별하기 위한 128비트짜리 수, 중복 생길 확률 매우 낮음

**장점**

- UUID를 만드는것은 단순하고 서버 사이의 조율이 필요 없어 동기화 이슈도 없음
- 각 서버가 자기가 쓸 ID를 알아서 만드는 구조이기 때문에 규모 확장도 쉬움

**단점**

- ID가 128비트로 길다
- 설계 범위가 64비트로 정해져 있으면 사용할 수 없다
- ID에 숫자가 아닌 값이 포함될 수 있음

#### 티켓 서버

[auto_increment 기능을 갖춘 데이터 베이스 서버=티켓서버]를 중앙 집중형으로 하나만 사용

**장점**

- 유일성이 보장되는 오직 숫자로만 구성된 ID를 쉽게 만들 수 있음
- 구현하기 쉽고, 중소 규모 애플리케이션에 적합

**단점**

- 티켓 서버가 SPOF가 됨 
→ 티켓 서버 장애 발생 시, 이 서버를 이용하는 모든 시스템이 영향을 받음
→ 이 이슈를 피하기 위해 티켓 서버 여러대로 늘림
→ 데이터 동기화 문제 발생

#### 트위터 스노플레이크 접근법

64비트 ID, 생성해야 하는 ID의 구조를 여러 절로 분할

- 사인 비트: 1비트 할당, 쓰임새는 없지만 나중을 위해서…
- 타임스탬프: 41비트 할당, epoch 이후로 몇밀리초 경과했는지 나타내는 값
(트위터는  1288834974657가 epoch값)
- 데이터센터 ID: 5비트 할당, 32개의 데이터 센터 지원
- 서버 ID: 5비트 할당, 데이터센터당 32개의  서버를 사용할 수 있음
- 일련번호: 12비트 할당, ID를 생성할때마다 일련번호를 1만큼 증가시키고 1밀리초 경과할때마다 0으로 초기화 됨

## 3단계 상세 설계

트위터 스노플레이크 접근법 사용해 설계 진행

불변값: 데이터 센터 ID, 서버 ID
가변값: 타임스탬프, 일련번호

#### 타임스탬프

타임스탬프 값 UTC로 만드는법:
→ 타임스탬프 값 십진수로 변환
→ 변환된 값에 epoch를 더함
→ 결과로 얻어진 밀리초 값 UTC 시각으로 변환

특이사항
* 타임스탬프는 최대값이 정해져 있기 때문에 69년동안만 정상동작 
→ 시간이 지나면 기원시각을 바꾸거나 다른 ID 체계로 마이그레이션 해야됨

#### 일련번호

일련번호는 12비트로 4096개의 값을 가질 수 있음

## 마무리

! 주어진 요구사항에 맞는 설계를 진행해야 한다

- 시계 동기화: 타임스탬프를 만드는 시계가 전부 같은 시계를 사용한다고 가정하고 사용함, 하나의 서버가 여러 코어에서 실행될때는 유효하지 않은 가정일수도 있다 → NTP가 그런 문제를 해결하는 가장 보편적 수단
- 각 section 길이 최적화: 동시성이 낮고 수명이 긴 애플리케이션은 일련번호 절의 길이를 줄이고 타임스탬프 절의 길이를 유동적으로 조절할 수 있음
- 고가용성: ID 생성기는 필수 불가결 컴포넌트로 아주 높은 가용성이 필요함
