# 6장. 키-값 저장소 설계

## 키-값 저장소

> 키-값 데이터베이스라고도 불리는 non-relational 데이터베이스
저장소에 저장되는 값은 고유 식별자를 키로 가져야 함
 

**Key → 일반 텍스트/해시 값 등 가능, 키는 짧을수록 유리**

**Value → 값은 무슨 타입이든 상관 없음**

- put(key, value): 키-값 쌍을 저장소에 저장
- get(key): 인자로 주어진 키에 매달리 값을 꺼냄

---

### 문제 이해 및 설계 범위 확정

1. 키-값 쌍의 크기 설정
2. 다양한 데이터 크기 저장할 수 있어야 함
3. 높은 가용성 제공
4. 높은 규모 확장성 제공
5. 데이터 일관성 수준 조정 가능해야 함
6. 응답 latency 짧아야 함

---

### 단일 서버 키-값 저장소

- 키-값 쌍을 메모리에 해시 테이블로 저장
    - 빠른 속도 보장
    - 모든 데이터를 메모리에 저장하는 것이 불가능 할 수 있음
    - 데이터 압축, 자주 쓰는 데이터만 메모리에 두고 나머지는 디스크에 저장하더라도 저장공간 부족 할 수 있음
        - **분산 키-값 저장소**를 만들어야 함

---

### 분산 키-값 저장소(분산 해시 테이블)

> 키-값 쌍을 여러 서버에 분산시킴
> 

#### CAP 정리

CAP 정리는 데이터 Consistency, Availability, Partition tolerance라는 세가지 요구사항을 동시에 만족하는 분산 시스템을 설계하는 것은 불가능 하다는 정리

- 데이터 일관성: 분산 시스템에 접속하는 모든 클라이언트는 어떤 노드에 접속 했는지에 관계없이 항상 일정한 데이터 값을 읽을 수 있어야 함
- 가용성: 분산 시스템에 접근할때 일부 노드에 장애가 발생해도 항상 응답을 받을 수 있어야 함
- 파티션 감내: 파티션은 두 노드 사이에 통신 장애가 발생했음을 의미, 파티션 감내는 네트워크에 파티션 생겨도 시스템은 계속 동작해야 함

**CAP 정리는 두가지를 충족하면 하나는 반드시 희생 된다는 것을 의미**

CP 시스템: 일관성, 파티션 감내를 지원하는 저장소. 가용성을 희생

AP 시스템: 가용성, 파티션 감내를 지원하는 저장소. 일관성을 희생

CA 시스템: 일관성, 가용성을 지원하는 저장소. 파티션 감내를 희생하는데 네크워크 장애는 피할수 없으므로, 시스템은 파티션 감내할 수 있도록 설계되어야 하기 때문에 CA 시스템은 전재하지 않음

**이상적 상태**

네트워크가 파티션 되는 상황은 일어나지 않고 하나의 노드에 기록된 내용은 다른 노드들에도 복제 돼서 데이터 일관성과 가용성이 만족됨

**실세계의 분산 시스템**

분산 시스템은 파티션 문제를 피할 수 없기때문에 파티션 문제가 발생하면 일관성과 가용성 중에 하나를 선택해야 함

#### 시스템 컴포넌트

키-값 저장소 구현에 사용될 핵심 컴포넌트 및 기술

- 데이터 파티션
- 데이터 다중화
- 일관성
- 일관성 불일치 해소
- 장애 처리
- 시스템 아키텍처 다이어그램
- 쓰기 경로
- 읽기 경로

**데이터 파티션**

대규모 애플리케이션은 전체 데이터를 한 서버에 다 넣는 것은 불가능하기 때문에 데이터를 작은 파티션들로 분할한 다음 여러 대 서버에 분할한 다음 여러대 서버에 저장한다

데이터를 나눌 때 중요한 문제

- 데이터를 여러 서버에 고르게 분산할 수 있는가
- 노드가 추가되거나 삭제될 때 데이터의 이동을 최소화할 수 있는가

→ 5장에서 배운 안정 해시로 데이터 파티션

**데이터 다중화**

높은 가용성과 안정성 확보를 위해 데이터를 N개의 서버에 비동기적으로 다중화할 필요가 있음

데이터를 다중화할때는 링을 순회하며 입력된 N개의 서버로 데이터를 복사하는데 가상노드일때는 물리 서버를 중복으로 선택하지 않는 것이 중요함

**데이터 일관성**

여러 노드에 다중화된 데이터는 적절히 동기화 되어야 함

정족수 합의 프로토콜을 사용해서 읽기/쓰기 연산에서 일관성을 보장할 수 있음

**정족수 합의(Quorum Consensus)**

- N = 사본 개수
- W = 쓰기 연산에 대한 정족수. 쓰기 성공으로 간주되려면 적어도 W개 서버로부터 쓰기 성공 응답을 받아야 함
- R = 읽기 연산에 대한 정족수. 읽기 성공으로 간주되려면 적어도 R개 서버로부터 응답을 받아야 함

중재자는 클라이언트와 노드 사이에서 프락시 역할을 함

W, R, N 값 구성에 따른 트레이드오프

**일관성 모델**

- 강한 일관성: 모든 읽기 연산은 가장 최근에 갱신된 결과를 반환. 클라이언트는 절대로 낡은(out-of-date) 데이터를 보지 못함
- 약한 일관성: 읽기 연산은 가장 최근에 갱신된 결과를 반환하지 못할 수 있음
- 결과적 일관성: 약한 일관성의 한 형태로, 갱신 결과가 결국에는 모든 사본에 반영(동기화)되는 모델

→ 강한 일관성 달성 방법: 모든 사본에 현재 쓰기 연산의 결과가 반영될 때까지 해당 데이터에 대한 읽기/쓰기를 금지

→ 이 방법은 고가용성 시스템에 적합하지 않음. 다이나모, 카산드라 같은 저장소는 결과적 일관성 모델 채택

**비 일관성 해소 기법: 데이터 버저닝**

- 버저닝: 데이터를 변경할 때마다 해당 데이터의 새로운 버전을 만드는 것. 각 버전의 데이터는 변경 불가능
- 벡터 시계: [서버, 버전]의 순서쌍을 데이터에 매단 것. 어떤 버전이 선행 버전인지, 후행 버전인지, 충돌이 있는지 판별하는데 사용
    - 데이터 D를 서버 Si에 기록하면 [Si, vi]가 있으면 vi를 증가시키고, 없으면 새 항목 [Si, 1]을 만듦
- 벡터 시계의 단점
    - 충돌 감지 및 해소 로직이 클라이언트에 들어가야 해서 클라이언트 구현이 복잡해짐
    - [서버, 버전]의 순서쌍 개수가 빠르게 늘어남 → 임계치 설정하여 오래된 순서쌍을 벡터 시계에서 제거하도록 해야 함

**장애 처리**

**장애 감지**

- 분산 시스템에서는 한 대 서버가 죽었다고 해서 바로 장애 처리를 하지는 않음. 보통 두 대 이상의 서버가 발생했다고 간주할 때 처리
- 가십 프로토콜: 분산형 장애 감지 방법
    - 각 노드는 멤버십 목록을 유지. 멤버십 목록은 각 멤버 ID와 그 박동 카운터 쌍의 목록
    - 각 노드는 주기적으로 자신의 박동 카운터를 증가시킴
    - 각 노드는 무작위로 선정된 노드들에게 주기적으로 자기 박동 카운터 목록을 보냄
    - 박동 카운터의 값이 지정된 시간 동안 갱신되지 않으면 해당 멤버는 장애 상태인 것으로 간주

**일시적 장애 처리**

- 엄격한 정족수: 읽기와 쓰기 연산을 금지
- 느슨한 정족수: W개의 건강한 서버와 R개의 건강한 서버를 선택하여 연산을 수행
    - 임시 위탁: 장애인 서버 대신 임시로 다른 서버가 처리, 복구 후 해당 데이터를 반환

**영구 장애 처리**

- 반-엔트로피 프로토콜: 사본들을 비교하여 최신 버전으로 갱신하는 과정을 포함
- 머클 트리: 사본 간의 일관성이 망가진 상태를 탐지하고 전송 데이터의 양을 줄이기 위해 사용
    - 각 노드의 해시값을 레이블로 가지는 트리 구조
    - 두 머클 트리의 루트 해시값이 같으면 같은 데이터, 다르면 버킷 기준으로 다른 데이터를 가진 버킷을 탐색하여 동기화

**시스템 아키텍처 다이어그램**

- 클라이언트는 키-값 저장소가 제공하는 두 가지 단순한 API(put, get)과 통신
- 중재자는 클라이언트에게 키-값 저장소에 대한 프락시 역할을 하는 노드
- 노드는 안정 해시의 해시 링 위에 분포
- 노드를 자동으로 추가 또는 삭제할 수 있도록 시스템은 완전히 분산
- 데이터는 여러 노드에 다중화됨
- 모든 노드가 같은 책임을 지므로 SPOF는 존재하지 않음

**노드가 지원해야 하는 기능**

- 클라이언트 API
- 장애 감지
- 데이터 충돌 해소
- 장애 복구 메커니즘
- 다중화
- 저장소 엔진

**쓰기 경로**

- 쓰기 요청이 커밋 로그 파일에 기록됨
- 데이터가 메모리 캐시에 기록됨
- 메모리 캐시가 가득 차거나 사전에 정의된 임계치에 도달하면 데이터는 디스크에 있는 SSTable에 기록됨
    - Sorted-String Table: (키, 값)의 순서쌍을 정렬된 리스트 형태로 관리하는 테이블

**읽기 경로**

- 데이터가 메모리 캐시에 있는지 검사
- 없으면 Bloom filter를 통해 어떤 SSTable에 키가 보관되어 있는지 검사
- SSTable에서 데이터를 가져와 클라이언트에게 반환
