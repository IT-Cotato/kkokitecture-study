# 2장. 개략적인 규모 추정
> 보편적으로 통용되는 성능 수치상에서 사고실험을 행하여 추정치를 계산하는 행위로서, 어떤 설계가 요구사항에 부합할 것인지 보기 위한 것

## 모든 프로그래머가 알아야 하는 응답지연 값
> 34p 표 2-2 참고

- 디스크는 느리고 메모리는 빠름
- 디스크 탐색은 느림
	- HDD(디스크)
		- 탐색 시간: **5~15ms** 
		- 회전 지연: 추가로 2~6ms 발생
	- SSD(참고)
		- 탐색 시간: **0.05~0.15ms** (50~150µs)
		- 기계적 움직임이 없으므로 회전 지연 없음
- 압축은 빠름
	- 데이터 전송 전 압축
- 데이터 센터는 여러 지역에 분산, 센터들 간 데이터 전송은 시간이 걸림

## 가용성에 관계된 수치들
##### 가용성
> 시스템이 오랜 시간 동안 지속적으로 중단 없이 운영될 수 있는 능력

##### 가용성(Availability) SLA 기준표

| 가용성      | 연간 다운타임 | 월간 다운타임 | 주간 다운타임 |
| -------- | ------- | ------- | ------- |
| 99%      | 3.65일   | 7.31시간  | 1.68시간  |
| 99.9%    | 8.77시간  | 43.83분  | 10.08분  |
| 99.99%   | 52.60분  | 4.38분   | 1.01분   |
| 99.999%  | 5.26분   | 26.30초  | 6.05초   |
| 99.9999% | 31.56초  | 2.63초   | 604ms   |

> 9가 많을수록 다운타임이 기하급수적으로 감소

## 예제: 트위터 QPS와 저장소 요구량 추정
##### 사용자 수 추정

- MAU (월간 활성 사용자) = 3억 (300M)
- DAU (일간 활성 사용자) = MAU × 50% = 1.5억 (150M)

##### QPS 추정

- 평균 QPS = DAU × 평균 요청 수 ÷ 86,400초
- 평균 QPS ≈ 1,736 QPS
- 피크 QPS = 평균 × 2 ≈ 3,472 QPS

##### 미디어 저장소 추정

- 일일 트윗 수 = DAU × 2 = 3억 트윗/일
- 미디어 포함 = 10% = 3천만 미디어/일
- 일일 저장량 = 3천만 × 1MB = 30TB / 일
- 5년 저장량 = 30TB × 365 × 5 = 약 55PB

## 팁
> 서비스의 규모 추정 면접에서 가장 중요한 것은 결과보다 올바른 절차를 밟느냐가 중요함
- 근사치를 활용한 계산을 한다
	- 면접에서는 계산 결과의 정확함을 평가하는것이 아니기 때문에 근사치를 활용해 계산 시간을 줄인다
- 가정은 미리 적어두고 빠르게 확인할 수 있도록 한다
- 숫자에 단위 붙이는걸 잊지 않는다
- 면접에 자주 나오는 개략적 규모 추정 문제
	- QPS, 최대 QPS, 저장소 요구량, 캐시 요구량, 서버 수 추정


# 3장.  시스템 설계 면접 공략법
> 시스템 설계 면접은 결과물보다 과정을 평가한다. 
-  완벽한 설계안을 요구하는 자리가 아님 
- 모호한 문제를 협력하여 해결책을 찾아가는 
- 시뮬레이션 - 정해진 결말도, 정답도 없음
##### 면접관이 실제로 보는 것 
1. 설계 기술 시연 - 어떻게 문제에 접근하는가 
2. 결정에 대한 방어 능력 - 왜 이런 설계를 선택했는가 
3. 협력 가능성 - 압박 상황에서도 소통이 되는가 
4. 좋은 질문 능력 - 모호한 문제를 구체화할 수 있는가 
##### Red Flag 
- 설계의 순수성에 집착 → 타협적 결정(tradeoff)을 무시 
- 과도한 엔지니어링(over-engineering) → 시스템 비용 증가 
- 완고함, 편협함


## 효과적 면접을 위한 4단계 접근법

### 1단계 문제 이해 및 설계 범위 확정
> 바로 답부터 들이밀지 않는다 
> 요구사항을 제대로 파악하지 않고 답을 내놓는 건 면접관 입장에서 부정적 신호
>  먼저 질문을 통해 요구사항과 가정들을 명확히 하는 것이 핵심
- 구체적으로 어떤 기능을 만들어야 하는지
- 제품 사용자 수 규모
- 회사의 규모는 얼마나 빠르게 커진다고 예상하는지? 
- 기간에 따른 회사 규모는 어떻게 추정되는지?
- 회사가 사용하는 기술 스택, 설계를 단순화 하기 위해 활용할 수 있는 기존 서비스

### 2단계 개략적인 설계안 제시 및 동의 구하기

- 개략적인 설계안을 제시하고 의견을 구한다. 면접관을 팀원처럼 대한다.
- 적을수 있는 곳에 핵심 컴포넌트를 포함하는 다이어그램을 그림
	핵심 컴포넌트
	- 클라이언트(모바일/웹)
	- API
	- 웹 서버
	- 데이터 저장소
	- 캐시
	- CDN
	- 메세지 큐
- 설계안이 규모에 맞는 제약사항들을 만족하는지 계산해본다
	- edge case를 발견하기 위해서 시스템의 구체적 사용 사례도 살펴본다

### 3단계 상세 설계
- 설계 대상 컴포넌트 사이의 우선순위를 정한다
	- 불필요한 세부사항에 시간을 쓰지 않느다
### 4단계 마무리
- 시스템 병목구간, 설계안에 대한 개선점 질문이 들어오는 경우
	- 개선할 부분이 없다는 답은 하지 않는다
- 설계를 요약해주기
	- 여러 해결책을 제시한 경우에 효과 있음
- 오류발생 상황에 대해 따져보기
	- 서버 오류, 네트워크 장애 등
- 운영 이슈 논의
	- 메트릭 수집, 모니터링, 로그, 배포 과정
- 규모 확장에 대한 논의
- 앞에서 다루지 못했던 세부적 개선사항 제안


#### 해야할것
- 스스로 내린 가정이 옳다고 진행하기 보다는 질문을 통해 확인
- 문제의 요구사항 이해
- 정답은 없음, 회사 규모에 따른 설계안인지 확인
- 면접관과 소통하며 사고의 흐름을 이해 시키기
- 하나의 해법 보다는 여러 해법을 제시하는게 좋음
- 개략적인 설계를 제시했을때 면접관이 동의하면, 각 컴포넌트의 세부사항을 설명한다.( 중요한 컴포넌트부터 차례대로)
- 면접관과 팀처럼 협력

### 하지말것
- 전형적인 면접 문제는 대비하지 않고 면접장에 가지 않는다
- 요구사항, 가정을 분명히 하고 설계를 시작하지 않는다
- 초기 설께안 작성할 때는 특정 컴포넌트의 세부사항을 너무 깊이 설명하지 않는다
- 질문 하는 것을 주저하지 안흔다.
- 설계안을 내놓았다고 면접이 끝났다고 생각하지 않는다.

### 시간 배분
- 1단계 - 문제 이해 및 설계 범위 확정: 3min ~ 10min
- 2단계 - 개략적 설계안 제시 및 동의 구하기: 10min ~ 15min
- 3단계 - 상세 설계: 10min ~ 50min
- 4단계 - 마무리: 3min ~ 5min
