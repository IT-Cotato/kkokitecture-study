# 4장. 처리율 제한 장치의 설계
#### 처리율 제한 장치

> 클라이언트 또는 서비스가 보내는 트래픽의 처리율을 제어하기 위한 장치이다
> 
- 장점
    - DoS(Denial of Service) 공격에 의한 자원 고갈을 방지 할 수 있음
    - 비용을 절감할 수 있음
    - 서버 과부하를 막음

## 1단계 문제 이해 및 설계 범위 확정

> 처리율 제한 장치 구현하는 알고리즘의 고유한 장단점과 어떤 제한 장치를 구현해야 하는 지 면접관에게 질문한다
> 

#### 질문 내용

- 어떤 종류의 처리율 제한 장치인가
- 어떤 기준을 통해 API 호출을 제어하는가
- 시스템 규모
- 분산 환경에서 동작해야하는지
- 장치는 독립된 서비스인지 아니면 애플리케이션 코드에 포함되는지
- 처리율 제한 장치에 의해 걸러졌을때 그 사실을 알려야 하는지

#### 요구사항

- 설정된 처리율을 초과하는 요청을 제한
- 낮은 응답시간
- 적은 메모리 사용
- 분산형 처리율 제한
- 예외처리
- 높은 결함 감내성

## 2단계 개략적 설계안 제시 및 동의 구하기

> 기본적인 클라이언트-서버 통신 모델 사용
> 

#### 처리율 제한 장치의 위치

1. 클라이언트 측 : 일반적으로 클라이언트는 처리율 제한을 걸기 어렵다. 클라이언트 요청은 쉽게 위변조가 가능하기때문에 통제하기 어렵기 때문이다.
2. 서버 측 : 그림 4-1 참고
3. 처리율 제한 장치를 API 서버에 두는 대신, 처리율 제한 미들웨어를 만들어 제한하는 것이다.
    1. 1, 2는 서버로 API 요청이 전송 되겠지만 세번째는 미들웨어에 가로막힌다
    2. 클라우드 마이크로 서비스에서 처리율 제한 장치는 API 게이트웨이에 구현된다.

**참고할 지침**

- 현재 사용하는 기술 스택이 서버 측 구현을 지원하기 충분할 정도로 효율이 높은지 확인
- 나의 사업에 필요한 제한 알고리즘을 찾는다. 서버 - 알고리즘 선택 자유로움, 제 3사업자가 제공하는 게이트웨이 - 선택지 제한됨
- 이미 사용자 인증, IP 허용목록 관리 등을 처리하기 위해 API게이트웨이가 설계에 포함됐다면 처리율 제한 기능도 포함시킴
- 처리율 제한 장치를 구현할 인력의 유무

#### 처리율 제한 알고리즘

**토큰 버킷 알고리즘**

- 동작원리
    - 토큰 버킷은 지정된 용량을 갖는 컨테이너이고 버킷이 가득 차면 추가로 공급된 토큰은 버려진다
    - 각 요청은 처리될 때마다 하나의 토큰을 사용한다 → 요청이 도착하면 버킷에 충분한 토큰이 있는기 검사한다
        - 충분한 토큰이 있는 경우 → 버킷에서 꺼내 씀
        - 충분한 토큰이 없는 경우 → 해당 요청은 버려짐
- 이 알고리즘은 2개의 파라미터를 받음
    - 버킷 크기 : 버킷에 담을 수 있는 토큰의 최대 개수
    - 토큰 공급률 : 초당 몇개의 토큰이 버킷에 공급되는지
- 버킷의 개수 설정
    - 통상적으로 API 엔드포인트마다 별도의 버킷을 둔다
    - IP 주소별로 처리율 제한을 적용한다면 IP 주소마다 버킷을 할당한다
    - 초당 처리 가능한 요청 개수로 제한하고 싶다면, 모든 요청이 하나이 버킷을 공유하도록 한다
- **장점**
    - 구현이 쉽다
    - 메모리 사용 측면에서 효율적
    - 짧은 시간에 집중된 트래픽 처리 가능
- **단점**
    - 두개의 파라미터를 가지고있는데, 이 값을 적절하게 튜닝하는 것이 어려움

**누출 버킷 알고리즘**

- 요청 처리율이 고정됨
- FIFO로 동작
- 동작 원리
    - 요청이 도착하면 큐가 가득 차 있는지 확인, 빈자리가 있는 경우에 큐에 요청 추가
    - 큐가 가득 차 있는 경우에는 새 요청 버려짐
    - 지정된 시간마다 큐에서 요청 꺼내서 처리
- 이 알고리즘은 2개의 파라미터를 받음
    - 버킷 크기 : 큐 사이즈와 같은 값, 큐에는 처리될 항목 보관
    - 처리율 : 지정된 시간당 몇개의 항목을 처리할지 지정(보통 초단위)
- **장점**
    - 큐의 크기가 제한되어 메모리 사용량에서 효율적
    - 고정된 처리율로 안정된 출력이 필요한 경우에 적합
- **단점**
    - 단시간에 많은 트래픽 → 오래된 요청 샇이고, 최신 요청들 버려짐
    - 두개의 인자를, 올바르게 튜닝하기 어려움

**고정 윈도 카운터 알고리즘**

- 동작 원리
    - 타임라인을 고정된 간격의 윈도우로 나누고, 각 윈도우마다 카운터를 붙인다
    - 요청이 접수될때 마다 이 카운터의 값은 1씩 증가한다
    - 카운터의 값이 설정된 임계치에 도달하면 새로운 요청은 새 윈도우가 열릴 때까지 버려짐
- **장점**
    - 메모리 효율이 좋음
    - 이해하기 쉬움
    - 윈도가 닫히는 시점에 카운터를 초기화하는 방식은 특정한 상황에서 좋음
- **단점**
    - 윈도우 경계 부근에서 일시적으로 트래픽이 많이 몰리면, 기대했던 시스템 처리 한도보다 많은 양의 요청이 처리됨

**이동 윈도 로깅 알고리즘**

- 고정 윈도 카운터 알고리즘의 문제점을 해결한 알고리즘
- 동작 원리
    - 요청의 타임스탬프를 추적, 타임스탬프는 Redis, sorted set같은 캐시에 보관
    - 새 요청이 오면 만료된 타임스탬프는 제거
    - 새 요청의 타임스탬프를 로그에 추가
    - 로그의 크기가 허용치보다 같거나 작으면 요청을 시스템에 전달, 그렇지 않으면 처리 거부
- **장점**
    - 알고리즘이 매우 정교함
    - 어느 윈도우를 보든, 허용되는 요청의 개수는 처리율 한도를 넘지 않음
- **단점**
    - 다량의 메모리 사용함(거부된 타임스탬프도 보관)

**이중 윈도 카운터 알고리즘**

- 고정 윈도 카운터 알고리즘 + 이동 윈도 로깅 알고리즘
- 동작 원리
    - 현재 시간 기준으로 두 개의 인접한 시간 윈도우(이전/현재)의 요청 수를 각각 카운트한다.
    - 현재 윈도우 요청 수에, 이전 윈도우 요청 수를 시간 비율에 따라 가중치로 일부 반영한다.
    - 이 합산 값이 허용된 처리율을 넘으면 요청을 차단하고, 아니면 허용한다.
- **장점**
    - 이전 시간대의 평균으로 현재 윈도의 상태 계산하기 때문에 짧은 시간에 몰리는 트래픽에 잘 대응
    - 메모리효율 좋음
- **단점**
    - 직전 시간대의 요청이 균등하게 분포되었다고 가정하고 추정치를 계산하기 때문에 다소 느슨

**카운터 보관 방법**

- 디스크는 느리기 때문에, 메모리상에서 동작하고 시간에 기반한 만료정책이 있는 캐시가 좋다

## 3단계 상세 설계

#### 처리율 제한 규칙

- 규칙들은 보통 설정 파일 형태로 디스크에 저장됨

#### 처리율 한도 초과 트래픽의 처리

- 한도 제한에 걸리면 API는 429 응답을 클라이언트한테 보내거나 나중에 처리하기 위해 큐에 보관

**처리율 제한 장치가 사용하는 HTTP 헤더**

- X-Ratelimit-Remaining
- X-Raatelimit-Limit
- X-Ratelimit-Retry-After
