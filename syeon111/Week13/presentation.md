# Cassandra가 채팅 이력 저장소로 적합한 이유

---

## 1. 왜 RDB가 채팅 이력에 안 맞나

채팅 시스템은 일반적인 서비스와 읽기/쓰기 패턴이 근본적으로 다르다.

- **쓰기가 압도적으로 많음**: 사용자들은 메시지를 보내는 것보다 읽는 게 훨씬 적음. 특히 활성 채팅방에서는 초당 수백 건의 쓰기가 지속적으로 발생
    - 채팅 이력은 수정/삭제가 거의 없고 insert만 계속 발생하는 append-only 패턴 — RDB가 강점을 보이는 트랜잭션, join, 복잡한 쿼리가 전혀 필요 없는 구조
    - 실제로 페이스북 메신저는 하루 600억 건, Discord는 수조 건의 메시지를 저장 — 이 규모에서 RDB 단일 인스턴스는 애초에 불가능
- **RDB의 쓰기 병목**: RDB는 쓰기가 발생할 때마다 인덱스를 갱신해야 함. 메시지가 쌓일수록 인덱스가 커지고 쓰기 성능이 점점 저하됨
- **Long tail 문제**: 사용자는 최근 메시지만 주로 읽고, 수개월 전 메시지는 거의 안 봄. 그러나 RDB는 오래된 데이터와 최근 데이터를 구조적으로 구분하지 않음
- **수평 확장의 어려움**: 메시지가 수조 건을 넘어가면 샤딩이 필요한데, RDB 샤딩은 구현이 복잡하고 join이나 트랜잭션 같은 기능을 포기해야 함 — 채팅 이력엔 어차피 필요 없는 기능들

## 2. Cassandra가 왜 잘 맞나

**LSM Tree 기반 쓰기 구조**

- Cassandra는 쓰기를 디스크에 바로 쓰지 않고, 우선 메모리(memtable)에 기록한 다음 나중에 디스크(SSTable)에 순차적으로 플러시
- 인덱스를 실시간으로 갱신하는 RDB와 달리 쓰기가 항상 빠르고 일정함
- 트레이드오프: 읽기는 memtable + 여러 SSTable을 합쳐서 읽어야 해서 쓰기보다 상대적으로 비쌈 — 채팅은 읽기보다 쓰기가 많으니 이 트레이드오프가 유리하게 작동

**수평 확장이 자연스러움**

- 데이터를 partition key 기준으로 여러 노드에 자동으로 분산
- 노드를 추가하면 자동으로 리밸런싱 — RDB처럼 샤딩 로직을 별도로 구현할 필요 없음
- 각 데이터를 기본 3개 노드에 복제해 장애 내성(fault tolerance) 확보

**TTL(Time To Live)**

- 특정 기간이 지난 데이터를 자동으로 삭제하는 기능 내장
- 오래된 채팅 이력을 별도 배치 작업 없이 자동 정리 가능

**일관된 해싱(Consistent Hashing)**

- 노드가 추가되거나 제거될 때 전체 데이터를 재분배하지 않고 영향받는 범위를 최소화하는 방식으로 동작 — 운영 중 노드를 추가해도 서비스 중단 없이 확장 가능

## 3. 채팅 이력 데이터 모델 설계 ← 핵심

!73d503cd99fd43a1d9b6c5bf6c159d72.jpeg

Cassandra에서 데이터 모델 설계의 핵심은 **partition key와 clustering key를 어떻게 잡느냐**다.

**partition key: channel_id**

- 같은 채팅방의 메시지를 같은 노드에 모아두는 효과
- 특정 채널의 메시지를 읽을 때 여러 노드를 탐색할 필요 없이 해당 노드에서 바로 읽어옴
- 단, 인기 있는 채널에 트래픽이 몰리면 그 노드만 과부하가 걸리는 **hot partition** 문제 발생 가능 (뒤에서 설명)

**clustering key: message_id**

- 같은 partition 안에서 message_id 기준으로 정렬된 상태로 저장
- 최근 메시지 N개를 가져오는 쿼리가 자동으로 빠름 — 별도 ORDER BY나 인덱스 없이

**message_id를 Snowflake ID로 만들면**

- timestamp + 서버 ID + sequence number를 조합한 64bit ID
- 유일성 + 시간순 정렬 두 가지를 동시에 만족
- DB에 created_at 컬럼을 따로 두지 않아도 message_id만으로 시간순 정렬 가능

**최종 테이블 구조**

```
(channel_id, bucket) → partition key   -- 채널 + 시간 버킷으로 파티션 분리
message_id            → clustering key  -- Snowflake ID, 시간순 정렬
user_id, content      → 나머지 컬럼
```

bucket을 추가하는 이유: channel_id만 쓰면 한 채널의 모든 메시지가 하나의 파티션에 쌓여 무한정 커짐 → 월별/주별 버킷으로 나눠 파티션 크기를 제한

## 4. Discord의 실제 사례 — Cassandra에서 ScyllaDB로

!c06890eb-9c3d-4141-831c-bf2fe4eade0e_800x1040.webp

Discord의 메시지 저장소 변천사: **MongoDB(2015) → Cassandra(2017) → ScyllaDB(2022)**

**Cassandra로 버티다 한계에 부딪힌 이유**

- 2017년 12개 노드, 수십억 건으로 시작했던 클러스터가 2022년에는 177개 노드, 수조 건으로 성장
- **Hot partition**: 대형 커뮤니티 채널(수만 명)에 트래픽이 몰리면 해당 파티션을 담당하는 노드 전체가 느려지고, 그 영향이 같은 노드의 다른 파티션까지 퍼지는 cascading latency 발생
- **GC 문제**: Cassandra는 Java 기반 → Garbage Collection 일시 정지가 잦았고, 심한 경우 운영자가 수동으로 노드를 재시작해야 하는 상황까지 발생
- 읽기 p99 레이턴시가 40~125ms 범위에서 들쭉날쭉, 예측 불가능한 수준

**ScyllaDB로 이전한 이유**

- C++ 기반이라 GC가 없음 → GC 일시 정지 문제 자체가 사라짐
- shard-per-core 아키텍처: CPU 코어마다 담당 데이터가 분리되어 hot partition의 영향이 다른 코어로 퍼지지 않음
- Cassandra와 쿼리 언어(CQL)가 호환 → 애플리케이션 코드 변경 최소화

**이전 결과**

- 177개 Cassandra 노드 → 72개 ScyllaDB 노드 (노드 수 59% 감소)
- 읽기 p99 레이턴시: 40~125ms → 15ms
- 쓰기 p99 레이턴시: 5~70ms → 5ms (일정하게 유지)

**마이그레이션 방식**

- ScyllaDB에 신규 데이터를 dual-write하면서 Spark migrator로 기존 데이터 이전 시도 → 예상 완료 시간 3개월
- 3개월은 너무 길다고 판단 → Rust로 데이터 마이그레이터를 하루 만에 재작성
- 초당 320만 건 처리, 3개월 → **9일**로 단축

**그 이후**

- 이전 완료 후 첫 번째 대형 트래픽 테스트가 2022년 월드컵 — 트래픽 급증을 문제없이 흡수하며 안정성 검증
- MongoDB → Cassandra → ScyllaDB로 DB는 계속 바뀌었지만 데이터 모델(partition key, clustering key 구조)은 처음부터 지금까지 그대로 — 모델이 틀린 게 아니라 구현체가 버티지 못한 것
