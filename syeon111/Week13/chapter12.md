# 12장. 채팅 시스템 설계

> 채팅 시스템이란 사람들이 하나플 이상 사용하는 커뮤니케이션 시스템으로, 현재 시장에서 가장 널리 쓰이고 있는 서비스들
> 

**대표적인 채팅 앱**

- WhatsApp, Facebook Messenger, WeChat, Slack, Discord, Line 등

---

## 1단계 문제 이해 및 설계 범위 확정

**요구사항 정리**

- 모바일 + 웹 둘 다 지원
- 1:1 채팅 + 그룹 채팅 둘 다 지원
- DAU 5천만 명
- 그룹 채팅 최대 인원: 100명
- 접속상태(온라인/오프라인) 표시 기능 필요
- 텍스트 메시지만 지원 (이미지/비디오는 추후)
- 메시지 길이: 100,000자 이하
- 종단 간 암호화(end-to-end encryption): 현재로서는 필요 없음

## 2단계 개략적인 설계안 제시 및 동의 구하기

#### 클라이언트-서버 통신

채팅 서비스가 제공해야 할 기본 기능

- 클라이언트로부터 메시지 수신
- 수신자(recipient) 결정 및 전달
- 수신자가 접속 중이 아닌 경우, 해당 메시지를 보관했다가 나중에 전달

클라이언트와 서버 사이의 주 통신 프로토콜로 웹소켓(WebSocket) 을 사용한다. 웹소켓을 사용하면 메시지를 보낼 때나 받을 때나 동일한 프로토콜을 쓸 수 있어 구현이 단순하고 서버 측에서 연결 관리를 효율적으로 할 수 있다.

#### 개략적 설계안

시스템을 세 가지 서비스로 나눈다.

**무상태 서비스**

- 로그인, 회원가입, 사용자 프로파일 표시 등 전통적인 요청/응답 서비스
- 로드밸런서 뒤에 위치하며 HTTP로 통신
- 서비스 탐색(service discovery): 클라이언트가 접속할 채팅 서버의 DNS 호스트명을 알려주는 역할

**상태 유지 서비스**

- 채팅 서비스와 접속상태 서비스, 두 가지가 상태 유지 서비스에 해당
- 각 클라이언트는 채팅 서버와 독립적인 네트워크 연결을 유지하며, 서버가 바뀌지 않는 한 같은 채팅 서버에 접속 유지

**제3자 서비스 연동**

- 채팅 앱에서 가장 중요한 제3자 서비스는 푸시 알림 서비스
- 앱이 실행 중이 아닌 경우에도 알림을 줄 수 있어야 함

#### 전체 컴포넌트

- 채팅 서버: 실시간으로 메시지를 주고받는 역할
- 접속상태 서버: 사용자의 접속 여부를 관리
- API 서버: 로그인, 회원가입, 프로파일 변경 등 그 외 전부 처리
- 알림 서버: 푸시 알림 전송
- 키-값 저장소: 채팅 이력(chat history) 보관

#### 저장소

채팅 시스템에 사용하는 데이터는 두 가지 유형이다.

- 사용자 프로파일, 친구 목록, 설정 등 → 일반적인 관계형 데이터베이스
- 채팅 이력 데이터 → NoSQL 권장

채팅 이력에 키-값 저장소를 쓰는 이유

- 채팅 이력 데이터의 양은 엄청남 (페이스북 메신저 기준 일 600억 건)
- 최근 메시지만 주로 조회하고, 오래된 메시지는 잘 보지 않음 (long tail)
- 키-값 저장소는 수평적 규모 확장(horizontal scaling)이 쉬움
- 디스코드, 페이스북 메신저, 슬랙 모두 키-값 저장소를 사용 중

#### 데이터 모델

**1:1 채팅 메시지 테이블 (message)**

- message_id (bigint, PK)
- message_from (bigint)
- message_to (bigint)
- content (text)
- created_at (timestamp)

**그룹 채팅 메시지 테이블 (group message)**

- channel_id (bigint, PK) — partition key. 그룹 채팅 자체를 나타내며 특정 채널의 메시지에만 접근
- message_id (bigint, PK)
- user_id (bigint)
- content (text)
- created_at (timestamp)

**메시지 ID**

- message_id는 유일성과 시간 순서(정렬 가능) 두 가지 조건을 만족해야 함
- RDBMS의 auto_increment는 NoSQL에서 보통 제공하지 않음
- 대안: 지역 순서 번호 생성기(local sequence number generator) — 전역이 아닌 같은 그룹 안에서만 유일성을 보장하면 되기 때문에 사용 가능

## 3단계 상세 설계

#### 서비스 탐색

- Apache Zookeeper를 사용하여 모든 채팅 서버를 등록하고, 클라이언트가 접속했을 때 가장 적합한 채팅 서버를 배정하는 기능을 구현
- 서버 선택 기준: 클라이언트의 위치(geographical), 서버 용량(capacity) 등

#### 1:1 채팅 메시지 처리 흐름 (그림 12-12)

1. 사용자 A가 채팅 서버 1로 메시지 전송
2. 채팅 서버 1이 ID 생성기를 사용해 해당 메시지의 ID 결정
3. 채팅 서버 1이 메시지 동기화 큐로 메시지 전송
4. 메시지가 키-값 저장소에 보관됨
5. (a) 사용자 B가 접속 중인 경우 → 채팅 서버 2로 전송, 사용자 B의 웹소켓 연결로 전달
6. (b) 사용자 B가 미접속 상태인 경우 → 푸시 알림 서버로 전달

#### 여러 단말 사이의 메시지 동기화

- 각 단말은 `cur_max_message_id`라는 변수를 유지 — 해당 단말이 현재 마지막으로 받은 메시지 ID를 추적
- 키-값 저장소에서 `cur_max_message_id`보다 큰 message_id를 가진 메시지를 새 메시지로 간주해서 동기화

#### 소규모 그룹 채팅 메시지 흐름

- A가 메시지를 보내면, 그 메시지가 그룹 내 모든 수신자의 메시지 동기화 큐에 각각 복사됨
- 각 사용자의 큐는 해당 사용자만 구독하므로 메시지 수신이 간단해짐
- 단, 그룹 크기가 500명 이하일 때 효과적. WeChat이 이 방식을 사용하며 그룹 크기를 500명으로 제한하고 있는 이유도 이것

#### 접속상태 표시

사용자의 접속 상태는 접속상태 서버(presence server)가 관리한다.

**로그인**: 사용자가 로그인하면 클라이언트와 실시간 서비스(real-time service) 사이에 웹소켓 연결이 맺어지고, 접속상태 서버가 `{status: online, last_active_at: timestamp}` 를 키-값 저장소에 보관

**로그아웃**: 웹소켓 연결이 끊어지면 키-값 저장소의 상태가 `offline`으로 변경

**접속 장애 처리**: 웹소켓 연결이 끊어졌다고 해서 바로 오프라인으로 바꾸면 안 됨. 클라이언트가 서버로 박동(heartbeat) 이벤트를 주기적으로 전송하고, 마지막 이벤트를 받은 지 x초 이내에 또 다른 박동 이벤트를 받으면 온라인 상태를 유지. x = 30초 동안 이벤트를 보내지 않으면 오프라인으로 변경

**상태 정보의 전송**: 발행-구독 모델(publish-subscribe model) 사용. 사용자 A와 친구 B, C, D가 있다면 A-B, A-C, A-D 총 세 개의 채널을 구독하고 각 채널로 접속상태 변화를 전달. 그룹 크기가 작을 때 효과적이며 그룹이 커지면 비용이나 시간이 많이 들게 됨

## 4단계 마무리

추가로 논의하면 좋을 것

- 미디어 지원: 사진이나 비디오 등의 미디어는 텍스트에 비해 크기가 크다. 압축 방식, 클라우드 저장소, 섬네일(thumbnail) 생성 등을 논의해 볼 것
- 종단 간 암호화: 발신인과 수신자 이외에는 아무도 메시지 내용을 볼 수 없도록 하는 방식
- 캐시: 클라이언트에 이미 읽은 메시지를 캐시하면 데이터 전송량을 줄일 수 있음
- 로딩 속도 개선: Slack은 사용자의 데이터, 채널 등을 지역화하여 앱 로딩 속도를 개선
- 오류 처리
    - 채팅 서버 오류: 채팅 서버 하나가 죽으면 서비스 탐색 기능이 동작하여 클라이언트가 새로운 서버에 자동으로 접속하도록 유도
    - 메시지 재전송: 재시도(retry)나 큐(queue)는 메시지의 안정적 전송을 보장하기 위해 흔히 사용되는 기법
