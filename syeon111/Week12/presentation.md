# Twitter — 팔로워 5천만 명의 트윗 한 개가 시스템을 어떻게 흔드나

---

## 1. Fail Whale 시대

- Twitter는 2007~2012년 사이 잦은 다운타임으로 악명이 높았음. 서비스가 죽으면 고래 그림이 떴고 이게 "Fail Whale"이라는 밈이 될 정도였음
- 초기 구조는 단순했음 — 누군가 트윗을 올리면 그 순간 팔로워 모두의 타임라인에 즉시 밀어넣는 방식 (팬아웃-온-라이트)
- 평범한 사용자 기준엔 문제 없었지만, Oprah나 Lady Gaga 같은 셀럽이 트윗을 올리는 순간 시스템이 다운되는 패턴이 반복됨
- 단순한 트래픽 문제가 아니라 **구조적 문제**로 판단, 아키텍처 자체를 다시 설계하기로 결정

---

## 2. 왜 셀럽 트윗 하나가 시스템을 죽였나

- Twitter의 읽기/쓰기 비율은 **300,000 QPS 읽기 vs 6,000 QPS 쓰기** — 읽기가 50배 많은 구조
- 이 비율 때문에 "쓰기에 미리 일을 몰아넣고 읽기는 빠르게" 전략(팬아웃-온-라이트)이 합리적으로 보였음
- 문제는 팔로워가 많은 계정: 팔로워 1억 명인 셀럽이 트윗을 올리면 1억 건의 타임라인 업데이트가 동시에 발생
- 타임라인 업데이트 1건에 1ms가 걸린다고 하면 → 1억 명 × 1ms = 100,000초, 즉 27시간
- 병렬 처리로 줄여도 셀럽들이 서로 멘션하고 리트윗하는 순간 동시에 수십억 건의 쓰기가 터짐 → 시스템 과부하

---

## 3. 1차 해결 — Redis로 타임라인 전체를 캐시에 올린다

- DB를 직접 읽는 방식 대신, 모든 사용자의 홈 타임라인을 Redis 클러스터에 미리 계산해 올려두는 방식으로 전환
- 누군가 트윗을 올리면 팬아웃 서비스가 소셜 그래프 DB에서 팔로워 목록을 조회한 뒤, 각 팔로워의 Redis 타임라인에 `(tweet_id, author_id, metadata)` 형태로 삽입
- 홈 타임라인은 Redis 클러스터에 최대 800개 항목까지 저장
- 한 사용자의 타임라인은 장애 대비를 위해 3개의 Redis 머신에 복제해 보관
- 트윗 텍스트 자체는 Redis에 넣지 않음 — tweet ID만 저장하고, 실제 텍스트는 읽을 때 별도 조회. 캐시 크기 최소화
- 30일 이상 비활성 사용자의 타임라인은 Redis에서 제거. 해당 사용자가 다시 접속하면 디스크에서 재구성
- 결과: 읽기는 Redis에서 O(1)로 즉시 응답. 하지만 쓰기는 여전히 O(팔로워 수) 문제가 남음

---

## 4. 여전히 남은 문제 — 셀럽 계정

- Redis 타임라인 캐시로 일반 사용자 문제는 해결됐지만, 셀럽 계정의 팬아웃은 여전히 시스템의 병목
- 셀럽들이 서로 트윗하고 리트윗하는 상황에서는 목표인 5초 이내 전달이 불가능한 경우가 많았고, 그 부작용으로 원본 트윗보다 답글이 먼저 도착하는 현상도 발생
- 셀럽은 수가 적지만 전체 팬아웃 트래픽의 대부분을 차지하는 구조 — 소수의 계정이 시스템 전체를 좌우하는 문제

---

## 5. 핵심 해결책 — 팔로워 수 기준으로 push/pull을 분기

- 팔로워 약 10,000명을 기준으로 일반 사용자는 팬아웃-온-라이트(push), 셀럽은 팬아웃-온-리드(pull)로 처리하는 하이브리드 방식 도입
- **일반 사용자 (팔로워 < ~10,000명)**: 기존대로 팬아웃-온-라이트. 트윗 올리는 순간 팔로워들의 Redis 타임라인에 즉시 삽입
- **셀럽 (팔로워 > ~10,000명)**: 팬아웃 없음. 트윗은 별도 저장소에만 보관
- 사용자가 타임라인을 열 때: 자신의 Redis 타임라인(일반 사용자 트윗)과 팔로우 중인 셀럽들의 최신 트윗을 그 순간 실시간으로 가져와 **엣지에서 병합(merge)**해서 보여줌
- 기준값(10,000명)은 아키텍처가 아니라 config 값 — 런타임에 조정 가능. 팔로워 수가 기준을 넘으면 플래그를 바꾸는 것만으로 해당 계정의 트윗이 팬아웃을 우회하게 됨

---

## 6. 결과

- 셀럽 팬아웃 문제를 해결하면서 Fail Whale 빈도가 크게 줄어들었음
- 목표인 5초 이내 전달이 대부분의 상황에서 달성 가능해졌고, 300,000 QPS의 읽기 트래픽을 안정적으로 처리
- 단, 하이브리드 구조는 두 가지 장애 모드를 동시에 관리해야 하는 운영 복잡도가 생김 — 셀럽 트윗 캐시 stampede와 일반 사용자 팬아웃 큐 backlog를 각각 별도로 모니터링해야 함
- 이 구조는 이후 Instagram, Facebook 등 대형 소셜 플랫폼의 피드 시스템 설계에도 동일하게 적용됨
