# 11장. 뉴스 피드 시스템 설계

> 뉴스 피드(news feed)란 홈 페이지 중앙에 지속적으로 업데이트되는 스토리들로, 사용자 상태 정보, 사진, 비디오, 링크, 앱 활동, 팔로우하는 사람/페이지/그룹으로부터 나오는 콘텐츠의 모음
> 

**비슷한 유형의 면접 문제**

- 페이스북 뉴스피드 설계
- 인스타그램 피드 설계
- 트위터 타임라인 설계

---

## 1단계 문제 이해 및 설계 범위 확정

**요구사항 정리**

- 모바일 앱 + 웹 둘 다 지원
- 사용자는 새 스토리를 올릴 수 있고, 친구들이 올리는 스토리도 볼 수 있어야 함
- 피드 정렬 기준: 시간 흐름 역순(reverse chronological order)
- 한 사용자의 최대 친구 수: 5,000명
- 트래픽: 매일 천만 명 방문(10million DAU)
- 스토리에 이미지, 비디오 등 미디어 파일 포함 가능

---

## 2단계 개략적인 설계안 제시 및 동의 구하기

설계안은 **(1) 피드 발행(feed publishing)** 과 **(2) 뉴스 피드 생성(news feed building)** 두 파트로 나뉜다.

#### 뉴스 피드 API

**피드 발행 API**

- 새 스토리를 포스팅하기 위한 API
- `POST /v1/me/feed`
- 인자: body(포스팅 내용), Authorization 헤더

**피드 읽기 API**

- 뉴스 피드를 가져오는 API
- `GET /v1/me/feed`
- 인자: Authorization 헤더

#### 피드 발행

- 사용자 → 로드밸런서 → 웹 서버 → 세 가지 서비스로 분기
    - **포스팅 저장 서비스**: 새 포스팅을 포스팅 캐시와 데이터베이스에 저장
    - **포스팅 전송 서비스**: 새 포스팅을 친구의 뉴스 피드에도 전송(팬아웃)
    - **알림 서비스**: 친구에게 새 포스팅 알림을 보내거나 푸시 알림 전송

#### 뉴스 피드 생성

- 지면 관계상 모든 친구의 포스팅을 시간 흐름 역순으로 모아서 만든다고 가정
- 사용자 → 로드밸런서 → 웹 서버 → 뉴스 피드 서비스 → 뉴스 피드 캐시

## 3단계 상세 설계

#### 피드 발행 흐름 상세 설계

**웹 서버**

- 클라이언트와 통신하는 기능뿐 아니라 인증이나 처리율 제한(rate limiting) 기능도 수행
- 올바른 Authorization 헤더를 가진 API 호출만 포스팅 가능
- 스팸이나 욕설을 올리지 못하도록 특정 기간 동안 한 사용자가 올릴 수 있는 포스팅 수에 제한

**포스팅 전송(팬아웃) 서비스**

팬아웃(fanout)이란 어떤 사용자의 새 포스팅을 그 사용자와 친구 관계에 있는 모든 사용자에게 전달하는 과정이다. 두 가지 모델이 있다.

- **팬아웃-온-라이트(fanout-on-write, push 모델)**: 포스팅이 생성되는 시점에 즉시 친구의 뉴스 피드를 갱신
    - 장점: 뉴스 피드를 실시간으로 업데이트할 수 있고, 사용자가 피드를 요청할 때 빠르게 응답 가능
    - 단점: 친구가 많은 사용자(핫키, hotkey)의 경우 쓰기 시점이 너무 많아 시간이 오래 걸림. 비활성 사용자의 피드까지 갱신하느라 자원 낭비 발생
- **팬아웃-온-리드(fanout-on-read, pull 모델)**: 사용자가 피드를 요청할 때(on-demand) 그제서야 최신 피드를 가져오는 방식
    - 장점: 비로그인 사용자의 경우 자원 소비 없음. 로그인하기 전까지 어떤 컴퓨팅 자원도 소비하지 않음
    - 단점: 뉴스 피드를 읽는 시점에 새 포스팅을 가져오는 작업이 필요하므로 피드 생성이 느릴 수 있음
- **두 방식 결합 (본 설계안 채택)**: 대부분의 사용자에게는 팬아웃-온-라이트, 팔로워가 많은 연예인이나 유명인처럼 친구/팔로워가 아주 많은 사용자는 팬아웃-온-리드를 사용해 가져오도록 함

**피드 발행 상세 흐름 (그림 11-4)**

1. 포스팅 전송 서비스가 그래프 데이터베이스에서 친구 ID 목록을 추출
2. 친구 정보 캐시(사용자 정보 캐시)에서 친구 데이터를 가져옴. 알림 설정, 뮤트 여부 등을 필터링해 알림을 받을 최종 친구 목록 확정
3. 친구 목록과 새 포스팅 ID를 메시지 큐에 적재
4. 포스팅 전송 작업 서버가 메시지 큐에서 데이터를 꺼냄
5. 뉴스 피드 캐시에 `<포스팅 ID, 사용자 ID>` 형태로 저장. 뉴스 피드 캐시는 포스팅 ID와 사용자 ID의 순서쌍만 보관하여 캐시 크기 최소화

#### 뉴스 피드 읽기 흐름 상세 설계

1. 사용자가 뉴스 피드 요청 (`GET /v1/me/feed`)
2. 로드밸런서가 요청을 웹 서버 중 하나로 보냄
3. 웹 서버가 피드를 가져오기 위해 뉴스 피드 서비스 호출
4. 뉴스 피드 서비스가 뉴스 피드 캐시에서 포스팅 ID 목록을 가져옴
5. 뉴스 피드 서비스가 사용자 이름, 사용자 사진, 포스팅 콘텐츠, 이미지 등을 사용자 캐시와 포스팅 캐시에서 가져와 완전한 뉴스 피드를 만듦
6. 생성된 뉴스 피드를 JSON 형태로 클라이언트에게 반환. 클라이언트는 해당 피드를 렌더링

#### 캐시 구조

캐시는 뉴스 피드 시스템의 핵심 컴포넌트로, 5계층으로 나눔

- **뉴스 피드**: 뉴스 피드의 ID 보관
- **콘텐츠**: 포스팅 데이터 보관. 인기 콘텐츠는 따로 보관
- **소셜 그래프**: 사용자 간 관계 정보 보관
- **행동(action)**: 포스팅에 대한 사용자 행위 정보 보관. '좋아요', 답글 등
- **횟수(counter)**: 좋아요 횟수, 응답 수, 팔로어 수, 팔로잉 수 등 보관

## 4단계 마무리

추가로 생각해보면 좋을 것

- **규모 확장성**
    - 수직적 규모 확장 vs 수평적 규모 확장
    - SQL vs NoSQL
    - 주-부(master-slave) 다중화
    - 복제본(replica) 읽기
    - 일관성 모델(consistency model)
    - 데이터베이스 샤딩(sharding)
- **웹 서버(web tier) 규모 확장**: 무상태(stateless)로 설계해 동적 수평 확장 가능하게
- **이미지나 비디오 같은 미디어 파일**: CDN에 저장해 빠르게 읽을 수 있도록
- **데이터 사전 로딩**: 피드를 읽는 시스템에 새로운 포스팅을 미리 가져와 지연을 낮추기
- **피드의 한 번에 불러오는 양 제한**: 페이지네이션(pagination) 적용
- **메시지 큐(Message Queue per Second)**: 초당 들어오는 메시지량을 기록하고(monitoring) 필요 시 시스템을 확장할 수 있도록
