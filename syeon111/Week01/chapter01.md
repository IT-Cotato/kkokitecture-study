## 2. 데이터베이스
> 사용자가 늘면 서버 하나로는 충분하지 않아서 여러 서버를 두어야 한다.
- 웹/모바일 트래픽 처리 서버(웹 계층), 데이터베이스로 분리후 독립적으로 확장 가능함

### DB 특징
- 관계형 데이터베이스(RDBMS) 특징
  - 자료를 테이블과 열, 칼럼으로 표현함
  - SQL을 사용하여 어러 테이블에 있는 데이터를 관계에 따라 조인하여 합칠 수 있음
- MySQL, 오라클 데이터베이스, PostgreSQL
- 비 관계형 데이터베이스(NoSQL) 특징
  - 고정된 테이블 구조 없이 다양한 형태의 데이터를 유연하게 저장·처리

### DB 선택 기준
- 일반적으로는 관계형 데이터 베이스 사용
- RDBMS가 구축하는 시스템에 적합하지 않은 경우
  - 초저지연 필요
  - 비정형 데이터
  - 스키마 없이 직렬화 데이터
  - 대용량 데이터 처리

## 3. 수직적 규모 확장 vs 수평적 규모 확장
### 수직적 규모 확장
- 서버에 고사양 자원을 추가하는 행위
- 서버로 유입되는 트래픽의 양이 적을때 수직정 확장 선택
- 단점
  - 확장에 한계가 있음
  - 장애에 대한 자동복구 방안, 다중화 방한 없음
  -> 서버에 장애 발생 시 웹사이트/앱 완전히 중단
### 수평적 규모 확장
- 더 많은 서버를 추가하여 성능을 개선하는 행위
- 대규모 애플리케이션을 지원할때 선택
### 로드밸런서
- 부하 분산 집합에 속한 웹 서버들에게 트래픽 부하를 고르게 분산하는 역할
- 클라이언트는 공인 IP로 접속하고, 로드밸런서가 사설 IP 서버로 전달
### 데이터베이스 다중화
- 서버 사이에 주-부 관계를 설정하고 데이터 원본은 주 서버에, 사본은 부 서버에 저장하는 방식
- 주 데이터베이스에서만 쓰기 연산 지원, 부 데이터 베이스는 주 DB의 사본 저장
- 부 DB에서 연산이 더 많기 때문에 부 DB의 수가 더 많음
### 데이터 베이스 다중화의 장점
- 더 나은 성능 : 부 DB에서 병렬로 처리될 수 있는 쿼리의 수가 늘어나므로, 성능 향상
- 안정성 : 데이터베이스 서버 가운데 일부가 파괴되어도 데이터 보존
- 가용성 : 여러 지욕에 복제해 둠으로써, 하나의 DB에서 장애가 발생하더라도 계속 운영됨

## 4. 캐시
> 값비싼 연산 결과 또는 자주 참조되는 데이터를 메모리 안에 두고, 뒤이은 요청이 보다 빨리 처리될 수 있도록 하는 저장소
### 캐시계층
> 데이터가 잠시 보관되는 곳
- 장점
  - DB보다 훨씬 빠름
  - 성능 개선 됨
  - 데이터 베이스의 부하 감소
  - 규모를 독립적으로 확장할 수 있음
### 캐시 사용 시 유의할 점
- 캐시는 어떤 상황에 바람직한가? 데이터 갱신은 자주 발생하지 않고, 참조가 빈번하게 일어날 떄 
- 어떤 데이터를 캐시에 두어야 하는가? 캐시는 휘발성 메모리 -> 영속적 데이터를 캐시에 두는 것은 바람직하지 않음
- 일관성은 어떻게 유지되는가? 캐시와 저장소 사이의 일관성을 유지하는 것은 어려운 문제
- 장애에는 어떻게 대처할 것인가? 캐시 서버가 한 대일 경우 SPOF 될 가능성 있음, 캐시 서버를 여러 지역에 걸쳐 분산시켜야 함
- 캐시 메모리는 얼마나 크게 잡을 것인가? 캐시 메모리가 너무 작으면 성능이 떨어지는 경우 있음 -> 캐시 과할당 해야함
- 데이터 방출 정책은 무엇인가? LRU 방식 정책이 제일 많이 쓰임

## 5. CDN
> 정적 콘텐츠를 전송하는데 쓰이는, 지리적으로 분산된 서버의 네트워크
### CDN 사용시 고려해야 할 사항
- 비용 : 자주 사용되지 않은 콘텐츠를 캐싱하는 것은 이득이 크지 않음
- 적절한 만료 시한 결정 : 시의성이 중요한 컨텐츠의 경우 만료 시점을 잘 정해야 함
- CDN 장애에 대한 대처 방안 : CDN 자체가 죽었을 경우 서비스가 어떻게 동작해야 하는지 고려해야 함
- 콘텐츠 무효화 방법 : CDN 서비스 사업자가 제공하는 API 이용, 콘텐츠의 다른 버전을 서비스하도록 오브젝트 비저닝 이용

## 6.무상태 웹 계층
> 웹 계층을 수평적으로 확장하는 방법, 상태 정보를 DB같은 지속성 저장소에 보관하고 필요할 때 가져옴
### 상태 아키텍처 (Stateful Architecture)
- 서버가 클라이언트의 상태를 저장하고, 이전 요청의 정보를 기억하여 처리함

### 무상태 아키텍처 (Stateless Architecture)
- 서버가 클라이언트의 상태를 저장하지 않고, 매 요청마다 독립적으로 처리함
- 장점 : 단순하고, 안정적이며 규모확장 간편함

## 7. 데이터 센터
> 여러개의 데이터 센터 중 하나에 심각한 장애가 발생시 모든 트래픽은 나머지 데이터 센터로 전송된다. 따라서 다중 데이터센터 아키텍처를 만들려면 몇 가지 기술적 난제를 해결해야 한다
### 해결 방법
- 트래픽 우회 : 가장 효율적으로 트래픽을 보내야 하기 때문에 지리적으로 가장 가까운 데이터센터로 트래픽을 보냄
- 데이터 동기화 : 여러개의 데이터 센터는 동기화 되어있어야 다른 센터가 마비됐을떄도 데이터에 접근가능함
- 텍스트와 배포 : 여러 위치에서 테스트 해봐야함, 자동화된 배포 도구는 모든 센터에 동일하게 설치되게 하는 것에 도움이 됨

## 8. 메세지 큐
> 메시지의 무손실을 보장하는, 비동기 통신을 지원하는 컴포넌트
- 메시지의 버퍼 역할을 하며, 비동기적으로 전송
### 장점
- 메세지 큐를 이용하면 서비스, 서버 간 결합이 느슨해져서, 규모 확장성이 보장되어야하는 애플리케이션을 구성하기 좋음
- 생산자는 소비자 프로세스가 다운되어 있어도 메시지 발행 가능
- 소비자는 생산자 서비스가 가용한 상태가 아니더라도 메시지 수신 가능

## 9. 로그, 메트릭 그리고 자동화
> 사업의 규모가 커질수록 로그, 메트릭, 자동화와 같은 도구가 필수적으로 필요
- 로그 : 에러 로그 모니터링은 시스템 오류와 문제를 쉽게 찾아낼 수 있음, 로그를 단일 서비스로 모아주는 도구 활용시 이점
- 메트릭 : 메트릭으로 유용한 정보 얻을 수 있음, 현재 상태 쉽게 파악
- 자동화 : 시스템이 커지면 생산성을 높이기 위해 자동화 도구 활용해야함, 빌드/테스트/배포 등의 절차 자동화할 수 있어 개발 생산성 크게 향상

## 10. 데이터베이스의 규모 확장
> 데이터의 양이 많아질수록 부하도 증가함 > 데이터베이스 증설
### 수직적 확장
> 기존 서버에 더 많은, 더 고성능의 자원을 증설
- 약점
  - 데이터베이스 서버 하드웨어는 한계가 있음, 적은양의 서버를 가지고 
    감당하기 힘들어지는 경우 많음
  - SPOF 위험 큼
  - 비용이 많이 들음
### 수평적 확장
> 더 많은 서버를 추가함으로써 성능 향상
- 유의할점
  - 데이터의 재 샤딩: 데이터를 여러 서버에 분배할 때 기존 데이터를 다시 나누는 작업이 필요함.
  - 유명인사 문제 : 일부 서버에 트래픽이 집중될 수 있어 부하가 불균형하게 발생함. 
  - 조인과 비정규화 : 서버 확장 시 데이터 간 관계를 처리하는 데 복잡도가 증가하고, 비정규화로 성능을 최적화해야 할 수 있음.
