# Notion의 PostgreSQL 데이터베이스 샤딩
> 원문 : [Database Sharding with PostgreSQL: A Case Study with Notion]( https://talent500.com/blog/notion-postgresql-database-sharding/)

---

## 1. 배경

### Notion의 성장과 DB 한계

Notion은 노트 앱에서 워크스페이스, 데이터베이스, 협업 툴로 확장되면서 **유저 수와 데이터 양이 폭발적으로 증가**했다.

- 초기: 단일 PostgreSQL 인스턴스에서 모든 데이터 처리.
- 문제 발생:
  - **쓰기 부하 폭증**: 워크스페이스 생성, 페이지 편집, 데이터베이스 행 추가 등 쓰기 작업 증가.
  - **읽기 쿼리 복잡도**: 조인·집계 쿼리가 느려짐.
  - **단일 포인트 오브 페일러(SPOF)**: 한 DB에 모든 데이터가 집중되어 장애 시 전체 서비스 중단 위험.
- **결과**: 수직 확장(CPU/RAM 추가)으로는 한계 도달 → **수평 확장(샤딩)** 도입 결정. 

## 왜 샤딩이 필요했나

| 문제점                  | 단일 DB의 한계                          | 샤딩의 해결책                          |
|-------------------------|-----------------------------------------|---------------------------------------|
| **트래픽 불균형**       | 일부 인기 워크스페이스가 전체 부하 80% 차지 | 데이터 분산으로 각 샤드 부하 균등화   |
| **조인 성능 저하**      | 대규모 테이블 간 조인 느림              | 샤드 내 데이터로 조인 최소화          |
| **장애 격리 부족**      | 한 DB 장애 = 전체 서비스 다운           | 샤드 독립 운영으로 부분 장애만 발생   |
| **확장성 한계**         | 하드웨어 업그레이드 비용·한계           | 샤드 추가로 무한 확장 가능            |

# 2. 샤딩이란?

> **샤딩(Sharding)**: 대규모 데이터를 여러 DB 인스턴스(샤드)로 나누어 저장·처리하는 수평 확장 기법.

Notion의 경우 **워크스페이스 ID를 샤딩 키**로 사용했다.

```
전체 데이터
├── Shard 0: workspace_id % 4 == 0 (워크스페이스 1,5,9...)
├── Shard 1: workspace_id % 4 == 1 (워크스페이스 2,6,10...)
├── Shard 2: workspace_id % 4 == 2 (워크스페이스 3,7,11...)
└── Shard 3: workspace_id % 4 == 3 (워크스페이스 4,8,12...)
```

## 샤딩 키 선택 기준

| 기준                  | Notion 적용 예시                              | 이유                                      |
|-----------------------|----------------------------------------------|------------------------------------------|
| **접근 패턴**         | 워크스페이스별 페이지·데이터베이스 조회      | 대부분 쿼리가 workspace_id로 필터링      |
| **데이터 분포 균등**  | 워크스페이스 ID 해시 모듈러 연산              | 인기 워크스페이스가 한 샤드에 몰리지 않음 |
| **성장 예측**         | 워크스페이스 수 비례 성장                    | 샤드 추가 시 데이터 재분배 용이          |

# 3. Notion의 샤딩 구현

## 1단계: 샤드 분리 및 라우팅

- **샤드 매니저(Shard Router)**: 애플리케이션 레이어에서 workspace_id를 받아 해당 샤드 DB 연결 정보 반환.
- **연결 풀**: 각 샤드별 풀을 미리 생성해 연결 오버헤드 최소화.
- **쿼리 라우팅 로직**:
  ```pseudocode
  shard_id = hash(workspace_id) % num_shards
  db_connection = shard_pools[shard_id]
  execute(query, db_connection)
  ```

## 2단계: 데이터 마이그레이션

**점진적 마이그레이션**으로 다운타임 없이 기존 데이터 분산:

```
기존 단일 DB
   ↓ (백그라운드 작업)
[데이터 복사] → Shard 0,1,2,3 생성
   ↓
[듀얼 라이트] → 단일 DB + 샤드 동시 쓰기 (1주일)
   ↓
[리드 스위치] → 읽기만 샤드에서 (쓰기는 여전히 듀얼)
   ↓
[쓰기 스위치] → 완전 샤드 전환
```

- **듀얼 라이트(Dual Write)**: 애플리케이션에서 단일 DB와 샤드 둘 다에 쓰기 → 데이터 동기화 보장.
- **모니터링**: 샤드 간 데이터 일치성 체크 후 전환.

## 3단계: 크로스 샤드 쿼리 처리

워크스페이스 간 협업(공유 페이지 등)으로 발생하는 **크로스 샤드 쿼리** 대응:

| 쿼리 유형             | 해결책                                      |
|-----------------------|--------------------------------------------|
| **워크스페이스 내**   | 샤드 내 단일 쿼리 (가장 빈번)              |
| **공유 페이지 조회**  | 페이지 소유 워크스페이스 샤드에서 조회     |
| **전체 통계**         | 애플리케이션 레이어에서 각 샤드 집계 후 합산 |
| **글로벌 검색**       | Elasticsearch 같은 별도 검색 엔진 사용     |

# 4. 핵심 기술 구성요소

## PostgreSQL Citus 확장 사용

Notion은 **Citus** (PostgreSQL의 분산 확장)를 도입해 샤딩을 간소화했다.

```
애플리케이션
    ↓
Coordinator Node (쿼리 라우팅)
    ↓
Worker Nodes (Shard 0,1,2,3...)
```

- **Coordinator**: 쿼리를 분석해 각 워커 노드로 분산 실행.
- **Worker**: 실제 데이터 저장·처리 샤드.
- **분산 테이블**: `CREATE TABLE pages (id, workspace_id, content);` → 자동 샤딩.

## 모니터링과 자동화

| 도구/기능                  | 역할                                              |
|----------------------------|--------------------------------------------------|
| **Prometheus + Grafana**   | 샤드별 CPU, I/O, 쿼리 지연 모니터링               |
| **자동 샤드 추가**         | 부하 임계치 초과 시 새 샤드 생성·데이터 재분배    |
| **Hot Shard 탐지**         | 특정 샤드 부하 과다 시 자동 재샤딩                |

# 5. 성과와 교훈

## 성과 지표

| 지표                  | 샤딩 전       | 샤딩 후          | 개선율     |
|-----------------------|---------------|------------------|------------|
| **읽기 지연 (p95)**   | 500ms         | 50ms             | 90% ↓      |
| **쓰기 처리량**       | 1,000 TPS     | 10,000 TPS       | 10배 ↑     |
| **장애 격리**         | 전체 서비스   | 샤드 단위        | 100% 격리  |
| **비용 효율**         | 고사양 단일   | 저사양 다수      | 40% ↓      |

## 도입 교훈

1. **샤딩 키는 신중히**: 워크스페이스 ID처럼 **접근 패턴과 성장 패턴**을 반영.
2. **점진적 도입**: 듀얼 라이트로 리스크 최소화.
3. **크로스 샤드 최소화**: 애플리케이션 로직으로 대부분 샤드 내 처리.
4. **모니터링 필수**: Hot Shard, 데이터 드리프트 조기 발견.
5. **Citus 같은 도구 활용**: PostgreSQL 네이티브 샤딩으로 운영 부담 ↓.

# 6. 검증 - 실제 트래픽 테스트

Notion은 샤딩 후 **블랙프라이데이급 트래픽 시뮬레이션**을 통해 검증했다.

- **Chaos Engineering**: 랜덤 샤드 다운 → 나머지 샤드 정상 처리 확인.
- **Hot Shard 시뮬**: 인기 워크스페이스 10배 트래픽 → 자동 재샤딩 작동 확인.
- 결과: **p99 지연 200ms 이내**, 서비스 가용성 99.99% 유지. 

이 접근으로 Notion은 단일 DB의 한계를 넘어 **수백만 워크스페이스**를 안정적으로 지원하며 성장 중이다.
