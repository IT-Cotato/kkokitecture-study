## 1. 규모

- 하루 85억 건 검색, 글자 하나 입력할 때마다 요청 → DAU 10억 명 기준 초당 수억 건의 자동완성 요청
- 응답 목표: **100ms 이내**. 연구에 따르면 100ms를 넘으면 사용자가 "느리다"고 체감하기 시작함
- 트라이에 저장된 고유 쿼리 수: 약 1억 개. 평균 20글자 기준 수십 GB → 전체가 메모리에 올라감. 디스크 접근은 없음

---

## 2. 랭킹 신호

자동완성 결과는 단순히 "많이 검색된 순서"가 아니다. 4가지 신호를 조합한다.

**빈도(frequency)**
- 얼마나 많이 검색됐는지. 단, raw count를 그대로 쓰면 "amazon" 같은 단어가 모든 prefix를 압도함
- log(frequency + 1)로 스케일을 압축해서 바이럴 쿼리가 결과를 독점하지 않도록 조정

**신선도(recency)**
- 오래된 검색보다 최근 검색에 가중치. 시간 감쇠 공식 `e^(-λ × age)` 적용
- λ=0.01 기준으로 24시간 전 검색은 79% 반영, 7일 전은 19%만 반영
- evergreen 쿼리("how to make pasta")와 트렌딩 쿼리("France vs Brazil score")의 신선도 처리 방식이 다름

**위치/언어**
- 같은 "fr"를 입력해도 한국에서는 "france", 미국에서는 "french toast"가 먼저 나올 수 있음
- 국가별/언어별 쿼리 로그를 별도로 집계. CDN 엣지 서버에 지역별 트라이를 따로 배포

**개인화**
- 로그인 사용자는 과거 30~90일 검색 기록이 반영됨
- 단, 개인 신호는 전체의 20~40%만 반영하고 나머지는 글로벌 데이터 기반
- 개인 비중이 너무 높으면 filter bubble 문제 발생 — 항상 똑같은 결과만 보여지는 현상
- 최종 랭킹 공식: `freq^0.5 × recency_decay × (1 + context_boost) × (1 + personal_boost)`
- frequency에 제곱근을 쓰는 이유: 인기 쿼리가 결과를 일방적으로 지배하는 걸 방지

## 3. 100ms를 어떻게 달성하나

**디바운싱(debouncing)**
- 글자 하나 입력할 때마다 요청을 보내면 "dinner" 6글자만 입력해도 6번 요청 → 실제론 마지막 결과만 필요
- 150~200ms 동안 추가 입력이 없을 때만 요청을 전송. 타이핑 중에는 요청을 취소하고 다시 대기
- 이것만으로 서버 요청 수가 60~80% 감소

**브라우저 캐싱**
- 구글은 자동완성 응답에 `Cache-Control: private, max-age=3600` 헤더를 붙여서 반환
- 같은 prefix를 다시 입력하면 서버에 요청하지 않고 브라우저 캐시에서 즉시 반환

**CDN 엣지 서버**
- 전 세계에 분산된 CDN 엣지 노드에 트라이의 스냅샷을 배포
- 사용자와 물리적으로 가까운 서버에서 응답하므로 네트워크 레이턴시 자체가 줄어듦
- 핫한 prefix("go", "am", "yo")는 CDN 레벨에서 캐싱 → 중앙 서버까지 요청이 도달하지 않음

**전체가 메모리에 상주**
- 트라이 전체(수십 GB)를 RAM에 올려두고 디스크 접근을 아예 없앰
- 각 노드에 top-k를 미리 저장해뒀기 때문에 요청이 들어오면 포인터 탐색만으로 O(p) 만에 반환 (p = prefix 길이)

## 4. 실시간 트렌딩 처리

배치 방식으로는 실시간 트렌드에 대응 불가능. 라이브 경기 중에 "Fr"를 입력하면 "France vs Brazil score"가 즉시 나와야 하는데, 주 1회 갱신으론 이게 안 된다.

**두 파이프라인을 병렬로 운영**

- **배치 파이프라인**: 수 시간~하루 단위로 전체 쿼리 로그를 집계해 트라이를 갱신. evergreen 쿼리 담당
- **스트리밍 파이프라인**: 실시간으로 검색 이벤트를 집계. 특정 쿼리가 단시간에 급증하면 트렌딩 풀에 별도 관리
- 트렌딩 쿼리는 일반 랭킹 파이프라인을 우회해서 빠르게 결과에 반영

**스냅샷 + 델타 오버레이**

- 트라이 전체를 매번 다시 빌드하면 수 시간 소요 → 베이스 스냅샷(배치) 위에 최신 델타만 덮어씌우는 방식
- 서빙 서버는 베이스 트라이를 계속 유지하면서, 델타 업데이트가 오면 해당 노드만 교체

---

## 5. 오타 처리

사용자의 실제 입력은 항상 정확하지 않다. "dinne"→"dinner", "gogle"→"google" 같은 케이스를 처리해야 한다.

- **Levenshtein distance**: 두 문자열 사이의 편집 거리. "dinne"→"dinner"는 r 1개 추가로 distance=1
- 편집 거리 1~2 이내의 후보 쿼리를 트라이에서 생성해 정상 랭킹 파이프라인에 태움
- 트라이 탐색 시 허용 편집 횟수를 제한해서 탐색 비용 제어
- 오타 교정 결과도 캐싱해두기 때문에 동일한 오타를 다시 입력하면 즉시 반환

---

## 6. 트라이 샤딩

트라이가 단일 서버에 안 들어갈 때 prefix 기준으로 분산

- 단순 알파벳 분할("a-f" → 서버1, "g-m" → 서버2)은 트래픽 편차 때문에 불균형 발생
- 실제로는 과거 쿼리 로그를 분석해서 **트래픽 기준으로 샤드 경계를 결정**하는 샤드 맵 관리자 사용
- "go", "am" 같은 hot prefix는 전용 서버나 별도 캐싱 레이어 사용

---

## 7. 필터링과 정책

구글은 자동완성 결과에 올라오는 내용에 대한 정책을 별도로 운영한다.

- 혐오 표현, 폭력, 개인정보 침해 등에 해당하는 쿼리는 자동완성에서 제거
- 사용자가 부적절한 예측을 신고하면 구글이 검토 후 제거 가능
- 선거 기간에는 특정 후보에 대한 예측이 영향을 줄 수 있어 별도 정책 적용
- 이 필터 레이어는 트라이 앞단에 독립적으로 구성되어 있어 트라이 구조 자체를 건드리지 않음
