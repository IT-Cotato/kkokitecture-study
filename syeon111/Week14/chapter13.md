# 13장. 검색어 자동완성 시스템

> 검색어 자동완성(autocomplete)이란 검색창에 단어를 입력할 때 가능한 검색어를 자동으로 완성해 주는 기능. 구글, 아마존 등에서 흔하게 볼 수 있음
>

---

## 1단계 문제 이해 및 설계 범위 확정

**요구사항 정리**

- 빠른 응답 속도: 100ms 이내
- 연관성: 자동완성 검색어는 검색어와 연관된 것이어야 함
- 정렬: 사용 빈도(popularity)에 따라 정렬
- 규모: DAU 천만 명
- 영어만 지원
- 대소문자 구별 없음
- 매일 천만 명, 1인당 10회 검색, 평균 20글자 → 일일 2억 건의 문자 입력

---

## 2단계 개략적인 설계안 제시 및 동의 구하기

시스템을 두 파트로 나눈다.

- **데이터 수집 서비스(data gathering service)**: 사용자가 입력한 질의를 실시간으로 수집하고 집계
- **질의 서비스(query service)**: 주어진 질의에 대해 인기 검색어 5개를 정렬해서 반환

#### 데이터 수집 서비스

- 빈도 테이블(frequency table): `(query, frequency)` 형태로 저장
- 사용자가 질의를 입력하면 frequency +1 업데이트

#### 질의 서비스

- 빈도 테이블에서 입력 prefix로 시작하는 항목을 frequency 내림차순으로 5개 반환
- 데이터가 많아지면 이 쿼리가 너무 느려짐 → 트라이(trie) 자료구조 필요

---

## 3단계 상세 설계

#### 트라이(Trie) 자료구조

- 문자열을 저장하고 탐색하는 데 특화된 트리 자료구조
- 루트 노드는 빈 문자열, 각 노드는 글자 하나를 저장하고 26개의 자식 노드(알파벳)를 가질 수 있음
- 각 노드에 해당 prefix로 시작하는 **가장 인기 있는 검색어 top k개를 캐시**해두는 방식으로 최적화
    - 예: "tr" 노드에 ["tree":10, "try":29, "true":35, "trump":35] 를 미리 저장
    - 질의할 때 해당 노드의 캐시를 바로 반환 → O(1)

**트라이 연산의 시간 복잡도**

- 캐시 없는 경우: prefix 길이 p, 노드 내 총 자식 수 n, 결과 k개 → O(p) + O(n) + O(n log k)
- 캐시 있는 경우: O(1) — 해당 prefix 노드에 top k가 이미 저장되어 있으므로

#### 데이터 수집 서비스 상세 설계

실시간으로 업데이트하는 방식은 대규모 트래픽에서 불가능 → 주기적인 배치 방식 채택

1. **로그 파일**: 검색 창에 입력된 모든 질의를 로그에 기록
2. **로그 취합 서버**: 로그를 일정 주기(예: 주 1회)로 취합, `(query, time, frequency)` 형태로 취합된 데이터 생성
3. **작업 서버**: 취합된 데이터로 트라이를 만들거나 업데이트 → 트라이 DB에 저장
4. **트라이 캐시**: 트라이 DB의 스냅샷을 주기적으로 캐시에 올려 읽기 성능 확보
5. **트라이 DB**: 영속적인 저장소. 문서 저장소(MongoDB 등) 또는 키-값 저장소 사용 가능

#### 질의 서비스 상세 설계

1. 검색 질의가 로드밸런서로 전달됨
2. API 서버가 트라이 캐시에서 데이터를 가져와 응답
3. 트라이 캐시에 없으면 트라이 DB에서 가져와 캐시를 채움

**최적화**

- **AJAX 요청**: 페이지 새로고침 없이 자동완성 결과를 보여줄 수 있음
- **브라우저 캐싱**: 자동완성 결과를 브라우저 캐시에 저장. 구글은 `Cache-Control: private, max-age=3600` 헤더를 사용
- **데이터 샘플링**: 모든 질의를 로깅하지 않고 N개 중 1개만 로깅 (전체 트래픽의 일부만 수집해도 충분히 정확한 빈도 집계 가능)

#### 트라이 연산

**트라이 생성**

- 작업 서버가 로그 취합 결과를 사용해 주 1회 생성
- 트라이 생성은 API 서버에서 하지 않음

**트라이 업데이트**

- 방법 1: 주 1회 새로운 트라이를 만들어 기존 것을 교체
- 방법 2: 개별 트라이 노드를 직접 업데이트 (느리지만 실시간성 필요할 때 사용)

**트라이 삭제**

- 부적절한 검색어(폭력, 혐오 등)를 제거하기 위해 API 서버와 트라이 캐시 사이에 **필터 레이어** 추가
- 트라이 DB에서 해당 검색어를 비동기적으로 삭제

#### 저장소 규모 확장

트라이가 하나의 서버에 다 담기지 않을 경우 **샤딩** 필요

- 방법 1 — 첫 글자 기준: a-m은 서버 1, n-z는 서버 2 등 (but 글자마다 편차가 크기 때문에 불균형 발생)
- 방법 2 — 과거 질의 데이터 분석 기반: 실제 트래픽 분포에 따라 샤드 경계를 결정하는 샤드 맵 관리자(shard map manager) 사용

## 4단계 마무리

추가로 논의하면 좋을 것

- **다국어 지원**: 트라이에 유니코드 문자 사용
- **국가별 인기 검색어 차별화**: 국가별로 다른 트라이를 사용하고 CDN을 활용해 응답 속도 향상
- **실시간 트렌드 검색어 반영**: 현재 설계는 주 1회 갱신이라 실시간 트렌드에 대응하기 어려움. 샤딩된 트라이를 사용하거나 최근 검색어에 더 높은 가중치를 부여하는 랭킹 모델 도입 필요
