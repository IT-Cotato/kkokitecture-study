# WeChat 백엔드 시스템의 발전 과정

## 1. 초기 백엔드 설계 (2011)

WeChat은 단 2개월의 개발 기간 만에 출시되었지만, 이후 수억 명의 사용자를 수용할 수 있었던 이유는 초기 아키텍처를 단순하면서도 확장 가능하게 설계했기 때문이다.

### 핵심 설계

- **Store-and-Forward 메시지 모델**
    - 메시지는 서버에 임시 저장한 뒤 수신자에게 전달
    - Push 알림으로 사용자에게 새로운 메시지를 알리고, 실제 메시지는 클라이언트가 서버에서 가져오는(Pull) 방식 사용
- **통합 데이터 동기화 프로토콜**
    - 계정, 연락처, 메시지를 하나의 프로토콜로 관리
    - 전체 데이터를 매번 동기화하는 대신 버전 정보만 관리하여 변경된 데이터만 전송
- **3계층 백엔드 구조**

```
Client
   ↓
Access Layer
   ↓
Logic Layer
   ↓
Storage Layer
```

### 효과

- 불필요한 네트워크 사용량 감소
- 클라이언트 구현 단순화
- 이후 새로운 기능 추가가 쉬운 구조 마련

---

# 2. 기능 증가와 비동기 처리

서비스가 성장하면서 그룹채팅, 친구추천, QQ 연동 등 다양한 기능이 추가되었다.

이 과정에서 모든 작업을 실시간으로 처리하면 응답속도가 느려지고 서버 부하가 증가하는 문제가 발생하였다.

### 해결 방법 : 비동기 Queue 도입

메시지를 Queue에 저장한 후 Worker가 백그라운드에서 처리하도록 변경하였다.

```
사용자
   ↓
Queue
   ↓
Worker
   ↓
메시지 전달
```

### 장점

- 사용자 응답속도 향상
- 서버 부하 분산
- 대량의 작업도 안정적으로 처리 가능

---

# 3. 그룹채팅 메시지 저장 방식

WeChat은 Fan-out on Write 방식을 선택하였다.

### Fan-out on Write

메시지를 보낼 때 각 사용자의 Inbox에 미리 저장하는 방식이다.

```
A가 그룹에 전송

↓

B Inbox 저장
C Inbox 저장
D Inbox 저장
```

### 선택 이유

- 초기 그룹 최대 인원이 10명으로 적었음
- 저장 공간보다 읽기 속도가 중요
- 기존 1:1 채팅과 동일한 동기화 방식을 사용할 수 있음

### 결과

사용자는 자신의 Inbox만 확인하면 되므로 메시지 조회 속도가 매우 빨라졌다.

---

# 4. 사용자 폭증과 서비스 분리

2011년 이후 사용자가 100만 명 → 1,000만 명 → 1억 명으로 급격히 증가하면서 기존 구조의 한계가 나타났다.

초기에는 모든 API가 하나의 **mmweb** 서버에서 동작하였다.

### 문제점

- 기능 하나 수정해도 전체 재배포 필요
- 일부 기능 오류가 전체 서비스 장애로 이어짐
- 개발 속도 저하

### 해결 방법 : Logicsvr 도입

기능별로 독립적인 서비스로 분리하였다.

예)

- Login Server
- Message Server
- Friend Server
- Timeline Server

### 효과

- 독립적인 개발 및 배포 가능
- 장애가 다른 서비스로 전파되지 않음
- 현재의 Microservice 구조와 유사한 형태

---

# 5. 운영 모니터링 시스템 구축

초기에는 서비스 상태를 이메일과 로그를 통해 확인하였다.

이 방식은 장애를 빠르게 발견하기 어려웠다.

### 개선

ID 기반 Monitoring 시스템 구축

각 기능은 자신의 상태를 Counter 형태로 기록한다.

```
Message Success

Login Success

Friend Request

Image Upload
```

↓

Monitoring Server가 실시간 수집

↓

그래프 및 알람 생성

### 효과

- 장애 조기 발견
- 신규 기능도 쉽게 모니터링 가능
- 운영 효율 향상

---

# 6. 저장 시스템(KVSvr) 개발

초기 저장 구조: MySQL Master-Slave 구조

### 문제점

- Master 장애 시 쓰기 불가능
- 읽기 성능 확장 한계
- 단일 장애점(SPOF)

### 해결

자체 분산 저장 시스템 **KVSvr** 개발

### 특징

- Strong Consistency 강한 일관성
- 수평 확장
- 장애 복구
- 내장 캐시
- 높은 읽기/쓰기 성능

### 결과

대부분의 핵심 데이터 저장 시스템이 KVSvr로 전환되었다.

---

# 7. WeChat 플랫폼으로 확장

WeChat은 단순한 메신저에서 다양한 서비스를 제공하는 플랫폼으로 발전하였다.

추가된 서비스

- Official Account
- WeChat Pay
- Hardware Platform

### 의미

메신저 하나가 아니라 다양한 서비스가 하나의 백엔드 위에서 동작하는 플랫폼 구조로 발전하였다.

---

# 8. 해외 데이터센터 구축

글로벌 사용자 증가로 인해 해외 사용자의 지연시간이 증가하였다.

### 해결

홍콩, 캐나다 등에 해외 데이터센터 구축

### 데이터 관리 방식

사용자마다 Home Data Center를 지정하였다.

예)

한국 사용자의 Master

↓

Hong Kong

↓

상하이로 비동기 복제

### 효과

- 빠른 응답속도
- 글로벌 서비스 제공
- 데이터 일관성 유지

---

# 9. 대규모 장애와 재해복구

2013년 광케이블 절단 사고로 약 2,000대 서버가 동시에 장애를 일으켰다.

서비스는 약 5시간 동안 중단되었다.

### 해결

3개 데이터센터가 동시에 서비스하는 Active-Active-Active 구조를 구축하였다.

```
Data Center A

Data Center B

Data Center C

(동시에 서비스)
```

### 장점

- 하나의 데이터센터 장애에도 서비스 지속
- 자동 장애 전환
- 높은 가용성 확보

---

# 10. 성능 최적화 및 장애 방지

### Coroutine 도입

기존 Thread 기반 RPC를 Coroutine으로 개선하였다.

### 결과

동시 처리량

수백 개 → 수천 개


### FastReject

서비스 과부하 시 처리하지 못하는 요청은 즉시 거절하도록 설계하였다.

### 효과

- 장애 전파 방지
- 시스템 안정성 향상
- 전체 서비스 다운 예방

# WeChat 백엔드 발전 과정 요약

| 단계 | 핵심 기술 | 목적 |
| --- | --- | --- |
| 초기 설계 | Store-and-Forward | 안정적인 메시지 전달 |
| 데이터 동기화 | Version 기반 Sync | 트래픽 감소 |
| 기능 확장 | Queue | 비동기 처리 |
| 그룹채팅 | Fan-out on Write | 빠른 메시지 조회 |
| 서비스 분리 | Logicsvr | 독립 배포 및 확장 |
| 운영 | Monitoring | 장애 조기 탐지 |
| 저장소 | KVSvr | 고성능 분산 저장 |
| 글로벌 | Multi Data Center | 해외 서비스 지원 |
| 장애 대응 | 3-DC Active 구조 | 고가용성 |
| 성능 | Coroutine, FastReject | 처리량 증가 및 장애 방지 |

---

### 핵심 교훈

WeChat은 처음부터 거대한 시스템을 설계한 것이 아니라, **사용자 증가와 새로운 요구사항에 맞춰 아키텍처를 단계적으로 발전시켰다.** 이러한 점진적인 진화 덕분에 오늘날 수억 명의 사용자를 안정적으로 지원하는 글로벌 메신저 서비스로 성장할 수 있었다.
