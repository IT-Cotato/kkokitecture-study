### 2. 응답지연(latency) 값

㎱ = nanosecond (나노초)

㎲ = microsecond (마이크로초)

㎳ = millisecond (밀리초)

1 ㎱= $10^-9$초

1 ㎲ = $10^-6$초 = 1,000㎱

1 ㎳ = $10^-3$초 = 1,000㎲ = 1,000,000㎱

- 메모리는 빠르지만 디스크는 아직 느리다
- 디스크 탐색은 가능한 피해라
- 단순한 압축 알고리즘은 빠르다
- 데이터를 인터넷으로 전송하기 전에 가능하면 압축해라
- 데이터센터는 보통 여러 region에 분산되어 있고, 센터들 간 데이터를 주고 받는 데는 시간이 걸린다

### Google Pro Tip: Use Back-of-the-envelope-calculations to Choose the Best Design

개략적인 규모 추정: **사고실험**과 일반적인 **성능 수치**를 조합해서 설계가 요구사항을 충족할지 감을 잡기 위해 만드는 예측치이다.

시스템을 직접 구축해보지 않고도 이 계산을 통해 대안 시스템들의 성능을 추정해내는 능력은 매우 중요하다

#### 알아야 할 수치들

- **L1 캐시 참조**: 0.5㎱
    - Level 1캐시. CPU 코어 내부에 직접 통합돼서 당장 사용할 데이터를 저장.
- **분기 예측** Branch Prediction: 5㎱
    - 파이프라이닝의 효율을 유지하기 위해, CPU가 프로그램의 다음 실행 경로를 미리 추측하여 멈춤 없이 명령어를 처리하는 기술
    - 분기 예측 실패 프로세스: 실패 감지 → 파이프라인 비우기 → 올바른 경로 탐색 → 다시 채우
- **L2 캐시 참조:** 7㎱
    - Level 2캐시. L1보다 느리지만 RAM보다는 훨씬 빠르다. 코어 내부 또는 바로 옆에 위치해서 L1에서 찾지 못한 데이터를 대비해 저장한다.
- **뮤텍스(Mutex) 잠금/해제:** 100㎱
    - **Mut**ual **Ex**clustion 상호 배제의 약자
    - 여러 개의 스레드가 하나의 공유 자원에 동시에 접근하면 데이터가 꼬일 수 있음. 공유 자원에 대한 동시 접근을 막기 위해 한 번에 하나의 스레드(또는 프로세스)만 임계 구역(Critical Section)에 진입하도록 보장하는 동기화 기법
        - **Lock (Acquire):** 임계 구역 진입 전 락을 요청함. 락이 사용 중이면 대기 큐에서 잠들고, 비어있으면 락을 획득하고 진입함.
        - **Unlock (Release):** 임계 구역 사용을 마치고 락을 반환함. 대기 중인 다른 스레드에게 진입 기회를 준다.
    - CPU의 기본 연산이 0.3㎱ 내외인 것에 비하면 100㎱는 300배이상 느린 작업이다.
        - **메모리 동기화**: 뮤텍스를 다룰 때는 캐시에 있는 데이터가 아니라 실제 RAM 수준에서 데이터의 일관성을 맞춰야함. 이 과정에서 지연이 발생
        - **원자적 연산**: 여러 스레드가 동시에 열쇠를 갖지 못하도록 하드웨어 수준에서 한 번에 하나만 처리하는 특수한 명령어를 사용. 이 명령어가 일반 명령어보다 비쌈
        - **커널 모드 전환**: 뮤텍스가 복잡해지면 유저 모드에서 커널 모드로 시스템 콜을 호출해야함. 이때 발생하는 오버헤드가 지연을 발생
- **메인 메모리 참조:** 100㎱
    - CPU 캐시에 데이터가 없을 때(Cache Miss), 메모리 컨트롤러를 통해 RAM에서 데이터를 가져오는 과정
    - CPU 연산보다 300배 이상 느리므로, 데이터의 지역성을 높여 캐시 적중률을 관리하는 것이 성능의 핵심임
- **Zippy로 1KB 압축:** 10,000㎱ (10㎲)
    - 구글에서 개발한 빠른 압축 알고리즘 Snappy를 사용하여 데이터를 압축하는 시간
    - 네트워크 전송 속도보다 압축 속도가 빠르다면, 데이터를 압축해서 보내는 것이 전체 응답 시간을 줄이는 데 유리하다
- **1Gbps 네트워크로 2KB 전송:** 20,000㎱ (20㎲)
    - 데이터를 패킷 단위로 쪼개 NIC를 통해 송신하는 과정
    - 데이터가 커질수록 이 시간은 선형적으로 증가함. 작은 데이터를 여러 번 보내는 것보다 큰 덩어리로 묶어 보내는 것이 효율적
- **메모리에서 1MB 순차 읽기:** 250,000㎱ (250㎲)
    - RAM에서 연속된 메모리 주소에 있는 1MB 데이터를 쭉 읽어오는 과정
- **동일 데이터센터 내 왕복(RTT):** 500,000㎱ (0.5㎳)
    - 같은 데이터센터 안에 있는 서버 A가 서버 B로 요청을 보내고 응답을 받는 시간
- **디스크 탐색(Disk seek):** 10,000,000㎱ (10㎳)
    - HDD의 물리적인 헤드가 데이터가 저장된 트랙으로 이동하는 시간
    - 물리적 장치가 직접 움직여야 하므로 매우 긴 시간임
    - 디스크 탐색이 발생하면 성능이 급격히 저하됨
- **네트워크에서 1MB 순차 읽기:** 10,000,000㎱ (10㎳)
    - 1Gbps 네트워크 대역폭을 통해 1MB의 데이터를 서버로부터 받아오는 시
- **디스크에서 1MB 순차 읽기:** 30,000,000㎱ (30㎳)
- **패킷 왕복 (캘리포니아 ↔ 네덜란드 ↔ 캘리포니아):** 150,000,000㎱ (150㎳)
    - 대륙 간 해저 광케이블을 통해 빛의 속도로 데이터가 오가는 시간
    - 아무리 하이테크 기술을 써도 지구 반대편까지 가는 물리적 거리는 극복하기 어려움
    - CDN이나 Multi-Region이 필수임

#### 주목할 점

- 각 옵션의 성능 차이가 얼마나 큰지 확인할 것
- 데이터센터는 물리적으로 멀리 떨어져 있으므로 무언가를 전송하는 데 시간이 오래 걸림
- 메모리는 빠르고 디스크는 느림
- 압축 알고리즘을 사용하면 네트워크 대역폭을 많이 아낄 수 있음
- Writes는 reads보다 40배 더 비쌈
- 전역 공유 데이터는 비용이 많이 든다. 이건 분산 시스템의 근본적 한계이다.
- 공유되었고 쓰기가 빈번한 객체의 Lock 경쟁은 트랙잭션을 직렬화하고 느리게 만들어 성능을 떨어뜨린다
    - Scaling writes 쓰기 확장성을 고려해 설계하라
    - Write contention 쓰기 경합을 낮추도록 최적화하라
    - 설계를 넓게 만들어라 → 가능한 한 병렬로 처리해라

### 3. 가용성에 관계된 수치들

**고가용성 high availability **

: 시스템이 오랜 시간 동안 지속적으로 중단 없이 운영될 수 있는 능력을 지칭

- 고가용성은 퍼센트로 값을 표현한다.
    - 100%는 시스템이 단 한 번도 중단된 적 없었음을 의미함
    - 대부분의 서비스는 99%에서 100% 사이의 값을 가짐

**SLA(Service Level Agreement)**

: 서비스 사업자가 보편적으로 사용하는 용어로, 서비스 사업자와 고객 사이 맺어진 합의를 의미함

- 이 합의에는 서비스 사업자가 제공하는 서비스의 가용시간(uptime)이 공식적으로 기술되어 있음
- 가용시간은 관습적으로 숫자 9를 사용해 표시하며, 9가 많을수록 좋은 것

### EX) 트위터 QPS와 저장소 요구량 추정

[가정]

- 월간 능동 사용자(MAU):  3억
- 매일 트위터 사용: 50%
- 사용자당 매일 평균 트윗 수: 2건
- 미디어를 포함 비율: 전체 트윗의 약 10%
- 데이터 5년간 보관

[추정]

**QPS(Query Per Second) 추정치**

- 일간 능동 사용자(DAU) = 3억 x 50% = 1.5억
    - 전체 트윗 수 = 1.5억 x 2트윗 = 3억 건
    - 미디어 트윗 수 = 3억 건 x 10% =3,000만 건
- QPS = 3억 / 24시간 / 3600초 = 약 3500건
    - 일 → 시간 (3억/24시간 → 시간 당 트윗 수: 12,500,000건)
    - 시간 → 분 (12,500,000건/60분 →분당 트윗 수: 약 208,333)
    - 분 → 초 (208,333건/60초 → 초당 트윗 수: 약 3,472)
- 최대 QPS(Peek QPS) = 2 X QPS = 약 7000건
    - 여기서 곱하는 2는 경험적인 안전 계수에 가까움

**미디어 저장을 위한 저장소 요구량**

- 평균 트윗 크기
    - tweet_id에 64바이트
    - 텍스트에 140바이트
    - 미디어 개당 용량: 1MB
- 미디어 저장소 요구량: 3,000만 건 x 1MB = 30TB/일
- 5년간 미디어를 보관하기 위한 저장소 요구량: 30TB X 365일 X 5년= 약 55PB

**올바른 절차 > 결과**

가장 중요한 것은 문제 해결 능력 

- 근사치 활용 계산 (99987/9.1 → 100,000/10)
- 가정은 나중에 볼 수 있게 적어둘 것
- 단위 붙이기. 나중에 헷갈림
- 많이 출제되는 개략적 규모 추정 문제는 QPS, 최대 QPS, 저장소 요구량, 캐시 요구량, 서버 수 등을 추정하는 것

## 3장. 시스템 설계 면접 공략법

“널리 알려진 제품 X를 설계해 보라”

→ 설계 과정에서 내린 결정들에 대한 방어 능력을 보여라

→ 면접관의 피드백을 건설적인 방식으로 처리할 자질이 있음을 보여라

면접관이 보는 것

- 협력에 적합한 사람인지
- 압박이 심한 상황도 잘 헤쳐 나갈 자질이 있는지
- 모호한 문제를 건설적으로 해결할 능력이 있는지

[Red Flag]

- 설계의 순수성에 집착한 나머지 타협적 결정을 도외시하고 **오버 엔지니어링**
- 완고함, 편협함

### 효과적 면접을 위한 4단계 접근법

#### 1단계: 문제 이해 및 설계 범위 확정

시스템 설계 면접을 볼 때는 생각 없이 바로 답을 내서 좋은 점수를 받기 어렵다 

- 요구사항을 완전히 이해하지 않고 답을 내놓는 행위 → red flag
- 면접은 퀴즈쇼가 아님. 정답 따위 없음.

**올바른 질문을 하는 것**

**적절한 가정을 하는 것**

**시스템 구축에 필요한 정보를 모으는 것**

⇒ 요구사항 정확히 이해하기

- 구체적으로 어떤 기능들을 만들어야 하나?
- 제품 사용자 수는 얼마나 되나?
- 회사의 규모는 얼마나 빨리 커지리라 예상하나?
    - 3달, 6달, 1년 뒤의 규모는 얼마가 되리라 예상하나?
- 회사가 주로 사용하는 기술 스택은 무엇인가?
- 설계를 단순화하기 위해 활용할 수 있는 기존 서비스로는 어떤 것들이 있는가?

**<예제: 뉴스 피드 시스템을 설계하라>**

요구사항을 정확히 이해하기 위한 질문

- 모바일 앱과 웹 앱 가운데 어느 쪽을 지원해야 하나요? 아니면 둘 다?
- 가장 중요한 기능은 무엇인가요?
- 이 뉴스 피드의 정렬 기준은 무엇인가요?
    - 정렬 기준이 있냐고 묻는 이유는, 피드에 올라갈 포스트마다 다른 가중치가 부여되어야 하는지 알고 싶어서 입니다
- 한 사용자는 최대 몇 명의 사용자와 친구를 맺을 수 있나요?
- 사이트로 오는 트래픽 규모는 어느 정도 인가요?
- 피드에 이미지나 비디오도 올라올 수 있나요?

→ 이렇게 모호함을 없애는 것이 중요하다

#### 2단계: 개략적인 설계안 제시 및 동의 구하기

개략적인 설계안을 제시하고 면접관의 동의를 얻어라 

- 설계안에 대한 최초 청사진을 제시하고 의견을 구해라
    - 팀원에게 하듯 대해라.
- 화이트보드나 종이에 핵심 컴포넌트를 포함하는 다이어그램을 그려라
    - 클라이언트(모바일/웹), API, 웹 서버, 데이터 저장소, 캐시, CDN, 메시지 큐 등이 포함
- 이 최초 설계안이 시스템 규모에 관계된 제약사항들을 만족하는지 개략적으로 계산해라.
- 가능하다면 시스템의 구체적 사용 사례도 몇가지 살펴보자
    - 미처 고려하지 못한 edge case를 발견하는 데 도움이 될 것

**<예제: 뉴스 피드 시스템을 설계하라>**

두 가지 처리 flow로 나눠서 생각

- 피드 발행 (feed publishing): 사용자가 포스트를 올리면 관련 데이터가 캐시/데이터베이스에 기록되고, 해당 사용자의 친구 뉴스 피드에 뜨게 됨
- 피드 생성 (feed building): 사용자 친구들의 포스트를 정렬 기준에 맞게 정렬하여 만듦

그림 3-1, 3-2 → 피드 생성 flow 개략적인 그림

#### 3단계: 상세 설계

현재 달성한 상태

- 시스템 전반적으로 달성해야 할 목표와 기능 범위
- 전체 설계의 개략적 청사진
- 해당 청사진에 대한 면접관의 의견 청취
- 상세 설계에서 집중해야 할 영역들 확인

해야할 것

- 면접관과 설계 대상 컴포넌트 사이의 우선순위를 정해라
- 면접관은 특정 시스템 컴포넌트들의 세부사항을 깊이 있게 설명하는 것을 바람
    - 단축 URL 생성기 설계 → 그 해시 함수의 설계를 구체적으로 어떻게 설명하는지
    - 채팅 시스템 설계 → 어떻게 latency를 줄이고 사용자의 온/오프라인 상태를 표시할 것인지
- 불필요한 세부사항에 시간 쓰지 말것
    - 페이스북 뉴스 피드의 순위를 매기는 데 사용되는 EdgeRank 알고리즘같은 불필요한 세부사항

**<예제: 뉴스 피드 시스템을 설계하라>**

1. 피드 발행 
2. 뉴스 피드 가져오기

이 둘에 대한 상세 설계를 보여라

#### 4단계: 마무리

- 면접관이 시스템 병목구간, 혹은 좀 더 개선 가능한 지점을 찾아내라 주문한다면 설계가 완벽하다/개선할 부분이 없다 등의 대답은 금지
- 만든 설계를 다시 한번 요약해주는 것도 좋음 (특히 여러 해결책을 제시한 경우)
- 오류가 발생하면 무슨 일이 생기는지 따져보기
- 운영 이슈 논의도 좋음
    - 메트릭 수집 방안, 모니터링 방법, 로그나 시스템 배포 등
- 규모 확장 요구에 어떻게 대처할 것인지 설명하는 것도 좋음
- 필요하지만 다루지 못한 세부적 개선사항들 제안도 가능

**결론**

[해야할 것]

- 질문을 통해 확인하기
- 문제의 요구사항 이해하기
- 정답은 없다는 것을 명심하기
- 면접관이 본인의 사고 흐름을 이해할 수 있도록 하기 (면접관과 소통하기)
- 가능하다면 여러 해법을 함께 제시하기
- 개략적 설계에 면접관이 동의하면, 각 컴포넌트의 세부사항을 설명하기 시작하기. 가장 중요한 컴포넌트부터
- 면접관의 아이디어를 이끌어내기

[하지 말아야 할 것]

- 전형적인 면접 문제들에도 대비하지 않고 가지 말기
- 요구사항이나 가정을 분명히 하지 않고 설계 제시하지 말기
- 처음부터 특정 컴포넌트의 세부사항을 너무 깊이 설명하지 말기 (개략적으로 설계를 마친 뒤 세부사항으로 넘어가기)
- 진행 중 막히면, 힌트 청하기를 주저하지 말 것
- 소통을 주저하지 말 것
- 설계안을 내놓는 순간 면접이 끝났다고 생각하지 말기. 의견을 일찍, 자주 구하기

[시간 배분]

45분의 시간이 주어진다 가정하고, 각 단계에 어느정도 시간을 쓰면 좋을지 

1단계 - 문제 이해 및 설계 범위 확정: 3분~10분

2단계 - 개략적 설계안 제시 및 동의 구하기: 10분~15분

3단계 - 상세 설계: 10분~25분

4단계 - 마무리: 3분~5분
