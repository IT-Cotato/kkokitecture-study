# 확장성 Scalability

### 1. 웹 호스팅 서비스 선택 시 고려사항

- **접근성**
    - 특정 IP 대역이나 서비스가 차단될 수 있으므로 다양한 네트워크 환경에서의 접근성을 확인해야함
- **보안**
    - SFTP(Secure File Transfer Protocol)를 지원하는지 확인
    - SFTP는 FTP와 달리 모든 트래픽을 암호화하여 username과 password 등 민감한 정보가 노출 되는 것을 방지함
- **무제한의 함정**
    - 무제한이라는 문구는 실제로는 여러 사용자가 하나의 서버를 공유하는 가상 호스팅일 가능성이 높음. 이는 자원 경쟁을 유발하며 많은 자원을 필요로 하는 경우 적합하지 않음

---
### 2. 가상 사설 서버 VPS

공유 호스팅과 달리 사용자가 독립적인 시스템을 임대하는 방식

- 물리적인 서버를 하이퍼바이저를 통해 여러 개의 가상 머신으로 분할
    - 하이버바이저 Hypervisor: 하드웨어를 여러개의 VM으로 나눠주는 소프트웨어
- 다른 고객과 자원을 공유하지만, 각 VM은 독립적인 운영체제와 자원을 할당받음
- VPS 제공 업체는 가상 머신에 접근 가능 → 완벽한 프라이버시는 보장되지 않음
- 더 높은 수준의 프라이버시는 자체 서버 운영이 필요

[VPS의 비용/특징]

- VPS는 공유 호스팅보다 일반적으로 더 높은 비용임
- AWS의 EC2 같은 서비스는 필요에 따라 가상 머신을 유연하게 확장하고 축소할 수 있음

---
### 3. 수직적 확장 Vertical Scaling

1) 수직적 확장 개념

- 기존 서버의 성능 자체를 향상 시키는 방식
- CPU, RAM, 디스크 공간 등 하드웨어 자체를 업그레이드해서 문제 해결

2) 한계

- 단일 머신으로 업그레이드할 수 있는 성능에는 물리적, 기술적 한계가 존재함
- 최신 기술로도 필요한 모든 자원을 확보하기 어려울 수 있음

3) 현대 서버의 다중 코어 및 병렬 처리

- 최신 서버는 여러 개의 CPU와 코어를 탑재해 동시에 여러 작업을 처리할 수 있음
- 쿼드 코어 머신은 4가지 작업을 동시에 수행 → 과거 단일 코어 머신보다 훨씬 효율적
- 서버는 여러 프로세스나 스레드를 생성해서 더 많은 요청을 병렬로 처리하는 것처럼 보이게 함

4) 하드웨어 ↔ 소프트웨어

- 하드웨어 성능이 향상되었지만, 소프트웨어의 비대함으로 인해 이런 자원을 완전히 활용하지 못하는 경우가 많음

---
### 4. 하드 드라이브 종류와 성능

- **Parallel ATA (IDE)**: 과거에 사용되었던 방식, 현재는 구형 컴퓨터에서만 볼 수 있음
- **SATA**: 현재 데스크톱/노트북에서 주로 사용
- **SAS (Serial Attached SCSI)**: 서버나 고성능 데스크톱에 사용, SATA보다 훨씬 빠름

→ SAS 드라이브는 더 높은 성능을 제공하지만, 가격이 더 비싸다

→ 데이터베이스는 디스크 쓰기 작업이 빈번하므로, SAS 드라이브를 사용하면 데이터 읽기/쓰기 속도를 크게 향상시킬 수 있음

---
### 5. 수평적 확장 Horizontal Scaling

: 단일 고성능 머신에 의존하는 대신, 여러 대의 저렴한 머신을 사용해서 시스템을 확장

- 시스템 성능 한계에 도달하는 것을 방지하고 비용 효율성을 높인다
- 데이터 센터는 여러 서버를 사용하여 복잡한 네트워크 토폴로지를 구축하고, 이를 통해 수평적 확장을 구현함

---
### 6. 로드밸런싱

1) 로드밸런싱의 필요성

- 여러 대의 웹 서버를 운영할 때, 들어오는 HTTP 요청을 각 서버로 분산시켜야함
- 단일 서버의 과부하를 방지하고 전체 시스템의 가용성을 높임

2) 로드밸런서 역할 

- 클라이언트와 여러 백엔드 서버 사이에 위치하여 트래픽을 분산하는 역할
- 클라이언트 요청은 로드밸런서로 전달, 로드 밸런서는 이를 적절한 백엔드 서버로 라우팅
- 백엔드 서버는 로드 밸런서의 IP 주소만 알면 돼서 자체적으로 공개 IP 주소가 필요하지 않음 → 프라이버시 강화 가능

3) 로드 밸런싱 구현 방식

- **서버 부하 기반 분산**: 각 서버의 CPU 사용량 등을 확인하여 가장 부하가 적은 서버로 요청을 보냄
    - 서버 간 통신이 필요해서 구현이 다소 복잡할 수 있음
- **DNS 기반 라운드 로빈**: DNS 서버가 요청 시마다 순차적으로 다른 서버의 IP 주소를 반환
    - 구현이 간단하고 기존 DNS 지식만으로도 가능
    - 서버 부하를 고려하지 않아 특정 서버에 부하가 집중될 수 있음
    - DNS 캐싱으로 클라이언트가 동일한 서버에 계속 연결될 수 있음 → 부하 분산 효과 떨어짐
- **로드밸런서 기반 분산**: DNS는 로드 밸런서의 IP 주소만 반환하고, 로드 밸런서가 실제 서버로 트래픽 분산 시키는 방식
    - 캐싱 문제 해결, 서버 부하 고려 → 정교한 분산 가능

### 7. 세션 관리

사용자의 로그인 상태, 장바구니 정보 등 → 세션을 통해 관리

- 여러 서버로 요청이 분산될 때, 각 서버가 서로 다른 세션 정보를 가지면 안됨
- 세션 정보가 특정 서버의 파일시스템에 저장될 경우, 해당 서버로 요청이 가지 않으면 세션 유실됨

<문제 해결 방안>

- **서비스 분리 & 전용 서버 활용**: PHP, 이미지, 동영상 등 서비스를 기능별로 분리하고 각 서비스에 전용 서버를 할당
    - 특정 서버가 다운되면 해당 서비스 전체가 중단되는 단점 존재
    - 단일 서비스 서버도 트래픽 증가 시 병목 현상 발생 간으
- **공유 스토리지 활용**: 모든 서버가 접근할 수 있는 외부 파일 서버에 세션 데이터를 저장
    - 공유 스토리지 서버 자체가 SPOF가 될 수 있음
    - 복제 Replication 사용 → 공유 스토리지의 SPOF 문제를 해결하기 위해, 데이터를 여러 곳에 복제하여 저장
- **RAID**: 여러 개의 하드 드라이브를 묶어 성능 향상/데이터 안정성 높이는 기술
    - RAID 0, RAID 1, RAID 10, RAID 5, RAID 6 등 여러 종류가 있음
    - RAID는 단일 서버 내에서의 디스크 장애에 대한 복원력을 높여주지만, 서버 자체의 전원 공급 장치, RAM, 메인보드 등의 고장은 여전히 발생 가능
    

[공유 스토리지 기술]

- Fibre Channel (FC): 고속, 고가용성 공유 스토리지 기술
- iSCSI: IP 네트워크를 사용하여 공유 스토리지를 제공하는 기술
- MySQL: 데이터베이스 자체를 공유 스토리지로 활용하여 세션 정보 저장 가능
- NFS (Network File System): 네트워크를 통해 파일 시스템을 공유하는 프로토콜

### 8. 로드 밸런서 구현/종류

1. 소프트웨어 기반 로드 밸런서
- **Amazon Elastic Load Balancer(ELB)**: AWS에서 제공하는 클라우드 기반 로드 밸런싱 서비스
- **HAProxy**: 무료 오픈 소스 로드 밸런서 소프트웨어 → 다양한 부하 분산 알고리즘 지원
- **Linux Virtual Server (LVS)**: 리눅스 환경에서 사용할 수 있는 무료 로드 밸런싱 솔루션

2. 하드웨어 기반 로드 밸런서
- Barracuda, Cisco, Citrix, F5 등 다양한 벤더에서 고성능 하드웨어 로드밸런서를 ㅔㅈ공함
- 매우 고가 → 주로 대규모 엔터프라이즈 환경에서 사용됨

3. 소프트웨어 로드 밸런서의 장점
- 하드웨어 기반보다 훨씬 저렴하게 구축할 수 있음
- HAProxy와 같은 무료 솔루션을 활용하면 비용 부담 없이 고가용성 시스템 구축 가능

### 9. 쿠키를 활용한 세션 관리

1. 쿠키를 이용한 세션 유지
- 사용자의 브라우저에 쿠키를 저장하여, 사용자가 특정 서버에 다시 접속할 때 해당 서버로 요청을 보내도록 유도
- 로드밸런서가 사용자의 세션 정보를 직접 관리하지 않아도 Sticky Session을 구현할 수 있게됨

2. 쿠키 기반 세션 관리의 단점
- 쿠키 만료: 쿠키는 설정된 시간이 지나면 만료되므로 장기적인 세션 유지가 어려울 수 있다
- 서버 IP 주소 노출: 쿠키에 서버 IP주소를 직접 저장하면, IP 주소 변경 시 문제가 발생하거나 서버 구조가 노출될 수 있다
- 보안 문제: 사용자가 쿠키를 위변조하여 다른 서버에 접근하려 할 수 있다

3. 개선된 쿠키 활용 방식
- 로드밸런서가 임의의 큰 난수를 생성하여 쿠키에 저장하고, 이 난수와 서버를 매핑하는 테이블을 관리한다
- 이를 통해 사용자의 브라우저에 민감한 정보를 노출하지 않고도 특정 서버로 요청을 라우팅할 수 있다

### 쿠키와 세션의 차이 

HTTP 프로토콜 → Stateless 프로토콜

- 커넥션을 끊는 순간 클라이언트와 서버의 통신이 끝남
- 처음 통신에서 데이터를 주고 받았다 해도, 다음 통신에서 이전 데이터를 유지하지 않음
- 그러나 실제로는 데이터 유지가 필요한 경우가 많음

정보가 유지되지 않으면 매번 페이지를 이동할 때마다 로그인을 다시하거나, 장바구니에서 상품이 사라지는 등의 일이 발생함

→ Stateful 경우를 대처하기 위해 쿠키와 세션을 사용하는 것

크게 두 방식의 차이는 **상태 정보의 저장 위치**이다.

- **쿠키** = 클라이언트(로컬PC)에 저장
- **세션** = 서버에 저장

#### 쿠키 Cookie

사이트 서버에서 사용자의 컴퓨터에 저장하는 작은 기록 정보 파일

HTTP에서 클라이언트의 상태 정보를 클라이언트 PC에 저장했다가 필요시 정보를 참조하거나 재사용

[특징]

- 이름, 값, 만료일, 경로 정보로 구성
- 클라이언트에 총 300개의 쿠키를 저장할 수 있음
- 하나의 도메인 당 20개의 쿠키 가짐
- 하나의 쿠키는 4KB까지 저장 가능

[동작 순서]

1. 사용자가 웹사이트 접근 (클라이언트가 페이지 요청)
2. 웹 서버는 쿠키 생성
3. 생성한 쿠키에 정보를 담아 클라이언트에게 돌려줌
4. 넘겨받은 쿠키는 로컬 PC에 저장됐다가 다시 서버에 요청할 때 요청과 함께 쿠키를 전송함
5. 동일 사이트 재방문 시 클라이언트의 PC에 해당 쿠키가 있는 경우, 요청 페이지와 함께 쿠키를 전송함

#### 세션 Session

일정 시간 동안 같은 브라우저로부터 들어오는 일련의 요구를 하나의 상태로 보고, 그 상태를 유지시키는 기술

→ 방문자가 웹 서버에 접속해 있는 상태를 하나의 단위로 보고 그것을 세션이라 함 

[특징]

- 웹 서버에 웹 컨테이너의 상태를 유지하기 위한 정보를 저장
- 브라우저를 닫거나, 서버에서 세션을 삭제했을 때만 삭제가 되므로 쿠키보다 비교적 보안이 좋음
- 저장 데이터에 제한 없음
- 각 클라이언트에 고유 Session ID를 부여 → Session ID로 클라이언트를 구분해 각 요구에 맞는 서비스 제공

[동작 순서]

1. 클라이언트가 페이지에 요청
2. 서버는 접근한 클라이언트의 Request-Header 필드인 Cookie를 확인하여 ,클라이언트가 해당 Session-id를 보냈는지 확인
3. Session-id 존재 x → 서버가 Session-id를 생성해 클라이언트에게 넘겨줌
4. 클라이언트는 서버로부터 받은 Session-id를 쿠키에 저장
5. 클라이언트는 서버에 요청시 이 쿠키의 Session-id 값을 같이 서버에 전달
6. 서버는 전달받은 Session-id로 session에 있는 클라이언트 정보를 가지고 요청을 처리 후 응답함

→ 결국 세션도 쿠키를 사용하는 것임

- 세션 방식이 보안이 더 좋음
    - 세션 → 쿠키를 이용해 Session-id만 저장 / 쿠키 → 로컬에 저장되기 때문에 변질, 스니핑 우려 존재
- 쿠키 방식이 속도 면에서 더 우수
    - 쿠키 → 쿠키에 정보 존재 / 세션 → 서버에 정보 존재
- 쿠키는 서버의 자원을 전혀 사용하지 않고, 세션은 서버의 자원을 사용함

#### JWT (JSON Web Token) 방식

: 인증에 필요한 정보들을 담은 Token을 암호화하여 클라이언트가 직접 들고 있게 하는 방식

**[특징]**

- **자가 수용:** 토큰 자체에 사용자 정보와 권한 정보가 포함되어 있어, 서버가 별도의 저장소를 조회할 필요가 없음
- **확장성(Scalability):** 서버가 세션 정보를 저장하지 않으므로, 서버가 여러 대인 **수평적 확장** 환경에서 별도의 세션 공유 설정 없이도 인증이 가능함
- **서명 기반:** 헤더(Header)와 페이로드(Payload)를 서버의 비밀키로 서명하여, 위변조 여부를 확인함

**[동작 순서]**

1. 클라이언트가 로그인 요청
2. 서버는 사용자 정보를 확인하고, 비밀키를 통해 암호화된 **JWT 토큰**을 생성하여 클라이언트에게 응답
3. 클라이언트는 전달받은 JWT를 로컬 스토리지나 **쿠키**에 저장
4. 이후 요청 시, HTTP 헤더에 JWT를 담아 보냄
5. 서버는 토큰의 서명을 검증하여 유효하다면 별도의 조회 없이 즉시 요청을 처리하고 응답

- **보안성:** **세션 > JWT > 쿠키**
    - 세션은 실제 정보가 서버에 있어 가장 안전하지만, JWT는 토큰 탈취 시 서버에서 강제로 로그아웃시키기가 어렵다는 단점이 있음
- **확장성:** **JWT > 쿠키 > 세션**
    - 서버를 여러 대 띄우는 현대 아키텍처에서는 서버 간 상태 공유가 필요 없는 JWT가 압도적으로 유리함
- **자원 사용:** 세션은 사용자가 늘어날수록 서버 메모리 부하가 커지지만, JWT는 서버 자원을 거의 사용하지 않고 CPU 연산만 사용함

### 10. PHP 성능 향상 기법

제한된 서버 자원으로 어떻게 더 많은 접속자를 동시에 처리할까?

- PHP와 같은 인터프리터 언어는 C++과 같은 컴파일 언어에 비해 상대적으로 실행 속도가 느리다
    - PHP 가속기: 매번 코드를 해석하는 낭비를 줄이기 위해, 미리 컴파일된 결과물인 오프코드(Opcode)를 메모리에 캐싱.

해결책: **정적캐싱** 

- 자주 바뀌지 않는 페이지는 PHP가 매번 실행되지 않도록 아예 정적 HTML파일로 저장해버리거나, Memcached를 이용해 DB 조회 결과를 메모리에 올려두는 방식
- PHP 엔진이 일을 덜 하게 만들수록 서버 한 대가 감당할 수 있는 사용자가 늘어난다

서버 한 대를 키우는 것보다 여러 대의 서버를 두는 것이 비용 효율적이다

→ PHP 성능을 최적화하면, 똑같은 저사양 서버 10대라도 최적화 전보다 훨씬 많은 트래픽을 처리할 수 있다. 즉, 인프라 비용을 아끼기 위한 수단

**확장성 측면**에서 볼 때, PHP 성능 향상은 소프트웨어 효율을 극대화하여 하드웨어 증설 비용을 최소화하고, 시스템 전체의 처리 용량을 늘리는 방법

### 13. 고가용성 아키텍처 구축

**1. 다계층 아키텍처 Multi-tiered Architecture**
- 네트워크, 로드밸런서, 웹 서버, DB 등으로 구성된 복잡한 시스템 구조
- 단일 서버 환경에서 벗어나 복잡한 구성 요소들을 연결해야함

**2. 로드 밸런서와 DB 계층의 이중화**
- 단일 로드 밸런서나 단일 master DB는 SPOF가 되므로, 이중화가 필수임
- 로드밸런서는 액티브-액티브 또는 액티브-패시브 모드로 구성하여 고가용성을 확보

**3. 이중화**
- **가용 영역 Availability Zone**: 동일한 지역 내에서도 서로 다른 전력 공급원, 네트워크 등을 공유하지 않는 독립적인 데이터 센터를 의미
- **지역 Region**: 여러 AZ를 포함하는 더 큰 지리적 단위
- **글로벌 로드 밸런싱:** DNS를 활용하여 사용자의 위치에 따라 가장 가까운 데이터 센터의 로드 밸런서로 트래픽을 분산시킴
- **네트워크 이중화**: 각 서버와 로드 밸런서는 2개 이상의 네트워크 인터페이스를 가지고 여러 스위치에 연결 되어야 함
    - 클라우드 방식으로는 Multi-AZ
- **데이터 센터 이중화:** 건물 전체의 장애에 대비하여 여러 지역에 데이터 센터를 분산 구축함
