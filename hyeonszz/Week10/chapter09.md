## 9장. 웹 크롤러 설계

#### 목적

새로 올라오거나 갱신된 콘텐츠를 찾아내는 것

#### 사례

- **검색 엔진 인덱싱 (Search Engine Indexing)**
    - 구글, 네이버와 같은 검색 엔진의 가장 기초가 되는 단계
    - 크롤러가 전 세계 웹사이트를 돌아다니며 텍스트, 이미지, 비디오 데이터를 수집함
    - 수집된 데이터는 인덱스라는 거대한 목록에 저장함 → 사용자가 검색어를 입력하면 실시간으로 웹을 찾는 것이 아니라 미리 정리된 인덱스에서 가장 관련성 높은 결과를 보여줌
- **웹 아카이빙 (Web Archiving)**
    - 나중에 사용할 목적으로 장기보관하기 위해 웹에서 정보를 모으는 절차
    - 시간이 지나면 사라지거나 변경될 수 있는 웹 페이지의 데이터를 보존하기 위해 스냅샷을 찍는 것
- **웹 마이닝 (Web Mining)**
    - 단순 수집을 넘어, 수집한 방대한 데이터 속에서 유의미한 패턴이나 지식을 추출하는 과정
    - 웹 마이닝을 통해 인터넷에서 유용한 지식을 도출해낼 수 있음
- **웹 모니터링 (Web Monitoring)**
    - 특정 웹사이트의 변화를 실시간 혹은 주기적으로 감시
    - 동일한 페이지를 방문해 이전 버전과 비교
    - 가격 비교 / 저작권 침해 감시 / 뉴스 업데이트 등에 사용 가능

---
### 1. 문제 이해 및 설계 범위 확정

---

#### 기본 알고리즘

1. URL 집합이 입력으로 주어지면, 해당 URL들이 가리키는 모든 웹 페이지를 다운로드한다
2. 다운받은 웹 페이지에서 URL들을 추출한다
3. 추출된 URL들을 다운로드할 URL 목록에 추가하고 위의 과정을 처음부터 반복한다

#### 좋은 웹 크롤러가 갖추어야 할 4가지 속성

- **규모 확장성 (Scalability)**
    - 웹은 수십억 개의 페이지가 존재하므로 데이터 양이 방대하다
    - 병렬성을 활용하면 보다 효과적으로 웹 크롤링이 가능하다
- **안정성 (Robustness)**
    - 비정상적인 웹 환경에서도 중단 없이 동작해야한다
    - 잘못된 HTML 코드, 아무 응답이 없는 서버, 장애, 악성 코드가 붙어 있는 링크 등 크롤링 함정을 스스로 감지하고 우회해야 한다
    - 시스템 장애로 크롤러가 중단되었을 때, 처음부터 다시 시작하는 것이 아니라 마지막 작업 지점부터 재개할 수 있는 체크포인트 기능이 필요하다
- **예절 (Politeness)**
    - 크롤러는 수집 대상 웹 사이트에 짧은 시간 동안 너무 많은 요청을 보내서는 안된다
    - DoS 공격과 유사하게 대상 서버가 마비될 수 있다
- **확장성 (Extensibility)**
    - 새로운 유형의 콘텐츠가 등장했을 때 전체 구조를 바꾸지 않고도 대응할 수 있어야 한다
    - 여기서의 확장성은 규모가 아니라 기능의 유연성을 의미한다

#### 개략적 규모 추정

- 매달 10억 개의 웹 페이지를 다운로드한다
- QPS=10억/30일/24시간/3600초=약 400페이지/초
- 최대 QPS=2xQPS=800
- 웹 페이지의 크기 평균은 500K라고 가정
- 10억 페이지 x 500k = 500TB/월
- 1개월치 데이터를 보관하는 데는 500TB, 5년간 보관한다고 가정하면 500TB x 12개월 x 5년 = 30PB

### 2. 개략적 설계안 제시 및 동의 구하기

---

**시작 URL 집합**

- 웹 크롤러가 크롤링을 시작하는 출발점
- 도메인 이름이 붙은 모든 페이지의 URL을 시작 URL로 사용 하는 예시도 존재
- 나라별 / 주제별 등으로 나눠서 사용할 수도 있음 → 정답은 없음

**미수집 URL 저장소**

- 대부분 크롤링 상태를 **다운로드할 URL**과 **다운로드된 URL** 이 2가지로 나눠서 관리함
- 다운로드할 URL을 저장 관리하는 컴포넌트를 미수집 URL 저장소라고 함
- FIFO queue 라고 생각하면 됨

**HTML 다운로더**

- 인터넷에서 웹 페이지를 다운로드하는 컴포넌트
- 다운로드할 페이지의 URL은 미수집 URL 저장소가 제공함

**도메인 이름 변환기**

- 웹 페이지를 다운받으려면 URL을 IP 주소로 변환하는 절차가 필요함
- HTML 다운로더는 도메인 이름 변환기를 사용하여 URL에 대응되는 IP 주소를 알아낸다

**콘텐츠 파서**

- 웹 페이지를 다운로드하면 파싱과 검증 절차를 거쳐야 한다
- 크롤링 서버 안에 콘텐츠 파서를 구현하면 크롤링 과정이 느려지게 될 수 있으므로, 독립된 컴포넌트로 만든다
    - 크롤러: 주로 네트워크 I/O를 사용함. 웹사이트에 요청을 보내고 응답 기다리는 시간이 대부분임
    - 파서: 수집한 HTML에서 텍스트 뽑고, 정규표현식 돌리고, 중복 검사하는 CPU 집약적 작업임

**중복 콘텐츠인가?**

- 웹 페이지의 해시 값 비교를 통해 중복 콘텐츠인지 확인

**콘텐츠 저장소**

- HTML 문서를 보관하는 시스템
- 저장소 구현에 쓰일 기술을 고를 때는 저장할 데이터의 유형/크기/저장소 접근 빈도/데이터의 유효 기간 등을 고려해야함

**URL 추출기**

- HTML 페이지를 파싱하여 링크들을 골라내는 역할을 함

**URL 필터**

- 특정한 콘텐츠 타입이나 파일 확장자를 갖는 URL, 접속 시 오류가 발생하는 URL, 접근 제외 목록에 포함된 URL 등을 크롤링 대상에서 배제하는 역할

**이미 방문한 URL?**

- 이미 방문한 적 있는 URL인지 추적하면 같은 URL을 여러 번 처리하는 일을 방지할 수 있음
- 추적 자료구조는 블룸 필터나 해시 테이블 사용

**URL 저장소**

- 이미 방문한 URL을 보관하는 저장소

#### 웹 크롤러 작업 흐름

미수집 URL 저장소에서 추출한 URL을 IP 주소로 변환하여 HTML 문서를 다운로드한 뒤, 독립된 파서를 통해 콘텐츠를 검증하고 링크를 추출합니다. 이후 추출된 URL 중 중복이나 필터링 대상을 제외한 새 URL만 저장소에 추가하며, 수집된 데이터는 콘텐츠 저장소에 보관하는 과정을 반복합니다.

### 3. 상세 설계

---

#### 1. DFS vs BFS

웹은 방향이 있는 그래프와 같다. 페이지는 노드이고, 하이퍼링크는 엣지라고 보면 된다.

크롤링 프로세스는 이 directed graph를 edge를 따라 탐색하는 과정이다

- DFS: 그래프 크기가 클 경우 어느 정도로 깊숙이 가게 될지 가늠이 어려움
- BFS: FIFO 큐를 사용하는 알고리즘으로, 큐의 한쪽으로는 탐색할 URL을 넣고 다른 한쪽으로는 꺼내기만 함
    - (-) 한 페이지에서 나오는 링크의 상당수는 같은 서버로 되돌아 간다
    - (-) URL간 우선순위를 두지 않는다

#### 2. 미수집 URL 저장소

미수집 URL 저장소를 활용하면 BFS방식의 문제를 해결할 수 있다

**Politeness**

- 동일 웹 사이트에 대해서는 한 번에 한 페이지만 요청
- 같은 웹 사이트의 페이지를 다운 받는 태스크는 시간차를 두고 실행

**우선순위**

- 유용성에 따라 URL의 우선순위를 나눌 때는 페이지랭크, 트래픽 양, 갱신 빈도 등 다양한 척도를 사용
- 순위결정장치는 URL 우선순위를 정하는 컴포넌트

| **큐 라우터** | 같은 호스트에 속한 URL은 언제나 같은 큐로 가도록 보장하는 역할 |
| --- | --- |
| **매핑 테이블** | 호스트 이름과 큐 사이의 관계르 보관하는 테이블 |
| **FIFO 큐** | 같은 호스트에 속한 URL은 언제나 같은 큐에 보관된다 |
| **큐 선택기** | 큐들을 순회하며 URL을 꺼내고, 나온 URL을 다운로드하도록 지정된 작업 스레드에 전달 |
| **작업 스레드** | 전달된 URL을 다운로드하는 작업 수행 |

#### 3. HTML 다운로더

HTML 다운로더는 단순히 페이지를 받는 것 이상으로, 거대한 웹을 효율적으로 훑기 위한 최적화가 필수적이다.

- **분산 크롤링:** 크롤링 작업을 여러 서버에 나누어 병렬로 처리한다. 각 서버는 여러 스레드를 돌려 다운로드 로직을 실행한다.
- **DNS 캐시:** DNS 조회는 동기적 작업이라 한 스레드가 조회 중이면 다른 스레드가 대기하게 된다. 조회된 IP를 캐싱하고 주기적으로 갱신해 이 병목을 줄인다.
- **지역성:** 크롤링 서버를 수집 대상 서버와 지리적으로 가까운 곳에 배치한다. 물리적 거리가 가까울수록 응답 속도는 빨라진다.
- **짧은 타임아웃:** 응답이 없거나 느린 서버에 무한정 대기할 수 없다. 최대 대기 시간을 짧게 설정하고, 초과 시 해당 페이지는 건너뛴다.

#### 4. 안정성 확보 전략

시스템이 중단 없이 돌아가기 위한 장치들이다.

- **안정 해시(Consistent Hashing):** 다운로더 서버들에 부하를 고르게 분산하고, 서버 추가/삭제 시 영향을 최소화한다.
- **체크포인트 저장:** 장애가 발생했을 때 처음부터 다시 시작하지 않도록, 크롤링 상태와 수집된 데이터를 지속적 저장장치에 주기적으로 기록한다.
- **예외 처리 및 데이터 검증:** 잘못된 HTML이나 예상치 못한 입력에도 시스템 전체가 무너지지 않게 방어 코드를 작성하고 데이터를 검사한다.

#### 5. 확장성 확보 전략

새로운 형태의 콘텐츠가 추가되어도 시스템 전체를 갈아엎지 않도록 설계해야 한다.

- **플러그인 구조:** 새로운 모듈을 쉽게 끼워 넣을 수 있는 구조를 취한다
- **예시:**
    - **PNG 다운로더:** 이미지 파일을 처리하는 전용 모듈
    - **웹 모니터:** 저작권 침해 등을 감시하기 위한 특수 목적 모듈

#### 6. 문제 있는 콘텐츠 감지 및 회피

- **중복 콘텐츠:** 웹 데이터의 약 30%는 중복이다. 해시나 체크섬을 사용하여 이미 수집한 데이터인지 빠르게 판별한다
- **거미 덫(Spider Trap):** 무한 루프에 빠지게 하는 URL 구조를 감지한다. URL 최대 길이를 제한하거나, 사람이 수작업으로 필터링 목록에 추가한다.
- **데이터 노이즈:** 광고, 스팸, 가치 없는 스크립트 등은 수집 대상에서 제외하여 저장 공간과 처리 효율을 높인다.

## 4. 마무리

웹 크롤러 설계의 핵심은 결국 **규모 확장성**과 **안정성**이다.

- **규모 확장성:** 수십억 개의 페이지를 처리하기 위해 병렬성과 분산 처리가 핵심이다.
- **예절(Politeness):** 대상 서버에 부하를 주지 않는 매너 있는 크롤링이 필수적이다.
- **확장성(Extensibility):** 웹의 변화에 유연하게 대응할 수 있는 모듈화된 설계가 중요하다.
