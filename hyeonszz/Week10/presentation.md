## 3. 크롤링 순서 결정 (Crawl Ordering Problem)

웹은 새로운 콘텐츠의 증가와 동적 페이지 등으로 인해 사실상 무한하므로, 제한된 리소스 내에서 수집 우선순위를 정하는 것이 필수적이다. 크롤러의 순서 결정은 다음 두 가지 지표를 목표로 한다.

- **커버리지 (Coverage):** 수집하려 하는 대상 페이지를 얼마나 많이 모았는가에 대한 비율
- **최신성 (Freshness):** 수집된 스냅샷이 실제 라이브 웹 페이지와 일치하는 정도(동기화 수준)

### 3.1 모델 

: 시스템의 복합한 물리적 아키텍처를 다 제외하고, 오직 URL의 수집 순서를 어떻게 제어할 것인가라는 알고리즘적 핵심 이론에만 집중하기 위해 단순화한 이론적 가설 체계

초당 다운로드 페이지 수를 뜻하는 크롤링 속도는 배치 크롤링에는 영향이 없으나, 점진적 크롤링의 재방문 스케줄링에서는 핵심 요소이다. 반복 다운로드를 제어하는 방식은 두 가지이다.

- **배치 크롤링 (Batch crawling):** 중복 방문 없이 1회성으로 수집 후 프로세스를 종료하며, 주기적으로 전체 과정을 처음부터 다시 시작하는 방식이다.
- **점진적 크롤링 (Incremental crawling):** 동일 페이지를 여러 번 재방문하며 개념적으로 영원히 중단 없이 지속되는 방식이다. 현대 상용 크롤러는 페이지별로 재방문 속도를 다르게 제어할 수 있는 점진적 크롤링을 주로 채택한다.

### 3.1.1 한계점 및 현실적 제약

이론적 모델과 달리 실제 대규모 크롤러 설계 시에는 다음과 같은 시스템적 제약이 따른다.

- **디스크 I/O 제약:** 대규모 미수집 URL 저장소는 디스크에 저장되므로 수시로 순서를 재정렬하기 어렵다. 실무에서는 우선순위별로 FIFO 큐 여러 개를 묶어서 관리한다.
- **예의(Politeness) 제약:** 동일 서버에 연달아 요청을 보내면 안 되므로, $n$개의 서버에 대해 독립적인 큐와 정책을 실행해야 한다.
- **분산 아키텍처:** 다수의 머신과 스레드가 병렬로 작동하므로, 전체 수집 리스트는 완전 정렬이 아닌 부분 순서 구조를 가진다.

### 3.2 웹의 특성

### 3.2.1 구적 특성 

- **나비넥타이(Bowtie) 구조:** 웹 그래프는 중심부 외에 서로 연결되지 않은 파편들이 많다. 따라서 단순히 깊이 탐색을 한다고 전체 웹을 모을 수 없으며, 시작 URL의 신중한 선정과 다중화가 필수적이다.
- **유사 중복/딥 웹:** 웹 페이지의 29%는 중복 또는 유사 중복이며, 딥 웹의 쿼리 인터페이스는 보통 루트 페이지 근처에 위치하므로 얕은 크롤링으로 쉽게 발견할 수 있다.

### 3.2.2 시간적 특성 

- **사이트 수준 진화:** 새 페이지 생성보다 링크 생성이 훨씬 빠르며, 1년 안에 기존 페이지와 링크의 80%가 소멸한다. 잘 고른 소수의 오래된 페이지만 모니터링해도 새 페이지의 90%를 발견할 수 있다.
- **페이지 수준 진화:** 일반적인 페이지 변경은 무작위적이고 독립적인 포아송 프로세스를 따른다. 변경 빈도는 시간이 지나도 안정적이므로 과거 이력으로 미래 주기를 예측할 수 있다.
- 극도로 자주 바뀌는 페이지는 중간 주기로 바뀌는 페이지보다 오히려 한 번에 바뀌는 콘텐츠의 누적 변경량이 적은 경향이 있다. 대부분의 변화는 사소한 영역에 국한된다.
- 페이지의 변화 유형은 정적, 적체, 스크롤로 분류된다. 웹 페이지는 일부 정적 영역을 포함하므로 캐시와의 분산에는 항상 상한선이 존재한다.

### 3.3 크롤링 순서 결정 정책의 분류

정책은 크게 (1) 커버리지 중심의 최초 다운로드 순서 제어, (2) 최신성 중심의 재다운로드 주기를 제어하는 정책, (3) 두 가지를 교차 배치하여 균형을 맞추는 종합 정책으로 분류된다. 결정 요인은 페이지의 중요도, 목적과의 연관성, 변경 빈도의 조합이다.

## 4. 배치 크롤링 순서 결정 (Batch Crawl Ordering)

배치 크롤링의 목표는 고정된 크롤링 속도 내에서 가치가 높은 페이지를 먼저 수집하여 시간 대비 가중 커버리지를 극대화하는 것이다.

### 4.1 포괄적 크롤링 (Comprehensive)

웹 전반의 고품질 콘텐츠 수집을 목표로 하며, 주로 페이지랭크 점수를 가중치로 삼는다.

- **너비 우선 탐색 (BFS):** 링크 발견 순서대로 수집하는 가장 단순한 방식이다. 고품질 Seed에서 시작하면 초기 단계에 우수한 가중 커버리지를 보장한다.
- **인링크 수 기준:** 수집된 그래프 내에서 인바운드 링크가 많은 순으로 수집한다. 계산은 쉽지만, 초반에 과도하게 탐욕적으로 작동하여 정작 중요한 페이지를 늦게 발견하는 병목이 발생할 수 있다. 
- **페이지랭크 예측치 기준:** 매번 재계산하는 것은 불가능하므로, 근사 계산하는 방식이 대규모 수집에 효과적이다.

### 4.1.1 검색 연관성 중심 목적

검색엔진에 데이터를 공급할 때는 절대적인 페이지랭크보다 실제 유저가 검색 결과에서 클릭할 확률이나 연관성 임팩트를 가중치로 삼아 미수집 URL의 우선순위를 동적 조정하는 것이 더 효과적이다.

### 4.2 스코프 크롤링

특정 주제, 지역, 언어 등 타겟 범위에 부합하는 콘텐츠만 집중 수집하여 정확도와 재현율을 높이는 방식이다.

- **주제별 크롤링:** 연관성 있는 페이지 주변에 또 다른 연관 페이지가 모여 있다는 특성을 활용한다. 링크 주변 텍스트와 URL 단어를 분석하거나 머신러닝 분류기를 통해 연관성을 예측한다.
- **탐색 활용의 균형:** 타겟 주제로 가기 위해 중간의 무관한 페이지를 거쳐야 하는 경우가 많으므로, 연관성 점수의 감쇠 모델을 쓰거나 고정된 $N$개의 페이지를 수집한 뒤에만 순서를 재정렬하는 메타 휴리스틱을 적용하여 지나친 탐욕성을 억제한다.

### 4.3 효율적인 대규모 구현

우선순위가 실시간으로 변하는 정책을 대규모 시스템에 적용하려면 디스크 기반의 지연 업데이트가 필수적이다. 글로벌 분석 점수를 즉각 반영하지 않고 가중치 로그를 사이드 파일에 기록한 뒤, 주기적인 정렬-병합을 통해 일괄 반영하는 방식으로 디스크 탐색 비용을 억제한다.

## 5. 점진적 크롤링 순서 결정 

점진적 크롤러는 새 URL 수집과 기존 URL의 재다운로드를 계속 교차 수행하므로, 한정된 자원 속에서 두 지표 간의 명확한 트레이드오프와 리소스 할당이 필요하다.

### 5.1 최신성 극대화 (Maximizing Freshness)

### 5.1.1 이진 최신성 모델 (Binary Freshness / Obsolescence)

캐시와 라이브 복사본이 완벽히 일치하면 1, 다르면 0으로 판단하는 모델이다. 변경 이벤트는 독립적인 포아송 프로세스로 가정한 상태에서 리소스를 할당한다.

- **균등 할당의 우위:** 페이지 변경 속도에 비례하여 방문 주기를 잡는 비례 할당 정책보다, 모든 페이지를 똑같은 주기로 방문하는 균등 할당 정책이 평균 이진 최신성을 더 높게 유지한다.
- **고급 부상자 분류(Triage) 효과:** 변경 속도가 크롤러의 방문 능력보다 압도적으로 빠른 페이지는 방문 직후 바로 stale(0) 상태가 되므로 자원 낭비이다. 최적의 리소스 할당을 위해서는 너무 자주 바뀌는 페이지는 과감히 포기하고, 중간 및 느리게 변경되는 페이지를 확실히 동기화하는 선택 집중 전략이 수학적으로 우월하다.

### 5.1.2 연속적 최신성 모델 

- **나이 기반:** 동기화가 깨진 방치 시간 자체를 불이익으로 계산한다. 시간이 지날수록 손실이 무한히 커지므로 어떤 페이지도 포기할 수 없으며, 변경 빈도가 높은 페이지일수록 재방문 빈도도 증가한다.
- **콘텐츠 기반 및 정보 수명:** 정보의 수명을 고려한다. 한 번 업데이트되면 오랫동안 캐시에 유지될 장기 수명 콘텐츠를 최우선으로 수집하고, 금방 덮어씌워질 휘발성 콘텐츠는 후순위로 미룬다.

### 5.2 업데이트 캡처

역사적 아카이빙이나 시계열 분석처럼 변경 이력을 유실 없이 수집하는 것이 목적인 경우이다. 이 시나리오는 최신성 극대화와 완벽히 정반대의 정책을 가진다. 데이터가 무기한 유실되기 전에 구출해야 하므로, 가장 자주 변경되는 페이지가 가장 높은 긴급성과 최우선순위를 가진다.

### 5.3 대규모 구현을 위한 테크닉

수억 개의 URL을 개별적으로 실시간 정렬하는 것은 디스크 I/O 병목으로 불가능하다. 이를 극대화하기 위해 **버킷 기반 스케줄링(Bucket-oriented NLP)** 아키텍처를 사용한다.

1. 페이지들을 개별 정렬하지 않고, 목표 재방문 빈도에 따라 여러 개의 디스크 기반 FIFO 큐로 그룹화한다.
2. 각 버킷은 head에서 꺼내 수집이 끝난 URL을 자동으로 tail에 다시 추가하는 순환 구조를 가진다.
3. 크롤러 머신은 가중 무작위 정책에 따라 각 버킷에서 URL을 pull하여 소모한다.
4. 버킷 단위로만 타겟 주기를 계산하므로 계산 복잡도가 극적으로 제어되며 시스템 확장성을 확보할 수 있다.
