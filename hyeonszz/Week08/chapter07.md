## **7장. 분산 시스템을 위한 유일 ID 생성기 설계**

### **1.**  문제 이해 및 설계 범위 확정

분산 환경에서 `auto_increment` 속성을 직접적으로 사용하지 못하는 이유는 

→ 단일 서버로는 초당 수만 건의 쓰기 요청을 감당하기 어렵고, 여러 DB 서버를 사용할 경우 Latency 및 데이터 동기화 문제가 발생하기 때문이다

설계방향정하기

- ID는 어떤 특성을 갖나요?
    - ID는 유일해야 하고, 정렬 가능해야 합니다.
- 새로운 레코드에 붙일 ID는 항상 1만큼 큰 값이어야 하나요?
    - ID의 값은 시간의 흐름에 따라 커질테지만 언제나 1씩 증가하는 것은 아닙니다. 확실한 것은, 아침에 만든 ID보다는 저녁에 만든 ID가 큰 값을 갖습니다
- ID는 숫자로만 구성되나요?
    - 그렇습니다
- 시스템 규모는 어느 정도입니까?
    - 초당 10,000 ID를 생성할 수 있어야 합니다

요구사항 확정

- ID는 유일해야 한다
- ID는 숫자로만 구성되어야 한다
- ID는 64비트로 표현될 수 있는 값이어야 한다
- ID는 발급 날짜에 따라 정렬 가능해야 한다
- 초당 10,000개의 ID를 만들 수 있어야 한다

### **2.** 개략적 설계안 제시 및 동의 구하기

| **방식** | **주요 장점 (+)** | **주요 단점 (-)** |
| --- | --- | --- |
| **다중 마스터 복제** | DB의 `auto_increment`를 K(서버 수)만큼 증가시켜 활용. 규모 확장이 어느 정도 가능함 | 여러 데이터 센터에 걸친 확장이 어렵고, 서버 추가/삭제 시 ID 연속성 및 유일성 관리가 복잡함 |
| **UUID** | 서버 간 조율 없이 독립적 생성 가능. 구현이 매우 단순하며 동기화 이슈 없음 | 128비트로 요구사항(64비트) 초과. 숫자가 아닌 문자가 포함되며 시간순 정렬이 불가능함 |
| **티켓 서버 (Ticket Server)** | `auto_increment` 전용 DB 서버를 중앙 집중형으로 운영. 구현이 쉽고 중소 규모에 적합 | SPOF 발생 위험. 이를 피하기 위해 서버를 늘리면 다시 동기화 문제가 발생함 |
| **Twitter Snowflake** | ID를 섹션별로 분할 관리. 64비트 내에서 유일성, 정렬, 확장성을 모두 잡은 독창적 방식 | 시계 동기화(Clock Synchronization) 처리가 필수적임 |

### **3. 상세 설계**

ID 구조를 비트 단위로 분할하여 관리하는 **Divide and Conquer** 방식을 사용한다

### **비트 할당 구조 (총 64비트)**

1. **Sign 비트 (1bit)**: 음수와 양수를 구분하는 데 사용할 수 있다
2. **Timestamp (41bits)**: 기원 시각(Epoch) 이후 경과된 밀리초(ms). 약 69년 동안 사용 가능. ID 정렬의 핵심
3. **데이터센터 ID (5bits)**: 최대 32개$(2^5)$ 데이터센터 지원
4. **서버 ID (5bits)**: 데이터센터당 32개, 총 1,024개 서버 지원
5. **일련번호 (12bits)**: 동일 밀리초 내에서 생성되는 ID를 구별. 각 서버는 1ms당 최대 4,096개($2^{12}$) ID 생성 가능

### **4.** 마무리

**A. 시계 동기화 (Clock Synchronization)**

설계상 서버 간 시간이 일치한다고 가정하지만, 실제 환경에서는 네트워크 지연 등으로 서버 간 시각 차이가 발생할 수 있다

- **해결책**: NTP(Network Time Protocol)를 사용하여 서버 간 시간을 동기화하며, 시계가 거꾸로 가는 경우 ID 생성을 잠시 중단하는 예외 처리가 필요하다

**B. 섹션 길이의 최적화**

애플리케이션의 특성에 따라 비트 길이를 조절할 수 있다

- **동시성이 낮고 수명이 긴 경우**: 일련번호 비트를 줄이고 타임스탬프 비트를 늘려 더 오랜 기간 서비스 가능하게 설계
- **동시성이 매우 높은 경우**: 일련번호 비트를 늘려 초당 처리량을 극대화

**C. 고가용성 (High Availability)**

ID 생성기는 시스템 전체의 핵심 컴포넌트이므로, 생성기 자체를 다중화하고 장애 발생 시 즉시 Failover 될 수 있는 구조를 갖춰야 한다.
