#  Netflix Tech Blog Active-Active

## 문제의 본질

Netflix: 대규모 서비스 + 빠른 배포  
        → 장애는 필연적으로 계속 발생
- 특히 위험한 장애:  리전 단위 장애 (서비스 전체 다운)

## 목표

-   99.99% 가용성 유지
-   어떤 장애가 나도 서비스 지속

## 배경

Netflix는 AWS 여러 리전에 서비스를 배포했다.
- 특정 AWS 구성요소나 리전 단위 장애가 전체 서비스 가용성에 영향을 줄 수 있었음
- 하나의 AWS 리전에서 발생하는 장애는 서비스 전체 중단으로 이어질 수 있어, 높은 수준의 가용성을 유지하기 위한 구조적 개선이 필요했음

→ 이를 해결하기 위해 Netflix는 먼저 **Isthmus 프로젝트**를 도입함


## Isthmus
>장애가 발생했을 때 트래픽을 다른 리전으로 넘겨 서비스 지속성을 확보하는 방식


### 역할
Isthmus는 장애 상황에서

1.  문제 생긴 리전을 감지
2.  사용자 트래픽을 **다른 정상 리전으로 우회(failover)** 함

### 한계

-   평소부터 여러 리전이 동시에 적극적으로 트래픽을 처리하는 구조는 아님
-   장애 대응은 가능하지만, 완전한 의미의 Active-Active와는 다름

### Isthmus vs Active-Active

| 단계 | 설명 |
|------|------|
| Isthmus | 장애 발생 시 다른 리전으로 전환 (Failover) |
| Active-Active | 평소부터 여러 리전이 동시에 트래픽 처리 |

### 주요 차이

- **Isthmus** = 소극적 대응 → 문제 발생 후 이동  
- **Active-Active** = 능동적 운영 → 항상 분산 처리

---
## 해결 전략: Active-Active

-   여러 AWS 리전에서 동시에 서비스 운영
-   (예: US-East + US-West)

기존(Isthmus):

-   장애 시 다른 리전으로 Failover

 Active-Active:

-   평소부터 **모든 리전이 동시에 처리**


---
## 1. 핵심 설계 원칙

-   **Isolation (격리)**  
    → 한 리전 장애 ≠ 다른 리전 영향 없음
    
-   **Redundancy (중복)**  
    → 동일 시스템을 여러 리전에 배치

## 2. Active-Active 구현 조건

1. 서비스는 Stateless
2. 데이터는 비동기 복제
3. 리전 간 호출 금지
4. 모든 리소스는 로컬 리전에서 접근

Active-Active의 핵심 목표는 리전 하나에 장애가 나도 다른 리전이 아무 문제 없이 계속 서비스를 제공하는 것이다. 따라서 각 리전은 **서로 의존하지 않고 독립적으로 동작**해야 한다.

**2-1. 서비스는 Stateless여야 한다**
-   어느 서버, 어느 리전으로 요청이 가도 처리할 수 있어야 함
-   서버에 상태를 저장하면 리전 전환 시 세션/로그인 정보가 끊길 수 있음
-   로드밸런싱과 장애 대응이 쉬워짐

**2-2. 데이터는 비동기 복제해야 한다**

Q. 동기 복제라면?
다른 리전 상태에 의존하게 만들어 지연과 장애 전파를 키움

Q. 비동기 복제라면?
로컬 리전에서 먼저 처리하고, 다른 리전에는 나중에 전파함

- 결과적으로 성능과 복원력을 함께 확보할 수 있음

**2-3. 리전 간 호출은 피해야 한다**
-   다른 리전 API 호출은 지연을 키움
-   네트워크 장애가 연쇄 장애로 이어질 수 있음
-   각 리전이 스스로 완결적으로 동작해야 함

**2-4. 리소스는 로컬 리전 중심으로 사용해야 한다**
-   DB, 캐시, 저장소 등을 자기 리전 안에서 우선 처리해야 함
-   다른 리전 리소스 의존성이 커질수록 복원력은 약해짐

---
## 3. 트래픽 흐름

-   평상시:
    -   Geo-DNS → 가까운 리전에 적절하게 라우팅 됨
    - 여러 리전이 동시에 트래픽을 처리
-   장애 시:
    -   트래픽 → 정상 리전으로 이동
    - 문제 있는 리전 비중을 줄이거나 제외하고 정상 리전이 더 많은 트래픽을 받아 처리함

Isthmus 처럼 장애가 나면 그때 리전을 옮기는 전환방식이 아닌, **원래 여러 리전이 돌아가고 있고 장애 시 트래픽 비율을 조정**하는 구조에 가깝다.

## 4. 핵심 기술 구성

### ① DNS (Denominator)

-   UltraDNS + Route53 조합
-   역할:
    -   지역 기반 라우팅
    -   빠른 트래픽 전환 (CNAME 변경)
      
**UltraDNS**
 	- 사용자 위치에 따라 어느 리전으로 보낼지 결정하는 지역 기반 라우팅을 담당
**Route53**
	- 실제 연결 대상을 관리하며 장애 시 빠르게 트래픽을 전환
   
#### Denominator
Netflix가 여러 DNS 제공자를 하나의 방식으로 관리하기 위해 만든 추상화 라이브러리
즉, UltraDNS와 Route 53을 각각 따로 다루지 않고 통합적으로 제어하게 해줌.
-   UltraDNS / Route 53 = 실제 DNS 제공자
-   Denominator = 그 위에서 DNS를 일관되게 제어하게 해주는 도구

### ② 트래픽 제어 (Zuul)
>넷플릭스 주울(Zuul)은 마이크로서비스 아키텍처(MSA)의 핵심 API 게이트웨이로 동적 라우팅, 보안, 모니터링, 회복성을 제공하는 오픈소스 기술이다

1. Zuul 처음 공개 글
https://netflixtechblog.com/announcing-zuul-edge-service-in-the-cloud-ab3af5be08ee

2. Zuul 2 아키텍처
https://netflixtechblog.com/zuul-2-the-netflix-journey-to-asynchronous-non-blocking-systems-45947377fb5c


#### < API Gateway 역할 >
Zuul은 트래픽을 적절한 서비스 클러스터로 안정적으로 라우팅할 수 있게 해주며, 이러한 라우팅을 런타임 중에도 변경할 수 있는 기능을 제공한다. 또한, 하위 서비스가 과부하에 걸리지 않도록 일부 트래픽을 차단(load shedding)할지 여부를 결정할 수 있는 기능도 제공한다.

#### 주요 역할

-   동적 라우팅
-   로드 셰딩(load shedding)
-   리전 정책 적용
-   장애 상황에서 유연한 요청 처리

Active-Active 구조와 운영상의 요구사항을 지원하기 위해 Zuul의 기존 기능을 넘어서는 몇가지 개선을 수행함. 

-   트래픽 제한 (load shedding)
	- 갑자기 요청이 너무 많이 몰리면, 정해둔 한도를 넘는 요청은 일부 차단해서 뒤쪽 서비스가 과부하되지 않도록 보호한다.
-   잘못된 리전 요청 처리
	- 사용자 요청이 원래 가야 할 지역이 아니라 다른 리전으로 들어오면, 이를 감지해서 올바른 리전으로 보내거나 클라이언트에게 다시 올바른 리전으로 접속하라고 안내한다.
-   failover 모드 지원
	- 특정 리전에 문제가 있거나 특별한 운영 상황이면, 다른 리전으로 요청을 넘기지 않고 그 리전이 직접 처리하게 만든다.

### ③ 데이터 계층 (Cassandra + EvCache)
> Cassandra는 여러 데이터 센터에서 대량의 데이터를 관리하기 위해 구축된 오픈 소스 NoSQL 데이터베이스이고, EvCache는 Netflix가 오픈소스로 공개한 Memcached 클라이언트 라이브러리이다.

-   Cassandra:
    -   멀티 리전 비동기 복제
-   EvCache:
    -   캐시 무효화로 데이터 일관성 유지

#### Cassandra

-   멀티 데이터센터 환경을 지원하는 분산 NoSQL DB
-   리전 간 **비동기 복제**에 적합함
-   Active-Active 구조에서 각 리전이 독립적으로 요청을 처리하는 기반

#### EVCache

-   Netflix의 분산 캐시 계층
-   빠른 읽기 성능 제공
-   데이터 변경 시 캐시 무효화 전략(다른 리전의 오래된 캐시를 지움)을 통해 리전 간 정합성 보조 역할을 함


#### 정리

-   Cassandra = 원본 데이터 저장/복제
-   EVCache = 빠른 읽기 + 캐시 계층 보완

한 리전에서 데이터가 쓰일 때마다, EvCache 클라이언트가 다른 리전에 메시지를 보내 해당 캐시 항목을 무효화한다. 그 결과, 다른 리전에서 이후에 해당 데이터를 읽을 때는 다시 계산하거나 Cassandra에서 데이터를 가져와 로컬 캐시를 업데이트하게 된다. 
-   빠른 읽기 + 리전 간 데이터 동기화

### ④ 배포 자동화 (Mimir)

> Mimir는 리전이 늘어나며 복잡해진 멀티 리전 배포를 자동화하기 위해 만든 워크플로우 도구이다. 카나리 분석과 자동 롤백을 함께 사용해, 여러 리전에 서비스를 안전하게 단계적으로 배포할 수 있게 했다.
-   멀티 리전 배포 자동화
-   Canary + 자동 롤백 지원


#### 1. 처음 상태 (2개)
처음에는 미국동부만 있었음
- Test (테스트용)
- Production (실서비스) 

#### 2. 유럽 진출 (4개)
- US-East에 Test, Production
- EU-West에 Test, Production

#### 3. Active-Active 도입 (6개)
미국을 두 리전으로 나눔
- US-East (Test, Production)
- US-West (Test, Production)
- EU-West (Test, Production)


리전이 늘어나면, 각 리전마다 Test, Production 환경이 필요해서 배포 환경 수가 증가한다. 여러 단계의 수동 배포 절차를 거치는 것은 비효율적이므로 멀티 리전 배포 과정을 자동화하기 위해 Mimir라는 워크플로우 도구를 개발했다. 여기에 자동화된 카나리 분석(canary analysis)과 자동 롤백 절차를 결합함으로써, 애플리케이션을 여러 위치에 단계적으로(staged) 자동 배포할 수 있게 되었다.

## 5. 장애 대응 전략 (Simian Army)

>Netflix는 일부러 장애를 만든다

실제 장애를 가정한 실험을 통해 시스템 복원력을 검증한다. 대표적으로 다음과 같은 도구들이 있다. 

-   Chaos Monkey → 서버 죽이기
-   Chaos Gorilla → AZ 전체 장애
-   Split-brain → 리전 연결 끊기
-   Chaos Kong → 리전 전체 장애

### 목적

-   실제 장애 전에 시스템이 버티는지 검증
-   장애 대응이 문서가 아니라 실제로 가능한지 확인

-   → 트래픽을 다른 리전으로 전환
-   → 빠르게 서비스 복구
