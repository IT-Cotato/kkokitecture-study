# Chapter 1. 사용자 수에 따른 규모 확장성 정리



## 1. 단일 서버 → 계층 분리

### 단일 서버
> 웹 앱, 데이터베이스 등이 전부 서버 한 대에서 실행


### 데이터베이스
> 사용자가 늘면 서버 하나로는 감당할 수 없기 때문에 여러 서버를 두어야 한다.  
> 하나는 웹/모바일 트래픽 처리 용도이고, 다른 하나는 데이터베이스용이다.  
> 웹 계층과 데이터 계층을 분리하면 그 각각을 독립적으로 확장해 나갈 수 있게 된다.


### DB 선택 기준
- **RDBMS (관계형):** 자료를 테이블/열/칼럼으로 관리. SQL을 사용해 여러 테이블을 join 가능 (MySQL, PostgreSQL 등)
- **NoSQL (비관계형):** 아주 낮은 응답 지연 시간, 비정형 데이터 처리, 대폭적인 수평 확장 필요 시 유리. (Redis, MongoDB, Cassandra 등)



### 수직적 규모 확장 vs 수평적 규모 확장
>서버 규모를 확장한다고 했을 때, 이에는 두 가지 방법이 있다.  
>스케일 업이라고 하는 수직적 규모 확장과  스케일 아웃이라고 하는 수평적 규모 확장

- **수직적 확장 (스케일 업)**: 서버에 고사양 자원을 추가하는 행위
- **수평적 확장 (스케일 아웃)**: 더 많은 서버를 추가하여 성능을 개선하는 행위


서버로 유입되는 트래픽의 양이 적을 때에는 수직적 규모 확장이 좋은 선택이다.  
대규모 애플리케이션을 지원하는 데는 수평적 규모 확장이 적절하다.


### 수직적 규모 확장의 한계


1. **물리적 한계**
	 한 대의 서버에 CPU나 메모리를 무한대로 증설할 수는 없다.

2. **장애 대응 한계**
  자동 복구(failover)나 다중화(redundancy) 방안을 스스로 제공하지 않는다.

3. **단일 장애점(SPOF)**
  서버에 장애가 발생하면 웹사이트나 앱이 전체 중단될 수 있다.

## 2. 로드밸런스 & DB 다중화

### 핵심 개념
- **로드밸런서 (Load Balancer):** 트래픽을 여러 서버로 분산하여 부하를 조절하고, 특정 서버 장애 시에도 서비스 중단을 방지.
- **데이터베이스 다중화 (Replication)**
  - **Master (주):** 쓰기(Write) 연산 담당
  - **Slave (부):** 읽기(Read) 연산 담당으로, Master로부터 데이터를 복제받음
  - **장점:** 읽기 성능 향상, 데이터 보존(안정성), 고가용성 보장

### 설명
>데이터베이스를 변경하는 명령어들 insert, delete, update 같은 경우 주 데이터베이스로만 전달되어야한다. 대부분의 애플리케이션의 경우, 읽기 연산의 비중이 쓰기 연산보다 훨씬 높기 때문에 부 데이터베이스의 수가 주 데이터베이스보다 많다.

### 장점
1. **성능향상**  
   읽기 연산이 부 데이터베이스 서버들로 분산되므로 병렬로 처리될 수 있는 질의 수가 늘어나므로, 성능이 좋아진다.
2. **안정성**  
   자연재해 등의 이유로 데이터베이스 서버 가운데 일부가 파괴되어도 데이터는 보존된다. 데이터를 지역적으로 멀리 떨어진 여러 장소에 다중화 해놓을 수 있기 때문이다.
3. **가용성**  
   데이터를 여러 지역에 복제해 둠으로써, 하나의 데이터베이스 서버에 장애가 발생하더라도 다른 서버에 있는 데이터를 가져와 계속 서비스할 수 있다.

## 3. 캐시 & CDN

### 핵심 개념
- **캐시 계층:** DB보다 훨씬 빠른 메모리에 데이터를 임시 보관. DB 부하를 줄이고 응답 속도 개선.
- **CDN (Content Delivery Network):** 이미지, 비디오 등 **정적 콘텐츠**를 사용자 근처 서버에 캐싱. 지리적 거리로 인한 로딩 지연 시간(Latency) 해결.

## 4. 무상태(Stateless) 웹 계층

### 상태 정보란?
>서버가 클라이언트의 이전 요청이나 정보를 기억하고 있는 데이터이다.

상태 정보를 보관하는 서버와 그렇지않은 서버가 있다. 상태 정보를 보관하는 서버는 클라이언트 정보, 즉 상태를 유지하여 요청들 사이에 공유되도록 한다. 무상태 서버에는 이런 장치가 없다.

### 상태 의존적인 아키텍처

- 같은 클라이언트로부터의 요청은 항상 같은 서버로 전송되어야 한다.
- 대부분의 로드밸런서가 이를 지원하기 위해 고정 세션(sticky session)이라는 기능을 제공하는데, 이는 로드밸런서에 부담을 준다

### 무상태 아키텍처

- 사용자로부터의 HTTP 요청은 어떤 웹 서버로도 전달될 수 있다. 웹 서버는 상태 정보가 필요할 경우 공유 저장소로부터 데이터를 가져온다.
- 상태 정보는 웹 서버로부터 물리적으로 분리되어 있다.

**장점:** 안정적, 규모확장 용이

## 5. 다중 데이터 센터

: 많은 사용자의 데이터를 안전하고 빠르게 처리하기 위해 최적화된 특수 시설

### 필요한 이유
- **수평적 규모 확장(Scale-out):** 서버를 수천 대 늘리려면 공간이 필요함.
- **장애 대응(Failover):** 데이터 센터 자체가 자연재해(지진, 화재)로 마비될 것에 대비해, 똑같은 데이터 센터를 다른 지역에 더 짓기도 함
- **Geo-routing**: 장애가 없는 상황에서 사용자는 가장 가까운 데이터 센터로 안내

데이터 센터 중 하나에 심각한 장애가 발생하면 모든 트래픽은 장애가 없는 데이터 센터로 전송됨

### 다중 데이터 센터 아키텍처 만들기 위해 해결해야할 기술적 난제
- **트래픽 우회**: 올바른 데이터 센터로 트래픽을 보내는 효과적인 방법을 찾아야 함.
- **데이터 동기화**: 데이터 센터마다 별도의 데이터베이스를 사용한다면, failover 트래픽이 다른 데이터베이스로 우회된다 해도, 찾는 데이터가 없을 수 있다.
- **테스트와 배포**: 여러 데이터 센터를 사용하도록 시스템이 구성된 상황이라면 웹 사이트나 애플리케이션을 여러 위치에서 테스트 해보는 것이 중요하다.

> 시스템을 더 큰 규모로 확장하기 위해서는 시스템의 컴포넌트를 분리하여, 각기 독립적으로 확장할 수 있도록 해야한다!

## 6. 메시지 큐(message queue)

> 무손실을 보장하고, 비동기 통신을 지원하는 컴포넌트

- 메시지의 무손실(durability): 메시지 큐에 보관된 메시지는 소비자가 꺼낼 때까지 안전히 보관된다는 특징

즉, 메시지의 버퍼 역할을 하며, 비동기적으로 전송한다. 메시지 큐를 사용하면 서비스 혹은 서버 간 결합이 느슨해져서, 규모 확장성이 보장되어야 하는 안정적 애플리케이션을 구성하기 좋다.


### 구성
- **생산자**: 소비자 프로세스가 다운되어 있어도 메시지를 발행할 수 있다.
- **소비자**: 생산자 서비스가 가용한 상태가 아니더라도 메시지를 수신할 수 있다.


#### ex) 사진 보정 애플리케이션
보정은 시간이 오래 걸릴 수 있는 프로세스이므로 비동기적으로 처리하면 편하다.

웹 서버는 job을 메시지 큐에 넣는다. 사진 보정 작업 프로세스들은 이 작업을 메시지 큐에서 꺼내 비동기적으로 완료한다.

- 생산자와 소비자 서비스의 규모는 각기 독립적으로 확장될 수 있다.

## 7. 로그, 메트릭 그리고 자동화

### 로그
>시스템의 오류와 문제들을 보다 쉽게 찾아내기 위해서는 에러 로그를 모니터링 하는 것이 중요하다.

### 메트릭
>사업 현황에 관한 유용한 정보를 메트릭을 통해 얻을 수 있다.

- 호스트 단위 메트릭: CPU, 메모리, 디스크 I/O에 관한 메트릭 등
- 종합 메트릭: 데이터베이스 계층의 성능, 캐시 계층의 성능 등
- 핵심 비즈니스 메트릭: 일별 능동 사용자, 수익, 재방문 등

### 자동화
>시스템이 크고 복잡해지면 생산성을 높이기 위해 자동화 도구를 활용해야한다.

## 8. 데이터베이스의 규모 확장

저장할 데이터가 많아지면 데이터베이스에 대한 부하도 증가한다.

데이터베이스 규모를 확장하는 데는 두 가지 접근법이 있다.


### 1) 수직적 확장 (스케일 업)
고성능의 자원을 증설

#### 단점
1. 데이터베이스 서버 하드웨어에는 한계가 있으므로 CPU, RAM 등을 무한 증설할 수는 없다 → 사용자가 늘어나면 결국 한 대 서버로는 감당하기 어려울 것이다.
2. SPOF(Single Point Of Failure)로 인한 위험성이 크다
3. 고비용

### 2) 수평적 확장 (샤딩)
더 많은 서버 추가

- 샤딩은 대규모 데이터베이스를 shard라고 부르는 작은 단위로 분할하는 기술을 말한다.
- 모든 샤드는 같은 스키마를 쓰지만, 샤드에 보관되는 데이터 사이에는 중복이 없다.

#### 단점
1. 데이터의 재 샤딩 (resharding)
2. 유명인사 문제
3. 조인과 비정규화
