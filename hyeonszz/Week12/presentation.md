# 뉴스 피드 시스템 설계: Twitter & Facebook

## 1. 직관적인 뉴스 피드 구현의 문제

가장 직관적인 뉴스 피드 구현

```sql
SELECT post_id FROM posts
WHERE author_id IN (
  SELECT followee_id FROM follows WHERE follower_id = :me
)
ORDER BY created_at DESC
LIMIT 20;
```

- 팔로우 수가 1,000명이라면 → 1,000개 유저의 포스트를 **매 요청마다** 조회 & 정렬
- DAU 1,000만 명 × 피드 요청 수십 회 = **수억 건의 실시간 조인 쿼리**
- 유저마다 팔로우 수가 달라서 응답 시간을 예측할 수 없음

**결론**: 대부분의 서비스에서 Read는 Write보다 훨씬 많이 발생하므로 Read 성능 최적화가 우선이다. 단, 팔로워가 수백만 명인 셀럽 계정에서는 Write 비용도 폭발적으로 커진다. 이 두 가지 압력을 동시에 해결하려는 시도에서 Fanout 아이디어가 나온다.

## 2. Fanout의 두 방향

### Fanout-on-Write (Push 모델)

포스팅 시점에 팔로워 모두의 피드에 미리 넣어두는 방식

```
User A가 포스팅
  → 팔로워 목록 조회 (graph DB)
  → 팔로워 각각의 피드 캐시에 post_id 삽입
  → 읽을 때는 캐시에서 상위 k개 ID를 바로 조회 (DB 접근 없이 빠른 읽기)
```

- (+) 읽기 빠름
- (-) 팔로워 100만 명이면 write 1번 = 캐시 업데이트 100만 번

### Fanout-on-Read (Pull 모델)

읽는 시점에 팔로우하는 유저들의 최신 포스트를 모아서 합치는 방식

```
User B가 피드 요청
  → 팔로잉 목록 조회
  → 각 유저의 최근 포스트 조회
  → 병합 & 정렬 후 반환
```

- (+) 쓰기 단순, 셀럽 문제 없음
- (-) 읽기 지연, 팔로잉 많을수록 느려짐

## 3. Twitter vs Facebook

### Twitter: **Fanout-on-Write**

Twitter는 Read가 Write보다 수십 배 많다

- ex) 300K QPS의 타임라인 조회 vs 5K QPS의 트윗 발행

**실제 구현 (2013년 공개 기준)**

트윗이 Write API에 도달하면, fanout daemon이 소셜 그래프 서비스에 쿼리를 보내 팔로워 목록을 가져온다. 그 다음 팔로워 각각의 홈 타임라인에 트윗 ID, 유저 ID, 리트윗 메타데이터를 Redis 클러스터에 삽입한다. Redis는 전체 트윗 텍스트가 아닌 ID만 저장하며, 당시 구현 기준으로 유저당 최근 약 800개의 트윗 ID만 유지했다.

> **왜 약 800개였나?** 메모리 사용량 통제를 위한 의도적 결정이다. 더 오래된 피드는 디스크에서 읽으면 되고, 어차피 대부분의 유저는 최근 피드만 본다.
> 

**Lady Gaga 이슈**

Lady Gaga가 당시 3,100만 팔로워를 가지고 있었는데, 트윗을 올리면 3,100만 유저의 타임라인을 업데이트해야 했다. 게다가 3번 복제해야 했다. 결과적으로 일부 유저는 그 트윗을 수 분간 지연되어 받아보기도 했다.

**해결책 Hybrid**

대다수 일반 유저에게는 Fanout-on-Write를 유지하되, 팔로워 수가 매우 많은 소수의 셀럽 계정은 별도로 처리한다. 셀럽의 트윗은 팬아웃하지 않고, 읽기 시점에 일반 유저의 캐시된 타임라인과 병합한다.

```
일반 유저 타임라인 = Redis 캐시 (fanout-on-write)
셀럽 트윗         = 읽기 시점에 조회 후 merge
최종 피드         = 두 결과를 합친 것
```

### Facebook: **Fanout-on-Read 중심**

Twitter가 쓰기 시점에 미리 피드를 쌓아두는 방향을 택했다면, Facebook은 읽기 시점에 피드를 조립하는 방향을 주된 철학으로 삼았다. 둘 다 순수한 단일 모델은 아니지만, 무게중심이 반대다.

Facebook의 뉴스 피드는 2005년에 Fanout-on-Write로 시작했다. 당시에는 메모리와 네트워크 성능이 충분하지 않았기 때문이다. Fanout-on-Read 방식으로의 전환은 2007년부터 시작됐다. 하드웨어가 충분히 강력해지면서 가능해진 결정이었다.

**Write Amplification 문제**

팔로워가 300명인 유저가 포스트를 올리면, 시스템에 300번의 쓰기가 발생한다. 이는 데이터를 메모리에서 관리 가능한 크기로 유지하던 문제를, 디스크가 필요한 대규모 저장 문제로 바꿔버린다.

Facebook이 도입한 시스템은 Multifeed다. 이는 Facebook 공식 Engineering 블로그에 직접 설명된 내용이다:

> *"When a person goes to his or her Facebook feed, Multifeed looks up the user's friends, finds all their recent actions, and decides what should be rendered based on a certain relevance and ranking algorithm."*
> 

즉, Multifeed는 유저가 피드에 접속하는 읽기 시점에 친구 목록을 조회하고 최근 활동을 수집한 뒤, 랭킹 알고리즘으로 무엇을 보여줄지 결정한다. 이 구조는 캐시된 후보 데이터를 활용하기 때문에 매 요청마다 DB를 풀스캔하는 것과는 다르다. Aggregator가 요청을 받으면 Leaf 서버들에 분산 쿼리를 날려 후보 포스트를 수집하고, 랭킹·필터링 후 반환하는 구조이다.

## 4. 캐싱 전략

피드 시스템의 성능은 캐시 설계에서 결정된다.

| 캐시 대상 | 저장 내용 | 이유 |
| --- | --- | --- |
| 뉴스 피드 캐시 | `(user_id, [post_id, ...])` | 전체 포스트가 아닌 ID만 → 메모리 절약 |
| 포스트 캐시 | `(post_id, 포스트 전체 내용)` | 인기 포스트는 수백만 피드에 등장 → 중복 저장 방지 |
| 유저 정보 캐시 | `(user_id, 프로필 정보)` | 모든 포스트 렌더링 시 필요, 자주 안 바뀜 |

Twitter의 Redis 클러스터는 각 유저의 홈 타임라인을 세 개의 다른 머신에 복제해 저장한다. 이를 통해 사실상 모든 활성 유저의 홈 타임라인을 메모리에 캐싱할 수 있고, 가장 빠른 응답 시간을 제공한다.

**비활성 유저 문제**

30일 이상 Twitter에 접속하지 않은 유저의 타임라인은 Redis 클러스터에 유지하지 않는다. 이런 유저가 복귀해 홈 타임라인을 요청하면, 디스크에서 타임라인을 재구성한다.

→ LRU 같은 캐시 교체 정책을 통해 비활성 유저를 캐시에서 제거해 메모리를 절약하는 실용적 결정이다. Twitter가 정확히 어떤 정책을 사용하는지는 공개되지 않았다.

## 6. 정리: 설계 결정의 근거

| 결정 사항 | 선택지 | 실제 선택 기준 |
| --- | --- | --- |
| Fanout 방향 | Write vs Read | **Read/Write 비율:** Twitter는 Read 압도적 → Write 시점 fanout 중심, Facebook은 Write Amplification 문제 → Read 시점 집계 중심 |
| 셀럽 계정 처리 | 동일 처리 vs 분리 | **팔로워 수 임계치** 기준으로 예외 처리 |
| 피드 정렬 | 시간순 vs ML 랭킹 | **팔로우 수 증가**로 시간순의 한계 → ML 전환 |
| 캐시 저장 단위 | 전체 포스트 vs ID만 | **메모리 효율**  ID만 저장하고 필요 시 fetch |
| 비활성 유저 | 항상 캐시 vs 제거 | 메모리 절약 vs 복귀 유저 경험 트레이드오프 |
