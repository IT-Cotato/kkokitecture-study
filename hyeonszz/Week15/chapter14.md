# CH14. 유튜브 설계

## 1단계 문제 이해 및 설계 범위 확정

- 넷플릭스나 훌루 같은 비디오 플랫폼을 설계하는 문제에도 적용 가능함
- 유튜브 시스템은 언뜻 보기에는 간단해 보이지만 실제로는 그 이면에 매우 복잡한 기술이 숨어있음

#### 유튜브 관련 통계자료

- 월간 능동 사용자 수: 20억
- 매일 재생되는 비디오 수: 50억
- 미국 성인 가운데 73%가 유튜브 이용
- 5천만 명의 창작자
- 유튜브의 광고 수입은 2019년 기준 150억 달러이며 2018년 대비 36% 증가
- 모바일 인터넷 트래픽 가운데 37%를 유튜브가 점유
- 80개 언어로 이용 가능

#### 설계 범위

- 가장 중요한 기능: 비디오 업로드, 시청
- 지원 클라이언트: 모바일 앱, 웹 브라우저, 스마트 TV
- DAU: 5백만명
- 사용자 평균 이용 시간: 30분
- 다국어 지원
- 현존하는 대부분의 종류·해상도 지원
- 암호화 필요
- 비디오 파일 크기 제한: 최대 1GB
- 기존 클라우드 서비스 활용 가능

#### 이번 장에서 설계할 기능 범위

- 빠른 비디오 업로드
- 원활한 비디오 재생
- 재생 품질 선택 기능
- 낮은 인프라 비용
- 높은 가용성과 규모 확장성, 그리고 안정성

#### 개략적 규모 추정

- DAU: 5백만 명
- 한 사용자는 하루에 평균 5개의 비디오를 시청
- 10%의 사용자가 하루에 1개 비디오 업로드
- 비디오 평균 크기는 300MB
- 비디오 저장을 위해 매일 새로 요구되는 저장 용량 = 5백만×10%×300MB = 150TB
- CDN 비용
    - CDN에서 나가는 데이터 양에 따라 과금
    - AWS CloudFront를 CDN 솔루션으로 사용할 경우, 100% 트래픽이 미국에서 발생한다고 가정하면 1GB당 $0.02의 요금이 발생
    - 따라서 매일 발생하는 요금은 5백만×비디오5개×0.3GB×$0.02 = $150,000

→ CDN을 통한 비디오 서비스는 비용이 상당함. 이 비용을 줄이는 방법은 상세 설계에서 다룸.

## 2단계 개략적 설계안 제시 및 동의 구하기

CDN과 BLOB 스토리지는 기존 클라우드 서비스를 활용한다.

**모든 것을 직접 만들지 않는 이유**

- 시스템 설계 면접은 모든 것을 밑바닥부터 만드는 것과는 관계가 없다. 주어진 시간 안에 적절한 기술을 골라 설계를 마치는 것이 그 기술 각각이 어떻게 동작하는지 상세히 설명하는 것보다 중요하다.
- 규모 확장이 쉬운 BLOB 저장소나 CDN을 만드는 것은 복잡할 뿐 아니라 많은 비용이 드는 일이다. 넷플릭스나 페이스북 같은 큰 회사도 모든 것을 스스로 구축하지는 않는다.

개략적으로 세 개 컴포넌트로 구성

- **단말 Client**: 컴퓨터, 모바일 폰, 스마트 TV를 통해서 유튜브를 시청할 수 있다.
- **CDN**: 비디오는 CDN에 저장한다. 재생 버튼을 누르면 CDN으로부터 스트리밍이 이루어진다.
- **API 서버**: 비디오 스트리밍을 제외한 모든 요청은 API 서버가 처리한다. 피드 추천, 비디오 업로드 URL 생성, 메타데이터 데이터베이스와 캐시 갱신, 사용자 가입 등이 API 서버가 처리하는 작업이다.

### [1] 비디오 업로드 절차

- **사용자**: 컴퓨터나 모바일 폰, 혹은 스마트 TV를 통해 유튜브를 시청하는 이용자
- **로드밸런서**: API 서버 각각으로 고르게 요청을 분산하는 역할
- **API 서버**: 비디오 스트리밍을 제외한 다른 모든 요청을 처리
- **메타데이터 데이터베이스**: 비디오의 메타데이터를 보관. 샤딩과 다중화를 적용하여 성능 및 가용성 요구사항 충족
- **메타데이터 캐시**: 성능을 높이기 위해 비디오 메타데이터와 사용자 객체를 캐시2
- **원본 저장소**: 원본 비디오를 보관할 대형 이진 파일 저장소 시스템
- **트랜스코딩 서버**: 비디오 트랜스코딩은 비디오 인코딩이라 부르기도 하는 절차로, 비디오의 포맷을 변환하는 작업. 단말이나 대역폭 요구사항에 맞는 최적의 비디오 스트림을 제공하기 위해 필요
- **트랜스코딩 비디오 저장소**: 트랜스코딩이 완료된 비디오를 저장하는 BLOB 저장소
- **CDN**: 비디오를 캐시하는 역할. 사용자가 재생 버튼을 누르면 비디오 스트리밍은 CDN을 통해 이루어짐
- **트랜스코딩 완료 큐**: 비디오 트랜스코딩 완료 이벤트들을 보관할 메시지 큐
- **트랜스코딩 완료 핸들러**: 트랜스코딩 완료 큐에서 이벤트 데이터를 꺼내어 메타데이터 캐시와 데이터베이스를 갱신할 작업 서버들

**비디오 업로드가 처리되는 절차** (두 프로세스가 병렬적으로 수행)

1. 비디오 업로드
2. 비디오 메타데이터 갱신 → 메타데이터에는 비디오 URL, 크기, 해상도, 포맷, 사용자 정보가 포함된다.

**(1) 비디오 업로드** (그림 14-5)

1. 비디오를 원본 저장소에 업로드한다.
2. 트랜스코딩 서버는 원본 저장소에서 해당 비디오를 가져와 트랜스코딩을 시작한다.
3. 트랜스코딩이 완료되면 아래 두 절차가 병렬적으로 수행된다.
    - 완료된 비디오를 트랜스코딩 비디오 저장소로 업로드한다.
        - 트랜스코딩이 끝난 비디오를 CDN에 올린다.
    - 트랜스코딩 완료 이벤트를 트랜스코딩 완료 큐에 넣는다.
        - 완료 핸들러가 이벤트 데이터를 큐에서 꺼낸다.
        - 완료 핸들러가 메타데이터 데이터베이스와 캐시를 갱신한다.
4. API 서버가 단말에게 비디오 업로드가 끝나서 스트리밍 준비가 되었음을 알린다.

**(2) 메타데이터 갱신** (그림 14-6)

원본 저장소 업로드와 병렬로, 단말이 메타데이터 갱신 요청을 API 서버에 전송 → API 서버가 캐시·DB 업데이트

### [2] 비디오 스트리밍 절차

재생 버튼을 누르면 스트리밍이 바로 시작되며, 다운로드 완료를 기다릴 필요가 없다.

**스트리밍 프로토콜**: 비디오 스트리밍용 표준 통신방법

- MPEG-DASH (Dynamic Adaptive Streaming over HTTP)
- 애플 HLS (HTTP Live Streaming)
- 마이크로소프트 스무드 스트리밍
- 어도비 HTTP 동적 스트리밍(HDS)

→ 프로토콜마다 지원 인코딩·플레이어가 다르므로 용례에 맞게 선택하는 것이 중요

## 3단계 상세 설계

지금까지 살펴본 개략적 설계안에서는 전체 시스템을 두 부분, 즉 비디오 업로드를 담당하는 부분과 비디오 스트리밍을 담당하는 부분으로 나눠 살펴봤다. 이번 절에서는 그 두 부분을 최적화 방안과 함께 좀 더 상세히 다듬고 오류 처리 메커니즘에 대해서도 소개한다.

### 비디오 트랜스코딩

단말이 녹화한 비디오는 다른 단말에서도 순조롭게 재생되려면 호환 가능한 비트레이트·포맷으로 저장되어야 함. 비트레이트는 비디오 비트가 얼마나 빨리 처리되어야 하는지를 나타내는 단위이며, 비트레이트가 높을수록 고화질이고 더 높은 컴퓨팅 파워·회선 속도가 요구됨.

**비디오 트랜스코딩이 중요한 이유**

- 가공되지 않은 원본 비디오는 저장 공간을 많이 차지한다. 초당 60프레임으로 녹화된 HD 비디오는 수백 GB의 저장공간을 차지하게 될 수 있다.
- 상당수의 단말과 브라우저는 특정 종류의 비디오 포맷만 지원한다. 따라서 호환성 문제를 해결하려면 하나의 비디오를 여러 포맷으로 인코딩해 두는 것이 바람직하다.
- 사용자에게 끊김 없는 고화질 비디오 재생을 보장하려면, 네트워크 대역폭이 충분하지 않은 사용자에게는 저화질 비디오를, 대역폭이 충분한 사용자에게는 고화질 비디오를 보내는 것이 바람직하다.
- 모바일 단말의 경우 네트워크 상황이 수시로 달라질 수 있다. 비디오가 끊김 없이 재생되도록 하기 위해서는 비디오 화질을 자동으로 변경할 수 있도록 하는 것이 바람직하다.

**인코딩 포맷 구성 요소**

- **컨테이너(container)**: 비디오·오디오·메타데이터를 담는 바구니 (.avi, .mov, .mp4 등)
- **코덱(codec)**: 화질 보존하며 파일 크기를 줄이는 압축/해제 알고리즘 (H.264, VP9, HEVC)

### 유향 비순환 그래프(DAG) 모델

비디오 트랜스코딩은 컴퓨팅 자원·시간이 많이 드는 작업이며, 창작자마다 다른 프로세싱 요구사항을 가짐. 이를 지원하고 병렬성을 높이기 위해 적절한 추상화를 도입, 클라이언트 프로그래머가 실행할 작업을 직접 정의하도록 함. 페이스북 스트리밍 비디오 엔진도 DAG모델을 도입해 작업을 순차/병렬로 배열함. 본 설계안도 유사한 DAG 모델을 채택.

원본 비디오는 비디오/오디오/메타데이터 3부분으로 나뉘어 처리됨. 

비디오 부분 작업:

- 검사: 품질·손상 확인
- 비디오 인코딩: 다양한 해상도·코덱·비트레이트 조합으로 인코딩
- 섬네일: 업로드 이미지 또는 자동 추출 이미지로 생성
- 워터마: 식별정보를 이미지로 오버레이 표시

#### 비디오 트랜스코딩 아키텍처

다섯 개 주요 컴포넌트로 구성: 전처리기, DAG 스케줄러, 자원 관리자, 작업 실행 서버, 임시 저장소. 결과물은 인코딩된 비디오.

**(1) 전처리기**

1. 비디오 분할: 비디오 스트림을 GOP 단위로 분할. GOP는 특정 순서로 배열된 프레임 그룹이며 독립적으로 재생 가능, 길이는 보통 몇 초. 오래된 단말·브라우저가 GOP 분할을 지원하지 않으면 전처리기가 대신 수행
2. DAG 생성: 클라이언트 프로그래머의 설정 파일에 따라 DAG 생성
3. 데이터 캐시: 전처리기는 분할된 비디오의 캐시 역할도 겸함. 안정성을 위해 GOP·메타데이터를 임시 저장소에 보관하며, 인코딩 실패 시 이를 활용해 재개

**(2) DAG 스케줄러**

DAG 그래프를 몇 개 단계로 분할하여 자원 관리자의 작업 큐에 넣음. 그림 14-15는 2단계 사례로, 1단계에서 비디오/오디오/메타데이터를 추출하고 2단계에서 비디오 인코딩·섬네일 추출·오디오 인코딩을 수행

**(3) 자원 관리자**

세 개의 큐와 작업 스케줄러로 구성

- 작업 큐: 실행할 작업이 담긴 우선순위 큐
- 작업 서버 큐 작업 서버 가용 상태 정보가 담긴 우선순위 큐
- 실행 큐: 현재 실행 중인 작업·서버 정보 큐
- 작업 스케줄러: 최적 작업/서버 조합 선정 및 실행 지시

동작 순서: 최고 우선순위 작업 선택 → 적합한 작업 서버 선정 → 실행 지시 → 할당 정보를 실행 큐에 기록 → 완료 시 실행 큐에서 제거

**(4) 작업 서버** 

DAG에 정의된 작업을 수행하며, 종류에 따라 구분 관리

**(5) 임시 저장소**

데이터 유형·크기·이용 빈도·유효기간에 따라 저장소 시스템 선택. 메타데이터는 크기가 작고 빈번히 참조되므로 메모리 캐시가 적합, 비디오/오디오는 BLOB 저장소가 적합. 프로세싱 완료 후 삭제

**인코딩된 비디오**

인코딩 파이프라인의 최종 결과물. `funny_720p.mp4` 형태의 이름을 가짐.

→ 그림 14-22처럼 작은 GOP로 분할하여 병렬 업로드하면 일부 실패 시에도 빠르게 재개 가능. 단말이 GOP 경계에 맞춰 분할을 수행하면 업로드 속도 향상

#### 속도 최적화: 업로드 센터를 사용자 근거리에 지정

업로드 센터를 여러 지역에 분산 배치. 미국 사용자는 북미 업로드 센터로, 중국 사용자는 아시아 업로드 센터로 전송. 본 설계안은 CDN을 업로드 센터로 활용.

#### 속도 최적화: 모든 절차를 병렬화

느슨하게 결합된 시스템을 만들어 병렬성을 높임. 원본 저장소→CDN 이동 절차는 단계 간 의존성이 있어 병렬화가 어려움. 결합도를 낮추기 위해 메시지 큐 도입

- 도입 전: 인코딩 모듈이 다운로드 모듈 작업 완료를 기다려야 함
- 도입 후: 인코딩 모듈은 더 이상 기다릴 필요 없이, 큐에 쌓인 이벤트 각각을 병렬 처리 가능

#### 안전성 최적화: 미리 사인된 업로드 URL

허가받은 사용자만 올바른 위치에 업로드하도록, 미리 사인된 업로드 URL을 이용

**변경된 업로드 절차**

1. 클라이언트가 HTTP 서버에 POST 요청 → 미리 사인된 URL 수신 
2. API 서버가 미리 사인된 URL 반환
3. 클라이언트가 해당 URL 위치에 비디오 업로드

#### 안전성 최적화: 비디오 보호

콘텐츠 제작자가 원본 도난을 우려해 업로드를 주저하는 문제 → 저작권 보호를 위한 세 가지 선택지:

- 디지털 저작권 관리(DRM): 애플 페어플레이, 구글 와이드바인, 마이크로소프트 플레이레디
- AES 암호화: 비디오 암호화 후 재생 시에만 복호화, 허락된 사용자만 시청 가능
- 워터마크: 소유자 정보를 이미지로 오버레이

#### 비용 최적화

CDN은 핵심 부분이지만 비용이 큼. 유튜브 비디오 스트리밍은 롱테일 분포를 따름 → 인기 비디오는 자주 재생되고 나머지는 거의 재생되지 않음. 이에 따른 최적화:

1. 인기 비디오는 CDN으로, 나머지는 비디오 서버로 재생
2. 인기 없는 짧은 비디오는 미리 인코딩하지 않고 필요할 때 인코딩
3. 특정 지역에서만 인기 있는 비디오는 다른 지역으로 옮길 필요 없음
4. CDN을 직접 구축하고 ISP와 제휴 (초대형 프로젝트, 대규모 사업자에 적합)

#### 오류 처리

대형 시스템에서 오류는 불가피함.

- 회복 가능 오류(recoverable error): 트랜스코딩 실패 등 → 재시도로 해결, 계속 실패 시 클라이언트에 오류 코드 반환
- 회복 불가능 오류(non-recoverable error): 잘못된 비디오 포맷 등 → 작업 중단 후 오류 코드 반환

**컴포넌트별 오류 처리**

- 업로드 오류: 재시도
- 비디오 분할 오류: 낡은 클라이언트가 분할 실패 시 서버가 전체 비디오를 받아 분할 처리
- 트랜스코딩 오류: 재시도
- 전처리 오류: DAG 그래프 재생성
- DAG 스케줄러 오류: 작업 재스케줄링
- 자원 관리자 큐 장애: replica 이용
- 작업 서버 장애: 다른 서버에서 재시도
- API 서버 장애: 무상태 서버이므로 신규 요청은 다른 API 서버로 우회
- 메타데이터 캐시 서버 장애: 데이터가 다중화되어 있어 다른 노드에서 조회 가능, 장애 서버는 교체
- 메타데이터 DB 서버 장애: 주 서버 장애 시 부 서버 중 하나를 주 서버로 승격, 부 서버 장애 시 다른 부 서버로 읽기 처리 후 교체

## 4단계 마무리

추가 논의 사항

- **API 계층의 규모 확장성 확보 방안**: API 서버는 무상태 서버이므로 수평적 규모 확장이 가능하다는 사실을 언급하면 좋을 것
- **데이터베이스 계층의 규모 확장성 확보 방안**: 데이터베이스의 다중화와 샤딩 방법
- **라이브 스트리밍**: 이번 장에서 설계한 시스템은 라이브 스트리밍용으로 설계한 게 아니긴 하지만, 라이브 스트리밍 시스템과 비-라이브 스트리밍 시스템 간에는 비슷한 점도 많다. 둘 다 비디오 업로드, 인코딩, 스트리밍이 필요하다는 점에서는 같다. 가장 중요한 차이는 다음과 같다.
    - 라이브 스트리밍의 경우에는 응답지연이 좀 더 낮아야 한다. 따라서 스트리밍 프로토콜 선정에 유의해야 한다.
    - 라이브 스트리밍의 경우 병렬화 필요성은 떨어질 텐데, 작은 단위의 데이터를 실시간으로 빨리 처리해야 하기 때문이다.
    - 라이브 스트리밍의 경우 오류 처리 방법을 달리해야 한다. 너무 많은 시간이 걸리는 방안은 사용하기 어렵다.
- **비디오 삭제**: 저작권을 위반한 비디오, 선정적 비디오, 불법적 행위에 관계된 비디오는 내려야 한다. 내릴 비디오는 업로드 과정에서 식별해 낼 수도 있지만, 사용자의 신고 절차를 통해 판별할 수도 있다.
