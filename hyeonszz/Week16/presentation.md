## 트랜잭션(Transaction)

: 하나의 논리적인 작업 단위

```sql
A 계좌 : 100,000원
B 계좌 : 50,000원

A에서 10,000원 출금
↓
B에 10,000원 입금
```

개발자가 보기에는 두 개의 SQL이지만 사용자 입장에서는 **계좌이체**라는 하나의 작업이다. 
→ 출금 성공 + 입금 실패가 되면 안된다. 
 다 성공하거나, 둘 다 실패해야 한다.
이러한 하나의 작업 단위를 트랙잭션이라고 한다. 

## ACID

: 트랜잭션이 어떤 성질을 가져야 하는가를 정의한것 

#### [1] Atomicity 원자성

: All or Nothing → 모든 작업이 성공하거나, 모두 취소되어야 한다. 

예를 들어, 출금 성공 → 입금 실패가 발생하면 출금도 취소한다. 이것이 Rollback 이며, 반대로 둘 다 성공하면 Commit 한다. 즉, 원자성은 부분 성공을 허용하지 않는다. 

#### [2] Consistency 일관성

: 트랜잭션 전후에 데이터베이스의 모든 규칙이 유지 되어야 한다. 예를 들어, 잔액 ≥ 0 이라는 규칙이 있으면 트랜잭션 후에 -5,000이 되어서는 안된다. consistency가 깨지게 되는 것이다. PRIMARY KEY, UNIQUE, FOREIGN KEY, CHECK, NOT NULL 역시 일관성이 보장 해야 하는 대상이다. 즉, DB가 항상 "유효한 상태"를 유지하는 것이다. 

#### [3] Isolation 독립성

: 동시에 실행되는 트랜잭션이 서로 영향을 주면 안 된다. 예를 들어, 영화관에 남은 좌석이 1개 뿐이고 A와 B가 동시에 예약 버튼을 누른다면 둘 다 성공해버릴 수도 있다. 이는 남는 좌석 -1 이라는 결과가 되며 이것이 동시성 문제이다. Isolation은 이런 문제를 막기 위해 존재한다. 

- **A실행 → 끝 → B실행** 구조가 가장 이상적이지만  Serial Execution 라고 하며 많은 인원이 동시 접속 시 성능이 나빠진다.
- DB는 완벽한 Isolation 대신 적당한 수준의 Isolation Level을 제공한다.

#### [4] Durability 지속성

: 성공적으로 수행된 트랜잭션은 영원히 반영되어야 한다. Commit이 끝났다면 서버가 꺼져도 데이터는 사라지면 안된다. 예를 들어, 시스템 문제로 DB 일관성 체크를 하더라도 이미 수행된 트랜잭션은 유지 되어야 한다. 이를 위해 DB는  WAL, Redo Log, Checkpoint 등을 사용한다. 

## Isolation Level

: Isolation Level은 강할수록 안전하지만 느려진다. 그래서 4단계가 존재한다. 

**① Read Uncommitted**

가장 약한 정책으로, 다른 트랜잭션이 Commit을 안 해도 읽을 수 있다. 
예를 들어, A가 200을 100으로 변경한 후 Commit을 하지 않은 상태에도 B는 100을 읽을 수 있다. 하지만 A가 200으로 Rollback하게 되면 B는 존재하지 않은 데이터를 읽은 것이다. 이것을 Dirty Read 라고 한다. 

**② Read Committed**

Commit된 데이터만 읽어서 Dirty Read를 막는다. 이는 Oracle의 기본이다.
하지만 A가 200을 100으로 변경하는 사이에 200을 읽고, 변경 후에 100을 읽으면 같은 트랜잭션인데 값이 달라지게 된다.  이것이 Non-repeatable Read이다.  

**③ Repeatable Read**

같은 Row는 항상 같은 값을 본다. 이는 MySQL InnoDB의 기본이며 Non-repeatable Read가 해결된다.하지만 

```sql
SELECT *

FROM users

WHERE age >=20
```

의 결과로 10명을 읽었는데, 다른 트랜잭션이 새로운 사용자를 추가한 후 읽으면 11명이 된다. 같은 조건인데 행이 하나 생겨버렸고, 이를 Phantom Read라고 한다.

④ Serializable

가장 강한 정책으로, A끝 → B시작 처럼 동작한다. 하지만 동시성이 가장 낮다.

## Isolation Level만으로 충분할까?

한 개의 재고가 남은 상품이 있다고 가정하자. A와 B가 동시에 상품을 구매한다면, A와 B 둘다 재고 -1을 수행하게 된다. 이는 두 명이 모두 구매에 성공했음을 의미하고 이 문제를 Lost Update라고 한다.  읽는 순간에는 둘다 재고가 1이었어서 성공했던 것이지만 결국 한번의 수정이 사라졌음을 의미하고 그래서 Lost Update인 것이다. 

Isolation Level은 어떤 데이터를 읽을 수 있는가를 정의한다. 실제로 “이 Row는 지금 다른 사람이 수정 중이다.”라고 막아주는 것은 Lock이다. 

Isolation

> **트랜잭션 간의 격리 수준을 정의하는 정책**
> 

Lock

> **그 정책을 구현하고 동시성 충돌을 방지하기 위한 구체적인 메커니즘**
> 

## Lock의 종류

- **Shared Lock (S Lock)**
    
    읽기 락으로, 여러 사람이 동시에 읽을 수 있다. 하지만 누군가 수정하려고 하면 기다려야 한다. 
    
- **Exclusive Lock (X Lock)**
    
    쓰기 락으로, A가 수정 중이라면 B는 수정할 수 없고 C는 읽을 수 있다. 
    

이 Lock을 언제 거는가에 따라 비관적 락과 낙관적 락으로 나뉜다.

#### 비관적 락(Pessimistic Lock)

: "충돌이 일어날 것이다.” 라고 가정하고 처음부터 잠가버린다. 

예를 들어, 영화관 좌석이 하나 남은 상태에서 A의 이 순간

```sql
SELECT *

FROM seat

WHERE id = 1

FOR UPDATE;
```

좌석이 잠긴다. 그 뒤 B도 실행하면 

```sql
SELECT ...

FOR UPDATE
```

즉시 실패하는 것이 아니라 기다린다. 

**A 잠금 → 수정 → commit → Lock 해제 → B 실행**

장점: 충돌이 발생하지 않는다. 재고/좌석/결제/계좌이체 등 동시에 수정되면 안 되는 곳에서 많이 사용한다. 

단점: 성능이 떨어진다. 100명이 구매하려 한다면 99명이 대기해야한다. 또한, Deadlock이 발생할 수 있다.

**Deadlock** 

- A가 상품 Lock을 잡고, B가 주문 Lock을 잡았다.
- A는 주문 Lock이 필요하고, B는 상품 Lock이 필요하다.
- 둘 다 영원히 기다린다 → Deadlock
- 일정 시간이 지나면 DB에서는 한쪽을 강제로 Rollback한다.

**주로 비관적 락을 사용하는 상황**

- 은행 계좌 이체
- 콘서트 티켓
- 영화관 좌석
- 재고 차감
- 포인트 차감

#### 낙관적 락(Optimistic Lock)

: "충돌은 거의 없을 것이다.”라고 가정해서 잠그지 않는다. Lock을 걸지 않는 대신 수정할 때 다른 사람이 먼저 수정했는지만 확인한다. 

낙관적 락은 진짜 Lock을 거의 걸지 않는다. DB를 잠그는 것이 아니라 Version을 비교해서 충돌을 감지하는 방식이다. 그래서 엄밀히 말하면 "Lock" 보다는 **충돌 감지(Conflict Detection)** 에 가깝다. 다만 동시성 제어 방법이기 때문에 관습적으로 Optimistic Lock이라고 부른다.

장점: 빠르다. 아무도 기다리지 않는다.

단점:  충돌이 발생하면 다시 해야 한다. 즉, 재시도 로직이 필요하다. 

**주로 낙관적 락을 사용하는 상황**

- 회원 정보 수정
- 게시글 수정
- 상품 정보 수정
- 관리자 페이지

| 구분 | 비관적 락 | 낙관적 락 |
| --- | --- | --- |
| 가정 | 충돌이 자주 발생한다 | 충돌이 거의 없다 |
| Lock | 실제 DB Lock 사용 | Version 비교 |
| 대기 | 다른 트랜잭션이 기다림 | 기다리지 않음 |
| 성능 | 상대적으로 느림 | 빠름 |
| 충돌 발생 | 애초에 막음 | 발생 후 감지 |
