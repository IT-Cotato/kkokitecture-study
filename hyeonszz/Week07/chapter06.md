# 가독성

## 6장. 키-값 저장소

### 1. 키-값 저장소

키-값 저장소는 고유 식별자(Key)와 데이터(Value) 쌍으로 이루어진 비관계형 데이터베이스이다. 

- put(key, value): 키-값 쌍을 저장소에 저장한다
- get(key): 인자로 주어진 키에 매달린 값을 꺼낸다

| **목표** | **전략** | **장점** | **단점** |
| --- | --- | --- | --- |
| **읽기 최적화** | 데이터 미리 정리  | 조회 속도 매우 빠름 | 쓰기 속도 저하, 메모리 사용량 증가 |
| **쓰기 최적화** | 정리 하지 않고 저장 | 쓰기 처리량 극대화 | 읽기 시 검색 비용 발생 |
| **메모리 절약** | 데이터 가공/압축 저장 | 비용 효율성 | 계산량 증가로 인한 성능 저하 |

**읽기 속도를 빠르게 하고 싶다**

→ 데이터를 미리 정리해서 저장 (예: 캐시, 인덱스)

- 조회는 빠르지만
    - 저장할 때 더 많은 작업이 필요해서 쓰기 속도가 느려진다
    - 메모리를 더 많이 사용한다

**쓰기를 빠르게 하고 싶다** 

→ 정리 하지 않고 막 저장

- 쓰기는 빠르지만
    - 나중에 읽을 때 읽기 속도가 느려진다
    - 검색 비용이 증가한다

**메모리를 아끼고 싶다**

→ 데이터를 최소한으로 저장

- 메모리는 아낄 수 있지만
    - 계산이 많이 필요해서 읽기가 느려진다
    - 한 번 가공해서 저장해야 하기 때문에 쓰기가 복잡해질 수 있다

### 2. CAP 정리

분산 시스템은 다음 세 가지 속성 중 두 가지만 선택할 수 있다는 이론이다
1. **일관성 (Consistency)**: 모든 클라이언트가 어떤 노드에 접속하든 같은 데이터를 봄
2. **가용성 (Availability)**: 일부 노드 장애 시에도 항상 응답을 받음
3. **파티션 감내 (Partition Tolerance)**: 네트워크 파티션 상황에서도 시스템이 동작함. 

- 네트워크 파티션(Network Partition): 서버들끼리 서로 통신이 안 되는 상태로 쪼개지는 것 → 서버가 죽은 게 아니라, 연결만 끊긴 것
- **이상적 환경**: 네트워크가 파티션 되는 상황은 일어나지 않을 것
- **실제**: 분산 시스템에서 네트워크 파티션은 피할 수 없으므로, 보통 **CP** 또는 **AP** 시스템 중 하나를 요구사항에 맞게 설계한다

#### CAP 정리에 따른 시스템 설계 선택

네트워크 파티션이 발생했을 때, 분산 시스템은 **일관성(C)**과 **가용성(A)** 중 무엇을 우선하느냐에 따라 시스템의 성격이 결정된다

1. **CP시스템 (가용성 대신 일관성 선택)**
    
    데이터의 **정확성과 무결성**이 무엇보다 중요한 경우
    
- **동작 원리**: 서버 간 통신 장애로 데이터 불일치 위험이 생기면, 시스템은 데이터 수정을 막기 위해 쓰기 연산을 중단한다
- **특징**: 가용성을 희생하는 대신 모든 사용자가 항상 최신 데이터를 보게 합니다.
- **사례:** 은행권 시스템
    - 온라인 뱅킹에서 계좌 잔액이 노드마다 다르게 보인다면 심각한 금융 사고로 이어진다
    - 따라서 네트워크 장애 시 일관성이 보장되지 않는다면, 시스템은 오류를 반환하며 서비스를 일시 중단하는 쪽을 택한다

2. **AP시스템 (일관성 대신 가용성 선택)**

데이터가 조금 낡았더라도 **서비스가 끊기지 않는 것**이 더 중요한 경우

- **동작 원리**: 일부 노드와 연결이 끊겨도 남은 노드에서 계속해서 읽기 및 쓰기 연산을 허용한다
- **특징**: 일관성을 일시적으로 포기하는 대신 서비스의 연속성을 보장한다
- **장애 복구**: 파티션 문제가 해결된 후, 동기화 과정을 통해 뒤처진 노드에 최신 데이터를 전달하여 최종적인 일관성(Eventual Consistency)을 맞춘다
- **사례:** SNS 피드
    - 친구의 새 게시글이 몇 초 늦게 보이더라도 인스타그램이나 페이스북 서비스 자체가 멈추지 않는 것이 사용자 경험 측면에서 더 중요하다

**결론: 설계 가이드라인**
분산 키-값 저장소를 설계할 때는 비즈니스 요구사항에 맞춰 CAP 우선순위를 설정해야한다. 
• **Strong Consistency (CP)**: 데이터의 정확성이 생명인 금융, 결제, 재고 관리 시스템.
• **High Availability (AP)**: 끊김 없는 서비스 제공이 중요한 SNS, 추천 시스템, 로그 수집기.

⇒ 실세계의 분산 시스템은 네트워크 파티션을 피할 수 없기 때문에, 사실상 설계의 핵심은 "장애 상황(P)에서 C와 A 중 무엇을 선택할 것인가"에 달려 있다

### 3. 시스템 컴포넌트

#### **[데이터 파티션]**

- **안정 해시 (Consistent Hashing)**: 데이터를 여러 서버에 균등하게 분산하며, 노드 추가/삭제 시 데이터 이동을 최소화한다
- **가상 노드 (Virtual Nodes)**: 서버 성능에 따라 가상 노드 수를 조절하여 부하를 최적화한다.

#### **[데이터 다중화]**

- **방법**: 해시 링 위에서 시계 방향으로 순회하며 첫 N개의 물리 서버에 사본을 저장한다.
- **안정성**: 데이터 센터 단위의 장애에 대비하여 사본을 지리적으로 분산된 센터에 보관한다
- **주의할 점**: 가상 노드를 사용하면 선택한 N개의 노드가 대응될 실제 물리 서버의 개수가 N보다 작아질 수 있다. 따라서 노드를 선택할 때 같은 물리 서버를 중복 선택하지 않도록 해야 한다.

#### **[일관성 관리]**

여러 노드에 다중화된 데이터는 적절히 동기화 되어야 한다. Quorum Consensus 프로토콜을 사용하면 읽기/쓰기 연산 모두에 일관성을 보장할 수 있다. 

- **정족수 합의 (Quorum Consensus)**
    - N: 복제본 수
    - W: 쓰기 성공에 필요한 응답 수
    - R: 읽기 성공에 필요한 응답 수
    - **R+W > N**: 강한 일관성(Strong Consistency) 보장
- **결과적 일관성 (Eventual Consistency)**: 가용성을 위해 쓰기 시 모든 복제본을 기다리지 않고, 나중에 동기화하는 모델

---

정족수란 분산 시스템에서 연산(읽기/쓰기)의 성공을 인정하기 위해 응답해야 하는 **최소한의 서버 수**를 의미한다

| **조건** | **특징** | **활용 케이스** |
| --- | --- | --- |
| **R = 1, W = N** | 읽기 속도 극대화 | 읽기 요청이 압도적으로 많은 서비스 |
| **R = N, W = 1** | 쓰기 속도 극대화 | 로그 기록 등 쓰기 가용성이 중요한 서비스 |
| **R + W > N** | **강한 일관성(Strong Consistency)** 보장 | 최신 데이터를 반드시 읽어야 하는 경우 |
| **R + W ≤ N** | 일관성 약화, 속도 향상 | 결과적 일관성(Eventual Consistency) 허용 시 |

#### [일관성 모델]

: 키-값 저장소를 설계할 때 고려해야 할 중요한 요소로, 데이터 일관성의 수준을 결정하며 종류가 다양하다

- 강한 일관성 (strong consistency) : 모든 읽기 연산은 가장 최근에 갱신된 결과를 반환한다
- 약한 일관성 (weak consistency) : 읽기 연산은 가장 최근에 갱신된 결과를 반환하지 못할 수도 있다
- 결과적 일관성 (eventual consistency): 약한 일관성의 한 형태로, 갱신 결과가 결국에는 모든 사본에 반영되는 모델

## 4. 장애 처리 및 불일치 해소

#### [데이터 버저닝]

비 일관성 해소 기법: 데이터 버저닝

- 데이터를 다중화할 수록 일관성이 깨질 가능성이 높아진다
- **벡터 시계 (Vector Clock)**: 데이터 충돌을 감지하기 위해 **[서버, 버전]** 순서쌍을 데이터에 부여한다. 이를 통해 어떤 데이터가 선행/후행 버전인지 판별한다.

**장애 감지 및 해소**

1. **가십 프로토콜 (Gossip Protocol)**: 분산된 노드들이 서로의 상태 정보를 주기적으로 교환하여 효율적으로 장애를 감지한다. 
2. **느슨한 정족수 (Sloppy Quorum)**: 장애 노드 대신 건강한 노드를 선택해 가용성을 유지한다.
3. **단서 후 임시 위탁 (Hinted Handoff)**: 임시 노드가 데이터를 맡아 처리하다가 원래 노드가 복구되면 데이터를 돌려준다. 
4. **머클 트리 (Merkle Tree)**: 영구적 장애 시, 해시 트리를 비교하여 데이터 불일치 구간만 빠르게 동기화한다. (반-엔트로피 프로토콜).

### **[장애 처리 전략]**

**<일시적 장애>**
서버가 잠시 다운되었을 때 시스템 중단을 방지하기 위한 전략

**엄격한 정족수 vs 느슨한 정족수**
• **엄격한 정족수 (Strict Quorum)**: 반드시 정해진 $N$개의 서버 중 $R, W$개를 채워야 함. 서버 장애 시 즉시 서비스가 제한됨.
• **느슨한 정족수 (Sloppy Quorum)**: 장애가 발생하면 가용 노드 중 아무나 선택해 정족수를 채움. 가용성을 우선시하는 방식.

**단서 후 임시 위탁 (Hinted Handoff)**
1. 장애가 발생한 서버 A 대신 서버 B가 임시로 쓰기 요청을 처리
2. 서버 B는 이 데이터가 원래 A의 것임을 나타내는 단서를 남겨둔다
3. 서버 A가 복구되면, B는 보관 중이던 변경 사항을 A에게 일괄 전달하여 데이터를 동기화한다.

**<영구적 장애>**
서버의 데이터가 영구적으로 손실되었거나 장기간 불일치가 발생했을 때의 해결책이다.

- **반-엔트로피(Anti-entropy) 프로토콜**
사본들을 주기적으로 비교하여 최신 상태로 동기화하는 과정이다. 이때 전체 데이터를 대조하면 네트워크 부하가 크기 때문에 **머클 트리**를 사용한다
- **머클 트리 (Merkle Tree / Hash Tree)**
• **구조**: 각 노드에 자식 노드들의 해시값을 합친 해시를 저장하는 트리 구조
• **장점:**
    - **효율적 비교**: 루트 해시값만 비교하면 데이터 일치 여부를 즉시 알 수 있다
    - **부분 동기화**: 루트가 다를 경우, 아래로 내려가며 다른 해시값을 가진 노드만 찾아내어 해당 데이터만 전송하므로 네트워크 트래픽을 획기적으로 줄인다

⇒ 정족수로 시스템의 가용성과 일관성 사이의 균형을 조절하고, **임시 위탁**으로 짧은 장애를 버티며, **머클 트리**를 이용한 반-엔트로피로 영구적인 데이터 불일치를 해결한다

## 5. 시스템 아키텍처 다이어그램

- **무상태 중재자**: 클라이언트의 요청을 받아 적절한 노드로 라우팅한다
- **완전 분산**: 모든 노드가 동등한 책임을 지며 단일 장애 지점(SPOF)이 없다
- **자동 확장**: 안정 해시 덕분에 노드를 자유롭게 증설하거나 제거할 수 있다

추가 정리

가십 프로토콜 (Gossip Protocol)

→ 이름 그대로 소문이 퍼지는 방식

1. **무작위 통신**: 각 노드는 주기적으로 무작위로 선정된 몇 개의 노드에게 자신의 상태 정보와 자기가 알고 있는 다른 노드들의 정보를 보낸다
2. **정보 업데이트**: 정보를 받은 노드는 자기가 가진 정보보다 더 최신 정보가 있으면 자신의 정보를 업데이트 한다
3. **지수적 전파**: 노드가 1,000개일 때, 한 노드가 장애가 발생했다는 소식은 몇 번의 통신만 거치면 모든 노드에게 전파된다

사용이유: 노드가 수천 대라면 한 대의 서버가 모든 노드의 상태를 확인 하는 건 불가능에 가깝다. 하지만 가십 프로토콜을 쓰면 중앙 관리자 없이도 모두가 서로의 상태를 알 수 있다
