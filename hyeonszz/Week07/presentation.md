# DynamoDB

Amazon DynamoDB는 AWS에서 제공하는 완전 관리형 NoSQL 데이터베이스 서비스이다. 어떤 규모에서도 10밀리초 미만의 지연 시간을 제공하도록 설계되어 있어, 전 세계적으로 대규모 트래픽을 처리하는 애플리케이션에서 표준처럼 사용된다.

## 1. 주요 특징

- Serverless
    - 서버를 직접 관리하거나 패치를 설치할 필요가 없다. 용량 모드에 따라 트래픽에 맞춰 자동으로 스택을 확장한다.
- Key-Value
    - JSON 유사 구조의 유연한 데이터 모델을 지원하여 스키마 변경이 자유롭다
- 일관된 성능
    - 데이터 양이 10GB든 100TB든 상관없이 일정한 응답 속도를 유지한다
- 고가용성
    - 데이터가 최소 3개의 가용 영역에 자동으로 복제되어 데이터 손실 위험이 매우 낮다

---

## 2. 데이터 구조

DynamoDB는 기존 RDBMS와는 다른 구조를 가지고 있다.

- Table: 데이터의 집합체
- Item: RDBMS의 Row와 유사하며, 각 아이템은 고유하게 식별될 수 있다
- Attribute: 아이템 내의 개별 데이터 요소로, RDBMS의 Column과 비슷하지만 아이템마다 서로 다른 속성을 가질 수 있다

핵심: 기본 키 (Primary Key)

DynamoDB는 데이터를 찾기 위해 두 가지 방식의 기본 키를 사용한다

1. 파티션 키 (Partition Key - PK)
    - 데이터가 어떤 물리적 파티션에 저장될지 결정한다
    - 내부 해시 함수를 통해 데이터를 고르게 분산시킨다
2. 정렬 키 (Sort Key - SK)
    - 동일한 파티션 키 내에서 데이터를 정렬하는 기준이다
    - PK와 SK를 조합하면 복합 기본 키가 되어 일대다 관계를 효율적으로 쿼리할 수 있다

---

## 3. 읽기/쓰기 용량 모드

비용과 성능 관리를 위해 아래와 같이 2가지 모드를 선택할 수 있다.

| **구분** | **온디맨드 (On-Demand)** | **예약 용량 (Provisioned)** |
| --- | --- | --- |
| **특징** | 트래픽에 따라 자동으로 확장 | 읽기/쓰기 용량을 직접 지정 |
| **장점** | 관리가 편하고 예측 불가능한 트래픽에 유리 | 트래픽이 일정할 때 비용 효율적임 |
| **과금** | 요청당 비용 지불 | 설정한 용량당 시간별 비용 지불 |

---

## 4. 고급 기능

- LSI & GSI (Secondary Indexes): 기본 키 외에 다른 속성으로 데이터를 조회하고 싶을 때 사용한다.
    - 특히 GSI(Global Secondary Index)는 파티션 키 자체를 새로 지정할 수 있어서 매우 강력하다
- DynamoDB Streams: 테이블의 데이터 변경 이벤트를 실시간으로 포착하여 Lambda 함수 등을 실행할 수 있게 해준다
- TTL (Time To Live): 특정 시간이 지나면 데이터를 자동으로 삭제하도록 설정할 수 있어, 세션 관리나 임시 로그 저장에 유용한다

언제 사용하면 좋을까?

- 사용자가 급격히 늘어날 가능성이 있는 서비스 (모바일 게임, 커머스 등)
- 일정한 성능(저지연)이 보장되어야 하는 실시간 애플리케이션
- 장비 관리보다는 비즈니스 로직 개발에 집중하고 싶은 프로젝트
- 분산 시스템에서 확장성 있는 백엔드 아키텍처를 구축할 때

---

## 5. 데이터 접근 패턴 (Data Access Pattern)

DynamoDB는 데이터를 저장한 이후에 조회 방식을 고민하는 것이 아니라, **어떤 방식으로 데이터를 조회할지 먼저 정의한 뒤 테이블을 설계하는 구조**를 가진다. 이는 기존 RDBMS와 가장 큰 차이점이다.

- GetItem
기본 키를 이용한 단건 조회
- Query
특정 파티션 키를 기준으로 여러 데이터를 조회하며, 정렬 키를 활용해 범위 검색이 가능하다
- Scan
테이블 전체를 조회하는 방식으로, 성능과 비용 측면에서 비효율적이므로 사용을 지양해야 한다

핵심적으로 DynamoDB는 Query 중심으로 설계해야 하며, Scan 사용을 최소화하는 것이 중요하다.

---

## 6. 일관성 모델 (Consistency Model)

DynamoDB는 두 가지 읽기 일관성 옵션을 제공한다.

- Eventually Consistent Read
기본 옵션으로, 데이터 변경 후 일정 시간이 지나면 반영된다. 비용이 저렴하고 성능이 효율적이다
- Strongly Consistent Read
항상 최신 데이터를 보장하지만, 비용이 더 높고 성능 부담이 존재한다

일반적인 서비스에서는 Eventually Consistent Read로 충분하며, 금융이나 결제와 같이 강한 정합성이 필요한 경우에만 Strongly Consistent Read를 사용한다.

---

## 7. 파티셔닝과 성능

DynamoDB의 성능은 파티션 키 설계에 크게 의존한다.

- 데이터는 여러 파티션에 분산 저장된다
- 파티션 키 값이 특정 값에 집중되면 일부 파티션에 과부하가 발생할 수 있다

이러한 문제를 Hot Partition이라고 하며, 이를 방지하기 위해서는 다음과 같은 설계가 필요하다.

- 파티션 키 값이 균등하게 분포되도록 설계
- 특정 키에 트래픽이 집중되지 않도록 구성

적절한 파티션 키 설계는 성능과 비용 최적화의 핵심 요소이다.

---

## 8. 트랜잭션

DynamoDB는 트랜잭션을 지원하여 여러 작업을 하나의 단위로 처리할 수 있다.

- TransactWriteItems
- TransactGetItems

이를 통해 여러 아이템 또는 여러 테이블에 대한 작업을 원자적으로 수행할 수 있다.

다만 RDBMS에 비해 기능 제약이 있으며, 트랜잭션 사용 시 성능과 비용이 증가할 수 있다.

---

## 9. 보조 인덱스 (Secondary Indexes 심화)

기본 키 외의 속성으로 데이터를 조회하기 위해 보조 인덱스를 사용한다.

- LSI (Local Secondary Index)
    - 동일한 파티션 키를 유지하면서 정렬 키만 변경
    - 테이블 생성 시에만 정의 가능
- GSI (Global Secondary Index)
    - 파티션 키와 정렬 키를 새롭게 정의 가능
    - 테이블 생성 이후에도 추가 가능

LSI는 동일한 데이터 그룹 내에서 다른 정렬 기준을 제공하고, GSI는 완전히 새로운 조회 패턴을 지원한다.

---

## 10. 비용 최적화

DynamoDB는 사용 방식에 따라 비용 차이가 크게 발생할 수 있다.

효율적인 비용 관리를 위해 다음과 같은 전략이 필요하다.

- Scan 대신 Query 사용
- 필요한 속성만 조회하여 데이터 전송량 최소화
- On-Demand와 Provisioned 모드를 상황에 맞게 선택
- TTL을 활용하여 불필요한 데이터 자동 삭제

---

## 11. AWS 서비스와의 연계

DynamoDB는 AWS의 다양한 서비스와 결합하여 사용되는 경우가 많다.

- API Gateway + DynamoDB
REST API 기반 백엔드 구성
- Lambda + DynamoDB
서버리스 아키텍처 구현
- DynamoDB Streams + Lambda
데이터 변경 이벤트 기반 처리

이러한 조합을 통해 완전한 서버리스 시스템을 구축할 수 있다.

---

## 12. 설계 패턴

### Single Table Design

최근 DynamoDB 설계에서 자주 사용되는 방식이다.

- 하나의 테이블에 여러 엔티티를 함께 저장
- 파티션 키와 정렬 키를 조합하여 관계를 표현

예시

- PK: USER#123
- SK: ORDER#456

이 방식은 JOIN 없이 관계를 표현할 수 있으며, 성능을 극대화할 수 있다. 다만 설계 난이도가 높은 편이다.

---

## 13. 한계 및 주의사항

DynamoDB는 다음과 같은 한계를 가진다.

- JOIN 연산 불가능
- 복잡한 쿼리 처리 어려움
- 데이터 모델링 난이도가 높음
- 설계가 잘못될 경우 성능 및 비용 문제 발생

따라서 초기 설계 단계에서 접근 패턴을 명확히 정의하는 것이 매우 중요하다.

---

## 14. 정리

DynamoDB는 Serverless 기반의 NoSQL 데이터베이스로, 자동 확장성과 낮은 지연 시간을 통해 대규모 트래픽 환경에서도 안정적인 성능을 제공한다.

반면 관계형 데이터 처리에는 적합하지 않으며, 데이터 접근 패턴 중심의 설계가 필수적이다.

따라서 DynamoDB는 확장성과 속도가 중요한 서비스에서 효과적인 선택이 될 수 있다.

### MongoDB vs DynamoDB

직접 인프라를 세밀하게 제어 → **MongoDB**

인프라 관리를 완전히 맡기고 성능에만 집중 → **DynamoDB**

데이터베이스 비교

| **구분** | **RDBMS (MySQL, PostgreSQL)** | **MongoDB (NoSQL)** | **DynamoDB (NoSQL)** |
| --- | --- | --- | --- |
| **모델 구조** | 표(Table) 형태, 엄격한 스키마 | 문서(Document) 형태, 유연함 | 키-값(Key-Value) 형태 |
| **핵심 강점** | **데이터 정합성**, 복잡한 Join | **개발 유연성**, 복잡한 객체 저장 | **무한 확장성**, 운영 자동화 |
| **운영 방식** | 서버 관리 필요 (RDS 등 사용) | 설치형 또는 관리형(Atlas) | **Serverless** (관리 필요 없음) |
| **확장성** | 수직 확장(사양 업그레이드) 중심 | 수평 확장(샤딩) 가능 | **자동 수평 확장** (클릭 몇 번) |
| **트랜잭션** | 매우 강력함 (금융, 회계 최적) | 지원함 (버전 4.0 이후) | 지원하지만 제약 사항 있음 |

“데이터 관계가 복잡하다”

→ 단순히 양이 많은 것이 아니라, 정보 간의 연결 고리를 의미한다

- 엔티티 간 연쇄 반응: 사원 한 명을 삭제할 때 급여, 근태, 프로젝트 할당 기록이 모두 영향을 받는 구조
- 다차원 조회: A 부서의 B 과장이 승인한 C 프로젝트의 지난달 자재비 → 하나를 알아내기 위해 4~5개의 테이블을 엮어야 하는 경우
- 재귀적 구조: 상위 부서 아래 하위 부서가 무한히 연결되는 조직도
