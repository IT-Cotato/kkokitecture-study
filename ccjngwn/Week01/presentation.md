# Netflix Active-Active for Multi-Regional Resiliency

> 원문: [Netflix TechBlog - Active-Active for Multi-Regional Resiliency](https://netflixtechblog.com/active-active-for-multi-regional-resiliency-c47719f6685b)

---

# 1. 배경

## 서비스의 실패율

일반적으로 조직이 직면하는 실패율은 **운영 배치 규모**와 **변화 속도**에 따라 달라진다.

- 공식: `실패율 = 규모 × 변화 속도`
- 규모 ↑ → 여러 하드웨어를 관리해야 함 → 하드웨어 고장 확률 ↑
- 속도 ↑ → 변경 사항을 배포할 때마다 버그 리스크가 생김 → 소프트웨어 고장 확률 ↑
- **결론**: 대규모 + 고속 추구 → 장애는 피할 수 없다

## 왜 Region 단위 대응이 필요했나

- 넷플릭스의 내부 가용성 목표는 **99.99%** 로, 서비스가 중단될 시간이 매우 적다.
- 여러 인스턴스와 AZ에 서비스를 배포하는 것만으로는 부족했다.
- Region 인프라 전면 장애는 드물지만, **빠른 변화 속도로 인해 Region 내 주요 서비스가 중단**될 수 있다.
- 이를 위해 **격리(Isolation)** 와 **중복(Redundancy)** 의 원칙을 활용한다.

| 원칙     | 설명                                                     | 예시                                         |
| -------- | -------------------------------------------------------- | -------------------------------------------- |
| **격리** | 한 Region의 장애가 다른 Region에 영향을 주지 않아야 한다 | US-East-1이 마비되어도 US-West-2는 정상 동작 |
| **중복** | 같은 것을 여러 곳에 배포한다                             | 리전을 2개 운영하여 장애 시 대안 확보        |

### 인스턴스 vs 가용성 존(AZ) vs 리전

```
Region (리전)
└── Availability Zone / AZ (가용성 존)
    └── Instance (인스턴스)
```

| 단위               | 설명                                 | 예시                                      |
| ------------------ | ------------------------------------ | ----------------------------------------- |
| **인스턴스**       | 서버 1대 (가상 머신)                 | EC2 서버 1개                              |
| **AZ (가용성 존)** | 같은 Region 안의 독립적인 데이터센터 | ap-northeast-2**a**, 2**b**, 2**c**       |
| **Region**         | 지리적으로 떨어진 지역               | 서울(ap-northeast-2), 버지니아(us-east-1) |

- **인스턴스 여러 개**: 서버 1대가 죽어도 다른 서버가 처리 → 단일 서버 장애 대응
- **AZ 여러 개**: 데이터센터 1곳에 정전/화재가 나도 다른 데이터센터가 살아있음 → 단일 데이터센터 장애 대응
- **Region 여러 개**: 서울 Region 전체가 문제가 생겨도 다른 Region이 살아있음 → Region 전체 장애 대응

# 2. Active-Active란?

> **Active-Passive**: 한 Region만 트래픽을 받고 나머지는 대기
>
> **Active-Active**: 모든 Region이 동시에 실제 트래픽을 처리

- Active-Active 솔루션은 사용자 요청 경로에 있는 모든 서비스를 여러 AWS Region에 걸쳐 배포한다.
- 넷플릭스의 경우 버지니아(US-East-1)와 오리건(US-West-2) 두 Region을 사용한다.

## 핵심 요구 사항

**1. 서비스는 Stateless여야 한다**

- 모든 데이터/상태 복제는 데이터 계층에서 처리되어야 한다.
- Stateful 서버라면? → 사용자가 US-East 서버 메모리에 "23분 시청 중"이라는 상태를 저장하고 있을 때, US-East 장애로 US-West로 failover되면 US-West 서버 메모리엔 아무것도 없다. → **격리 원칙 위반**

**2. 유저 호출 경로에 Cross-Regional 호출이 없어야 한다**

- US-East에서 처리 중에 US-West의 S3를 호출하는 상황이라면, US-West가 느려질 때 US-East도 같이 죽어버린다. → **격리 원칙 위반**

**3. Region 내 모든 Resource에 접근할 수 있어야 한다**

- Cross-Regional 호출이 없어야 하므로, 각 Region은 자기 Region 안의 자원만 써야 한다.
- 따라서 S3 버킷에 데이터를 올리는 애플리케이션은 **모든 Region의 S3 버킷에 동일한 데이터를 게시**해야 한다.
- 단, 이 복제는 유저 요청 경로가 아닌 **백그라운드 비동기 복제**로 이루어지므로 격리 원칙에 위배되지 않는다.

# 3. 핵심 기술 구성요소

정상 운영 상태에서는 사용자가 가장 가까운 AWS Region으로 GeoDNS 라우팅되며, 대략 **50:50** 비율로 나뉜다. Region 전체에 심각한 장애가 발생할 경우, GeoDNS를 무시하고 모든 트래픽을 정상 Region으로 유도한다.

이를 위한 기술적 도전 과제:

- 트래픽을 올바른 Region으로 유도하는 효과적인 도구
- Thundering Herd를 처리하기 위한 Traffic Shaping과 Load Shedding
- 상태/데이터 비동기 교차 지역 복제

---

## DNS (Denominator, UltraDNS, Route53)

트래픽을 올바른 Region으로 유도하는 도구 조합이다.

**UltraDNS**: 유저 위치에 따라 다른 Region으로 라우팅해주는 GeoDNS

- 지연 기반 라우팅(Latency-based Routing)은 트래픽이 예고 없이 왔다갔다해 Thundering Herd를 유발할 수 있어 사용하지 않았다.

**Route53**: UltraDNS와 ELB 사이에 위치하여 빠른 트래픽 전환을 담당

- CNAME 한 줄만 바꾸면 트래픽이 즉시 다른 Region으로 이동한다.

```
[정상 상태]
유저 → UltraDNS (위치 기반 라우팅)
     → Route53 ("US-East ELB로 가세요")
     → US-East 서버

[장애 발생 시 - Route53 CNAME만 변경]
유저 → UltraDNS (그대로)
     → Route53 ("US-West ELB로 가세요" 로 변경)
     → US-West 서버
```

**Denominator**: UltraDNS와 Route53을 하나의 도구로 통합 제어하는 라이브러리

- 두 서비스의 API가 달라 각각 제어하면 복잡해지는 문제를 해결한다.

---

## Zuul (Traffic Shaping, Load Shedding)

Thundering Herd Events를 처리하기 위한 트래픽 제어 도구다.

- **Thundering Herd**: 갑자기 엄청난 트래픽이 한꺼번에 몰려오는 현상 (ex. Failover 직후)
- **Traffic Shaping**: 트래픽이 한꺼번에 안 들어오도록 속도를 조절
- **Load Shedding**: 감당할 수 없는 요청은 에러로 돌려보내 서버 보호

### 잘못 라우팅된 요청 처리

- 사용자 요청이 Geo Directional 기록과 일치하지 않으면 **잘못 라우팅된 요청**으로 정의한다.
- 단일 사용자 세션이 여러 Region에 걸치면 데이터 일관성이 깨지기 때문에 반드시 처리해야 한다.
- 처리 방법은 두 가지다.

| 방법             | 설명                                                  |
| ---------------- | ----------------------------------------------------- |
| **Isthmus 모드** | Zuul이 직접 올바른 Region으로 요청을 전달             |
| **Redirect**     | 클라이언트에게 올바른 Region으로 다시 요청하도록 안내 |

### Failover 모드

- Region을 Failover 모드로 선언하면, 잘못 라우팅된 요청을 다른 Region으로 보내지 않고 **로컬에서 처리**한다.
- **올바른 Region 자체가 죽었을 때** 사용한다. (다른 Region으로 보내봤자 거기도 죽었으므로)

### Traffic Shaping + Load Shedding

- 최대 트래픽 레벨을 정의하여 초과 요청은 자동으로 차단한다.
- 서비스가 아직 확장 중이거나, 캐시가 Cold 상태일 때 DB 과부하를 방지하기 위함이다.

## 데이터 복제 (Cassandra, EvCache)

상태/데이터 비동기 교차 지역 복제를 담당한다.

### Cassandra

**핵심 특징**: 다방향 + 다중 데이터센터 비동기 복제

- 어느 Region에서 써도 다른 Region으로 비동기 복제된다.
- 복제 완료를 기다리지 않고 즉시 응답하므로 격리 원칙을 유지한다.

**Consistency Level**: 몇 개의 노드에서 확인을 받아야 성공으로 볼 건지를 정하는 것

| Level               | 설명                                                 |
| ------------------- | ---------------------------------------------------- |
| **CL_ONE**          | 노드 1개에서만 확인받으면 성공 (빠름)                |
| **CL_LOCAL_QUORUM** | 로컬 Region의 과반수 노드에서 확인받으면 성공 (안전) |

**Active-Active 이전**: 데이터를 쓴 Region에서 바로 읽으니 복제 지연이 문제없었다.

**Active-Active 이후**: Failover 시 다른 Region에서 읽어야 하므로 복제 속도가 중요해졌다.

- 실험: US-East에 100만 건 쓰기 → **500ms 후** US-West에서 읽기 → 데이터 손실 없음

### EvCache

Cassandra 앞에 Memcached 캐시 레이어를 배치하여 **1ms 이내 응답**을 목표로 한다.

**문제**: Cassandra는 비동기 복제로 Region 간 동기화가 되지만, Memcached는 복제 기능이 없어 Region 간 캐시 불일치가 발생한다.

**해결**: EvCache에 **원격 캐시 무효화** 기능을 추가했다.

```
US-East에서 데이터 업데이트
         ↓
EvCache → SQS를 통해 US-West에 "해당 캐시 삭제" 메시지 전송
         ↓
US-West Memcached에서 해당 캐시 삭제
         ↓
다음 요청 시 Cassandra에서 최신 데이터 읽어서 캐시 갱신
```

## 배포 자동화 (Mimir)

Region이 늘어날수록 배포 환경이 배로 늘어난다.

```
초기:  US-East (테스트 + 프로덕션) = 2개
EU 추가: + EU-West (테스트 + 프로덕션) = 4개
Active-Active: + US-West (테스트 + 프로덕션) = 6개
```

코드 하나 바꿀 때마다 6번 수동 배포해야 하는 문제가 생겼다.

**Mimir**: 다지역 배포 자동화 워크플로우 도구

- 배포 목표와 규칙을 정의하면 단계적으로 자동 배포한다.
- **카나리아 배포**: 전체 배포 전에 일부에만 먼저 배포해서 문제 확인
- **자동 롤백**: 배포 후 문제가 감지되면 자동으로 이전 버전으로 되돌림
- Region 간 업데이트 사이에 여러 시간을 대기하여 전 세계 배포 전에 문제를 조기 발견한다.

# 4. 검증 - Simian Army

> 일부러 장애를 내서 시스템의 약점을 찾고, 반복할수록 더 강해지는 **Anti-fragile** 구조를 만든다.

## Chaos Gorilla

- **범위**: AZ 전체 장애
- **목적**: 남은 AZ의 서비스가 품질 저하 없이 사용자 요청을 계속 처리할 수 있는지 확인
- Active-Active 도입 후에도 계속 실행하여 변경된 아키텍처의 내성을 검증했다.

## Split-Brain

- **범위**: Region 간 네트워크 연결 완전 차단
- **목적**: 연결이 끊긴 상태에서도 각 Region이 독립적으로 정상 동작하는지 검증 (격리 원칙)
- 복제 메시지는 큐에 쌓이다가 연결 복구 후 처리된다.
- Active-Active 프로젝트 기간 동안 여러 번 수행하며 많은 문제를 발견하고 해결했다.

## Chaos Kong

- **범위**: Region 전체 장애
- **목적**: US-West 하나만으로 넷플릭스 전체 트래픽을 감당할 수 있는지 검증
- 실제 장애와 달리 트래픽을 **천천히 단계적으로** 이동시켜 유저 경험 손상 없이 진행했다.
- 24시간 동안 US-West만으로 운영 후 문제 없음 확인 → 50:50 상태로 복귀

|               | Chaos Gorilla | Split-Brain    | Chaos Kong      |
| ------------- | ------------- | -------------- | --------------- |
| **장애 범위** | AZ 1개        | Region 간 연결 | Region 1개 전체 |
| **검증 목적** | AZ 장애 내성  | 격리 원칙 검증 | Region Failover |

## 실제 장애 대응 사례

- 미국 중간 계층 서비스 중 하나가 심각한 성능 저하를 겪었고, 클러스터 대부분이 응답 불능 상태가 되었다.
- Active-Active 덕분에 사용자 요청을 정상 Region으로 라우팅하여 **짧은 시간 내에 모든 사용자의 서비스 품질이 복구**되었다.
- 이후 팀은 서비스를 중단 없이 원인을 분석하고 수정한 뒤, 트래픽을 복구된 Region으로 다시 되돌렸다.
