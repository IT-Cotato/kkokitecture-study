# 디스코드가 엘릭서를 5,000,000명의 동시 사용자로 확장한 방법

처음부터 디스코드는 엘릭서의 초기 사용자였다.

> [!note]- 엘릭서(Elixir)란?
> Erlang VM 위에서 돌아가는 현대적인 프로그래밍 언어

> [!note]- Erlang VM이란?
> 전화 교환기처럼 **절대 꺼지면 안되는 시스템**을 만들기 위해 개발된 언어
> **동시성에 특화**: 수백만 개의 경량 프로세스를 동시에 돌릴 수 있다.
> **장애 격리**: 프로세스 하나가 죽어도 나머지는 멀쩡하다.
> **핫 스왑**: 서버를 끄지 않고 코드 교체가 가능하다.
> 그러나 Erlang은 문법이 너무 낡아서 엘릭서가 나오게 되었다.

그래서 Erlang VM은 discord가 구축하고자 했던 고동시 실시간 시스템의 완벽한 후보가 되었고, Elixir에서 Discord의 원래 프로토타입을 개발하였다.

이 블로그를 쓸 당시 Discord는 거의 **500만 명의 동시 사용자**와 **초당 수백만 건의 이벤트**가 시스템을 통해 흐르고 있다. 하지만 Elixir를 사용할 당시, Erlang 생태계는 production에 사용된 자료가 부족했고, Discord가 경험한 교훈과 라이브러리들을 정리했다.

---

## Message Fanout

### 동작 원리

Discord는 기능이 풍부하지만, 대부분은 게시/구독에 집중되어 있다.

- 사용자는 WebSocket에 접속해 세션 프로세스를 가동하고, 이 세션은 길드(내부 Discord 서버) 프로세스를 포함하는 원격 Erlang 노드와 통신한다.
- 길드에서 무언가가 게시되면, 그 글은 그와 연결된 모든 세션에 분산된다.

> [!note]- 추가 개념
> 세션 노드: 유저들의 접속을 관리하는 서버
> 길드 노드: 채널/메시지 로직을 처리하는 서버
> 세션 프로세스: 나와 Discord 사이의 전용 통로

사용자가 온라인에 접속하면 길드에 연결되고, 길드는 다른 모든 연결된 세션에 presence(온라인)을 게시한다.

```elixir
def handle_call({:publish, message}, _from, %{sessions: sessions}=state) do
Enum.each(sessions, &send(&1.pid, message))
{:reply, :ok, state}
end
```

이런 길드의 로직을 통해 publish 요청이 들어오면 이 함수를 실행한다.

- message: 보낼 메시지
- state 안에서 sessions(이 길드에 접속 중인 세션 프로세스들의 목록) 목록을 꺼낸다.
- 각 sessions를 하나씩 순회하면서 각 세션 프로세스(pid)한테 message를 전송한다.

### 문제점

이 방법은 순차적으로 메시지를 전송하므로, 25명 미만의 그룹으로 길드를 생성했을 때는 괜찮았다.

- 대규모 그룹을 위해 Discord를 사용하기 시작하면서 최대 3만 명의 동시 사용자가 있었다.
- 피크 시간대에는 이러한 프로세스들이 메시지 큐를 따라가지 못하는 현상이 나타나기 시작했다.
  - 길드에 새로운 메시지가 들어오면 이를 길드에 연결된 모든 세션 프로세스들에게 순차적으로 전달하므로 오랜 시간이 걸린다.
  - 피크 시간대에는 많은 메시지가 들어오면서 각 메시지를 처리하는 시간보다 메시지가 쌓이는 속도가 빨랐다.

### 원인 파악

길드 프로세스 내 핫 패스(가장 자주 실행되는 코드 경로)가 얼마나 걸리는지 측정해서 원인을 발견하였다.

- 프로세스 간 메시지 전송이 생각보다 비쌌다.
  - `send/2`: Erlang에서 프로세스한테 메시지를 보내는 함수
  - `reduction cost`: Erlang이 프로세스 스케쥴링할 때 쓰는 작업 단위
  - 프로세스가 `send/2`를 호출해서 메시지를 보내려고 했는데, reduction을 너무 많이 사용해서 잠시 기다리고 나중에 다시 보내는 de-scheduling이 일어났다.
  - 이 시간이 30μs에서 70μs까지 걸렸다.
- Erlang 프로세스는 사실상 단일 스레드이며, 작업을 병렬화하는 유일한 방법은 샤드(shard)이다.
  - 이건 코드를 많이 고쳐야해서 작업이 너무 커졌다.

메시지 전송 작업을 분산해야 했다.

### 첫 번째 아이디어

Erlang에서 프로세스를 만드는 비용이 저렴하기 때문에, 메시지가 올 때마다 새 프로세스를 만들어서 전송을 맡기는 전략을 떠올렸다.

```txt
메시지 도착
    ↓
프로세스1 생성 → 1만 명한테 전송
프로세스2 생성 → 1만 명한테 전송
프로세스3 생성 → 1만 명한테 전송
```

하지만 선형성 때문에 불가능했다.

- 선형성: 메시지가 **보낸 순서대로** 도착해야 한다는 보장
- 프로세스를 막 생성하면 스케줄링 순서가 제각각이다.

```txt
메시지A 전송용 프로세스 생성
메시지B 전송용 프로세스 생성
    ↓
스케줄러가 B를 먼저 실행할 수도 있음
    ↓
유저 화면에 B가 A보다 먼저 도착!
```

또한 길드가 할 일이 점점 늘어났다.

```txt
Guild 프로세스가 하는 일들:
- 메시지 fan-out
- 유저 권한 관리
- 음성채널 상태 관리
- 온라인 상태 추적
- ...계속 늘어나는 중
```

게시마다 프로세스를 만들어도 Guild 자체가 바빠지는 건 해결되지 않았다.

### 두 번째 아이디어: Manifold

Manifold는 PID(프로세스 식별자)의 원격 노드에 메시지를 보내는 작업을 분배하며, 송신 프로세스가 최대 `send/2`를 호출하는 것은 관련 원격 노드 수와 같다.

- Manifold는 먼저 PID를 원격 노드별로 그룹화한 뒤, 각 노드에서 `Manifold.Partitioner`로 전송함으로써 이를 수행한다.
- Partitioner는 `:erlang.phash2/2`를 사용하여 PID를 안정 해싱하고, 코어 수별로 그룹화하여 자식 worker에게 보낸다.
- 마지막으로, 그 worker들은 실제 프로세스에 메시지를 전달한다.

이렇게 하면 파티셔너가 과부하되지 않고 send/2가 보장하는 선형 조정 가능성을 유지할 수 있었다.

- 안정 해시를 사용하기 때문에 **같은 PID는 항상 같은 worker가 담당**한다.

또 다른 좋은 효과는 메시지 전송에 드는 CPU 비용을 분산시킬 뿐만 아니라, 노드 간 네트워크 트래픽도 줄일 수 있다.

## Fast Access Shared Data

### 동작 원리

Discord는 안정 해시로 구현된 분산 시스템이다.

- 특정 엔티티(Guild 등)가 어느 노드에 있는지 찾기 위해 **해시 링 자료구조**를 사용한다.
- 유저가 접속하면 "내가 속한 Guild는 어느 노드에 있지?"를 해시 링에서 조회하고, 해당 노드에 연결한다.

### 문제점

유저가 한꺼번에 재접속하는 상황이 오면, 링을 관리하는 Erlang 프로세스 하나가 너무 바빠져서 시스템 전체가 과부하됐다.

원인을 분석해보니:

- 평균 유저는 5개의 Guild에 속해있고, 세션 서버 하나에 최대 50만 개의 세션이 있다.
- 유저가 접속할 때마다 자기가 속한 Guild마다 노드 조회를 해야 한다.
- 프로세스 간 요청/응답 비용이 약 12μs인데, 세션 서버가 재시작되면 링 조회만 하는 데 약 30초가 걸렸다.

> [!note]- 왜 30초나 걸렸을까?
> 유저 한 명이 Guild 5개에 속해있고, 세션이 50만 개라면 조회 횟수 = 5 × 500,000 = 250만 번 12μs × 250만 = 약 30초

### 해결 과정

**1단계: 링 프로세스를 여러 개로 복제**

링 데이터를 가진 프로세스를 여러 개 띄워서 요청을 분산하려 했다. 하지만 이게 핫 패스였기 때문에 더 좋은 방법을 고민했다.

**2단계: ETS 도입**

> [!note]- ETS란?
> C로 구현된 빠른 인메모리 딕셔너리. 여러 프로세스가 동시에 읽을 수 있다. 단, 데이터를 읽고 쓸 때 복사가 발생한다.

링 데이터를 ETS에 올려서 여러 프로세스가 직접 읽게 했더니 7μs로 줄었다.

- 하지만 링 자료구조 자체가 커서 ETS에서 복사하는 비용이 대부분을 차지했다.
- 여전히 조회 시간이 17.5초나 걸렸다.

**3단계: FastGlobal (최종 해결)**

`mochiglobal`이라는 기법을 발견했다.

- Erlang VM의 특성을 이용: 항상 같은 상수 데이터를 반환하는 함수는 **읽기 전용 공유 힙**에 데이터를 저장한다.
- 이 영역에 있는 데이터는 복사 없이 읽을 수 있다.

> [!note]- 왜 복사가 없으면 빨라지냐?
> ETS는 읽을 때마다 데이터를 해당 프로세스 메모리에 복사해야 한다. 공유 힙은 모든 프로세스가 같은 메모리를 그냥 참조한다. 복사 비용이 없으니 훨씬 빠른 것이다.

결과: 조회 비용이 **0.3μs**로 줄어들면서 전체 조회 시간이 **750ms**까지 떨어졌다.

단점: 링이 변경될 때 모듈을 런타임에 새로 컴파일해야 해서 최대 1초가 걸린다.

- 하지만 링은 자주 변경되지 않아서 감수할 수 있는 비용이었다.

Discord는 이를 Elixir로 포팅해서 **FastGlobal** 라이브러리로 공개했다.

## Limited Concurrency

### 문제점

Fast Access 문제를 해결하고 나니 새로운 문제가 생겼다.

- 이전엔 링 조회가 느려서 자연스럽게 요청 속도가 제한됐는데, 빨라지고 나니 500만 개의 세션이 길드 레지스트리(10개 프로세스)에 한꺼번에 몰렸다.

> [!note]- 길드 레지스트리란?
> 각 길드 프로세스의 PID를 관리하는 프로세스
> "길드 A는 어느 노드의 어느 프로세스에 있다"를 알고 있다.

연쇄 장애가 이렇게 발생했다:

```txt
세션들이 길드 레지스트리에 요청
    ↓
요청이 타임아웃됨 (처리 못 함)
    ↓
타임아웃된 요청이 큐에 그대로 남아있음
    ↓
세션들이 백오프 후 재시도 → 요청이 더 쌓임
    ↓
세션들이 다른 서비스 메시지도 못 받고 메시지 큐가 터짐
    ↓
Erlang VM 전체 OOM(메모리 부족)
    ↓
연쇄 서비스 장애
```

> [!note]- 백오프(backoff)란?
> 요청이 실패했을 때 바로 재시도하지 않고 잠깐 기다렸다가 다시 시도하는 전략.
> 기다리는 시간을 점점 늘려가는 방식이 일반적이다.

### 해결 방법: Semaphore

핵심 아이디어: **애초에 요청이 넘치면 일찍 거절하자.**

> [!note]- 세마포어(Semaphore)란?
> 동시에 처리할 수 있는 요청 수를 제한하는 기법.
> "지금 10개까지만 처리할 수 있어, 11번째부터는 거절할게"

서킷 브레이커는 사용하지 않았다.

> [!note]- 서킷 브레이커(Circuit Breaker)란?
> 타임아웃이 일정 수준 이상 발생하면 일정 시간 동안 모든 요청을 차단하는 패턴.
> Discord는 이 방식을 쓰면 "일시적으로 아무 시도도 안 하는 상태"가 생겨서 원하지 않았다.

Erlang에서 세마포어를 어떻게 구현하냐면:

- ETS의 `update_counter/4` 함수가 원자적 조건부 증가를 지원한다.
- 현재 동시 요청 수를 ETS에 저장해두고, 요청이 올 때마다 카운터를 증가시킨다.
- 한도를 초과하면 바로 거절한다.

```txt
요청 도착
    ↓
현재 동시 요청 수 확인 (ETS에서 원자적으로)
    ↓
한도 미만이면 → 처리
한도 초과면  → 즉시 거절 (큐에 쌓이지 않음)
```

결과: 이후 비슷한 상황이 발생했을 때 세션 서비스는 전혀 영향을 받지 않았고, 장애가 난 서비스만 재시작 후 수분 내에 복구됐다.

Discord는 이를 **Semaphore** 라이브러리로 공개했다.

## 마무리

| 문제                                                | 해결                                                          |
| --------------------------------------------------- | ------------------------------------------------------------- |
| Message Fanout: 메시지 3만 번 순차 전송이 너무 느림 | Manifold: 노드별로 묶어서 한 번만 전송, 안정 해시로 워커 분배 |
| Fast Access: 해시 링 조회가 병목                    | FastGlobal: 복사 없는 공유 힙으로 0.3μs 달성                  |
| Limited Concurrency: 요청 폭주로 연쇄 장애          | Semaphore: 동시 요청 수 제한으로 입장 제한                    |

Elixir/Erlang을 선택한 것은 Discord의 요구사항(수백만 동시접속, 실시간, 무중단)과 딱 맞았다.
