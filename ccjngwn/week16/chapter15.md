# 15장 구글 드라이브 설계

구글 드라이브는 클라우드 파일 저장소이면서, 여러 단말 사이의 파일을 동기화해 주는 시스템이다.

사용자는 파일을 업로드하고, 다운로드하고, 공유하고, 이전 버전으로 되돌릴 수 있어야 한다.

또 한 단말에서 파일을 수정하면 다른 단말에서도 빠르게 같은 상태를 볼 수 있어야 한다.

---

# 1단계 문제 이해 및 설계 범위 확정

## 기능 요구사항

- 파일 추가
    - 드래그 앤 드롭으로 파일을 업로드할 수 있어야 한다.
- 파일 다운로드
- 여러 단말 사이의 파일 동기화
    - 한 단말에서 파일을 추가하거나 수정하면 다른 단말에도 자동으로 반영되어야 한다.
- 파일 갱신 이력 조회
    - 이전 버전의 파일을 조회하거나 복원할 수 있어야 한다.
- 파일 공유
    - 가족, 친구, 동료와 파일을 공유할 수 있어야 한다.
- 파일 변경 알림
    - 파일이 추가, 수정, 삭제, 공유되면 관련 사용자에게 알려야 한다.
- 모바일 앱과 웹 앱을 지원해야 한다.
- 모든 파일 형식을 지원해야 한다.
- 저장소에 보관되는 파일은 암호화해야 한다.
- 파일 크기는 최대 10GB까지 지원한다.

구글 문서처럼 여러 사용자가 같은 문서를 동시에 편집하는 기능은 이번 설계 범위에서 제외한다.

---

## 비기능 요구사항

### 안정성

저장소 시스템에서 가장 중요한 요구사항이다.

사용자의 파일이 손실되면 안 된다.

### 빠른 동기화

파일 동기화가 너무 오래 걸리면 사용자는 서비스를 불편하게 느낀다.

특히 여러 단말을 동시에 사용하는 경우, 한쪽에서 수정한 파일이 다른 단말에 빨리 반영되어야 한다.

### 네트워크 대역폭 효율

파일을 수정할 때마다 전체 파일을 다시 업로드하면 네트워크를 너무 많이 사용한다.

모바일 데이터 환경에서는 더 큰 문제가 될 수 있다.

### 규모 확장성

사용자와 저장 데이터가 계속 늘어나도 시스템을 쉽게 확장할 수 있어야 한다.

### 높은 가용성

일부 서버가 장애를 일으키거나 네트워크 일부가 끊겨도 서비스는 계속 사용할 수 있어야 한다.

---

## 개략적 규모 추정

- 가입 사용자 수: 5천만 명
- 일간 능동 사용자 수: 1천만 명
- 사용자당 무료 저장 공간: 10GB
- 사용자당 하루 평균 업로드 파일 수: 2개
- 파일 평균 크기: 500KB
- 읽기와 쓰기 비율: 1:1

전체 저장 공간은 다음과 같다.

```
5천만 명 x 10GB = 500PB
```

따라서 전체 저장 공간은 약 500PB가 필요하다.

업로드 API의 평균 QPS는 다음과 같다.

```
1천만 명 x 2회 / 24시간 / 3600초 = 약 240 QPS
```

최대 QPS를 평균의 2배로 가정하면 다음과 같다.

```
최대 QPS = 480 QPS
```

실제 서비스에서는 시간대별 트래픽이 다르겠지만, 개략적 추정 단계에서는 피크 트래픽을 평균의 2배 정도로 잡아 안전 마진을 둔다.

# 2단계 개략적 설계안 제시 및 동의 구하기

처음부터 복잡한 분산 시스템을 그리기보다는, 서버 한 대로 시작한 다음 점진적으로 확장하는 방식으로 접근한다.

---

## 초기 설계

초기에는 서버 한 대에 다음 기능을 모두 넣을 수 있다.

- 파일 업로드와 다운로드를 처리하는 웹 서버
- 사용자 정보, 로그인 정보, 파일 정보를 저장하는 데이터베이스
- 실제 파일을 보관하는 파일 저장소

파일 저장소의 전체 용량은 1TB라고 가정한다.

서버에는 `drive/`라는 루트 디렉터리를 만들고, 그 아래에 사용자별 네임스페이스를 둔다.

```
drive/
├── user1/
│   ├── recipes/
│   └── chicken_soup.txt
├── user2/
│   ├── football.mov
│   └── sports.txt
└── user3/
    └── best_pic_ever.png
```

각 사용자는 자기만의 네임스페이스를 가진다.

파일은 네임스페이스와 상대 경로를 합쳐 유일하게 식별할 수 있다.

---

## API 설계

기본적으로 세 가지 API가 필요하다.

- 파일 업로드 API
- 파일 다운로드 API
- 파일 갱신 이력 조회 API

모든 API는 사용자 인증을 요구해야 한다.

또 클라이언트와 서버 사이의 데이터 전송은 HTTPS로 보호해야 한다.

---

### 파일 업로드 API

파일 업로드 방식은 두 가지로 나눌 수 있다.

- 단순 업로드
    - 파일 크기가 작고 한 번의 요청으로 업로드할 수 있을 때 사용한다.
- 이어 올리기 업로드
    - 파일 크기가 크거나 네트워크 연결이 불안정할 때 사용한다.
    - 업로드가 중간에 실패해도 처음부터 다시 올리지 않고 중단된 지점부터 재개할 수 있다.

이어 올리기 업로드 API 예시는 다음과 같다.

```
https://api.example.com/files/upload?uploadType=resumable
```

이어 올리기는 다음 순서로 진행된다.

1. 이어 올리기 URL을 받기 위한 최초 요청을 보낸다.
2. 파일 데이터를 업로드하고 업로드 상태를 확인한다.
3. 장애가 발생하면 중단된 위치부터 다시 업로드한다.

---

### 파일 다운로드 API

다운로드할 파일 경로를 전달한다.

```
https://api.example.com/files/download
```

```json
{
  "path": "/recipes/soup/best_soup.txt"
}
```

---

### 파일 갱신 이력 조회 API

파일의 이전 버전 목록을 조회한다.

```
https://api.example.com/files/list_revisions
```

```json
{
  "path": "/recipes/soup/best_soup.txt",
  "limit": 20
}
```

- `path`: 갱신 이력을 조회할 파일 경로
- `limit`: 반환할 갱신 이력의 최대 개수

---

## 단일 서버의 한계

파일이 계속 업로드되면 단일 서버의 저장 공간은 금방 부족해진다.

가장 먼저 생각할 수 있는 방법은 사용자 ID를 기준으로 파일을 여러 서버에 나누어 저장하는 것이다.

```
server = user_id % 서버 개수
```

하지만 이 방식은 저장 공간 문제만 어느 정도 해결할 뿐이다.

특정 저장 서버에 장애가 발생하면 해당 서버에 저장된 파일을 잃을 수 있다.

따라서 실제 파일 저장에는 Amazon S3 같은 객체 저장소를 사용하는 것이 좋다.

S3는 높은 규모 확장성, 높은 가용성, 데이터 다중화, 여러 리전 복제를 제공한다.

여러 리전에 파일을 복제해 두면 한 리전에 장애가 발생해도 다른 리전의 복제본으로 파일을 제공할 수 있다.

---

## 개선된 개략적 설계

단일 서버 구조에서 다음 컴포넌트를 분리한다.

- 로드밸런서
- API 서버
- 메타데이터 데이터베이스
- 메타데이터 캐시
- 블록 저장소 서버
- 클라우드 저장소
- 아카이빙 저장소
- 알림 서비스
- 오프라인 사용자 백업 큐

개략적 흐름은 다음과 같다.

```
사용자 단말
    |
로드밸런서
    |
API 서버
    |
    |-- 메타데이터 데이터베이스
    |-- 메타데이터 캐시
    |-- 알림 서비스
    |-- 오프라인 사용자 백업 큐

블록 저장소 서버
    |
클라우드 저장소
    |
아카이빙 저장소
```

---

## 주요 컴포넌트

### 사용자 단말

웹 브라우저나 모바일 앱처럼 사용자가 파일을 사용하는 클라이언트다.

### 로드밸런서

사용자 요청을 여러 API 서버에 고르게 분산한다.

특정 API 서버에 장애가 발생하면 해당 서버로 요청을 보내지 않고 정상 서버로 우회한다.

### API 서버

파일 업로드 흐름을 제외한 대부분의 요청을 처리한다.

- 사용자 인증
- 사용자 프로필 관리
- 파일 메타데이터 갱신
- 파일 공유
- 파일 버전 조회

API 서버는 무상태 서버로 설계한다.

그래야 서버를 쉽게 추가하거나 제거할 수 있고, 장애가 발생해도 다른 서버가 요청을 이어받을 수 있다.

### 블록 저장소 서버

파일을 작은 블록으로 나누고, 각 블록을 클라우드 저장소에 업로드한다.

블록 저장소 서버는 다음 작업을 담당한다.

- 파일 분할
- 블록 압축
- 블록 암호화
- 변경된 블록만 업로드

파일을 다시 구성할 때는 블록을 기존 순서대로 조합한다.

블록 크기는 Dropbox 사례를 참고해 최대 4MB로 잡는다.

### 클라우드 저장소

파일 블록이 실제로 저장되는 공간이다.

Amazon S3 같은 객체 저장소를 사용할 수 있다.

### 아카이빙 저장소

오랫동안 사용되지 않는 비활성 데이터를 보관하는 저비용 저장소다.

Amazon S3 Glacier 같은 저장소를 사용할 수 있다.

### 메타데이터 데이터베이스

사용자, 단말, 파일, 디렉터리, 파일 버전, 블록 정보 같은 메타데이터를 저장한다.

실제 파일 데이터는 저장하지 않는다.

### 메타데이터 캐시

자주 조회되는 파일 메타데이터와 사용자 정보를 캐싱한다.

캐시를 사용하면 API 응답 속도를 높일 수 있다.

### 알림 서비스

파일이 추가, 수정, 삭제, 공유되었을 때 관련 클라이언트에 변경 사실을 알려준다.

클라이언트는 알림을 받은 뒤 API 서버에 최신 메타데이터를 요청하고 필요한 블록을 내려받는다.

### 오프라인 사용자 백업 큐

사용자가 오프라인 상태라 알림을 받을 수 없을 때 변경 정보를 임시로 저장한다.

사용자가 다시 접속하면 큐에 저장된 정보를 이용해 동기화를 진행한다.

---

## 동기화 충돌

두 사용자나 두 단말이 같은 파일을 동시에 수정하면 충돌이 발생할 수 있다.

처리 전략은 먼저 서버에 도착한 변경을 정상 반영하고, 나중에 도착한 변경은 충돌로 판단하는 것이다.

충돌이 발생하면 시스템은 두 버전을 모두 유지한다.

- 서버에 저장된 최신 버전
- 사용자가 수정한 로컬 버전

예를 들어 다음과 같이 충돌 사본을 만들 수 있다.

```
SystemDesignInterview
SystemDesignInterview_user2_conflicted_copy
```

사용자는 두 파일을 직접 병합하거나, 한 버전으로 다른 버전을 덮어쓸 수 있다.

실시간 공동 편집 문제는 차등 동기화 같은 별도 기술이 필요하지만, 이번 설계 범위에서는 제외한다.

- 알림 서비스
- 저장 공간 절약

## 블록 저장소 서버

큰 파일을 수정할 때마다 전체 파일을 다시 업로드하면 네트워크 대역폭 낭비가 크다.

이를 줄이기 위해 두 가지 최적화를 사용한다.

### 델타 동기화

전체 파일이 아니라 변경된 블록만 전송한다.

예를 들어 파일이 10개 블록으로 나뉘어 있고, 그중 2번과 5번 블록만 바뀌었다고 하자.

그러면 전체 파일이 아니라 2번 블록과 5번 블록만 업로드하면 된다.

```
기존 파일: block 1 ~ block 10
수정된 블록: block 2, block 5
업로드 대상: block 2, block 5
```

델타 동기화를 사용하면 업로드 시간과 네트워크 사용량을 줄일 수 있다.

### 압축

각 블록은 전송 전에 압축한다.

압축 알고리즘은 파일 형식에 따라 다르게 선택할 수 있다.

- 텍스트 파일: gzip, bzip2
- 이미지, 비디오: 해당 형식에 적합한 압축 방식

### 암호화

저장소에 보관되는 파일은 암호화해야 한다.

따라서 블록 저장소 서버는 블록을 클라우드 저장소에 올리기 전에 암호화한다.

### 블록 업로드 흐름

1. 파일을 작은 블록으로 분할한다.
2. 각 블록을 압축한다.
3. 각 블록을 암호화한다.
4. 암호화된 블록을 클라우드 저장소에 업로드한다.

---

## 높은 일관성 요구사항

구글 드라이브 같은 시스템에서는 같은 파일이 클라이언트마다 다르게 보이면 안 된다.

따라서 메타데이터 계층은 강한 일관성을 제공해야 한다.

메타데이터 캐시와 데이터베이스에도 같은 원칙을 적용한다.

- 캐시의 데이터와 데이터베이스의 원본 데이터가 일치해야 한다.
- 데이터베이스에 쓰기가 발생하면 관련 캐시를 무효화해야 한다.

관계형 데이터베이스는 ACID를 기본적으로 지원하므로 강한 일관성을 구현하기 쉽다.

반면 NoSQL 데이터베이스는 보통 최종 일관성을 기반으로 하므로, 강한 일관성을 만들려면 추가 동기화 로직이 필요하다.

이번 설계에서는 메타데이터 저장소로 관계형 데이터베이스를 사용한다.

---

## 메타데이터 데이터베이스

메타데이터 데이터베이스는 실제 파일 내용이 아니라 파일을 설명하는 정보를 저장한다.

주요 테이블은 다음과 같다.

| 테이블 | 역할 |
| --- | --- |
| `user` | 사용자 이름, 이메일, 프로필 등 사용자 정보 저장 |
| `device` | 사용자의 단말 정보와 푸시 알림 ID 저장 |
| `namespace` | 사용자의 루트 디렉터리 정보 저장 |
| `file` | 파일 이름, 상대 경로, 최신 버전, 체크섬 저장 |
| `file_version` | 파일의 갱신 이력과 버전 정보 저장 |
| `block` | 특정 파일 버전을 구성하는 블록과 순서 저장 |

### user

사용자의 기본 정보를 저장한다.

```
user_id
user_name
email
profile_photo
created_at
```

### device

사용자의 단말 정보를 저장한다.

한 사용자는 여러 단말을 가질 수 있다.

```
device_id
user_id
push_id
last_logged_in_at
```

### namespace

사용자의 루트 디렉터리 정보를 저장한다.

공유 폴더 여부도 이 계층에서 관리할 수 있다.

```
namespace_id
owner_id
is_shared
created_at
```

### file

파일의 최신 상태와 경로를 저장한다.

```
file_id
namespace_id
file_name
relative_path
is_directory
latest_version
checksum
created_at
last_modified
```

### file_version

파일의 버전 이력을 저장한다.

이 테이블의 기존 행은 읽기 전용으로 유지하여 갱신 이력의 무결성을 보장한다.

```
version_id
file_id
device_id
version_number
last_modified
```

### block

파일 버전을 구성하는 블록과 블록 순서를 저장한다.

특정 버전의 파일은 블록을 `block_order` 순서대로 이어 붙여 복원할 수 있다.

```
block_id
file_version_id
block_order
```

## 파일 업로드 절차

파일 업로드는 두 요청이 병렬로 처리되는 구조다.

- 파일 메타데이터 등록
- 실제 파일 데이터 업로드

---

### 파일 메타데이터 등록

1. 클라이언트가 새 파일의 메타데이터 등록 요청을 API 서버에 보낸다.
2. API 서버는 메타데이터를 데이터베이스에 저장한다.
3. 파일 상태를 `pending`으로 설정한다.
4. 알림 서비스에 새 파일이 추가되었다는 사실을 전달한다.
5. 알림 서비스는 관련 클라이언트에 파일 업로드가 진행 중임을 알린다.

---

### 실제 파일 업로드

1. 클라이언트가 파일 콘텐츠를 블록 저장소 서버로 업로드한다.
2. 블록 저장소 서버는 파일을 작은 블록으로 나눈다.
3. 각 블록을 압축하고 암호화한다.
4. 블록을 클라우드 저장소에 업로드한다.
5. 업로드가 끝나면 클라우드 저장소가 완료 콜백을 보낸다.
6. 완료 콜백은 API 서버로 전달된다.
7. API 서버는 파일 상태를 `uploaded`로 변경한다.
8. 알림 서비스에 파일 업로드가 완료되었다고 알린다.
9. 알림 서비스는 관련 클라이언트에 업로드 완료를 통지한다.

파일을 수정하는 경우에도 전체 흐름은 비슷하다.

---

## 파일 다운로드 절차

다운로드는 다른 단말에서 파일이 추가되거나 수정되었을 때 시작된다.

클라이언트가 변경을 알게 되는 경우는 두 가지다.

- 클라이언트가 온라인 상태인 경우
    - 알림 서비스가 변경 사실을 즉시 알려준다.
- 클라이언트가 오프라인 상태인 경우
    - 변경 정보는 오프라인 사용자 백업 큐에 저장된다.
    - 사용자가 다시 접속하면 최신 변경분을 받아간다.

다운로드 흐름은 다음과 같다.

1. 알림 서비스가 클라이언트에 파일 변경 사실을 전달한다.
2. 클라이언트가 API 서버에 변경 메타데이터를 요청한다.
3. API 서버가 메타데이터 데이터베이스에서 최신 정보를 조회한다.
4. API 서버가 최신 메타데이터를 클라이언트에 반환한다.
5. 클라이언트가 블록 저장소 서버에 필요한 블록을 요청한다.
6. 블록 저장소 서버가 클라우드 저장소에서 해당 블록을 내려받는다.
7. 블록 저장소 서버가 클라이언트에 블록을 전달한다.
8. 클라이언트가 전달받은 블록을 순서대로 조합해 파일을 복원한다.

---

## 알림 서비스

파일 일관성을 유지하려면 로컬에서 일어난 변경을 다른 클라이언트에 알려야 한다.

알림 서비스는 파일 추가, 수정, 삭제, 공유 같은 이벤트가 발생했을 때 관련 클라이언트에 변경 사실을 전달한다.

알림 서비스를 구현하는 방식은 크게 두 가지다.

- 롱 폴링
- 웹소켓

### 롱 폴링

클라이언트가 서버에 요청을 보내고, 새로운 이벤트가 생길 때까지 연결을 유지하는 방식이다.

이벤트가 발생하면 서버는 응답을 반환하고 연결을 닫는다.

클라이언트는 응답을 받거나 타임아웃이 발생하면 다시 새 요청을 보낸다.

### 웹소켓

클라이언트와 서버 사이에 지속적인 양방향 통신 채널을 만드는 방식이다.

채팅처럼 실시간 양방향 통신이 필요한 서비스에 잘 맞는다.

### 롱 폴링을 선택하는 이유

구글 드라이브의 변경 알림은 채팅처럼 양방향 통신이 필요한 기능이 아니다.

서버가 클라이언트에게 파일 변경 사실을 알려주는 단방향 통신에 가깝다.

또 파일 변경 이벤트는 채팅 메시지만큼 자주 발생하지 않고, 한 번에 대량의 데이터를 주고받을 필요도 없다.

따라서 이 설계에서는 롱 폴링을 사용한다.

---

## 저장 공간 절약

파일의 모든 버전을 계속 저장하면 저장 공간이 빠르게 부족해진다.

특히 파일은 여러 데이터센터에 복제되기 때문에 저장 비용이 더 커질 수 있다.

이를 줄이기 위해 다음 전략을 사용한다.

### 중복 블록 제거

같은 블록을 여러 번 저장하지 않도록 한다.

두 블록의 해시값이 같으면 같은 블록으로 판단할 수 있다.

중복 제거는 사용자 계정 단위로 적용할 수 있다.

### 버전 수 제한

보관할 파일 버전 수에 상한을 둔다.

상한을 초과하면 가장 오래된 버전부터 삭제한다.

### 중요한 버전 위주로 보관

자주 수정되는 파일은 짧은 시간 동안 수많은 버전이 생길 수 있다.

모든 버전을 저장하지 않고, 일정 간격의 버전이나 사용자가 지정한 중요 버전만 보관할 수 있다.

최근 버전에 더 큰 가중치를 두는 방식도 가능하다.

### 비활성 데이터 아카이빙

수개월 또는 수년간 접근되지 않은 데이터는 저렴한 아카이빙 저장소로 옮긴다.

Amazon S3 Glacier 같은 저장소는 접근 속도는 느리지만 저장 비용이 낮다.

---

## 장애 처리

대규모 시스템에서는 장애를 완전히 피할 수 없다.

따라서 각 컴포넌트가 실패했을 때 어떻게 복구할지 미리 설계해야 한다.

### 로드밸런서 장애

주 로드밸런서가 장애를 일으키면 보조 로드밸런서가 활성화되어 트래픽을 이어받는다.

로드밸런서들은 하트비트를 주고받으며 서로의 상태를 확인한다.

### 블록 저장소 서버 장애

다른 블록 저장소 서버가 미완료 작업이나 대기 중인 작업을 이어받는다.

### 클라우드 저장소 장애

파일을 여러 리전에 복제한다.

한 리전에서 파일을 가져올 수 없으면 다른 리전의 복제본을 사용한다.

### API 서버 장애

API 서버는 무상태로 설계한다.

장애가 발생하면 로드밸런서가 해당 서버를 제외하고 다른 정상 서버로 요청을 전달한다.

### 메타데이터 캐시 장애

캐시 서버를 여러 노드에 복제한다.

한 노드가 장애를 일으키면 다른 노드에서 데이터를 조회하고, 장애 노드는 새 서버로 교체한다.

### 메타데이터 데이터베이스 장애

주 데이터베이스에 장애가 발생하면 부 데이터베이스 중 하나를 새로운 주 데이터베이스로 승격한다.

부 데이터베이스에 장애가 발생하면 다른 부 데이터베이스가 읽기 요청을 처리하고, 장애 노드는 새 서버로 교체한다.

### 알림 서비스 장애

알림 서버는 많은 클라이언트와 롱 폴링 연결을 유지한다.

서버 한 대가 장애를 일으키면 해당 서버에 붙어 있던 클라이언트들이 동시에 재접속을 시도할 수 있다.

이 과정에서 복구가 느려질 수 있으므로 다음을 고려해야 한다.

- 알림 서버 다중화
- 재접속 요청 분산
- 재시도에 지연 시간 적용
- 서버별 연결 수 제한

### 오프라인 사용자 백업 큐 장애

백업 큐도 여러 서버에 복제해야 한다.

큐 하나에 장애가 발생하면 클라이언트가 다른 백업 큐를 다시 구독하도록 한다.

# 4단계 마무리

이번 장에서는 구글 드라이브 같은 클라우드 파일 저장 및 동기화 시스템을 설계했다.

핵심은 실제 파일과 메타데이터를 분리하는 것이다.

실제 파일은 블록으로 나누어 클라우드 저장소에 저장하고, 메타데이터 데이터베이스에는 파일 경로, 버전, 블록 순서 같은 정보만 저장한다.

파일을 블록 단위로 다루면 변경된 부분만 전송할 수 있어 네트워크 사용량을 줄일 수 있다.

또 압축과 암호화를 적용해 전송 효율과 보안을 함께 챙길 수 있다.

알림 서비스는 클라이언트가 최신 변경 사항을 알 수 있게 해 준다.

이 설계에서는 양방향 통신이 꼭 필요하지 않기 때문에 웹소켓 대신 롱 폴링을 사용했다.

마지막으로 중복 제거, 버전 제한, 아카이빙을 통해 저장 공간을 절약하고, 각 컴포넌트를 다중화하여 장애에 대비한다.

---

## 추가로 논의할 수 있는 것

### 클라이언트가 클라우드 저장소에 직접 업로드하는 방식

블록 저장소 서버를 거치지 않고 클라이언트가 클라우드 저장소에 직접 파일을 업로드할 수도 있다.

이 방식은 파일을 한 번만 전송하면 되므로 업로드가 더 빠를 수 있다.

하지만 파일 분할, 압축, 암호화 로직을 웹, iOS, Android 클라이언트에 각각 구현해야 한다.

클라이언트는 조작될 가능성이 있으므로 암호화 로직을 클라이언트 안에 두는 것도 부담이다.

따라서 이번 설계에서는 복잡한 처리를 블록 저장소 서버에 집중시킨다.

### 접속 상태 관리 서비스 분리

온라인/오프라인 상태 관리 로직을 알림 서비스에서 분리해 별도 서비스로 둘 수도 있다.

이렇게 하면 다른 서비스에서도 접속 상태 정보를 재사용할 수 있고, 알림 서비스의 책임도 단순해진다.

---

## 핵심 정리

- 실제 파일과 메타데이터는 서로 다른 저장소에 분리한다.
- 실제 파일은 작은 블록으로 나누어 클라우드 저장소에 저장한다.
- 변경된 블록만 전송하는 델타 동기화로 네트워크 사용량을 줄인다.
- 블록을 압축하고 암호화해 전송 효율과 보안을 개선한다.
- 메타데이터는 강한 일관성이 필요하므로 관계형 데이터베이스를 사용한다.
- 데이터베이스에 쓰기가 발생하면 관련 캐시를 무효화한다.
- 알림 서비스는 롱 폴링으로 파일 변경 사실을 클라이언트에 전달한다.
- 오프라인 사용자의 변경 정보는 백업 큐에 저장한다.
- 중복 제거, 버전 제한, 아카이빙으로 저장 공간을 절약한다.
- 각 컴포넌트는 다중화하여 단일 장애 지점을 줄인다.
