# 왜 이 주제를 골랐는가?

15장에서는 구글 드라이브 같은 파일 저장소를 설계하면서 동기화 충돌을 간단히 다룬다.

두 사용자가 같은 파일을 동시에 수정하면, 먼저 서버에 도착한 변경은 반영하고 나중에 도착한 변경은 충돌로 처리한다.

그리고 충돌이 난 로컬 버전은 별도 파일로 남겨 사용자가 직접 병합하게 한다.

이 방식은 파일 저장소에서는 꽤 현실적인 선택이다.

하지만 여기서 한 단계 더 들어가면 질문이 생긴다.

왜 시스템이 알아서 병합하지 않을까?

왜 어떤 서비스는 충돌 사본을 만들고, 어떤 서비스는 Google Docs나 Figma처럼 여러 사람이 동시에 편집해도 자연스럽게 합쳐질까?

이번 발표에서는 이 차이를 파일 동기화, 실시간 협업 편집, CRDT와 OT 관점에서 정리해본다.

---

# 동기화 충돌은 언제 생기는가?

동기화 충돌은 같은 데이터가 여러 장소에서 동시에 바뀔 때 발생한다.

대표적인 상황은 다음과 같다.

- 두 사용자가 같은 파일을 동시에 수정한다.
- 한 사용자가 오프라인 상태에서 파일을 수정하는 동안, 다른 사용자가 온라인에서 같은 파일을 수정한다.
- 어떤 사용자가 파일을 열어둔 상태에서 자동 저장이 발생하고, 다른 곳에서도 같은 파일이 수정된다.

Dropbox는 이런 경우 충돌 사본을 만든다.

예를 들어 원래 파일이 `report.docx`라면, 충돌한 버전은 다음과 같이 별도 파일로 저장될 수 있다.

```
report.docx
report (conflicted copy).docx
```

이 방식의 핵심은 시스템이 한쪽 변경을 조용히 버리지 않는다는 것이다.

자동 병합은 하지 못하더라도, 사용자의 작업물은 보존한다.

---

# 왜 그냥 마지막 저장이 이기게 하면 안 될까?

가장 단순한 전략은 Last Write Wins다.

가장 늦게 저장된 값을 최종 값으로 선택하는 방식이다.

예를 들어 두 클라이언트가 같은 파일 이름을 바꾸면, 서버에 더 늦게 도착한 변경을 최종 상태로 삼을 수 있다.

이 방식은 단순하고 빠르다.

하지만 문제는 사라진 변경을 사용자가 알아차리기 어렵다는 점이다.

```
사용자 A: 발표자료 초안 작성
사용자 B: 오프라인에서 예전 버전 수정
사용자 B의 변경이 나중에 업로드됨
결과: 사용자 A의 작업이 덮어써질 수 있음
```

파일 저장소에서 데이터 손실은 치명적이다.

따라서 단순한 Last Write Wins만으로는 부족한 경우가 많다.

충돌 사본은 투박하지만, 적어도 사용자의 변경을 버리지 않는다.

---

# 충돌 사본은 실패가 아니라 제품 선택이다

충돌 사본이 생기면 사용자는 불편하다.

두 파일을 열어 비교하고, 어떤 내용을 살릴지 직접 판단해야 한다.

하지만 파일 저장소 입장에서는 이게 더 안전한 선택일 수 있다.

파일은 내부 구조를 시스템이 이해하기 어렵다.

`txt` 파일이라면 줄 단위 병합을 시도할 수 있겠지만, `docx`, `pptx`, `psd`, `fig`, `zip` 같은 파일은 단순 텍스트가 아니다.

심지어 같은 확장자라도 애플리케이션마다 저장 구조가 다를 수 있다.

파일 저장소가 모든 파일 포맷의 의미를 이해하고 안전하게 병합하는 것은 현실적으로 어렵다.

그래서 일반적인 파일 동기화 시스템은 다음 원칙을 택한다.

```
자동으로 잘못 병합하느니,
두 버전을 모두 남기고 사용자에게 판단을 맡긴다.
```

이 관점에서 보면 충돌 사본은 단순한 기술 한계가 아니라 데이터 보존을 우선하는 제품 결정이다.

---

# 충돌을 탐지하려면 무엇이 필요할까?

충돌을 처리하려면 먼저 충돌을 탐지해야 한다.

단순히 파일 이름만 보면 부족하다.

보통은 파일의 버전 정보를 함께 본다.

예를 들어 클라이언트가 파일을 수정할 때 다음 정보를 서버에 보낸다고 하자.

```
file_id: 123
base_version: 7
new_content: ...
```

서버의 최신 버전이 아직 7이면, 이 변경은 정상적으로 반영할 수 있다.

하지만 서버의 최신 버전이 이미 8이면, 클라이언트는 오래된 버전을 기반으로 수정한 것이다.

이때 충돌이 발생했다고 판단할 수 있다.

```
클라이언트가 수정한 기준 버전: 7
서버의 현재 최신 버전: 8
결과: 충돌
```

이 방식은 Git에서 브랜치가 갈라지는 상황과 비슷하다.

서로 다른 변경이 같은 조상 버전에서 출발했는지 확인하는 것이다.

---

# 버전 벡터는 무엇을 해결하려고 하는가?

단일 서버가 모든 쓰기 순서를 결정한다면 버전 번호 하나로도 충분할 수 있다.

하지만 여러 복제본에서 동시에 쓰기를 허용하면 이야기가 복잡해진다.

예를 들어 데이터센터 A와 데이터센터 B가 있고, 둘 다 쓰기를 받을 수 있다고 하자.

두 데이터센터에서 동시에 같은 파일이 수정되면 단순한 숫자 버전만으로는 어느 변경이 먼저인지 판단하기 어렵다.

이때 사용할 수 있는 개념이 버전 벡터다.

버전 벡터는 각 복제본이 몇 번 변경되었는지 함께 기록한다.

```
A에서 한 번 수정: { A: 1, B: 0 }
B에서 한 번 수정: { A: 0, B: 1 }
```

두 벡터는 서로 포함 관계가 아니다.

즉 한쪽이 다른 쪽보다 명확히 최신이라고 말할 수 없다.

이 경우 시스템은 두 변경이 동시에 발생했다고 판단하고 충돌로 처리한다.

버전 벡터는 자동 병합 자체를 해결하는 기술은 아니다.

대신 어떤 변경이 다른 변경을 포함하는지, 아니면 서로 독립적으로 발생했는지를 판단하는 데 도움을 준다.

---

# 일반 파일 동기화와 실시간 협업 편집은 다르다

구글 드라이브의 일반 파일 동기화와 Google Docs, Figma 같은 실시간 협업 편집은 비슷해 보이지만 다른 문제다.

일반 파일 동기화는 파일 전체나 블록을 저장하고 동기화한다.

시스템은 파일의 내부 의미를 모르는 경우가 많다.

반면 실시간 협업 편집은 문서의 내부 구조를 애플리케이션이 이해한다.

텍스트 문서라면 문자의 삽입, 삭제, 이동을 operation으로 표현할 수 있다.

디자인 도구라면 특정 객체의 특정 속성을 바꾸는 operation으로 표현할 수 있다.

```
일반 파일 동기화:
파일 A가 바뀌었다

협업 편집:
객체 17의 x 좌표를 120으로 바꿨다
3번째 위치에 "hello"를 삽입했다
```

충돌을 자동으로 해결하려면 시스템이 변경의 의미를 알아야 한다.

그래서 실시간 협업 편집은 파일 저장소보다 더 좁은 도메인을 깊게 이해하는 방식으로 설계된다.

---

# Operational Transformation

Operational Transformation, 줄여서 OT는 실시간 공동 편집에서 오래 사용된 접근법이다.

핵심 아이디어는 동시 작업이 서로 다른 순서로 도착하더라도 같은 결과가 나오도록 operation을 변환하는 것이다.

예를 들어 문자열이 다음과 같다고 하자.

```
abcd
```

사용자 A는 맨 앞에 `x`를 삽입한다.

사용자 B는 1번 위치부터 두 글자를 삭제한다.

두 작업이 동시에 일어나면, 삭제 위치는 삽입 작업의 영향을 받는다.

따라서 서버나 클라이언트는 operation의 위치를 조정해야 한다.

```
Delete(at: 1, n: 2)
Insert(at: 0, text: "x")

Insert가 먼저 반영되면 삭제 위치는 1에서 2로 밀려야 한다.
```

OT는 이런 변환을 통해 모든 클라이언트가 같은 결과에 도달하도록 만든다.

Google Docs 같은 텍스트 기반 협업 편집 시스템에서 중요한 개념이다.

---

# OT의 어려움

OT는 강력하지만 구현이 어렵다.

operation 종류가 많아질수록 각 operation이 다른 operation과 만났을 때 어떻게 변환되어야 하는지 정의해야 한다.

삽입, 삭제만 있는 텍스트 편집기라면 그래도 해볼 만하다.

하지만 이동, 그룹화, 정렬, 스타일 변경, 객체 삭제, 부모 변경 같은 operation이 들어오면 경우의 수가 빠르게 늘어난다.

Figma는 ordered sequence 편집 글에서 OT를 검토했지만, 자신들의 문제에는 너무 복잡하다고 판단했다.

특히 Figma 같은 디자인 도구에서는 레이어 순서를 바꾸는 이동 작업이 흔하다.

이동을 삭제와 삽입으로 표현하면 구현은 가능하지만, 실제 의도와 다르게 복잡해질 수 있다.

결국 OT는 좋은 기술이지만 모든 협업 편집 문제에 가장 단순한 답은 아니다.

---

# CRDT

CRDT는 Conflict-free Replicated Data Type의 약자다.

여러 복제본이 독립적으로 업데이트되더라도 나중에 자동으로 병합되어 같은 상태에 도달하도록 설계된 자료구조다.

CRDT의 핵심은 다음과 같다.

- 각 복제본은 다른 복제본과 즉시 조율하지 않고도 변경을 받을 수 있다.
- 서로 다른 복제본에서 동시에 변경이 일어나도 병합 규칙이 정해져 있다.
- 모든 변경이 전파되고 나면 결국 같은 상태로 수렴한다.

예를 들어 grow-only set은 가장 단순한 CRDT 중 하나다.

원소를 추가하는 작업만 허용한다면, 여러 복제본에서 어떤 순서로 추가가 일어나도 최종 집합은 같다.

```
Replica A: {apple}
Replica B: {banana}

merge 결과: {apple, banana}
```

중요한 점은 CRDT가 모든 문제를 공짜로 해결해주는 마법이 아니라는 것이다.

자료구조가 수학적으로 잘 설계되어 있어야 하고, 삭제나 순서 변경 같은 작업은 훨씬 까다롭다.

---

# Figma는 진짜 CRDT를 그대로 쓰지는 않았다

Figma의 multiplayer 시스템은 CRDT에서 영감을 받았지만, 완전한 탈중앙 CRDT 시스템은 아니다.

Figma에는 서버라는 중앙 권위가 있다.

클라이언트는 변경을 서버로 보내고, 서버는 변경을 검증하고 순서를 정한 뒤 다른 클라이언트에 전파한다.

이 구조에서는 모든 복제본이 완전히 독립적으로 합의할 필요가 없다.

서버가 최종 순서를 정할 수 있기 때문이다.

Figma는 이 점을 활용해 순수 CRDT보다 더 단순하고 빠른 구조를 선택했다.

문서 구조도 파일 전체가 아니라 객체와 속성 단위로 생각한다.

```
Map<ObjectID, Map<Property, Value>>
```

즉 같은 객체의 서로 다른 속성을 바꾸는 작업은 충돌하지 않는다.

충돌은 같은 객체의 같은 속성을 동시에 바꿀 때 주로 발생한다.

이 경우에는 마지막으로 서버에 도착한 값을 선택할 수 있다.

---

# 중앙 서버가 있으면 왜 쉬워질까?

완전한 P2P 협업 시스템에서는 모든 클라이언트가 서로 다른 순서로 변경을 받을 수 있다.

따라서 어떤 순서로 병합해도 같은 결과가 나와야 한다.

이 조건은 강력하지만 구현 비용이 크다.

반면 중앙 서버가 있으면 서버가 변경의 최종 순서를 정할 수 있다.

클라이언트는 낙관적으로 로컬 변경을 먼저 적용하더라도, 결국 서버가 정한 순서에 맞춰 상태를 보정하면 된다.

```
클라이언트 A -> 서버: 변경 1
클라이언트 B -> 서버: 변경 2

서버가 순서 결정:
1. 변경 1
2. 변경 2
```

중앙 서버 방식은 오프라인 완전 지원이나 탈중앙성은 약해질 수 있다.

하지만 구현 난이도, 성능, 디버깅 가능성 면에서는 장점이 있다.

실제 제품에서는 이 트레이드오프가 중요하다.

---

# 그래도 서버만 믿으면 안 된다

서버가 순서를 정한다고 해서 모든 문제가 끝나는 것은 아니다.

Figma는 multiplayer 서버가 파일 상태를 메모리에 들고 빠르게 동기화한다.

하지만 메모리는 휘발성이다.

서버가 죽으면 아직 영속 저장소에 기록되지 않은 변경이 사라질 수 있다.

처음에는 주기적으로 checkpoint를 만들어 S3에 저장하는 방식이 있었다.

하지만 checkpoint 간격이 길면 서버 장애 시 최근 변경이 유실될 수 있다.

그래서 Figma는 write-ahead log와 비슷한 journal을 추가했다.

변경이 들어올 때마다 순번을 붙이고 journal에 기록해두면, 서버가 죽었다가 다시 올라와도 마지막 checkpoint 이후의 변경을 재생해서 최신 상태에 가까이 복구할 수 있다.

협업 편집에서 충돌 해결만큼 중요한 것은 변경을 잃지 않는 것이다.

# 자동 병합은 사용자 의도를 모른다

자동 병합 알고리즘은 데이터 구조의 일관성을 맞출 수 있다.

하지만 사용자의 의도를 항상 이해하지는 못한다.

예를 들어 두 사람이 같은 디자인 화면을 수정한다고 하자.

한 사람은 버튼 위치를 바꾸고, 다른 사람은 같은 버튼이 들어 있는 프레임 크기를 바꿨다.

데이터 구조상으로는 둘 다 병합할 수 있을지 모른다.

하지만 결과 화면이 사용자가 의도한 디자인인지까지는 별개의 문제다.

Figma의 autosave 글에서도 긴 시간 오프라인으로 작업한 큰 diff를 나중에 병합하는 것은 작은 실시간 충돌보다 훨씬 어렵다고 설명한다.

실시간 협업에서는 충돌이 작게 자주 발생하고, 사용자가 화면에서 즉시 이상함을 알아차릴 수 있다.

반면 오프라인에서 몇 시간 작업한 변경은 하나의 큰 브랜치처럼 쌓인다.

이걸 자동 병합하면 기술적으로는 수렴해도, 제품적으로는 이상한 결과가 나올 수 있다.

# 충돌 해결 전략 비교

| 전략 | 장점 | 단점 | 어울리는 상황 |
| --- | --- | --- | --- |
| Last Write Wins | 단순하고 빠르다 | 이전 변경이 조용히 사라질 수 있다 | 값 하나를 저장하는 설정, 중요도가 낮은 상태 |
| 충돌 사본 생성 | 사용자 변경을 보존한다 | 사용자가 직접 병합해야 한다 | 일반 파일 저장소 |
| 버전 벡터 | 동시 변경 여부를 판단하기 좋다 | 병합 자체를 해결하지는 않는다 | 다중 복제본, 오프라인 동기화 |
| OT | 텍스트 공동 편집에 강하다 | operation 조합이 많아지면 복잡하다 | 문서 편집기, 긴 ordered sequence |
| CRDT | 자동 병합과 eventual consistency를 제공한다 | 메타데이터, 삭제, 순서 처리 비용이 있다 | 오프라인 우선 앱, 협업 도구, 분산 복제 |
| 중앙 서버 기반 병합 | 구현과 운영이 비교적 단순하다 | 서버 의존성이 커진다 | Figma 같은 클라우드 협업 제품 |

# 15장 설계와 연결해서 보기

15장의 구글 드라이브 설계는 일반 파일 동기화 시스템이다.

따라서 충돌 해결 전략으로 충돌 사본을 만드는 방식이 자연스럽다.

파일 저장소는 모든 파일 포맷의 의미를 이해할 수 없다.

그래서 자동 병합보다 데이터 보존을 우선한다.

하지만 만약 설계 범위가 Google Docs 같은 문서 편집기로 바뀐다면 이야기가 달라진다.

그때는 파일을 단순한 byte 덩어리로 보면 안 된다.

문자 삽입, 삭제, 스타일 변경 같은 operation 단위로 모델링해야 한다.

Figma 같은 도구라면 객체, 속성, 레이어 순서, 그룹 관계 같은 도메인 모델을 기준으로 충돌을 다뤄야 한다.

즉 충돌 해결 전략은 저장 시스템만의 문제가 아니라 제품 도메인 모델의 문제다.

# 설계 면접에서 말할 수 있는 포인트

구글 드라이브 설계에서 충돌 처리를 질문받으면 다음처럼 답할 수 있다.

먼저 파일마다 버전을 관리한다.

클라이언트는 자신이 수정한 기준 버전을 함께 보낸다.

서버의 최신 버전과 기준 버전이 같으면 정상 반영한다.

다르면 동시 수정이 있었던 것으로 보고 충돌을 만든다.

일반 파일은 시스템이 의미 있게 병합하기 어렵기 때문에 두 버전을 모두 보존한다.

텍스트 파일처럼 병합 가능한 일부 포맷에 대해서는 자동 병합을 선택적으로 제공할 수 있지만, 기본 정책은 데이터 손실 방지다.

실시간 협업 편집까지 요구사항에 포함된다면 별도 설계가 필요하다.

이때는 OT, CRDT, 중앙 서버 기반 ordering 같은 접근법을 비교하고, 편집 대상의 데이터 모델에 맞는 방식을 선택해야 한다.

# 결론

파일 동기화 충돌은 단순히 “누가 마지막에 저장했는가”의 문제가 아니다.

핵심은 사용자의 변경을 잃지 않으면서, 가능한 경우에는 자연스럽게 병합하는 것이다.

일반 파일 저장소에서는 파일 내부 의미를 알기 어렵기 때문에 충돌 사본을 만드는 방식이 안전하다.

반면 실시간 협업 도구는 문서 내부 구조를 operation 단위로 이해하기 때문에 OT나 CRDT 계열의 알고리즘을 활용할 수 있다.

Figma 사례에서 볼 수 있듯이 실제 제품은 순수 이론을 그대로 적용하기보다, 중앙 서버, 도메인 모델, 성능 요구사항, 장애 복구 전략을 함께 고려해 절충한다.

결국 좋은 충돌 해결 설계는 알고리즘 선택만으로 끝나지 않는다.

어떤 변경을 자동으로 합칠 수 있고, 어떤 변경은 사용자에게 보여줘야 하는지 결정하는 제품 설계까지 포함한다.
