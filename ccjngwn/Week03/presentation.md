# 처리율 제한 장치를 활용한 API 확장

> 원문: [Scaling your API with rate limiters - Stripe Engineering Blog](https://stripe.com/blog/rate-limiters)
> 작성자: Paul Tarjan | 2017년 3월 30일

---

## Rate limiting이 필요한 이유

API를 운영하다 보면 다음과 같은 상황에 직면할 수 있다.

- 한 사용자의 트래픽 급증으로 다른 사용자에게 영향을 줌
- 결함 있는 스크립트가 대량의 요청을 쏟아냄
- 의도적인 서버 공격(DoS)
- 낮은 우선순위 요청이 중요 트래픽에 미치는 영향
- 시스템 장애 시 우선순위 기반 트래픽 제어 필요

Rate limiting은 **API의 안정성과 신뢰성을 유지**하기 위한 가장 강력한 방법 중 하나다.

---

## 언제 써야 하고, 언제 쓰면 안 될까?

Rate limiting의 핵심 전제는 **"사용자가 요청 속도를 조절해도 결과에 영향이 없어야 한다"** 는 것이다.

### 써도 되는 경우

요청을 늦추거나 나눠서 보내도 최종 결과가 똑같이 유효한 상황이다.

- 블로그 포스팅 업로드
- 프로필 수정
- 파일 다운로드
- 배치 데이터 처리

→ 지금 당장 처리되지 않아도 나중에 처리되면 되니까, 속도 제한이 합리적이다.

### 쓰면 안 되는 경우

요청을 늦추는 게 아예 선택지가 아닌 상황이다. 타이밍 자체가 서비스의 핵심인 경우다.

- 실시간 주식 거래 (1초 늦으면 손해)
- 수강 신청 / 티켓 예매 (선착순이라 지연 = 실패)
- 실시간 멀티플레이어 게임 (지연 = 끊김)

→ 이런 경우엔 rate limiting 대신 인프라 확장이나 대기열(queue) 설계가 더 적합하다.

## Rate limiter vs Load shedder

- **Rate limiter**: 사용자가 요청을 **너무 빠르게** 보내지 못하도록 속도를 제한한다. 사용자 입장에서 "좀 천천히 보내세요"에 해당한다.
- **Load shedder**: 서버가 **이미 한계에 달했을 때** 덜 중요한 요청을 통째로 잘라낸다. 서버 입장에서 "지금은 중요한 것만 처리할게요"에 해당한다.

| 구분      | Rate limiter                              | Load shedder                                  |
| --------- | ----------------------------------------- | --------------------------------------------- |
| 판단 기준 | 사용자의 요청 속도                        | 서버의 현재 부하 상태                         |
| 핵심 질문 | "이 사용자가 너무 많이 보내고 있나?"      | "지금 서버가 버틸 수 있나?"                   |
| 적용 시점 | 사용자가 요청을 나눠서 보낼 수 있을 때    | 장애 직전 또는 장애 상황에서                  |
| 예시      | 1초에 100개씩 보내는 사용자를 10개로 제한 | 서버 사용률 90% 초과 시 비중요 요청 전부 거부 |

## Stripe가 운영하는 4가지 Rate limiter

### 1. 요청 Rate limiter (Request Rate Limiter)

가장 기본적이고 중요한 리미터.

- **동작**: 사용자당 초당 최대 N개 요청 제한
- **버스트 허용**: 급격한 트래픽 스파이크에 대비해 일시적인 버스트 허용
- **효과**: 이 리미터만으로도 수백만 개의 악성/실수 요청 거부 (특히 테스트 모드에서)

> "이 달에만 수백만 개의 요청을 거부했으며, 특히 테스트 모드에서 효과적이었다."

### 2. 동시 요청 리미터 (Concurrent Requests Limiter)

초당 요청 수가 아닌, **동시에 처리 중인 요청 수**를 제한한다.

- **동작**: 동시에 처리할 수 있는 최대 요청 수 제한 (예: 20개)
- **적합한 상황**: CPU 집약적인 엔드포인트에서 리소스 경합 방지
- **효과**: 월 약 12,000개 요청 거부

#### 왜 CPU 집약적인 작업에 특히 유리할까?

이미지 변환, 암호화, 대용량 데이터 집계처럼 **요청 하나를 처리하는 데 CPU를 많이, 오래 쓰는 API**가 있다. 일반적인 API는 DB 조회 후 바로 반환하기 때문에 대부분의 시간을 I/O 대기에 쓰고 CPU는 잠깐만 쓰인다. 반면 이런 API는 처리가 끝날 때까지 CPU를 계속 붙잡는다.

이 상태에서 요청이 동시에 몰리면:

```
요청 쌓임 → CPU 100% → 모든 요청 느려짐 → 사용자 재시도 → 부하 가중 → 서버 다운
```

초당 요청 수만 제한해서는 이 상황을 막을 수 없다. 요청이 천천히 들어와도 각각 10초씩 걸리면 동시에 수백 개가 쌓일 수 있기 때문이다.

동시 요청을 제한하면 이 악순환을 끊을 수 있다. 처리 중인 요청들이 CPU를 충분히 확보한 채 빠르게 완료되고, 자리가 비면 다음 요청을 받는다. 한정된 자원을 너무 많은 요청이 나눠 가지려다 모두가 느려지는 **자원 경쟁(Resource Contention)** 자체를 막는 것이다.

결국 동시성 제한 장치는 **"딱 처리할 수 있는 만큼만 들여보내기"** 로 서버가 집중할 수 있는 환경을 만들어, 전체 처리량을 오히려 높인다.

### 3. Fleet Usage Load Shedder

> **Fleet이란?** 서비스를 구성하는 서버 인스턴스 전체 집합을 말한다. "우리 fleet이 80% 찼다"는 건 전체 서버들의 평균 사용률이 80%라는 뜻이다.

인프라 수준에서 **중요 요청을 위한 여유 용량을 확보**한다.

- **동작**: 전체 fleet의 일정 비율을 중요 요청 전용으로 예약
- **예시**: 20%를 예약하면, 비중요 요청은 서버 사용률이 80%를 초과할 때 HTTP 503으로 거부
- **효과**: 월 소수의 요청만 거부 (평상시에는 거의 작동하지 않음)

### 4. Worker Utilization Load Shedder

**최후의 방어선**. 시스템이 극한 상황일 때 작동한다.

- **동작**: 트래픽을 우선순위별로 4단계로 분류하여 순서대로 제거
  1. 중요 메서드 (Critical methods)
  2. POST 요청
  3. GET 요청
  4. 테스트 모드 요청
- **점진적 복구**: 빠르게 제거하고 느리게 복구하여 플래핑(flapping) 방지
- **효과**: 평상시 월 100개 거부 / 장애 시 핵심 서비스 보호에 매우 효과적

#### 플래핑(Flapping)이란?

부하가 임계값 근처에서 왔다 갔다 할 때, 시스템이 허용 ↔ 거부를 빠르게 반복하며 불안정해지는 현상이다.

예를 들어 서버 사용률이 90%일 때 요청을 거부하기 시작했다고 하자. 요청이 거부되면 부하가 줄어 89%가 된다. 그러면 다시 허용한다. 요청이 들어와 90%가 된다. 다시 거부한다. 이게 반복된다.

```
부하 90% → 거부 → 부하 89% → 허용 → 부하 90% → 거부 → ...
```

사용자 입장에선 요청이 됐다 안 됐다를 반복하고, 서버 입장에선 on/off 전환이 계속 일어나 오히려 오버헤드가 생긴다.

이를 막으려면 **빠르게 제거하고 느리게 복구**해야 한다. 부하가 줄었다고 바로 허용을 재개하지 않고, 충분히 안정된 상태가 지속되는 걸 확인한 뒤에 천천히 트래픽을 다시 받는다.

## 구현 방식

### 알고리즘: 토큰 버킷 (Token Bucket)

Stripe는 **토큰 버킷 알고리즘**을 사용한다.

```
1. 중앙 버킷에 토큰이 일정 속도로 채워진다.
2. 요청이 들어오면 버킷에서 토큰 1개를 꺼낸다.
3. 토큰이 없으면 요청을 거부한다.
4. 버킷은 최대 용량을 초과해 채워지지 않는다.
```

이 방식은 **평균 속도를 제어**하면서도 **일시적인 버스트를 허용**할 수 있다.

### 기술 스택: Redis

**Redis**를 통해 분산 환경에서 중앙집중식으로 카운터를 관리한다.

- 자체 운영 Redis
- 또는 AWS ElastiCache 같은 관리형 서비스 사용 가능

## 구현 시 반드시 고려해야 할 사항

### 1. 안전한 미들웨어 통합

Rate limiting 코드에 버그가 생기거나 Redis가 다운되더라도 **요청 처리는 계속되어야 한다**. 리미터는 보조 수단이지, 시스템의 단일 장애점이 되어서는 안 된다.

### 2. 명확한 에러 메시지

- Rate limiter → **HTTP 429** (Too Many Requests)
- Load shedder → **HTTP 503** (Service Unavailable)
- 사용자가 조치할 수 있는 안내 메시지 포함

### 3. 비활성화 기능 (Kill Switch)

기능 플래그(feature flag)를 통해 리미터를 즉시 해제할 수 있도록 설계해야 한다. 잘못된 임계값 설정으로 정상 트래픽을 막았을 때 빠르게 롤백할 수 있어야 한다.

### 4. Dark launch

Rate limiter를 처음 도입할 때 임계값을 잘못 설정하면 정상 트래픽까지 막아버리는 사고가 날 수 있다. Dark launch는 이를 방지하기 위한 단계적 도입 방식이다.

리미터 로직은 실제로 동작하지만, **차단은 하지 않고 로그만 남긴다.** 사용자는 아무것도 느끼지 못하는 채로, 개발자는 실제 트래픽 패턴을 관찰할 수 있다.

```
[Dark launch 단계]
요청 들어옴 → 리미터 판단 → "차단했을 것" 로그만 기록 → 요청은 그대로 통과

[활성화 단계]
요청 들어옴 → 리미터 판단 → 실제 차단 (HTTP 429 / 503 반환)
```

로그를 보면서 "이 임계값이면 정상 사용자가 얼마나 막히는지"를 미리 확인하고, 수치를 조정한 뒤에 실제 차단을 켠다. 프로덕션 트래픽을 실험 대상으로 쓰되, 사용자에게는 영향을 주지 않는 방식이다.

## 도입 순서

Rate limiter를 처음 도입할 때 권장하는 순서:

1. **요청 Rate limiter**부터 시작 (가장 효과적, 가장 우선)
2. **동시 요청 리미터** 추가
3. **Fleet Usage Load Shedder** 추가
4. **Worker Utilization Load Shedder** 추가
5. 각 단계에서 dark launch → 모니터링 → 활성화 순으로 진행
